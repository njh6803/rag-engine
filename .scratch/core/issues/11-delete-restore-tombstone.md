# 11: 삭제, 되살림, 묘비

**What to build:** 문서 담당자가 키로 문서를 지우면 그 커밋으로 검색에서 빠지고, 보관 기간 안에 같은 키로 다시 넣으면 문서 UUID를 그대로 두고 되살아난다. 내용이 같으면 보관해 둔 조각을 되돌려 다시 임베딩하지 않는다. 물리 삭제된 문서의 묘비 행에 같은 키가 오면 그 행을 다시 써 UUID를 잇는다.

**Blocked by:** 10 (수집의 갱신 갈래)

**Status:** ready-for-agent

- [ ] `DELETE /api/v1/ingest/documents?key=<키>`(URL 인코딩한 쿼리 매개변수): 204, 이미 지운 문서도 204, 없는 키는 404 `document_not_found`. `admin` 토큰이 필요하다.
- [ ] 삭제의 작업 단위(명세 "삭제, 되살림, 묘비" 절): 문서 행과 그 그룹이 든 지식베이스 행(`FOR UPDATE`)을 잠그고 세대를 올리며 `deleted_at`을 쓰고, 모든 색인 판의 조각을 `archived_chunks`로 옮기고, 그 문서의 색인 상태 행을 모두 지우고, 대기 작업을 지운다. `building` 판이 있을 때의 전환 검사는 부르는 자리를 두고 14가 채운다.
- [ ] 실행 중인 작업은 첫째 단계에서 지워진 문서를 보면 성공으로 끝나고, 그 뒤에 지워졌으면 셋째 단계의 세대 대조가 잡는다.
- [ ] 되살림: `deleted_at`은 있고 `purged_at`은 없는 문서에 같은 (원천, 키)가 오면 같은 작업 단위에서 `deleted_at`을 비우고 그룹을 요청의 것으로 쓴다. 내용 해시가 같으면 대상 판의 보관 조각 가운데 만든 내용 해시가 같은 것을 복사 칸을 지금 값으로 고쳐 되돌리고 색인 상태 `indexed`를 쓰며, 나머지 보관 조각은 지운다. 되돌릴 조각이 없는 대상 판이 있으면 작업을 넣고 그 판이 건설 중인 판이 아니면 `pending`을 쓴다. 내용 해시가 다르면 보관 조각을 지우고 갱신으로 간다. `action`은 `restored`이고 `job_id`는 작업이 없으면 null이다.
- [ ] 묘비 행(`purged_at`이 있는 문서)에 같은 (원천, 키)가 오면 그 행을 다시 써 UUID를 잇고 세대를 이어서 올리며 `action`은 `created`다. 정리 작업은 core에 없으므로 시험은 묘비 행을 데이터베이스에 직접 만든다. core는 설정 이름 `RAG_DELETED_RETENTION_DAYS`와 `purged_at`의 모양만 둔다.
- [ ] HTTP 시험: 스토리 5, 6, 삭제 뒤 검색에서 빠짐, 지운 문서의 `get_document`가 `document_not_found`이고 `list_knowledge_bases`의 `document_count`에서 빠짐(09가 지은 갈래), 되살림(다른 그룹으로 되살린 것, 갱신한 내용이 색인되기 전에 지웠다가 같은 내용으로 되살린 것. 옛 지식베이스의 검색에도 옛 글로도 나오지 않는다. 판 전환을 사이에 둔 되살림은 14), 내용 해시가 같은 되살림 뒤에 새 원본이 남지 않음, 묘비 행의 `created`.
- [ ] 어댑터 시험: 보관 표 이동(지운 문서의 조각이 검색 표에 없고 보관 표에 있다).
- [ ] 가짜 포트 시험: 삭제가 커밋된 뒤 셋째 단계에 든 작업이 조각을 쓰지 않는다, 지운 뒤 같은 내용으로 되살린 사이에 옛 작업이 영구 실패해도 되살린 조각과 색인 상태를 건드리지 않는다(재시도를 다 쓰는 갈래는 이 티켓 뒤에 도는 12가 맡는다).
- [ ] 검사 넷이 초록이다.
