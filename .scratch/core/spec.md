이 명세는 `GLOSSARY.md`의 말만 쓴다. 코드 식별자(`UnitOfWork`, `Embedder`, 설정 이름, 표와 칸 이름, JSON 칸 이름)는 영어 그대로다. 구현 파일의 경로는 적지 않고, 규칙 문서·ADR·테스트 선례의 경로만 적는다.

명세 안에서만 쓰는 말 넷. **세대**는 문서 행의 `generation`(데이터 모델 절)이고 문서에 관해 쓸 차례를 가리킨다. **올린 세대**는 작업의 한 시도가 첫째 단계에서 올린 그 값이고 작업 행에 적는다. **대상 판**은 문서의 그룹이 든 지식베이스들의 살아 있는 판(현재 판과 건설 중인 판)이고, 작업에서는 셋째 단계가 그때 읽은 것이다. **복사 칸**은 필터를 위해 문서에서 조각으로 복사한 그룹 참조, 갱신일, 시행일, 접근 그룹이다(조각을 만든 원본의 내용 해시는 복사 칸이 아니다). 판의 상태 말(현재 판, 건설 중인 판, 물러난 판, 살아 있는 판)은 `GLOSSARY.md`에 있다.

## Problem Statement

조직의 문서는 PDF, DOCX, HWPX 파일로 흩어져 있고, 조직의 에이전트(MCP 클라이언트)는 그 문서에서 질문에 맞는 대목을 찾아 근거와 함께 답하고 싶다. 그런데 문서를 밖으로 보낼 수 없는 조직(폐쇄망)에서 쓸 수 있는, 어떤 MCP 클라이언트에서나 붙는 검색 서버가 없다. 문서 담당자는 문서를 넣고 고치고 지우는 분명한 길을 원하고, 에이전트는 검색 결과마다 문서의 어디에서 온 글인지(근거 위치)와 언제 문서인지(갱신일)를 받아 답의 근거로 적고 싶다. 수집이 도는 동안에도 검색은 멈추지 않아야 하고, 문서 속 지시에 속은 에이전트가 문서를 지우는 일은 구조로 막혀야 한다.

## Solution

문서 담당자가 관리 API(수집 API)나 관리 명령으로 문서 파일을 밀어 넣으면, 서버는 원본을 저장하고 작업을 작업 대기열에 넣어 바로 응답한다. 작업자(별도 프로세스)가 작업을 꺼내 문서를 파싱하고, 지식베이스마다 조각으로 자르고, 임베딩 서버로 벡터를 만들고, 키워드 토큰을 뽑아 그 문서의 옛 조각과 한 번에 바꾼다. 그 사이 검색은 옛 조각을 그대로 본다.

MCP 클라이언트는 같은 서버의 `/mcp` 경로로 접속해 읽기 도구 셋(`search`, `get_document`, `list_knowledge_bases`)만 본다. `search`는 질의를 벡터 검색과 키워드 검색으로 함께 찾아 합치고 리랭커로 순서를 고친 뒤, 조각마다 근거 위치(쪽, 절, 블록 종류와 범위)와 갱신일, 점수를 붙여 돌려준다. 결과에는 `format_version`이 실려 클라이언트가 형식에 기댈 수 있다. 문서를 지우면 즉시 검색에서 빠지고 보관 기간 동안 되살릴 수 있다. 운영자는 관리 명령으로 서버와 작업자를 띄우고 데이터베이스를 마이그레이션하며 첫 토큰을 만들고, 관리 API로 토큰을 발급·회수하고 지식베이스의 상태와 재색인, 작업과 문서의 상태를 본다. 쓰기는 관리 API, 수집 API, 관리 명령으로만 열린다.

## User Stories

1. As a 문서 담당자, I want 문서 파일 하나를 수집 API에 밀어 넣고 바로 작업 ID를 받고 싶다, so that 긴 파싱을 기다리지 않고 다음 문서를 넣을 수 있다.
2. As a 문서 담당자, I want 같은 키로 파일을 다시 넣으면 옛 문서가 갱신되기를 바란다, so that 문서가 둘이 되지 않는다.
3. As a 문서 담당자, I want 내용이 같은 파일을 다시 넣었을 때 서버가 건너뛰기를 바란다, so that 재색인 비용이 들지 않는다.
4. As a 문서 담당자, I want 문서를 넣을 때 그룹과 메타데이터(제목, 시행일 같은 것)와 갱신일을 함께 줄 수 있기를 바란다, so that 검색 결과에 실리는 문서 정보가 정확하다.
5. As a 문서 담당자, I want 키로 문서를 지울 수 있기를 바란다, so that 폐기된 규정이 검색에 나오지 않는다.
6. As a 문서 담당자, I want 지운 문서를 보관 기간 안에 같은 키로 다시 넣으면 되살아나기를 바란다, so that 실수로 지운 문서를 되살릴 수 있다.
7. As a 문서 담당자, I want 작업 ID로 수집이 끝났는지, 실패했으면 왜 실패했는지 보고 싶다, so that 깨진 파일을 고쳐 다시 넣을 수 있다.
8. As a 문서 담당자, I want 문서 ID나 키로 문서의 상태(받음, 파싱됨, 실패, 삭제됨)와 지식베이스마다의 색인 상태를 보고 싶다, so that 어떤 문서가 검색되는지 안다.
9. As a 문서 담당자, I want 폴더 하나를 관리 명령 한 줄로 수집하고 끝날 때까지 기다릴 수 있기를 바란다, so that 표본 문서들을 서버 없이도 넣을 수 있다.
10. As a 문서 담당자, I want 암호가 걸렸거나 깨진 파일이 어떤 까닭으로 거부됐는지 코드로 알고 싶다, so that 같은 실패를 반복하지 않는다.
11. As a 문서 담당자, I want 너무 큰 파일이 업로드 단계에서 거부되기를 바란다, so that 서버가 멈추지 않는다.
12. As a MCP 클라이언트, I want 질의와 개수를 주고 조각 목록을 받고 싶다, so that 답을 만들 근거를 얻는다.
13. As a MCP 클라이언트, I want 조각마다 문서의 키, 제목, 쪽, 절, 블록 범위를 받고 싶다, so that 답에 근거 위치를 적을 수 있다.
14. As a MCP 클라이언트, I want 조각마다 문서의 갱신일을 받고 싶다, so that 답에 문서가 언제 것인지 적을 수 있다.
15. As a MCP 클라이언트, I want 결과에 형식의 판이 실리기를 바란다, so that 판이 오를 때 내 파서를 고칠 수 있다.
16. As a MCP 클라이언트, I want 지식베이스를 이름으로 고르고 안 고르면 기본 지식베이스가 쓰이기를 바란다, so that 설정 없이도 검색이 된다.
17. As a MCP 클라이언트, I want 그룹과 갱신일 기간으로 결과를 거를 수 있기를 바란다, so that 특정 부서나 최근 문서만 찾을 수 있다.
18. As a MCP 클라이언트, I want 질의가 벡터와 키워드 둘 다로 검색되기를 바란다, so that 고유 명사와 숫자(조항 번호, 모델 이름)도 놓치지 않는다.
19. As a MCP 클라이언트, I want 한국어 질의가 형태소 단위로 키워드 검색되기를 바란다, so that 조사와 어미가 달라도 같은 낱말을 찾는다.
20. As a MCP 클라이언트, I want 리랭커가 순서를 고친 결과를 받고 싶다, so that 상위 몇 개만 써도 답의 근거가 된다.
21. As a MCP 클라이언트, I want 문서 ID로 문서의 정보와 원하면 전문을 받고 싶다, so that 조각만으로 모자랄 때 문맥을 더 읽는다.
22. As a MCP 클라이언트, I want 지식베이스 목록과 문서 수를 받고 싶다, so that 어디에서 찾을지 고른다.
23. As a MCP 클라이언트, I want 도구 목록에 쓰기 도구가 없기를 바란다, so that 내가 문서 속 지시에 속아도 문서를 지울 수 없다.
24. As a MCP 클라이언트, I want 수집이 도는 동안에도 검색이 응답하기를 바란다, so that 업무 시간에 문서를 넣어도 된다.
25. As a MCP 클라이언트, I want 수집 중인 문서의 옛 조각과 새 조각이 섞여 나오지 않기를 바란다, so that 답이 한 판의 문서에서 나온다.
26. As a MCP 클라이언트, I want 오류가 났을 때 코드로 까닭(지식베이스 없음, 문서 없음, 잘못된 인자, 검색 불가)을 알고 싶다, so that 다시 시도할지 사용자에게 알릴지 정한다.
27. As a MCP 클라이언트, I want 내 토큰이 허용하는 지식베이스만 보이고 검색되기를 바란다, so that 다른 지식베이스의 존재를 모른다.
28. As a 운영자, I want 서버와 작업자를 관리 명령으로 따로 띄우고 싶다, so that 작업자 수를 서버와 따로 조절한다.
29. As a 운영자, I want 데이터베이스 스키마를 관리 명령으로 올리고 기본 그룹·지식베이스가 설정값으로 만들어지기를 바란다, so that 설치 뒤 바로 문서를 넣을 수 있다.
30. As a 운영자, I want 첫 관리 토큰을 서버 없이 명령으로 만들고 싶다, so that 닭과 달걀 문제 없이 시작한다.
31. As a 운영자, I want 관리 API로 토큰을 이름·역할·만료·지식베이스 범위와 함께 발급하고 목록을 보고 회수하고 싶다, so that 클라이언트마다 다른 토큰을 주고 유출되면 끊는다.
32. As a 운영자, I want 토큰 없는 요청과 틀린 토큰이 거부되고 허용 호스트 밖의 요청도 거부되기를 바란다, so that 내부망에서도 기본이 닫힌다.
33. As a 운영자, I want 지식베이스의 설정(임베딩 모델, 청킹)이 바뀌어 재색인이 필요해지면 관리 API가 그것을 보여 주고, 재색인을 시작하면 끝날 때까지 옛 색인으로 검색되기를 바란다, so that 모델을 바꿔도 검색이 멈추지 않는다.
34. As a 운영자, I want 작업자가 죽어도 그 작업이 다른 작업자에게 넘어가기를 바란다, so that 수집이 멈춰 있지 않는다.
35. As a 운영자, I want 일시 실패(임베딩 서버 다운)는 재시도되고 영구 실패(깨진 파일)는 바로 실패로 끝나기를 바란다, so that 대기열이 영구 실패로 막히지 않는다.
36. As a 운영자, I want 악의적이거나 비정상인 문서(압축 폭탄, 쪽이 수만 장인 PDF)가 작업자를 죽이지 않기를 바란다, so that 다른 문서의 수집이 계속된다.
37. As a 운영자, I want 로그에 질문 내용, 문서 내용, 토큰이 남지 않고 지연 시간과 요청 ID만 남기를 바란다, so that 로그를 외부 지원에 넘겨도 된다.
38. As a 운영자, I want 요청마다 요청 ID가 응답 헤더와 로그와 작업에 이어지기를 바란다, so that 느린 검색이나 실패한 수집을 추적한다.
39. As a 운영자, I want 서버의 생존 확인 경로가 인증 없이 응답하기를 바란다, so that 컨테이너 오케스트레이터가 상태를 본다.
40. As a 다른 시스템(수집 API 호출자), I want 문서를 HTTP 한 번으로 보내고 202를 받고 싶다, so that 내 쪽 스크립트가 단순하다.
41. As a 파서 플러그인 작성자, I want 파서 인터페이스가 판이 붙은 Protocol이고 entry point로 끼워지기를 바란다, so that 서버 코드를 고치지 않고 새 형식을 더한다.
42. As a 클라이언트 개발자, I want 검색 도구의 출력 스키마를 MCP 도구 목록에서 읽을 수 있기를 바란다, so that 형식을 문서 없이도 안다.
43. As a 리뷰어, I want 층의 경계가 import-linter로 판정되기를 바란다, so that 어댑터가 도메인으로 새는 것을 기계가 잡는다.

## Implementation Decisions

### 층, 패키지, 조립

- [넘겨받음] 층은 `rag_engine.main` > `rag_engine.server`·`rag_engine.worker` > `rag_engine.adapters` > `rag_engine.app` > `rag_engine.domain` 다섯이고 경계는 `pyproject.toml`의 import-linter layers 계약이 판정한다(ADR 0007). 계약을 다섯 층으로 고치고 `CLAUDE.md`의 레이어 절과 `.scratch/plan-head.md`의 목표 배치를 같이 고치는 일은 계약 티켓(Further Notes)이 패키지를 만들 때 한다. 포트는 `domain`의 `typing.Protocol`이고 `app`의 유스케이스는 포트만 부른다.
- [정함] 계약 티켓이 고치는 것. `pyproject.toml`의 layers 계약을 다섯 층으로 고치고(`rag_engine.server`와 `rag_engine.worker`는 한 층의 독립 형제라 서로 import하지 않는다) 다섯 패키지를 모두 만든다(없는 층은 계약이 판정하지 못한다). forbidden 계약 하나를 더해 `rag_engine.domain`과 `rag_engine.app`이 서드파티(sqlalchemy, psycopg, alembic, pgvector, fastapi, starlette, mcp, httpx, uvicorn, pydantic, pydantic_settings, kiwipiepy, pdfplumber, pdfminer, docx, hwpx)를 import하지 못하게 한다. 두 층이 쓰는 서드파티는 uuid6 하나다(데이터 모델 절). 같이 고치는 문서는 `CLAUDE.md`의 레이어 절, `.scratch/plan-head.md`의 목표 배치(고친 뒤 `tools/plan_table.py`), `README.md`의 트리, `server`가 패키지가 되면 `.claude/rules/server.md`의 `paths`다.
- [정함] `domain`에는 엔티티(원천, 그룹, 지식베이스, 색인 판, 문서, 파싱 결과와 블록, 조각, 색인 상태, 작업, 토큰)와 포트, 이 저장소의 예외 계층이 있다. 엔티티는 불변 데이터클래스이고 식별자는 표준 라이브러리 `uuid.UUID`다. `app`의 유스케이스는 문서 수집, 문서 삭제, 작업 처리(문서 색인), 검색, 문서 정보 조회, 지식베이스 목록·조회, 재색인 시작, 토큰 발급·목록·회수, 작업·문서 조회, 기본 레코드 보장(마이그레이션 뒤)이다. `adapters`에는 PostgreSQL(SQLAlchemy Core 표 정의, alembic 환경과 마이그레이션, 작업 단위와 다섯 포트(`Catalog`, `DocumentStore`, `VectorIndex`, `JobQueue`, `TokenStore`)의 어댑터), TEI(임베딩, 리랭커), 파서 셋과 파서 레지스트리와 자식 프로세스 실행기, 청킹 전략, Kiwi 키워드 토크나이저, 로컬 볼륨 파일 저장소, 설정(pydantic-settings), 로그 포매터가 있다. 설정과 로그 포매터는 바깥 환경을 읽고 쓰는 것이라 `adapters`에 두고 `app`과 `domain`은 그것을 import하지 않는다.
- [정함] 조립은 두 자리다. `server`의 `create_app`이 설정 객체를 받아 엔진, 작업 단위 공장, 어댑터, 유스케이스를 만들고 REST 경로와 MCP 도구를 붙인다. `worker`의 작업자 조립이 같은 설정으로 같은 어댑터를 만들고 작업 처리 루프를 돈다. 둘이 공유하는 조립 코드는 `adapters`에 둔다. 테스트는 설정 객체를 바꿔 넣어 같은 조립을 쓴다.
- [넘겨받음] MCP 하위 앱은 `MCPServer.streamable_http_app()`을 `"/"`에 마운트하고 REST 경로를 모두 더한 뒤 마지막에 붙이며, 최상위 lifespan이 `session_manager.run()`을 연다(ADR 0005, `.claude/rules/server.md`).
- [정함] MCP 전송 설정 둘의 조립 자리는 `create_app`이다. 설정 객체의 `RAG_MCP_STATELESS`(기본 true)와 `RAG_MCP_JSON_RESPONSE`(기본 false)를 `streamable_http_app(stateless_http=…, json_response=…)`의 인자로 그대로 넘기고, `RAG_ALLOWED_HOSTS`를 ADR 0014의 두 꼴로 펼쳐 전송 보안 설정의 허용 호스트로 넘긴다. 기본은 세션 없음 + SSE 응답이다(진행률 프로브 `mcp-sdk/probe_progress.py`, 일지 결정 요약 18).

### 포트 열셋과 그 값

- [이력] 포트는 열셋이다. ADR 0007의 열(Connector, Transform, Parser, Chunker, Embedder, Reranker, VectorIndex, JobQueue, DocumentStore, BlobStore)에 작업 단위 포트 `UnitOfWork`와 `Catalog`, `TokenStore`를 더했다. ADR 0007의 2026-11-10 이력 둘과 본문 포인터가 그 변경이다. 아래는 포트마다 무엇의 자리인지(교체 경계, 테스트 가짜 자리, 전략 자리)를 밝힌 것이고, PR #2 둘째 회차 claude-review의 Minor(Chunker·Embedder·Reranker는 구현이 하나뿐인데 포트인 까닭)에 답한다.
- [정함] `UnitOfWork`는 `begin()`이 비동기 컨텍스트 관리자를 내고, 그 안에서 얻는 작업 단위 객체가 `catalog`(Catalog), `documents`(DocumentStore), `index`(VectorIndex), `jobs`(JobQueue) 넷을 속성으로 낸다. 넷은 한 연결의 한 트랜잭션을 공유한다. 블록을 예외 없이 나가면 커밋, 예외로 나가면 롤백이다. 명시적 `commit()`은 두지 않는다(두 길이 있으면 한쪽을 잊는다). PostgreSQL 어댑터는 비동기 연결 하나와 트랜잭션을 열고 네 어댑터를 그 연결 위에 만든다. 작업 대기열의 `NOTIFY`는 PostgreSQL이 커밋 시점에 보내므로 작업 단위 안에서 그냥 부르면 된다. 산문에서는 "작업 단위"라 쓰고 대기열의 "작업"과 가른다(`GLOSSARY.md` 작업 항목).
- [정함] 작업 단위 안에서 얻는 포트는 `Catalog`, `DocumentStore`, `VectorIndex`, `JobQueue` 넷뿐이고 나머지 포트는 트랜잭션 밖에서 부른다. 원본은 작업 단위를 열기 전에 새 경로에 저장하고, 작업 단위가 롤백되면 그 요청이 새로 저장한 원본만 지운다(최선 노력. 옛 원본은 건드리지 않는다. 경로 규칙은 "수집 파이프라인과 작업" 절). 커밋 뒤에 지우는 원본(옛 원본, 문서 행이 가리키지 않는 새 원본)도 최선 노력이다. 지우지 못한 고아 원본은 두고, 정리는 source-sync의 정리 작업이 받는다.
- [정함] `Connector`와 `Transform`은 플러그인 자리(교체 경계, ADR 0012)다. core에는 구현이 없다. 수집 API와 `ingest` 명령은 커넥터가 아니라 밀어 넣는 원천 종류이고, 파이프라인의 변환 자리는 비워 둔다(변환 목록이 빈 채로 파싱으로 간다). Connector 1.0의 메서드(`list`, `fetch`, `check`)는 ADR 0012가 정했다. Transform의 메서드 모양은 ADR 0012가 명세에 맡겼고, core에 변환이 없으므로 처음 구현하는 source-sync의 명세가 정한다.
- [정함] `Parser`는 플러그인 자리(교체 경계)이고 테스트 가짜 자리이기도 하다. 내장 셋(PDF, DOCX, HWPX)도 entry point 그룹 `rag_engine.parsers`에 등록해 로드하는 길이 하나다(ADR 0012). 파이프라인 시험은 실제 파서와 작은 픽스처 문서로 하고, 실패 분류(시간 초과, 메모리 초과, 예외)의 시험만 테스트 쪽 가짜 파서를 레지스트리에 더해 한다.
- [정함] `Chunker`는 전략 자리다. 교체 경계도 테스트 가짜 자리도 아니다. 지식베이스 설정의 전략 이름으로 저장소 안의 구현을 고르고(ADR 0010), search-eval이 전략을 더할 때 `app`을 고치지 않게 하는 것이 포트의 값이다. 결정적이라 시험은 실제 전략으로 한다. 토큰 수를 세는 일은 `Embedder`의 토큰화 메서드에 맡기고, 시험에서는 글자 수로 세는 가짜 토큰 세기를 끼운다. 구현이 하나여도 포트로 부르는 까닭은 층이다. 구조 우선 전략은 문장 경계를 kiwipiepy로 얻어 `adapters`에 살고, `app`은 `adapters`를 import하지 못한다.
- [정함] `Embedder`와 `Reranker`는 외부 서비스의 경계(교체 경계)이자 테스트 가짜 자리다. 다른 임베딩 서버 어댑터의 자리이고(ADR 0010 Consequences), `app`의 동시성·실패 분류 시험에서 가짜가 들어간다. HTTP 표면 시험에서는 실제 TEI 어댑터가 TEI 스텁 서버(Testing Decisions)에 붙는다.
- [정함] `Catalog`, `VectorIndex`, `DocumentStore`, `JobQueue`는 PostgreSQL 어댑터 하나씩이고 작업 단위 안에서만 얻는다. 교체 조건은 ADR 0006 Consequences 첫 항목이다. 시험은 실제 테스트 PostgreSQL이고, 가짜(메모리 안)는 `app`의 동시성 교차 시험에서만 쓴다.
- [정함] `BlobStore`는 교체 경계다(S3 호환은 나중 어댑터, ADR 0013). core는 로컬 볼륨 어댑터 하나이고 시험은 임시 디렉터리로 한다.
- [사용자 선택] `Catalog`는 원천, 그룹, 지식베이스(지식베이스와 그룹의 다대다를 포함), 색인 판 레코드를 맡고 작업 단위 안에서 얻는다(지식베이스 행의 잠금과 판 전환이 문서 상태·색인 상태와 한 트랜잭션에 든다). `TokenStore`는 토큰을 맡고 작업 단위 밖에서 부른다. 기존 포트의 몫을 넓히는 안(이름이 맡는 일보다 좁게 읽힌다)과 `Catalog` 하나가 토큰까지 맡는 안(인증 표가 문서 설정과 섞인다)은 고르지 않았다. PR #3 봇 5회차의 claude-review Major(이 표들을 맡는 포트가 ADR 0007에도 명세에도 없다)에 답해 사용자가 2026-11-10에 골랐고, ADR 0007 이력 2026-11-10 "포트 열에 `Catalog`와 `TokenStore`를 더한다"가 그 변경이다.
- [정함] 지식베이스 행의 잠금(수집 파이프라인 절의 잠금 규칙), 재색인 시작의 판 레코드 생성, 판 전환(현재 판 참조와 판 상태), `migrate`의 기본 레코드 보장이 `Catalog`를 지나고, 판마다의 HNSW 부분 색인과 조각은 `VectorIndex`의 몫이다(재색인 시작은 `Catalog`로 판 레코드를, `VectorIndex`로 그 판의 색인을 만든다). `TokenStore`는 PostgreSQL 어댑터 하나다. 발급·목록·회수와 인증의 해시 조회는 다른 표와 한 트랜잭션에 들 일이 없어 작업 단위 밖이다. 시험은 실제 테스트 PostgreSQL이고 가짜는 두지 않는다.
- [정함] 표와 포트의 대응은 `Catalog`가 `sources`·`groups`·`knowledge_bases`·`knowledge_base_groups`·`index_versions`, `DocumentStore`가 `documents`·`document_contents`, `VectorIndex`가 `chunks`·`archived_chunks`·`document_index_states`, `JobQueue`가 `jobs`, `TokenStore`가 `tokens`다. 색인 상태는 (문서, 판)마다 조각과 함께 바뀌므로 `VectorIndex`에 둔다.

### 설정

- [넘겨받음] 설정은 pydantic-settings가 환경 변수 `RAG_*`, `.env`, 비밀 파일에서 읽는다(ADR 0015). 필수 셋은 `RAG_DATABASE_URL`(연결 문자열 하나, ADR 0002), `RAG_DATA_DIR`(원본 볼륨, ADR 0013), `RAG_ALLOWED_HOSTS`(ADR 0014. 비어 있으면 기동 거부)다. 로그는 `RAG_LOG_FORMAT`(`json` 기본, `text`)이다. 삭제 보관 기간은 `RAG_DELETED_RETENTION_DAYS`(30)다.
- [정함] 기본 지식베이스의 설정은 환경 변수로 받고 `migrate`가 데이터베이스 행으로 만든다. `RAG_DEFAULT_EMBEDDING_URL`(임베딩 TEI 끝점), `RAG_DEFAULT_EMBEDDING_MODEL`(기본 `BAAI/bge-m3`), `RAG_DEFAULT_EMBEDDING_DIMENSIONS`(1024), `RAG_DEFAULT_RERANKER_URL`(리랭커 TEI 끝점. 비우면 리랭커 없음), `RAG_DEFAULT_RERANKER_MODEL`(`BAAI/bge-reranker-v2-m3`), `RAG_DEFAULT_CHUNKING_STRATEGY`(`structure_first`), `RAG_DEFAULT_CHUNK_TOKENS`(512), `RAG_DEFAULT_CHUNK_OVERLAP_TOKENS`(64). 기본 그룹·지식베이스·원천의 이름은 모두 `default`다.
- [정함] 수집과 작업자의 설정. `RAG_MAX_UPLOAD_MB`(100), `RAG_WORKER_CONCURRENCY`(작업자 프로세스 하나가 동시에 처리하는 작업 수, 2), `RAG_WORKER_POLL_SECONDS`(5), `RAG_JOB_LEASE_SECONDS`(600), `RAG_JOB_MAX_ATTEMPTS`(6), `RAG_JOB_BACKOFF_BASE_SECONDS`(30. 실수를 받는다), `RAG_TEI_BATCH_SIZE`(TEI 호출 하나(임베딩, 토큰 세기, 리랭크)에 보내는 글의 수, 32. 끝점의 `/info`가 알리는 `max_client_batch_size`보다 크면 그 값으로 낮춘다), `RAG_TEI_TIMEOUT_SECONDS`(60).
- [정함] 파싱 한도의 설정. `RAG_PARSE_TIMEOUT_SECONDS`(300), `RAG_PARSE_MEMORY_MB`(2048), `RAG_PARSE_MAX_PAGES`(1000), `RAG_PARSE_MAX_UNZIPPED_MB`(512), `RAG_PARSE_MAX_COMPRESSION_RATIO`(100), `RAG_PARSE_MAX_TEXT_MB`(64). ZIP 항목 수 상한 4096은 상수다. 값의 근거는 "파싱의 격리와 자원 한도" 절이다.
- [정함] 검색의 설정. `RAG_SEARCH_CANDIDATES`(벡터와 키워드 각각의 후보 수, 50), `RAG_SEARCH_DEFAULT_TOP_K`(10), `RAG_SEARCH_MAX_TOP_K`(50), `RAG_SEARCH_TIMEOUT_SECONDS`(질의 임베딩부터 리랭크까지, 20).
- [정함] 기본값은 계약이 아니라 설정이다. 구현 티켓이 Docker에서 잰 값(수락 기준의 지연 측정)으로 기본값을 바꾸는 일은 ADR 없이 티켓이 한다. 이름을 바꾸거나 뜻을 바꾸는 일만 이 명세를 고친다.

### 데이터 모델과 스키마

- [넘겨받음] 모델은 두 층이다. 문서는 그룹 하나에 속하고, 지식베이스는 그룹 집합 위의 색인 하나이며 자기 임베딩 모델과 청킹 설정을 가진다. 같은 그룹이 지식베이스 둘에 들면 파싱은 한 번, 청킹과 임베딩은 지식베이스마다 한다. 문서는 (원천, 키)로 식별하고 내용 해시는 변경 감지에만 쓴다. 첫 판은 기본 그룹 하나와 기본 지식베이스 하나다(ADR 0008).
- [넘겨받음] 식별자는 UUIDv7이고 파이썬에서 만들며 열은 `uuid`다. 시각은 UTC `timestamptz`로 저장하고 ISO 8601 `Z`로 낸다(ADR 0015).
- [정함] UUIDv7 라이브러리는 uuid6 2025.0.1(MIT)이다. 프로브 `uuid/probe.py`(출력 `probe_out.txt`, pyright strict 0 오류 `pyright_out.json`)로 쟀다. uuid6의 값은 표준 라이브러리 `uuid.UUID`의 하위 타입이고(프로브가 MRO와 `str()`로 봤다), 그래서 `uuid.UUID`를 받는 SQLAlchemy `Uuid` 타입과 pydantic `UUID` 칸에도 변환 없이 들어간다. 그 두 자리는 티켓 세션이 프로브 `uuid/probe_sqlalchemy.py`(출력 `probe_sqlalchemy_out.txt`)로 쟀다. pydantic 2.14.3의 `uuid.UUID` 칸이 넣은 uuid6 객체를 그대로 들고(`is`) JSON으로 하이픈 문자열을 내고, SQLAlchemy 2.1.8 Core의 `sa.Uuid` 열에 psycopg 비동기로 넣고 읽은 값이 같으며 읽은 값은 표준 라이브러리 `uuid.UUID`다. 순수 파이썬 휠이라 폐쇄망 반입과 플랫폼이 자유롭다. uuid-utils 1.2.0은 10만 개 생성이 다섯 배 빠르지만(0.05s 대 0.23s) 값이 `uuid.UUID`의 하위 타입이 아니고(호환 모듈을 따로 써야 한다) 바이너리 휠이다. 식별자 생성 속도는 이 서버의 병목이 아니다. 둘 다 같은 밀리초 안에서 단조 증가했다.
- [정함] 표는 열둘이다. `sources`(원천. 이름 유일, 종류. 첫 판의 종류는 밀어 넣기 `push` 하나), `groups`(그룹. 이름 유일, 설명), `knowledge_bases`(지식베이스. 이름 유일, 설명, 임베딩 끝점·모델·차원, 리랭커 끝점·모델(없을 수 있음), 청킹 전략 이름·상한·겹침, 현재 색인 판 참조(없을 수 있음), 기본 지식베이스 표시(참인 행은 하나뿐, 부분 유일 색인)), `knowledge_base_groups`(지식베이스와 그룹의 다대다), `index_versions`(색인 판. 지식베이스 참조, 스키마 판, 임베딩 끝점·모델·차원, 청킹 설정(jsonb)과 그 해시, 토크나이저 판, 상태 `building`·`current`·`retired`, 만든 시각, 물러난 시각), `documents`(문서), `document_contents`(파싱 결과), `document_index_states`(색인 상태), `chunks`(조각), `archived_chunks`(보관 표), `jobs`(작업), `tokens`(인증 토큰). 여기에 alembic의 판 표가 더 있다.
- [정함] `documents`의 칸은 원천 참조, 키, 그룹 참조, 제목, MIME, 크기, 내용 해시(sha256), 원본 경로(파일 저장소의 키), 메타데이터(jsonb 객체), 갱신일 `updated_at`, 시행일 `effective_date`(비움), 접근 그룹 `access_groups`(빈 배열), 상태 `status`(`received`·`parsed`·`failed`), 오류 코드, 세대 `generation`(정수), `deleted_at`, `purged_at`, 만든 시각, 행을 마지막으로 고친 시각이다. 상태는 수집이 내용 해시를 새로 쓸 때(`created`, 내용이 바뀐 `updated`·`restored`) `received`가 되고, 색인 작업이 그 내용의 파싱을 마치면 `parsed`, 파싱이 영구 실패하면 `failed`가 된다(`received`나 `parsed`로 갈 때 오류 코드를 비운다. 수집 파이프라인 절). (원천 참조, 키)는 유일하다. 세대는 문서에 관해 쓸 차례를 가리킨다. 행을 처음 만들 때 1이고 줄지 않는다(묘비 행을 다시 쓰는 수집도 이어서 올린다). 응답이 `unchanged`가 아닌 수집, 삭제, 색인 작업의 첫째 단계가 같은 작업 단위에서 하나 올리고, 작업은 세대가 제가 올린 값 그대로일 때만 문서에 관해 쓴다(수집 파이프라인 절의 잠금 규칙). 갱신일은 문서의 갱신일(검색 결과에 싣는 값)이고 행을 고친 시각과 다르다. 호출자가 갱신일을 주면 그 값, 주지 않으면 내용이 바뀐 수집의 시각이다. 메타데이터만 바뀐 수집은 갱신일을 바꾸지 않는다. 시행일과 접근 그룹은 칸만 두고 채우지 않는다(doc-freshness, doc-permission).
- [정함] `document_contents`는 문서마다 한 행(최신 파싱 결과)이다. 파서 이름, 파서의 인터페이스 판과 라이브러리 판, 블록 목록(jsonb), 파싱한 원본의 내용 해시, 뽑은 글의 해시, 파싱 시각이 든다. 블록은 종류(`heading`·`paragraph`·`table`·`list_item`), 글, 제목 수준(제목만), 쪽 번호(1부터. 없을 수 있음), 순번(문서 안에서 0부터)이다. 표 블록의 글은 행마다 한 줄이고 칸은 ` | `로 잇는다.
- [정함] `document_index_states`는 (문서, 색인 판)마다 한 행이다. 상태 `pending`·`indexed`·`failed`, 조각 수, 만든 내용 해시(`indexed`일 때 그 조각을 만든 문서 내용 해시. `indexed`를 쓰는 쪽이 조각의 만든 내용 해시를 함께 적는다), 오류 코드, 고친 시각이 든다. 재색인의 진행(건설 중인 판에서 남은 문서 수)은 이 표로 센다. "재색인 필요"는 이 표가 아니라 아래 색인 판 요소의 비교로 판정한다.
- [정함] `chunks`의 칸은 문서 참조, 색인 판 참조, 순번, 글, 토큰 수, 근거 위치(jsonb: 쪽, 절 경로, 블록 종류, 블록 순번 범위), 임베딩 `embedding`(차원 없는 `vector`), 키워드 `keywords`(tsvector), 조각을 만든 원본의 내용 해시(되살림이 대 본다. 복사한 칸이 아니라 문서가 바뀌어도 고치지 않는다), 그리고 필터를 위해 문서에서 복사한 그룹 참조, 갱신일, 시행일, 접근 그룹이다. (색인 판, 문서, 순번)이 유일하다. 복사한 칸은 문서가 바뀌면 같은 트랜잭션에서 같이 고친다. `archived_chunks`는 같은 칸에 보관 시각을 더한 것이고 벡터·키워드 색인은 없다.
- [이력] 벡터 열은 차원을 적지 않은 `vector`이고 HNSW 색인은 색인 판마다 부분 표현식 색인 `CREATE INDEX … USING hnsw ((embedding::vector(D)) vector_cosine_ops) WHERE index_version_id = <판>`이다. 질의도 `embedding::vector(D) <=> :query`로 같은 캐스트를 쓴다. ADR 0006 이력 2026-11-10과 포인터가 이 변경이다. 근거는 프로브 `facts/pgvector_readme_facts.py`(README 842행의 예)다.
- [정함] 판의 HNSW 색인은 색인 판 행을 만드는 작업 단위(재색인 시작, `migrate`의 첫 판)가 조각 표에 쓸 것을 다 쓴 뒤 커밋 직전에 만든다. 그 판의 조각이 0개라 빠르지만, 커밋까지 조각 표의 INSERT를 막는다(SELECT는 막지 않는다). 판이 물러나면 그 색인은 트랜잭션 밖에서 `DROP INDEX CONCURRENTLY IF EXISTS`로 지운다. 일반 `DROP INDEX`는 커밋까지 조각 표의 SELECT를 막고, 열린 읽기 트랜잭션 뒤에 줄을 서면 그 뒤에 온 SELECT까지 막아 검색이 멈춘다. `CONCURRENTLY`는 줄을 서도 새 SELECT를 막지 않고 트랜잭션 안에서는 부를 수 없다(`ActiveSqlTransaction`, `25001`). 근거는 티켓 세션의 프로브 `pg-ddl/ddl_locks.py`(조각 20만 행에서 0행에 맞는 색인 만들기 0.16~0.19s. 출력 `ddl_locks_out.txt`)와 `pg-ddl/drop_concurrently.py`(출력 `drop_concurrently_out.txt`)다. 거리는 코사인이다. 키워드의 GIN 색인은 표 전체에 하나다(조건에 색인 판 참조가 함께 들어 GIN 뒤의 필터로 좁혀진다).
- [정함] 임베딩 차원은 2,000 이하다. `vector` 열의 HNSW 색인이 받는 차원이 2,000까지라서다(README 252행과 2,000을 넘는 벡터의 FAQ 827~829행. 같은 프로브). 넘는 차원은 `migrate`가 설정 오류로 거부해(관리 명령 절) 색인 판이 그 차원으로 만들어지지 않는다.
- [거절] 2,000을 넘는 차원을 `halfvec`(4,000까지)로 여는 것은 첫 판에 두지 않는다. 기본 모델(`RAG_DEFAULT_EMBEDDING_MODEL`)은 한도 안이고, 그 필요는 search-eval이 모델을 바꿀 때 본다.
- [정함] 색인 판의 요소 넷은 스키마 판(코드의 상수. 첫 판은 1), 임베딩 모델 이름과 차원, 청킹 설정 해시(전략 이름·상한·겹침·전략 구현 판·문장 분리기 판을 정렬한 JSON의 sha256. 문장 분리기 판은 청킹이 문장 경계를 얻는 kiwipiepy와 kiwipiepy_model의 판이다), 토크나이저 판(kiwipiepy의 판, kiwipiepy_model의 판, 키워드 규칙의 판을 붙인 문자열)이다. 지식베이스의 현재 설정에서 계산한 넷이 현재 판의 넷과 다르면 "재색인 필요"다(ADR 0008). 키워드 규칙(품사 집합, 전처리)을 바꾸는 것도 토크나이저 판을 올리는 일이라 재색인이다. 요소마다 재색인의 범위가 다르다(ADR 0008). 임베딩 모델·차원·청킹 해시가 바뀌면 청킹부터 다시 하고, 토크나이저 판만 바뀌면 조각과 임베딩은 그대로 두고 키워드만 다시 만든다(방법은 아래 작업 절). 임베딩 끝점은 요소가 아니라 판에 적어 두는 주소다(같은 모델을 다른 주소로 옮겨도 재색인하지 않는다. 관리 명령 절의 `migrate`). 청킹 설정은 해시만이 아니라 원본(전략 이름·상한·겹침)도 판에 적고, 작업은 판마다 그 판에 적힌 전략 이름·상한·겹침으로 청킹한다. 전략 구현 판과 문장 분리기 판은 코드와 이미지에 하나뿐이라 해시에만 들고, 그것이 바뀐 뒤의 판은 "재색인 필요"로 드러난다. 재색인 중에는 지식베이스 설정이 새 값이라, 현재 판의 문서가 바뀌었을 때 설정에서 다시 읽으면 현재 판을 새 설정으로 청킹하게 된다. 코드와 이미지에 하나뿐인 구현(청킹 전략의 구현, 문장 분리기, 키워드 토크나이저)은 판마다 옛것을 고를 수 없다. 그 구현이 바뀐 코드가 돌면 재색인이 전환될 때까지 현재 판에는 옛 구현으로 만든 조각·키워드와 그사이 갱신된 문서를 새 구현으로 만든 것이 섞이고, 검색은 질의를 새 토크나이저로 나눈다(키워드 토큰 절의 질의 토큰화 규칙의 예외다). 갱신된 문서를 현재 판에 새 구현으로 쓰지 않는 길은 둘인데, 옛 조각을 두면 원천에 없는 옛 글이 남아 원칙 VI에 어긋나고, 옛 조각을 지우기만 하면 그 문서가 전환까지 검색에서 빠진다. 그래서 가용성을 지키려 이 섞임을 받아들인다. 바뀐 구현의 판은 판의 요소(청킹 해시, 토크나이저 판)에 들어 "재색인 필요"로 드러나고, 섞임은 판 전환으로 걷힌다. 그동안 섞인 문서끼리는 조각 경계와 키워드 규칙이 달라 키워드 쪽의 재현율이 떨어질 수 있다. 벡터는 판에 적힌 한 임베딩 모델로 만들므로 경계가 다른 조각끼리도 견줄 수 있다.
- [이력] Kiwi(kiwipiepy나 그 모델)를 올리면 청킹의 문장 경계도 바뀔 수 있어 두 요소가 함께 바뀌므로 청킹부터 다시 하고, 토크나이저 판만 바뀌는 것은 키워드 규칙만 바꾼 때다. ADR 0008 이력 2026-11-10과 본문 포인터 둘이 이 변경이다(티켓 세션에서 사용자가 골랐다).
- [정함] `jobs`의 칸은 종류(`index_document` 하나), 문서 참조, 상태 `queued`·`running`·`succeeded`·`failed`, 시도 횟수, 다음 실행 시각 `run_after`, 임대 만료 `leased_until`, 작업자 ID, 올린 세대(이번 시도가 첫째 단계에서 올린 문서의 세대. 꺼낼 때 비운다), 마지막 오류 코드, 요청 ID, 만든·시작·끝난 시각이다. 같은 문서의 대기(`queued`) 작업은 부분 유일 색인으로 하나다(ADR 0009). 대기 작업이 이미 있으면 넣는 쪽이 그것을 다시 쓴다(수집 파이프라인 절). 실행 중인 작업이 있어도 새 대기 작업은 들어간다. 작업자가 꺼내는 조건(아래)은 같은 문서의 실행 중 작업을 거르지 않아, 같은 문서의 작업 둘이 동시에 돌 수 있다(수집이나 재색인 시작이 실행 중인 작업 옆에 넣은 작업, 임대가 끝나 다른 작업자가 가져간 같은 작업). 문서마다 직렬화하지 않는 대신 작업의 첫째 단계가 세대를 올리고 쓰는 단계마다 대 보아(수집 파이프라인 절의 잠금 규칙), 문서에 관해 쓰는 것은 세대를 올린 작업 가운데 가장 늦게 시작한 작업 하나다. 그래서 결과는 가장 늦게 시작한 작업의 결과로 모인다. 예외는 올린 세대를 모르는 재시도 소진 하나다. 그 문서가 지금 내용으로 색인되지 않은 판에 `failed`만 쓰고, 세대를 올린 작업이 뒤에 그 판에 쓰면 덮인다(수집 파이프라인 절의 재시도 소진).
- [정함] `tokens`의 칸은 이름, 토큰 원문의 sha256(유일), 역할 `admin`·`reader`, 지식베이스 범위(지식베이스 참조 배열. 비면 전부), 만료 시각(없을 수 있음), 회수 시각, 만든 시각이다. 마지막 사용 시각은 두지 않는다(요청마다 쓰기가 생긴다).

### 수집 API

- [넘겨받음] 수집 API는 `POST /api/v1/ingest/documents`의 multipart다. 파일 `file`과 폼 칸 `key`(없으면 파일 이름), `group`(없으면 기본 그룹), `metadata`(JSON 객체 문자열)를 받고, 202와 작업 ID를 돌려준다. 같은 (원천, 키)면 갱신이고 내용 해시가 같으면 건너뛴다. 삭제는 같은 경로의 DELETE다. 크기 상한은 `RAG_MAX_UPLOAD_MB`다. 방향은 다른 시스템이 우리에게 미는 것이다(일지 결정 요약 21).
- [정함] 폼 칸 `updated_at`(ISO 8601)을 더한다. 호출자가 문서의 갱신일을 알면 넘긴다. 원천은 밀어 넣는 원천 `default` 하나이고 수집 API와 `ingest` 명령이 같은 원천에 넣는다. 제목은 `metadata.title`이 문자열이면 그것, 아니면 확장자를 뗀 파일 이름이다. 수집 API의 판은 경로의 `v1`이다. 칸을 더하는 것은 같은 판이고, 칸을 지우거나 뜻을 바꾸면 `v2`다(원칙 VII).
- [정함] 응답은 `action` 칸으로 가른다. 새 문서면 `created`, 내용이나 그룹이 바뀌었으면 `updated`, 지운 문서가 돌아왔으면 `restored`, 내용은 같지만 앞선 색인이 실패한 문서(문서 상태가 `failed`이거나 살아 있는 판의 색인 상태에 `failed`가 있음)면 `requeued`이고, 넷 다 202에 `document_id`와 `job_id`가 실린다(`restored`에서 보관 조각이 대상 판(문서의 그룹이 든 지식베이스의 살아 있는 판)을 모두 채우면 작업이 없어 `job_id`가 null이다). 내용과 그룹이 같고 색인도 실패하지 않았으면 `unchanged`이고 200에 `job_id`가 null이다. 메타데이터·갱신일만 달라졌으면 `unchanged`인 채로 문서 행과 조각의 복사 칸을 같은 트랜잭션에서 고친다. 그룹이 바뀌면 같은 작업 단위에서 그 문서의 모든 조각(물러난 판의 것도)의 복사 칸을 새 그룹으로 고치고, 새 그룹이 들지 않는 지식베이스(문서가 빠지는 지식베이스)의 살아 있는 판에서 그 문서의 조각과 색인 상태를 지우며(그 지식베이스에 `building` 판이 있으면 전환 검사를 한다), 대상 지식베이스가 바뀌므로 작업을 넣는다(파싱은 해시가 같아 건너뛴다). 그래서 문서는 빠지는 지식베이스의 검색에서 그 커밋으로 바로 빠지고, 작업이 실패해도 옛 조각이 남지 않는다.
- [정함] 형식은 확장자 `.pdf`·`.docx`·`.hwpx`를 먼저 보고, 없거나 맞지 않으면 바이트 머리(`%PDF`, ZIP 머리와 안의 내용 종류)로 가린다. 셋 밖이면 415 `unsupported_media_type`, 크기를 넘으면 413 `upload_too_large`, 폼 칸 `group`이 없는 그룹 이름이면 404 `group_not_found`다. 이 셋은 작업을 만들지 않고 즉시 거부한다.
- [정함] `DELETE /api/v1/ingest/documents?key=<키>`가 소프트 삭제다. 204이고, 이미 지운 문서도 204, 없는 키는 404 `document_not_found`다. 키는 URL 인코딩한 쿼리 매개변수다(키에 `/`가 들 수 있다). 키로 문서 상태를 보는 길은 수집 API가 아니라 관리 API의 문서 목록(`key=` 필터)이다.
- [정함] 같은 키를 동시에 넣는 두 요청은 (원천, 키) 유일 제약과 한 트랜잭션으로 직렬화한다. 뒤의 요청이 충돌하면, 제가 만든 문서 UUID 아래에 쓴 원본을 이긴 문서의 UUID 아래 새 원본 UUID 경로로 옮긴 뒤 한 번 다시 읽어 갱신으로 처리한다(원본 경로 규칙은 수집 파이프라인 절).
- [넘겨받음] 수집 API는 쓰기라 `admin` 역할 토큰이 필요하다(ADR 0001, 0014).

### 수집 파이프라인과 작업

- [정함] 수집 요청의 트랜잭션 전 단계는 원본 저장이다. 파일 저장소에 `RAG_DATA_DIR/blobs/<문서 UUID>/<원본 UUID>`(수집 요청마다 새로 만드는 UUID)로 쓰고(ADR 0013과 그 이력 2026-11-10 "원본은 문서 UUID 디렉터리 아래에 수집 요청마다 새 이름으로 둔다"), 그 뒤 작업 단위 하나에서 문서 행을 만들거나 고치고 `index_document` 작업을 넣고 `NOTIFY`한다. 경로가 요청마다 달라 갱신의 새 원본이 옛 원본을 덮지 않고(옛 원본을 읽는 중인 작업자가 반쯤 바뀐 파일을 읽지 않는다), 같은 문서에 같은 내용을 동시에 넣는 두 요청도 다른 경로에 써서 한쪽의 정리가 다른 쪽이 커밋한 원본을 지우지 않는다. 문서 행의 원본 경로는 응답이 `created`(묘비 행을 다시 쓰는 것 포함)이거나 내용 해시가 바뀐 수집에서만 새 원본으로 바꾸고, 그때 옛 원본(작업 단위가 잠그고 읽은 문서 행의 원본 경로)은 작업 단위가 커밋된 뒤에 지운다(최선 노력). 그 밖의 수집(`unchanged`, `requeued`, 그룹만 바뀐 `updated`, 내용 해시가 같은 되살림)은 문서 행이 새 원본을 가리키지 않으므로 커밋 뒤에 새 원본을 지운다. 롤백되면 새 원본을 지운다. 커밋 뒤에 옛 원본을 지우면 그것을 읽던 앞 세대의 시도는 문서에 쓰지 않는다(파싱 실패는 세대 대조에 걸리고, 읽기 실패는 일시 실패라 다음 시도가 첫째 단계에서 새 원본 경로를 읽는다). 지우지 못한 원본(Windows에서 열린 파일 등)은 고아 원본으로 남는다(포트 절).
- [정함] 같은 문서의 대기 작업은 하나라서(부분 유일 색인) 작업을 넣는 쪽은 대기 작업이 이미 있으면 그것을 다시 쓴다. 수집(작업을 넣는 모든 `action`)은 새 행을 넣지 않고 그 행의 `run_after`를 지금으로 당기고 요청 ID를 이번 요청의 것으로 바꾸며 시도 횟수는 둔다. 응답의 `job_id`는 그 행의 ID다(부분 유일 색인에 거는 `INSERT … ON CONFLICT … DO UPDATE` 한 문장). 재색인 시작은 아래 잠금 규칙대로 잠근 대기 작업이 있는 문서를 건너뛴다. 일시 실패한 시도를 다시 예약하는 작업 단위는 문서 행, 그 문서의 그룹이 든 지식베이스 행(`FOR SHARE`. 재색인 시작이 넣는 작업과 직렬화한다), 작업 행 순으로 잠그고, 같은 문서에 다른 대기 작업이 있으면 다시 예약하지 않고 이번 오류 코드로 작업을 `failed`로 끝낸다. 문서 쪽(재시도 소진의 `failed` 쓰기)은 하지 않는다. 그 대기 작업이 뒤에 첫째 단계부터 해 그때의 문서를 맡기 때문이다. 둘째 대기 작업을 넣거나 `running`을 `queued`로 되돌리면 부분 유일 색인이 `UniqueViolation`(`23505`)으로 막는다(프로브 `pg-ddl/ddl_locks.py`의 F).
- [정함] 작업 `index_document`의 뜻은 이 문서를 그 그룹이 든 모든 지식베이스의 살아 있는 색인 판(`current`와 `building`)에 맞추는 것이다. 지정 색인 판 인자는 없다. 그래서 재색인도 문서마다 같은 종류의 작업 하나를 넣으면 되고, 대기 작업의 유일성이 자연스럽다. 처리 순서는 넷이다. 첫째, 작업 단위 하나에서 문서 행과 작업 행을 잠그고(아래 잠금 규칙의 작업 행 조건) 문서를 읽어 지워졌으면 아무것도 하지 않고 성공으로 끝내고, 아니면 세대를 하나 올려 그 값을 작업 행의 올린 세대에 적고, 그 값과 그때의 내용 해시, 원본 경로를 기억한다(둘째 단계는 그 원본 경로를 파싱한다). 둘째, 파싱 결과가 없거나 파싱한 내용 해시가 문서의 내용 해시와 다르거나 파서의 판이 바뀌었으면 파싱해(아래 격리 절) 파싱 결과 행을 쓰고, 같은 작업 단위에서 문서 상태를 `parsed`로 쓰고 오류 코드를 비운다. 맞는 파싱 결과가 있어 파싱을 건너뛰었는데 문서 상태가 `parsed`가 아니면(내용을 바꿨다가 옛 내용으로 되돌린 수집이 `received`로 둔 경우) 셋째 단계가 처음 쓰는 작업 단위에서 그렇게 쓴다. 쓰는 작업 단위는 아래 잠금 규칙의 세대 대조를 따른다. 세대가 첫째 단계에서 올린 값과 다르면 쓰지 않고 넷째로 간다(새 상태는 세대를 올린 수집이나 삭제, 뒤에 시작한 작업이 맞춘다. 늦게 끝난 옛 작업이 새 파싱 결과를 덮지 않는다). 셋째, 그때의 살아 있는 판을 대상 판으로 읽어 판마다 청킹(그 판에 적힌 청킹 설정으로), 토큰 세기와 임베딩(그 판에 적힌 끝점·모델·차원으로), 키워드 토큰화를 한 뒤 작업 단위 하나에서 문서 행을 잠그고 세대를 다시 읽는다(아래 잠금 규칙의 세대 대조). 세대가 첫째 단계에서 올린 값과 다르면(그사이 지워졌거나, 내용·그룹이 바뀌었거나, 지운 뒤 되살아났거나, 같은 내용을 다시 넣은 수집이 왔거나, 같은 문서의 다른 작업이 뒤에 시작했다) 조각을 쓰지 않고 넷째로 간다. 새 상태는 세대를 올린 쪽이 맞춘다(수집은 작업을 넣거나 보관 조각을 되돌리고, 삭제는 조각을 보관 표로 옮기며, 뒤에 시작한 작업은 제가 쓴다). 아니면 그 (문서, 판)의 옛 조각을 지우고 새 조각(만든 내용 해시와 복사 칸은 잠근 문서 행의 값)을 넣고 색인 상태를 `indexed`로 쓴다. 삭제와 수집의 작업 단위도 같은 문서 행을 잠그거나 고치므로 셋은 직렬화되고, 지운 문서의 조각이나 옛 내용·옛 그룹의 조각이 검색 표에 다시 들어가지 않는다. 대상 판이 `building`이고 같은 지식베이스의 `current` 판과 임베딩 모델·차원·청킹 해시가 같으면(토크나이저 판만 다른 재색인) 청킹과 임베딩을 하지 않고 `current` 판의 그 문서 조각 가운데 만든 내용 해시가 첫째 단계에서 기억한 해시와 같은 것(글, 위치, 임베딩)을 복사해 키워드만 다시 만든다. 그런 조각이 없으면(`current` 판이 아직 옛 내용이면) 다른 판처럼 청킹과 임베딩을 한다(ADR 0008이 가른 범위 둘을 작업 종류 하나의 두 길로 한다). 색인 상태를 쓴 뒤 그 지식베이스에 `building` 판이 있으면 그 지식베이스마다 "전환 검사"를 한다. 지식베이스 행을 `FOR UPDATE`로 잠근 채 그 판의 모든 색인 상태가 `indexed`나 `failed`인지 보고, 맞으면 같은 작업 단위에서 판 전환(아래)을 한다. 잠금이 검사부터 전환까지를 지식베이스마다 직렬화해, 마지막 두 문서를 동시에 끝낸 작업자 둘이 서로를 `pending`으로 보고 둘 다 전환하지 않는 일이 없다. 넷째, 작업을 `succeeded`로 끝낸다(셋째 단계에서 어느 판의 임베딩이 영구 실패했으면 `failed`. 아래 영구 실패 항목). 세대 대조에 걸려 넷째로 온 작업도 이 규칙대로 끝난다(문서에 쓰지 않았어도 `succeeded`이고, 그 전에 어느 판의 임베딩이 영구 실패했으면 `failed`). 그래서 작업의 상태는 그 작업이 끝난 모양이지 문서의 색인 결과가 아니고, 문서의 결과는 문서 상태와 판마다의 색인 상태(관리 API의 문서 조회)가 원천이다(`ingest --wait`도 문서로 판정한다. 관리 명령 절). 문서 단위 원자 교체(ADR 0008)는 셋째 단계의 작업 단위가 보장한다.
- [정함] 잠금 규칙. 작업 단위는 PostgreSQL의 기본 격리 수준인 Read Committed에서 돌아, 잠금을 얻은 뒤의 질의는 그 사이 커밋된 행을 본다. 잠금 순서는 문서 행, 지식베이스 행(여럿이면 ID 순), 작업 행이다. 세대 대조: 색인 작업이 문서에 관해 쓰는 작업 단위(파싱 결과, 조각과 색인 상태, 영구 실패, 재시도 소진)는 모두 문서 행을 먼저 잠그고 세대를 읽어, 그 작업이 첫째 단계에서 올린 값 그대로일 때만 쓴다. 다르면 그사이 수집·삭제나 같은 문서의 뒤에 시작한 작업이 세대를 올린 것이라 문서에 관해서는 쓰지 않는다. 그래서 같은 문서의 작업이 동시에 돌아도 문서에 쓰는 것은 세대를 올린 작업 가운데 가장 늦게 시작한 작업 하나다(올린 세대를 모르는 재시도 소진만 예외다. 아래 재시도 소진). 작업 행 조건: 색인 작업이 쓰는 작업 단위는 모두(첫째 단계의 세대 올림, 문서에 관해 쓰는 단계, 작업 행을 고치는 끝냄·다시 예약·임대 연장) 그 작업 단위가 잠그는 문서 행과 지식베이스 행을 잠금 순서대로 잠근 뒤 마지막에 작업 행을 잠가 작업자 ID와 시도 횟수가 그 시도가 꺼낼 때 쓴 값 그대로인지 보고, 아니면 임대가 끝나 다른 작업자가 그 작업을 가져간 것이라 그 작업 단위를 롤백해 아무것도 쓰지 않고 그 시도를 버린다(가져간 시도가 문서 쪽을 맡는다). 작업 행의 잠금은 커밋까지 가므로 그동안 다른 작업자가 그 작업을 가져가지 못한다. 첫째 단계도 이 조건을 보므로, 임대를 잃은 뒤에야 첫째 단계에 든 시도가 세대를 다시 올려 가져간 시도의 결과를 버리게 하지 못한다. 지식베이스 행을 잠그는 작업 단위는 잠근 뒤에 그 지식베이스의 살아 있는 판을 읽는다(색인 작업의 셋째 단계는 잠그지 않고 읽는다. 그사이 시작한 재색인은 아래대로 그 문서에 새 작업을 넣는다). 문서 행은 `FOR NO KEY UPDATE`로 잠근다(키 열을 바꾸지 않는 `UPDATE`도 같은 잠금을 건다). 재색인 시작은 그 지식베이스 행을 `FOR UPDATE`로 잠그고, 문서들의 대기 작업 행을 `FOR UPDATE`로 잠근 뒤 잠근 대기 작업이 없는 문서에만 새 작업을 넣는다. 작업자가 꺼낼 때의 `SKIP LOCKED`는 잠긴 대기 작업을 재색인 시작이 커밋될 때까지 건너뛰므로, 그 작업의 셋째 단계는 새 판도 대상 판으로 읽는다(잠그기 전에 꺼내져 `running`이 된 작업의 문서는 잠근 대기 작업이 없어 새 작업을 받는다). 응답이 `unchanged`가 아닌 수집은 문서 행을 쓴 바로 뒤, 작업을 넣거나 조각을 고치기 전에, 문서가 드는 지식베이스 행을 `FOR SHARE`로, 그룹이 바뀌어 문서가 빠지는 지식베이스 행을 `FOR UPDATE`로 잠근다. 삭제는 그 문서의 그룹이 든 지식베이스 행을, 전환 검사는 그 지식베이스 행을 `FOR UPDATE`로 잠근다. 그래서 재색인 시작은 수집·삭제와 지식베이스 행에서 직렬화된다. 수집이 먼저 커밋되면 재색인 시작이 그 문서를 세고, 재색인 시작이 먼저 커밋되면 수집과 그 작업이 새 판도 대상 판으로 보며, 삭제는 재색인 시작이 쓴 `pending`과 작업까지 지운다. 문서가 빠지는 지식베이스의 조각과 색인 상태는 그룹을 바꾸는 수집이 지우므로(수집 API 절), 삭제는 지금 그룹의 지식베이스만 잠그면 된다. 문서 행을 `FOR UPDATE`로 잠그지 않는 까닭은, 재색인 시작이 지식베이스 행을 잠근 채 넣는 색인 상태·작업 행의 외래 키 검사가 문서 행에 `FOR KEY SHARE`를 걸기 때문이다. `FOR UPDATE`는 그 잠금을 막아, 문서 행을 잠근 뒤 지식베이스 행을 기다리는 수집·삭제와 재색인 시작이 서로를 기다린다(교착). `FOR NO KEY UPDATE`는 막지 않는다. 근거는 프로브 `facts/pg_row_lock_facts.py`(PostgreSQL 18 문서의 행 잠금 절, 격리 수준 절, SELECT 절의 `SKIP LOCKED`, `REL_18_STABLE`의 `ri_triggers.c`에서 `RI_FKey_check`가 조립하는 질의. 출력 `pg_row_lock_facts_out.txt`)다.
- [정함] 파싱이 영구 실패하면 문서 상태를 `failed`로, 오류 코드를 쓰고, 모든 살아 있는 판에서 그 문서의 조각을 지우고 색인 상태를 `failed`로 쓴다. 옛 조각을 두지 않는 까닭은 원천의 지금 내용을 읽을 수 없는데 옛 글을 답의 근거로 내는 것이 원칙 VI에 어긋나기 때문이다. 작업은 재시도 없이 `failed`로 끝난다. 임베딩의 영구 실패(`embedding_rejected`, `embedding_dimension_mismatch`)는 문서 상태를 바꾸지 않고(파싱은 됐다) 그 판에서 셋째 단계를 멈추지 않는다. 남은 대상 판의 계산을 이어 가고, 셋째 단계가 쓸 때 그 (문서, 판)에는 옛 조각을 지우고 색인 상태를 `failed`로 쓴다(나머지 판은 위대로 `indexed`). 판마다 끝점·모델·차원이 다를 수 있어 한 판의 거부를 다른 판의 실패로 볼 수 없고, 거기서 멈추면 남은 판(건설 중인 판)의 `pending`을 맡을 작업이 없어 그 판이 전환되지 않는다. 남은 판에 일시 실패가 없으면 작업은 넷째 단계에서 `failed`로 끝나고 마지막 오류 코드는 그 영구 실패의 코드다. 남은 판에서 일시 실패가 나면 그 시도는 일시 실패로 다뤄 다시 예약하고(아래), 다음 시도는 첫째 단계부터 거부된 판까지 모든 대상 판을 다시 한다. 재시도를 다 쓰면 아래 재시도 소진대로 끝난다. 같은 내용을 다시 넣으면 `requeued`로 작업이 다시 들어간다. 두 영구 실패 모두 색인 상태를 `failed`로 쓴 뒤 위의 전환 검사를 한다(마지막 문서가 실패해도 판이 `building`에 남지 않는다). 영구 실패를 쓰는 작업 단위도 세대 대조(위 잠금 규칙)를 따라, 세대가 첫째 단계에서 올린 값과 다르면 문서 상태·조각·색인 상태를 건드리지 않고(남은 판에도 쓰지 않는다) 작업만 `failed`로 끝낸다(지운 뒤 되살린 문서의 되돌린 조각이나 뒤에 시작한 작업이 쓴 조각을 옛 작업의 실패가 지우지 않는다).
- [정함] 실패는 둘로 가른다. 영구 실패는 파싱의 모든 실패(시간 초과, 메모리 초과, 파서 예외, 한도 초과, 암호 문서), 임베딩 서버의 400·413·422, 벡터 차원 불일치다. 일시 실패는 데이터베이스의 일시 오류(아래 오류 번역 항목), 임베딩·리랭커 서버의 연결 실패·시간 초과·424·429·5xx, 파일 저장소의 입출력 오류다. 영구 실패만 난 시도는 다시 예약하지 않고 `failed`로 끝나고(파싱은 즉시, 임베딩은 남은 대상 판을 마친 뒤. 남은 판에 일시 실패가 섞이면 일시 실패로 다룬다. 위 항목), 일시 실패는 `run_after`를 `RAG_JOB_BACKOFF_BASE_SECONDS × 4^(시도 횟수 − 1)`(30초, 2분, 8분, 32분, 그다음부터는 한 시간 상한) 뒤로 두어 다시 예약하며, `RAG_JOB_MAX_ATTEMPTS`(6)를 다 쓰면 작업이 `failed`이고, 그때 문서 행을 잠그고 그 문서의 그룹이 든 지식베이스 행을 `FOR UPDATE`로 잠근 뒤(재색인 시작과 직렬화해, 그것이 쓴 `pending`과 작업을 보고 판정한다) 같은 문서를 처음부터 맡을 다른 작업이 없고 세대가 마지막 시도가 첫째 단계에서 올린 값 그대로일 때만(마지막 시도가 첫째 단계를 마치기 전에 실패해 올린 값이 없거나, 아래 임대 인수에서 그 값을 모르면 다른 작업만 본다) 문서가 지워지지 않았으면(지운 문서의 색인 상태 행은 삭제가 모두 지웠다) 그 문서의 그룹이 든 지식베이스의 살아 있는 판 가운데 그 문서가 지금 내용으로 색인되지 않은 판(색인 상태가 `pending`이거나, 없거나, `indexed`인데 만든 내용 해시가 문서의 내용 해시와 다른 판)에서 그 문서의 조각을 지우고 색인 상태를 마지막 오류 코드로 `failed`로 쓰고 전환 검사를 한다(문서 상태는 바꾸지 않는다. 그래서 같은 내용을 다시 넣으면 `requeued`이고 건설 중인 판이 그 문서에 막히지 않는다). 문서를 처음부터 맡을 다른 작업은 대기 중인 작업과, 실행 중이면서 올린 세대가 빈 작업이다. 둘 다 뒤에 첫째 단계부터 해 그때의 문서를 맡는다(셋째 단계에 가면 그때의 살아 있는 판을 모두 대상 판으로 읽고, 그 전에 시도를 다 쓰면 제가 재시도 소진을 쓴다. `worker_lost`로 꺼내진 것 포함). 올린 세대가 채워진 실행 중 작업은 세지 않는다. 그 값이 지금 세대와 다르면 그 시도는 세대 대조에 걸려 문서에 쓰지 않고, 그 작업이 다시 꺼내지면(일시 실패 뒤 다시 예약된 것, 임대 인수) 올린 세대를 비우고 첫째 단계부터 다시 해 그때 문서를 맡는다. 같으면 그 시도는 셋째 단계에서 대상 판을 이미 읽었을 수 있어, 읽은 뒤에 생긴 판(그 뒤에 시작한 재색인의 건설 중인 판)을 맡지 않는다. 올린 세대가 채워진 실행 중 작업을 세면 그 판의 `pending`을 어느 작업도 맡지 않을 수 있어 건설 중인 판이 전환되지 않고 다음 재색인도 거부될 수 있다. 세대가 같은 시도가 뒤에 제 대상 판에 쓰는 것은 세대 대조를 지나므로(재시도 소진은 세대를 올리지 않는다) 재시도 소진이 쓴 `failed`를 `indexed`로 덮는다. 그래서 그 시도가 쓰기 전까지 그 문서는 그 판에서 `failed`로 보이고 검색에 없으며(지운 조각은 지금 내용으로 만든 것이 아니었다), 그사이 같은 내용을 다시 넣으면 `requeued`가 세대를 올려 그 시도는 쓰지 않고 새 작업이 맡는다. 그 시도가 건설 중인 판도 대상 판으로 읽었으면 재시도 소진의 `failed`로 판이 먼저 전환될 수 있고, 그때 그 시도는 새 현재 판에 써 문서가 다시 검색에 들며, 물러난 옛 판에 쓴 조각은 아래 판 전환 항목대로 검색에 보이지 않는다. 색인 상태가 없는 판(재색인을 시작한 뒤에 그 지식베이스에 든 문서의 건설 중인 판 등)에도 `failed`를 쓰는 것은 판이 전환된 뒤에도 실패가 남아 같은 내용을 다시 넣으면 `requeued`로 다시 들어가게 하기 위해서이고, 진행 셈에서는 끝난 것으로 세므로 판을 막지 않는다. 그 판들의 조각을 지우는 까닭은 파싱의 영구 실패와 같다. 남은 조각은 문서의 지금 내용으로 만든 것이 아니어서, 두면 원천의 지금 내용이 아닌 글을 답의 근거로 낸다(원칙 VI). 오류 코드는 `parse_timeout`, `parse_memory_exceeded`, `parse_failed`, `too_many_pages`, `document_too_large`, `compressed_too_large`, `encrypted_document`, `embedding_rejected`, `embedding_dimension_mismatch`, `embedding_unavailable`, `database_unavailable`, `blob_store_error`, `internal_error`, `worker_lost`다(`internal_error`는 어느 갈래에도 들지 않는 예외다. 아래 오류 번역 항목. 마지막은 임대 인수에서 시도를 다 쓴 작업이다. 아래 작업자 항목).
- [정함] 오류 번역. 어댑터는 서드파티 예외를 `domain`의 영구·일시 실패 예외(오류 코드를 든다)로 바꿔 올리고, 서드파티 예외의 메시지는 옮기지 않는다(질의, 문서 내용, 연결 정보가 들 수 있다. 원칙 V). 데이터베이스의 일시 실패는 연결 실패(SQLSTATE `08` 갈래와 연결 끊김), 직렬화 실패 `40001`, 교착 `40P01`, 관리자 종료 `57P01`~`57P03`이고 오류 코드는 `database_unavailable`이다. `DataError`, `IntegrityError` 같은 나머지 데이터베이스 오류는 일시 실패가 아니다. 파일 저장소의 입출력 오류는 `blob_store_error`(일시)다. 어느 갈래에도 들지 않는 예외는 작업자가 `internal_error`로 받아 다시 예약하지 않고 재시도 소진과 같이 끝낸다(작업 `failed`, 같은 잠금과 같은 문서 쪽 쓰기, 전환 검사). 같은 예외가 다시 날 것이라 재시도는 시간만 쓰기 때문이다. 파싱 결과의 글에서는 저장 전에 U+0000을 지운다(파서 인터페이스 항목). 글 칸의 NUL은 psycopg가 서버에 보내기 전에 `DataError`(sqlstate 없음)로 거부하고, jsonb의 NUL은 PostgreSQL이 `UntranslatableCharacter`(`22P05`)로 거부한다(프로브 `pg-ddl/ddl_locks.py`의 E. 보내기 전이라는 것은 psycopg 3.3.8의 문자열 덤퍼 `psycopg/types/string.py`가 NUL을 보면 그 예외를 내는 것을 읽어 확인했다).
- [정함] 작업자는 `SELECT … FOR UPDATE SKIP LOCKED`로 `queued`이고 `run_after`가 지난 작업, 또는 `running`인데 `leased_until`이 지난 작업을 하나 꺼내 `running`으로 바꾸고 시도 횟수를 올리고 올린 세대를 비우며 `leased_until`을 `RAG_JOB_LEASE_SECONDS` 뒤로 둔다(ADR 0009). 처리 중에는 임대 기간의 삼분의 일마다 임대를 늘린다. 작업자가 죽으면 임대가 끝난 뒤 다른 작업자가 가져가고, 그 시도는 횟수에 센다. 죽지 않고 늦기만 한 작업자의 시도는 잠금 규칙의 세대 대조와 작업 행 조건에 걸려 문서에도 작업 행에도 쓰지 못한다. 임대가 끝난 작업의 시도 횟수가 이미 `RAG_JOB_MAX_ATTEMPTS` 이상이면 다시 돌리지 않는다. 꺼내는 것은 다른 작업과 같아 시도 횟수를 올리고 임대를 둔다(그래서 시도 횟수가 최대를 넘을 수 있다. 늦은 시도와 같은 프로세스가 꺼내도 시도 횟수가 달라져 작업 행 조건이 늦은 시도를 거른다). 꺼낸 작업 단위는 그대로 커밋하고, 이어지는 작업 단위가 잠금 순서대로 문서 행, 지식베이스 행, 작업 행을 잠가 재시도 소진과 같이 끝낸다(작업 `failed`, 오류 코드 `worker_lost`). 꺼낼 때 올린 세대를 비우므로 꺼낸 쪽은 죽은 시도가 올린 세대를 모르고, 문서 쪽은 위 재시도 소진 규칙에서 문서를 처음부터 맡을 다른 작업만 본다. 꺼내는 작업 단위가 작업 행을 쥔 채 문서 행을 기다리면 잠금 순서를 거슬러, 문서 행을 쥐고 작업 행을 기다리는 임대 잃은 시도와 서로를 기다린다. 작업자 ID는 호스트 이름과 PID다.
- [정함] 작업자 프로세스는 `LISTEN rag_jobs`로 깨어나고 `RAG_WORKER_POLL_SECONDS`마다 폴링하며, `RAG_WORKER_CONCURRENCY`개의 작업을 비동기로 함께 처리한다. SIGTERM이나 SIGINT를 받으면 새 작업을 꺼내지 않고 진행 중인 작업을 끝낸 뒤 나간다. Windows는 다른 프로세스가 보낸 SIGTERM을 전달하지 않으므로(종료만 시킨다) SIGBREAK(`CTRL_BREAK_EVENT`)를 같은 뜻으로 받는다. 테스트를 위해 지금 꺼낼 수 있는 작업을 모두 처리하고 돌아오는 한 번 돌기 입구를 둔다.
- [정함] 재색인 시작은 먼저 트랜잭션 밖에서 그 지식베이스의 물러난 판에 남은 정리(아래 판 전환 항목)를 하고, 그 뒤 작업 단위 하나에서 지식베이스 행을 잠근 뒤 한다(위 잠금 규칙). 지식베이스에 `building` 판이 있으면 409 `reindex_in_progress`다. 없으면 현재 설정(끝점·모델·차원, 청킹, 토크나이저 판)을 적은 새 색인 판을 `building`으로 만들고, 그 지식베이스의 그룹에 든 살아 있는 문서마다 색인 상태 `pending`을 쓰고 `index_document` 작업을 넣은 뒤(이미 대기 작업이 있으면 그 행을 잠그고 건너뛴다. 위 잠금 규칙) 그 판의 HNSW 부분 색인을 만든다(데이터 모델 절). 문서가 하나도 없으면 색인을 만든 뒤 같은 작업 단위에서 판을 전환한다. 재색인을 시작한 뒤에 그 지식베이스에 든 문서(새 문서, 그룹을 바꿔 들어온 문서, 되돌릴 조각 없이 되살린 문서)는 건설 중인 판에 색인 상태가 없어 진행 셈에 들지 않는다. 그 문서의 작업은 셋째 단계에서 살아 있는 판을 읽어 건설 중인 판이나 전환된 새 현재 판에 쓰므로, 판이 먼저 전환되어도 작업이 끝나면 새 현재 판에 든다(작업이 끝나기 전에 검색에 없는 것은 재색인이 없을 때와 같다). 수집은 건설 중인 판에 `pending`을 쓰지 않는다. 쓰면 수집이 이어지는 동안 판이 전환되지 않을 수 있다. 응답은 202에 새 색인 판 ID와 넣은 작업 수다.
- [정함] 판 전환은 지식베이스 행을 잠근 작업 단위에서 현재 판 참조를 새 판으로 바꾸고 새 판을 `current`, 옛 판을 `retired`로 쓴다. 검색은 `current` 판만 보므로 전환 전에는 옛 조각을, 전환 뒤에는 새 조각을 본다(ADR 0008). 옛 판의 정리는 전환을 커밋한 뒤 같은 작업자가 한다. HNSW 색인을 트랜잭션 밖에서 `DROP INDEX CONCURRENTLY IF EXISTS`로 먼저 지우고(데이터 모델 절), 조각은 정한 수씩 묶음마다 별도 트랜잭션에서 지운다(큰 지식베이스에서 한 트랜잭션을 길게 하지 않기 위해서다. 묶음 크기는 상수다). 그 사이에 작업자가 죽거나, 전환 전에 대상 판을 읽은 작업이 정리 뒤에 그 판에 조각을 써서 물러난 판에 조각이 남아도 검색에는 보이지 않고, 다음 재색인 시작이 제 작업 단위를 열기 전에 트랜잭션 밖에서 물러난 판마다 같은 정리를 한다.
- [정함] 색인 판 행을 만들거나 고치는 작업 단위(재색인 시작, 판 전환, `migrate`의 첫 판 만들기와 끝점 고치기)는 모두 그 지식베이스 행을 `FOR UPDATE`로 잠근 뒤 쓴다. `migrate`는 지식베이스 행이 없으면 만든 뒤 잠근다. 그래서 `migrate`와 재색인 시작이 겹쳐도 새 판이 옛 끝점으로 남지 않는다(먼저 커밋한 쪽이 쓴 것을 뒤의 쪽이 잠근 뒤에 읽는다).
- [정함] 지식베이스에 현재 판이 아직 없으면(설치 직후) 검색은 빈 결과를 낸다. 첫 색인 판은 `migrate`의 기본 레코드 보장이 기본 지식베이스에 `current`로 만든다(조각 0개). 그래서 첫 문서의 작업이 바로 `current` 판에 들어간다.

### 파싱의 격리와 자원 한도

- [정함] 파싱은 작업자 프로세스가 아니라 spawn한 자식 프로세스에서 한다. 자식은 파서 이름, 원본의 경로, 한도를 받고 파싱 결과를 돌려준다. 자식이 `RAG_PARSE_TIMEOUT_SECONDS` 안에 끝나지 않으면 죽이고 `parse_timeout`, 자식이 메모리 한도로 죽거나 `MemoryError`를 내면 `parse_memory_exceeded`, 파서가 예외를 내면 `parse_failed`다. 메모리 한도는 리눅스에서 `RLIMIT_AS`(`RAG_PARSE_MEMORY_MB`)로 걸고, Windows(개발 기계)에서는 걸지 않고 그 사실을 로그에 남긴다. 컨테이너는 리눅스다.
- [정함] ZIP 컨테이너(DOCX, HWPX)는 파싱 전에 부모가 목록만 읽어 검사한다. 항목 4096개 초과, 압축 해제 합계 `RAG_PARSE_MAX_UNZIPPED_MB` 초과, 압축된 크기가 1MiB를 넘는 항목의 압축비 `RAG_PARSE_MAX_COMPRESSION_RATIO` 초과는 `compressed_too_large`, 암호화된 항목은 `encrypted_document`다. PDF는 암호가 걸려 있으면 `encrypted_document`, 쪽 수가 `RAG_PARSE_MAX_PAGES`를 넘으면 `too_many_pages`다. 뽑은 글이 `RAG_PARSE_MAX_TEXT_MB`(UTF-8 바이트)를 넘으면 `document_too_large`다.
- [거절] 표 칸 수의 한도는 두지 않는다. 쪽 수, 시간, 메모리, 글 크기의 한도가 표도 덮는다.
- [정함] 한도 값의 근거. 라이브러리 셋에 내장 한도가 거의 없다는 것을 프로브 `parsers/limits_probe.py`(출력 `limits_probe_out.txt`)로 쟀다. pdfplumber 0.11.10과 pdfminer.six 20260107에는 쪽 수 인자(`maxpages`) 말고 시간·메모리·크기 한도가 없고, python-docx 1.2.0은 lxml 파서에 `remove_blank_text=True, resolve_entities=False`만 주고(`huge_tree`는 주지 않아 lxml 기본값 그대로다) ZIP 한도가 없으며, python-hwpx 6.11.0은 읽기 경로의 `opc/xml_utils.py`에서 `resolve_entities=False, no_network=True, huge_tree=False`를 주고 `opc/security.py`에 ZIP 한도 상수(항목 4096, 항목당 128MiB, 합계 512MiB, 압축비 1000. 출력의 `zip_limit_values` 절)를 가진다. 다만 python-hwpx에는 기본 파서로 `etree.fromstring`·`etree.parse`를 부르는 자리도 25곳 있고(출력의 `xml_default` 절. `oxml/schema.py`의 `XMLParser()`는 옵션이 없다) 그 가운데 어느 것이 HWPX 읽기 경로에 드는지는 재지 않았다. 그래서 python-hwpx의 한도에도 기대지 않는다. 그래서 한도는 우리가 바깥에서 두고, python-hwpx의 값과 겹치는 것은 우리 것이 먼저 걸리게 같거나 엄격하게 잡았다(합계 512MiB는 같고 압축비는 100). 1000쪽, 300초, 2GiB, 64MiB는 어림이고 설정이라 티켓이 바꿀 수 있다.
- [정함] 파서 인터페이스는 `interface_version` `"1.0.0"`의 Protocol이다(판의 규칙은 원칙 VII. 메서드나 칸을 더하면 minor, 지우거나 뜻을 바꾸면 major). 받는 MIME 목록, 그리고 원본 바이트, MIME, 한도 값 객체(지금은 쪽 수 상한 `max_pages` 하나)를 받아 파싱 결과(블록 목록)를 내는 메서드 하나다. 파서가 알리는 실패는 인터페이스가 정한 예외 둘(암호 문서 → `encrypted_document`, 쪽 수 초과 → `too_many_pages`)이고, 그 밖의 예외는 모두 `parse_failed`다. 글 크기(`document_too_large`)는 파서가 아니라 자식 프로세스의 실행기가 파싱 결과를 받은 뒤 보고, 같은 자리에서 블록 글의 U+0000을 지운다. 자식 프로세스에서 돌므로 파서는 상태를 들지 않는다. entry point 그룹 `rag_engine.parsers`에 등록하고 major가 다르면 거부하고 기록한다(ADR 0012).
- [넘겨받음] 내장 파서는 pdfplumber(PDF), python-docx(DOCX), python-hwpx(HWPX)다. 스캔본 OCR과 HWP 5.0 바이너리는 다음 판이다(tech.md 파서 칸, hwp-binary).
- [정함] 파서가 내는 블록의 최소 규칙. PDF는 쪽마다 글을 줄 단위로 읽어 빈 줄로 문단을 가르고 표는 pdfplumber의 표 추출로 표 블록을 내며 쪽 번호를 붙인다. DOCX는 제목 스타일을 제목 블록(수준 포함)으로, 문단을 문단 블록으로, 표를 표 블록으로 내고 쪽 번호는 없다. HWPX는 문단과 표를 같은 식으로 내고 제목은 개요 수준이 있는 문단을 제목으로 삼으며 쪽 번호는 없다. 글이 하나도 없는 문서(스캔본)는 `parsed`이되 조각이 0개다.

### 청킹과 토큰 세기

- [넘겨받음] 청킹은 `Chunker` 포트 뒤의 전략이고 첫 판은 구조 우선 하나다. 파서가 준 제목·문단·표 경계를 우선하고, 넘치면 문장 경계에서 나누며, 조각 사이에 겹침을 둔다. 상한은 토큰 수로 재고 임베딩 서버의 `/tokenize`로 센다. 기본 512·64 토큰은 어림이고 search-eval이 정한다(ADR 0010).
- [정함] 구조 우선 전략의 규칙 일곱. 첫째, 블록을 순서대로 걸으며 제목 블록으로 절 경로를 유지하고, 제목 블록은 조각이 되지 않고 다음 조각의 절 경로가 된다. 둘째, 같은 절의 블록을 모아 다음 블록을 더하면 임베딩에 보내는 글(아래 문단. 절 경로 줄까지)이 상한을 넘는 지점에서 조각을 닫는다. 셋째, 블록 하나가 상한을 넘으면 문장 경계(kiwipiepy의 문장 분리)에서 나누고, 문장 하나가 넘으면 토큰 경계에서 나눈다. 넷째, 표 블록은 행 단위로 나누고 나뉜 조각마다 머리 행을 되풀이한다(머리 행과 한 행이 상한을 넘으면 그 행은 토큰 경계에서 나누고, 그 조각에는 머리 행이 없다. 그래서 어느 조각에도 머리 행이 들지 못했으면 머리 행만 담은 조각을 맨 앞에 둔다). 다섯째, 겹침은 같은 절 안에서만 두고 앞 조각의 끝 문장들을 겹침 토큰 수 안에서 통째로 가져온다. 여섯째, 절의 마지막 조각이 상한의 10% 아래면 앞 조각에 합친다(합쳐도 상한 안일 때). 일곱째, 절 경로 줄은 상한의 4분의 1 안에 둔다. 넘치면 바깥 제목부터 뺀다. 제목 블록 하나의 글이 그 4분의 1을 넘으면 제목으로 보지 않고 문단 블록으로 다룬다(절 경로에 들지 않고 조각 글이 된다). 그래서 안쪽 제목 하나는 늘 들어가고, 어떤 조각도 절 경로만으로 상한을 넘지 않는다. 절 경로가 비면 절 경로 줄과 빈 줄을 넣지 않는다. `location.section`은 뺀 제목까지 든 온전한 절 경로다. 새 오류 코드는 없다.
- [정함] 임베딩과 키워드에 넣는 글은 절 경로를 ` > `로 이은 한 줄(위 일곱째 규칙대로 줄인 것)과 빈 줄 뒤의 조각 글이다. 이 글은 함수 하나가 짓고 임베딩, 키워드, 리랭크의 `texts`가 모두 그 글을 쓴다. 검색 결과의 `text`는 조각 글만이고 절 경로는 `location.section`에 따로 싣는다. 절 경로가 임베딩에 들어야 "제3조 정의"처럼 제목에만 있는 말로도 찾는다. 상한은 이 글 전체(절 경로 줄, 빈 줄, 조각 글)의 토큰 수에 모델의 특수 토큰 수를 더한 값으로 잰다. TEI는 임베딩 요청의 글에 특수 토큰을 붙여 센 길이를 `max_input_length`와 비교하므로(`core/src/tokenization.rs`의 `encode_input`이 `tokenize_input`에 `true`를 넘기고 `seq_len > max_input_length`면 거부한다. 프로브 `facts/tei_tokenization_facts.py`, 소스 389·399행) 조각 글만 상한 안이어도 거부될 수 있다. 특수 토큰 수는 끝점마다 첫 호출 전에 짧은 글 하나를 `add_special_tokens`를 켜고 끄고 두 번 `/tokenize`해 그 차로 센다(빈 문자열은 TEI가 거부한다. 같은 프로브의 `tokenize` 문맥).
- [정함] 근거 위치는 조각이 덮는 블록들에서 만든다. `page`는 첫 블록의 쪽 번호(1부터. 없으면 null), `section`은 절 경로의 제목 글 배열(바깥에서 안쪽 순. 절이 없으면 빈 배열), `block_kind`는 첫 블록의 종류, `block_range`는 덮은 블록 순번의 처음과 끝 `[first, last]`(0부터, 양 끝 포함)다. 표를 행으로 나눈 조각은 `block_kind`가 `table`이고 `block_range`가 같은 블록을 가리킨다.
- [정함] 토큰 수는 `/tokenize`에 `add_special_tokens: false`로 문자열 배열을 보내 센다(특수 토큰이 없어 `start`·`stop`이 null인 토큰이 나오지 않는다). 토큰 경계로 나눠야 할 때는 UTF-8 바이트 오프셋을 글자 인덱스로 바꾼다. 글자마다 UTF-8 바이트 길이의 누적 합 배열을 만들고 이분 탐색으로 바이트 오프셋을 글자 인덱스로 옮긴다. 바이트 오프셋이 글자 중간에 떨어지면 그 글자의 앞 경계로 내린다. ADR 0010이 명세에 맡긴 변환이다. `/tokenize`의 입력이 문자열 배열을 받는 것은 프로브 `facts/tei_info_and_rerank_fields.py`로 봤다(`TokenizeInput`이 문자열 또는 문자열 배열).
- [정함] 토큰 세기는 상한 안인지 가리는 데만 쓰고, 상한 안의 조각은 다시 세지 않는다. 호출은 `RAG_TEI_BATCH_SIZE`개씩 묶는다.

### 임베딩 서버와 리랭커 어댑터

- [넘겨받음] 임베딩은 `/v1/embeddings`, 토큰 세기는 `/tokenize`, 리랭크는 `/rerank`이고 모두 TEI 1.9.4 형식이다. 컨테이너 하나가 모델 하나를 들고 지식베이스 설정에 끝점·모델·차원이 있다(ADR 0010).
- [정함] 어댑터는 끝점마다 첫 호출 전에 `/info`를 읽어 `model_id`(또는 `served_model_name`)가 부르는 쪽이 넘긴 모델(임베딩이면 그 색인 판에 적힌 모델, 리랭커면 지식베이스 설정의 모델)과 같은지, `max_input_length`가 조각 상한 이상인지 확인하고 `auto_truncate` 값을 로그에 남긴다. 다르면 그 끝점은 "설정 불일치"이고 검색은 `search_unavailable`, 작업은 일시 실패(`embedding_unavailable`)다. 운영자가 고칠 설정 문제라 영구 실패로 두지 않는다. `/info`의 칸은 프로브 `facts/tei_info_and_rerank_fields.py`로 봤다(`model_id`, `served_model_name`, `model_type`, `max_input_length`, `auto_truncate`가 필수 칸).
- [정함] 임베딩 호출은 `input`에 문자열 배열(`RAG_TEI_BATCH_SIZE`개씩), `model`에 모델 이름을 싣고 `data[i].embedding`을 순서대로 받는다. 벡터 길이가 설정 차원과 다르면 `embedding_dimension_mismatch`다. 응답 코드 400·413·422는 `embedding_rejected`(영구), 424·429와 연결 실패·`RAG_TEI_TIMEOUT_SECONDS` 초과는 `embedding_unavailable`(일시)이다. OpenAPI가 적은 응답 코드는 이 다섯이고(같은 프로브의 출력), 거기 없는 5xx(프록시나 서버 오류)도 일시로 다룬다.
- [정함] 리랭크 호출은 `query`, `texts`(후보의 글. 절 경로 포함), `truncate: true`, `truncation_direction: "Right"`(`TruncationDirection`의 열거 값은 `Left`·`Right` 둘이고 기본은 `Right`다. 프로브 `facts/tei_info_and_rerank_fields.py`), `raw_scores: false`, `return_text: false`를 보내고 `index`와 `score` 배열을 받는다. 실패하면 검색은 리랭크 없이 RRF 점수로 응답하지 않고 `search_unavailable`을 낸다. 조용히 품질이 바뀐 결과를 내지 않기 위해서다.
- [거절] 리랭크 실패 때 RRF 순서로 대체 응답은 하지 않는다.
- [정함] TEI 응답의 토큰 오프셋(`start`·`stop`)은 입력의 UTF-8 바이트 오프셋이고 특수 토큰은 null이다(ADR 0010). 어댑터의 글자 인덱스 변환은 위 청킹 절의 규칙이다.

### 키워드 토큰

- [넘겨받음] 한국어 형태소 분석은 앱의 kiwipiepy가 하고 토큰을 `to_tsvector('simple', …)`에 넣어 GIN 색인을 걸며 질의도 같은 토크나이저로 자른다(ADR 0006. 토크나이저를 바꾼 뒤 재색인이 전환되기 전까지의 예외는 데이터 모델과 스키마 절의 색인 판 요소 항목). Kiwi는 py.typed가 없어 우리 스텁을 둔다.
- [정함] 키워드로 넣는 토큰은 품사 태그가 일반 명사 `NNG`, 고유 명사 `NNP`, 수사 `NR`, 외국어 `SL`, 한자 `SH`, 숫자 `SN`, 어근 `XR`인 토큰과, Kiwi가 한 덩이로 내는 웹 형식 토큰(`W_URL`, `W_EMAIL`, `W_HASHTAG`, `W_SERIAL`)이다. 외국어 토큰은 소문자로 바꾼다. 동사·형용사 어간, 조사, 어미, 의존 명사, 대명사, 기호는 넣지 않는다. 프로브 `kiwi/probe.py`(출력 `probe_out.txt`)로 표본 넷의 토큰을 봤다. "지식베이스"는 `지식/NNG 베이스/NNG`로 갈리고 질의도 같이 갈리므로 맞는다. `normalize_coda`를 켠다. 이 규칙의 판은 1이고 토크나이저 판의 일부다.
- [정함] Kiwi에 넣기 전에 라틴 글자·숫자 뒤에 붙은 ASCII 문장 부호(`.,;:!?`)를 공백으로 뗀다. 다만 뒤가 라틴 글자·숫자·`/`로 이어지면 낱말 안의 부호나 웹 주소의 일부라 그대로 둔다(`0.8.7`, `https://`. 구현 티켓 core 06이 `https://example.com`의 콜론이 떼여 주소가 갈리는 것을 보고 더했다). 프로브에서 영어 문장 끝의 `search.`가 `s/SL earch./SL`로 갈렸고, 마침표를 공백으로 뗀 다섯째 표본은 `search/SL ./SF`로 바로 섰다(`kiwi/probe_out.txt`). 전처리는 토크나이저 규칙의 일부라 바꾸면 판을 올린다.
- [정함] 조각의 tsvector는 선택한 토큰을 공백으로 이어 `to_tsvector('simple', …)`에 넣어 만든다. 질의는 같은 규칙으로 토큰을 뽑아 OR로 이은 `to_tsquery('simple', …)`이고(토큰이 하나도 없으면 키워드 검색을 건너뛴다), 순위는 `ts_rank_cd`다. 문장 분리(청킹의 문장 경계)는 kiwipiepy의 문장 분리를 쓴다.

### 검색 흐름

- [정함] `search`의 처리는 일곱 단계다. 첫째, 지식베이스를 고른다(인자가 없으면 기본 지식베이스. 없거나 토큰 범위 밖이면 `knowledge_base_not_found`. 범위 밖 지식베이스의 존재를 드러내지 않는다. User Stories 27). 둘째, 현재 색인 판이 없으면 빈 결과를 낸다. 셋째, 질의를 현재 판에 적힌 끝점·모델·차원으로 임베딩하고 키워드 토큰을 뽑는다(둘은 병렬). 지식베이스 설정이 아니라 판의 것을 쓰는 까닭은 재색인 중 설정은 새 모델인데 현재 판의 벡터는 옛 모델이라서다. 넷째, SQL 하나로 후보를 모은다. 그 SQL은 같은 문장에서 둘째 단계가 읽은 판이 아직 `current`인지도 읽는다. 그사이 판이 전환되어 아니면 결과를 버리고 둘째 단계부터 한 번 다시 하고(새 현재 판의 끝점·모델로 다시 임베딩한다), 다시 해도 아니면 `search_unavailable`이다. 벡터 쪽은 현재 판의 조각에서 코사인 거리 순 `RAG_SEARCH_CANDIDATES`개, 키워드 쪽은 같은 조각에서 `ts_rank_cd` 순 같은 수이고, 둘을 바깥 조인해 RRF(`1/(60+순위)`의 합)로 합쳐 후보 수만큼 자른다. 필터(그룹, 갱신일 기간)는 두 쪽의 `WHERE`에 같이 든다. 두 쪽의 `WHERE`에는 조각에 복사한 그룹이 그 지식베이스의 그룹 집합에 드는 조건도 늘 든다. v0에는 지식베이스의 그룹 집합을 고치는 길이 없고(admin이 받는다), 그룹을 바꾸는 수집이 같은 작업 단위에서 문서가 빠지는 지식베이스의 조각을 지우므로(수집 API 절) 넷째 단계는 그 문장의 시점에 `current`인 판만 읽으므로 이 조건이 실제로 거르는 조각은 없다. 이 조건은 볼 수 없는 문서의 조각을 내지 않는다(원칙 V)는 것을 검색 SQL에서도 지키는 방어 조건이고, 아래 `iterative_scan`을 켜는 필터로 세지 않는다. 다섯째, 지식베이스에 리랭커가 있으면 후보 전부를 `RAG_TEI_BATCH_SIZE`개씩 나눠 리랭크하고 점수를 합쳐 점수 순으로 바꾼다(점수는 질의와 글의 쌍마다 독립이라 묶음을 나눠도 같다). 여섯째, `top_k`개를 자르고 결과를 만든다. 일곱째, 지연을 기록한다. 전체가 `RAG_SEARCH_TIMEOUT_SECONDS`를 넘으면 `search_unavailable`이다. 결과는 넷째 단계의 SQL이 본 시점의 상태이고, 토큰의 인증과 범위는 요청을 받을 때 판정한다. 그 뒤에 커밋된 삭제와 그룹 변경은 그 요청의 결과에 들지 않는다. 리랭크 뒤에 다시 확인해도 확인과 응답 사이의 틈은 남으므로, 볼 수 없는 문서의 조각을 내지 않는다(원칙 V)는 넷째 단계의 시점에서 지킨다. 그 시점에 결과의 문서는 지워지지 않았고 그 지식베이스의 그룹에 들었다(삭제는 같은 작업 단위에서 모든 판의 조각을 보관 표로 옮기고, 그룹 변경은 살아 있는 판의 조각을 지우며, 넷째 단계는 그 시점의 현재 판만 읽는다).
- [정함] 벡터 쪽 SQL은 트랜잭션 안에서 `SET LOCAL hnsw.ef_search`를 후보 수로 두고, 필터가 있으면 `SET LOCAL hnsw.iterative_scan = relaxed_order`를 더한다. 기본 `ef_search` 40은 후보 50개를 채우지 못한다(pgvector README 935행, 프로브 `facts/pgvector_readme_facts.py`).
- [정함] 검색 SQL은 판의 부분 HNSW 색인을 일반 계획에서도 타도록, 판의 UUID와 차원을 매개변수가 아니라 문장 안의 리터럴로 적는다(`vector_index.py`의 `search_sql`). 부분 색인의 술어(`index_version_id = '<UUID>'`)와 색인의 식 `embedding::vector(D)`가 계획 시점에 상수여야 색인이 맞기 때문이다. 질의 벡터와 후보 수와 키워드는 매개변수로 남는다. UUID와 정수는 서버가 만든 값이라 문장에 적어도 주입 위험이 없다(질의 글은 문장에 들지 않는다). 어댑터 시험이 `explain_search_generic`(`plan_cache_mode = force_generic_plan`)로 그 계획이 색인 스캔을 고르는 것을 고정한다(`tests/adapters/test_vector_index_chunks.py`).
- [거절] 좁은 필터에서 정확 스캔으로 바꾸는 분기는 두지 않는다. 그 필요는 search-eval의 보고서가 잰 뒤에 정한다.
- [정함] 점수 `score`는 리랭커가 있으면 리랭크 점수, 없으면 RRF 점수다. `rank`는 1부터다. 같은 문서의 조각 여럿이 나와도 합치지 않는다(클라이언트의 몫).

### MCP 도구

- [넘겨받음] MCP로 여는 도구는 `search`, `get_document`, `list_knowledge_bases` 셋뿐이고 이름은 고정이다. 결과 객체에 `format_version`(semver 문자열)이 실리고 형식은 outputSchema로 공개한다(ADR 0001, 0008, 0015). 도구마다 읽기 전용 표지를 단다(`.claude/rules/server.md`).
- [정함] 첫 판의 `format_version`은 `"1.0.0"`이다. 도구 주석은 읽기 전용, 파괴적이지 않음, 멱등, 열린 세계 아님이다. 출력 스키마는 pydantic 모델에서 나오고 계약 시험이 스키마와 판을 본다.
- [정함] `search`의 입력은 `query`(문자열, 비어 있으면 `invalid_argument`), `top_k`(정수, 기본 `RAG_SEARCH_DEFAULT_TOP_K`, 1 이상 `RAG_SEARCH_MAX_TOP_K` 이하), `knowledge_base`(이름, 선택), `filter`(선택. `groups` 그룹 이름 배열, `updated_after`·`updated_before` 오프셋이 붙은 ISO 8601 날짜·시각)다. `updated_after`는 그 시각을 포함하고 `updated_before`는 포함하지 않는다. 오프셋이 없거나 읽을 수 없는 시각은 `invalid_argument`다. `groups`에 없는 그룹 이름이 들어도 오류가 아니고 그 이름은 아무 문서에도 맞지 않는다(그룹의 존재를 드러내지 않는다). 출력은 `format_version`, `knowledge_base`(쓴 지식베이스 이름), `results` 배열이다. 결과 하나는 `chunk_id`, `document_id`, `source`(원천 이름), `key`, `title`, `text`, `location`(`page`, `section`, `block_kind`, `block_range`), `updated_at`, `effective_date`(지금은 null), `access_groups`(지금은 빈 배열), `metadata`(문서의 메타데이터), `score`, `rank`다. 킥오프 입력 2절의 칸(조각, 경로·쪽·위치, 갱신일, 점수, 시행일·접근 그룹 칸)을 모두 덮는다.
- [정함] `get_document`의 입력은 `document_id`와 `include_text`(기본 false)이고, 출력은 `format_version`, `document_id`, `source`, `key`, `title`, `group`, `mime`, `size_bytes`, `updated_at`, `metadata`, `chunk_counts`(토큰 범위 안의 지식베이스 이름마다 조각 수. 범위 밖 지식베이스는 이름도 내지 않는다. `list_knowledge_bases`와 같은 규칙), 그리고 `include_text`면 파싱 결과의 블록 글을 빈 줄로 이은 `text`다. 파싱 결과가 없거나 그 파싱한 내용 해시가 문서의 내용 해시와 다르면(새 내용이 아직 파싱되지 않았다) `text`는 null이다. 옛 파싱 결과를 내면 원천의 지금 내용이 아닌 글을 내고(원칙 VI), 그룹을 바꾼 문서면 옛 그룹의 지식베이스에서만 볼 수 있던 글을 새 그룹의 토큰에 낸다(원칙 V). 지워진 문서와 토큰 범위 밖 지식베이스에만 든 문서는 `document_not_found`다.
- [정함] `list_knowledge_bases`는 입력이 없고 출력은 `format_version`과 `knowledge_bases` 배열(`name`, `description`, `document_count`, `is_default`)이다. `document_count`는 그 지식베이스의 그룹 집합에 드는 그룹의, 지워지지 않은 문서 수다(색인 상태와 상관없다). 토큰 범위 밖은 목록에서 뺀다.
- [정함] 도구 오류는 `isError`가 참인 결과이고 글 내용 하나가 Problem Details와 같은 모양의 JSON 문자열(`type`, `title`, `status`, `code`, `request_id`)이다. 코드는 `knowledge_base_not_found`, `document_not_found`, `invalid_argument`, `search_unavailable`, `internal_error`다. 인증 실패는 도구에 닿기 전에 미들웨어가 401로 낸다(인증과 권한 절). `detail`에 질의나 문서 내용을 넣지 않는다(ADR 0015).
- [정함] 도구 처리기는 미들웨어가 판정한 인증 결과를 읽는다. 미들웨어가 토큰 레코드를 ASGI scope에 두고, 도구는 SDK의 Context(`ctx.request_context.request.scope`)로 그 값에 닿는다. 티켓 세션이 프로브 `mcp-sdk/probe_scope.py`와 `mcp-sdk/probe_scope_legacy.py`(출력 `*_out.txt`)로 쟀다. 전송 모드 셋(세션 없음 + SSE, 세션 없음 + JSON, 세션 유지 + SSE)과 2025-06-18 프로토콜의 레거시 initialize 길에서 모두 도구가 scope의 최상위 키와 `scope["state"]`의 키를 읽었다.

### 인증과 권한

- [넘겨받음] 토큰은 데이터베이스에 두고 관리 API로 발급·회수하며, 원문은 발급 응답에 한 번만 나오고 저장은 해시다. 판정은 FastAPI 앱 바깥의 ASGI 미들웨어가 REST와 `/mcp` 둘 다에서 베어러 토큰을 보고 401과 403을 낸다. `RAG_ALLOWED_HOSTS`는 필수이고 불일치는 421이다(ADR 0014).
- [정함] 토큰 원문은 `rag_` 접두와 32바이트 난수의 URL 안전 base64다. 역할은 `admin`(REST와 MCP 전부)과 `reader`(MCP와 `/health`만)다. `reader`가 REST를 부르면 403 `forbidden`이다. 지식베이스 범위는 `reader`에만 뜻이 있고 `admin` 토큰에 범위를 주면 422다. 토큰이 없거나 모르는 해시면 401 `unauthenticated`, 회수됐으면 401 `unauthenticated`(회수 사실을 드러내지 않는다), 만료됐으면 401 `token_expired`다. `/health`만 인증 밖이다. 허용 호스트 판정(421)은 MCP SDK의 전송 보안이 `/mcp`에서만 하고, REST 경로는 Host를 보지 않는다.
- [정함] `bootstrap-token [--name 이름]`(기본 `bootstrap`)은 살아 있는(회수·만료되지 않은) `admin` 토큰이 하나도 없을 때만 발급하고, 있으면 종료 코드 1과 안내를 낸다. 잃어버린 토큰은 데이터베이스에서 회수 시각을 적고 다시 돌리는 것이 운영 절차다.

### 관리 API

- [사용자 선택] core의 관리 API는 최소다. 토큰 발급·목록·회수, 지식베이스 목록·조회(재색인 필요 표시)와 재색인 시작, 작업 조회, 문서 조회다. 그룹·지식베이스·원천의 생성·수정·삭제는 admin과 source-sync가 받는다(Out of Scope). 사용자가 2026-11-10에 세 선택지(최소 관리 API를 core에, 수집·검색만, 관리 API를 넓게) 가운데 골랐다. 고른 선택지의 설명은 원천의 생성·수정·삭제도 admin으로 넘긴다고 적었지만, 이 명세는 그것을 source-sync로 보낸다. 원천 종류(서버 경로, 커넥터)와 연결 정보를 짓는 기능이 source-sync이고 admin 계획은 core와 source-sync의 관리 API 위에 선다고 적혀 있기 때문이다(`.scratch/admin/plan.md`).
- [정함] 끝점은 `/api/v1/admin` 아래 열이다. `GET /knowledge-bases`(이름, 설명, 문서 수, 현재 색인 판 요약, `reindex_needed`, 건설 중인 판의 진행), `GET /knowledge-bases/{name}`(위에 색인 판 목록과 설정), `POST /knowledge-bases/{name}/reindex`(202, 409 `reindex_in_progress`), `GET /jobs/{job_id}`(작업 행과 함께 그 문서의 결과(문서 조회와 같은 상태, 오류 코드, 지식베이스마다의 색인 상태)와 같은 문서에 대기·실행 중인 작업이 남았는지를 낸다. 작업의 상태는 문서의 결과가 아니어서(수집 파이프라인 절의 넷째 단계) 작업 ID로 수집이 끝났는지와 실패한 까닭은 이 둘로 본다), `GET /jobs?status=&limit=&after=`(최근 순, 커서는 마지막 작업 ID), `GET /documents/{document_id}`(상태, 오류 코드, 지식베이스마다의 색인 상태와 조각 수, 메타데이터), `GET /documents?status=&group=&key=&limit=&after=`(`key`는 그 키의 문서 하나를 찾는 필터), `POST /tokens`(201. 이름, 역할, 지식베이스 이름 배열(선택), 만료 시각(선택. 지난 시각이면 422)을 받고 원문을 한 번 돌려준다), `GET /tokens`(원문 없음), `DELETE /tokens/{id}`(204, 회수). 모두 `admin` 역할이다. 커서 페이지는 UUIDv7이 시간순이라 ID 비교로 한다.
- [넘겨받음] 에러 봉투는 RFC 9457 Problem Details에 `code`를 더한 모양이고 FastAPI의 422도 같은 모양이다(ADR 0015).
- [정함] Problem Details의 칸은 `type`(`about:blank`), `title`, `status`, `code`, `request_id`, 선택 `detail`이다. 422는 `code: validation_error`에 `errors` 배열(`loc`, `type`, `msg`. 입력 값 `input`과 `ctx`는 싣지 않는다)을 더한다. 미디어 타입은 `application/problem+json`이다. 코드 목록은 `unauthenticated`, `token_expired`, `forbidden`, `validation_error`, `document_not_found`, `knowledge_base_not_found`, `group_not_found`, `job_not_found`, `token_not_found`, `upload_too_large`, `unsupported_media_type`, `reindex_in_progress`, `search_unavailable`, `internal_error`다. 코드마다 HTTP 상태가 하나이고 원천은 `src/rag_engine/server/problems.py`의 `ERROR_STATUS`다(`search_unavailable` 503, `internal_error` 500, `invalid_argument`와 `validation_error` 422. 계약 티켓 02가 정했고 나머지는 코드 이름의 뜻대로 401·403·404·409·413·415다).
- [정함] `/health`는 인증 없이 `{"status": "ok"}`만 낸다(지금의 모양 그대로). 데이터베이스나 임베딩 서버를 보지 않는 생존 확인이고, 준비 확인은 두지 않는다.

### 관리 명령

- [넘겨받음] 관리 명령은 `serve`, `worker`, `migrate`, `bootstrap-token`, `ingest <경로> [--wait]` 다섯이다. 명령은 REST와 같은 app 층 유스케이스를 부르고 같은 연결 문자열로 데이터베이스에 직접 붙는다(tech.md 관리 명령 칸, 일지 결정 요약 22). `migrate`가 `alembic upgrade head`를 돌리고 서버는 기동 때 자동으로 돌리지 않는다(ADR 0011).
- [정함] `migrate`는 마이그레이션 뒤 기본 레코드를 보장한다. 기본 원천 `default`(종류 `push`), 기본 그룹 `default`, 기본 지식베이스 `default`(설정의 `RAG_DEFAULT_*`로. 이미 있으면 설정값으로 고친다)와 그 지식베이스에 기본 그룹을 넣고, 현재 색인 판이 없으면 첫 판을 `current`로 만든다. 멱등이다. 설정이 바뀐 뒤 다시 돌리면 지식베이스의 설정이 바뀌어 "재색인 필요"가 된다. 살아 있는 판(현재 판과 건설 중인 판) 가운데 임베딩 모델·차원이 설정과 같고 끝점만 다른 판은 끝점도 같이 고친다(같은 모델이 다른 주소로 옮긴 것이라 재색인이 아니다). 건설 중인 판도 고쳐야, 옛 주소를 내린 뒤 그 판의 작업과 전환 뒤의 검색이 옛 주소를 부르지 않는다. 차원이 2,000을 넘으면 설정 오류로 종료 코드 1이고 지식베이스 행을 만들지도 고치지도 않는다. 그것이 테스트가 재색인을 일으키는 길이다.
- [정함] `ingest <경로> [--group 이름] [--wait] [--timeout 초]`는 파일 하나나 폴더를 받는다. 폴더면 지원 확장자의 파일을 재귀로 걷고 키는 폴더 기준 상대 경로(POSIX 구분자)다. `--group`이 없는 그룹 이름이면 아무 파일도 넣지 않고 종료 코드 1이다. 파일마다 수집 유스케이스를 직접 불러 `action`을 한 줄씩 찍는다. `--wait`면 넣은 파일의 문서마다(응답의 `document_id`. 작업이 없는 `unchanged`·`restored`도 든다. 앞서 넣은 작업이 아직 돌 수 있다) 그 문서의 대기·실행 중 작업이 없어질 때까지 폴링하고(작업자가 따로 떠 있어야 한다. 안내를 찍는다), 그때 색인이 실패한 문서(문서 상태가 `failed`이거나 살아 있는 판의 색인 상태에 `failed`가 있다. 수집 API 절의 `requeued` 조건과 같다)가 하나라도 있으면 종료 코드 1이다(관리 API의 작업 조회와 같은 판정이다). 넣은 작업의 상태로 판정하지 않는 까닭은 작업의 상태가 문서의 결과가 아니어서다(수집 파이프라인 절의 넷째 단계). 넣은 작업이 세대 대조에 걸려 쓰지 않고 `succeeded`로 끝나도 같은 문서의 뒤 작업이 실패할 수 있고, 거꾸로 `failed`로 끝나도 뒤 작업이 문서를 색인할 수 있다. 그사이 지워진 문서는 실패로 세지 않는다. `--timeout`(기본 0, 무한)이 지나면 종료 코드 2다.
- [정함] `worker`는 작업자 프로세스를 띄운다. 인자는 없고 설정만 읽는다. `serve`는 지금의 `--host`·`--port`를 유지한다.

### 삭제, 되살림, 묘비

- [넘겨받음] 삭제는 소프트 삭제다. `deleted_at`을 적고 조각을 보관 표로 옮겨 검색 표에는 산 것만 남기며, 보관 기간 뒤 정리 작업이 물리 삭제하고 묘비 행만 남긴다(ADR 0013).
- [정함] 삭제 요청의 작업 단위는 문서 행과 그 그룹이 든 지식베이스 행을 잠그고(수집 파이프라인 절의 잠금 규칙) `deleted_at`을 쓰고, 모든 색인 판의 조각을 `archived_chunks`로 옮기고, 그 문서의 색인 상태 행을 모두 지우고(건설 중인 판의 진행 셈에서 빠진다), 그 문서의 대기 작업을 지우며, 그 문서가 든 지식베이스에 `building` 판이 있으면 위의 전환 검사를 한다(완료할 작업이 없는 `pending`이 판을 막지 않는다). 실행 중인 작업은 첫 단계에서 지워진 문서를 보면 성공으로 끝나고, 그 뒤에 지워졌으면 셋째 단계의 다시 읽기가 잡는다.
- [정함] 되살림은 같은 (원천, 키)가 `deleted_at`은 있고 `purged_at`은 없는 문서로 다시 들어올 때다(ADR 0013이 어림으로 적은 방향 그대로). 같은 작업 단위에서 `deleted_at`을 비우고 그룹을 요청의 그룹으로 쓴다. 대상 판은 그 그룹이 든 지식베이스의 살아 있는 판이다. 내용 해시가 같으면 보관 표의 조각 가운데 대상 판의 것이면서 만든 내용 해시가 문서의 내용 해시와 같은 것을 검색 표로 되돌리되 복사 칸(그룹, 갱신일, 시행일, 접근 그룹)은 문서 행의 지금 값으로 쓰고, 그 판마다 색인 상태 `indexed`를 다시 쓰며, 나머지(물러난 판의 것, 그룹이 바뀌어 대상이 아닌 판의 것, 다른 내용으로 만든 것)는 지우고 `action`은 `restored`다. 되돌릴 조각이 없는 대상 판(삭제와 되살림 사이에 판이 바뀌었거나, 그룹이 바뀌었거나, 삭제 전에 갱신한 내용이 아직 색인되지 않았던 판)이 있으면 작업을 넣고(`job_id`가 실린다) 그 판이 건설 중인 판이 아니면 색인 상태 `pending`을 쓴다(건설 중인 판에 쓰지 않는 까닭은 재색인 시작 항목에 있다). 내용 해시가 다르면 보관 표의 조각을 지우고 갱신으로 간다(`restored`에 작업 ID). 문서 UUID는 그대로다.
- [정함] 묘비 행(`purged_at`이 있는 문서)과 같은 (원천, 키)가 다시 오면 그 행을 다시 써서 UUID를 잇고 `action`은 `created`다. 묘비는 "있었다"는 표시이지 새 문서를 막는 장치가 아니다. `GLOSSARY.md` 묘비 항목을 이에 맞춰 고쳤다.
- [거절] 정리 작업(보관 기간이 지난 문서의 물리 삭제)과 되살리는 관리 API는 core에 없다. core는 설정 이름 `RAG_DELETED_RETENTION_DAYS`와 묘비 행의 모양(`purged_at`)만 정한다.

### 로그, 요청 ID, 지연 기록

- [넘겨받음] 로그는 JSON Lines이고 필드는 `time`, `level`, `logger`, `event`, `request_id`, `duration_ms`이며, 예외는 타입·프레임·이 저장소가 정의한 예외의 메시지만 싣는다. 엔진은 `hide_parameters=True`다. 질문 내용, 연결 정보, 문서 내용은 남기지 않고 검색은 지연만 남긴다(ADR 0004, 0011, 0015, 원칙 V).
- [정함] 요청 ID는 요청마다 서버가 UUIDv7로 만들고 응답 헤더 `X-Request-Id`로 돌려준다. 들어오는 `X-Request-Id`는 믿지 않고 쓰지 않는다(로그 주입을 막는다). 수집 요청이 넣은 작업은 그 요청 ID를 들고, 작업자 로그의 `request_id`는 그 값이다. 관리 명령 `ingest`는 실행마다 UUIDv7 요청 ID 하나를 만들어 그 실행의 로그와 넣은 작업에 쓴다.
- [정함] 로그 이벤트. `http_request`(메서드, 경로 템플릿, 상태 코드, 지연), `search`(임베딩·SQL·리랭크 지연과 전체 지연. 지식베이스 이름, `top_k`, 후보 수, 결과 수는 싣지 않는다. ADR 0004가 검색은 지연만 남긴다고 정했다), `job_started`·`job_finished`(작업 ID, 종류, 문서 ID, 시도 횟수, 결과, 오류 코드, 파싱·임베딩·쓰기 지연). 문서의 키와 제목은 로그에 싣지 않고 문서 ID만 싣는다. 질의 글은 어디에도 싣지 않는다.
- [정함] uvicorn은 `access_log=False`로 띄운다. 접근 로그는 쿼리 문자열이 든 경로(삭제의 `key=`)를 남기고, 같은 요청은 `http_request` 이벤트가 경로 템플릿으로 남긴다. uvicorn과 MCP SDK의 로거는 우리 포매터를 지나게 붙여 다른 모양의 줄이 섞이지 않게 한다.

### 테스트 데이터베이스와 이미지 판

- [넘겨받음] 테스트용 PostgreSQL은 Docker의 `pgvector/pgvector:0.8.7-pg18-trixie`(운영과 같은 판)이고 `RAG_TEST_DATABASE_URL`이 가리키는 데이터베이스를 쓰며 없으면 skip이 아니라 실패한다(tech.md 테스트 칸). 검사 러너가 `compose.test.yml`로 띄우는 변경을 맡는 티켓은 Further Notes의 사용자 선택 항목(core 01)이다. 설계와 tech.md 테스트 칸은 하네스 티켓으로 적었다.
- [정함] 격리는 템플릿 데이터베이스다. 세션 픽스처가 `RAG_TEST_DATABASE_URL`의 서버에 템플릿 데이터베이스를 만들어 alembic을 한 번 올리고 `migrate`의 기본 레코드 보장을 돌린 뒤, 테스트마다 템플릿에서 복제한 새 데이터베이스를 만들어 쓰고 지운다. 그래서 테스트가 서로의 행을 보지 않고 마이그레이션은 세션에 한 번만 돈다. 테스트 역할에는 데이터베이스 생성 권한이 있어야 한다(compose의 기본 역할이 그렇다). Windows 개발 기계에서는 psycopg 비동기를 위해 Selector 이벤트 루프를 테스트 설정이 고른다(ADR 0011).

## Testing Decisions

- [사용자 선택] 주 이음매는 서버의 HTTP 표면이다. REST는 httpx로, MCP는 공식 SDK의 클라이언트로 접속하고, 뒤에는 Docker의 실제 테스트 PostgreSQL과 TEI 스텁 서버를 붙인다. 작업자는 테스트 안에서 한 번 돌기 입구로 돌린다. 보조 이음매는 PostgreSQL 어댑터의 SQL과 파서(픽스처 문서)이고, `app`을 가짜 포트로 시험하는 것은 실제 데이터베이스로 재현하기 어려운 동시성 교차와 실패 분류뿐이다. 사용자가 2026-11-10에 세 선택지(HTTP 표면 + 실제 PG + TEI 스텁, 유스케이스 단위 + 가짜 포트, 전부 실물) 가운데 골랐다. ADR 0007 Consequences의 첫 항목은 이 선택으로 범위가 좁아져 이력과 포인터를 달았다.
- [정함] 좋은 테스트는 바깥에서 보이는 행동만 본다. 수집 API로 넣고 작업자를 한 번 돌린 뒤 MCP `search`로 찾아 결과의 칸을 보는 식이다. 표의 행 수나 내부 함수 호출을 보지 않고, SQL 어댑터 시험도 두 작업자가 같은 작업을 꺼내지 않는다는 식으로 행동을 쓴다. 테스트 이름은 한국어 행동 명세다(`CODING_STANDARDS.md`). 비동기 테스트는 `async def`이고 `RuntimeWarning`은 에러이며 skip은 실패다(`.claude/rules/tests.md`).
- [정함] TEI 스텁은 테스트가 띄우는 작은 ASGI 앱 하나로 임베딩 끝점과 리랭커 끝점 둘을 흉내 낸다. `/info`는 설정한 `model_id`·`max_input_length`·`auto_truncate`·`model_type`을 내고, `/v1/embeddings`는 결정적 벡터(글을 낱말로 갈라 낱말 해시로 정한 차원에 부호를 더한 뒤 정규화한 단어 주머니 벡터. 같은 글은 같은 벡터, 낱말이 겹치면 가까운 벡터)를 내고, `/tokenize`는 낱말과 기호 단위의 토큰에 UTF-8 바이트 오프셋을 붙여 내며 `add_special_tokens`가 참이면 앞뒤에 오프셋이 null인 특수 토큰을 더하고, `/rerank`는 질의와 글의 낱말 집합 겹침으로 점수를 낸다. 스텁은 요청 횟수와 마지막 요청 본문을 기억해 테스트가 배치 크기와 `truncate` 같은 칸을 단언할 수 있게 한다. 선례는 `/v1/embeddings` 하나를 고정 난수 벡터로 흉내 낸 프로브 `embedding/fake_server.py`이고, 스텁은 그것을 끝점 넷과 결정적 벡터로 넓힌다. 실제 모델의 품질은 search-eval의 몫이다.
- [정함] 시험하는 모듈과 주요 사례. 계약 시험(`tests/contract/`): 도구 목록이 셋이고 모두 읽기 전용 표지가 있으며 outputSchema에 `format_version`이 있다, `search`·`get_document`·`list_knowledge_bases`의 결과가 스키마와 판 `"1.0.0"`에 맞는다, 토큰 없는 접속은 401, 허용 호스트 밖은 421, 범위 밖 지식베이스는 `knowledge_base_not_found`. HTTP 시험: 수집 → 작업자 한 번 → 검색의 왕복(PDF, DOCX, HWPX 픽스처 하나씩), `action` 다섯(`created`, `updated`, `unchanged`, `restored`, `requeued`)과 그룹 변경 뒤의 작업, 415·413·404, 원본 경로를 바꾸지 않는 수집(`unchanged`, `requeued`, 그룹만 바뀐 `updated`, 내용 해시가 같은 되살림) 뒤에 새 원본이 남지 않음, 삭제 뒤 검색에서 빠짐, 되살림(판 전환을 사이에 둔 것, 다른 그룹으로 되살린 것, 갱신한 내용이 색인되기 전에 지웠다가 같은 내용으로 되살린 것 포함. 옛 지식베이스의 검색에도, 옛 글로도 나오지 않는다), 그룹을 바꾼 직후 작업 전에도 옛 지식베이스의 검색에 그 문서가 나오지 않음, 내용과 그룹을 바꾼 직후 파싱 전의 `get_document`(`include_text`)가 옛 글 대신 null `text`를 냄, 재색인 중 지운 문서가 전환을 막지 않음, 재색인 중 그 지식베이스에 든 새 문서와 되돌릴 조각 없이 되살린 문서가 전환을 막지 않고 작업이 끝나면 새 현재 판에 듦, 토큰 범위 밖 지식베이스가 `chunk_counts`에 없음, 재색인 시작과 전환 전후의 검색 결과, 토크나이저 판만 바뀐 재색인이 임베딩을 다시 부르지 않음(그 재색인 중 내용이 바뀐 문서는 `building` 판에 옛 글의 조각을 복사하지 않음), 관리 API 열과 Problem Details 모양, 작업 조회가 그 문서의 결과와 같은 문서에 남은 작업을 냄(세대 대조에 걸려 `succeeded`로 끝난 작업도 뒤 작업이 남았으면 남았다고 낸다), `reader`의 REST 403, `/health`. 작업자 시험: 파싱의 영구 실패 즉시 `failed`(고친 파일을 넣으면 문서 상태가 `received`를 거쳐 `parsed`로 돌아오고, 그 뒤 같은 내용을 다시 넣으면 `unchanged`), 내용을 바꿨다가 옛 내용으로 되돌려 파싱을 건너뛰어도 문서 상태가 `parsed`로 돌아옴, 한 판의 임베딩 영구 실패 뒤에도 남은 대상 판을 처리함(재색인 중 현재 판의 모델이 거부해도 건설 중인 판에 쓰고 그 판을 막지 않으며 작업은 `failed`), 일시 실패의 백오프와 최대 시도, 최대 시도 뒤 색인 상태 `failed`와 다시 넣을 때의 `requeued`(내용을 바꾼 문서는 옛 조각을 지우고 `failed`, 재색인 중 그 지식베이스에 든 문서는 건설 중인 판에도 `failed`가 남아 전환 뒤에도 `requeued`, 지운 문서는 색인 상태 행을 만들지 않음), 임대 만료 뒤 다른 작업자의 인수, 두 작업자가 같은 작업을 꺼내지 않음, 재색인 중 바뀐 문서를 판마다 그 판에 적힌 청킹 설정으로 청킹함, 파싱 자식 프로세스의 시간 초과·예외·메모리 한도(리눅스에서는 한도가 걸리고 Windows에서는 "걸지 않음"이 기록되는 두 갈래를 한 테스트가 플랫폼에 따라 단언한다. skip이 아니다). 어댑터 시험: 작업 단위의 커밋·롤백, 잠금 규칙(연결 둘로 한쪽 작업 단위를 열어 둔 채 다른 쪽을 돌린다. 재색인 시작이 열린 동안 수집과 삭제가 지식베이스 행에서 기다리되 교착하지 않고, 어느 쪽이 먼저 커밋되든 새 판의 색인 상태에서 그 문서가 빠지거나 남지 않는다. 재시도 소진도 지식베이스 행에서 기다려 재색인 시작이 쓴 `pending`을 `failed`로 쓰지 않는다. 재색인 시작이 잠근 대기 작업은 작업자가 꺼내지 않는다. 마지막 두 문서를 동시에 끝내도 판이 한 번만 전환된다. 같은 키를 두 번 넣으면 둘째 수집이 대기 작업을 다시 쓴다), 색인 판마다 HNSW 부분 색인이 있고 물러나면 없음, RRF SQL의 순위, 보관 표 이동, TEI 어댑터의 바이트 오프셋 → 글자 인덱스 변환(한국어·이모지가 섞인 글), 배치 크기, 오류 번역(TEI, PostgreSQL, 파일 저장소. 메시지를 옮기지 않음). 청킹 시험: 규칙 일곱을 글자 수로 세는 가짜 토큰 세기로(절 경로가 상한의 4분의 1을 넘는 문서와 그보다 긴 제목 블록을 포함한다). 키워드 시험: 품사 선택과 전처리, 질의와 조각이 같은 토큰을 낸다. 관리 명령 시험: `migrate`의 멱등과 설정 변경 뒤 "재색인 필요", 끝점만 바뀐 설정은 살아 있는 판(건설 중인 판 포함)의 끝점을 고치고 재색인이 아님, 2,000을 넘는 차원의 거부, `bootstrap-token`의 거부, `ingest --wait`의 종료 코드(넣은 작업이 세대 대조에 걸려 `succeeded`로 끝나도 같은 문서의 뒤 작업이 실패하면 1이고, `failed`로 끝나도 뒤 작업이 색인하면 0이며, 앞서 넣은 작업이 도는 문서를 다시 넣어 `unchanged`여도 그 작업을 기다린다). 가짜 포트 시험(동시성 교차): 삭제가 커밋된 뒤 셋째 단계에 든 작업이 조각을 쓰지 않는다, 내용이나 그룹이 바뀐 뒤 셋째 단계에 든 작업이 옛 조각을 쓰지 않는다, 지운 뒤 같은 내용으로 되살린 사이에 옛 작업이 영구 실패하거나 재시도를 다 써도 되살린 조각과 색인 상태를 건드리지 않는다, 같은 문서의 작업 둘이 동시에 돌면 늦게 시작한 작업의 결과로 모인다(먼저 시작한 작업이 늦게 영구 실패해도 조각과 문서 상태를 건드리지 않는다), 임대가 끝나 다른 작업자가 같은 작업을 가져가면 처음 작업자는 문서에도 작업 행에도 쓰지 않는다, 임대를 잃은 뒤에야 첫째 단계에 든 시도가 세대를 올리지 않는다, 시도 횟수를 다 쓴 작업을 임대 인수로 꺼내면 다시 돌리지 않고 `worker_lost`로 끝낸다(늦은 시도와 같은 프로세스가 꺼내도 늦은 시도는 쓰지 않는다), 마지막 시도가 첫째 단계 전에 실패해 재시도를 다 써도 문서를 처음부터 맡을 다른 작업이 없으면 `pending`을 `failed`로 쓴다, 작업이 셋째 단계에서 대상 판을 읽은 뒤 재색인이 시작되고 재색인이 넣은 작업이 첫째 단계 전에 재시도를 다 쓰면 건설 중인 판에 `failed`를 쓰고, 그 문서가 그 판의 마지막 `pending`이었으면 판이 전환되어 새 현재 판의 검색에 그 문서가 없다(먼저 읽은 작업은 제가 읽은 판에만 쓴다. 같은 내용을 다시 넣으면 `requeued`), 재색인 뒤 건설 중인 판까지 읽은 작업이 끝나기 전에 재색인이 넣은 작업이 첫째 단계 전에 재시도를 다 써 판이 먼저 전환되어도 먼저 읽은 작업이 끝나면 문서가 새 현재 판에 `indexed`로 든다, 같은 문서의 옛 작업이 아직 실행 중이어도 늦게 시작한 작업이 재시도를 다 쓰면 `pending`을 `failed`로 쓴다, 같은 문서에 같은 새 내용을 넣은 두 수집 가운데 한쪽이 롤백되어도 커밋된 쪽의 원본을 지우지 않는다, 내용을 바꾼 수집이 커밋 뒤 옛 원본을 지우는 동안 같은 문서를 옛 내용으로 되돌리는 수집이 와도 커밋된 원본이 남는다. 실제 데이터베이스로는 교차 시점을 잡기 어렵다.
- [정함] 위 목록에 더하는 시험. spec-reviewer가 User Stories에 대 보아 빈 곳으로 짚었다. 필터(17): `groups`와 갱신일 기간이 결과를 거르고, 필터가 있을 때 `iterative_scan`이 켜져 후보를 채운다. 로그(37): 수집·검색·작업의 로그에 질의 글, 문서 글·키·제목, 토큰 원문이 없다. 요청 ID(38): 응답 헤더의 `X-Request-Id`가 그 요청의 로그와 넣은 작업의 작업자 로그에 이어지고, 들어온 `X-Request-Id`는 쓰지 않는다. 파서 판(41): major가 다른 파서를 entry point에서 거부하고 기록한다. 메타데이터와 갱신일(4)이 검색 결과의 `metadata`·`updated_at`에 실린다. 리랭크(20): 리랭커가 순서를 바꾸고, 리랭커가 실패하면 `search_unavailable`이다. 오류 코드(26): 도구 오류 코드마다 한 사례. 토큰(31): `token_expired`, 회수된 토큰의 401, 범위를 준 `admin` 토큰의 422. 인증(32): 토큰 없는 요청과 틀린 토큰이 REST와 `/mcp` 둘 다에서 401이다. 끝점 `/info`의 모델 불일치가 검색의 `search_unavailable`과 작업의 `embedding_unavailable`을 낸다. `RAG_ALLOWED_HOSTS`가 비면 기동하지 않는다. `max_client_batch_size`가 `RAG_TEI_BATCH_SIZE`보다 작으면 그 값으로 낮춘다. 판이 전환되는 사이의 검색이 둘째 단계부터 다시 한다(가짜 포트).
- [정함] 시간에 기대는 시험의 설정. `NOTIFY`로 깨어나는 시험은 `RAG_WORKER_POLL_SECONDS`를 단언의 기한보다 크게 두어 폴링으로 지나가지 않게 한다. 백오프는 기다리지 않고 `run_after`의 차로 본다(`RAG_JOB_BACKOFF_BASE_SECONDS`는 실수를 받는다). 임대 만료 시험은 `RAG_JOB_LEASE_SECONDS=1`로 한다. 토큰 발급은 지난 만료 시각을 422로 거부하므로, 만료 시험은 1초 뒤에 만료하는 토큰을 발급하고 기다린다.
- [정함] 작업자 프로세스를 실제로 띄우는 시험은 하나다. `rag-engine worker`를 하위 프로세스로 띄워 `NOTIFY`로 깨어나 작업을 처리하고 종료 신호에 끝나는 것을 본다(리눅스는 SIGTERM, Windows는 `CTRL_BREAK_EVENT`를 보내는 플랫폼 갈래이고 skip이 아니다). 나머지는 한 번 돌기 입구로 인프로세스에서 한다.
- [정함] 픽스처 문서는 작다. DOCX와 HWPX는 각 라이브러리의 쓰기 기능으로 테스트가 만들고(제목, 문단, 표가 든 두세 쪽 분량), PDF는 글이 든 작은 파일 하나를 저장소에 둔다. 암호 PDF, 압축 폭탄 ZIP(큰 0 바이트 항목), 쪽 수가 많은 PDF는 테스트가 만든다.
- [정함] 선례. MCP 계약 시험 `tests/contract/test_mcp_tools.py`(uvicorn을 스레드로 띄우고 SDK 클라이언트로 접속), `tests/test_health.py`, `tests/conftest.py`(UTF-8, `GIT_*` 벗기기, skip을 실패로), 가짜 임베딩 서버 `.scratch/core/probes/embedding/fake_server.py`, Context에서 헤더를 읽는 `.scratch/core/probes/mcp-sdk/probe_sdk.py`와 scope를 읽는 `probe_scope.py`.
- [정함] 수락 기준의 지연 측정("동시 요청 여러 개의 검색 지연을 대상 사양에서 재서 프로브로 남긴다")은 테스트가 아니라 프로브다. 마지막 구현 티켓이 Docker에서 실제 TEI(CPU 이미지)와 표본 문서들로 재고 `.scratch/core/probes/`에 스크립트와 출력을 남긴다. 그 결과는 설정 기본값(후보 수, 배치 크기)을 바꿀 수 있고 계약은 바꾸지 않는다.

## Out of Scope

- [넘겨받음] 첫 슬라이스가 만들지 않는 것은 원천과 동기화(커넥터, 주기 실행, 정리 작업), 관리자 페이지, 이미지와 단독 compose, 스캔본 OCR과 HWP 5.0 바이너리, 접근 그룹으로 거르는 검색(칸만 둔다), 답 생성이다(`.scratch/plan-head.md`).
- [정함] source-sync가 받는 것: 커넥터와 변환 인터페이스의 메서드 모양과 변환 단계 끼우기, 서버 경로 원천, 원천의 생성·수정·삭제 관리 API, 보관 기간이 지난 문서의 정리 작업과 주기, 보관 중인 문서를 되살리는 관리 API, 고아 원본의 정리. `.scratch/source-sync/plan.md` 본문에 적었다. 그 계획의 Blocked by는 core와 release-image다.
- [정함] admin이 받는 것: 그룹과 지식베이스의 생성·수정·삭제 관리 API, 화면이 요구하는 문서·작업 목록 조회의 확장. `.scratch/admin/plan.md` 본문에 적었다. 그 계획의 Blocked by는 source-sync(그 뒤에 core)다.
- [정함] release-image가 받는 것: 서버·작업자 이미지를 둘로 가르는 Dockerfile 변경(core는 킥오프의 Dockerfile 하나에서 `rag-engine worker`가 돌게만 한다), TEI 컨테이너 둘과 마이그레이션 서비스의 compose 항목, 모델 파일의 폐쇄망 반입, 메모리 예산(32GB 기준, 16GB 최소)의 문서화. `.scratch/release-image/plan.md` 본문에 적었다. 그 계획의 Blocked by는 core다.
- [정함] search-eval이 받는 것: 조각 상한·겹침 기본값의 판정, 키워드 품사 집합의 재검토, 리랭커와 후보 수의 효과, 정확 스캔 분기의 필요, 시멘틱 청킹 전략. `.scratch/search-eval/plan.md` 본문에 적었다. 그 계획의 Blocked by는 core다.
- [사용자 선택] 최소 점수로 결과를 거르는 `search`의 칸(사용자가 넘긴 제안)은 core에 두지 않고 search-eval로 통째로 넘긴다. 티켓 세션에서 사용자가 골랐다. 리랭커가 없는 지식베이스에서의 뜻, 거른 뒤의 빈 결과, 계약의 판(입력 인자의 추가가 `format_version`에 드는 변경인지)은 그 설계 인터뷰가 정한다(`.scratch/search-eval/plan.md` 본문).
- [넘겨받음] doc-permission이 접근 그룹 필터와 주체(`_meta`)를, doc-freshness가 시행일과 "오래됨" 칸을, change-log가 토큰 발급·회수와 문서 변경의 기록을, hwp-binary가 HWP 5.0을 받는다. core는 칸만 둔다(ADR 0008, 0014, `.scratch/kickoff-input.md` 2절). 그 계획들의 Blocked by는 모두 core 뒤의 기능이다.
- [거절] 커넥터의 `changes_since`, S3 파일 저장소, RabbitMQ 어댑터, 시멘틱 청킹, 로컬 토크나이저는 설계가 거부했거나 나중으로 미룬 것이고 이 명세도 두지 않는다(ADR 0009, 0010, 0012, 0013).
- [거절] 준비 확인(readiness) 끝점, 토큰의 마지막 사용 시각, 들어오는 `X-Request-Id` 신뢰, 결과의 문서 단위 묶기는 두지 않는다.
