# source-sync: 원천(업로드, 서버 경로, 수집 API)과 동기화. 원천에서 더하고 고치고 지운 문서가 다음 동기화 뒤 검색에 반영된다
**슬라이스:** 2
**Blocked by:** core, release-image

core가 지은 수집 파이프라인과 수집 API 위에 서버 경로 커넥터와 업로드 원천, 커넥터와 변환의 인터페이스를 짓고(업로드와 수집 API는 커넥터가 아니라 밀어 넣는 원천 종류다. ADR 0008), 킥오프 입력 4절의 동기화 규칙(수동과 주기 실행, 증분, 삭제 반영의 정리 작업, 겹침 방지, 시간대와 동시 처리 수, 재시도, 작업 기록, 수집 정책, 연결 정보의 암호화 보관, 메타데이터 대응)을 넣는다. 수집 API의 판(경로의 `v1`)은 core가 붙였다(core 명세 수집 API 절). 서버 경로 원천의 폴더는 읽기 전용 볼륨으로 붙이고, 그 설정을 단독 compose와 설치 안내에 더한다(release-image가 정한 판 태그와 단독 compose의 규칙으로). 설계 인터뷰의 입력은 킥오프 입력 4절이다.

core 명세(`.scratch/core/spec.md`, 2026-11-10)가 넘긴 것: 커넥터와 변환 인터페이스의 메서드 모양과 수집 파이프라인에 변환 단계를 끼우는 일(core의 파이프라인은 변환 자리를 비워 둔다), 서버 경로 원천, 원천의 생성·수정·삭제 관리 API(core는 밀어 넣는 원천 `default` 하나와 수집 API·`ingest` 명령만 둔다), 보관 기간(`RAG_DELETED_RETENTION_DAYS`)이 지난 소프트 삭제 문서의 정리 작업과 그 주기(core는 설정 이름과 묘비 행의 모양만 정한다), 보관 중인 문서를 되살리는 관리 API(core는 같은 (원천, 키)가 다시 들어올 때의 되살림만 한다), 수집 요청이 지우지 못한 고아 원본 파일(작업 단위가 롤백된 뒤의 새 원본, 커밋 뒤에 지울 옛 원본과 문서 행이 가리키지 않는 새 원본)의 정리.

수락: 서버 경로의 파일을 더하고 고치고 지우면 다음 주기 실행 뒤 검색 결과가 따라 바뀌고(지운 문서의 조각이 나오지 않는다), 같은 원천의 작업이 겹쳐 돌지 않으며, 수집 API로 보낸 문서가 바로 검색되고, 암호가 걸린 파일이 건너뜀으로 기록되는 테스트가 통과한다.
