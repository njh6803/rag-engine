## Problem Statement

지금 이 서버에는 원천이 `default` 하나뿐이다. 수집 API는 원천을 고르는 칸이 없어서, 그룹웨어와 위키가 같은 키 "123"으로 문서를 보내면 뒤에 온 문서가 앞 문서를 덮어쓴다. 연동 하나를 끊고 싶어도 그 시스템이 보낸 문서만 골라 지울 길이 없다.

서버가 스스로 문서를 읽어 오는 길도 없다. 공유 폴더에 규정집이 있어도 운영자가 `ingest` 명령으로 한 번 넣을 수 있을 뿐이고, 그 뒤에 폴더에서 파일을 고치거나 지워도 색인은 모른다. 지운 파일의 문서가 검색에 계속 나온다(원칙 VI에 어긋난다). 정해진 때에 무엇을 돌리는 장치가 없어서 "매일 새벽 2시에 폴더를 다시 본다"를 시킬 수도 없다.

지운 문서의 뒤처리도 비어 있다. 임시 삭제된 문서는 보관 기간(기본 30일)이 지나도 지워지지 않고 조각과 원본이 계속 쌓인다. 실수로 지운 문서를 되살리려면 같은 파일을 같은 키로 다시 보내야 한다. 수집 요청이 실패하며 남긴 원본 파일을 치우는 일도 없다.

마지막으로, 색인할 글을 얻을 수 없는 문서가 엉뚱하게 기록된다. 암호가 걸린 파일은 실패(`encrypted_document`)로 남아 운영자가 고쳐야 할 장애처럼 보이고, 글자가 없는 스캔본은 조각이 0개인 성공으로 남아 "넣었는데 왜 검색이 안 되느냐"를 문서 목록에서 알아볼 수 없다.

## Solution

운영자는 관리 API로 원천을 만든다. 다른 시스템이 문서를 보내 주는 원천(밀어 넣는 원천)은 `groupware`, `wiki`처럼 시스템마다 하나씩 만들고, 보내는 프로그램은 수집 API의 `source` 칸에 그 이름을 적는다. 같은 키라도 원천이 다르면 다른 문서로 남는다. `source`를 적지 않은 요청은 지금처럼 `default`에 들어가므로 이미 쓰던 방법은 그대로다.

서버 폴더의 문서는 서버 경로 원천(가져오는 원천)으로 가져온다. 운영자는 단독 compose의 `.env`에 서버 기계의 폴더 하나를 적고(적지 않으면 묶음 안의 `sources/` 폴더다), 그 아래에 문서 폴더를 두거나 공유 폴더를 붙인다. 그 폴더가 서버와 작업자 컨테이너의 `/sources`에 읽기 전용으로 붙는다. 관리 API로 원천을 만들 때 하위 폴더 이름(예: `규정집`), 그룹, 일정(예: `0 2 * * *`는 매일 02:00)을 적는다.

작업자는 5초마다 일정이 된 원천이 있는지 보고 동기화 작업을 넣는다. 동기화는 폴더의 파일 목록을 받아 색인과 대 본다. 새 파일과 바뀐 파일은 넣고, 폴더에서 사라진 파일의 문서는 임시 삭제해 검색에서 뺀다. 수정 시각과 크기가 그대로인 파일은 읽지 않는다. 폴더가 붙지 않아 빈 폴더로 보이거나 문서가 될 파일이 하나도 보이지 않을 때는 아무것도 지우지 않고 그 동기화를 실패로 남긴다. 동기화가 끝나면 무엇이 시작시켰는지, 몇 건을 더하고 바꾸고 지웠는지, 왜 실패했는지가 동기화 기록에 남고 운영자는 관리 API로 본다. 운영자는 일정을 기다리지 않고 "지금 동기화"를 시킬 수 있고, 원천을 잠깐 쉬게 하려면 일시 중지한다.

원천을 지우면 그 순간 그 원천의 문서가 모두 검색에서 빠진다. 보관 기간 안에는 관리 API 호출 하나로 원천을 되살릴 수 있고, 함께 지워졌던 문서가 임베딩을 다시 하지 않고 돌아온다. 밀어 넣는 원천의 문서 하나를 실수로 지웠을 때도 관리 API로 되살린다. 보관 기간이 지난 문서와 원천은 작업자가 하루에 한 번 도는 정리 작업으로 완전히 지운다.

암호가 걸린 파일과 글자가 없는 스캔본은 실패가 아니라 건너뜀으로 기록되고, 문서 목록에서 실패와 따로 보인다. 지원하지 않는 형식이거나 너무 크거나 제외 패턴에 맞는 파일은 문서로 만들지 않고 동기화 기록에 사유별 개수만 남긴다.

## User Stories

1. As a 운영자, I want 문서를 보내는 시스템마다 원천을 따로 만들고 싶다, so that 서로 다른 시스템의 같은 키가 한 문서로 겹치지 않는다.
2. As a 연동 개발자(문서를 보내는 프로그램을 만드는 사람), I want 수집 API 요청에 원천 이름을 적고 싶다, so that 내 시스템의 문서가 내 원천에만 들어간다.
3. As a 연동 개발자, I want 원천 이름을 적지 않은 기존 요청이 지금처럼 `default`에 들어가기를 바란다, so that 이미 돌고 있는 연동을 고치지 않는다.
4. As a 연동 개발자, I want 없는 원천이나 지운 원천, 서버가 스스로 읽는 원천의 이름을 적으면 까닭이 드러나는 오류 코드를 받고 싶다, so that 이름을 잘못 적은 것인지 원천이 지워진 것인지 가린다.
5. As a 운영자, I want 서버 기계의 폴더 하나를 `.env`에 적는 것으로 서버가 읽을 수 있는 범위를 정하고 싶다, so that 원천을 더할 때마다 compose 파일을 고치지 않는다.
6. As a 운영자, I want 원천을 만들 때 하위 폴더 이름만 적고 싶다, so that 컨테이너 안의 경로를 알 필요가 없다.
7. As a 보안 담당자, I want 관리 토큰을 가진 쪽이 부모 폴더 밖의 파일이나 심볼릭 링크 너머의 파일을 문서로 색인하지 못하기를 바란다, so that 검색으로 서버 안의 다른 파일을 읽어 내지 못한다.
8. As a 운영자, I want 원천을 만들 때 폴더가 없거나 다른 원천의 폴더와 겹치면 바로 거부되기를 바란다, so that 첫 동기화가 실패하거나 같은 파일이 두 원천에 들어가는 것을 나중에야 알지 않는다.
9. As a 운영자, I want 원천을 만든 뒤 "연결 확인"으로 폴더가 읽히는지 보고 싶다, so that 동기화를 돌리기 전에 권한과 붙임 상태를 확인한다.
10. As a 운영자, I want 일정을 cron 표현식으로 적고 싶다, so that "평일 02:00"이나 "30분마다" 같은 때를 그대로 적는다.
11. As a 운영자, I want 틀린 표현식이나 초 칸이 든 여섯 칸짜리 표현식이 저장할 때 거부되기를 바란다, so that 돌지 않는 일정을 저장해 놓고 기다리지 않는다.
12. As a 운영자, I want 일정의 시각이 한국 시간으로 읽히고 설정 하나로 바꿀 수 있기를 바란다, so that `0 2 * * *`가 오전 11시에 돌지 않는다.
13. As a 운영자, I want 원천 보기에서 다음 실행 시각을 보고 싶다, so that 일정이 내가 뜻한 대로 읽혔는지 확인한다.
14. As a 운영자, I want 일정을 기다리지 않고 "지금 동기화"를 시키고 싶다, so that 방금 고친 문서를 바로 반영한다.
15. As a 운영자, I want 폴더에 더한 파일이 다음 동기화 뒤 검색되기를 바란다, so that 파일을 폴더에 두는 것만으로 문서가 들어간다.
16. As a 운영자, I want 폴더에서 고친 파일의 옛 내용이 다음 동기화 뒤 검색에서 새 내용으로 바뀌기를 바란다, so that 낡은 규정으로 답하지 않는다.
17. As a 운영자, I want 폴더에서 지운 파일의 문서가 다음 동기화 뒤 검색에서 빠지기를 바란다, so that 폐지된 문서가 근거로 쓰이지 않는다.
18. As a 운영자, I want 바뀌지 않은 파일은 동기화가 다시 읽지 않기를 바란다, so that 큰 폴더의 동기화가 매번 모든 파일을 읽지 않는다.
19. As a 운영자, I want 공유 폴더가 붙지 않아 빈 폴더로 보이거나 문서가 아닌 파일만 보일 때 동기화가 문서를 지우지 않기를 바란다, so that 네트워크 장애 한 번으로 그 원천의 문서가 모두 검색에서 빠지지 않는다.
20. As a 운영자, I want 정말로 폴더를 비웠거나 모든 파일을 수집 정책으로 뺐을 때는 "빈 목록도 반영"을 켜서 동기화하고 싶다, so that 보호 장치 때문에 지운 문서가 남지 않는다.
21. As a 운영자, I want 같은 원천의 동기화가 겹쳐 돌지 않기를 바란다, so that 긴 동기화가 끝나기 전에 다음 일정이 와도 같은 문서를 두 번 넣지 않는다.
22. As a 운영자, I want 작업자를 여럿 띄워도 일정 하나가 동기화를 한 번만 시작시키기를 바란다, so that 작업자 수를 늘렸다고 동기화가 겹치지 않는다.
23. As a 운영자, I want 큰 폴더의 색인이 밀려 있어도 다른 원천의 동기화와 "지금 동기화"가 곧 돌기를 바란다, so that 다른 원천에서 지운 문서가 몇 시간씩 검색에 남지 않는다.
24. As a 운영자, I want 원천을 잠깐 일시 중지하고 나중에 다시 시작하고 싶다, so that 폴더를 정리하는 동안 동기화가 중간 상태를 반영하지 않는다.
25. As a 운영자, I want 동기화마다 언제 무엇이 시작시켜 어떻게 끝났고 몇 건을 더하고 바꾸고 지웠는지 보고 싶다, so that 어젯밤 동기화가 돌았는지와 무엇을 했는지 확인한다.
26. As a 운영자, I want 실패한 동기화의 까닭을 코드로 보고 싶다, so that 폴더가 없는 것인지 경로가 거부된 것인지 가려 조치한다.
27. As a 운영자, I want 암호가 걸린 파일과 글자가 없는 스캔본이 실패가 아니라 건너뜀으로 따로 보이기를 바란다, so that 고쳐야 할 장애와 원래 색인할 수 없는 파일을 가른다.
28. As a 운영자, I want 지원하지 않는 형식, 너무 큰 파일, 제외 패턴에 맞는 파일이 문서 목록을 채우지 않고 개수로만 보이기를 바란다, so that 문서 목록에는 받은 문서만 있다.
29. As a 운영자, I want 원천마다 제외 패턴을 더하고 싶다, so that `임시/` 폴더나 `*_초안.docx` 같은 파일을 받지 않는다.
30. As a 운영자, I want 임베딩 서버가 잠깐 꺼져 색인이 실패한 문서가 파일을 고치지 않아도 다음 동기화에서 다시 시도되기를 바란다, so that 장애가 풀린 뒤 파일마다 수정 시각을 바꾸지 않는다.
31. As a 운영자, I want 원천을 지우면 그 원천의 문서가 그 순간 검색에서 빠지기를 바란다, so that 연동을 끊은 시스템의 문서가 계속 근거로 쓰이지 않는다.
32. As a 운영자, I want 실수로 지운 원천을 보관 기간 안에 호출 하나로 되살리고 싶다, so that 문서 수만 건을 다시 보내거나 다시 임베딩하지 않는다.
33. As a 운영자, I want 실수로 지운 업로드 문서 하나를 관리 API로 되살리고 싶다, so that 같은 파일을 찾아 다시 올리지 않는다.
34. As a 운영자, I want 기본 원천(`default`, `upload`)은 지울 수 없기를 바란다, so that 원천 이름을 적지 않은 수집 요청이 갈 곳을 잃지 않는다.
35. As a 운영자, I want 보관 기간이 지난 문서와 원천이 저절로 완전히 지워지기를 바란다, so that 지운 문서의 조각과 원본이 디스크에 계속 쌓이지 않는다.
36. As a 운영자, I want 수집이 실패하며 남긴 원본 파일이 저절로 치워지기를 바란다, so that 파일 저장소에 주인 없는 파일이 쌓이지 않는다.
37. As a 운영자, I want 정리 작업이 내 서버 폴더(`/sources`)의 파일을 절대 지우지 않기를 바란다, so that 색인을 정리하다 원본 문서를 잃지 않는다.
38. As a 운영자, I want 로그와 동기화 기록에 문서의 키, 제목, 폴더 이름, 커넥터가 낸 예외의 글이 남지 않기를 바란다, so that 로그를 모아 보내도 문서 이름과 연결 정보가 새지 않는다(원칙 V).
39. As a 커넥터를 만드는 개발자, I want 커넥터가 구현할 인터페이스와 그 버전이 정해져 있기를 바란다, so that 서버 코드를 고치지 않고 새 원천을 붙인다.
40. As a 운영자, I want 인터페이스 버전이 맞지 않는 커넥터가 조용히 돌지 않고 거부되어 기록되기를 바란다, so that 업그레이드 뒤 동기화가 엉뚱하게 도는 것을 막는다.
41. As a 운영자, I want 설치 안내에 폴더를 붙이는 법과 공유 폴더를 나중에 붙였을 때 할 일이 적혀 있기를 바란다, so that 동기화가 빈 폴더만 보는 까닭을 찾아 헤매지 않는다.
42. As a 개발자, I want 일정을 시계를 기다리지 않고 시험하고 싶다, so that 일정 시험이 몇 분씩 걸리지 않는다.
43. As a 운영자, I want "지금 동기화"에 "모두 다시 읽기"를 켜서 원천 하나의 파일을 모두 다시 읽게 하고 싶다, so that 수정 시각이 그대로인 채 내용만 바뀐 파일과 파서를 고친 뒤의 실패·건너뜀 문서를 지식베이스 전체를 재색인하지 않고 다시 처리한다.

## Implementation Decisions

### 따르는 것과 범위

- [넘겨받음] 원천의 두 갈래(밀어 넣는 원천, 가져오는 원천)와 문서의 주인, 서버 경로 원천의 폴더는 ADR 0021이 정했고, 동기화의 일정과 실행, 건너뜀, 동기화 기록, 정리 작업은 ADR 0022가 정했다. 이 명세는 그 결정을 옮기고, 두 ADR이 "명세가 재거나 정하는 것"으로 넘긴 것과 기능 계획이 넘긴 물음을 정한다.
- [넘겨받음] 이번에 짓지 않는 것은 변환 인터페이스, 연결 정보의 암호화 보관, 수집 전용 토큰(ADR 0021 "이번에 짓지 않는 것"), 그리고 원천마다의 실행 시간대와 동시 처리 수다(ADR 0022 "부하를 조절하는 장치는 두지 않는다").
- [넘겨받음] 관리 명령은 더하지 않는다. `ingest <경로>` 명령은 지금처럼 `default` 원천에 한 번 넣는 명령으로 남는다(ADR 0021 Consequences).
- [정함] `ingest <경로>`로 `default`에 넣어 둔 폴더를 서버 경로 원천으로 다시 읽으면 같은 파일이 두 원천의 문서가 되어 검색에 두 번 나온다(기능 계획이 넘긴 물음). 서버는 이것을 막거나 합치지 않는다. 문서는 (원천, 키)로 가르므로 원천이 다르면 내용이 같아도 다른 문서이고(core 명세), 원천 너머로 합치면 어느 원천이 그 문서를 가졌는지가 흐려진다(원칙 VI). 옮기는 절차는 설치 안내가 적는다. 서버 경로 원천을 만들어 첫 동기화가 끝난 것을 동기화 기록으로 본 뒤, `default`에 넣었던 문서를 수집 API의 삭제 요청으로 하나씩 지운다. 지울 문서는 관리 API의 문서 목록을 `source=default`로 걸러 찾는다. `ingest` 명령이 붙인 키는 넣은 폴더 기준의 상대 경로라서(코드를 읽었다), 같은 폴더를 원천 폴더로 삼으면 두 원천에서 키가 같다.
- [정함] 업로드에는 끝점을 따로 두지 않는다. `upload`는 `migrate`가 `default`와 함께 만들어 두는 밀어 넣는 원천이고, 파일을 올리는 쪽(관리자 페이지)은 수집 API에 `source=upload`를 적어 보낸다.
- [넘겨받음] 관리 API의 경로는 `/api/v1/admin` 그대로이고, 수집 API도 칸을 더하는 것이라 `v1` 그대로다(ADR 0021, ADR 0022 Consequences, 원칙 VII).

### 층과 포트

- [넘겨받음] 커넥터 인터페이스는 `typing.Protocol`이고 구현은 `interface_version`(semver 문자열)을 가진다. 설치는 entry point 그룹 `rag_engine.connectors`로 등록한다(ADR 0012). entry point는 파이썬 패키지가 설치될 때 "이 이름으로 이것을 내놓는다"고 알려 두는 표준 장치이고, 그룹은 그 이름들을 종류별로 묶는 칸이다.
- [정함] 커넥터 인터페이스(Protocol, 그것이 주고받는 값, 예외 하나)는 `domain`에 둔다. 커넥터를 만드는 쪽이 import하는 계약이면서 `app`이 부르는 포트다. 서버 경로 커넥터와, entry point를 읽어 이름으로 커넥터를 찾는 일은 `adapters`에 둔다.
- [정함] 새 포트는 넷이다. `Connector`(커넥터 인터페이스 그 자체다), `ConnectorRegistry`(커넥터의 이름과 원천의 설정을 받아 그 커넥터를 만들어 내고, 인터페이스 버전을 판정한다), `ScheduleCalculator`(일정 표현식을 확인하고 다음 실행 시각을 낸다), `SyncRecordStore`(동기화 기록을 저장한다)다. `SyncRecordStore`는 작업 단위 안에서 얻는다. 동기화 기록을 동기화 작업을 넣는 같은 작업 단위에서 만들기 때문이고(동기화 기록 절), 그래서 한 트랜잭션을 공유하는 포트가 넷에서 다섯이 된다. 나머지 셋은 작업 단위 밖에서 부른다. 원천의 저장은 `Catalog`에, 변경 확인값과 건너뜀과 원천 단위의 삭제·되살림은 `DocumentStore`와 `VectorIndex`에, 새 작업 종류와 꺼내는 순서는 `JobQueue`에, 원본의 열거는 `BlobStore`에 더한다. 메서드의 이름은 구현 티켓이 정한다.
- [이력] ADR 0007의 본문은 포트를 이름으로 나열한다. `Connector`는 그 열에 이미 있고 나머지 셋이 새로 든다. 앞선 명세들이 포트를 더할 때마다 한 것처럼 그 ADR에 2026-11-21 이력을 더하고 포트 열 문장 뒤에 포인터를 달았다.
- [넘겨받음] 다음 실행 시각은 cronsim 2.8이 계산하고, 계산하는 자리를 포트 뒤에 둔다(ADR 0022 "계산하는 라이브러리"). cronsim은 `adapters`만 import하고, 의존성을 더하는 티켓이 `pyproject.toml`의 import 금지 목록에 그 이름을 더한다(ADR 0022 Consequences).
- [정함] 커넥터는 서버와 작업자가 모두 쓴다. 서버는 연결 확인에, 작업자는 동기화와 색인에 쓴다. 서버는 원천을 만들고 고치고 되살릴 때 서버 경로 원천의 폴더 확인도 한다. 이 확인은 커넥터 인터페이스 밖에 있지만(커넥터 인터페이스 절) 같은 부모 폴더를 읽는다. 그래서 부모 폴더를 두 컨테이너에 모두 붙인다(ADR 0021 "서버 경로 원천의 폴더").
- [정함] 동기화, 원천 삭제, 원천 되살리기, 정리의 유스케이스는 `app`에 두고 포트만 부른다. 일정 확인을 몇 초마다 돌리는 일은 `worker`의 조립이 맡는다.

### 설정

- [정함] `RAG_SOURCES_DIR`(기본 `/sources`)는 부모 폴더의 컨테이너 안 경로다. 서버와 작업자가 같은 값을 읽고, 시험은 임시 폴더로 바꾼다. 운영자가 바꿀 일은 없고, 단독 compose는 이 값을 `/sources`로 정해 `.env`가 덮어쓰지 못하게 한다(단독 compose 절).
- [정함] `RAG_SCHEDULE_TIMEZONE`(기본 `Asia/Seoul`)은 일정 표현식의 시각을 읽는 시간대이고 IANA 시간대 이름을 받는다(ADR 0022 "시간대"가 명세에 넘긴 이름). 모르는 이름이면 서버와 작업자가 기동을 거부한다. 저장하는 시각은 모두 UTC다(ADR 0015).
- [정함] `RAG_SYNC_RECORD_RETENTION_DAYS`(기본 90)는 동기화 기록의 보관 기간이다(ADR 0022가 명세에 넘겼다). 정리 작업이 끝난 지 그 기간이 지난 기록을 지운다.
- [넘겨받음] 임시 삭제의 보관 기간은 `RAG_DELETED_RETENTION_DAYS`(기본 30)다(ADR 0013, core 명세). 이 기능이 처음 쓰는 곳을 만들므로 `.env.example`에 예시 줄을 더한다(release-image 명세가 넘겼다).
- [넘겨받음] 일정 확인의 주기는 작업자가 작업 대기열을 살피는 주기 `RAG_WORKER_POLL_SECONDS`(기본 5)다(ADR 0022 "시작시키는 쪽").
- [정함] 크기 상한은 수집 API와 같은 `RAG_MAX_UPLOAD_MB`(기본 100)를 쓴다. 가져오는 원천에 따로 두는 상한은 없다.
- [정함] `RAG_SOURCE_READ_TIMEOUT_SECONDS`(기본 600)는 작업자가 커넥터 호출 하나(목록의 다음 항목 하나, 파일 하나 읽기)를 기다리는 한도다(동기화의 차례 절). 작업 담당 기록의 기한과 따로 둔다. 공유 폴더의 빠르기와 파일의 크기가 설치마다 달라 상수로 두지 않았다. 서버가 요청 안에서 하는 연결 확인과 폴더 확인이 기다리는 10초는 상수다(관리 API 절, 서버 경로 커넥터와 원천 폴더 절).
- [거절] 정리 작업의 시각, 원천 삭제 작업의 묶음 크기, 고아 원본의 유예 시간을 설정으로 여는 것. 값은 아래 절이 상수로 정하고, 바꿀 까닭이 생기면 그때 연다.

### 데이터 모델과 스키마

- [넘겨받음] 원천 표의 갈래 칸(`kind`)이 받는 값에 `pull`을 더한다. 지금은 `push` 하나다(ADR 0021 Consequences).
- [정함] 원천 표에 더하는 칸은 다음과 같다. 가져오는 원천만 쓰는 것은 커넥터의 이름(`connector`), 커넥터 설정(`config`, JSON 객체), 그룹(`group_id`), 일정 표현식(`schedule`, 없으면 일정 없음), 다음 실행 시각(`next_run_at`), 일시 중지(`paused`), 제외 패턴 목록(`exclude_patterns`)이다. 모든 원천이 쓰는 것은 지운 시각(`deleted_at`, 지움 표시)과 만든 시각이다. 밀어 넣는 원천은 앞의 일곱 칸이 비어 있어야 하고 가져오는 원천은 커넥터 이름과 그룹이 있어야 한다는 것을 표의 제약으로 건다.
- [정함] 원천 이름은 지운 원천을 포함해 하나뿐이다(지금의 유일 제약 그대로). 그래서 지운 원천의 이름은 정리 작업이 그 원천을 완전히 지울 때까지 다시 쓸 수 없다(ADR 0021이 명세에 넘겼다). 같은 이름을 다시 쓰게 하면 되살릴 때 이름이 부딪치고, 수집 요청이 적은 이름이 어느 원천인지 갈린다.
- [정함] 원천 이름은 1~63자이고 영문 소문자, 숫자, `-`, `_`만 쓰며 영문 소문자나 숫자로 시작한다. 관리 API의 경로와 수집 API의 칸에 그대로 들어가는 값이라 URL에서 바뀌지 않는 글자로 좁혔다.
- [정함] 문서 표에 더하는 칸은 셋이다. 변경 확인값(`change_marker`, 커넥터가 준 문자열 그대로이고 밀어 넣는 원천의 문서에서는 비어 있다), 건너뜀 사유(`skip_reason`), 원천과 함께 지워졌다는 표시(`deleted_with_source`)다. 문서 상태가 받는 값에 `skipped`를 더한다(ADR 0022 "건너뜀").
- [정함] 문서 표의 원본 경로 칸은 비어 있을 수 있게 고친다. 가져오는 원천의 문서는 원본을 파일 저장소에 복사하지 않고 그 칸을 비운다(ADR 0013 "서버 경로 원천은 원본이 그 경로에 이미 있으므로 복사하지 않고 경로만 가리킨다". 가리키는 경로는 문서의 키다).
- [정함] 작업 표가 받는 종류는 다섯이 된다. 문서 한 건을 색인하는 `index_document`(지금 있는 것), 동기화 작업 `sync_source`, 원천 삭제 작업 `delete_source`, 원천 되살리기 작업 `restore_source`, 정리 작업 `cleanup`이다. 작업 표에 원천을 가리키는 칸(`source_id`)과 옵션 칸(JSON 객체)을 더하고, 문서를 가리키는 칸은 비어 있을 수 있게 고친다. 색인 작업은 문서만, 원천 단위 작업은 원천만 가리키고, 정리 작업은 둘 다 가리키지 않는다는 것을 표의 제약으로 건다.
- [정함] 문서를 가리키지 않는 작업에는 부분 유일 색인(조건에 맞는 행들 안에서만 같은 값이 둘 있지 못하게 막는 색인) 하나를 둔다. 대기 중이거나 실행 중인 작업 가운데 (원천, 종류)가 같은 것은 하나뿐이고, 원천이 빈 값끼리도 같은 값으로 본다(`NULLS NOT DISTINCT`). 이 색인이 같은 원천의 동기화가 겹치지 않는 것과 정리 작업이 하나만 도는 것을 구조로 받친다. 프로브가 쟀다(작업 대기열 절).
- [정함] 동기화 기록은 새 표(`sync_records`)에 둔다. 행 하나가 동기화 한 번이고 칸은 동기화 기록 절이 정한다. 원천을 완전히 지울 때 그 원천의 기록도 함께 지운다.
- [넘겨받음] 마이그레이션이 든 PR의 제목에는 느낌표가 붙는다(ADR 0020, ADR 0021·0022 Consequences).
- [정함] 마이그레이션은 이미 있는 문서를 건너뜀으로 옮긴다(ADR 0022 Consequences가 명세에 넘겼다). 문서 상태가 `failed`이고 오류 코드가 `encrypted_document`인 문서는 `skipped`와 사유 `encrypted`로, 파싱 결과에 글이 없는 문서(지금은 `parsed`이고 조각이 0개다)는 `skipped`와 사유 `no_text`로 옮기고, 그 문서의 색인 상태는 아래 건너뜀 절의 모양(`indexed`, 오류 코드 없음)으로 맞춘다. 옮기지 않으면 같은 종류의 문서가 업그레이드 앞뒤로 다른 상태에 남아, 문서 목록의 실패 수가 무엇을 세는지 설치마다 달라진다.

### 커넥터 인터페이스 1.0

- [넘겨받음] 커넥터 인터페이스 1.0은 열거와 받기다. `interface_version`, 원천 안의 (키, 변경 확인값)을 전부 내는 `list()`, 바이트와 MIME과 갱신 시각과 메타데이터를 내는 `fetch(key)`, 연결을 확인하는 `check()`다. 서버가 열거 결과를 색인과 대 봐 더함·바뀜·지움을 판정하고, 커넥터는 기억해 두는 것이 없다(ADR 0012).
- [사용자 선택] 커넥터는 원천의 설정(JSON 객체) 하나를 받아 만들어진다. entry point가 가리키는 것은 설정을 받아 커넥터를 돌려주는 보통 함수다(비동기 함수가 아니다). 이 함수는 설정의 모양만 보고 원천에 닿지 않는다. 파일 시스템도 네트워크도 부르지 않는다. 그래서 이 호출에는 커넥터 호출의 한도를 걸지 않고, 커넥터가 이 약속을 지키는 한 멈춘 원천이 이 호출을 붙잡지 못한다. 설정이 그 커넥터가 받는 모양이 아니면 만들 때 인터페이스의 예외를 사유 `invalid_config`로 올린다. 그 밖에 필요한 값(부모 폴더, 토큰)은 커넥터가 환경 변수나 비밀 파일에서 스스로 읽는다(ADR 0021 "연결 정보의 암호화 보관"이 설치처 커넥터에 정한 길과 같다). `fetch`와 `check()`는 비동기 함수이고, `list()`는 비동기 반복이다(아래 항목). 서버 경로 원천의 폴더를 정하는 확인(폴더 찾기, 경로 확인, 겹침 확인)은 만드는 함수의 일이 아니다. 서버가 10초 한도 안에서 따로 부르는 확인이고 인터페이스 1.0에 들지 않는다(서버 경로 커넥터와 원천 폴더 절). 그 확인을 어느 포트의 메서드로 둘지는 구현 티켓이 정한다. 고르지 않은 안은 만드는 함수도 원천에 닿을 수 있게 하는 안이다. 커넥터를 짓는 쪽이 연결을 미리 열 수 있지만, 그 호출에도 한도와 돌아오지 않는 호출의 기억(동기화의 차례 절)을 걸어야 하고 만드는 함수도 비동기여야 한다(사용자가 2026-11-22에 티켓을 나누며 골랐다. 명세 검토가 막는 지적으로 냈다).
- [정함] `list()`는 항목을 하나씩 내는 비동기 반복이고, 항목은 키, 변경 확인값(문자열), 크기(바이트. 모르면 비운다)다. 크기는 ADR 0012가 적은 두 값에 더한 칸이고, 서버가 파일을 읽지 않고 크기 상한을 적용하는 데 쓴다. 같은 키를 두 번 내면 서버는 그 동기화를 `connector_error`로 실패시킨다.
- [정함] `fetch(key)`의 결과는 바이트, MIME(모르면 비우고 서버가 키의 확장자로 가른다), 갱신 시각(없으면 수집 시각을 쓴다), 메타데이터(JSON 객체)다. 문서의 제목은 메타데이터의 `title`이 문자열이면 그것이고, 아니면 서버가 키의 마지막 토막에서 확장자를 떼어 만든다(수집 API가 파일 이름으로 제목을 만드는 것과 같은 규칙이다. 코드를 읽었다).
- [정함] `check()`는 원천을 읽을 수 있는지 보고, 안 되면 인터페이스의 예외를 올린다.
- [사용자 선택] 인터페이스가 정하는 예외는 하나이고 닫힌 사유 값 다섯을 든다. `invalid_config`(원천의 설정이 그 커넥터가 받는 모양이 아니다. 커넥터를 만들 때만 난다), `unreadable`(원천이나 그 항목을 읽을 수 없다), `rejected`(경로 확인에 걸렸다), `not_found`(그 키의 문서가 없다), `too_large`(받을 수 있는 크기를 넘는다)다. `invalid_config`를 따로 둔 것은 경로가 없는 커넥터(db-source의 SQL 커넥터)도 설정 오류를 알려야 하기 때문이다. 1.0을 낸 뒤에 사유를 더하면 1.0을 아는 서버가 모르는 값을 받으므로 지금 정한다. 고르지 않은 안은 `rejected`가 설정 오류까지 뜻하게 넓히는 안이다. 그 안에서는 SQL 커넥터의 설정 오류도 "경로 확인에 걸렸다"로 보여 운영자가 까닭을 헷갈린다(사용자가 2026-11-22에 티켓을 나누며 골랐다. 명세 검토가 막는 지적으로 냈다). 서버는 사유 값만 쓰고 예외의 글은 응답, 동기화 기록, 로그 어디에도 싣지 않는다. 그 밖의 예외는 서버가 `connector_error`로 옮기고 로그에는 예외의 종류 이름만 남긴다(원칙 V, PR 직전 리뷰가 넘겼다. 설치처가 만든 커넥터의 예외 글에는 토큰이나 연결 문자열이 섞일 수 있다).
- [정함] 커넥터는 자기가 한 번에 내는 바이트의 크기를 스스로 지킨다. 서버 경로 커넥터는 `RAG_MAX_UPLOAD_MB`를 넘는 파일을 끝까지 읽지 않고 `too_large`로 알린다. 서버는 받은 바이트의 크기를 한 번 더 보고 넘으면 버린다. `fetch`에 상한을 넘기는 인자를 더하지 않은 것은 ADR 0012가 적은 모양(`fetch(key)`)을 그대로 두려는 것이다.
- [넘겨받음] 서버와 작업자는 커넥터를 로드할 때 `interface_version`의 major가 다르면 그 커넥터를 거부하고 기록한다(ADR 0012).
- [정함] 거부는 두 자리에서 드러난다. 그 커넥터 이름으로 원천을 만드는 요청은 422이고, 이미 있는 원천의 동기화는 `connector_unavailable`로 실패해 동기화 기록에 남는다. 설치되지 않은 커넥터 이름도 같다. 이미 있는 원천의 저장해 둔 설정을 만드는 함수가 `invalid_config`로 받지 않을 때도(커넥터를 올린 뒤 설정의 규칙이 바뀌었다) 그 동기화는 `connector_unavailable`이고, 연결 확인도 같은 코드로 답한다. 운영자가 할 일이 커넥터를 올린 뒤의 설정을 맞추는 것이라 업그레이드의 까닭과 한 코드로 묶었다.
- [정함] 원천의 설정(`config`)에는 비밀 값을 넣지 않는다는 것을 인터페이스의 설명에 적는다(ADR 0021은 비밀을 넣는 칸을 두지 않았다). 관리 API의 원천 보기는 설정을 그대로 보여 주고, 서버는 그 안에서 비밀을 가려낼 수 없다. 그래서 진단 묶음은 원천의 설정을 싣지 않게 diag-bundle에 넘긴다(Out of Scope).
- [정함] `rag-engine --version`이 계약마다 버전을 한 줄씩 찍는 목록에 커넥터 인터페이스의 버전 `1.0.0`을 더한다(release-image 명세 "번호가 보이는 자리"의 목록에 칸을 더한다). 서버 경로 커넥터의 `interface_version`도 이 값이다. 꼴은 파서 인터페이스의 값 `1.0.0`과 같게 세 자리로 적는다(코드를 읽었다).

### 서버 경로 커넥터와 원천 폴더

- [넘겨받음] 서버 경로 원천은 부모 폴더 아래의 하위 폴더 하나를 읽는다. 원천을 만들 때는 하위 폴더 이름만 적고, 서버는 부모 폴더 밖의 경로를 받지 않으며, 원천 폴더 안의 심볼릭 링크를 따라가지 않는다. 밖인지는 적은 글자가 아니라 실제로 가리키는 자리로 가르고, 이 확인은 동기화가 돌 때마다 다시 한다(ADR 0021 "서버 경로 원천의 폴더").
- [정함] 커넥터 이름은 `server_path`이고 설정은 `folder` 하나다. 값은 부모 폴더 기준의 상대 경로이고 여러 단계를 받는다(`규정집/인사`). 빈 값, `.`, `..` 토막이 든 값, `/`로 시작하는 값, 역슬래시나 NUL이 든 값은 받지 않고, 만드는 함수가 `invalid_config`로 알린다(커넥터 인터페이스 절). 끝의 `/`는 떼고 저장한다. `.`을 받지 않으므로 부모 폴더 자체는 원천이 될 수 없고, 부모 폴더 바로 아래의 파일(묶음의 `sources/README.txt`)은 어느 원천에도 들지 않는다(PR 직전 리뷰가 넘긴 물음).
- [정함] 경로 확인은 부모 폴더에서 원천 폴더까지의 토막마다 한다. 어느 토막이든 심볼릭 링크이거나 폴더가 아니면 `rejected`다. 확인하는 때는 원천을 만들 때, 폴더를 고칠 때, 원천을 되살릴 때, 연결 확인, 동기화의 시작, 그리고 파일 하나를 읽을 때다. 파일을 읽을 때는 원천 폴더에서 그 파일까지의 토막도 같은 방식으로 보고, 마지막 토막이 보통 파일이 아니면 읽지 않는다. 색인 작업이 원본을 읽을 때도 이 확인을 지난다. 읽을 키에 빈 토막, `.`이나 `..` 토막, 역슬래시나 NUL이 있거나 키가 `/`로 시작하면 파일 시스템을 부르지 않고 `rejected`로 알린다. 키는 `list()`가 낸 것뿐이라 보통은 닿지 않지만, `fetch`는 커넥터의 공개 입력이고 링크를 따르지 않는 열기(`O_NOFOLLOW`)는 링크만 막고 링크가 아닌 `..`은 막지 못하기 때문이다(PR 직전 리뷰가 냈다).
- [정함] 확인과 열기는 한 동작으로 한다. 경로를 먼저 확인하고 나중에 같은 경로를 다시 여는 구현은, 그 사이에 원천 폴더에 쓸 수 있는 쪽이 토막 하나를 심볼릭 링크로 바꿔 놓으면 부모 폴더 밖의 파일을 읽게 된다(PR 직전 리뷰가 냈다). 그래서 서버 경로 커넥터는 부모 폴더를 연 자리에서 시작해 토막마다 링크를 따르지 않는 열기로 내려가고(리눅스의 `O_NOFOLLOW`와, 연 폴더를 기준으로 그 아래 이름을 여는 열기), 마지막에 연 파일이 보통 파일인지 그 연 파일로 확인한 뒤 거기서 읽는다. 마지막 토막은 막히지 않는 열기(`O_NONBLOCK`)를 더해 연다. 쓰는 쪽이 없는 이름 있는 파이프(FIFO)는 읽기로 여는 호출 자체가 돌아오지 않아, 연 파일로 종류를 확인하기 전에 멈추기 때문이다. 프로브가 쟀다. 제품 작업자 이미지에서 FIFO를 `O_RDONLY|O_NOFOLLOW`로 연 호출은 3초 뒤에도 돌아오지 않았고, `O_NONBLOCK`을 더하자 0.00초에 돌아와 연 파일이 FIFO로 보였다. 보통 파일은 `O_NONBLOCK`을 더해 열어도 쓴 바이트가 그대로 읽혔다(`fifo-open/probe_out_linux.txt`의 A, B, C). 목록은 FIFO를 열지 않고 뺀다(보통 파일이 아닌 것. 아래 항목). 그래서 이 열기가 막는 것은 목록을 받은 뒤 그 자리가 FIFO로 바뀐 파일의 `fetch`다. 목록도 연 폴더에서 그 폴더의 항목을 읽으며 내려간다. 토막이 링크로 바뀌어 있으면 열기 자체가 실패하고, 커넥터는 확인에 걸린 것과 똑같이 다룬다. 이 열기는 제품이 도는 리눅스에 있고 개발 기계의 Windows에는 없다(손으로 봤다. `hasattr(os, 'O_NOFOLLOW')`, `os.open in os.supports_dir_fd`, `os.scandir in os.supports_fd`를 찍는 한 줄이 개발 PC에 지어져 있던 서버 이미지 `rag-engine-test/rag-engine-server:0.1.0-rc.1`의 Python 3.12.16에서는 셋 다 `True`를, 개발 PC의 Python 3.12.10에서는 셋 다 `False`를 냈다. 그 이미지를 어느 커밋에서 지었는지는 보지 않았다). 이 열기가 없는 운영체제에서는 커넥터가 확인한 뒤 여는 길로 돌고 그 틈을 닫지 못한다. 제품 이미지는 리눅스라 늘 앞의 길로 돈다. 파서의 메모리 상한이 같은 꼴이다(리눅스에서만 걸리고 시험이 운영체제마다 다른 기대를 적는다. 코드를 읽었다).
- [정함] 원천을 만들 때 폴더가 없으면 422로 거부한다. 이 확인과 아래의 겹침 확인은 커넥터 인터페이스 밖의 일이다(커넥터 인터페이스 절의 만드는 함수 항목). 폴더는 적은 글자 그대로 찾고, 없으면 유니코드 정규화(NFC. 한글을 합쳐 적는 꼴)로 맞췄을 때 이름이 같은 폴더가 하나뿐인 경우에만 그 폴더로 보고 디스크에 있는 이름으로 저장한다. macOS에서 만든 한글 폴더는 풀어 적은 꼴로 저장되어, 운영자가 입력한 이름과 글자가 달라 보이지 않는데도 찾지 못하기 때문이다.
- [정함] 한 원천의 폴더가 지우지 않은 다른 원천의 폴더와 같거나, 그 안에 있거나, 그것을 품으면 409 `source_folder_overlap`으로 거부한다. 같은지는 글자가 아니라 실제 폴더로 가른다(대소문자를 가리지 않는 공유 폴더, 합쳐 적은 한글과 풀어 적은 한글). 폴더가 지금 없어 실제 폴더를 알 수 없는 원천과는 저장해 둔 경로의 글자로 견준다. 폴더가 답하지 않아 실제 폴더를 알 수 없는 원천과도 그렇게 견준다(아래의 폴더 확인 한도 항목). 겹치면 같은 파일이 두 원천의 문서가 되어 검색 결과에 두 번 나온다. 지운 원천과는 견주지 않고, 지운 원천을 되살릴 때 다시 본다(기능 계획과 PR 직전 리뷰가 넘긴 물음).
- [정함] 겹침 확인과 저장은 작업 단위 하나에서 하고, 서버 경로 원천의 폴더를 정하는 요청(원천을 만드는 요청, 폴더를 고치는 요청, 원천을 되살리는 요청)끼리는 차례로 지난다. 차례를 세우지 않으면 `a`를 만드는 요청과 `a/b`를 만드는 요청이 동시에 왔을 때 서로가 넣을 행을 보지 못한 채 둘 다 확인을 지난다(PR 직전 리뷰가 냈다). 원천의 이름은 유일 색인이 받치지만, 폴더의 겹침은 실제 폴더를 봐야 알 수 있어 색인으로 받칠 수 없다. 장치는 PostgreSQL의 트랜잭션 수준 자문 잠금(정해 둔 키 하나를 잡으면 다른 트랜잭션이 같은 키를 기다리고, 커밋이나 롤백에서 풀리는 잠금)이고, 그 작업 단위가 맨 먼저 잡는다. 원천 행을 잠그는 것으로는 아직 없는 행끼리의 겹침을 막지 못하고, 원천 표를 통째로 잠그면 그동안 일정 확인이 기다린다. 자문 잠금이 이 자리에서 그렇게 도는지는 재지 않은 어림이고, Testing Decisions의 시험이 판정한다. 폴더 확인이 한도를 넘긴 요청은 작업 단위를 되돌리므로 이 잠금도 그때 풀린다(아래 항목).
- [사용자 선택] 원천을 만들거나 폴더를 고칠 때 서버가 요청 안에서 하는 폴더 확인(새 폴더의 경로 확인과 다른 원천과의 겹침 확인)은 요청 하나에 10초까지만 기다린다. 연결 확인과 같은 상수다. 끊긴 공유 폴더에서는 이 확인이 돌아오지 않을 수 있고(Further Notes), 그 요청이 위 항목의 잠금을 쥔 채 멈추면 다른 원천의 폴더를 정하는 요청도 함께 멈춘다. 정한 것은 넷이다. 첫째, 새 폴더의 확인이 10초 안에 끝나지 않으면 422로 거절하고 까닭의 종류를 `unreadable`로 싣는다(관리 API 절). 권한이 없어 읽을 수 없는 폴더도 같은 응답이다. 둘째, 겹침을 볼 때 다른 원천의 폴더가 그 10초 안에 답하지 않으면 그 원천과는 저장해 둔 경로의 글자로 견준다(위 겹침 항목이 폴더가 없는 원천에 쓰는 규칙과 같다). 다른 원천의 확인은 원천마다 따로 내보내 같은 10초 동안 함께 기다린다. 끊긴 원천 하나 때문에 멀쩡한 원천까지 글자로 견주게 되지 않고, 원천이 많다고 요청이 10초보다 오래 걸리지도 않는다. 셋째, 한도를 넘긴 요청은 작업 단위를 되돌려 잠금을 풀고, 늦게 돌아온 확인은 아무것도 쓰지 못한다. 넷째, 이 확인이 남긴 돌아오지 않는 호출도 동기화의 차례 절의 기억(커넥터 이름과 설정)에 든다. 그래서 같은 폴더로 다시 온 요청은 10초를 다시 기다리지 않고 곧바로 같은 422를 받고, 이미 답하지 않는 것으로 기억된 다른 원천과는 기다리지 않고 글자로 견준다. 지운 원천을 되살리는 요청은 새 폴더를 정하는 것이 아니라서 폴더를 읽을 수 없어도 받고, 겹침만 이 규칙으로 본다(원천 삭제와 되살리기 절). 고르지 않은 안은 둘이다. 다른 원천의 폴더가 하나라도 답하지 않으면 그 요청을 거절하는 안은 겹침을 놓치지 않지만, 끊긴 원천이 하나라도 있는 동안에는 어떤 원천도 만들거나 폴더를 고칠 수 없다. 답하지 않는 폴더를 확인 없이 받는 안에서는 없는 폴더나 겹치는 폴더로 원천이 만들어지고, 운영자는 첫 동기화가 실패하거나 검색에 같은 문서가 두 번 나온 뒤에야 안다. 치르는 값은 셋이다. 첫째, 글자로 견주는 동안에는 대소문자나 한글을 적는 꼴만 다른 같은 폴더를 겹침으로 잡지 못할 수 있다. 둘째, 그렇게 놓친 겹침은 폴더가 다시 답한 뒤에도 서버가 다시 보지 않는다. 겹침은 폴더를 정하는 요청에서만 보기 때문이다. 그때는 같은 파일이 두 원천의 문서가 되어 검색에 두 번 나오고, 운영자가 한쪽 원천의 폴더를 고치거나 그 원천을 지워야 한다. 셋째, 10초 한도는 폴더 확인에만 걸리고 위 항목의 잠금을 기다리는 시간에는 걸리지 않는다. 서로 다른 막힌 폴더로 온 요청이 잇달아 오면 뒤의 요청은 앞의 요청 하나마다 10초까지 더 기다린다(같은 폴더로 다시 온 요청은 기억 덕에 기다리지 않는다). 기다리는 요청은 저마다 데이터베이스 연결 하나를 쥔다. 잠금을 작업 단위 안에서 잡기 때문이다. 서버의 연결은 기본 15개까지라(`src/rag_engine/adapters/postgres/engine.py`를 읽었다) 그런 요청이 그만큼 겹치면 검색도 연결을 기다린다(PR 직전 리뷰가 냈다). 잠금을 기다리는 시간에도 한도를 둘지는 ADR 0023이 받아들인 이 값을 바꾸는 일이라 사용자의 판단으로 남겼다(일지 `2026-11-22-0344-source-sync-tickets.md`). 둘째와 셋째는 셀프 리뷰가 냈다(첫째와 이 항목의 규칙은 사용자가 2026-11-21에 골랐다. ADR 0023 "서버가 요청 안에서 하는 폴더 확인". 앞서는 이 한도와 응답을 정하지 않은 채 Further Notes에 적어 두었다).
- [정함] 목록은 원천 폴더 아래를 끝까지 걸어 보통 파일을 모두 낸다. 키는 원천 폴더 기준의 상대 경로이고 토막을 `/`로 잇는다(ADR 0008). 키는 디스크에 있는 이름 그대로이고 정규화하지 않는다. 제목만 NFC로 맞춘다. 키를 고치면 그 키로 파일을 다시 찾지 못한다.
- [정함] 심볼릭 링크(파일이든 폴더든), 보통 파일이 아닌 것(소켓, 장치), 이름을 UTF-8로 읽을 수 없는 파일은 목록에 넣지 않는다. 그 수는 동기화 기록에 세지 않고 작업자 로그에 종류별 개수만 한 줄 남긴다. 열거 항목에 "받지 않은 것"을 싣는 칸을 인터페이스에 더하지 않으려는 것이다.
- [정함] 걷는 도중에 하위 폴더를 읽지 못하면(권한, 끊긴 공유 폴더) 그 폴더를 빼고 계속하지 않고 `unreadable`로 목록 전체를 실패시킨다(ADR 0022 Consequences의 조건 "목록을 받는 도중에 난 읽기 오류(하위 폴더의 권한, 끊긴 공유 폴더)는 줄어든 목록으로 삭제를 반영하지 않고 그 동기화를 실패로 본다").
- [넘겨받음] 변경 확인값은 파일의 수정 시각과 크기다(ADR 0022 "동기화의 차례"). 문서의 갱신일은 파일의 수정 시각으로 채운다.
- [정함] 변경 확인값의 글은 수정 시각(나노초 단위 정수)과 크기를 쌍점으로 이은 문자열이다. 서버는 그 글이 같은지만 본다.
- [정함] 서버 경로 원천의 문서에서 MIME은 키의 확장자로 정하고, 메타데이터는 빈 객체다. 제목과 갱신일 밖의 메타데이터(작성 부서, 시행일)는 파일에서 얻을 곳이 없어 채우지 않는다(기능 계획이 명세에 넘긴 "메타데이터 대응"). 칼럼에서 그 값을 가져오는 일은 db-source가 매핑으로 정한다.
- [정함] 원천의 폴더는 만든 뒤에 고칠 수 있다(ADR 0021이 명세에 넘겼다). 고치면 다음 동기화가 새 폴더의 목록으로 대 보므로, 새 폴더에 같은 키가 없는 문서는 임시 삭제되고 새 파일은 새 문서로 들어온다. 그룹은 고칠 수 없다. 그룹을 바꾸면 그 원천 문서의 조각이 든 지식베이스가 통째로 바뀌는데, 그 길은 그룹과 지식베이스의 관리 API를 짓는 admin이 정한다(Out of Scope).

### 수집 정책

- [넘겨받음] 지원하지 않는 형식(PDF, DOCX, HWPX 밖), 크기 상한을 넘는 파일, 제외 패턴에 맞는 파일은 문서로 만들지 않고 동기화 기록에 사유별 개수만 남긴다. 기본 제외는 숨김 파일과 폴더, 오피스 임시 파일(이름이 `~$`로 시작)이고 원천마다 제외 패턴을 더할 수 있다(ADR 0022 "남기는 것").
- [정함] 수집 정책은 커넥터가 아니라 서버가 적용한다(기능 계획이 넘긴 물음). 커넥터는 원천에 있는 것을 그대로 내고 서버가 걸러야, 사유별 개수를 서버가 셀 수 있고 설치처가 만든 커넥터도 같은 정책을 받는다.
- [정함] 적용하는 차례와 사유 이름은 다음과 같다. 먼저 제외 패턴이고(`excluded`), 다음이 형식이며(`unsupported_type`), 마지막이 크기다(`too_large`). 파일 하나는 처음 걸린 사유 하나로만 센다.
- [정함] 기본 제외는 키의 어느 토막이든 `.`으로 시작하는 것과 마지막 토막이 `~$`로 시작하는 것이다. 원천의 제외 패턴으로 끌 수 없다.
- [정함] 제외 패턴은 glob이다. `*`는 `/`를 뺀 글자 여럿, `?`는 `/`를 뺀 글자 하나, `**`는 `/`를 넘는 글자 여럿에 맞는다. 패턴에 `/`가 없으면 키의 토막 하나하나(폴더 이름과 파일 이름)에 대 보고, 어느 토막에든 맞으면 제외한다. 그래서 `임시`는 `임시`라는 폴더 아래 전부를, `*_초안.docx`는 어느 폴더에 있든 그 이름의 파일을 뺀다. 패턴에 `/`가 있으면 키 전체에 대 본다. 대소문자를 가린다. 원천 하나에 50개까지, 패턴 하나는 200자까지 받는다.
- [정함] 형식은 키의 확장자만으로 가른다. `.pdf`, `.docx`, `.hwpx`(대소문자를 가리지 않는다)가 아니면 읽지 않고 `unsupported_type`으로 센다. 수집 API는 확장자가 셋 밖이면 바이트 머리로 형식을 가리지만(코드를 읽었다), 동기화가 그렇게 하면 폴더의 모든 파일을 읽어야 한다. 설치처가 만든 커넥터도 같은 규칙을 받으므로, 키가 이 세 확장자로 끝나지 않는 항목은 문서가 되지 않는다. 이것을 인터페이스의 설명에 적는다. 게시글 번호처럼 확장자가 없는 키와 파일이 아닌 본문 글을 문서로 받는 길은 db-source가 정한다(Out of Scope).
- [정함] 크기는 목록이 준 크기로 먼저 거르고, 읽을 때 커넥터가 한 번 더 지킨다(목록을 받은 뒤 커진 파일, 목록이 크기를 내지 않는 커넥터의 파일). 읽다가 `too_large`가 나온 파일은 목록에서 크기로 걸린 파일과 똑같이 다룬다. 같은 사유로 세고 후보에서 뺀다. 그래서 그 키의 문서가 이미 색인에 있으면 같은 동기화의 삭제 반영이 지운다(아래 항목). 읽지 못해 실패로 세고 문서를 그대로 두는 파일(동기화의 차례 절)로 다루지 않는다. 그렇게 두면 상한을 넘게 된 파일의 옛 내용이 검색에 남고, 목록이 크기를 내지 않는 커넥터에서는 동기화를 몇 번 돌려도 그대로 남는다(PR 직전 리뷰가 냈다).
- [정함] 수집 정책에 걸린 파일의 문서가 이미 색인에 있으면 목록에 없는 문서와 똑같이 삭제 반영한다. 제외 패턴을 더한 다음 동기화에서 그 패턴에 맞는 문서가 검색에서 빠진다. 패턴을 걷으면 그다음 동기화가 되살린다. 다만 그렇게 걸러서 후보가 하나도 남지 않으면 삭제를 반영하지 않는다(동기화의 차례 절의 빈 목록 판정).

### 동기화의 차례

- [넘겨받음] 동기화 한 번은 가져오는 원천 하나에 대해 다섯 가지를 차례로 한다. 커넥터로 원천의 목록을 받고, 색인의 문서 목록과 대 보고, 새 문서와 바뀐 문서를 넣고, 목록에 없는 문서를 임시 삭제하고(삭제 반영), 결과를 동기화 기록에 남긴다. 동기화 한 번은 작업 대기열의 작업 하나로 돈다(ADR 0022 "동기화의 차례").
- [정함] 시작할 때 원천과 커넥터를 본다. 원천에 지움 표시가 있으면 `source_deleted`로, 커넥터가 없거나 인터페이스 버전이 맞지 않으면 `connector_unavailable`로 끝낸다. 그 뒤 동기화 기록을 `running`으로 쓰고 시작 시각을 적는다.
- [정함] 목록은 끝까지 받은 뒤에 쓴다. 받는 도중에 예외가 나면 그 동기화는 아무것도 넣지도 지우지도 않고 실패로 끝난다. 사유는 커넥터의 예외가 `unreadable`이면 `source_unreadable`, `rejected`면 `source_path_rejected`, 그 밖이면 `connector_error`다.
- [정함] 받은 목록에 수집 정책을 적용해 후보를 만든다. 대조와 삭제 반영은 후보를 쓴다.
- [넘겨받음] 원천 폴더가 없거나, 목록이 0건인데 색인에는 그 원천의 문서가 있으면 삭제를 반영하지 않고 그 동기화를 실패(사유: 원천을 읽을 수 없음)로 기록한다. 운영자가 정말로 폴더를 비운 것이면 "지금 동기화"에 "빈 목록도 반영"을 켜서 돌린다(ADR 0022 "목록이 비면 지우지 않는다").
- [사용자 선택] 문서가 될 파일이 하나도 없을 때도 지우지 않는다. 빈 목록인지는 수집 정책을 적용한 뒤의 후보로 가른다(기능 계획이 넘긴 물음). 후보가 0건이고 그 원천에 지워지지 않은 문서가 하나라도 있으면 삭제를 반영하지 않고 그 동기화를 실패로 끝낸다. 되살린 원천에서 원천 되살리기 작업을 기다리는 문서(원천과 함께 지워졌다는 표시가 남은 문서)도 이 판정에서는 있는 문서로 센다. 실패 사유는 둘로 가른다. 커넥터가 낸 항목이 0건이면 `source_unreadable`이고, 항목은 있는데 모두 수집 정책에 걸렸으면 `nothing_accepted`다. 폴더는 읽혔는데 "읽을 수 없음"으로 알리면 운영자가 권한이나 연결을 살피게 되어 사유를 갈랐다. 뒤의 경우에는 동기화 기록에 목록 건수(`listed`)와 걸린 사유별 개수(`not_accepted`)가 남아 운영자가 무엇에 걸렸는지 본다. 목록을 받지 못한 실패에서는 `listed`가 비어 있고, 받았는데 0건이었으면 0이다. 고르지 않은 안은 수집 정책을 적용하기 전의 목록으로 가르는 안이다. 그 안에서는 파일은 있는데 모두 수집 정책에 걸린 경우를 목록대로 반영하므로, 공유 폴더가 붙지 않은 자리에 문서가 아닌 파일만 있을 때(붙지 않았음을 알리려고 둔 표시 파일, 숨김 파일) 그 원천의 문서가 모두 검색에서 빠진다(PR 직전 리뷰가 냈고, 사용자가 2026-11-21에 이 경우도 막는 쪽을 골랐다). 치르는 값은 제외 패턴이나 크기 상한으로 일부러 모든 파일을 뺀 운영자도 "빈 목록도 반영"을 한 번 켜서 돌려야 한다는 것이다. 한 번 반영하고 나면 그 원천에 문서가 없으므로 그 뒤의 일정은 이 판정에 걸리지 않는다.
- [이력] ADR 0022의 본문은 원천 폴더가 없거나 목록이 0건일 때 지우지 않는다고 적는다. 위 항목이 문서가 될 파일이 하나도 없을 때까지 넓혔으므로, 본문만 읽으면 지금의 범위를 좁게 알게 된다. 그 ADR에 2026-11-21 이력을 더하고 그 문장 뒤에 포인터를 달았다. 일부만 줄어든 경우는 목록대로 지운다는 것과 한 번에 지우는 양에 비율 한도를 두지 않는다는 것은 그대로다.
- [정함] 이 판정은 두 자리에서 한다. 후보를 만든 직후와 삭제 반영을 시작하기 직전이다. 뒤의 자리는 읽다가 `too_large`가 나와 후보가 모두 빠진 경우를 잡는다(수집 정책 절. 목록이 크기를 내지 않는 커넥터에서 난다). 후보가 모두 빠졌다는 것은 읽은 파일이 모두 상한을 넘었다는 뜻이라 그때까지 넣은 문서가 없고, 그 동기화는 `nothing_accepted`로 끝나며 아무것도 지우지 않는다.
- [정함] "빈 목록도 반영"은 폴더가 있고 목록을 끝까지 받았는데 후보가 0건일 때만 통한다. 목록이 0건인 경우와 파일이 모두 수집 정책에 걸린 경우다. 켜고 돌린 동기화는 위의 두 자리를 모두 지나 삭제를 반영하고 성공으로 끝난다. 폴더가 없거나 읽지 못하면 켜도 실패한다(PR 직전 리뷰가 넘긴 물음. ADR 0022는 이 옵션을 운영자가 폴더를 비운 경우의 길로만 적었다. 폴더가 없을 때 통하지 않게 한 것은 그 범위 안이고, 파일이 모두 수집 정책에 걸린 경우에도 통하게 한 것은 위 이력이 적는다). 폴더가 사라진 원천의 문서를 검색에서 빼려면 운영자가 빈 폴더를 그 자리에 만들어 두고 이 옵션으로 동기화하거나, 원천을 지운다. 설치 안내가 이 길을 적는다.
- [정함] 대조는 후보마다 같은 (원천, 키)의 문서를 찾아 넷으로 가른다. 문서가 없거나, 삭제 기록만 있거나, 임시 삭제되어 있으면 새 문서다. 문서가 있고 변경 확인값이 같으면 파일을 읽지 않는다. 문서가 있고 변경 확인값이 다르거나 비어 있으면 파일을 읽어 내용 해시를 비교한다. 읽지 못하면 그 파일은 실패로 세고 문서는 그대로 둔다. 커넥터가 `too_large`로 알린 파일은 읽지 못한 것이 아니라 수집 정책에 걸린 것이라 후보에서 뺀다(수집 정책 절).
- [넘겨받음] 변경 확인값이 앞서 받은 값과 같으면 파일을 읽지 않는다. 달라졌으면 읽어서 내용 해시를 비교하고, 내용이 같으면 다시 색인하지 않는다(ADR 0022 "동기화의 차례", ADR 0012).
- [사용자 선택] "지금 동기화"에 "모두 다시 읽기" 옵션을 둔다(ADR 0022가 "변경 확인값이 같아도 원천의 파일을 모두 다시 읽게 하는 길을 둘지는 명세가 정한다"로 넘겼다). 켜고 돌린 동기화는 변경 확인값이 같아도 후보의 파일을 모두 읽어 내용 해시를 비교한다. 내용이 바뀐 파일은 바뀐 문서로 넣고, 내용이 그대로인 문서 가운데 실패했거나 건너뛴 것은 색인 작업을 다시 넣어 다시 시도시키며, 내용이 그대로이고 색인된 문서는 건드리지 않는다. 일정이 시작한 동기화에는 이 옵션이 없다. 옵션을 두지 않는 안은 고르지 않았다. 그 안에서는 수정 시각과 크기가 그대로인 채 내용만 바뀐 파일과 실패로 남은 문서를 다시 처리하려면 운영자가 파일의 수정 시각을 바꾸거나 지식베이스 전체를 재색인해야 한다.
- [이력] ADR 0012의 본문은 변경 확인값이 "같으면 받기를 건너뛰고, 다르면 받아 내용 해시로 다시 확인한다"고 적는다. "모두 다시 읽기"로 돌린 동기화는 값이 같아도 받으므로 그 문장이 그대로는 참이 아니다. 그 ADR에 2026-11-21 이력을 더하고 그 문장 뒤에 포인터를 달았다. 커넥터가 열거할 때 크기를 함께 내는 것(커넥터 인터페이스 절)과 인터페이스 버전의 값 `1.0.0`은 본문에 더하기만 하는 것이라 같은 이력에 적어 두기만 했다.
- [정함] "모두 다시 읽기"가 다시 넣은 색인 작업이 문서를 다시 파싱할지는 core 명세의 조건 그대로다(파싱 결과가 없거나, 파싱한 내용 해시가 다르거나, 파서 버전이 바뀌었을 때). 그래서 암호가 걸린 문서와 파싱에 실패한 문서는 다시 파싱하고, 글자가 없는 문서는 파서 버전이 바뀌었을 때만 다시 파싱한다.
- [정함] 새 문서와 내용이 바뀐 문서는 수집 유스케이스로 넣는다. 그룹은 원천의 그룹이고, 원본은 파일 저장소에 쓰지 않으며, 변경 확인값을 문서 행에 함께 적는다. 임시 삭제된 문서가 돌아온 경우의 되살림(내용이 같으면 삭제 보관함의 조각을 되돌린다)은 core 명세의 규칙 그대로다. 문서마다 작업 단위 하나이고, 넣은 문서의 색인 작업은 동기화 작업의 요청 ID를 잇는다.
- [정함] 읽어 보니 내용이 같은 문서는 변경 확인값만 새 값으로 적는다. 갱신일을 포함해 다른 칸은 고치지 않는다. 내용이 그대로면 복사만 다시 한 파일이고, 갱신일을 고치면 조각의 복사 칸까지 다시 써야 한다.
- [정함] 문서를 넣거나 지우는 작업 단위마다 원천의 지움 표시를 다시 본다. 표시가 서 있으면 그 문서를 쓰지 않고 동기화를 `source_deleted`로 끝낸다(원천 삭제와 되살리기 절). 삭제 반영 도중에 끝나면 그때까지 지운 문서는 지운 채로 남고, 나머지 문서는 지우지 않는다. 지운 채로 남은 문서에는 원천과 함께 지워졌다는 표시가 없다. 그래서 원천보다 먼저 따로 지운 문서와 같게, 원천을 되살려도 돌아오지 않고 보관 기간도 그 문서를 지운 날부터 센다(원천 삭제와 되살리기 절, 정리 작업 절). 목록에서 사라졌거나 수집 정책에 걸린 파일의 문서라 그대로 두고, 그 파일을 폴더에 되돌려 놓거나 걸린 정책을 걷으면 다음 동기화가 되살린다(문서 되살리기 절. PR 봇 리뷰가 냈고, 명세 검토가 수집 정책에 걸린 경우를 더했다).
- [정함] 삭제 반영은 넣기가 끝난 뒤에 한다. 시작하기 전에 위의 빈 목록 판정을 한 번 더 하고(후보가 하나도 남지 않았으면 지우지 않는다), 지나면 그 원천의 지워지지 않은 문서 가운데 후보에 키가 없는 것을 문서마다 임시 삭제한다. 문서 하나를 지우는 일은 core 명세의 삭제 절차 그대로이고 문서마다 작업 단위 하나다. 이번에 읽지 못해 실패로 센 파일은 후보에 있으므로 지우지 않는다. 읽다가 `too_large`가 나온 파일은 후보에서 빠졌으므로 그 키의 문서를 지운다. 되살린 원천에는 이미 지워져 있으면서 원천과 함께 지워졌다는 표시가 남은 문서(원천 되살리기 작업이 아직 되살리지 않은 문서)가 있을 수 있다. 그런 문서도 후보에 키가 없으면 표시를 지우고 지운 시각을 그 순간으로 고쳐, 원천 되살리기 작업이 폴더에서 이미 사라진 파일의 문서를 되살리지 않게 한다(원천 삭제와 되살리기 절).
- [정함] 동기화 한 번이 끝나는 때는 동기화 작업이 끝날 때다. 넣은 문서의 색인이 끝나기를 기다리지 않는다(ADR 0022가 명세에 넘겼고 Consequences의 조건 "삭제 반영은 그 동기화가 넣은 문서의 임베딩이 끝나기를 기다리지 않는다"를 지킨다). 겹침도 이 작업이 대기 중이거나 실행 중인지로 가른다.
- [정함] 동기화 작업은 도는 동안 작업 담당 기록의 기한을 늘린다(색인 작업과 같은 장치). 색인 작업이 그러듯(코드를 읽었다) 진행과 상관없이 정해 둔 간격으로 늘린다. 느린 공유 폴더에서 큰 파일 하나를 읽는 동안 기한이 지나 그 동기화를 잃는 일을 막는다(PR 봇 리뷰가 냈다. 앞서는 목록의 항목을 받을 때와 문서 하나를 처리했을 때만 늘리게 적었는데, 그러면 기한보다 오래 걸리는 읽기 하나가 재시도마다 같은 자리에서 끊긴다). 돌아오지 않는 읽기가 자리 하나를 끝없이 잡는 것은 기한이 아니라 아래의 커넥터 호출 한도가 막는다. 동기화는 기한을 늘릴 때마다 원천의 지움 표시도 본다(아래의 끝없는 목록 항목). 작업자가 죽으면 기한이 지난 뒤 다른 작업자가 그 작업을 가져가 처음부터 다시 한다. 이미 넣은 문서는 변경 확인값이 같아 다시 읽지 않으므로 다시 해도 결과가 같다. 죽은 동기화가 겹침 판정을 잡고 있는 시간은 그 기한(`RAG_JOB_LEASE_SECONDS`, 기본 600초)까지다(ADR 0022 Consequences의 조건 "죽은 동기화가 겹침 판정을 계속 잡고 있지 않는다").
- [넘겨받음] 목록을 받지 못한 동기화는 실패로 기록하고 다음 일정에 다시 한다(ADR 0022 "실패").
- [정함] 그래서 원천 쪽의 까닭으로 실패한 동기화(`source_unreadable`, `nothing_accepted`, `source_path_rejected`, `connector_unavailable`, `connector_error`, `source_deleted`)는 작업의 재시도 규칙을 타지 않고 한 번에 실패로 끝난다. 데이터베이스가 끊긴 것 같은 일시 실패만 색인 작업과 같은 규칙으로 다시 예약한다.
- [사용자 선택] 돌아오지 않는 커넥터 호출의 규칙은 위의 기한 늘리기와 아래 여섯 항목이다. PR 봇 리뷰를 반영하며 사용자 승인 없이 더했던 규칙 여섯(기한 늘리기, 기다리는 한도, 한도보다 느린 읽기의 길, 읽기를 맡는 스레드, 원천마다 끝나지 않은 호출 수의 상한, 남아 있는 동안 다시 부르지 않기)을 설계 인터뷰가 다시 봤고, 사용자가 2026-11-21에 상한만 걷고 나머지를 두는 쪽을 골랐다(ADR 0023. 일지 `docs/journal/2026-11-21-2139-source-sync-stuck-calls-design.md`). 고르지 않은 안은 셋이다. 여섯을 그대로 두고 프로세스 전체의 상한을 더하는 안, 커넥터를 따로 띄운 프로세스에서 부르고 한도를 넘기면 그 프로세스를 끝내는 안, 기한 늘리기만 두고 나머지를 걷는 안이다. 안마다 치르는 값은 ADR 0023 Considered Options에 있다. 둘째 안은 둘째 커넥터를 짓는 db-source가 다시 본다(Out of Scope).
- [정함] 작업자는 커넥터 호출 하나를 정해 둔 시간만큼만 기다린다(PR 봇 리뷰가 냈다). 작업자가 커넥터를 부르는 자리는 동기화의 `list()`와 `fetch`, 색인 작업의 `fetch`이고 `check()`는 부르지 않는다. 동기화를 시작하며 하는 경로 확인은 `list()`가 첫 항목을 내기 전에 그 안에서 한다. 호출 하나는 `list()`가 다음 항목을 내거나 끝날 때까지와 `fetch` 한 번이다. 한도는 항목 하나에 걸리고, 목록 전체가 끝나는 조건(전체 시간이나 항목 수의 상한)은 두지 않는다(아래의 끝없는 목록 항목). 한도는 `RAG_SOURCE_READ_TIMEOUT_SECONDS`(기본 600초)이고 작업 담당 기록의 기한과 따로 둔다. 한도를 기한에 묶으면, 느린 공유 폴더 때문에 한도를 늘리는 설치에서 죽은 작업자의 작업을 되찾는 시간까지 함께 늘어난다. 한도를 넘기면 기다리기를 그만둔다. 동기화는 `source_unreadable`로 끝난다. 원천 쪽 실패라 다시 시도하지 않고, 그때까지 넣은 문서는 그대로 두며 삭제는 반영하지 않는다. 읽지 못한 파일 하나를 실패로 세고 계속하는 경우(위의 대조 항목)와 달리 동기화를 끝내는 것은, 한도를 넘긴 호출이 남아 있는 동안에는 그 커넥터를 같은 설정으로 더 부르지 않기 때문이다(아래의 돌아오지 않는 호출 항목). 도는 중에 다른 자리의 호출이 먼저 한도를 넘겨 그 설정이 막혀도 같다. 그 동기화가 다음에 부르려던 호출은 나가지 않고, 동기화는 남은 파일을 하나씩 실패로 세지 않고 `source_unreadable`로 끝난다. 색인 작업은 일시 실패 `source_unreadable`로 다시 예약된다(가져오는 원천의 문서 색인 절).
- [정함] 한도보다 오래 걸리는 읽기는 끊긴 것이 아니어도 끝나지 못한다. 기본값에서는 크기 상한(100MB)에 가까운 파일을 초당 170KB쯤보다 느리게 읽는 공유 폴더가 그렇다(상한을 한도로 나눈 값이고 잰 것이 아니다). 그런 파일이 하나 있으면 동기화가 그 파일에서 매번 `source_unreadable`로 끝나, 차례가 그 뒤인 파일과 삭제 반영에 닿지 못한다. 어느 파일에서 걸렸는지는 동기화 기록에도 로그에도 남지 않는다(문서의 키를 싣지 않는다. 로그 절). 그래서 운영자가 가는 길은 한도를 늘리는 것과 크기 상한을 낮추는 것이다(크기 상한은 수집 API와 함께 쓰는 값이라 그쪽도 함께 낮아진다). 크기 상한을 낮추면 걸린 파일만이 아니라 새 상한을 넘는 파일이 모두 수집 정책에 걸려, 그 파일들의 문서가 다음 동기화에서 삭제 반영되고 검색에서 빠진다(수집 정책 절. PR 봇 리뷰가 냈다). 그 문서들을 남기려면 한도를 늘리는 길을 먼저 쓴다. 걸린 파일을 짐작할 수 있으면(가장 큰 파일) 제외 패턴으로 뺄 수도 있다. 제외 패턴으로 뺀 파일도 수집 정책에 걸린 파일이라, 그 파일의 문서가 이미 색인에 있으면 다음 동기화에서 삭제 반영되어 검색에서 빠진다(수집 정책 절). 크기 상한을 낮추거나 제외 패턴을 더한 뒤 문서가 될 파일이 하나도 남지 않으면, 그 동기화는 `nothing_accepted`로 실패하고 아무것도 지우지 않는다(위의 빈 목록 판정). 이 두 결과는 앞서 이 항목에 빠져 있었다. 한도를 넘겼다는 것은 작업자 로그의 한 줄로 안다(로그 절). 설치 안내가 이 길을 적는다. 읽는 도중의 진행을 보고 더 기다릴지를 정하는 안은 고르지 않았다. `fetch`는 바이트를 한 번에 내는 모양이라(ADR 0012) 서버가 읽기의 진행을 볼 수 없고, 보려면 커넥터 인터페이스를 바꿔야 한다.
- [정함] 파일을 읽고 해시를 계산하는 일은 스레드로 넘겨, 동기화가 도는 동안에도 같은 작업자의 다른 자리와 일정 확인이 멈추지 않게 한다. 서버 경로 커넥터가 파일 시스템을 부르는 스레드는 이벤트 루프의 기본 스레드 풀에서 꺼내지 않고, 원천끼리 나눠 쓰는 풀에서도 꺼내지 않는다. 호출마다 스레드를 새로 하나 띄우고, 같은 설정의 호출끼리도 스레드를 나눠 쓰지 않는다(앞서는 원천마다 제 스레드를 쓴다고 적었다. 돌아오지 않는 호출을 기억하는 단위가 설정으로 바뀌어 고쳤다). 서버가 인터페이스 밖에서 하는 서버 경로 원천의 폴더 확인(커넥터 인터페이스 절)도 같은 규칙으로 스레드를 띄운다. 이 확인도 끊긴 공유 폴더에서 돌아오지 않을 수 있고, 서버의 기본 풀을 차지하면 검색이 멈추기 때문이다(셀프 리뷰가 냈다). 기본 풀은 스레드 수에 상한이 있고(CPU 수에 4를 더한 값이며 32를 넘지 않는다) 서버와 작업자가 도는 동안 파싱, 원본 파일의 쓰기와 읽기와 지우기, 검색의 키워드 토큰화가 이 풀을 쓴다(코드를 읽었다. 그 밖에 서버가 뜰 때의 준비와 `ingest` 명령도 쓴다. Further Notes). 파싱은 작업자에서, 검색은 서버에서 돈다. 돌아오지 않는 읽기가 그 풀의 스레드를 차지하면 작업자에서는 다른 원천의 색인이, 서버에서는 검색이 멈춘다. 원천끼리 나눠 쓰는 풀도 같아서, 한 원천의 막힌 호출이 그 풀을 채우면 멀쩡한 원천의 호출이 스레드를 얻지 못한다(PR 봇 리뷰가 냈다). 이 스레드는 프로세스가 내려가는 것을 붙잡지 않게 띄운다(파이썬의 daemon 스레드). 프로브가 쟀다. 읽기에 막힌 스레드를 그렇게 띄운 프로세스는 할 일을 마친 뒤 스스로 내려갔다(개발 PC에서 0.50초, 제품 작업자 이미지에서 1.12초). 표준 라이브러리의 스레드 풀이나 이벤트 루프의 기본 풀에 막힌 스레드가 있는 프로세스는 8초를 기다려도 내려가지 않아 프로브가 죽였다(`stuck-calls/probe_out_windows.txt`와 `stuck-calls/probe_out_linux.txt`의 D). 그래서 그 풀을 그대로 쓰면 작업자가 종료 신호를 받아 하던 일을 마친 뒤에도 스스로 내려가지 못하고, Docker가 유예 시간(기본 10초) 뒤에 강제로 끝낼 때까지 남을 것이다(프로브가 잰 것은 할 일을 마친 프로세스가 스스로 내려가는지이고, 종료 신호와 유예 시간은 Docker 문서를 읽은 것이다. Further Notes). 이 프로브는 빈 파이프를 읽는 것으로 막힘을 흉내 냈고, 끊긴 실제 공유 폴더에서의 동작은 Further Notes가 따로 적는다.
- [정함] 끝나지 않은 채 남는 커넥터 호출의 수에는 상한을 두지 않는다. 원천마다의 상한도 프로세스 전체의 상한도 없다. 아래 항목의 기억 때문에, 한 설정이 막힌 것으로 기억된 뒤에는 그 설정으로 새 호출이 나가지 않는다. 그래서 설정 하나에 남는 호출은 기억되기 전에 나가 있던 것뿐이다. 작업자의 자리 하나는 커넥터 호출을 한 번에 하나만 내보내므로(동기화는 파일을 차례로 읽는다. 기본 자리 수는 2다. 코드를 읽었다) 보통은 자리 수를 넘지 않고, 작업 담당 기록을 잃어 거두어진 시도의 호출이 겹치면 그보다 늘 수 있다(아래 항목). 서버에서는 첫 호출이 10초를 넘기기 전에 온 요청의 수만큼이다. 남는 호출 하나가 쥐는 것은 스레드 하나다. 프로브가 쟀다. 읽기에 막힌 스레드 500개를 띄운 프로세스가 실제로 쥔 메모리(VmRSS)는 29064kB에서 36144kB로 늘어 스레드 하나에 14.2kB였다(제품 작업자 이미지에서 쟀다. `stuck-calls/probe_out_linux.txt`의 F). 이 값은 아무것도 읽지 못한 채 빈 파이프에서 막힌 스레드의 것이다. 파일을 읽던 도중에 막힌 `fetch`는 그때까지 읽은 바이트도 쥐고, 서버 경로 커넥터는 크기 상한(기본 100MB)을 넘게 읽지 않으므로 호출 하나에 그만큼까지 늘 수 있다(위 규칙으로 따진 어림이고 재지 않았다. PR 직전 리뷰가 냈다). 앞서는 원천마다 상한(작업자는 자리 수의 네 배, 서버는 넷)을 두고 상한이 차면 프로세스를 다시 띄우게 적었다. 그 수는 재지 않고 정한 것이었다. 그리고 위의 기억이 있으면 설정 하나에 남는 호출은 기억되기 전에 나간 것뿐이라(보통 자리 수 안이다) 원천마다의 상한에는 거의 닿지 않는다. 프로세스 전체에 남는 호출은 막힌 설정의 수에 따라 늘고, 원천마다의 상한은 그 수를 막지 못한다. 수를 세는 장치와 로그와 시험이 느는 데 견주어 막아 주는 것이 거의 없어 걷었다(ADR 0023. 그 ADR은 걷는 까닭을 막힌 스레드가 쥐는 메모리로 적었고, 명세 검토가 이 까닭으로 바로잡았다). 치르는 값은 끊긴 폴더가 많으면 막힌 스레드가 그 수만큼 남고, 읽던 도중에 막힌 호출이면 읽은 바이트도 함께 남는다는 것이다. 폴더가 다시 답하거나 프로세스가 내려가면 없어진다.
- [정함] 돌아오지 않는 커넥터 호출(한도를 넘겨 기다리기를 그만둔 뒤에도 끝나지 않은 호출)은 프로세스(서버, 작업자)가 커넥터의 이름과 그 호출에 쓴 설정(`config`)으로 기억하고, 그렇게 남은 호출이 하나라도 있는 동안에는 같은 커넥터를 같은 설정으로 새로 부르지 않는다(PR 봇 리뷰가 냈다. 일정이 돌 때마다 막힌 호출이 하나씩 쌓이는 것을 막는다). 기억의 단위가 원천이 아니라 커넥터의 이름과 설정인 것은, 원천이 아직 없는 만드는 요청의 폴더 확인까지 한 장치로 묶으려는 것이다(앞서는 원천과 설정으로 적었다. ADR 0023). 한도를 넘겨 기다리기를 그만두는 자리는 넷이다. 동기화의 `list()`와 `fetch`, 색인 작업의 `fetch`(가져오는 원천의 문서 색인 절), 10초를 넘긴 연결 확인의 `check()`(관리 API 절), 10초를 넘긴 폴더 확인(서버 경로 커넥터와 원천 폴더 절)이다. 그런 호출은 취소하지도 끝내지도 않고 둔다. 서버 경로 커넥터의 읽기는 스레드에서 돌고, 읽기에 막힌 스레드는 밖에서 끝낼 길이 없어서 파일 시스템 호출이 돌아올 때까지 남는다. 파이썬 문서는 스레드를 밖에서 없애거나 멈출 수 없다고 적고(조사 서브에이전트가 원문을 받아 봤다. Further Notes), 프로브가 끝내 볼 만한 길 셋을 재 봤다. 한도를 걸면 기다리던 쪽은 한도(1.0초)에 돌아왔지만 읽던 스레드는 살아 있었고, 돌고 있는 일의 취소는 실패했다. 밖에서 스레드에 예외를 넣는 길은 파이썬 코드를 도는 스레드는 끝냈지만 읽기에 막힌 스레드는 끝내지 못했다(`stuck-calls/probe_out_linux.txt`의 A, B, C. 개발 PC의 출력 `stuck-calls/probe_out_windows.txt`도 같다). 작업 담당 기록을 잃어 작업이 거두어질 때 나가 있던 호출은 바로 기억하지 않는다. 멀쩡한 호출이면 곧 돌아오는데, 바로 기억하면 데이터베이스가 끊겨서 잃은 시도의 다음 시도가 원천의 실패로 끝난다. 그 호출이 제 한도까지 돌아오지 않으면 그때 한도를 넘긴 호출로 기억한다. 남아 있는 동안 그 커넥터와 설정을 쓰는 원천의 동기화는 시작할 때든 도는 중이든 `source_unreadable`로 끝나고, 색인 작업의 읽기는 일시 실패 `source_unreadable`이며, 연결 확인은 기다리지 않고 `source_unreadable`로 답하고, 폴더 확인은 기다리지 않고 그 폴더를 읽을 수 없는 것으로 본다. 얼마 동안 다시 부르지 않을지를 시간으로 정하지 않은 것은 남아 있는 호출이 곧 표지이기 때문이다. 폴더가 다시 답하면 그 호출이 돌아온다. 그 설정으로 남은 호출이 모두 돌아오면(공유 폴더가 다시 답했거나 운영체제가 오류를 냈다) 다시 부른다. 운영자가 원천의 설정을 고치면(폴더를 멀쩡한 곳으로 옮겼다) 옛 설정의 호출이 남아 있어도 새 설정으로는 부른다(PR 봇 리뷰가 냈다. 고친 설정이 다음 동기화부터 쓰인다는 관리 API 절의 규칙을 지킨다). 옛 설정의 호출은 폴더가 다시 답하거나 프로세스가 내려갈 때까지 남는다. 이 기억은 프로세스 안에만 있다. 프로세스를 다시 띄우면 비고, 작업자가 여럿이면 저마다 한 번씩 겪는다. 기억은 설정마다 따로다. 같은 공유 폴더에 원천이 여럿이면 원천마다 폴더가 달라서(겹치는 폴더로는 원천을 만들 수 없다), 그 공유 폴더가 끊겼을 때 원천마다 한 번씩 한도만큼 자리를 잡는다. 그동안 다른 원천의 작업은 남은 자리에서 돌고, 자리가 모두 그런 원천에 잡혀 있으면 기다린다. 공유 폴더가 끊긴 뒤 첫 호출이 한도를 넘기기까지는 그 원천의 문서를 읽는 자리가 모두 기다릴 수 있다. 한도를 더 짧게 잡지 않은 것은 큰 파일을 느린 공유 폴더에서 읽는 시간과 끊긴 읽기를 가를 수 없어서다. 이 장치가 풀지 못하는 경우가 하나 있다. 설치처가 만든 커넥터가 읽기를 스레드로 넘기지 않고 비동기 함수 안에서 그대로 막히면, 한도가 지켜지지 않고 그 프로세스의 다른 일도 함께 멈춘다. 프로브가 쟀다. 3초 동안 막히는 호출에 건 1초 한도는 3.00초 뒤에야 돌아왔고, 그동안 같은 프로세스에서 0.1초마다 돌던 다른 일이 한 번도 돌지 못했다(같은 출력의 G). 서버 경로 커넥터는 읽기를 스레드로 넘기므로 걸리지 않는다. 커넥터를 만드는 사람을 위한 안내가 이것을 적도록 db-source에 넘긴다(Out of Scope). 읽기를 스레드에 넘기지 않고 비동기로 하는 커넥터의 호출을 한도에서 취소할지도 db-source가 정한다. 그런 호출은 취소로 끝낼 수 있지만, 끝낸 호출은 남지 않아 이 기억에 들지 않는다. 취소하지 않고 두면 스스로 돌아오지 않는 호출이 프로세스를 다시 띄울 때까지 그 설정을 막는다(셀프 리뷰가 냈다).
- [사용자 선택] 동기화는 작업 담당 기록의 기한을 늘릴 때마다 원천의 지움 표시를 보고, 표시가 서 있으면 `source_deleted`로 끝난다. 기한은 그 삼분의 일마다 늘리므로(코드를 읽었다) 기본값에서는 200초마다 본다. 목록을 받는 중이든 파일 하나를 읽는 중이든 같다. 기한을 늘리는 일은 처리와 따로 돈다(지금의 색인 작업이 그렇다. 작업 담당 기록을 잃은 것이 드러나면 처리를 멈추고 그 시도를 버린다. 코드를 읽었다). 동기화에서는 기한을 늘리는 쪽이 표시를 보면 처리를 멈추되 그 시도를 버리지 않고, 문서를 쓰는 작업 단위에서 표시를 본 동기화와 같게 `source_deleted`로 끝낸다(위 항목. 동기화 기록을 실패로 닫고 다시 시도하지 않는다). 그때까지 넣은 문서와 지운 문서는 그대로 두고 남은 삭제는 반영하지 않는다(넣은 문서는 원천 삭제 작업이 옮기고, 지운 문서는 문서를 넣거나 지우는 작업 단위마다 표시를 보는 위 항목대로 지운 채로 남는다). 그때 나가 있던 커넥터 호출은 작업 담당 기록을 잃어 거두어진 시도의 호출과 같게 다룬다(위 항목). 이 항목을 둔 까닭은 끝없는 목록이다. 커넥터 호출의 한도는 `list()`의 다음 항목 하나에 걸린다. 그래서 한도 안에 새 항목을 끝없이 내는 커넥터의 동기화는 끝나지 않고, 기한은 진행과 상관없이 늘어나므로 그 원천의 삭제 반영과 다음 동기화가 막힌다. 서버 경로 커넥터의 목록은 링크를 따르지 않고 폴더를 훑어 끝이 있으므로, 걸리는 것은 설치처가 만든 커넥터다. 그 커넥터가 비동기 함수 안에서 그대로 막히면 기한을 늘리는 일도 함께 멈춰 이 길로는 멈추지 않는다(위 항목이 적은, 이 장치가 풀지 못하는 경우와 같다. 같은 프로세스의 다른 일이 돌지 못한 것을 프로브의 G가 쟀다). 기다리는 일 없이 항목을 곧바로 끝없이 내는 커넥터는 이 길로 멈춘다. 아래 항목의 규칙(커넥터 호출을 호출마다 따로 띄운 일로 내보낸다)이 작업자를 항목마다 이벤트 루프로 돌아가게 하기 때문이다. 그때까지 받은 항목은 메모리에 쌓인다(목록은 끝까지 받은 뒤에 쓴다. 아래 항목이 그 값을 적는다). 앞서의 명세에는 목록을 받는 중인 동기화를 멈추는 길이 없었다. 지움 표시를 보는 자리가 시작할 때와 문서를 넣거나 지우는 작업 단위마다였는데, 목록은 끝까지 받은 뒤에 쓰므로 받는 중에는 그 자리에 닿지 않았다(PR 봇 리뷰가 냈다). 이제 운영자가 끝나지 않는 동기화를 멈추는 길은 그 원천을 지우는 것이다. 치르는 값은, 멈추려면 원천을 지웠다가 되살려야 하고 그동안 그 원천의 문서가 검색에서 빠진다는 것이다. 되살리기는 그 동기화의 기록이 `source_deleted`로 닫힌 것을 본 뒤에 한다. 지운 뒤 동기화가 표시를 보기 전에(기본값에서는 200초 안에) 되살리면 그 동기화는 표시를 보지 못하고 이어서 돌 수 있고, 그동안 그 원천의 "지금 동기화"와 일정은 계속 `sync_in_progress`에 걸린다(원천 삭제와 되살리기 절. 셀프 리뷰가 냈다). 그때는 다시 지우고 기록이 닫히기를 기다린다. 설치 안내가 이 차례를 적는다. 서버가 이 틈을 막게 하는 안 둘(도는 동안 되살리기를 거절한다, 원천마다 지운 횟수를 적어 가려낸다)은 사용자가 2026-11-21에 고르지 않았다(ADR 0023 Considered Options. 일지의 질문 6). 고르지 않은 안은 셋이다. 동기화 한 번이 받는 목록에 상한(항목 수나 전체 시간)을 두는 안은 사람이 손대지 않아도 멈추지만, 재지 않고 정하는 수와 새 설정이 하나 늘고 파일이 아주 많은 정상 폴더가 걸릴 수 있다. 도는 동기화를 취소하는 요청을 관리 API에 두는 안은 원천과 문서를 건드리지 않고 멈추지만, 경로 하나와 실패 사유 하나가 늘고 그 요청을 쓸 관리자 페이지가 이 기능 뒤에 온다. 아무 길도 두지 않는 안에서는 멈추는 길이 원천을 지운 뒤 작업자를 다시 띄우는 것 하나다(앞서의 규칙을 이어 읽은 어림이고 시험으로 확인한 것이 아니다). 목록 전체의 상한은 db-source가, 동기화를 취소하는 요청은 admin이 다시 본다(Out of Scope. 사용자가 2026-11-21에 골랐다. ADR 0023 "끝없는 목록").
- [사용자 선택] 작업자는 커넥터 호출 하나(`list()`의 다음 항목 하나, `fetch` 한 번)를 호출마다 따로 띄운 일(asyncio의 Task)로 내보내고, 그 일을 취소하지 않은 채 한도까지 기다린다. ADR 0023의 "취소하지도 끝내지도 않고 둔다"를 지키는 꼴이고, 이 꼴에서는 항목을 하나 받을 때마다 작업자가 이벤트 루프로 한 번 돌아간다. 그래서 기다리는 일 없이 항목을 곧바로 끝없이 내는 커넥터의 목록을 받는 중에도 작업 담당 기록의 기한을 늘리는 일이 돌고, 위 항목대로 지움 표시를 보고 멈춘다. 프로브가 쟀다. 그런 반복을 2초쯤 받는 동안, 0.1초마다 깨어나는 같은 루프의 다른 일은 `async for`로 그대로 받거나 항목마다 `asyncio.wait_for`나 `asyncio.timeout`을 걸면 한 번도 돌지 못했고, 항목마다 따로 띄운 일을 기다리면 20번 돌았다(제품 작업자 이미지에서 쟀다. 개발 PC에서는 21번이었다. `endless-list/probe_out_linux.txt`와 `endless-list/probe_out_windows.txt`). 치르는 값은 받는 속도다. 같은 출력(제품 작업자 이미지)에서 그대로 받으면 초당 44만 개쯤, 따로 띄운 일로 받으면 3만 8천 개쯤이었다. 서버 경로 커넥터는 폴더를 훑는 데 이보다 오래 걸릴 것이라 이 차이가 드러나지 않으리라 본다(어림이다). 끝없는 목록을 받는 동안 쌓이는 메모리에는 상한이 없다. 같은 출력에서 받은 항목을 쌓아 둘 때 항목 하나가 250~270바이트쯤이었으므로, 원천을 지운 뒤 동기화가 표시를 보기까지 기본값으로 200초를 받으면 항목이 750만 개쯤 쌓이고 메모리가 2GB쯤 는다(잰 속도와 항목 하나의 메모리를 곱한 어림이다. 제품의 동기화가 항목마다 더 쥐는 것은 넣지 않았다). 원천을 지우지 않으면 끝없이 는다. 단독 compose는 컨테이너에 메모리 상한을 두지 않고 작업자를 `restart: unless-stopped`로 띄운다(배포 파일 묶음의 `compose.yaml`을 읽었다). 그래서 메모리가 모자라 작업자가 죽으면 다시 뜨고, 기한이 지난 뒤 그 동기화를 처음부터 다시 돈다. 원천을 지웠으면 그 시도는 시작할 때 `source_deleted`로 끝나고, 지우지 않았으면 같은 일이 되풀이된다. 목록 전체의 상한은 db-source가 이 메모리와 함께 다시 본다(Out of Scope). 고르지 않은 안은 이것을 한계로만 적고 받는 꼴을 구현에 맡기는 안이다. 그 안에서는 구현이 고른 꼴에 따라 끝없는 목록의 동기화가 원천을 지워도 멈추지 않을 수 있다(사용자가 2026-11-22에 티켓을 나누며 골랐다. 명세 검토가 냈다).
- [정함] 서버가 부르는 `check()` 한 번과 서버 경로 원천의 폴더 확인 한 번도 위 항목과 같은 꼴로 내보낸다. 호출마다 따로 띄운 일로 내보내고, 그 일을 취소하지 않은 채 10초까지 기다린다. 이 둘은 항목을 끝없이 내는 반복이 아니어서 위 항목을 고른 까닭(작업자가 항목마다 이벤트 루프로 돌아간다)이 닿지 않는다. 그래도 ADR 0023의 "한도를 넘긴 호출은 취소하지도 끝내지도 않고 둔다"는 한도를 넘겨 기다리기를 그만두는 네 자리(위의 돌아오지 않는 호출 항목) 모두에 걸리므로, 한 장치로 묶어 그 규칙을 한 곳에서 지킨다. 앞서는 이 둘을 위 항목에 함께 적었는데, 사용자가 고른 선택지는 목록의 다음 항목 하나와 받기 한 번만 들어서 나눴다(셀프 리뷰가 냈다).

### 동기화 기록

- [넘겨받음] 동기화 한 번마다 시작과 끝, 무엇이 시작시켰는지(일정, 손으로), 결과와 실패 사유, 개수(더함, 바뀜, 지움, 그대로, 사유별 건너뜀, 수집 정책에 걸린 파일의 사유별 개수, 실패)를 남긴다. 건너뜀은 문서로 받은 것이고 수집 정책에 걸린 파일은 문서로 만들지 않은 것이라 따로 센다(ADR 0022 "남기는 것").
- [정함] 기록은 동기화 작업을 대기열에 넣는 같은 작업 단위에서 만든다. 상태는 다섯이다. `queued`(대기열에서 차례를 기다린다), `running`, `succeeded`, `failed`, 그리고 `not_started`다.
- [넘겨받음] 앞 동기화가 돌고 있으면 일정이 온 회차는 시작하지 않고 그 사실을 동기화 기록에 남긴다(ADR 0022 "겹침 방지").
- [정함] 그 회차의 기록이 `not_started`다. 작업은 넣지 않고, 실패 사유 칸에 `sync_in_progress`를 적으며, 시작 시각은 비우고 끝 시각은 만든 시각과 같다.
- [정함] 기록의 칸은 다음과 같다. 원천, 작업(없으면 비운다), 시작시킨 것(`trigger`: `schedule`이나 `manual`), 지금 동기화의 옵션, 만든 시각과 시작 시각과 끝 시각, 상태, 실패 사유(`failure_code`), 목록 건수(`listed`), 개수 일곱이다. 개수 가운데 `added`, `updated`, `deleted`, `unchanged`는 수이고, `skipped`, `not_accepted`, `failed`는 사유를 키로 하는 JSON 객체다.
- [정함] 개수는 그 동기화가 파일과 문서를 본 순간의 분류다. `not_accepted`는 수집 정책에 걸린 파일이고 키는 `excluded`, `unsupported_type`, `too_large`다. `added`는 새 문서로 넣은 파일이고 되살린 것을 포함한다. `updated`는 내용이 바뀌어 다시 넣은 파일이다. 내용이 그대로인 파일은 그 문서의 지금 상태로 갈라, 건너뜀이면 `skipped`에 사유별로(`encrypted`, `no_text`), 문서나 색인이 실패로 남아 있으면 `failed`에 오류 코드별로, 그 밖이면 `unchanged`로 센다. 이번에 읽지 못한 파일은 `failed`의 `source_unreadable`로 센다. `deleted`는 삭제 반영으로 임시 삭제한 문서이고, 지워져 있던 문서에서 원천과 함께 지워졌다는 표시를 지운 것도 여기에 센다. 그래서 `listed`는 `not_accepted`, `added`, `updated`, `skipped`, `failed`, `unchanged`를 모두 더한 값과 같다.
- [정함] 새로 들어오거나 바뀐 파일이 건너뜀이나 실패로 끝날지는 색인 작업이 파싱해 봐야 안다. 그런 파일은 이번 기록에 `added`나 `updated`로 세어지고, 다음 동기화의 기록부터 `skipped`나 `failed`로 세어진다. 수락의 "암호가 걸린 파일이 건너뜀으로 기록되는"은 문서 상태와, 그다음 동기화 기록의 `skipped`로 본다.
- [정함] 실패로 끝난 동기화도 그때까지 센 개수를 남긴다. 작업자가 죽어 다른 작업자가 처음부터 다시 돈 동기화의 개수는 마지막 시도가 본 것이라, 앞 시도가 넣은 문서는 `unchanged`로 세어진다.
- [정함] 실패 사유는 닫힌 코드만 적는다(오류 코드 절). 커넥터가 낸 예외의 글, 폴더 이름, 문서의 키와 제목은 기록에 싣지 않는다(원칙 V, PR 직전 리뷰가 넘겼다).
- [정함] 기록은 끝난 지 `RAG_SYNC_RECORD_RETENTION_DAYS`(기본 90일)가 지나면 정리 작업이 지운다. 원천마다 가장 최근 기록 하나는 기간이 지나도 남겨, 오래 돌지 않은 원천의 원천 보기에도 마지막 동기화가 보이게 한다.

### 일정과 일정 확인

- [넘겨받음] 일정은 cron 표현식(분, 시, 일, 월, 요일 다섯 칸)이고 관리 API가 받아 데이터베이스에 보관한다. 일정이 없는 원천은 "지금 동기화"로만 돈다(ADR 0022 "적는 법").
- [정함] 공백으로 가른 칸이 다섯이 아닌 표현식은 라이브러리에 넘기기 전에 거부한다. 프로브가 쟀다. cronsim 2.8은 여섯 칸짜리를 오류 없이 받아 첫 칸을 초로 읽는다(`'*/10 * * * * *'`의 다음 시각이 `06:43:10`, `06:43:20`으로 10초 간격이다). 일곱 칸, 네 칸, 빈 글, `@daily`는 `Wrong number of fields`로 거부한다(`cron-expr/probe_out.txt`의 C). 여섯 칸을 그대로 두면 운영자가 실수로 적은 표현식이 초 단위로 동기화를 시작시킨다(기능 계획이 넘긴 물음이고, 설계에서는 리뷰어의 웹 요약이었다).
- [정함] 값이 틀린 표현식과 오지 않는 날짜(2월 31일)도 저장할 때 거부한다. 프로브가 쟀다. cronsim은 둘 다 표현식을 만들 때 예외를 올렸다(`'61 * * * *'`은 `CronSimError(표현식을 만들 때): Bad minute`, `'0 0 31 2 *'`은 `CronSimError(표현식을 만들 때): Bad day-of-month`. 같은 출력의 D와 E). 응답은 422 `validation_error`이고 어느 칸인지는 `schedule`이며, 라이브러리의 예외 글은 응답에 옮기지 않는다.
- [넘겨받음] 표현식의 시각은 설치 전체에 하나인 시간대 설정으로 읽고 기본값은 한국 시간이다. 작업자가 꺼져 있어 시각을 놓쳤으면 다시 켜졌을 때 한 번만 돌린다(ADR 0022 "시간대", "놓친 일정").
- [정함] 다음 실행 시각은 네 때에 "지금" 다음의 시각으로 다시 계산한다. 일정을 적거나 고칠 때, 일시 중지한 원천을 다시 시작할 때, 지운 원천을 되살릴 때, 일정 확인이 그 원천을 처리했을 때다. 일정을 없애거나, 일시 중지하거나, 원천을 지우면 그 칸을 비운다. 그래서 다시 시작한 직후와 일정을 고친 직후에는 놓친 회차를 바로 돌리지 않고 다음 시각을 기다린다(기능 계획이 넘긴 물음).
- [넘겨받음] 작업자가 원천마다의 다음 실행 시각을 작업 대기열을 살피는 주기에 함께 보고 동기화 작업을 넣는다. 작업자를 여럿 띄워도 같은 일정이 한 번만 시작되게 데이터베이스의 행 잠금으로 가른다(ADR 0022 "시작시키는 쪽").
- [정함] 일정 확인 한 번은 작업 단위 하나다. 다음 실행 시각이 지났고 일시 중지도 지움 표시도 없는 원천의 행을, 다른 연결이 잡은 행은 건너뛰며 잠근다(`FOR UPDATE SKIP LOCKED`). 잡은 원천마다 동기화 기록과 동기화 작업을 넣고(겹치면 `not_started` 기록만 남긴다) 다음 실행 시각을 옮긴 뒤 커밋한다. 놓친 회차가 여럿이어도 한 번만 넣고 지금 다음의 시각으로 옮긴다.
- [정함] 이 모양이 한 번만 시작시킨다는 것을 프로브가 쟀다. 연결 여덟이 원천 40개의 일정을 25회차 동안 동시에 확인했을 때, 시각이 지난 원천을 트랜잭션 하나에서 모두 잡는 이 모양은 넣은 작업이 1000건(기대 1000건)이고 한 원천에 더 들어간 작업이 0건이었다(`schedule-once/probe_out.txt`의 A2). 원천 하나마다 커밋하는 모양도 같았다(A). 잠금 없이 읽고 넣는 대조군은 같은 조건에서 4028건을 넣었고, 읽기와 넣기 사이에 틈을 2ms 둔 쪽은 4728건을 넣었다(B). 프로브가 잰 것은 다음 실행 시각을 옮기고 작업을 넣는 데까지다. 동기화 기록을 만드는 일과 겹침 판정은 프로브에 넣지 않았다. 구현의 시험은 Testing Decisions가 정한다.
- [정함] 일정 확인은 작업자의 자리(작업을 꺼내 처리하는 동시 실행 단위)와 따로 도는 주기 일이다. 자리가 모두 긴 작업을 처리하고 있어도 주기마다 돈다(ADR 0022가 명세에 넘긴 물음. 지금 작업자는 꺼낼 작업이 없을 때만 주기를 기다린다. 코드를 읽었다). 넣은 동기화 작업은 자리가 비는 대로 색인 작업보다 먼저 꺼내진다.
- [정함] 일정 확인이 실패하면(데이터베이스가 끊겼다) 로그에 남기고 다음 주기에 다시 한다. 작업자를 멈추지 않는다.
- [정함] 일정이 넣은 작업에는 일정 확인이 새 요청 ID를 만들어 붙인다. 작업 표의 요청 ID 칸은 비울 수 없고, 그 동기화가 넣은 색인 작업의 로그까지 한 ID로 이어진다.
- [넘겨받음] 일시 중지는 가져오는 원천에만 있다. 일시 중지한 원천은 일정이 와도 동기화를 시작하지 않고, 이미 대기열에 들어간 문서는 끝까지 처리하며, 색인된 문서는 검색에 남는다. 되돌리는 일은 "다시 시작"이다(ADR 0022 "일시 중지").
- [정함] 일시 중지는 일정 확인이 새 동기화를 넣지 않게 할 뿐이다. 그 순간 대기 중이거나 돌고 있던 동기화는 끝까지 돈다. 일시 중지한 원천에도 "지금 동기화"는 받는다. 운영자가 폴더를 정리한 뒤 일정을 켜기 전에 한 번 돌려 보는 길이다(기능 계획이 넘긴 물음).
- [정함] 일정 확인의 "지금"은 인자로 받는다. 시험은 시계를 기다리지 않고 시각을 주어 일정 확인을 한 번 돌린다.

### 작업 대기열

- [넘겨받음] 작업자는 문서 한 건을 색인하는 작업보다 동기화 작업과 정리 작업을 먼저 꺼낸다(ADR 0022 "동기화와 정리 작업을 먼저 꺼낸다").
- [정함] 순서는 작업의 종류로 가르고 우선순위를 적는 칸은 두지 않는다(ADR 0022가 명세에 넘겼다). 색인 작업이 아닌 작업 넷(동기화, 원천 삭제, 원천 되살리기, 정리)을 먼저 꺼내고, 그 안에서는 지금처럼 예약 시각과 식별자 순이다. 그런 작업이 없을 때 색인 작업을 지금 순서대로 꺼낸다. 우선순위가 둘로 고정이라 칸을 두면 쓰지 않는 값이 생긴다.
- [정함] 꺼내는 일은 두 번 묻는다. 먼저 색인 작업이 아닌 것만 그 작업들만 담은 부분 색인으로 묻고, 없으면 지금의 질의로 색인 작업을 묻는다. 프로브가 쟀다. 색인 작업 10만 건이 대기 중일 때 종류를 정렬 키에 넣은 질의 하나는 가운데값 192.8ms였고(지금의 질의는 78.7ms), 색인 작업이 아닌 것만 먼저 묻는 질의는 1.6ms였다(`schedule-once/probe_out.txt`의 F).
- [정함] 원천 단위 작업과 정리 작업이 겹치지 않는 것은 데이터 모델 절의 부분 유일 색인이 받친다. 프로브가 쟀다. 연결 여덟이 같은 원천에 동기화 작업을 동시에 넣는 50회차에서 회차마다 들어간 작업이 하나였고(`{1: 50}`. 연결 여덟이 모두 답하지 않은 회차는 0이었다), 앞 작업이 실행 중일 때는 들어가지 않았고 끝난 뒤에는 들어갔다(같은 출력의 D1, D2). 원천도 문서도 가리키지 않는 정리 작업 둘은 빈 값을 서로 다른 값으로 보는 보통의 유일 색인에서는 둘 다 들어갔고(E1), 빈 값끼리 같은 값으로 보는 색인에서는 둘째가 거부됐다(E2). 겹치면 넣지 않는 문장(`ON CONFLICT`)은 색인의 조건을 바인드 값이 아니라 문장의 글자로 적는다. 바인드 값으로 적은 문장은 같은 연결에서 되풀이하다 실패했고, 제품이 문장을 만드는 SQLAlchemy는 그 조건을 바인드 값으로 만든다(Further Notes).
- [정함] 원천 단위 작업과 정리 작업이 쓰는 작업 단위도 core 명세의 작업 행 조건을 따른다. 작업 단위마다 마지막에 작업 행을 잠가 작업자와 시도 횟수가 꺼낼 때의 값 그대로인지 보고, 아니면 그 작업 단위를 되돌리고 그 시도를 버린다. 기한이 지나 다른 작업자가 가져간 작업을 앞 작업자가 뒤늦게 이어 쓰지 못하게 하는 장치이고, 묶음으로 일하는 작업은 묶음마다 이 확인을 한다.
- [정함] 원천 단위 작업과 정리 작업의 일시 실패(데이터베이스가 끊겼다)는 색인 작업과 같은 재시도 규칙(최대 6번, 간격을 늘려 간다)으로 다시 예약한다. 작업 담당 기록의 기한과 연장, 기한이 지난 작업을 다른 작업자가 가져가는 것도 색인 작업과 같다.
- [정함] 관리 API의 작업 조회는 새 종류를 그대로 보인다. 작업 응답의 종류가 받는 값이 다섯이 되고, 문서 식별자는 비어 있을 수 있으며, 원천 단위 작업에는 원천 이름을 싣는 칸(`source`)을 더한다. 작업 하나 보기의 문서 칸도 원천 단위 작업과 정리 작업에서는 비운다. 칸의 뜻이 바뀌는데 `v1`에 두는 까닭은 ADR 0022 Consequences가 문서 상태에 대해 적은 것과 같다(정식 릴리스가 아직 없고, 이 API를 쓸 관리자 페이지가 이 기능 뒤에 온다).

### 가져오는 원천의 문서 색인

- [정함] 색인 작업은 원본 경로가 빈 문서의 원본을 그 원천의 커넥터로 읽는다(`fetch`). 읽는 때는 파싱이 필요할 때뿐이다(core 명세: 파싱 결과가 없거나, 파싱한 내용 해시가 다르거나, 파서 버전이 바뀌었을 때). 파싱 결과가 남아 있으면 재색인은 원천을 읽지 않는다.
- [정함] 읽은 바이트의 내용 해시가 문서 행의 내용 해시와 다르거나, 그 키의 파일이 없거나, 크기 상한을 넘으면 원천이 목록을 받은 뒤에 바뀐 것이다(ADR 0022가 명세에 넘긴 "목록을 만든 뒤 색인하는 사이에 파일이 바뀌거나 사라진 문서"). 색인 작업은 조각을 쓰지 않고, 그 문서의 변경 확인값을 비우고, 대상 판의 색인 상태를 `failed`와 `source_changed`로 쓰고 재시도 없이 끝난다. 변경 확인값이 비었으므로 다음 동기화가 그 파일을 다시 읽어 바뀐 내용으로 넣고, 파일이 사라졌거나 상한을 넘게 됐으면 삭제 반영한다(상한을 넘은 파일은 수집 정책에 걸린 파일이다. 수집 정책 절). 다시 읽어 보니 내용이 문서 행의 것 그대로이면(운영자가 파일을 원래 내용으로 되돌려 놓았다) 색인 작업을 다시 넣는다(아래 항목).
- [정함] 원천을 읽을 수 없으면(폴더가 붙지 않았다, 권한이 없다, 경로 확인에 걸렸다) 일시 실패 `source_unreadable`이고 지금의 재시도 규칙으로 다시 예약한다. 읽기가 돌아오지 않을 때와, 커넥터를 만들지 못한 때(설치되지 않았다, 인터페이스 버전이 맞지 않는다, 저장해 둔 설정을 받지 않는다)도 같다. 뒤의 경우에는 그 원천의 동기화도 `connector_unavailable`로 실패하므로, 운영자가 커넥터를 바로잡은 뒤의 동기화가 그 문서의 색인 작업을 다시 넣는다(아래 항목). 색인 작업은 `fetch`를 커넥터 호출의 한도(`RAG_SOURCE_READ_TIMEOUT_SECONDS`, 동기화의 차례 절)만큼만 기다리고, 넘으면 기다리기를 그만두고 같은 일시 실패로 다시 예약한다. 색인 작업은 도는 동안 진행과 상관없이 작업 담당 기록의 기한을 늘리므로(코드를 읽었다), 이 한도가 없으면 끊긴 공유 폴더의 문서 하나가 작업자의 자리 하나를 끝없이 잡는다. 그 뒤로는 동기화의 차례 절의 돌아오지 않는 호출 항목이 같은 설정으로 그 원천을 읽는 것을 막는다(PR 봇 리뷰가 낸 지적을 색인 작업까지 넓혀 본 것이다).
- [넘겨받음] 색인이 실패로 끝난 문서는 파일이 바뀌지 않아도 다시 시도되는 길이 있어야 한다(ADR 0022 Consequences의 조건).
- [정함] 그 길의 하나는 동기화다. 동기화는 내용이 바뀌지 않은 문서(변경 확인값이 같아 읽지 않은 문서와, 읽어 보니 내용이 같은 문서)의 색인 상태를 보고, 일시 실패의 코드(`embedding_unavailable`, `database_unavailable`, `blob_store_error`, `source_unreadable`)나 `worker_lost`나 `source_changed`로 실패해 있으면 색인 작업을 다시 넣는다. 변경 확인값이 같은 문서는 이때도 동기화가 파일을 읽지 않고, 읽는 것은 색인 작업이다. 임베딩 서버가 한동안 꺼져 재시도를 다 쓴 문서가 다음 일정에서 저절로 다시 돈다. 영구 실패(`parse_failed` 같은 것)는 같은 파일로 다시 해도 같은 결과라 다시 넣지 않는다. 파서를 고친 뒤에 영구 실패를 다시 시도시키는 길은 "모두 다시 읽기"로 돌린 동기화와 재색인이다.
- [정함] 문서의 색인에 쓰이는 작업 코드로 둘을 더한다. `source_unreadable`은 일시 실패의 코드이고 `source_changed`는 다시 시도하지 않는 실패의 코드다. 둘 다 가져오는 원천의 문서에만 쓰인다. 이 기능이 작업 코드에 더하는 값 전체는 오류 코드 절이 적는다.

### 건너뜀

- [넘겨받음] 문서 상태에 건너뜀과 그 사유(암호가 걸림, 글자가 없음)를 더한다. 관리 API의 문서 목록에서 실패와 따로 세고, 같은 내용을 다시 넣어도 다시 파싱하지 않으며(파일이 바뀌면 다시 본다), 밀어 넣는 원천의 문서에도 같은 상태를 쓴다. 검색 도구의 계약은 바뀌지 않는다(ADR 0022 "건너뜀").
- [정함] 문서 상태 값은 `skipped`이고 사유 값은 `encrypted`와 `no_text`다. 사유는 문서 상태가 `skipped`일 때만 있다.
- [정함] 암호가 걸린 파일은 파서가 지금처럼 알리고(파서 인터페이스는 바꾸지 않는다), 색인 작업은 그것을 실패로 적지 않고 문서 상태를 `skipped`와 `encrypted`로 쓴 뒤 성공으로 끝난다. 오류 코드 `encrypted_document`는 문서, 색인 상태, 작업 행의 오류 코드 칸에 더는 쓰이지 않는다.
- [정함] 글자가 없는 문서는 파싱 결과에서 색인할 글이 하나도 나오지 않는 문서다(공백만 있는 것도 같다). 색인 작업은 문서 상태를 `skipped`와 `no_text`로 쓰고 성공으로 끝난다. 지금은 이 문서가 `parsed`이고 조각이 0개다(코드를 읽었다. 파서는 글이 없으면 빈 목록을 내고, 색인 작업은 파싱 결과를 저장해 문서 상태를 `parsed`로 쓴 뒤 조각 0개와 색인 상태 `indexed`를 쓴다. 글자 없는 파일을 넣어 돌려 보지는 않았고, ADR 0022도 읽기만 했다고 밝혔다). 데이터 모델 절의 마이그레이션은 문서 상태가 아니라 저장된 파싱 결과에 글이 없는지로 옮길 문서를 고르므로, 이 읽기가 틀렸더라도 고르는 조건은 그대로 선다.
- [넘겨받음] 건너뜀으로 남은 문서는 재색인으로 새 색인 판을 지을 때 판 전환을 막지 않는다. 판 전환의 조건은 모든 색인 상태가 `indexed`나 `failed`인 것이다(ADR 0022 Consequences의 조건).
- [정함] 그래서 건너뜀 문서의 색인 상태는 대상 판마다 `indexed`로 쓴다(조각은 0개다). 건너뜀을 쓴 색인 작업도 다른 색인 작업처럼 마지막에 전환 검사(건설 중인 판의 색인 상태가 모두 `indexed`나 `failed`이면 판을 전환한다. core 명세)를 한다. 그래서 건너뜀 문서가 그 판에서 마지막으로 끝난 문서여도 판이 전환된다. 색인 상태에 새 값을 더하면 판 전환의 조건과 진행을 세는 자리를 모두 고쳐야 한다. 관리 API는 문서 상태로 건너뜀을 보이므로, 색인 상태가 `indexed`인 것이 운영자에게 색인된 문서로 읽히지 않는다.
- [정함] 건너뜀 문서와 내용이 같은 파일이 다시 들어오면 수집 API의 응답은 `unchanged`이고 작업을 넣지 않는다. 동기화도 그 문서를 그대로 두고 `skipped`로 센다. 내용이 다른 파일이 들어오면 보통의 갱신이고 문서 상태가 `received`로 돌아가 다시 파싱한다. 이것은 수집 API의 계약이 바뀌는 자리다. 지금은 암호가 걸려 실패로 남은 문서와 같은 내용을 다시 보내면 응답이 `requeued`이고 색인 작업이 다시 들어간다(앞선 색인이 실패한 문서이기 때문이다. 코드를 읽었다). 이 기능 뒤에는 같은 요청이 `unchanged`를 받고 작업이 들어가지 않는다. 응답이 받는 값의 목록은 그대로이고, 같은 요청에 오는 값만 바뀐다. 글자가 없는 문서는 지금도 `parsed`라 같은 요청이 `unchanged`를 받으므로 바뀌지 않는다. 수집 API를 `v1`에 두는 까닭은 작업 조회의 칸에 대해 적은 것과 같다(작업 대기열 절. 정식 릴리스가 아직 없다). 지금의 시험 가운데 암호 실패를 기대하는 것은 건너뜀을 넣는 티켓이 함께 고친다(명세 검토가 냈다).
- [넘겨받음] 건너뜀으로 남은 문서는 파서가 바뀐 뒤에 다시 볼 길이 있어야 한다(ADR 0022 Consequences의 조건).
- [정함] 그 길의 하나는 재색인이다. 재색인이 넣은 색인 작업은 건너뜀 문서도 다시 본다. 암호 건너뜀은 파싱 결과가 없어 다시 파싱하고, 글자 없음은 파싱 결과에 적힌 파서 버전이 지금과 다르면 다시 파싱한다(core 명세의 다시 파싱하는 조건 그대로다). 글이 나오면 문서 상태가 `parsed`로 돌아가 색인된다. 가져오는 원천에는 길이 하나 더 있다. "모두 다시 읽기"로 돌린 동기화가 건너뜀 문서의 색인 작업을 다시 넣는다(동기화의 차례 절).
- [정함] 관리 API의 문서 목록은 상태로 거르는 값에 `skipped`를 받고, 문서 응답에 건너뜀 사유 칸(`skip_reason`)을 싣는다. 원천 보기는 그 원천의 문서 수를 전체, 실패, 건너뜀으로 따로 보인다.

### 원천 삭제와 되살리기

- [넘겨받음] 원천을 지우면 그 원천의 문서도 함께 임시 삭제한다. 지우는 순간 그 원천의 문서가 모두 검색에서 빠지고, 보관 기간이 지나면 정리 작업이 문서와 원천을 완전히 지운다. 지운 원천은 아무것도 받지 않는다. 새 문서가 들어오지 않고, 그 원천의 문서를 하나씩 되살리는 요청도 받지 않으며, 동기화도 시작하지 않는다(ADR 0021 "원천을 지우면 그 원천의 문서도 함께 임시 삭제한다", "지운 원천은 아무것도 받지 않는다").
- [정함] `default`와 `upload`는 지울 수 없다(409 `source_protected`). `migrate`가 만들어 두는 원천이고, `ingest` 명령과 원천을 적지 않은 수집 요청이 `default`로 간다.
- [정함] 지우는 요청은 작업 단위 하나에서 원천 행에 지움 표시(지운 시각)를 쓰고, 다음 실행 시각을 비우고, 그 원천의 대기 중인 동기화 작업을 지우며(그 동기화 기록은 `failed`와 `source_deleted`로 닫는다), 원천 삭제 작업을 넣는다. 응답은 202이고 그 작업의 식별자를 싣는다. 문서 행과 조각은 이 요청이 고치지 않는다.
- [정함] 지움 표시가 선 순간부터 그 원천의 문서는 지워진 문서로 읽힌다. `search`는 결과 조각의 문서와 원천을 읽는 자리에서 지움 표시가 있는 원천의 조각을 빼고, `get_document`는 지워진 문서에 하는 것과 같게 답하며, 관리 API의 문서 조회와 목록은 그 문서를 `deleted`로 보인다. 그래서 조각을 하나도 옮기기 전에 그 원천의 문서가 모두 검색에서 빠진다. 후보를 뽑는 질의는 지금처럼 조각 표만 읽고 원천을 묻지 않는다(코드를 읽었다). 그래서 원천 삭제 작업이 조각을 다 옮기기 전의 검색은 뺀 만큼 결과가 요청한 건수보다 적을 수 있다. 검색 도구의 계약은 바뀌지 않는다.
- [정함] 문서 수를 세는 자리 셋(MCP 도구 `list_knowledge_bases`의 지식베이스 목록, 관리 API의 지식베이스 보기, 원천 보기)은 문서 행의 지운 시각만 보고 원천의 지움 표시는 보지 않는다(앞의 둘은 지금 그렇게 센다. 코드를 읽었다). 그래서 원천을 지운 직후에는 이 수가 검색에 나오는 문서보다 많고, 원천 삭제 작업이 문서를 옮기는 대로 줄어 작업이 끝나면 맞는다. 세는 질의마다 원천을 잇는 조건을 더하지 않은 것은, 어긋나는 동안이 작업 하나가 도는 동안뿐이기 때문이다.
- [이력] ADR 0013의 본문은 검색 표에 산 것만 두어 검색 SQL에 삭제 필터가 없다고 적는다. 위 항목으로 검색이 원천의 지움 표시를 보는 자리가 하나 생기므로, 그 ADR에 2026-11-21 이력을 더하고 그 문장 뒤에 포인터를 달았다.
- [정함] 표시를 먼저 세우고 문서는 작업자가 묶음으로 옮긴다(설계의 셀프 리뷰가 명세에 넘긴 물음). 프로브가 쟀다. 문서 1만 건과 조각 10만 개인 원천을 한 트랜잭션에서 임시 삭제하면 커밋 전까지 16.12초가 걸렸고, 그동안 그 원천의 문서 행 하나를 `FOR UPDATE`로 잠그려던 다른 연결이 막혔다(프로브는 1.50초를 기다린 뒤 그 시도를 거뒀다. `source-delete/probe_out.txt`의 A). 제품의 색인 작업과 수집은 문서 행을 `FOR NO KEY UPDATE`로 잠근다(코드를 읽었다). 문서 행을 고치는 트랜잭션은 그 잠금도 막으므로 제품에서도 같은 결과일 것이다. 다만 이것은 PostgreSQL의 행 잠금 규칙에 따른 어림이고, 그 잠금으로 재지는 않았다. 묶음으로 나눠 묶음마다 커밋하면 전체 시간은 비슷하고 잠금을 쥐는 시간이 짧아졌다. 문서 500건씩이면 전체 15.50초에 묶음 하나의 가운데값이 0.62초, 가장 긴 묶음이 1.83초였고(같은 출력의 B), 50건씩이면 전체 16.83초에 가운데값 0.08초, 가장 긴 묶음 0.48초였다(`source-delete/probe_out_batch50.txt`의 B). 한 번에 하면 관리 API 요청 하나가 문서 수만큼 길어지고 그동안 그 원천의 수집과 색인이 기다린다.
- [정함] 원천 삭제 작업은 그 원천의 지워지지 않은 문서를 50건씩 묶어, 묶음마다 작업 단위 하나에서 core 명세의 문서 삭제와 같은 일을 한다. 묶음마다 맨 먼저 원천 행을 잡고(아래의 공유 잠금) 지움 표시가 서 있는지 다시 본다. 표시가 없으면(그사이 원천을 되살렸다) 아무것도 옮기지 않고 성공으로 끝난다. 표시가 서 있으면 문서 행을 식별자 순으로 잠그고 그 문서들의 그룹이 든 지식베이스 행을 잠근 뒤(core 명세의 잠금 순서), 세대를 올리고, 지운 시각을 원천의 지운 시각으로 쓰고, 원천과 함께 지워졌다는 표시를 세우고, 모든 색인 판의 조각을 삭제 보관함으로 옮기고, 색인 상태 행과 그 문서의 대기 중인 색인 작업을 지우며, 건설 중인 판이 있으면 전환 검사를 한다. 원천과 함께 지워졌다는 표시가 있는 문서의 보관 기간은 문서의 지운 시각이 아니라 원천을 따른다. 정리 작업이 그런 문서를 따로 지우지 않고 원천과 함께 지우기 때문이다(정리 작업 절). 문서의 지운 시각을 원천의 것으로 적는 것은 관리 API의 문서 조회가 보이는 값을 원천과 맞추려는 것이다.
- [정함] 원천을 지우기 전에 이미 임시 삭제되어 있던 문서는 건드리지 않는다. 표시가 없어 원천을 되살려도 돌아오지 않고(ADR 0021), 보관 기간도 그 문서를 지운 날부터 센다.
- [정함] 지운 원천에 새 문서가 들어가지 않게 순서를 세운다. 문서를 넣거나 되살리는 작업 단위(수집 API, 동기화, 문서 되살리기)는 맨 먼저 원천 행을 다른 작업 단위가 고치지 못하게 잡은 채(공유 잠금) 지움 표시를 보고, 표시가 서 있으면 쓰지 않는다. 지우는 요청은 그 원천 행을 고치므로 둘 가운데 하나가 먼저 끝난다. 수집이 먼저 끝나면 그 문서는 원천 삭제 작업이 옮기고, 삭제가 먼저 끝나면 수집이 거절된다. 잠금 순서는 core 명세의 순서 앞에 원천 행을 둔 것이다(원천 행, 문서 행, 지식베이스 행, 작업 행).
- [정함] 지우는 순간 돌고 있던 동기화는 다음 문서를 쓰기 전에 표시를 보고 `source_deleted`로 끝난다. 목록을 받는 중이거나 파일 하나를 오래 읽는 중이어도, 작업 담당 기록의 기한을 늘릴 때 표시를 보고 끝난다(동기화의 차례 절의 끝없는 목록 항목). 실행 중인 색인 작업은 core 명세가 지워진 문서에 하는 것과 같게 다룬다. 첫째 단계에서 원천의 지움 표시를 보면 아무것도 쓰지 않고 성공으로 끝난다. 그 뒤에 원천 삭제 작업이 그 문서를 옮겼으면 세대가 달라 쓰지 않고, 아직 옮기지 않았으면 쓴 조각을 원천 삭제 작업이 옮긴다(ADR 0021이 명세에 넘긴 "원천을 지우는 순간 대기 중이거나 돌고 있던 그 원천의 작업을 거두는 방법"). 지우고 되살리는 일이 그 동기화가 표시를 한 번 보고 다음에 보기 전에 모두 끝나면, 그 동기화는 표시를 보지 못하고 이어서 돈다. 되살리기는 원천 삭제 작업이 끝난 뒤에만 받으므로, 그 작업이 표시를 보는 두 때 사이에 끝날 때만 난다. 문서를 쓰는 중에는 그 사이가 문서 하나를 처리하는 동안이라 좁다. 목록을 받는 중이거나 파일 하나를 오래 읽는 중에는 그 사이가 기한을 늘리는 간격(기본 200초)이라, 문서가 적은 원천을 지우고 곧바로 되살리면 난다(앞서는 문서 하나를 처리하는 동안에만 난다고 적었다. 셀프 리뷰가 바로잡았다). 이 경우는 막지 않는다. 이어서 도는 동기화가 하는 일은 되살린 뒤에 시작한 동기화가 하는 일과 같고(아래의 원천 되살리기 작업이 끝나기 전에 온 동기화 항목), 다른 것은 목록을 받은 때가 이르다는 것뿐이다. 다만 끝나지 않는 동기화를 멈추려고 지운 것이면 멈추지 않은 것이므로, 그때는 동기화 기록이 `source_deleted`로 닫힌 것을 본 뒤에 되살린다(동기화의 차례 절의 끝없는 목록 항목). 받아 둔 목록이 그 뒤에 폴더에서 바뀐 것을 모르는 것은 오래 도는 동기화가 모두 같고, 다음 동기화가 맞춘다. 원천 행에 번호를 두어 지웠다 되살린 원천의 동기화를 끝내는 안은 고르지 않았다(PR 봇 리뷰가 냈다). 원천 행의 칸 하나와 동기화의 실패 사유 하나가 늘고, 그것으로 막는 어긋남은 지우지 않은 원천에서도 난다. 끝나지 않는 동기화를 멈추려는 경우의 틈을 두고 같은 안(원천마다 지운 횟수를 적는 안)을 2026-11-21의 막힌 호출 설계 인터뷰에서 사용자에게 다시 올렸고, 사용자는 안내에 차례를 적는 쪽을 골랐다(ADR 0023 Considered Options).
- [정함] 지움 표시가 선 동안 시작한 재색인은 원천 삭제 작업이 아직 옮기지 않은 문서를 살아 있는 문서로 세어, 새 색인 판에 그 문서의 색인 상태 `pending`을 쓰고 색인 작업을 넣는다(재색인의 시작은 문서 행으로 센다. 코드를 읽었다). 그 색인 작업은 원천의 지움 표시를 보고 아무것도 쓰지 않은 채 끝나므로 `pending`이 남는다. 원천 삭제 작업이 그 문서를 옮길 때 색인 상태 행을 지우고 전환 검사를 하므로 새 판의 전환이 막히지 않는다. 원천 삭제 작업이 실패로 끝나 있으면 정리 작업이 다시 넣고, 그 전에 원천을 되살리면 원천 되살리기 작업이 그 문서의 색인을 다시 잇는다(아래).
- [정함] 원천 삭제 작업이 도중에 죽으면 작업 담당 기록의 기한이 지난 뒤 다른 작업자가 가져가 남은 문서부터 잇는다. 이미 옮긴 문서는 지워져 있어 다시 고르지 않는다.
- [넘겨받음] 지운 원천은 보관 기간 안에 관리 API로 되살린다. 호출 하나로 원천을 되돌리면 원천과 함께 지워졌던 문서가 같이 검색에 돌아오고, 그사이 색인 판이 바뀌지 않았으면 임베딩을 다시 하지 않는다. 가져오는 원천은 되돌린 뒤의 동기화가 그사이 폴더에서 바뀐 것을 다시 맞춘다. 그 전에 따로 지운 문서는 원천을 되살려도 돌아오지 않는다(ADR 0021 "지운 원천은 보관 기간 안에 관리 API로 되살린다").
- [정함] 되살리는 요청은 작업 단위 하나에서 지움 표시를 걷고, 일정이 있고 일시 중지가 아니면 다음 실행 시각을 다시 계산하고, 원천 되살리기 작업을 넣는다. 응답은 202이고 그 작업의 식별자를 싣는다. 표시를 걷은 순간부터 그 원천은 다시 요청을 받고, 문서는 원천 되살리기 작업이 되살리는 대로 검색에 돌아온다.
- [정함] 원천 되살리기 작업은 원천과 함께 지워졌다는 표시가 있는 문서를 50건씩 묶어, 묶음마다 작업 단위 하나에서 core 명세의 되살림과 같은 일을 한다. 묶음마다 맨 먼저 원천 행을 잡고 지움 표시가 없는지 다시 본다. 표시가 서 있으면(그사이 원천을 다시 지웠다) 아무것도 되살리지 않고 성공으로 끝난다. 표시가 없으면 세대를 올리고, 지운 시각과 표시를 비우고, 삭제 보관함의 조각 가운데 대상 판의 것이면서 만든 내용 해시가 문서의 내용 해시와 같은 것만 조각 표로 되돌려 그 판의 색인 상태를 `indexed`로 쓰고, 나머지 보관 조각은 지운다(core 명세의 조건 그대로다). 되돌릴 조각이 없는 대상 판이 있으면 core 명세의 되살림대로 색인 작업을 넣는다. 그런 경우는 둘이다. 지운 뒤에 색인 판이 바뀌었거나, 지우기 전에 바뀐 내용이 아직 색인되지 않았던 경우다. 뒤의 경우에 옛 내용으로 만든 조각을 되돌리지 않으므로 검색에 옛 글이 돌아오지 않는다. 건너뜀 문서는 조각이 없으므로 대상 판마다 색인 상태만 다시 쓴다. 그룹과 내용은 문서 행의 것 그대로다.
- [정함] 원천 되살리기 작업은 표시가 있는 문서를 모두 되살린 뒤에, 그 원천의 지워지지 않은 문서 가운데 색인이 멈춘 문서에 색인 작업을 넣는다. 색인이 멈춘 문서는 대상 판 가운데 색인 상태가 `indexed`도 `failed`도 아닌 판(`pending`이거나 상태 행이 없다)이 있는데 그 문서의 색인 작업이 대기 중도 실행 중도 아닌 문서다. 원천 삭제 작업이 재시도를 다 쓰고 실패로 끝난 원천을 되살리면 이런 문서가 남는다. 지움 표시가 선 동안 돈 색인 작업은 아무것도 쓰지 않고 끝났는데, 원천 삭제 작업이 그 문서를 옮기지 못했기 때문이다. 이 단계가 없으면 그 문서는 지워지지도 색인되지도 않은 채 남고, 재색인으로 짓던 새 색인 판은 그 문서의 `pending` 때문에 전환되지 않는다.
- [정함] 되살리기의 묶음도 50건인 까닭은 묶음 하나가 잠금을 쥐는 시간이다. 프로브가 쟀다. 같은 원천을 문서 500건씩 묶어 되살리면 전체 794.88초에 묶음 하나의 가운데값이 39.41초, 가장 긴 묶음이 46.03초였고(`source-delete/probe_out.txt`의 D), 50건씩이면 전체 760.94초에 가운데값 3.58초, 가장 긴 묶음 8.53초였다(`source-delete/probe_out_batch50.txt`의 D). 묶음을 줄여도 전체 시간은 늘지 않았다. 삭제보다 훨씬 오래 걸리는 까닭은 조각을 조각 표로 되돌릴 때마다 그 표의 색인들(벡터 색인과 키워드 색인)에 한 건씩 넣기 때문으로 보인다. 그 가운데 벡터 색인의 몫이 크리라는 것은 어림이고, 색인을 하나씩 빼고 재는 대조는 하지 않았다(Further Notes).
- [정함] 원천 되살리기 작업이 끝나기 전에 그 원천으로 온 수집과 동기화는 그대로 받는다. 표시가 남은 문서와 같은 키가 들어오면 core 명세의 되살림이 그 문서를 되살리고 표시를 지운다. 문서를 되살리는 일은 어느 쪽이든 문서 행을 잠근 뒤 아직 지워져 있는지 다시 보므로 한 번만 일어난다.
- [정함] 되살린 원천에서 원천 되살리기 작업이 아직 되살리지 않은 문서를 지우라는 요청이 오면, 그 문서는 되살아나지 않아야 한다. 그래서 수집 API의 삭제 요청과 동기화의 삭제 반영은 이미 지워져 있는 문서에 원천과 함께 지워졌다는 표시가 남아 있으면 그 표시를 지우고 지운 시각을 그 순간으로 고친다. 그 문서는 따로 지운 문서가 되어 원천 되살리기 작업이 되살리지 않고, 보관 기간도 그 순간부터 센다. 지금의 문서 삭제는 이미 지워진 문서를 만나면 아무것도 고치지 않으므로(코드를 읽었다) 이 갈래를 더한다. 요청에 대한 응답은 이미 지워진 문서를 지울 때의 지금 응답 그대로다.
- [정함] 지워지지 않은 원천을 되살리려 하면 409 `source_not_deleted`다. 그 원천의 원천 삭제 작업이나 원천 되살리기 작업이 대기 중이거나 실행 중이면 지우는 요청과 되살리는 요청을 모두 409 `source_change_in_progress`로 거절한다. 두 작업이 같은 원천의 문서를 서로 반대쪽으로 옮기지 않게 하려는 것이다. 작업이 재시도를 다 쓰고 실패로 끝난 뒤에는 요청을 받는다. 지우다 만 원천을 되살리면 원천 되살리기 작업이 옮겨진 문서를 되살리고 색인이 멈춘 문서를 다시 잇는다(위 항목). 되살리다 만 원천을 다시 지우면 아직 되살리지 않은 문서는 표시가 남은 채 지워져 있고, 원천 삭제 작업이 나머지 문서를 옮긴다. 두 무리의 지운 시각은 다르지만 표시가 있는 문서의 보관 기간은 원천을 따르므로 같은 날 끝난다.
- [정함] 보관 기간이 지난 지운 원천은 정리 작업이 아직 지우지 않았어도 되살릴 수 없다(409 `source_retention_expired`). 정리 작업은 원천 하나를 여러 묶음에 걸쳐 지우므로, 지우는 도중에 되살리는 요청이 끼어들 틈을 기간으로 막는다.
- [정함] 가져오는 원천을 되살릴 때는 폴더의 겹침을 다시 본다. 그사이 다른 원천이 겹치는 폴더를 쓰게 됐으면 409 `source_folder_overlap`이고 되살리지 않는다. 겹침은 서버 경로 커넥터와 원천 폴더 절의 폴더 확인 한도 항목대로 본다. 되살리는 원천의 폴더나 다른 원천의 폴더가 10초 안에 답하지 않으면 그 폴더는 저장해 둔 경로의 글자로 견준다. 폴더가 지금 없거나 읽을 수 없어도 되살리기는 받는다. 문서는 삭제 보관함에서 돌아오고 파일을 읽지 않기 때문이다. 응답에 연결 확인의 결과를 함께 실어 운영자가 그 자리에서 알게 하고, 폴더를 읽을 수 없는 동안의 동기화는 `source_unreadable`로 실패해 문서를 지우지 않는다.
- [정함] 지운 원천의 일정, 제외 패턴, 커넥터 설정은 고칠 수 없다(409 `source_deleted`). 되살린 뒤에 고친다.

### 문서 되살리기

- [넘겨받음] 관리 API의 되살리기는 밀어 넣는 원천의 문서에만 연다. 업로드와 수집 API로 넣었다가 지운 문서는 보관 기간 안에 관리 API 호출 하나로 되살린다. 보관해 둔 조각을 되돌리고, 그사이 색인 판이 바뀌었으면 보관해 둔 원본으로 다시 색인한다. 가져오는 원천의 문서는 API로 되살리지 않고, 원천 폴더에 파일을 되돌려 놓으면 다음 동기화가 되살린다(ADR 0021 "관리 API의 되살리기는 밀어 넣는 원천의 문서에만 연다").
- [정함] 되살리는 요청은 문서 식별자를 받아 작업 단위 하나에서 core 명세의 되살림을 내용이 같은 경우로 한다. 그룹, 제목, 메타데이터는 문서 행의 것 그대로이고, 대상 판의 보관 조각 가운데 만든 내용 해시가 문서의 내용 해시와 같은 것만 되돌려 색인 상태를 `indexed`로 쓰며, 되돌릴 조각이 없는 대상 판이 있으면(지운 뒤에 색인 판이 바뀌었거나, 지우기 전에 바뀐 내용이 아직 색인되지 않았다) 색인 작업을 넣는다. 건너뜀 문서는 조각이 없으므로 대상 판마다 색인 상태만 다시 쓴다(원천 되살리기 작업과 같다. 셀프 리뷰가 냈다). 원천과 함께 지워졌다는 표시가 남아 있던 문서면 그 표시도 지운다. 응답은 200이고 문서와, 넣은 작업이 있으면 그 식별자를 싣는다.
- [정함] 거절하는 경우는 넷이다. 없는 문서와 삭제 기록(보관 기간이 지나 내용을 지운 문서)은 404 `document_not_found`, 지워지지 않은 문서는 409 `document_not_deleted`, 가져오는 원천의 문서는 409 `wrong_source_kind`, 지운 원천의 문서는 409 `source_deleted`다. 되살리는 요청은 문서 행을 잠근 뒤에 이 조건을 본다. 보관 기간이 지났는지는 보지 않아서, 기간이 지났어도 정리 작업이 아직 완전히 지우지 않은 문서는 되살린다(PR 직전 리뷰가 원천 되살리기와 다르다고 짚었다). 원천은 정리 작업이 여러 묶음에 걸쳐 지워서, 지우는 도중에 되살리는 요청이 끼어들 틈을 기간으로 막는다(위 절). 문서 하나는 정리 작업이 문서 행을 잠근 작업 단위 하나에서 지우므로 그런 틈이 없다. 둘이 겹치면 먼저 잠근 쪽대로 정해진다. 정리 작업이 먼저면 그 문서는 삭제 기록이 되어 404이고, 되살리기가 먼저면 정리 작업이 그 문서를 건너뛴다.

### 정리 작업

- [넘겨받음] 정리 작업은 작업자가 하루에 한 번 돌린다. 보관 기간(`RAG_DELETED_RETENTION_DAYS`)이 지난 문서의 조각과 원본을 지워 삭제 기록만 남기고, 지운 원천을 완전히 지우며(그 원천에 딸린 삭제 기록도 함께 지운다), 어느 문서도 가리키지 않는 원본 파일을 치운다(ADR 0022 "정리 작업").
- [정함] 정리 작업은 일정 확인이 넣는다. 일정 시간대(`RAG_SCHEDULE_TIMEZONE`)로 가장 최근의 새벽 3시보다 뒤에 넣은 정리 작업이 없으면 하나 넣는다(ADR 0022가 명세에 넘긴 "정리 작업이 도는 시각"). 그래서 날마다 새벽 3시가 지난 첫 일정 확인이 넣고, 작업자가 그 시각에 꺼져 있었으면 다시 켜진 뒤의 첫 일정 확인이 넣는다. 정리 작업을 넣은 적이 없는 설치에서는 첫 일정 확인이 넣는다. 정리 작업이 이미 대기 중이거나 실행 중이면 넣지 않는다(데이터 모델 절의 부분 유일 색인).
- [정함] 첫째로 보관 기간이 지난 임시 삭제 문서 가운데 원천과 함께 지워졌다는 표시가 없는 것을 완전히 지운다. 표시가 있는 문서는 이 단계가 건드리지 않는다. 지운 원천의 것이면 아래 둘째가 원천과 함께 지우고, 되살린 원천의 것이면 원천 되살리기 작업이 되살릴 문서이기 때문이다. 표시를 보지 않으면, 보관 기간이 끝나기 직전에 되살린 원천의 문서를 원천 되살리기 작업이 되살리기 전에 이 단계가 완전히 지울 수 있다. 지운 원천에 든 문서라도 원천보다 먼저 따로 지운 것은 표시가 없으므로, 이 단계가 그 문서를 지운 날부터 세어 지운다. 문서 50건씩 작업 단위 하나에서 문서 행을 잠그고, 아직 지워져 있고 표시가 없고 기간이 지났는지 다시 본 뒤, 삭제 보관함의 조각과 파싱 결과를 지우고 원본 경로를 비우고 완전히 지운 시각을 적는다. 그 행이 삭제 기록으로 남는다. 다시 보는 까닭은 그사이 같은 키가 다시 들어와 되살아났을 수 있어서다.
- [정함] 원본 파일은 그 작업 단위를 커밋한 뒤에 지운다. 먼저 지우면 작업 단위가 되돌려졌을 때 문서 행이 없는 파일을 가리킨다. 커밋한 뒤 지우지 못한 파일은 어느 문서도 가리키지 않는 원본이 되어 다음 정리 작업이 치운다.
- [정함] 둘째로 보관 기간이 지난 지운 원천을 완전히 지운다. 그 원천의 문서를 50건씩 묶어 문서 행, 조각, 삭제 보관함의 조각, 파싱 결과, 색인 상태를 지우고(원천 삭제 작업이 옮기지 못한 문서와 삭제 기록까지 모두다), 그 원천을 가리키는 작업 행과 동기화 기록을 지운 뒤, 마지막에 원천 행을 지운다. 문서 행을 지우기 전에는 그 문서를 가리키는 작업 행을 끝난 색인 작업까지 모두 지운다. 작업 표가 문서를 가리키는 외래 키에는 지울 때의 동작이 정해져 있지 않아서(코드를 읽었다), 작업 행이 남아 있으면 데이터베이스가 문서 행을 지우지 못하게 막는다. 묶음마다 원천 행을 잠그고 지움 표시가 그대로인지 다시 본다. 원천 삭제 작업이 옮기지 못한 문서는 색인 상태가 남아 있어서, 그 상태를 지운 묶음은 그 문서들의 그룹이 든 지식베이스에 건설 중인 판이 있으면 원천 삭제 작업처럼 지식베이스 행을 잠그고(core 명세의 잠금 순서) 전환 검사를 한다. 하지 않으면 그 문서의 `pending`(위의 재색인 항목)이 판을 막던 마지막 상태였을 때, 상태가 사라진 뒤에도 다른 색인 작업이 끝나기 전까지 판이 전환되지 않는다(셀프 리뷰가 냈다). 원천 행이 지워지면 그 이름을 다시 쓸 수 있다.
- [정함] 셋째로 어느 문서도 가리키지 않는 원본 파일을 치운다. 파일 저장소의 원본 가운데 문서 행의 원본 경로에 없고 쓴 지 24시간이 지난 파일을 지운다. 수집은 원본을 먼저 쓰고 문서 행을 그 뒤에 적으므로(코드를 읽었다), 방금 쓴 파일은 아직 가리키는 문서 행이 없을 수 있다(ADR 0022 Consequences의 조건 "정리 작업은 수집 요청이 방금 써서 아직 문서 행이 가리키지 않는 원본을 치우지 않는다"). 원본 경로는 수집할 때마다 새로 짓는 이름이라(코드를 읽었다), 한 번 가리키는 문서가 없어진 파일을 뒤에 다른 문서가 가리키는 일은 없다. 이 일에 쓰는 열거를 파일 저장소 포트에 더한다.
- [정함] 넷째로 끝난 지 `RAG_SYNC_RECORD_RETENTION_DAYS`가 지난 동기화 기록을 지운다. 원천마다 가장 최근 기록 하나는 남긴다(동기화 기록 절).
- [정함] 다섯째로 멈춘 원천 삭제와 원천 되살리기를 다시 잇는다. 원천마다 원천 행을 잠근 작업 단위에서 조건을 보고 작업을 넣는다. 지움 표시가 선 원천에 지워지지 않은 문서가 남았는데 원천 삭제 작업이 대기 중도 실행 중도 아니면 원천 삭제 작업을 다시 넣는다. 지움 표시가 없는 원천은 원천 되살리기 작업이 대기 중도 실행 중도 아닌데 다음 둘 가운데 하나에 맞으면 원천 되살리기 작업을 다시 넣는다. 원천과 함께 지워졌다는 표시가 남은 문서가 있거나, 그 원천의 마지막 원천 되살리기 작업이 실패로 끝나 있는 경우다. 뒤의 조건은 문서를 모두 되살린 뒤 색인이 멈춘 문서를 잇는 단계에서 실패한 작업을 다시 돌리려는 것이다. 원천 행을 잠그고 보는 까닭은 조건을 본 뒤 작업을 넣기 전에 지우는 요청이나 되살리는 요청이 끼어들지 못하게 하려는 것이다. 재시도를 다 쓰고 실패한 작업이 원천을 반쯤 옮긴 채로 두지 않게 한다.
- [정함] 정리 작업은 원천 폴더(`RAG_SOURCES_DIR` 아래)의 파일을 건드리지 않는다. 가져오는 원천의 문서는 원본 경로가 비어 있어 지울 원본이 없다.
- [정함] 정리 작업이 도중에 실패하거나 죽으면 색인 작업과 같은 규칙으로 다시 돈다. 다섯 가지는 모두 조건에 맞는 것을 다시 찾아 하는 일이라 처음부터 다시 해도 결과가 같다.

### 수집 API

- [넘겨받음] 수집 API는 밀어 넣는 원천의 문서만 넣고 지운다. 가져오는 원천의 이름을 적어 보낸 요청은 거부한다(ADR 0021 "수집 API는 밀어 넣는 원천의 문서만 넣고 지운다").
- [정함] 문서를 넣는 요청의 폼에 `source` 칸을, 지우는 요청의 쿼리에 `source`를 더한다. 값은 원천의 이름이고 적지 않으면 `default`다. 지금의 요청은 그대로 통한다(코드를 읽었다. 지금은 두 요청 모두 원천을 적는 칸이 없다).
- [정함] 없는 원천은 404 `source_not_found`, 지운 원천은 409 `source_deleted`, 가져오는 원천은 409 `wrong_source_kind`다(ADR 0021이 명세에 넘긴 오류 코드). 원천 이름의 규칙에 어긋나는 값은 422다.
- [정함] 건너뜀 문서와 같은 내용을 다시 보낸 요청의 응답은 `unchanged`다(건너뜀 절). 응답의 모양은 바뀌지 않는다. 암호가 걸린 문서에서는 지금의 `requeued`가 `unchanged`로 바뀐다(건너뜀 절이 이 계약 변경을 적는다).

### 관리 API

- [넘겨받음] 관리 API에 원천의 생성·수정·삭제(core 명세가 넘겼다), 원천 되살리기와 문서 되살리기(ADR 0021), 일정 고치기, 일시 중지와 다시 시작, 지금 동기화, 동기화 기록 보기가 더해지고, 원천 보기가 다음 실행 시각을 보여 주며, 문서 목록이 건너뜀을 가려 보인다(ADR 0022 Consequences). 경로는 모두 `/api/v1/admin` 아래이고 지금의 관리 토큰으로 부른다.
- [정함] 더하는 경로는 열셋이다.

| 경로 | 하는 일 | 성공했을 때 |
|---|---|---|
| `POST /sources` | 원천을 만든다 | 201과 원천 |
| `GET /sources` | 원천 목록. `include_deleted=true`면 지운 원천도 낸다 | 200 |
| `GET /sources/{name}` | 원천 하나 | 200 |
| `PATCH /sources/{name}` | 일정, 제외 패턴, 커넥터 설정을 고친다 | 200과 원천 |
| `DELETE /sources/{name}` | 원천을 지운다 | 202와 작업 식별자 |
| `POST /sources/{name}/restore` | 지운 원천을 되살린다 | 202와 작업 식별자, 연결 확인 결과 |
| `POST /sources/{name}/check` | 연결 확인 | 200과 결과 |
| `POST /sources/{name}/sync` | 지금 동기화 | 202와 동기화 기록 식별자, 작업 식별자 |
| `POST /sources/{name}/pause` | 일시 중지 | 200과 원천 |
| `POST /sources/{name}/resume` | 다시 시작 | 200과 원천 |
| `GET /sources/{name}/sync-records` | 동기화 기록 목록(최근 것부터) | 200 |
| `GET /sources/{name}/sync-records/{id}` | 동기화 기록 하나 | 200 |
| `POST /documents/{document_id}/restore` | 밀어 넣는 원천의 문서를 되살린다 | 200과 문서, 넣은 작업이 있으면 그 식별자 |

- [정함] 원천을 만드는 요청은 `name`과 `kind`(`push`나 `pull`)를 받는다. 가져오는 원천은 `connector`와 `config`를 반드시 적고, `group`(그룹 이름. 적지 않으면 기본 그룹), `schedule`(적지 않으면 일정 없음), `exclude_patterns`(적지 않으면 빈 목록)를 골라 적는다. 밀어 넣는 원천은 이름만 받고 뒤의 다섯 칸을 적으면 422다.
- [정함] 가져오는 원천은 만든 직후 동기화를 스스로 시작하지 않는다. 일정이 오거나 운영자가 "지금 동기화"를 부를 때 처음 돈다. 만들자마자 큰 폴더의 수집이 시작되어 운영자가 제외 패턴을 고칠 틈이 없는 일을 막는다.
- [정함] 만드는 요청을 거절하는 경우는 다음과 같다. 이름이 규칙에 어긋나면 422, 이름이 이미 있으면(지운 원천 포함) 409 `source_already_exists`, 없는 그룹은 수집 API와 같게 404 `group_not_found`다. 설치되지 않았거나 인터페이스 버전이 맞지 않는 커넥터 이름, 커넥터가 받지 않는 설정, 없는 폴더, 경로 확인에 걸린 폴더, 읽을 수 없는 폴더(권한이 없거나, 확인이 10초 안에 끝나지 않는다. 서버 경로 커넥터와 원천 폴더 절), 틀린 일정 표현식, 규칙에 어긋나는 제외 패턴은 422다. 폴더가 다른 원천과 겹치면 409 `source_folder_overlap`이다. 422는 모두 `validation_error`이고, 오류 목록의 항목마다 어느 칸인지(위치 `loc`의 마지막 토막이 `name`, `connector`, `config`, `schedule`, `exclude_patterns`)와 까닭의 종류(`type`)를 싣는다. `config`의 종류 값은 넷이다. 커넥터가 받지 않는 설정이 `invalid_config`, 없는 폴더가 `not_found`, 경로 확인에 걸린 폴더가 `rejected`, 읽을 수 없는 폴더가 `unreadable`이다. 커넥터 인터페이스의 사유 값과 같은 글자이고, 운영자는 이 값으로 폴더를 만들지, 링크를 걷을지, 권한과 붙임 상태를 살필지 가른다. `connector`의 종류 값은 `connector_unavailable`이다(명세 검토가 값의 이름이 빠졌다고 냈다).
- [정함] 원천 응답의 칸은 `name`, `kind`, `connector`, `config`, `group`, `schedule`, `next_run_at`, `paused`, `exclude_patterns`, `created_at`, `deleted_at`, 문서 수 `documents`, 마지막 동기화 `last_sync`다. 문서 수는 지워지지 않은 문서를 문서 상태로 센 `total`, `failed`, `skipped`다. `last_sync`는 가장 최근 동기화 기록이고 없으면 null이다. 밀어 넣는 원천에서는 가져오는 원천만 쓰는 칸이 null이다. 목록과 하나 보기의 모양이 같다.
- [정함] 고치는 요청은 가져오는 원천에만 통하고 `schedule`(null이면 일정을 없앤다), `exclude_patterns`, `config` 가운데 적은 칸만 고친다. 이름, 갈래, 커넥터, 그룹은 받지 않는다. `config`를 고치면 만들 때와 같은 확인(커넥터의 설정 확인, 폴더, 겹침)을 다시 한다. 고친 것은 다음 동기화부터 쓰이고, 고치는 순간 돌고 있던 동기화는 시작할 때 읽은 값으로 끝까지 돈다. 옛 설정으로 부른 호출이 돌아오지 않은 채 남아 있어도 새 설정으로 커넥터를 부른다(동기화의 차례 절의 돌아오지 않는 호출 항목). 밀어 넣는 원천에는 고칠 칸이 없어 409 `wrong_source_kind`다.
- [정함] 연결 확인은 요청 안에서 바로 돌고, 결과를 `ok`(참이나 거짓)와 실패했을 때의 `code`(`source_unreadable`, `source_path_rejected`, `connector_unavailable`, `connector_error`)로 답한다. 원천을 읽지 못해도 응답은 200이다. 요청은 성공했고 읽히지 않는 것은 원천이기 때문이다. 10초 안에 끝나지 않으면 `source_unreadable`로 답한다. 끊긴 공유 폴더는 읽기가 돌아오지 않을 수 있다. 그렇게 답한 뒤에도 그 호출은 돌아올 때까지 남으므로, 그 호출이 남아 있고 설정이 그대로인 동안 그 원천의 연결 확인은 커넥터를 부르지 않고 바로 `source_unreadable`로 답한다. 설정을 고친 뒤의 연결 확인은 새 설정으로 부른다(동기화의 차례 절의 돌아오지 않는 호출 항목). 같은 설정의 연결 확인을 한 번에 하나만 내보내는 규칙은 두지 않는다. 첫 호출이 10초를 넘기기 전에 온 요청은 저마다 커넥터를 부르고, 그 뒤의 요청은 위 규칙대로 부르지 않는다. 그래서 끊긴 원천에 연결 확인을 여러 번 눌러 쌓이는 호출은 첫 10초 사이에 누른 만큼이다. 앞서는 한 번에 하나만 내보내게 적었는데, 원천마다의 상한에 닿지 않게 하려던 규칙이라 그 상한과 함께 걷었다(ADR 0023). 이 결과는 서버 컨테이너가 본 것이고, 동기화를 도는 작업자 컨테이너가 보는 것과 다를 수 있다(단독 compose 절).
- [정함] 지금 동기화는 응답에 동기화 기록의 식별자와 작업의 식별자를 싣는다. 같은 원천의 동기화가 대기 중이거나 실행 중이면 409 `sync_in_progress`이고 기록을 남기지 않는다(`not_started` 기록은 일정이 온 회차에만 남긴다). 일시 중지한 원천에도 받는다.
- [정함] 지금 동기화의 본문은 옵션 둘을 받는다. `apply_empty`는 "빈 목록도 반영"이고 `reread`는 "모두 다시 읽기"다(동기화의 차례 절). 둘 다 적지 않으면 거짓이고, 켠 옵션은 그 동기화 기록의 옵션 칸에 남는다.
- [정함] 일시 중지와 다시 시작은 가져오는 원천에만 통한다. 이미 그 상태인 원천에 다시 불러도 200이다.
- [정함] 동기화 기록 목록은 최근 것부터 내고, 지금의 작업 목록과 문서 목록처럼 `limit`와 `after`로 다음 쪽을 받는다(코드를 읽었다). 지운 원천의 기록도 원천이 완전히 지워지기 전까지 볼 수 있다.
- [정함] 문서 목록에 원천 이름으로 거르는 `source`를 더하고, 상태로 거르는 값에 `skipped`를 더한다. `key`만 적으면 모든 원천에서 그 키의 문서를 찾는다(원천마다 하나씩 있을 수 있다). 문서 응답에 건너뜀 사유(`skip_reason`)를 더한다. 원천 이름은 지금도 실린다(코드를 읽었다).
- [정함] 없는 원천을 가리킨 요청은 모두 404 `source_not_found`다. 지운 원천은 보기(`GET`), 되살리기, 동기화 기록 보기만 받고, 고치기, 지우기, 연결 확인, 지금 동기화, 일시 중지, 다시 시작은 409 `source_deleted`다. 밀어 넣는 원천에 가져오는 원천만의 일(고치기, 연결 확인, 지금 동기화, 일시 중지, 다시 시작)을 부르면 409 `wrong_source_kind`다.

### 오류 코드

- [정함] HTTP 응답(Problem Details)의 `code`에 열둘을 더한다.

| 코드 | 상태 | 뜻 |
|---|---|---|
| `source_not_found` | 404 | 그 이름의 원천이 없다 |
| `sync_record_not_found` | 404 | 그 식별자의 동기화 기록이 그 원천에 없다 |
| `source_already_exists` | 409 | 같은 이름의 원천이 이미 있다(지운 원천 포함) |
| `source_deleted` | 409 | 지운 원천이라 받지 않는다 |
| `source_not_deleted` | 409 | 지워지지 않은 원천을 되살리려 했다 |
| `source_protected` | 409 | `default`와 `upload`는 지울 수 없다 |
| `source_change_in_progress` | 409 | 그 원천을 지우거나 되살리는 작업이 아직 끝나지 않았다 |
| `source_retention_expired` | 409 | 보관 기간이 지나 되살릴 수 없다 |
| `source_folder_overlap` | 409 | 폴더가 다른 원천의 폴더와 겹친다 |
| `wrong_source_kind` | 409 | 그 갈래의 원천에는 없는 일이다 |
| `sync_in_progress` | 409 | 같은 원천의 동기화가 대기 중이거나 돌고 있다 |
| `document_not_deleted` | 409 | 지워지지 않은 문서를 되살리려 했다 |

- [정함] 작업 행과 색인 상태의 오류 코드 칸에 쓰이는 값에 일곱을 더한다. 문서의 색인에 쓰이는 것이 `source_unreadable`(원천을 읽을 수 없다. 일시 실패라 다시 시도한다)과 `source_changed`(목록을 받은 뒤 원천의 파일이 바뀌거나 사라졌다. 다시 시도하지 않는다)다. 동기화 작업에 쓰이는 것이 `source_unreadable`, `nothing_accepted`(목록의 파일이 모두 수집 정책에 걸려 문서가 될 파일이 하나도 없는데 그 원천에는 문서가 있다), `source_path_rejected`(경로 확인에 걸렸다), `connector_unavailable`(커넥터가 설치되지 않았거나, 인터페이스 버전이 맞지 않거나, 저장해 둔 설정을 받지 않는다), `connector_error`(커넥터가 인터페이스에 없는 예외를 냈거나 같은 키를 두 번 냈다), `source_deleted`(도는 중에 원천이 지워졌다)다. 동기화 기록의 실패 사유도 같은 값을 쓰고, 일정이 겹쳐 시작하지 못한 회차만 `sync_in_progress`를 쓴다.
- [정함] `encrypted_document`는 파서가 암호가 걸린 파일을 알리는 신호로만 남고, 문서와 색인 상태와 작업 행의 오류 코드 칸에는 더 쓰이지 않는다(건너뜀 절).
- [정함] 동기화 기록의 개수 `failed`가 쓰는 키는 작업 코드이고, `skipped`가 쓰는 키는 건너뜀 사유 둘, `not_accepted`가 쓰는 키는 수집 정책의 사유 셋이다. 모르는 키가 생기지 않게 셋 모두 닫힌 값이다.
- [정함] MCP 도구의 오류 코드는 바뀌지 않는다.

### 로그

- [넘겨받음] 질문 내용, 연결 정보, 원본 문서의 내용을 로그에 남기지 않는다(원칙 V). core 명세는 문서의 키와 제목을 로그에 싣지 않고 문서 ID만 싣게 정했고, 수집 코드의 독스트링도 원본 경로와 문서의 키를 싣지 않는다고 적는다(코드를 읽었다. 로그를 남기는 자리를 모두 훑어 확인한 것은 아니다).
- [정함] 동기화는 시작과 끝에 한 줄씩 남긴다. 싣는 것은 원천 이름, 동기화 기록의 식별자, 요청 ID, 시작시킨 것, 끝에서는 결과와 실패 코드와 개수와 걸린 시간이다. 문서의 키, 파일 이름, 폴더 이름을 포함한 커넥터 설정, 커넥터가 낸 예외의 글은 싣지 않는다. 설치처가 만든 커넥터의 예외에서는 예외의 종류 이름만 남긴다.
- [정함] 파일 하나를 읽지 못한 것은 줄마다 남기지 않고 동기화의 끝 줄에 코드별 개수로만 남긴다. 어느 파일인지는 관리 API의 문서 목록(실패한 문서)과 동기화 기록의 개수로 본다. 새 파일이라 문서가 아직 없으면 개수만 남는다.
- [정함] 서버 경로 커넥터가 목록에 넣지 않은 것(심볼릭 링크, 보통 파일이 아닌 것, 이름을 읽을 수 없는 파일)은 동기화마다 종류별 개수를 한 줄로 남긴다.
- [정함] 커넥터 호출이 한도를 넘겨 기다리기를 그만둘 때 그 프로세스(서버, 작업자)가 한 줄을 남긴다(동기화의 차례 절). 싣는 것은 원천 이름(원천이 아직 없는 만드는 요청의 폴더 확인에서는 비운다), 호출의 종류(`list`, `fetch`, `check`, 폴더 확인), 그 프로세스에 끝나지 않은 채 남은 호출의 수다. 문서의 키와 커넥터 설정은 싣지 않는다. 남은 호출이 있어 커넥터를 부르지 않고 답한 것은 줄마다 남기지 않는다. 운영자는 이 줄로 동기화나 연결 확인이 `source_unreadable`로 끝난 까닭이 한도인지를 알고, 남은 호출의 수로 막힌 스레드가 얼마나 남았는지 본다.
- [정함] 일정 확인은 동기화나 정리 작업을 넣었을 때와 겹쳐서 넣지 못했을 때만 한 줄을 남긴다. 아무것도 넣지 않은 확인은 남기지 않는다(5초마다 도는 일이다). 정리 작업은 끝에 한 줄로 종류별 개수(완전히 지운 문서, 완전히 지운 원천, 치운 원본, 지운 동기화 기록, 다시 넣은 작업)를 남긴다.

### 단독 compose와 설치 안내

- [넘겨받음] 단독 compose에서 운영자는 `.env`에 서버 기계의 폴더 하나를 적는다. 그 폴더가 서버와 작업자 컨테이너의 `/sources`에 읽기 전용으로 붙고, 원천을 더할 때 compose 파일을 고치지 않는다. 공유 폴더(NFS, SMB)는 운영자가 서버 기계에서 그 부모 폴더 아래에 붙인다(ADR 0021 "서버 경로 원천의 폴더").
- [정함] `.env`에 적는 변수의 이름은 `RAG_ENGINE_SOURCES_DIR`이고, 적지 않으면 설치 폴더의 `sources/`다. compose는 서버와 작업자 두 서비스에 그 폴더를 `/sources`로 읽기 전용으로 붙인다. 마이그레이션 컨테이너에는 붙이지 않는다.
- [정함] compose가 정하는 서버 설정에 `RAG_SOURCES_DIR`(`/sources`)를 더한다. 설치 안내는 compose가 정하는 값이라 `.env`에 적어도 compose의 값이 이긴다고 변수 셋을 적어 두었는데, 그 변수가 넷이 된다.
- [정함] 묶음에 `sources/README.txt`를 넣는다. 빈 폴더는 묶음에 담기지 않기 때문이고, 그 파일은 이 폴더 아래에 원천마다 하위 폴더를 만든다는 것을 두세 줄로 적는다. 부모 폴더 바로 아래의 파일이라 어느 원천에도 들지 않는다(서버 경로 커넥터 절).
- [정함] `.env.example`에 주석 처리한 예시 줄 다섯을 더한다. `RAG_ENGINE_SOURCES_DIR`, `RAG_SCHEDULE_TIMEZONE`, `RAG_DELETED_RETENTION_DAYS`, `RAG_SYNC_RECORD_RETENTION_DAYS`, `RAG_SOURCE_READ_TIMEOUT_SECONDS`다.
- [정함] 서버와 작업자는 uid 10001로 돈다(단독 compose 파일 `compose.yaml`의 머리 주석이 그렇게 적는다. 설치 안내는 이미지가 정한 사용자라고만 적는다). 원천 폴더와 그 안의 파일은 그 사용자가 읽을 수 있어야 하고, 읽지 못하면 연결 확인과 동기화가 `source_unreadable`로 알린다. 권한을 맞추는 법은 설치 안내가 적는다.
- [사용자 선택] 전파 설정(컨테이너에 붙여 준 폴더 안에 나중에 또 붙인 폴더가 컨테이너에도 보이게 할지를 정하는 Docker의 설정)은 compose에 넣지 않는다. 설치 안내에 "공유 폴더는 서버를 띄우기 전에 붙이고, 띄운 뒤에 붙였거나 떼었다 다시 붙였으면 서버와 작업자를 다시 띄운다(`docker compose restart server worker`)"를 적는다. 고르지 않은 안은 둘이다. compose에 `rslave`를 넣어 다시 띄우지 않아도 보이게 하는 안과, `.env`의 변수로 둘 가운데 고르게 하는 안이다.
- [정함] 그 선택의 근거는 프로브가 쟀다(`mount-propagation/probe_out.txt`. 괄호의 수는 그 출력의 단계 번호다). 기본 설정으로 띄운 컨테이너에는 뜬 뒤에 붙인 하위 폴더의 파일이 보이지 않았다(2). `rslave`로 띄운 컨테이너에는 보였다(2). 그런데 서버 기계의 루트가 shared가 아닐 때는 `rslave`로 컨테이너가 뜨지 않았고(0), 나중에 전해진 폴더에는 읽기 전용으로 붙였는데도 쓰기가 됐다(3). 붙이기 전에 떠 있던 컨테이너를 `docker restart`로 다시 띄우면 그 폴더가 보였고 쓰기는 막혔다(4). 떼었다 다시 붙인 폴더는 다시 띄우기 전까지 떼기 전의 내용이 그대로 보였고, 다시 띄운 뒤에 새 내용이 보였다(5, 6). 부모 폴더 자체가 나중에 붙은 경우에도 기본 설정에서는 보이지 않았다(7). 단독 compose가 붙일 모양(짧은 문법, `.env`의 변수, 서버와 작업자 두 서비스, uid 10001)에서 설치 안내가 적을 명령 `docker compose restart server worker`로 다시 띄워도 결과가 같았다. 뜬 뒤에 붙인 폴더는 다시 띄우기 전에는 두 컨테이너에 보이지 않다가 다시 띄운 뒤에 보였고 쓰기는 막혔으며, 떼었다 다시 붙인 폴더는 다시 띄운 뒤에 새 내용이 보였다(9).
- [정함] 그 측정의 한계는 둘이다. 측정은 Docker Desktop의 WSL2 커널 위에 띄운 리눅스 Docker에서 했고, 배포판 리눅스 서버에서 하지 않았다. 공유 폴더는 메모리 파일 시스템으로 흉내 냈고, 실제 NFS·SMB 공유 폴더에서는 재지 않았다(끊긴 공유 폴더의 읽기는 프로브 `stuck-mount`가 실제 공유 폴더로 쟀지만, 전파 설정은 재지 않았다).
- [이력] ADR 0021의 본문은 전파 설정으로 풀리는지를 명세가 재고, 풀리지 않으면 "다시 띄운다"를 설치 안내에 적는다고 했다. 재 보니 전파 설정으로 풀리기는 하지만 위의 두 문제가 있어 사용자가 설치 안내에 적는 쪽을 골랐다. 그 ADR에 2026-11-21 이력을 더하고 그 문장 뒤에 포인터를 달았다.
- [정함] 공유 폴더가 붙지 않은 채 동기화가 돌아도 문서가 지워지지 않는 것은 동기화의 차례 절의 빈 목록 판정이 맡는다. 컨테이너에는 빈 폴더로 보이거나 원천 폴더가 없는 것으로 보이고, 어느 쪽이든 `source_unreadable`로 실패한다. 공유 폴더를 붙이는 자리에 문서가 아닌 파일만 놓여 있으면 `nothing_accepted`로 실패한다. 막지 못하는 경우가 하나 남는다. 그 자리에 문서 형식의 파일이 놓여 있으면 그 파일이 후보가 되어, 나머지 문서는 목록에 없는 문서로 삭제 반영된다(일부만 줄어든 경우는 목록대로 지운다는 ADR 0022의 결정이다). 그래서 설치 안내가 공유 폴더를 붙이는 자리에는 문서 파일을 두지 말라고 적는다. 떼었다 다시 붙인 뒤 다시 띄우지 않은 동안의 동기화는 컨테이너에 보이는 떼기 전의 목록대로 돌아, 그사이 바뀐 것을 반영하지 못한다. 설치 안내가 다시 붙였을 때도 다시 띄우라고 적는 까닭이다.
- [정함] 설치 안내(묶음의 `README.md`)는 네 군데를 고친다. 6절 "문서 넣기"에 하위 절 "서버 폴더의 문서 가져오기"를 더하고, 3절이 compose가 정하는 값으로 적은 셋을 넷으로 고치고, 11절 "볼륨과 지우면 안 되는 것"에 `sources/`는 이 서버가 읽기만 하고 쓰거나 지우지 않는다는 것을 적고, 14절 "업그레이드"가 그대로 두는 것으로 적은 목록에 `sources/`를 더한다. 새 절을 끼워 넣지 않고 하위 절로 더하므로 안내 안에서 다른 절을 번호로 가리킨 자리(9절, 10절, 12절, 14절)가 그대로다.
- [정함] 6절의 새 하위 절이 적는 것은 다음과 같다. 원천 폴더를 만들고 권한을 맞추는 법, 공유 폴더를 붙이는 때와 다시 띄우는 명령, 관리 API로 원천을 만들고 연결 확인과 지금 동기화를 부르고 동기화 기록을 보는 예시 명령, 일정을 적는 법과 시간대, 폴더가 비었거나 사라졌거나 문서가 될 파일이 하나도 없을 때 동기화가 문서를 지우지 않는다는 것과 그때의 길("빈 목록도 반영", 빈 폴더를 그 자리에 만들어 두는 길, 원천을 지우는 길), 공유 폴더를 붙이는 자리에는 문서 파일을 두지 않는다는 것, 느린 공유 폴더에서 큰 파일을 읽다가 동기화가 `source_unreadable`로 끝날 때의 길(`RAG_SOURCE_READ_TIMEOUT_SECONDS`를 늘리거나 크기 상한을 낮춘다. 크기 상한을 낮추면 새 상한을 넘는 다른 파일의 문서도 다음 동기화에서 검색에서 빠지므로 한도를 늘리는 길을 먼저 쓴다. 걸린 파일을 짐작할 수 있으면 제외 패턴으로 뺀다. 제외 패턴으로 뺀 파일의 문서도 다음 동기화에서 검색에서 빠진다는 것과, 크기 상한을 낮추거나 제외 패턴을 더한 뒤 문서가 될 파일이 하나도 남지 않으면 그 동기화가 `nothing_accepted`로 실패하고 아무것도 지우지 않는다는 것을 함께 적는다), 끊긴 공유 폴더 때문에 원천이 계속 `source_unreadable`일 때 할 일의 차례와 SMB 공유 폴더를 `hard` 옵션 없이 붙인다는 것(아래 두 항목), 원천을 지우고 되살리는 법과 보관 기간, 끝나지 않는 동기화를 멈추는 차례(그 원천을 지우고, 그 동기화의 기록이 `source_deleted`로 닫힌 것을 본 뒤에 되살린다. 닫히기 전에 되살려 그 동기화가 이어서 돌면 다시 지우고 기록이 닫히기를 기다린다. 동기화의 차례 절의 끝없는 목록 항목), 심볼릭 링크를 따라가지 않는다는 것, `ingest` 명령으로 `default`에 넣어 둔 폴더를 서버 경로 원천으로 옮기는 절차(따르는 것과 범위 절), 이 기능이 없던 묶음에서 올라온 설치에서는 Docker가 `sources/`를 root의 폴더로 만들어 둔다는 것(아래 항목)이다.
- [사용자 선택] 끊긴 공유 폴더 때문에 원천이 계속 `source_unreadable`일 때 설치 안내가 적는 차례는 셋이다. 첫째, 공유 폴더를 되살린다(파일 서버나 네트워크를 고친다). 막혀 있던 호출은 이것으로 돌아오고, 그 설정의 호출이 모두 돌아오면 다음 동기화가 다시 부른다(동기화의 차례 절의 돌아오지 않는 호출 항목). 둘째, 되살릴 수 없거나 되살린 뒤에도 그 원천이 계속 `source_unreadable`이면 서버와 작업자를 함께 다시 띄운다(`docker compose restart server worker`). 둘을 함께 띄우는 것은 어느 컨테이너가 먼저 그 폴더를 보다 막혔는지 운영자가 알 수 없어서다(아래의 같은 폴더를 함께 기다리는 경우). 셋째, 그 명령이 컨테이너를 멈추지 못했다는 오류로 실패하면 공유 폴더를 되살린 뒤 다시 치고(프로브에서는 `docker stop`이 `did not receive an exit event`를 냈다. `docker compose restart`가 내는 글은 재지 않았다. 명세 검토가 짚었다), 되살릴 수 없으면 서버 기계(또는 Docker)를 다시 띄운다. 함께 적는 것이 셋 있다. 하나, 첫째에서 공유 폴더를 떼었다 다시 붙였거나 셋째에서 서버 기계를 다시 띄웠으면, 공유 폴더를 붙인 뒤에 서버와 작업자를 다시 띄워야 컨테이너에 새로 붙인 폴더가 보인다(위의 전파 설정 항목). 둘, 둘째에서 다시 띄운 작업자가 그 원천의 동기화에서 막힌 호출을 기다리던 중이었으면, 작업자는 Docker의 유예 시간(기본 10초) 뒤에 강제로 끝나고(작업자는 종료 신호를 받으면 진행 중인 작업을 끝낸 뒤 나간다는 작업자 코드의 설명과 Docker 문서를 읽고 따진 어림이다) 그 동기화는 작업 담당 기록의 기한(기본 600초)이 지날 때까지 도는 중으로 남아 그동안 "지금 동기화"가 시작되지 않고, 기한이 지나면 작업자가 처음부터 다시 돈다(동기화의 차례 절의 기한 항목). 셋, 공유 폴더가 끊긴 채 다시 띄우면 기억이 비어 새 호출이 다시 막히고(한도까지, SMB의 기본값에서는 오류로 돌아올 때까지), 서버와 작업자가 다시 같은 폴더를 함께 기다려 다음에 다시 띄울 때 셋째의 실패가 또 날 수 있다. 근거는 프로브 `stuck-mount`가 SMB(CIFS)와 NFS 공유 폴더를 붙여 쟀다(Further Notes). 공유 폴더를 다시 잇자 막혀 있던 호출은 4.2초 안에 돌아왔다(`hard`로 붙인 SMB에서 서버를 떼거나 죽인 두 칸은 다시 잇는 명령이 커널 헛돎 속에서 돌아오지 않아 재지 못했다). 제품이 쓰려는 모양(읽기를 맡은 daemon 스레드만 막혀 있는 프로세스)의 컨테이너는 끊고 10초에 멈췄을 때 열한 칸 모두에서 `docker stop`이 0.2~1.2초에 끝났고 `docker restart`로 다시 떴다(멈출 때 읽기가 이미 돌아와 있던 칸도 센 수다). 멈추고 다시 띄우는 일이 맞지 않은 경우는 SMB에서 둘이다(셋째 예외인 커널 헛돎은 아래 항목). 다른 컨테이너의 프로세스가 같은 공유 폴더를 먼저 보다 막혀 있으면, 나중에 그 폴더를 본 컨테이너의 `docker stop`이 24초 뒤 그 오류로 실패하고 컨테이너가 남았다. 먼저 보던 프로세스를 SIGKILL로 끝내자 남은 컨테이너도 멈췄다(그 뒤에 다시 친 `docker stop`은 0.02~0.03초에 끝났다). 서버가 응답만 멈춘 지 200초쯤 뒤에는 막힌 프로세스가 SIGKILL로도 8초 안에 끝나지 않았고, 그때 멈춘 컨테이너도 같은 오류로 실패했다. 서버와 작업자를 함께 다시 띄우면 앞의 경우가 풀리는지와, 서버 기계를 다시 띄우면 풀리는지는 재지 않았다(어림). 고르지 않은 안은 둘이다. 다시 띄우기만 적는 안은 안내가 짧지만 끊긴 채 다시 띄우는 길로 이끈다. 서버의 폴더 확인을 작업 대기열을 거쳐 작업자에게 맡겨 두 컨테이너가 같은 폴더를 함께 기다리지 않게 하는 안은 폴더 확인이 겹치는 경우만 없애고(연결 확인은 여전히 서버에서 돌아, 두 컨테이너가 같은 폴더를 함께 기다리는 경우가 남는다), 원천을 만드는 요청이 작업자를 기다리게 한다(사용자가 2026-11-22에 골랐다. 일지의 질문 7).
- [사용자 선택] 설치 안내는 SMB 공유 폴더를 `hard` 옵션 없이 기본값(soft)으로 붙이라고 적는다. 까닭은 실측에서 본 커널의 헛돎이다. SMB 공유 폴더 여섯 칸(기본값 셋, `hard` 셋)을 함께 끊어 두었을 때, 커널의 작업 스레드 하나가 CPU 하나를 17분쯤 쥐고 헛돌았다. 그동안 Docker의 명령 일부(`start`, `network connect`, `unpause`, `inspect`)와 공유 폴더 떼기가 돌아오지 않았고, 가상 기계의 디스크 저널 스레드와 `dockerd`도 막혔다고 커널이 적었다(`docker ps`와 `docker exec`는 바로 돌아왔다). `hard`로 붙인 두 칸(서버를 네트워크에서 뗀 칸과 서버를 죽인 칸)의 서버로 가는 연결을 살아 있는 서버로 돌리는 규칙을 손으로 넣자 3초 안에 풀려 그 두 칸 가운데 하나가 일으킨 것으로 보지만, 근거는 시각이 맞아떨어진 것 하나다(`stuck-mount/lockup_seen.txt`. 프로브의 출력이 아니라 손으로 친 명령과 그 출력이다. Docker Desktop의 WSL2 커널 6.18.58.1에서 한 번 봤고, 어느 칸인지 가르지 못했으며 다시 일으켜 확인하지 않았다). soft에서는 막힌 호출이 대부분 10~264초 안에 오류로 돌아왔다(헛돈 첫 실행에서는 285초가 걸린 호출이 있었다). 목록에서 나면 그 동기화가 `source_unreadable`로 끝나고, 파일 하나에서 나면 그 파일을 실패로 세고 계속한다. 어느 쪽이든 다음 일정이나 "지금 동기화"에서 다시 보고, 색인 작업은 재시도 규칙으로 다시 예약된다. 치르는 값은 둘이다. 하나는 `hard`의 좋은 점(서버가 돌아오면 막힌 호출이 성공으로 이어진다)을 버린다는 것이다. soft에서도 미리 열어 둔 파일의 읽기는 서버를 얼린 400초 동안 돌아오지 않았다. 다른 하나는 목록을 받은 뒤에 끊기면 그 동기화가 오래 돌 수 있다는 것이다. 바뀐 파일마다 읽기가 오류로 돌아올 때까지 기다리고(실측에서 10초에서 4분 남짓) 그 파일을 실패로 센 뒤 다음 파일로 가므로, 바뀐 파일이 많으면 그만큼 도는 중으로 남고 그 동기화는 `source_unreadable`이 아니라 실패한 파일을 센 채 끝난다. 그래서 첫째 차례의 계기("계속 `source_unreadable`")는 다음 동기화가 목록에서 오류를 받을 때 보인다(명세의 규칙과 잰 시간으로 따진 어림이다). NFS는 기본값(hard)에서 이번 실측에 문제가 없어 따로 적지 않는다. 고르지 않은 안은 안내에 적지 않고 프로브 기록과 Further Notes에만 남기는 것이다(사용자가 2026-11-22에 골랐다. 일지의 질문 8과, 고른 설명의 재시도 대목을 바로잡은 질문 10).
- [정함] 단독 compose에 볼륨 하나를 더하는 변경은 올릴 때 운영자가 손댈 것이 없다. 변수를 적지 않으면 `sources/`를 쓰고, 이 기능이 없던 묶음에서 올라와 그 폴더가 없으면 Docker가 빈 폴더를 만든다. 프로브가 쟀다. `sources/`가 없고 변수도 적지 않은 설치 폴더에서 `docker compose up`이 종료 코드 0으로 끝났고, Docker가 그 폴더를 root의 것(권한 755)으로 만들었으며, uid 10001로 도는 두 컨테이너가 그 빈 폴더를 읽었다(`mount-propagation/probe_out.txt`의 10). 잰 compose 5.6.1에서는 긴 문법으로 적어도 폴더가 만들어졌다. 그래서 그 PR의 제목에는 느낌표를 붙이지 않는다(ADR 0020 "올릴 때 운영자가 손댈 것의 기준"). 그렇게 만들어진 폴더는 root의 것이라 운영자가 그 아래에 원천 폴더를 만들 때 관리자 권한이 필요하고, 설치 안내가 이것을 적는다. 마이그레이션이 든 PR에는 느낌표가 붙는다.

### 규약 문서와 낡은 문장

- [넘겨받음] cronsim을 의존성으로 더하는 티켓이 `docs/constitution/tech.md`의 작업 대기열 칸에 일정과 그 라이브러리를 적고, `pyproject.toml`의 import 금지 목록에 그 이름을 더한다. 목록이 열일곱에서 열여덟이 되므로 그 수를 적은 자리(계약의 이름과 그 위의 주석, `CLAUDE.md` 레이어 절)도 같은 티켓이 고친다(ADR 0022 Consequences).
- [정함] 그 티켓은 헌법 문서를 고치므로 `docs/constitution/README.md`가 적은 규칙대로 헌법 버전을 올리고, 커밋 전에 형제 브랜치와 버전이 겹치는지 본다(`CLAUDE.md` 환경 함정).
- [넘겨받음] 관리 API의 응답 모델 머리 설명이 문서 상태를 넷이라고 적은 것은 건너뜀을 넣는 티켓이 고친다(ADR 0022 Consequences).
- [정함] 오류 코드를 정의한 자리의 머리 설명과 주석이 적은 수(작업 코드 열넷, Problem Details의 코드 열넷)는 코드를 더하는 티켓마다 고친다.
- [정함] 포트를 정의한 모듈의 머리 설명에는 이 기능으로 낡게 되는 문장이 둘 있다(코드를 읽었다). 작업 단위 안에서 얻는 포트가 넷뿐이라는 문장은 `SyncRecordStore`를 넣는 티켓이 다섯으로 고친다. `Connector`와 `Transform`의 Protocol을 source-sync가 만든다는 문장은 커넥터 인터페이스를 넣는 티켓이 고친다. 변환 인터페이스는 db-source로 넘어갔기 때문이다(ADR 0021 "이번에 짓지 않는 것").
- [정함] 설치 안내와 `.env.example`은 단독 compose 절이 정한 대로 그 절의 티켓이 고친다. `docs/release-notes/features/`의 기능 단락은 이 기능의 마지막 티켓을 닫는 커밋이 쓴다(`CLAUDE.md` 지도).

### 티켓을 나눌 때 함께 둘 것

- [정함] 지움 표시가 선 원천의 문서를 지워진 문서로 읽는 변경(`search`가 그 조각을 빼는 것, `get_document`와 관리 API의 문서 조회·목록이 그 문서를 지워진 것으로 보이는 것. 원천 삭제와 되살리기 절)과 원천을 지우는 관리 API는 한 티켓에 둔다. 따로 내면 지운 원천의 문서가 원천 삭제 작업이 끝날 때까지 검색에 남거나, 검색에서는 빠졌는데 문서 조회에는 살아 있는 문서로 보이는 판이 생긴다(명세 검토가 `get_document`와 문서 조회를 더했다).
- [정함] 건너뜀으로 옮기는 마이그레이션, 색인 작업이 건너뜀을 쓰는 변경, 관리 API의 문서 목록이 건너뜀을 보이는 변경(`status=skipped`, `skip_reason`), 수집 API가 건너뜀 문서에 `unchanged`로 답하는 변경은 한 티켓에 둔다. 마이그레이션만 먼저 나가면 그 뒤에 들어온 암호 걸린 문서가 다시 실패로 남고, 문서 목록이 뒤에 나가면 건너뜀 문서를 거를 길이 없는 판이 생긴다.
- [정함] 수집과 동기화가 원천 행을 잡고 지움 표시를 보는 변경은 원천을 지우는 관리 API보다 먼저이거나 같은 티켓이다. 뒤에 오면 지운 원천에 문서가 들어가는 틈이 생긴다.
- [정함] 단독 compose에 부모 폴더를 붙이는 변경, `.env.example`, 설치 안내, 단독 compose 시험은 한 티켓에 둔다. 그 티켓은 원천 만들기와 지금 동기화가 선 뒤에 온다. 단독 compose 시험이 원천을 만들어 동기화한 문서를 검색으로 본다.
- [정함] `rag-engine --version`의 목록에 커넥터 인터페이스 버전을 더하는 일은 커넥터 인터페이스를 넣는 티켓에 둔다.
- [정함] 이 기능의 스키마(표, 칸, 제약, 색인)는 커넥터 인터페이스를 넣는 첫 티켓의 마이그레이션 하나에 모두 둔다. 마이그레이션은 저마다 바로 앞의 마이그레이션을 가리켜 한 줄로 이어지므로, 나란히 도는 티켓이 저마다 마이그레이션을 더하면 서로 부딪친다. 그 뒤의 티켓 가운데 마이그레이션을 더하는 것은 건너뜀으로 옮기는 마이그레이션(데이터만 옮긴다)을 넣는 티켓 하나다.
- [정함] 문서를 가리키지 않는 작업을 처음 넣는 티켓은 다섯 가지를 함께 고친다. 작업 엔티티의 문서 칸을 비울 수 있게 하는 것, 작업자가 작업의 종류로 갈라 처리하는 것, 꺼내는 순서, 관리 API의 작업 조회(작업 대기열 절의 마지막 항목), 같은 원천의 같은 종류 작업을 하나로 묶는 부분 유일 색인을 쓰는 문장이다. 지금의 작업 응답은 문서 식별자와 문서를 반드시 싣고, 작업자는 모든 작업을 문서의 색인으로 돈다(명세 검토가 코드를 읽고 냈다). 그래서 하나라도 뒤에 오면 그 사이의 판에서 작업 목록이 실패하거나 작업자가 동기화 작업을 색인 작업으로 잘못 돈다.
- [정함] 커넥터 호출의 한도, 호출마다 따로 띄운 일, 돌아오지 않는 호출의 기억(동기화의 차례 절)은 서버와 작업자가 저마다 커넥터를 처음 부르는 티켓보다 먼저이거나 같은 티켓이다. 뒤에 오면 그 사이의 판에서 끊긴 공유 폴더 하나가 서버의 요청이나 작업자의 자리를 끝없이 잡는다.
- [정함] 원천 이름의 규칙(데이터 모델과 스키마 절)은 원천 이름을 받는 첫 티켓에 둔다. 그 티켓이 `migrate`가 만드는 `default`와 `upload`가 규칙에 맞는지도 시험으로 본다.
- [정함] 수집 API의 삭제와 동기화의 삭제 반영이 원천과 함께 지워졌다는 표시를 지우는 변경(원천 삭제와 되살리기 절)은 원천 되살리기와 같은 티켓이거나 그보다 먼저다. 뒤에 오면 되살린 원천에서 따로 지운 문서를 원천 되살리기 작업이 되살린다. 정리 작업을 넣는 티켓은 첫째 단계가 그 표시가 있는 문서를 건너뛰는 것과 다섯째 단계가 멈춘 원천 삭제와 원천 되살리기를 다시 잇는 것을 함께 넣는다(정리 작업 절. 명세 검토가 냈다). 다섯째 단계가 원천 되살리기 작업을 다시 넣으므로 그 티켓은 원천 되살리기보다 뒤에 온다.

## Testing Decisions

- [사용자 선택] 주 이음매는 core와 같다. 서버의 HTTP 표면(관리 API, 수집 API, `/mcp`)을 실제 테스트 PostgreSQL과 TEI 스텁(임베딩 서버 TEI를 흉내 내는 시험용 가짜 서버) 위에서 부르고, 작업자는 한 번 돌리는 입구로 돌린다(core 명세 Testing Decisions의 선례). 이 기능이 더하는 것은 둘이다. 부모 폴더를 시험마다 만드는 임시 폴더로 바꾸고(`RAG_SOURCES_DIR`), 일정은 시계를 기다리지 않고 "지금 시각"을 넣어 일정 확인을 한 번 돌린다. 고르지 않은 안은 둘이다. 실제 컨테이너를 띄운 단독 compose 시험에서 전 과정을 보는 안(컨테이너를 띄우는 만큼 CI가 느려진다)과, 컨테이너에 폴더를 붙이는 장면을 자동 시험에서 빼는 안(compose 파일의 실수를 CI가 잡지 못한다)이다.
- [정함] 시험은 밖에서 보이는 것으로 판정한다. 관리 API의 응답, 검색 결과, 동기화 기록, 문서 목록, 작업 목록이다. 표의 행을 직접 읽는 것은 아래 어댑터 시험뿐이다.
- [정함] 주 이음매에서 보는 장면은 다음과 같다.

| 장면 | 밖에서 보이는 것 |
|---|---|
| 폴더에 PDF, DOCX, HWPX를 하나씩 두고 원천을 만들어 지금 동기화하고 작업자를 한 번 돌린다 | 세 문서가 검색에 나오고 동기화 기록의 `added`가 3이다 |
| 파일 하나를 지우고 동기화한다(임베딩 스텁이 답하지 않게 둔 채) | 그 문서가 검색에서 빠진다. 같은 동기화가 넣은 문서의 색인이 끝나지 않아도 빠진다 |
| 파일의 내용을 고친 뒤 동기화한다. 따로, 수정 시각만 바꾼 뒤 동기화한다 | 앞은 `updated`가 1이고 새 색인 작업이 생긴다. 뒤는 `unchanged`이고 작업이 생기지 않는다 |
| 아무것도 바뀌지 않은 원천을 동기화한다(읽은 횟수를 세는 가짜 커넥터) | `fetch`가 한 번도 불리지 않는다 |
| 원천 폴더를 없애거나 비운 뒤 동기화한다 | 기록이 `failed`와 `source_unreadable`이고 문서는 검색에 그대로다. 빈 폴더에 "빈 목록도 반영"을 켜면 문서가 빠진다. 없는 폴더에는 켜도 실패한다 |
| 숨김 파일, `~$` 파일, 제외 패턴에 맞는 파일, 지원하지 않는 형식, 상한을 넘는 파일을 둔다 | 문서가 생기지 않고 `not_accepted`의 사유별 개수에 든다. 문서가 하나도 없는 원천에서는 모든 파일이 걸려도 그 동기화가 실패가 아니다 |
| 이미 색인된 문서가 있는 원천에서 문서 파일을 모두 치우고 숨김 파일과 지원하지 않는 형식의 파일만 둔 뒤 동기화한다 | 기록이 `failed`와 `nothing_accepted`이고 `listed`와 `not_accepted`의 개수가 남으며, 문서는 검색에 그대로다. "빈 목록도 반영"을 켜면 문서가 빠지고 기록은 `succeeded`다. 그 뒤의 보통 동기화는 실패가 아니다 |
| 제외 패턴을 더한 뒤 동기화한다(패턴에 맞지 않는 문서 하나는 남긴다) | 그 패턴에 맞는, 이미 색인된 문서가 검색에서 빠진다 |
| 암호가 걸린 PDF와 글자가 없는 PDF를 둔다 | 문서 상태가 `skipped`이고 사유가 실린다. 작업은 `succeeded`다. 다음 동기화 기록의 `skipped`에 세어지고 문서 목록의 `status=skipped`에 나온다 |
| 일정이 지난 원천에 일정 확인을 한 번 돌리고, 같은 시각으로 한 번 더 돌린다 | 동기화 작업이 하나다. 놓친 회차가 여럿이어도 하나다. 일시 중지한 원천에는 생기지 않는다. 앞 동기화가 대기 중이면 `not_started` 기록만 남는다 |
| 일정에 여섯 칸 표현식, 값이 틀린 표현식, 2월 31일을 적는다 | 422이고 응답에 라이브러리가 낸 글이 없다 |
| 원천을 지운 직후에(작업자를 돌리기 전에) 검색하고 그 원천으로 수집을 보낸다 | 그 원천의 문서가 검색에 없고, 수집은 409 `source_deleted`다 |
| 지운 원천을 되살리고 작업자를 한 번 돌린다(임베딩 호출을 세는 스텁) | 문서가 검색에 돌아오고 임베딩 호출이 0번이다. 원천을 지우기 전에 따로 지운 문서는 돌아오지 않는다 |
| 밀어 넣는 원천의 지운 문서를 되살린다. 따로, 가져오는 원천의 지운 문서를 되살리려 한다 | 앞은 검색에 돌아온다. 뒤는 409 `wrong_source_kind`다 |
| 시각을 넣어 정리 작업을 한 번 돌린다 | 보관 기간이 지난 지운 문서는 되살리는 요청이 404가 되고, 보관 기간이 지난 지운 원천의 이름으로 새 원천을 만들 수 있다(그 원천의 문서에 끝난 색인 작업이 남아 있어도 지워진다). 하루 넘게 묵은 주인 없는 원본은 지워지고 방금 쓴 원본은 남는다. 부모 폴더(`RAG_SOURCES_DIR`) 아래의 파일은 하나도 지워지지 않는다 |
| 지운 원천을 되살리는 요청만 보내고, 작업자를 돌리기 전에 보관 기간이 지난 시각을 넣어 정리 작업을 돌린 뒤 작업자를 돌린다 | 그 원천의 문서가 검색에 돌아온다. 정리 작업이 원천과 함께 지워졌다는 표시가 남은 문서를 지우지 않았다 |
| 지운 원천을 되살리는 요청을 보낸 뒤, 작업자를 돌리기 전에 그 원천의 문서 하나를 수집 API로 지우고 작업자를 돌린다 | 그 문서만 검색에 돌아오지 않는다 |
| 문서의 내용을 바꿔 넣고, 그 색인이 돌기 전에 원천을 지웠다가 되살린 뒤 작업자를 돌린다 | 검색에 옛 내용이 나오지 않고 새 내용이 나온다 |
| 재색인을 시작한 지식베이스에서 건너뜀 문서의 색인 작업을 마지막에 돌린다 | 새 색인 판으로 전환된다 |
| 글자가 없어 건너뛴 문서를 둔 채, 글을 내는 가짜 파서(파서 버전이 다르다)로 바꿔 끼우고 재색인한다 | 그 문서가 검색에 나오고 문서 상태가 `skipped`가 아니다 |
| 수집 API에 `source`를 적지 않거나, `upload`나 없는 이름이나 가져오는 원천의 이름을 적는다 | 차례로 `default`에 들어가고, `upload`에 들어가고, 404이고, 409다. 넣은 문서는 작업자를 한 번 돌린 뒤 검색에 나온다. 원천이 다르면 같은 키가 서로 다른 문서로 남는다 |
| 원천의 폴더에 `..`가 든 값, `/`로 시작하는 값, 없는 폴더, 심볼릭 링크인 폴더, 다른 원천과 겹치는 폴더를 적는다 | 차례로 422와 `invalid_config`, 422와 `invalid_config`, 422와 `not_found`, 422와 `rejected`, 409 `source_folder_overlap`이다 |
| 서로 겹치는 폴더(`a`와 `a/b`)의 원천을 만드는 요청 둘을 동시에 보낸다. 첫째 요청은 겹침 확인을 지난 뒤 커밋하기 전에 붙잡아 둔다(폴더를 여는 호출이나 그 뒤의 자리를 바꿔 끼운다. 시험 서버는 스레드에서 돈다. `tests/conftest.py`의 선례). 둘째 요청을 보낸 뒤 첫째를 풀어 준다 | 하나만 만들어지고 다른 하나는 409 `source_folder_overlap`이다. 원천 목록에 둘 가운데 하나만 있다. 첫째를 붙잡지 않으면 두 요청이 저절로 차례로 지나 잠금이 없어도 이 시험이 초록이 된다(명세 검토가 냈다) |
| 원천을 만든 뒤 연결 확인을 부른다. 따로, 폴더를 지운 뒤와 폴더를 여는 호출이 권한 오류를 내게 바꿔 끼운 뒤에 부른다 | 앞은 200과 `ok` 참이다. 뒤의 둘은 200과 `ok` 거짓, `code` `source_unreadable`이다 |
| 일정 `0 2 * * *`를 적어 원천을 만들고 원천 보기를 부른다. 시간대 설정을 바꿔 한 번 더 한다. 그 뒤 일정을 없애거나 일시 중지하고, 다시 시작한 원천에는 다음 시각을 넣어 일정 확인을 돌린다 | `next_run_at`이 그 시간대의 다음 02:00을 UTC로 적은 값이다. 일정을 없애거나 일시 중지하면 null이고, 다시 시작하면 다음 시각이 다시 차고 그 시각의 일정 확인이 동기화 작업을 넣는다 |
| `default`와 `upload`를 지우려 한다 | 409 `source_protected`이고 두 원천은 그대로다 |
| 원천을 지운 뒤 작업자를 돌리기 전에 되살리려 한다. 따로, 되살린 뒤 작업자를 돌리기 전에 다시 지우려 한다 | 둘 다 409 `source_change_in_progress`다 |
| 보관 기간보다 오래전에 지운 원천을 정리 작업이 지우기 전에 되살리려 한다(관리 API는 시각을 받지 않으므로, 원천을 지우는 유스케이스를 지난 시각으로 불러 둔다) | 409 `source_retention_expired`이고 원천은 지운 채다 |
| 규칙에 어긋나는 이름(대문자가 든 것, 64자, `-`로 시작하는 것)으로 원천을 만들고, 같은 이름을 수집 API의 `source`에 적는다 | 모두 422다 |
| 시간대 설정에 모르는 이름을 주고 서버와 작업자를 띄운다 | 둘 다 뜨지 않는다(설정의 잘못을 기동에서 거부하는 지금의 시험 선례를 따른다) |
| 이미 색인된 문서 둘 가운데 하나의 파일이 상한을 넘게 된 뒤 동기화한다(목록에는 크기를 비워 내고 읽을 때 `too_large`를 내는 가짜 커넥터) | 그 문서가 검색에서 빠지고 `not_accepted`의 `too_large`에 세어진다. `failed`에는 세어지지 않는다. 다른 문서는 그대로다 |
| 문서가 하나뿐인 원천에서 그 파일이 상한을 넘게 된 뒤 동기화한다(같은 가짜 커넥터) | 기록이 `failed`와 `nothing_accepted`이고 문서는 검색에 그대로다 |
| 수정 시각과 크기를 그대로 둔 채 내용만 바꾼 파일을 보통 동기화하고, 이어서 "모두 다시 읽기"로 동기화한다 | 앞은 그대로다. 뒤는 `updated`가 1이다 |
| 임베딩 스텁이 실패하게 해 재시도를 다 쓴 문서를 둔 채 동기화한다 | 그 문서의 색인 작업이 다시 들어간다 |
| 동기화가 넣은 문서의 색인이 돌기 전에 그 파일을 바꾸거나 지우고 작업자를 한 번 돌린다 | 색인 상태가 `failed`와 `source_changed`다. 다음 동기화가 바뀐 내용으로 다시 넣거나 삭제 반영한다. 파일을 원래 내용으로 되돌려 놓았으면 다음 동기화가 색인 작업을 다시 넣는다 |

- [정함] 원천 삭제 작업과 원천 되살리기 작업이 지움 표시를 다시 보는 것은 작업을 대기열에 직접 넣어 시험한다. 관리 API는 그런 순서의 요청을 거절하므로 밖에서는 만들 수 없는 장면이다. 지움 표시가 걷힌 원천에 원천 삭제 작업을 돌리면 문서를 지우지 않고 끝나고, 지움 표시가 선 원천에 원천 되살리기 작업을 돌리면 문서를 되살리지 않고 끝난다. 원천 삭제 작업이 실패로 끝난 원천(지움 표시가 선 동안 색인 작업이 아무것도 쓰지 않고 끝난 문서가 남아 있다)을 되살리고 작업자를 돌리면 그 문서가 검색에 나온다.

- [정함] 서버 경로 커넥터는 실제 파일 시스템으로 따로 시험한다. 보는 것은 심볼릭 링크 넷(파일, 하위 폴더, 원천 폴더 자체, 부모 폴더에서 원천 폴더까지의 중간 토막), 한글 이름의 두 꼴(합쳐 적은 것과 풀어 적은 것), 상한을 넘는 파일, 읽을 수 없는 하위 폴더가 목록 전체를 `unreadable`로 실패시키는 것이다. 링크는 실제로 만든다. 저장소의 선례는 둘로 갈린다. `tests/test_ingest_command.py`를 비롯한 시험들은 링크를 실제로 만들고, `tests/tools/test_release.py`는 Windows에서 링크를 만들 권한이 없을 수 있다는 까닭으로 링크인지 묻는 호출만 바꿔 끼운다(둘 다 코드를 읽었다). 이 커넥터는 링크를 따라가지 않는 것이 실제 파일 시스템에서 판정되어야 하므로 앞의 선례를 따른다. 확인과 열기가 한 동작인지는 링크로 바꿔치는 경쟁으로 본다. 다른 스레드가 원천 폴더 안의 하위 폴더 하나를 진짜 폴더와 부모 폴더 밖을 가리키는 링크로 번갈아 바꾸는 동안 그 아래 파일을 되풀이해 읽고, 읽은 내용에 밖에 둔 파일의 내용이 한 번도 없는지 본다. 이 틈을 닫는 열기는 리눅스에만 있으므로 기대는 운영체제마다 적는다(아래 원칙 I의 항목). 리눅스에서는 밖의 내용이 한 번도 나오지 않아야 하고, 그 열기가 없는 운영체제에서는 커넥터가 확인한 뒤 여는 길로 돈다는 것을 단언한다. 읽기 오류는 권한 비트로 만들지 않고 폴더를 여는 호출이 오류를 내게 바꿔 끼운다. 권한 비트는 Windows 개발 기계에서 읽기를 막지 못하고, 시험을 root로 돌리는 환경(컨테이너 안)에서도 막지 못한다고 보기 때문이다(어림이고 재지 않았다. 앞서는 CI가 root로 돈다고 적었는데, CI의 파이썬 잡은 컨테이너 없이 ubuntu-24.04 러너에서 돈다. 명세 검토가 짚었고 워크플로를 읽었다).
- [정함] 일정 계산 어댑터의 시험은 다섯 칸 표현식의 다음 실행 시각(시간대 설정 기준), 칸 수가 다섯이 아닌 표현식의 거부, 값이 틀린 표현식과 오지 않는 날짜의 거부를 본다. 기대값은 프로브(`cron-expr/probe_out.txt`)의 표에서 옮긴다.
- [정함] 작업 대기열 어댑터의 시험은 셋을 본다. 색인 작업 여럿이 대기 중일 때 동기화 작업을 먼저 꺼내는 것, 같은 원천의 같은 종류 작업이 대기 중이거나 실행 중이면 둘째가 들어가지 않는 것, 정리 작업이 하나만 들어가는 것이다. 겹치면 넣지 않는 문장은 한 연결에서 스무 번 되풀이해 본다. 처음 몇 번만 통과하고 그 뒤에 실패하는 꼴을 프로브가 봤기 때문이다(Further Notes).
- [넘겨받음] 작업자를 여럿 띄워도 같은 일정이 한 번만 시작되는지는 명세가 시험으로 판정한다(ADR 0022 "시작시키는 쪽").
- [정함] 그 시험은 연결 여럿으로 일정 확인을 같은 시각에 동시에 돌려, 원천마다 동기화 작업이 하나만 들어갔는지 본다. 프로브 `schedule-once`의 A2를 시험으로 옮긴 것이다.
- [정함] 잠금 순서의 시험은 core 명세의 어댑터 시험 선례를 따른다(연결 둘로 한쪽 작업 단위를 열어 둔 채 다른 쪽을 돌린다). 원천을 지우는 요청과 그 원천으로 온 수집이 겹칠 때 어느 쪽이 먼저 커밋되든 지운 원천에 살아 있는 문서가 남지 않고, 서로를 기다리다 멈추지 않는다.
- [정함] 설치처가 만든 커넥터는 가짜 커넥터로 흉내 낸다. 인터페이스 버전의 major가 다르면 원천 만들기가 422이고 이미 있는 원천의 동기화가 `connector_unavailable`이다. 인터페이스에 없는 예외를 비밀번호처럼 보이는 글과 함께 내면 응답, 동기화 기록, 로그 어디에도 그 글이 없다(원칙 V). 같은 키를 두 번 내면 `connector_error`다.
- [정함] 돌아오지 않는 호출은 호출을 붙잡아 둘 수 있는 가짜 커넥터로 시험한다. 커넥터 호출의 한도를 짧게 준 작업자에서 열둘을 본다. `list()`가 돌아오지 않는 원천의 동기화가 한도를 넘겨 `source_unreadable`로 끝나고 다시 시도되지 않는 것, 끊긴 원천이 하나이고 자리가 남아 있을 때 그동안 다른 원천의 동기화와 색인 작업이 끝나는 것, `fetch`가 돌아오지 않는 문서의 색인 작업이 자리를 잡고 있지 않고 일시 실패로 다시 예약되는 것, 호출이 남아 있는 동안 같은 설정의 다음 동기화는 커넥터를 부르지 않고 끝나지만 설정을 고친 뒤의 동기화는 커넥터를 부르는 것, 같은 커넥터를 같은 설정으로 쓰는 다른 원천의 동기화도 커넥터를 부르지 않고 끝나는 것(기억의 단위가 원천이 아니다), 도는 중인 동기화가 다른 자리의 호출이 한도를 넘겨 그 설정이 막히면 남은 파일을 하나씩 실패로 세지 않고 `source_unreadable`로 끝나는 것, 막힌 설정이 자리 수보다 많아도 저마다 한 번씩 한도를 넘긴 뒤에는 멀쩡한 원천의 동기화와 색인 작업이 끝나는 것(상한이 없어도 작업자가 멈추지 않는다), 붙잡아 둔 호출을 풀어 준 뒤의 동기화가 성공하는 것, 한도 안에 끝나는 느린 호출을 기다리는 동안 작업 담당 기록의 기한이 지나지 않는 것(기한을 한도보다 짧게 주고 본다), 작업 담당 기록을 잃어 거두어진 시도의 호출이 한도 안에 돌아오면 다음 시도가 커넥터를 부르는 것, 한도를 넘겨 기다리기를 그만둔 호출이 남은 채 종료 신호를 받은 작업자가 스스로 내려가는 것, 그리고 끝없는 목록이다. 작업자가 내려가는 것은 작업자 프로세스를 실제로 띄워 보거나(`tests/test_worker_command.py`의 선례), 내려가기를 붙잡는 스레드(daemon이 아닌 스레드)가 남지 않았는지로 본다. 한도 안에서 기다리는 중인 호출은 진행 중인 작업이라 작업자가 그 작업이 끝나기를 기다리므로, 한도를 넘기기 전의 호출로 보면 이 장면을 재지 못한다(명세 검토가 냈다). 끝없는 목록은 항목 사이에 기다리는 일 없이 항목을 끝없이 내는 가짜 커넥터의 동기화가 원천을 지운 뒤 기한을 늘리는 때에 `source_deleted`로 끝나는지와(기한을 짧게 주고 본다. 항목 사이에 기다리는 가짜 커넥터로 보면 받는 꼴이 어떻든 이벤트 루프가 돌아 이 시험이 초록이 된다), 한도 안에서 파일 하나를 읽는 중에 원천을 지워도 같은지를 본다. 연결 확인은 둘을 본다. 한도를 넘겨 답한 뒤의 요청이 기다리지 않고 답하는지와, 설정을 고친 뒤의 요청이 커넥터를 부르는지다. 폴더 확인은 서버 경로 커넥터가 폴더를 여는 호출을 붙잡아 두게 바꿔 끼워 일곱을 본다(10초 상수는 시험이 짧은 값으로 바꿔 끼운다). 새 폴더의 확인이 돌아오지 않는 만드는 요청과 고치는 요청이 422와 `unreadable`을 받고 원천이 만들어지거나 고쳐지지 않는 것, 폴더를 여는 호출이 권한 오류를 내는 폴더도 같은 응답인 것, 그 요청이 끝난 뒤 다른 원천을 만드는 요청이 기다리지 않고 지나는 것(잠금이 풀렸다), 붙잡아 둔 확인을 뒤늦게 풀어 줘도 원천이 만들어지거나 설정이 고쳐지지 않는 것, 같은 폴더로 다시 온 요청이 기다리지 않고 같은 422를 받는 것, 다른 원천의 폴더가 답하지 않을 때 요청이 한도 안에 끝나고 그 원천과 글자로 겹치는 폴더는 409이며 겹치지 않는 폴더는 만들어지는 것, 지운 원천을 되살리는 요청이 그 원천의 폴더를 여는 호출이 돌아오지 않아도 한도 안에 받아들여지는 것이다(원천 삭제와 되살리기 절. 셀프 리뷰가 이 장면이 빠졌다고 냈다). 한도를 넘길 때의 로그 한 줄에 문서의 키와 커넥터 설정이 없다는 것도 본다. 서버 경로 커넥터가 기본 스레드 풀을 쓰지 않는 것과 호출 하나에 스레드를 하나만 쓰는 것은 그 커넥터의 시험이 본다. 설치처가 만든 커넥터가 이벤트 루프를 막는 경우는 시험하지 않는다. 이 장치가 풀지 못하는 경우로 적어 둔 것이다(동기화의 차례 절).
- [정함] 마이그레이션의 시험은 옛 스키마에 암호 실패로 남은 문서와 조각이 0개인 문서를 만들어 두고 올린 뒤, 둘이 건너뜀으로 옮겨졌는지 본다.
- [정함] 단독 compose 시험에는 장면 하나를 더한다. 설치 폴더의 `sources/` 아래에 폴더와 파일을 두고 띄운 뒤 원천을 만들어 지금 동기화하면 그 문서가 검색에 나오고, 서버와 작업자 컨테이너가 `/sources`에 쓰지 못한다. 지금의 단독 compose 시험과 같은 조건에서 돈다.
- [정함] 검색 도구의 형식은 바뀌지 않으므로 MCP 클라이언트로 접속하는 지금의 계약 시험이 그대로 초록이어야 한다(원칙 VII). 커넥터 인터페이스의 버전은 `rag-engine --version` 출력의 시험이 본다.
- [정함] 자동 시험에 두지 않는 것은 셋이다. 전파 설정과, 컨테이너가 뜬 뒤에 붙인 폴더의 동작은 프로브로만 쟀다(특권 컨테이너가 있어야 한다. 실제 NFS·SMB 공유 폴더로는 프로브도 재지 않았다). 끊긴 실제 공유 폴더에서 읽기 호출과 신호와 컨테이너가 어떻게 되는지도 프로브 `stuck-mount`로만 쟀다(특권 컨테이너와 커널 모듈이 있어야 하고, 한 번에 20분쯤 걸리며, SMB 칸들을 함께 돌린 첫 실행에서 커널이 17분쯤 헛돌아 가상 기계의 Docker 명령 일부가 돌아오지 않은 일이 있다). 큰 폴더의 동기화 시간 같은 성능도 시험하지 않는다.
- [넘겨받음] 환경이 없어 건너뛴 시험은 초록이 아니다(원칙 I). 플랫폼에 따라 결과가 갈리는 장면은 건너뛰지 않고 플랫폼마다의 기대를 단언한다(core 명세 Testing Decisions의 선례).

## Out of Scope

- **admin(관리자 페이지)이 받는 것.** 가져오는 원천의 그룹을 만든 뒤에 고치는 길(그룹과 지식베이스의 관리 API와 함께 정한다), 부모 폴더 아래의 폴더 목록을 보여 주어 폴더를 고르게 하는 화면과 그 API, 실패하거나 건너뛴 문서 하나를 골라 다시 시도시키는 API, cron 표현식을 사람이 읽는 말로 보여 주고 고르게 하는 화면, 파일을 올리는 화면(수집 API에 `source=upload`를 적어 보낸다), 수집 전용 토큰(ADR 0021 "이번에 짓지 않는 것"), 도는 동기화를 원천과 문서를 건드리지 않고 취소하는 요청(ADR 0023 "이번에 짓지 않는 것". 지금 끝나지 않는 동기화를 멈추는 길은 원천을 지우는 것이다).
- **db-source(SQL 원천)가 받는 것.** 변환 인터페이스, 연결 정보의 암호화 보관(ADR 0021), 칼럼에서 제목과 갱신일 밖의 메타데이터를 가져오는 매핑, 확장자가 없는 키와 파일이 아닌 본문 글을 문서로 받는 길(수집 정책 절의 형식 규칙), 커넥터를 만드는 사람을 위한 안내(설치처가 만든 커넥터를 이미지에 넣는 절차를 포함한다. 둘째 커넥터를 지으며 쓴다. 목록에는 끝이 있어야 한다는 것과, 읽기를 스레드로 넘기지 않고 비동기 함수 안에서 막히면 서버가 건 한도가 지켜지지 않는다는 것을 적는다), 동기화 한 번이 받는 목록 전체의 상한(항목 수나 전체 시간. 끝없는 목록을 받는 동안 쌓이는 메모리에 상한이 없다는 것을 함께 넘긴다. 동기화의 차례 절), 커넥터를 따로 띄운 프로세스에서 부르고 한도를 넘기면 그 프로세스를 끝내는 방식(둘 다 ADR 0023 "이번에 짓지 않는 것").
- **diag-bundle(진단 묶음)이 받는 것.** 원천의 설정(`config`)을 진단 묶음에 싣지 않는 것. 서버는 그 안의 비밀을 가려낼 수 없다. "원천 폴더 없음"의 진단은 이 명세의 연결 확인이 내는 코드를 쓴다.
- **backup-upgrade(백업과 업그레이드)가 받는 것.** 가져오는 원천의 원본은 파일 저장소에 없어 백업에 들지 않는다는 것, 백업을 되돌린 뒤 원천마다 동기화를 한 번 돌리는 절차, 원천의 설정(`config`)이 데이터베이스에 가리지 않은 채 들어 있어 백업에도 그대로 실린다는 것(설정에 비밀을 넣지 않는다는 약속을 어긴 커넥터를 쓰는 설치에서는 백업에 그 값이 든다).
- **이번에 두지 않는 것.** 원천마다의 실행 시간대와 동시 처리 수(ADR 0022), 원천 이름 바꾸기, 파일이 바뀌는 순간을 알아채 바로 동기화하는 감시(일정과 "지금 동기화"로만 돈다), PDF·DOCX·HWPX 밖의 형식, 가져오는 원천의 원본을 파일 저장소에 복사해 두는 선택지, 끝난 작업 행을 기간으로 지우는 일(작업 표는 지금처럼 계속 쌓이고, 크기가 문제가 되면 그때 정한다. 다만 정리 작업이 원천을 완전히 지울 때는 그 원천과 그 원천의 문서를 가리키는 작업 행을 함께 지운다).

## Further Notes

- 프로브의 측정은 모두 개발 PC에서 한 것이고 배포판 리눅스 서버에서 한 것이 아니다. `cron-expr`는 그 PC의 Python 3.12.10에서 바로 돌렸고, 명세를 쓴 세션의 나머지 셋은 Windows Docker Desktop(WSL2 커널)에 띄운 컨테이너를 상대로 돌렸다. 막힌 호출의 설계 세션이 더한 `stuck-calls`는 그 PC의 Python 3.12.10과, 같은 Docker Desktop에 띄운 제품 작업자 이미지(Python 3.12.16)에서 세 번씩 돌렸고, 커밋한 출력은 마지막 회차의 것이다(앞선 두 회차의 출력은 덮어써 남아 있지 않다. 프로브 안내가 그 회차들에서 세션이 본 값을 적는다). 티켓을 나눈 세션이 명세 검토의 물음 둘로 더한 `endless-list`(끝없는 목록을 받는 꼴)는 그 PC의 Python 3.12.10과 제품 작업자 이미지에서, `fifo-open`(이름 있는 파이프를 여는 호출)은 제품 작업자 이미지에서만 한 번씩 돌렸다. 시간은 그 기계의 값이고 디스크와 CPU에 따라 달라진다. 실행 명령과 버전은 `.scratch/source-sync/probes/README.md`에 있다.
- 되살리기가 삭제보다 오래 걸리는 까닭은 조각 표의 색인들로 보이고, 그 가운데 벡터 색인(HNSW)의 몫이 크리라는 것은 어림이다. 프로브에서 조각 10만 개를 삭제 보관함으로 복사하는 데 11.50초, 조각 표로 되돌리는 데 751.45초가 걸렸다(`source-delete/probe_out.txt`의 A, C). 프로브의 삭제 보관함에는 기본 키와 문서를 가리키는 색인만 있었고, 조각 표에는 그 둘에 더해 유일 제약의 색인과 벡터 색인과 키워드 색인(GIN)이 있어서 넣는 행마다 그 색인들에 함께 들어갔다(프로브의 스크립트를 읽었다). 어느 색인이 시간을 쓰는지 가르는 대조(색인을 하나씩 빼고 재기)는 하지 않았다. 조각을 다 채운 표에 벡터 색인을 한꺼번에 짓는 데는 78.1초가 걸렸다(같은 출력의 준비). 그래서 문서가 1만 건쯤인 원천을 되살리면 모든 문서가 검색에 돌아오기까지 10분 넘게 걸릴 수 있고, 그동안 응답의 작업 식별자로 진행을 본다.
- 그 프로브가 보지 못한 것은 지식베이스 행의 잠금과 전환 검사, 대기 중인 색인 작업을 지우는 일, 검색과 색인이 함께 도는 부하다(프로브의 머리 설명). 묶음의 크기(문서 50건)는 이 측정에서 고른 값이고 설정으로 열지 않았다. 정리 작업의 묶음은 같은 값을 그대로 쓴 것이고 따로 재지 않았다.
- 부분 유일 색인에 걸리면 넣지 않는 문장(`ON CONFLICT`)은 색인의 조건을 문장에 값으로 박아 적어야 한다. 프로브에서 그 조건의 값을 바깥에서 넘기는 꼴(바인드 값)로 적은 문장은 같은 연결에서 11번째 실행에 `InvalidColumnReference`(42P10)로 실패했고, 값을 문장에 적은 꼴은 20번 모두 통과했다(`schedule-once/probe_out.txt`의 D3). 프로브는 psycopg 3.3.8로 문장을 직접 보냈다. 제품도 psycopg 3을 쓰지만 SQLAlchemy가 문장을 만들고, 그 문장으로는 재지 않았다. 몇 번만 돌려 보는 시험은 이 실패를 잡지 못한다. SQLAlchemy 2.1.8의 PostgreSQL 방언은 `ON CONFLICT`의 색인 조건(`index_where`)을 다른 조건처럼 처리해 그 안의 값을 바인드 값으로 넘긴다(명세 검토가 먼저 읽었고, 티켓을 나눈 세션이 이 저장소의 가상 환경에 깔린 그 버전의 소스를 읽었다). 그래서 작업 대기열 절이 그 조건을 문장의 글자로 적게 정했다.
- 원천의 설정에 비밀 값을 넣지 않는 것은 인터페이스의 설명이 정한 약속일 뿐이고 서버가 막지 못한다. 설치처가 만든 커넥터가 설정에 토큰을 받게 지어지면 관리 API의 원천 보기에 그 값이 그대로 보인다.
- 변경 확인값은 수정 시각과 크기라서, 둘이 모두 그대로인 채 내용만 바뀐 파일은 동기화가 알아채지 못한다(수정 시각을 되돌려 놓는 복사 도구가 그런 파일을 만든다). 그런 파일은 "모두 다시 읽기"로 돌린 동기화가 잡는다.
- 연결 확인은 서버 컨테이너에서 돌고 동기화는 작업자 컨테이너에서 돈다. 공유 폴더를 붙인 뒤 한쪽 컨테이너만 다시 띄우면 연결 확인은 성공하는데 동기화는 `source_unreadable`로 실패할 수 있다.
- 이 명세가 ADR 본문을 바꾼 곳은 넷이고 이력과 포인터를 달았다. ADR 0007(포트 열에 새 포트 셋이 든다), ADR 0012("모두 다시 읽기"로 돌린 동기화는 변경 확인값이 같아도 받는다), ADR 0013(검색이 원천의 지움 표시를 보는 자리가 생긴다), ADR 0021(전파 설정을 재고도 compose에 넣지 않는다)이다. ADR 0022에는 이력을 더하지 않았다. 그 ADR은 "모두 다시 읽기"를 둘지를 명세에 넘겼다. 그리고 그 ADR이 색인 작업보다 먼저 꺼낸다고 적은 둘(동기화 작업, 정리 작업)에 이 명세가 원천 삭제 작업과 원천 되살리기 작업을 더한 것은, 본문의 문장을 거짓으로 만들지 않고 더하는 것이다.
- 돌아오지 않는 호출의 규칙이 딛고 선 사실은 잰 것과 읽은 것으로 갈린다. 잰 것은 프로브 `stuck-calls`의 출력에 있다. 한도를 걸어도 읽던 스레드가 남는다는 것, 돌고 있는 일은 취소되지 않는다는 것, 밖에서 스레드에 예외를 넣어도 읽기에 막힌 스레드는 끝나지 않는다는 것(파이썬 코드를 도는 스레드는 끝났다), 표준 라이브러리의 스레드 풀과 이벤트 루프의 기본 풀에 막힌 스레드가 있으면 프로세스가 할 일을 마친 뒤 8초 안에 스스로 내려가지 못하고(프로브가 8초에 죽였다) daemon 스레드만 있으면 내려간다는 것, 막힌 스레드 하나가 쥐는 메모리, 이벤트 루프를 막는 호출에는 한도가 통하지 않는다는 것이다(동기화의 차례 절이 항목마다 출력의 자리를 적는다). 앞서는 취소와 종료 때의 기다림을 표준 라이브러리 소스를 읽은 것으로 적었다. 이 프로브는 빈 파이프를 읽는 것으로 막힘을 흉내 냈다. 읽은 것은 셋이다. 스레드를 밖에서 없애거나 멈출 수 없다는 것은 조사 서브에이전트가 파이썬 threading 문서의 원문을 받아 본 것이다. 기본 스레드 풀의 상한은 개발 PC에 깔린 Python 3.12.10의 표준 라이브러리 소스를 읽은 것이다(`asyncio/threads.py`, `asyncio/base_events.py`, `concurrent/futures/thread.py`). 끊긴 공유 폴더에서 읽기가 붙인 방식에 따라 오류로 돌아오기도 하고 끝없이 기다리기도 한다는 것은, 조사 서브에이전트가 리눅스 매뉴얼(nfs(5), mount.cifs(8))과 커널 소스의 원문을 받아 본 것이다. NFS는 기본이 hard라 요청을 끝없이 다시 보내고, SMB는 기본이 soft라 오류를 돌려준다. 이 사실은 뒤에 프로브 `stuck-mount`가 실제 공유 폴더로 재 맞았다(아래 항목). 주소와 파일 이름은 설계 일지(`docs/journal/2026-11-21-2139-source-sync-stuck-calls-design.md`)의 "확인한 것"에 있다. 돌아오지 않는 호출을 커넥터의 이름과 설정으로 기억하는 규칙은 어느 쪽이든 서도록 정한 것이다. 커넥터 호출의 한도 기본값(600초)과, 연결 확인과 폴더 확인이 기다리는 10초는 재지 않고 정한 값이다.
- 끊긴 실제 공유 폴더에서의 동작은 프로브 `stuck-mount`가 쟀다(실측 서브에이전트가 돌렸다). Docker Desktop(엔진 29.9.2, WSL2 커널 6.18.58.1) 안의 특권 Docker-in-Docker 컨테이너를 서버 기계로 삼아 SMB 3.1.1(리눅스의 `cifs`로 붙였다)과 NFS v4.2 공유 폴더를 붙이고, 제품 작업자 이미지로 띄운 컨테이너에 넘긴 뒤 파일 서버를 얼리거나 네트워크에서 떼거나 죽였다. 파일 서버도 같은 가상 기계에 띄운 컨테이너였고, NFS 서버는 같은 커널의 nfsd였다. 붙이는 방식과 끊는 법을 짝지은 칸은 열하나다. 출력은 넷이고, 첫 실행의 CIFS 칸은 끊고 190초쯤부터 아래의 커널 헛돎 속에서 잰 값이라 CIFS는 헛돌지 않은 재실행 둘로 판정했다(`stuck-mount/probe.sh`의 머리 설명. `hard`로 붙인 CIFS의 떼기와 죽이기 두 칸은 다시 돌지 않아 첫 실행의 값만 있다). 매뉴얼을 읽은 사실은 맞았다. NFS hard와 CIFS hard는 다시 잇기 전까지 돌아오지 않았고, NFS soft는 180초쯤 뒤 EIO로, CIFS soft는 끊는 법에 따라 10~264초 뒤 EHOSTDOWN으로 돌아왔다(헛돈 첫 실행에서는 285초가 걸린 호출이 있었다. 늦게 부른 호출과 미리 열어 둔 파일은 더 걸리거나 다시 이을 때까지 돌아오지 않았다). 다시 이으면 막혀 있던 호출은 4.2초 안에 돌아왔다(CIFS hard의 떼기와 죽이기 칸은 재지 못했다). 읽기에 막힌 프로세스는 대개 SIGKILL을 받고 0.03초 안에 끝났다. 제품이 쓰려는 모양(daemon 스레드만 막힌 프로세스)은 주 스레드가 끝난 지 0.02~0.06초 뒤 사라졌고, 그 모양의 컨테이너는 끊고 10초에 멈추면 `docker stop`이 0.2~1.2초에 끝났다. 맞지 않은 경우는 SMB에서만 셋이 났다. 같은 폴더를 다른 프로세스가 먼저 보던 중에 나중에 본 프로세스는 SIGKILL을 받고도 곧바로 끝나지 않았고(5~6초 뒤에 끝나거나 8초 안에 끝나지 않았다), 두 프로세스가 다른 컨테이너에 있으면 나중 쪽 컨테이너의 `docker stop`이 24초 뒤 실패했다. 서버가 응답만 멈춘 지 200초쯤 뒤에는 SIGKILL도 8초 안에 통하지 않았고, 그때 멈춘 컨테이너도 `docker stop`이 같은 오류로 실패했다. SMB 여섯 칸을 함께 끊어 둔 첫 실행에서는 커널이 17분쯤 헛돌았다. `hard`로 붙인 두 칸 가운데 하나가 일으킨 것으로 보지만 근거는 시각이 맞아떨어진 것 하나이고, 이것은 프로브의 출력이 아니라 손으로 친 명령의 기록이다(`stuck-mount/lockup_seen.txt`). 이 결과로 정한 것은 단독 compose와 설치 안내 절의 두 `[사용자 선택]` 항목이고, ADR 0023의 결정은 바뀌지 않았다. 자식 프로세스 방식을 다시 볼 db-source에는 SMB에서 SIGKILL이 늘 통하지는 않는다는 것을 함께 넘겼다. 칸마다의 수는 설계 일지의 "확인한 것"(실제 공유 폴더 절)에 있다.
- 앞서 이 명세가 정하지 않고 적어 둔 것 셋은 2026-11-21의 막힌 호출 설계 인터뷰가 정했다(ADR 0023. 일지 `docs/journal/2026-11-21-2139-source-sync-stuck-calls-design.md`). 셋 모두 끊긴 공유 폴더와 끝나지 않는 커넥터 호출의 처리이고 PR 봇 리뷰가 냈던 것이다. 동기화의 차례 절의 돌아오지 않는 호출의 규칙도 그 인터뷰가 함께 다시 봤다(그 절의 첫 `[사용자 선택]` 항목).
  - 폴더를 정하는 요청이 멈출 때. 서버 경로 커넥터와 원천 폴더 절의 폴더 확인 한도 항목이 정했다. 기다리는 한도(10초), 거절하는 응답(422와 `unreadable`), 한도를 넘긴 요청이 잠금을 푸는 것, 늦게 돌아온 확인이 아무것도 쓰지 못하는 것, 답하지 않는 다른 원천과는 저장해 둔 경로의 글자로 견주는 것, 원천이 아직 없는 만드는 요청의 막힌 확인을 커넥터의 이름과 설정으로 묶는 것이다.
  - 프로세스 전체의 상한. 두지 않는다. 원천마다의 상한도 함께 걷었다(동기화의 차례 절의 상한 항목).
  - 목록 전체가 끝나는 조건. 두지 않는다. 그 대신 동기화가 작업 담당 기록의 기한을 늘릴 때마다 원천의 지움 표시를 봐서, 운영자가 원천을 지우면 멈춘다(동기화의 차례 절의 끝없는 목록 항목).
  - 이번에 짓지 않고 넘긴 것은 넷이다. 셋은 db-source가 받는다. 목록 전체의 상한, 커넥터를 따로 띄운 프로세스에서 부르고 한도를 넘기면 그 프로세스를 끝내는 방식(비동기로 읽는 커넥터의 호출을 한도에서 취소할지도 그때 함께 정한다), 커넥터를 만드는 사람을 위한 안내에 적을 것 둘(목록에는 끝이 있어야 한다는 것, 비동기 함수 안에서 막히면 한도가 지켜지지 않는다는 것)이다. 하나는 admin이 받는다. 도는 동기화를 취소하는 요청이다(Out of Scope. 두 기능의 계획 `.scratch/db-source/plan.md`와 `.scratch/admin/plan.md`에 받는 쪽의 말로 적었다).
