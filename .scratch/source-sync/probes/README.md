# source-sync 프로브

source-sync 명세 세션(2026-11-21)에서 명세(`.scratch/source-sync/spec.md`)의 근거로 쓰려고 돌린 스크립트와 그 출력이다. ADR 0021과 0022가 "명세가 재거나 정하는 것"으로 넘긴 물음 가운데 재서 가를 수 있는 것을 쟀다. 실행 명령은 각 스크립트의 머리 설명에 있다. 측정은 모두 개발 PC에서 했고 배포판 리눅스 서버에서 한 것이 아니다. `cron-expr`는 그 PC의 Python에서 바로 돌렸고, 그 세션의 나머지 셋(`schedule-once`, `source-delete`, `mount-propagation`)은 Windows Docker Desktop(엔진 29.9.2, WSL2 커널 6.18.58.1)에 띄운 컨테이너를 상대로 돌렸다. 표의 끝 두 줄(`stuck-calls`, `stuck-mount`)은 같은 날 뒤이어 연 막힌 호출의 설계 세션이 ADR 0023과 명세 "동기화의 차례"의 근거로 돌린 것이다. `stuck-calls`는 그 PC의 Python과, 같은 Docker Desktop에 띄운 제품 작업자 이미지에서 돌렸다. `stuck-mount`는 실측 서브에이전트가 같은 Docker Desktop에서 돌렸다. **주의:** `stuck-mount`의 첫 실행 중에 커널의 작업 스레드 하나가 CPU 하나를 쥐고 17분 넘게 헛돌아, 그동안 Docker Desktop 가상 기계에서 Docker의 명령 일부(`start`, `network connect`, `unpause`, `inspect`)와 공유 폴더 떼기가 돌아오지 않았다(그 줄의 설명과 `probe.sh` 머리 설명의 "주의"). 다시 돌릴 때는 다른 일을 그 가상 기계에 올려 두지 않는다.

| `mount-propagation/probe.sh`, `inner.sh`, `inner_compose.sh` | 컨테이너가 뜬 뒤에 서버 기계에서 붙인 공유 폴더가 컨테이너에 보이는지. 기본 전파 설정과 `rslave`(`docker run`과 compose의 긴 문법)에서 나중에 붙인 하위 폴더가 보이는지, 서버 기계의 루트가 shared가 아닐 때 `rslave`로 뜨는지, 읽기 전용으로 붙였을 때 나중에 전해진 폴더에 쓰기가 되는지, 붙인 뒤에 새로 띄운 컨테이너와 `docker restart`로 다시 띄운 컨테이너가 보는지, 떼었다 다시 붙였을 때 따라가는지, 부모 폴더 자체가 나중에 붙은 경우, Docker Desktop에서 `rslave`를 적으면 오류가 나는지, 단독 compose가 붙일 모양(짧은 문법, `.env`의 변수, 서버와 작업자 두 서비스, uid 10001)에서 `docker compose restart server worker`로 다시 띄운 컨테이너가 보는지, 설치 폴더에 `sources/`가 없고 변수도 적지 않았을 때 컨테이너가 뜨는지와 만들어진 폴더의 주인. 공유 폴더는 tmpfs로 흉내 냈다. 출력 `probe_out.txt` | 명세 "단독 compose와 설치 안내"(전파 설정을 compose에 넣지 않는 까닭, 설치 안내의 "다시 띄운다", 볼륨을 더하는 변경에 올릴 때 운영자가 손댈 것이 없다는 것), ADR 0021 "서버 경로 원천의 폴더"와 그 이력 2026-11-21 | Docker Desktop(특권 컨테이너를 띄울 수 있어야 한다), 이미지 `docker:29.9.2-dind`와 `alpine:3.22`, Git Bash | Docker 엔진 29.9.2(바깥과 안쪽 모두), compose 5.6.1, 커널 6.18.58.1-microsoft-standard-WSL2 |
