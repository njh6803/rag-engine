# source-sync 프로브

source-sync 명세 세션(2026-11-21)에서 명세(`.scratch/source-sync/spec.md`)의 근거로 쓰려고 돌린 스크립트와 그 출력이다. ADR 0021과 0022가 "명세가 재거나 정하는 것"으로 넘긴 물음 가운데 재서 가를 수 있는 것을 쟀다. 실행 명령은 각 스크립트의 머리 설명에 있다. 측정은 모두 개발 PC에서 했고 배포판 리눅스 서버에서 한 것이 아니다. `cron-expr`는 그 PC의 Python에서 바로 돌렸고, 나머지 셋은 Windows Docker Desktop(엔진 29.9.2, WSL2 커널 6.18.58.1)에 띄운 컨테이너를 상대로 돌렸다.

| 프로브 | 무엇을 재는지 | 어디가 근거로 드는지 | 다시 돌 때 필요한 것 | 잰 버전 |
|---|---|---|---|---|
| `cron-expr/probe.py` | 일정을 계산하는 라이브러리 cronsim이 표현식을 어떻게 읽는지. 설치된 버전과 타입 정보(`py.typed`)와 기대는 패키지, 다섯 칸 표현식 셋의 다음 실행 시각(한국 시간과 UTC), 칸 수가 다섯이 아닌 표현식(여섯 칸, 일곱 칸, 네 칸, 빈 글, `@daily`)을 받는지, 값이 틀린 표현식과 오지 않는 날짜(2월 31일)의 예외, 요일을 적는 여러 꼴, 시간대 없는 시각과 서머타임. 명세의 규칙(칸이 다섯일 때만 넘긴다)을 쓴 함수 `next_run`까지 실행과 타입 검사(pyright strict)를 지난다. 출력 `probe_out.txt`, `pyright_out.json` | 명세 "일정과 일정 확인"(여섯 칸 표현식의 거부, 틀린 표현식의 응답, 시간대), ADR 0022 "계산하는 라이브러리" | `uv run --with cronsim==2.8 --with tzdata`(Windows에는 시간대 자료가 없어 `tzdata`를 얹는다). 타입 검사는 exclude를 비운 임시 pyrightconfig. 네트워크는 패키지를 받을 때만 쓴다 | cronsim 2.8, Python 3.12.10, pyright 1.1.414 |
| `schedule-once/probe.py` | 작업자 여럿이 같은 순간에 일정을 확인할 때 동기화 작업이 원천마다 한 번만 들어가는지. 원천 행 잠금(`FOR UPDATE SKIP LOCKED`. 원천 하나마다 커밋하는 모양 A와, 시각이 지난 원천을 트랜잭션 하나에서 모두 잡는 명세의 모양 A2), 잠금 없는 대조, 조건부 `UPDATE`를 연결 여덟, 원천 40개, 25회차로 돈다. 동기화 기록을 만드는 일과 겹침 판정은 넣지 않았다. 원천마다 종류마다 대기·실행 중 작업을 하나로 묶는 부분 유일 색인(동시에 넣기 50회차, 앞 작업이 실행 중일 때와 끝난 뒤, `ON CONFLICT` 술어를 리터럴과 바인드 값으로 적은 문장을 스무 번씩), 문서도 원천도 가리키지 않는 작업 둘이 유일 색인에 걸리는지와 `NULLS NOT DISTINCT`, 색인 작업 10만 건이 대기 중일 때 작업을 꺼내는 질의 셋의 시간. 출력 `probe_out.txt` | 명세 "일정과 일정 확인"(한 번만 시작), "동기화의 차례"(겹침 방지의 구조), "작업 대기열"(작업 종류와 꺼내는 순서) | Docker의 `pgvector/pgvector:0.8.7-pg18-trixie` 컨테이너(머리 설명의 `docker run`), `uv run --with "psycopg[binary]==3.3.8"` | PostgreSQL 18.6, psycopg 3.3.8 |
| `source-delete/probe.py` | 원천 하나를 지우고 되살릴 때 그 원천의 문서와 조각을 옮기는 데 걸리는 시간. 문서 1만 건과 조각 10만 개(1024차원 벡터, HNSW와 GIN 색인)를 한 트랜잭션에서 삭제 보관함으로 옮기고 되돌리는 시간과 문장마다의 시간, 그 트랜잭션이 열린 동안 다른 연결의 읽기·쓰기·문서 행 잠금이 막히는지, 문서 500건씩과 50건씩 묶어 묶음마다 커밋했을 때의 전체 시간과 묶음 하나의 시간. 표는 core의 스키마에서 이 측정에 닿는 칸만 옮겼다. 출력 `probe_out.txt`(묶음 500건), `probe_out_batch50.txt`(묶음 50건) | 명세 "원천 삭제와 되살리기"(지움 표시를 먼저 세우고 조각은 작업자가 묶음으로 옮기는 까닭, 묶음의 크기), Further Notes(되살리기가 삭제보다 오래 걸리는 까닭), ADR 0013 이력 2026-11-21 | `schedule-once/probe.py`와 같은 컨테이너와 `uv run --with "psycopg[binary]==3.3.8"`. 인자는 주소, 문서 수, 문서마다의 조각 수, 묶음의 문서 수(커밋한 출력은 `10000 10 500`과 `10000 10 50`). 그 크기로 한 번에 30분쯤 걸린다 | PostgreSQL 18.6, pgvector 0.8.7, psycopg 3.3.8 |
| `mount-propagation/probe.sh`, `inner.sh`, `inner_compose.sh` | 컨테이너가 뜬 뒤에 서버 기계에서 붙인 공유 폴더가 컨테이너에 보이는지. 기본 전파 설정과 `rslave`(`docker run`과 compose의 긴 문법)에서 나중에 붙인 하위 폴더가 보이는지, 서버 기계의 루트가 shared가 아닐 때 `rslave`로 뜨는지, 읽기 전용으로 붙였을 때 나중에 전해진 폴더에 쓰기가 되는지, 붙인 뒤에 새로 띄운 컨테이너와 `docker restart`로 다시 띄운 컨테이너가 보는지, 떼었다 다시 붙였을 때 따라가는지, 부모 폴더 자체가 나중에 붙은 경우, Docker Desktop에서 `rslave`를 적으면 오류가 나는지, 단독 compose가 붙일 모양(짧은 문법, `.env`의 변수, 서버와 작업자 두 서비스, uid 10001)에서 `docker compose restart server worker`로 다시 띄운 컨테이너가 보는지, 설치 폴더에 `sources/`가 없고 변수도 적지 않았을 때 컨테이너가 뜨는지와 만들어진 폴더의 주인. 공유 폴더는 tmpfs로 흉내 냈다. 출력 `probe_out.txt` | 명세 "단독 compose와 설치 안내"(전파 설정을 compose에 넣지 않는 까닭, 설치 안내의 "다시 띄운다", 볼륨을 더하는 변경에 올릴 때 운영자가 손댈 것이 없다는 것), ADR 0021 "서버 경로 원천의 폴더"와 그 이력 2026-11-21 | Docker Desktop(특권 컨테이너를 띄울 수 있어야 한다), 이미지 `docker:29.9.2-dind`와 `alpine:3.22`, Git Bash | Docker 엔진 29.9.2(바깥과 안쪽 모두), compose 5.6.1, 커널 6.18.58.1-microsoft-standard-WSL2 |
