# 08: 지움 반영과 빈 목록 보호

**What to build:** 폴더에서 지운 파일과 수집 정책에 걸리게 된 파일의 문서가 다음 동기화 뒤 검색에서 빠진다. 같은 동기화가 넣은 문서의 색인이 끝나기를 기다리지 않는다. 공유 폴더가 붙지 않아 폴더가 비었거나 사라졌거나 문서가 될 파일이 하나도 보이지 않을 때는 동기화가 아무것도 지우지 않고 실패로 남는다. 운영자가 정말로 폴더를 비웠거나 모든 파일을 수집 정책으로 뺐으면 "빈 목록도 반영"을 켜서 동기화한다(스토리 17, 19, 20, 29의 제외).

**Blocked by:** 07 (지금 동기화로 새 파일과 바뀐 파일 넣기)

**Status:** done

- [x] 삭제 반영은 넣기가 끝난 뒤에 한다(명세 "동기화의 차례"의 삭제 반영 항목). 그 원천의 지워지지 않은 문서 가운데 후보에 키가 없는 것을 문서마다 작업 단위 하나에서 core 명세의 삭제 절차대로 임시 삭제하고 `deleted`로 센다. 이번에 읽지 못해 실패로 센 파일은 후보에 있으므로 지우지 않고, 읽다가 `too_large`가 나온 파일은 후보에서 빠졌으므로 그 키의 문서를 지운다. 수집 정책에 걸린 파일의 문서도 목록에 없는 문서와 똑같이 지운다(명세 "수집 정책"의 마지막 항목). 동기화는 넣은 문서의 색인이 끝나기를 기다리지 않고 동기화 작업이 끝날 때 끝난다.
- [x] 빈 목록 판정을 두 자리에서 한다(명세 "동기화의 차례", 사용자 선택). 후보를 만든 직후와 삭제 반영을 시작하기 직전이다(구현은 뒤의 한 자리만 둔다. 후보가 0건이면 앞의 자리에서 읽을 파일이 없어 두 자리의 결과가 같기 때문이고, 뒤의 자리가 읽다가 후보에서 빠진 경우까지 잡는다. 명세 문구를 어떻게 할지는 일지 "다음"의 to-spec 물음이다). 후보가 0건이고 그 원천에 지워지지 않은 문서가 하나라도 있으면 삭제를 반영하지 않고 실패로 끝낸다. 커넥터가 낸 항목이 0건이면 `source_unreadable`, 항목은 있는데 모두 수집 정책에 걸렸으면 `nothing_accepted`다. 원천과 함께 지워졌다는 표시가 남은 문서도 이 판정에서는 있는 문서로 센다(그런 문서는 12가 원천을 되살린 뒤에 생기고, 이 규칙의 시험도 12가 둔다). 목록을 받지 못한 실패에서는 `listed`가 비고, 받았는데 0건이면 0이다.
- [x] "빈 목록도 반영"(`apply_empty`)은 폴더가 있고 목록을 끝까지 받았는데 후보가 0건일 때만 통한다. 켜고 돌린 동기화는 두 자리를 모두 지나 삭제를 반영하고 성공으로 끝난다. 폴더가 없거나 읽지 못하면 켜도 실패한다. 일정이 시작한 동기화에는 이 옵션이 없다(명세 "동기화의 차례", "관리 API"의 지금 동기화 본문 항목).
- [x] 작업 행의 오류 코드 칸에 쓰이는 값에 `nothing_accepted`를 더하고, 코드 수를 적은 머리 설명과 주석을 고친다(명세 "오류 코드").
- [x] 시험(주 이음매, 명세 "Testing Decisions"의 장면 표): 파일 하나를 지우고 임베딩 스텁이 답하지 않게 둔 채 동기화하면 그 문서가 검색에서 빠지고, 같은 동기화가 넣은 문서의 색인이 끝나지 않아도 빠진다. 원천 폴더를 없애거나 비운 뒤 동기화하면 기록이 `failed`와 `source_unreadable`이고 문서는 검색에 그대로이며, 빈 폴더에 "빈 목록도 반영"을 켜면 문서가 빠지고 없는 폴더에는 켜도 실패한다. 이미 색인된 문서가 있는 원천에서 문서 파일을 모두 치우고 숨김 파일과 지원하지 않는 형식의 파일만 둔 뒤 동기화하면 기록이 `failed`와 `nothing_accepted`이고 `listed`와 `not_accepted`의 개수가 남으며 문서는 그대로이고, "빈 목록도 반영"을 켜면 문서가 빠지고 기록은 `succeeded`이며 그 뒤의 보통 동기화는 실패가 아니다. 제외 패턴을 더한 뒤 동기화하면(패턴에 맞지 않는 문서 하나는 남긴다) 그 패턴에 맞는 문서가 검색에서 빠진다.
- [x] 시험(읽을 때 커지는 파일): 목록에는 크기를 비워 내고 읽을 때 `too_large`를 내는 가짜 커넥터로 본다. 이미 색인된 문서 둘 가운데 하나의 파일이 상한을 넘게 된 뒤 동기화하면 그 문서가 검색에서 빠지고 `not_accepted`의 `too_large`에 세어지며 `failed`에는 세어지지 않고 다른 문서는 그대로다. 문서가 하나뿐인 원천에서 같은 일이 나면 기록이 `failed`와 `nothing_accepted`이고 문서는 검색에 그대로다(삭제 반영 직전의 판정이 잡는다).
- [x] 시험: 동기화가 넣은 문서의 색인이 돌기 전에 그 파일을 지우고 작업자를 한 번 돌리면 색인 상태가 `failed`와 `source_changed`이고, 다음 동기화가 그 문서를 삭제 반영한다.
