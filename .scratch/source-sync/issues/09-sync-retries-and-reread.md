# 09: 실패 문서 다시 시도와 모두 다시 읽기

**What to build:** 임베딩 서버가 잠깐 꺼져 재시도를 다 쓰고 실패로 남은 문서가, 파일을 고치지 않아도 다음 동기화에서 저절로 다시 색인된다. 운영자는 "지금 동기화"에 "모두 다시 읽기"를 켜서 원천 하나의 파일을 모두 다시 읽게 하고, 수정 시각과 크기가 그대로인 채 내용만 바뀐 파일과 파서를 고친 뒤의 실패·건너뜀 문서를 지식베이스 전체를 재색인하지 않고 다시 처리한다(스토리 30, 43).

**Blocked by:** 08 (지움 반영과 빈 목록 보호)

**Status:** ready-for-agent

- [ ] 동기화는 내용이 바뀌지 않은 문서(변경 확인값이 같아 읽지 않은 문서와, 읽어 보니 내용이 같은 문서)의 색인 상태를 보고, 일시 실패의 코드(`embedding_unavailable`, `database_unavailable`, `blob_store_error`, `source_unreadable`)나 `worker_lost`나 `source_changed`로 실패해 있으면 색인 작업을 다시 넣는다(명세 "가져오는 원천의 문서 색인"). 변경 확인값이 같은 문서는 이때도 동기화가 파일을 읽지 않고, 읽는 것은 색인 작업이다. 영구 실패(`parse_failed` 같은 것)는 다시 넣지 않는다.
- [ ] `source_changed`로 실패한 문서는 변경 확인값이 비어 있어 다음 동기화가 다시 읽는다. 다시 읽어 보니 내용이 문서 행의 것 그대로이면(운영자가 파일을 원래 내용으로 되돌려 놓았다) 색인 작업을 다시 넣는다(명세 "가져오는 원천의 문서 색인"의 `source_changed` 항목).
- [ ] 지금 동기화의 `reread`("모두 다시 읽기")에 뜻을 붙인다(명세 "동기화의 차례", 사용자 선택). 켜고 돌린 동기화는 변경 확인값이 같아도 후보의 파일을 모두 읽어 내용 해시를 비교한다. 내용이 바뀐 파일은 바뀐 문서로 넣고, 내용이 그대로인 문서 가운데 실패했거나 건너뛴 것은 색인 작업을 다시 넣으며, 내용이 그대로이고 색인된 문서는 건드리지 않는다. 다시 넣은 색인 작업이 다시 파싱할지는 core 명세의 조건 그대로다(암호 건너뜀과 파싱 실패는 다시 파싱하고, 글자 없음은 파서 버전이 바뀌었을 때만). 일정이 시작한 동기화에는 이 옵션이 없다.
- [ ] 시험(주 이음매, 명세 "Testing Decisions"의 장면 표): 수정 시각과 크기를 그대로 둔 채 내용만 바꾼 파일을 보통 동기화하면 그대로이고, 이어서 "모두 다시 읽기"로 동기화하면 `updated`가 1이다. 임베딩 스텁이 실패하게 해 재시도를 다 쓴 문서를 둔 채 동기화하면 그 문서의 색인 작업이 다시 들어간다. 동기화가 넣은 문서의 색인이 돌기 전에 그 파일을 바꿨다가 원래 내용으로 되돌려 놓으면, 색인 상태가 `failed`와 `source_changed`가 된 뒤 다음 동기화가 색인 작업을 다시 넣는다. 영구 실패로 남은 문서는 보통 동기화가 다시 넣지 않고 "모두 다시 읽기"는 다시 넣는다. 글자가 없어 건너뛴 문서는 "모두 다시 읽기"가 색인 작업을 다시 넣고, 파서 버전이 그대로이면 다시 파싱하지 않는다(파싱 횟수를 세는 가짜 파서로 본다. 02의 재색인 시험이 파서를 바꿔 끼우는 길을 쓴다).
- [ ] 검사 넷이 초록이다. 원칙 II는 `tools/check_type_escapes.py`가 판정한다.
