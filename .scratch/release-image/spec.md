# release-image 명세: main이 움직이면 CI가 검색 서버와 작업자의 이미지로 릴리스하고, 운영자는 단독 compose로 프록시 뒤에 다섯 컨테이너를 띄운다

**Status:** ready-for-agent
**기능 계획:** `.scratch/release-image/plan.md`
**근거:** ADR 0020과 그 이력(2026-11-18 넷 가운데 뒤의 둘이 이 명세의 것이다), ADR 0010과 그 이력 2026-11-17, 2026-11-18(뒤의 것이 이 명세의 것이다), ADR 0004, 0007, 0011, 0014, 0016, 0018, agent-os 저장소(GitHub의 `njh6803/agent-os`이고 개발 PC의 사본은 `C:\project\agent`다. 읽기만 했다)의 ADR 0056과 그 이력, 그 저장소의 release-image 명세와 구현(그 저장소의 origin/dev 커밋 `1aac0cf`에서 읽었다), 설계 일지 `docs/journal/2026-11-17-1716-release-image-design.md`, `GLOSSARY.md`, 프로브 `.scratch/release-image/probes/`(README 표). 설계 인터뷰는 하지 않았고(to-spec), 설계가 정하지 않았거나 명세에 넘긴 것 가운데 넷을 2026-11-18에 사용자에게 물었다(단독 compose 시험이 쓰는 임베딩 서버, 이미지 둘의 내용물, MCP 서버 정보에 번호를 넣을지, 프록시의 로그).
**표시와 수:** 결정을 적은 항목마다 머리에 표시 하나를 단다. 사실만 적은 문단(Problem Statement, Solution, User Stories, Further Notes의 메모)에는 달지 않는다. `[넘겨받음]`은 설계(ADR 0020, 그것이 따르는 agent-os ADR 0056, 기능 계획이 넘긴 것)가 정한 것을 옮긴 것, `[사용자 선택]`은 이 세션에서 사용자가 고른 것, `[정함]`은 이 명세가 정한 것, `[이력]`은 ADR에 이력을 더한 것, `[거절]`은 두지 않기로 한 것이다. 본문의 표시 수는 `[넘겨받음]` 29, `[사용자 선택]` 4, `[정함]` 97, `[이력]` 4, `[거절]` 6이다. 항목 여럿에 표시 하나를 함께 다는 방식은 쓰지 않았고, 수는 본문을 고칠 때마다 `grep`으로 다시 센다(to-spec 스킬 3단계).

이 명세는 `GLOSSARY.md`의 말로 쓴다. 사용자가 2026-11-18에 선택 화면에서 고른 새 이름으로 브랜치 `chore/glossary-release-names`의 PR(병합됨)이 용어집, 기능 계획, 헌법 두 문서(`docs/constitution/tech.md`, `docs/constitution/operations.md`)의 낱말을 바꿨고, ADR 0020은 그 이름을 이력 2026-11-18 "용어집이 제품 판의 이름을 릴리스로 바꿨다"에 적었다. 이 명세는 그 PR이 병합되기 전에 썼고 병합 뒤에 dev를 합쳐 맞췄다. ADR 0020 본문과 agent-os의 글은 옛 이름으로 쓰여 있어, 그 글을 이름째 인용할 때만 옛 이름이 나온다. 옛 이름과 새 이름의 대응은 다음과 같다. **릴리스**는 옛 "제품 판"이다(검색 서버와 작업자의 이미지, 배포 파일 묶음을 함께 밖으로 내는 단위와 그 번호). 동사로 쓴 "릴리스한다"는 옛 "판 내기"다. **정식 릴리스**는 옛 "정식 판"이고, **버전 태그**는 옛 "판 태그"(git 태그 `v<번호>`)이며, **릴리스 노트 원고**는 옛 "릴리스 노트 조각"이다. **출시 후보**와 **업그레이드**는 이름이 그대로다. GitHub에 올리는 게시물은 앞말을 붙여 **GitHub 릴리스**라고 가른다. 그 밖의 이름(계약의 **판**, 색인 판, 요청자)은 용어집대로 쓴다.

코드 식별자, 설정 이름, 파일 이름은 영어 그대로다. 구현 파일의 경로는 적지 않는다. 규칙 문서·ADR·시험 선례의 경로, 운영자가 보는 파일의 이름(배포 파일 묶음 안의 것), 하네스의 규칙이 판정하는 경로(제품 변경의 경로, 마이그레이션 파일의 자리), 이 기능이 새로 두는 재료의 자리만 적는다.

명세 안에서만 쓰는 말은 다음과 같다. **제품 변경**은 릴리스에 실릴 변경으로 세는 경로를 고친 변경이다(ADR 0020의 말. 경로는 "제품 변경의 경로" 절). **릴리스 워크플로**는 main이 움직일 때 번호를 계산하고 이미지를 짓고 시험하고 올리고 GitHub 릴리스를 만드는 GitHub Actions 워크플로이고, agent-os의 `release.yml`을 옮긴 것이다. **단독 compose 시험**은 배포 파일 묶음과 지은 이미지로 단독 compose를 실제로 띄워, 관리 명령으로 표본 문서를 넣고 MCP 클라이언트로 검색까지 해 보는 시험이다. **프록시**는 단독 compose에서 TLS를 끝내고 경로를 갈라 서버에 넘기는 nginx 컨테이너다. **바깥 이미지**는 이 저장소가 짓지 않고 받아 쓰는 이미지(nginx, pgvector가 든 PostgreSQL, TEI)다. **이미지의 번호 태그**는 Docker 이미지에 붙이는 `<번호>` 태그이고, git의 버전 태그 `v<번호>`와 가른다. **느낌표**는 커밋과 PR 제목의 형식(`feat!:` 꼴)에서 업그레이드할 때 운영자가 손댈 것이 있다는 표시다. **사람 몫**은 세션이 대신할 수 없어 사용자가 직접 하는 준비다(ADR 0020 Consequences "사람 몫").

## Problem Statement

운영자에게는 지금 이 서버를 설치할 꾸러미가 없다. 저장소를 내려받아 Dockerfile로 이미지를 직접 짓고, 시험용 compose 파일을 참고해 PostgreSQL과 임베딩 서버를 손으로 엮어야 한다. 번호가 붙은 이미지가 없어서, 돌고 있는 서버가 어느 코드인지 물어볼 자리도 없다. `rag-engine --version`이 없고, MCP 클라이언트가 접속할 때 받는 서버 정보(`serverInfo.version`)는 빈 문자열이며, API 문서의 판 칸은 FastAPI가 채운 기본값 `0.1.0`이다. 업그레이드할 때 무엇을 손대야 하는지 알려 주는 글도 없다. 인증 토큰이 네트워크로 오가는데 서버는 TLS를 하지 않고, TLS를 맡을 자리가 설치에 정해져 있지 않다.

MCP 클라이언트를 만드는 사람은 판이 고정된 실제 서버로 시험할 길이 없고, 공개 시연(2027-01 초)도 그런 서버가 있어야 한다. 개발자 쪽에서는 이미지를 손으로 지어 올리면 번호를 잘못 붙이거나 시험하지 않은 이미지를 올리기 쉽다. agent-os 저장소가 이 일을 CI로 자동화한 규칙(agent-os ADR 0056)을 먼저 짓고 첫 릴리스까지 돌려 봤고, ADR 0020이 그 규칙을 따르기로 정했다. 그러나 이 저장소에는 아직 그 워크플로와 도구가 하나도 없고, 단독 compose의 파일도, 프록시 설정도, 설치 안내도 없다.

## Solution

main이 움직이면(출시 PR이나 핫픽스 PR이 병합되면) 릴리스 워크플로가 지난 릴리스 뒤로 제품 변경이 있는지 본다. 있으면 그동안 병합된 PR의 제목에서 다음 번호를 계산하고(정식 릴리스 `0.1.0` 전에는 출시 후보 `0.1.0-rc.N`만 낸다), 검색 서버와 작업자의 이미지를 짓고, 그 이미지로 단독 compose 시험을 돌리고, 취약점을 점검한다. 모두 지나면 Docker Hub의 `njh6803/rag-engine-server`와 `njh6803/rag-engine-worker`에 올리고, GitHub 릴리스를 만들고 버전 태그를 단다. GitHub 릴리스에는 배포 파일 묶음 `rag-engine-<번호>.tar.gz`, 릴리스 노트, 이미지마다 소프트웨어 목록(SBOM)과 취약점 점검 결과가 붙는다.

운영자는 깨끗한 리눅스 VM에서 묶음을 풀고, `.env`에 서버 이름과 데이터베이스 비밀번호를 적고, `tls/`에 인증서를 두고, `docker compose up -d --wait`를 친다. 프록시, 검색 서버, 작업자, PostgreSQL, 임베딩 서버의 다섯 컨테이너가 뜨고(그 앞에 마이그레이션이 한 번 돈다), 밖으로 열린 포트는 프록시의 443 하나다. 임베딩 모델은 첫 시작 때 임베딩 서버가 `models/embedding/` 폴더에 내려받는다. 인터넷이 막힌 곳에서는 다른 기계에서 받은 그 폴더와 `docker save`로 내보낸 이미지 파일을 옮겨 둔다. 운영자는 관리 명령으로 첫 인증 토큰을 내고 문서 폴더를 넣은 뒤, MCP 클라이언트에 `https://<서버 이름>/mcp`와 토큰을 적어 검색한다.

`rag-engine --version`, MCP 서버 정보, API 문서가 모두 이미지의 번호 태그와 같은 번호를 보이고, `--version`은 그 릴리스에 든 계약의 판도 한 줄씩 찍는다. 업그레이드할 때는 새 릴리스 노트의 "업그레이드할 때 할 일"을 읽고 `.env`의 번호 한 줄을 바꿔 다시 띄운다. 개발자는 운영자가 손댈 것이 생기는 PR의 제목에 느낌표를 붙이고, 마이그레이션 파일을 고친 PR에 느낌표가 없으면 CI가 막는다. 단독 compose 시험은 main으로 가는 PR과 main 푸시에서만 돌아, dev로 가는 티켓 PR은 그 시간을 기다리지 않는다.

## User Stories

1. As a 운영자, I want 릴리스마다 번호가 붙은 검색 서버와 작업자 이미지를 받고 싶다, so that 저장소를 내려받아 직접 짓지 않는다.
2. As a 운영자, I want 이미지를 공개 레지스트리(Docker Hub)에서 계정 없이 받고 싶다, so that 설치 전에 가입하거나 토큰을 받지 않는다.
3. As a 운영자, I want 배포 파일 묶음 하나를 풀면 설치에 필요한 파일이 모두 있기를 바란다, so that 여러 곳에서 파일을 모으지 않는다.
4. As a 운영자, I want 묶음의 `.env.example`에 이미지 번호와 이름공간이 이미 채워져 있기를 바란다, so that 내려받은 묶음과 다른 번호의 이미지를 잘못 띄우지 않는다.
5. As a 운영자, I want `.env`에 꼭 채워야 하는 값이 비어 있으면 compose가 무엇이 없는지 알려 주며 멈추기를 바란다, so that 반쯤 뜬 설치를 붙잡고 원인을 찾지 않는다.
6. As a 운영자, I want 명령 한 줄(`docker compose up -d --wait`)로 모든 컨테이너를 띄우고 싶다, so that 띄우는 차례를 외우지 않는다.
7. As a 운영자, I want 그 명령이 돌아왔을 때 서버가 이미 답할 수 있기를 바란다, so that 첫 요청이 502로 실패하지 않는다.
8. As a 운영자, I want 마이그레이션이 서버보다 먼저 저절로 돌기를 바란다, so that 업그레이드마다 마이그레이션 명령을 따로 치지 않는다.
9. As a 운영자, I want 밖으로 열린 포트가 443 하나이기를 바란다, so that 방화벽에 열 것이 하나뿐이고 데이터베이스와 임베딩 서버가 밖에 드러나지 않는다.
10. As a 운영자, I want 인증서 파일 둘을 `tls/`에 두는 것으로 TLS를 켜고 싶다, so that 서버 설정을 따로 고치지 않는다.
11. As a 운영자, I want 시험 삼아 띄울 때 쓸 자체 서명 인증서를 만드는 명령을 안내에서 그대로 복사하고 싶다, so that 인증서가 없어도 설치를 먼저 해 본다.
12. As a 운영자, I want 오래된 TLS 판(1.0, 1.1)으로는 접속이 안 되기를 바란다, so that 보안 점검에서 지적받지 않는다.
13. As a 운영자, I want 프록시가 MCP 경로, 수집 API, 관리 API, `/health`만 넘기고 나머지는 404로 막기를 바란다, so that API 문서 화면 같은 것이 인증 없이 밖에 보이지 않는다.
14. As a 운영자, I want 허용하지 않은 서버 이름으로 온 MCP 요청이 421로 거부되기를 바란다, so that DNS 리바인딩 공격(남의 도메인 이름이 이 서버의 주소를 가리키게 해 브라우저가 이 서버에 요청을 보내게 하는 공격)을 프록시 뒤에서도 막는다.
15. As a 운영자, I want 프록시의 접근 로그에 경로만 남고 질의 문자열이 남지 않기를 바란다, so that 문서 키가 로그로 새지 않는다(원칙 V).
16. As a 운영자, I want 서버가 멈춘 동안에도 프록시의 오류 로그에 요청의 질의 문자열이 남지 않기를 바란다, so that 장애 중에 로그를 모아 보내도 문서 키가 나가지 않는다.
17. As a 운영자, I want 임베딩 서버의 로그에 질의와 문서의 글이 남지 않는다는 것이 재어져 있기를 바란다, so that 임베딩 서버의 로그를 따로 끄지 않아도 된다는 것을 믿는다.
18. As a 운영자, I want 큰 문서를 수집 API로 올릴 때 크기 제한을 서버 설정 하나(`RAG_MAX_UPLOAD_MB`)로만 정하고 싶다, so that 프록시 설정을 함께 고치지 않는다.
19. As a 운영자, I want 서버와 작업자, 프록시, 임베딩 서버가 root가 아닌 사용자로 돌기를 바란다, so that 컨테이너가 뚫려도 피해가 줄어든다.
20. As a 운영자, I want 서버 컨테이너를 다시 만들거나 다시 시작한 뒤 프록시가 손대지 않아도 다시 닿기를 바란다, so that 업그레이드나 장애 뒤에 프록시까지 다시 띄우지 않는다.
21. As a 운영자, I want 서버 프로세스가 죽으면 컨테이너가 저절로 다시 뜨기를 바란다, so that 밤사이 멈춘 서버를 아침에 발견하지 않는다.
22. As a 운영자, I want 임베딩 모델을 첫 시작 때 서버가 스스로 내려받기를 바란다, so that 인터넷이 되는 곳에서는 모델을 따로 준비하지 않는다.
23. As a 폐쇄망 운영자, I want 인터넷이 되는 기계에서 받은 이미지 다섯과 모델 폴더를 파일로 옮겨 설치하고 싶다, so that 인터넷이 막힌 곳에서도 같은 릴리스를 띄운다.
24. As a 폐쇄망 운영자, I want 옮긴 이미지가 받은 것과 같은지 이미지 ID로 대조하는 명령을 안내에서 보고 싶다, so that 옮기는 도중에 바뀐 이미지를 띄우지 않는다.
25. As a 운영자, I want 메모리가 얼마나 필요한지(기준 32GB, 최소 16GB) 설치 전에 알고 싶다, so that 모자란 VM을 준비하지 않는다.
26. As a 운영자, I want 리랭커를 켜는 방법(compose 프로필, 설정, 마이그레이션 다시 돌리기, 후보 수와 검색 시간 제한)을 안내에서 보고 싶다, so that 기본 설치 뒤에 품질을 올린다.
27. As a 운영자, I want 첫 인증 토큰을 관리 명령 한 줄로 내고 싶다, so that 관리 API를 처음 부를 토큰을 얻는다.

## Implementation Decisions

### 따르는 것과 옮기는 방식

- [넘겨받음] 이 저장소는 agent-os ADR 0056이 정한 판 내기(이 명세의 말로 릴리스)를 그 이력까지 따르고, ADR 0020이 적은 다른 것만 바꾼다. 따르지 않는 결정(agent-os 제품의 배치)과 값이 다른 결정(레지스트리와 계정, 제품 변경)은 ADR 0020 "이 저장소에서 다른 것"이 적는다.
- [넘겨받음] agent-os가 릴리스를 위해 들인 것을 모두 옮긴다. 이 저장소에 없던 파일이라 agent-os의 것을 복사한 뒤 이 저장소의 값(이미지 둘, 제품 변경의 경로, 묶음의 이름)으로 고친다(ADR 0020 "옮기는 방식"). 그 저장소의 웹 의존성(node, pnpm)과 브라우저 시험(Playwright)은 옮기지 않는다.
- [정함] 옮길 원본은 agent-os의 origin/dev 커밋 `1aac0cf`의 파일이다. 티켓이 시작할 때 agent-os가 그 뒤로 릴리스 쪽을 고쳤으면(`git -C C:/project/agent fetch origin` 뒤에 `git -C C:/project/agent log b74a8adf2..origin/dev -- .github/workflows/release.yml tools/release.py tools/release_ci.py tools/check_notes.py deploy/ tests/tools/test_release.py tests/tools/test_release_ci.py tests/tools/test_release_workflow.py tests/tools/test_check_notes.py tests/tools/test_deploy_guide.py`가 비지 않으면) 그 변경을 함께 옮길지 티켓이 사용자에게 묻는다. 묻지 않고 따라가면 이 명세가 잰 꼴과 옮긴 파일이 어긋난다. 받아 오기를 먼저 치는 것은 그 클론의 추적 ref가 낡았으면 변경이 있어도 비어 보이기 때문이다(명세 검토는 받아 오지 않은 ref로 쳐서 비었다). 두 명령 가운데 하나가 오류로 끝나도 출력이 비어 보이므로, 오류는 빈 것으로 보지 않는다. 경로는 Git Bash에서 역슬래시가 지워지지 않게 `C:/project/agent`로 쓴다. 확인의 기점은 `b74a8adf2`다. 그 커밋(agent-os PR 607, 2026-11-18)은 `1aac0cf` 뒤로 릴리스 쪽 파일 넷(`.github/workflows/release.yml`, `tools/check_notes.py`, `tests/tools/test_check_notes.py`, `tests/tools/test_release.py`)의 낱말만 바꿨다(조각을 원고로, 되돌려 합치기 PR을 운영에서 개발로 합치기 PR로). 이 저장소는 자기 용어집의 이름으로 옮기므로 옮길 것이 없다고 티켓 세션이 판정했고, 사용자가 2026-11-18에 기점을 올리기로 골랐다. 옮기는 파일은 그대로 `1aac0cf`에서 읽는다.
- [정함] 옮긴 글(운영 문서의 절, 병합 절차, 설치 안내, 도구의 출력 문구)은 이 저장소의 새 이름(릴리스, 정식 릴리스, 버전 태그, 릴리스 노트 원고, GitHub 릴리스)으로 쓴다.

### 저장소의 자리

- [정함] 이미지를 짓는 파일은 agent-os와 같이 `deploy/images/`에 둔다. 이미지 둘을 짓는 Dockerfile 하나와 그 옆의 무시 파일(BuildKit이 Dockerfile 이름 뒤에 `.dockerignore`를 붙여 찾는 파일), 이미지 둘을 함께 짓는 bake 설정(`docker-bake.hcl`)이다. 빌드 컨텍스트는 저장소 루트다. 지금 루트에 있는 Dockerfile과 `.dockerignore`는 그 자리로 옮기고 루트에 남기지 않는다. 루트에 두 벌이 있으면 어느 것이 릴리스되는지 헷갈린다.
- [정함] 배포 파일 묶음의 원천은 `deploy/standalone/`이고, 릴리스 설정 파일은 `deploy/release.toml`이다(agent-os와 같은 자리). 릴리스 노트 원고는 `docs/release-notes/` 아래 `features/`(기능 소개 단락), `upgrade/`(업그레이드할 때 할 일), `intro/`(정식 릴리스 번호마다 소개 글) 세 폴더다.

### 제품 변경의 경로

- [정함] 제품 변경으로 세는 경로는 `src/`, `pyproject.toml`, `uv.lock`, `deploy/` 넷이다. ADR 0020이 든 것(`src`, 의존성 잠금 파일, Dockerfile, 단독 compose의 파일, 프록시 설정, 설치 안내, 릴리스 설정 파일) 가운데 `src`와 잠금 파일 밖의 것은 모두 `deploy/` 아래에 있다.
- [정함] `pyproject.toml`은 칸을 가리지 않고 통째로 넣는다. 까닭은 셋이다. 첫째, 이미지를 짓는 입력이다(Dockerfile이 그 파일을 복사해 패키지를 깐다). 둘째, 잠금 파일이 따라 바뀌지 않으면서 이미지를 바꾸는 칸이 있다. `[project.scripts]`는 `rag-engine` 명령을 정하고, `[tool.hatch.build.targets.wheel]`은 패키지에 무엇이 드는지 정한다(빌드 백엔드는 hatchling이다). 셋째, 거꾸로 하네스의 칸(`[tool.ruff]`, `[tool.pyright]`, `[tool.importlinter]`, `[tool.pytest]`, 개발 의존성 묶음)만 고친 커밋이 그 파일 때문에 릴리스를 하나 더 낼 걱정은 작다. 커밋 `e7eeab6`까지의 병합이 아닌 커밋 60개 가운데 `pyproject.toml`을 고친 것은 9개이고, 9개 모두 `uv.lock`도 고쳤다. 8개는 `src`도 고쳤고, 나머지 하나(`87e981c`, core 01)는 개발 의존성에 테스트 데이터베이스 드라이버를 더한 커밋이라 `pyproject.toml`과 `uv.lock`만 고쳤다. 잠금 파일에는 개발 의존성도 실리므로, 그 커밋은 `pyproject.toml`을 세지 않아도 `uv.lock` 때문에 이미 제품 변경이다(`git rev-list --count --no-merges e7eeab6`, `git log --no-merges --format=%h e7eeab6 -- pyproject.toml`, 커밋마다 `git diff-tree --name-only -r`로 손으로 셌다). 그리고 릴리스는 출시 PR이 dev의 여러 티켓을 한꺼번에 main에 올릴 때 나므로, 그 묶음 전체가 하네스만 고쳤을 때만 빈 릴리스가 난다.
- [거절] agent-os처럼 `pyproject.toml`을 빼는 것. `[project.scripts]`나 패키지에 드는 파일만 바꾼 PR이 릴리스되지 않는다.
- [거절] `pyproject.toml`에서 칸을 골라 세는 것. 판정이 TOML을 읽어 앞뒤를 견줘야 해 도구가 복잡해지고, 얻는 것이 없다. 위의 셈대로 `pyproject.toml`을 고친 커밋은 모두 `uv.lock`도 고쳐, 칸을 골라 세어도 잠금 파일 때문에 같은 커밋이 제품 변경으로 세어진다.
- [정함] `README.md`와 `docs/`는 세지 않는다. Dockerfile이 `README.md`를 복사하는 것은 패키지 메타데이터의 긴 설명(`readme` 칸)을 채우려는 것이고 동작을 바꾸지 않는다. 릴리스 노트 원고도 세지 않는다(agent-os와 같다).
- [넘겨받음] 테스트용 `compose.test.yml`과 평가용 `compose.eval.yml`은 운영자의 설치에 닿지 않아 세지 않는다(ADR 0020 "제품 변경의 범위").
- [이력] ADR 0020에 이력 "명세가 제품 변경의 목록과 번호가 보이는 자리를 넓혔다"를 더하고, "제품 변경의 범위"의 목록 문장 뒤에 포인터를 단다. 본문의 목록에 `pyproject.toml`이 없어 본문만 읽으면 그 파일을 고친 PR이 릴리스되지 않는다고 읽기 때문이다.

### 번호와 느낌표

- [넘겨받음] 번호는 ADR 0056 결정 "번호"대로 지난 릴리스 뒤로 main에 쌓인 커밋의 제목에서 계산한다. 첫 릴리스는 `0.1.0-rc.1`이고, 정식 릴리스 `0.1.0` 전에는 끝의 `-rc.N`만 오른다. 번호는 이 저장소의 git 태그와 PR 제목에서만 계산하고 agent-os의 번호와 맞추지 않는다(ADR 0020 "번호는 따로 센다").
- [정함] 릴리스 설정 파일에서 출시 후보 단계를 적는 줄은 `candidate_for = "0.1.0"`이다. 그 줄이 있는 동안 번호는 `0.1.0-rc.N`으로만 나고, release-0-1의 마지막 티켓이 그 줄을 지운다(ADR 0020 "첫 정식 판의 신호").
- [넘겨받음] 업그레이드할 때 운영자가 손댈 것(설정, 환경 변수, 데이터, 플러그인 코드)이 있는 변경의 제목에 느낌표를 붙인다. 그 위에 셋을 언제나 그 기준에 드는 변경으로 못박는다. 데이터베이스 마이그레이션이 든 변경, 재색인이 필요해지는 변경(색인 판의 요소가 바뀌는 것, ADR 0008), 계약의 판에서 앞자리를 올리는 변경이다(ADR 0020 "올릴 때 운영자가 손댈 것의 기준").
- [정함] 마이그레이션 파일은 `src/rag_engine/adapters/postgres/migrations/versions/` 아래의 `.py` 파일이다. PR 제목 검사는 그 아래 파일을 더하거나 고치거나 지우거나 옮긴 PR의 제목에 느낌표가 없으면 막는다. 이미 릴리스된 마이그레이션을 고치는 것도 업그레이드에 닿을 수 있어 더한 것과 가르지 않는다.
- [정함] 그 판정은 agent-os 노트 검사의 판정 (가)(제목과 느낌표와 업그레이드 원고의 짝)에 더한다. (가)는 이미 PR의 바뀐 파일 목록을 읽고, `ci.yml`의 `ticket` 잡(필수 검사 `verify`가 기다린다)과 제목을 고칠 때 도는 PR 제목 워크플로에서 함께 돈다. 따로 검사를 두면 제목을 고친 뒤 다시 도는 길을 하나 더 지어야 한다.
- [정함] 재색인이 필요해지는 변경과 계약의 앞자리를 올리는 변경은 기계가 알아보지 않고 PR 서식의 칸 "업그레이드할 때 운영자가 손댈 것"이 묻는다(ADR 0020이 정한 방식). 그 칸은 세 항목(마이그레이션, 재색인, 계약의 앞자리)을 따로 묻는다.
- [넘겨받음] 이 검사는 티켓 PR과 핫픽스 PR에 걸고, 출시 PR(dev에서 main으로)과 되돌려 합치기 PR(main에서 dev로)은 면제한다. 그 둘은 제목이 번호의 원천이 아니고 변경 목록에 그동안의 마이그레이션이 모두 들기 때문이다(ADR 0020).
- [정함] 마이그레이션 리비전의 끝(alembic의 head)이 하나인지 보는 저장소 상태 시험을 둔다. 핫픽스 PR이 main에 마이그레이션을 더하는 동안 dev에도 같은 부모를 가리키는 마이그레이션이 있으면, 되돌려 합치기 PR에서 head가 둘이 된다. 그러면 `migrate`(`command.upgrade(config, "head")`)가 "Multiple head revisions are present"로 실패해 서버가 뜨지 않는다(같은 부모를 가리키는 빈 리비전 둘로 alembic의 `ScriptDirectory`를 불러 손으로 봤다). 시험이 되돌려 합치기 PR의 CI를 막는다. 그 PR은 머리가 main 자체이고 로컬에서 합쳐 dev로 푸시하는 길을 쓰지 않으므로(`next-session` `merge.md`의 "되돌려 합치기") 두 head를 잇는 합치는 리비전을 더할 자리가 없다. 그래서 그때 세션은 할 일을 짐작하지 않고 멈추고 사용자에게 묻고, 푸는 길은 그 일이 처음 날 때 정한다(티켓 세션이 2026-11-18에 사용자에게 물어 정했다).
- [넘겨받음] 느낌표가 붙은 PR은 `upgrade/`에 원고를 하나 이상 새로 더해야 하고, 느낌표가 없는 PR이 그 폴더에 새 원고를 더하면 막는다(agent-os 노트 검사 (가)). 마이그레이션 PR의 원고는 업그레이드 전에 백업하라고 적는다. 백업과 복원의 절차는 backup-upgrade가 정하고, 그 전의 원고는 PostgreSQL 볼륨을 백업하라는 한 줄로 쓴다.
- [넘겨받음] squash 병합의 제목을 PR 제목으로 쓰는 저장소 설정은 사람 몫이고, PR 제목 검사를 옮기는 티켓을 병합하기 전에 바꾼다(ADR 0020 Consequences "사람 몫"). 지금 값은 `COMMIT_OR_PR_TITLE`이고, 이 설정에서 커밋이 하나인 PR의 squash 제목이 PR 제목이 아니라 커밋 제목을 따른다는 것은 재려 했으나 사례가 없었다. 이 저장소에서 병합된 티켓 PR 59개 가운데 커밋이 하나인 것은 0개이고, agent-os(설정 `PR_TITLE`)에서 최근에 닫힌 PR 300개 가운데 병합된 티켓 PR 292개를 보니 커밋이 하나인 3개도 PR 제목과 커밋 제목이 같았다(프로브 `squash_title/`). 그래서 그 동작은 여전히 어림이고, 설정을 바꾸면 그 어림과 상관없이 PR 제목이 번호 도구에 닿는다.
- [정함] 병합하는 쪽은 squash 제목을 직접 주지 않는다. 제목을 주면(`gh pr merge --subject`, 웹 화면에서 제목을 고치기) 설정과 상관없이 그 제목이 main에 남아, 검사를 지난 PR 제목의 느낌표가 빠질 수 있다. 이 저장소의 병합 절차(`next-session`의 `merge.md` 병합 명령 `gh pr merge <번호> --squash --match-head-commit <HEAD>`)는 제목을 주지 않으므로 설정의 PR 제목을 쓴다. 병합 절차를 옮기는 티켓이 그 절의 병합 명령 곁에 이 까닭을 적는다.

### 이미지와 계정

- [넘겨받음] 이미지는 검색 서버와 작업자 둘이고, Docker Hub의 `njh6803/rag-engine-server`와 `njh6803/rag-engine-worker`에 공개로 올린다(ADR 0020 "이미지와 계정"). 토큰은 agent-os의 것과 따로 발급해 이 저장소의 GitHub 환경 `release`에만 둔다.
- [넘겨받음] 이미지의 태그는 번호 태그 `<번호>`와 커밋 태그 `sha-<커밋 해시 40자>` 둘이고 `latest`는 두지 않는다. 릴리스 워크플로는 커밋 태그로 먼저 올리고, 모든 단계가 지난 뒤 번호 태그를 붙인다(ADR 0056 "판마다 나오는 것", agent-os `release.yml`).
- [정함] bake 설정(Docker의 `buildx bake`가 읽는, 이미지 여럿을 한 번에 짓는 목록)의 대상 이름은 `server`와 `worker`이고, 두 대상은 같은 Dockerfile의 두 단계를 짓는다. bake 변수는 agent-os의 bake 설정과 같은 다섯이다. 이름공간(`NAMESPACE`), 이미지 태그(`TAG`. 첫 짓기는 번호, 올리는 짓기는 `sha-<커밋 해시>`), 번호(`VERSION`. 빌드 인자 `APP_VERSION`으로 넘긴다), 커밋 해시(`REVISION`), 저장소 주소(`SOURCE`)이고, 뒤의 둘은 아래 라벨을 채운다. 시험과 CI는 이름공간과 태그를 바꿔 짓는다.
- [정함] 이미지에는 OCI 라벨(이미지에 붙는 이름표. 컨테이너 이미지 표준이 정한 이름이라 레지스트리와 점검 도구가 읽는다) 셋을 단다. `org.opencontainers.image.version`(번호), `org.opencontainers.image.revision`(커밋 해시), `org.opencontainers.image.source`(저장소 주소)다. 프로브의 시제품이 단 라벨이 이 셋이다(`run_out.txt`의 `[build]` 줄).

### 이미지의 구성

- [사용자 선택] 서버 이미지와 작업자 이미지는 내용물이 같고 시작 명령만 다르다. 서버는 `rag-engine serve --host 0.0.0.0 --port 8000`, 작업자는 `rag-engine worker`로 시작한다. 시제품으로 지어 보니 두 이미지가 각 524MB이고 층 8개가 모두 같아(프로브 `build` 단계), 하나를 받으면 다른 하나는 거의 추가로 받지 않는다(받는 양은 재지 않았다). 관리 명령은 어느 이미지에서도 돈다.
- [정함] 이미지는 두 단계로 짓는다. 빌드 단계는 uv로 잠금 파일대로 운영 의존성만 깔고(`--locked --no-dev`), 그 뒤 번호를 넣어 프로젝트를 편집 가능하지 않은 꼴로 깐다. 잠금 파일은 프로젝트의 번호(`0.0.0`)도 적으므로 `--locked`는 번호를 바꾸기 전에 치고, 번호를 바꾼 뒤에는 `--frozen`으로 깐다. 번호를 바꾼 사본에서는 `uv lock --check`가 잠금 파일을 고쳐야 한다며 종료 1로 끝났다(PR 직전 리뷰가 uv 0.10.8로 손으로 봤다). hatchling은 `METADATA`의 Version 칸에 받은 번호(`0.0.1-rc.1`)를 그대로 적고 휠 파일 이름만 `0.0.1rc1`로 바꾸므로, 깐 뒤 `importlib.metadata`가 받은 번호를 그대로 돌려준다(같은 리뷰가 임시 패키지를 `uv build --wheel`로 지어 깔아 보고 손으로 봤고, 프로브 `standalone/run_out.txt`의 `[build]` 줄이 이미지 안의 패키지 번호를 `0.1.0-rc.1`로 쟀다). 실행 단계는 빌드 단계의 가상 환경만 복사한다. 시제품 Dockerfile이 이 꼴이다(`.scratch/release-image/probes/standalone/Dockerfile`).
- [정함] 바탕 이미지(`python:3.12-slim`)와 uv 이미지(`ghcr.io/astral-sh/uv:0.10.8`)는 태그에 digest를 붙여 고정한다. 값은 티켓이 그날 받은 digest로 정한다. 시제품은 BuildKit(Docker가 이미지를 짓는 엔진)이 두 태그를 받아 지었지만, 받은 바탕 이미지가 이미지 저장소에 남지 않아(`docker image inspect`가 없는 이미지라고 답했다) 이 세션은 digest를 읽지 않았다.
- [정함] 번호는 빌드 인자 `APP_VERSION`으로 받는다. 빠지거나 꼴(`X.Y.Z`나 `X.Y.Z-rc.N`)이 틀리면 짓기가 실패하고, 빌드 단계 안의 `pyproject.toml` 사본에서만 `version`을 바꾼 뒤 깐다. 깐 뒤 설치된 패키지의 번호가 인자와 같은지 대조한다(agent-os의 `serve.Dockerfile`과 같은 방법). 저장소의 `version`은 `0.0.0` 그대로 둔다. 시제품에서 번호 없이 지으면 종료 코드 1과 안내 문구가 나왔고, 이미지 안의 패키지 번호가 넘긴 번호와 같았다(프로브 `build` 단계).
- [정함] 실행 단계에는 init 프로세스(컨테이너의 1번 프로세스로 돌며 종료 신호를 앱에 넘기고 끝난 자식 프로세스를 거두는 작은 프로그램)로 `tini`를 깔고 진입점으로 둔다. 사용자는 uid·gid(리눅스의 사용자 번호와 그룹 번호) 10001의 `rag`이고, 쓸 자리 `/data`(파일 저장소)를 그 사용자의 것으로 만든다. 시제품의 두 이미지가 uid 10001로 돌았다(프로브 `checks` 단계). `tini`는 바탕 이미지의 Debian 패키지 저장소에서 짓는 날의 판을 받으므로 digest처럼 고정되지 않는다(agent-os와 같다). 그 판은 이미지의 소프트웨어 목록이 적는다.
- [정함] 운영 의존성에 `python-multipart`를 직접 선언한다. 수집 API의 파일 올리기가 그 패키지로 본문을 읽는데, 지금은 다른 패키지가 끌어오는 전이 의존으로만 들어 있어 그 패키지가 의존을 떼면 이미지에서 올리기가 깨진다.
- [정함] 헬스체크는 Dockerfile에 두지 않고 단독 compose가 둔다. 서버 이미지의 헬스체크는 파이썬 표준 라이브러리(`urllib`)로 `http://127.0.0.1:8000/health`를 본다. 이미지에 `curl`을 더 깔지 않기 위해서다.
- [정함] 단독 compose는 서버, 작업자, 마이그레이션 컨테이너의 루트 파일 시스템을 읽기 전용으로 붙이고 `/tmp`만 메모리 파일 시스템(tmpfs)으로 준다. 서버에서 `/tmp`를 떼면 1MiB를 넘는 올리기가 실패한다. 시제품에서 `/tmp` 없이 2MB를 올리면 400(`There was an error parsing the body`)이었고, 있으면 2MB와 20MB가 202였다(프로브 `checks` 단계). 멀티파트 파서가 1MiB를 넘는 본문을 임시 파일로 받기 때문이다(starlette 1.10.0 `formparsers.py`의 `spool_max_size = 1024 * 1024`를 읽었다. 1MiB 언저리의 크기는 재지 않았다).
- [정함] 서버의 `/tmp`에는 크기 상한 1GiB를 준다(compose `tmpfs` 항목의 `size`). 그 크기는 `.env`의 `RAG_ENGINE_SERVER_TMP_SIZE`로 바꿀 수 있고, 비어 있으면 `1g`다(`${RAG_ENGINE_SERVER_TMP_SIZE:-1g}` 꼴). compose 파일을 고치게 하면 업그레이드가 새 묶음의 `compose.yaml`로 바꿀 때 그 고침이 사라지기 때문이다. 그 자리는 메모리이고, 크기 상한(`RAG_MAX_UPLOAD_MB`, 기본 100MB)을 넘는 업로드도 수집 API가 크기를 보기 전에 끝까지 그 자리에 쓰인다(`src/rag_engine/server/ingest_api.py` 독스트링과 코드를 읽었다). 상한을 두면 큰 업로드가 차지할 수 있는 메모리가 그 크기에서 멈춘다. 1GiB는 기본 상한의 업로드 열 개를 함께 받는 크기이고, 설치 안내는 `RAG_MAX_UPLOAD_MB`를 올리는 설치가 `.env`의 이 크기도 함께 올리라고 적는다. 업로드를 크기 상한에서 미리 끊는 것(`Content-Length`를 먼저 보는 것)은 수집 API의 동작이라 이 기능이 바꾸지 않는다.

### 번호가 보이는 자리

- [넘겨받음] `rag-engine --version`과 서버가 만드는 API 문서의 판 칸이 이미지의 번호 태그와 같은 번호를 보인다(ADR 0020 "제품 판의 번호가 보이는 자리").
- [사용자 선택] 셋째 자리로 MCP 초기화 응답의 서버 정보(`serverInfo.version`)에도 같은 번호를 싣는다. 지금은 빈 문자열이다. 클라이언트가 화면이나 접속 기록에 `rag-engine 0.1.0-rc.1`처럼 서버의 번호를 남길 수 있게 하려는 것이고, MCP 표준의 칸이라 원칙 III에 걸리지 않는다. 검색 도구의 형식과 그 판(`1.1.0`)은 바뀌지 않는다.
- [이력] 위의 셋째 자리를 ADR 0020의 같은 이력("명세가 제품 변경의 목록과 번호가 보이는 자리를 넓혔다")에 적고, "제품 판의 번호가 보이는 자리"의 둘을 적은 문장 뒤에 포인터를 단다.
- [정함] 세 자리 모두 설치된 패키지의 메타데이터(`importlib.metadata`)에서 번호를 읽는다. 이미지 안에서는 `APP_VERSION`이 넣은 번호이고, 개발 체크아웃에서는 `0.0.0`이다. 번호를 코드에 따로 적지 않아 둘이 어긋날 수 없다.
- [정함] `rag-engine --version`의 첫 줄은 `rag-engine <번호>`이고, 이어서 지금 판이 붙은 계약마다 한 줄씩 `<계약의 이름> <판>`을 찍는다. 검색 도구의 형식(지금 `1.1.0`), 수집 API와 관리 API의 경로에 든 판(`v1`), 파서 인터페이스(`1.0.0`), 색인 형식의 스키마 판(`1`)이다. 원칙 VII이 드는 계약에 판이 더 붙으면 그 줄을 더한다. 줄의 꼴은 릴리스 노트가 그대로 옮길 수 있게 사람이 읽는 글로 쓴다.
- [정함] `--version`은 필수 설정(데이터베이스 주소, 허용 호스트, 임베딩 서버 주소)을 검증하지 않고 끝난다. 다른 하위 명령은 모두 필수 설정을 검증하는데, 릴리스 워크플로가 설정 없이 이미지에서 번호를 읽어야 하기 때문이다(아래 릴리스 노트 절).

### 단독 compose

- [넘겨받음] 기본 컨테이너는 프록시(nginx), 검색 서버, 작업자, PostgreSQL, 임베딩 서버 다섯이고, 서버 앞에 한 번 도는 마이그레이션 서비스를 둔다(ADR 0011). 리랭커는 켜는 설치가 compose 프로필로 더한다(ADR 0010 이력 2026-11-17). 밖으로 여는 포트는 프록시의 443 하나이고 80은 열지 않는다(ADR 0020 "단독 compose의 배치").
- [정함] 서비스 이름은 `proxy`, `postgres`, `embedding`, `migrate`, `server`, `worker`이고, 리랭커는 프로필 `reranker`의 서비스 `reranker`다. 설치 안내는 서비스 이름과 Docker Hub 저장소 이름의 대응표를 둔다(agent-os 설치 안내와 같다).
- [정함] 이 저장소가 짓는 이미지는 `.env`의 `RAG_ENGINE_NAMESPACE`와 `RAG_ENGINE_VERSION`으로 고른다(`${RAG_ENGINE_NAMESPACE}/rag-engine-server:${RAG_ENGINE_VERSION}` 꼴). 두 값이 없으면 compose가 무엇이 없는지 적은 문구로 멈춘다(`${이름:?문구}` 꼴, agent-os의 compose와 같다). 묶음의 `.env.example`은 표지 `@RAG_ENGINE_NAMESPACE@`와 `@RAG_ENGINE_VERSION@`을 담고, 묶음을 짓는 도구가 그 릴리스의 값(`njh6803`, 번호)으로 채운다.
- [정함] 바깥 이미지 셋은 digest로 고정한다. 프록시는 nginx 1.30.6 alpine(`nginx@sha256:583b7f2fce1cdb8da5ad5c39ebd3c33b98b87d493190e548bdee1fa8c619c311`, agent-os의 단독 compose와 같다), PostgreSQL은 `pgvector/pgvector:0.8.7-pg18-trixie@sha256:5895949dfcdf308eb0cd31c950c93c14895c77f33fbedfecf1fa511ab1d4bcd2`, 임베딩 서버와 리랭커는 `ghcr.io/huggingface/text-embeddings-inference:cpu-1.9.4@sha256:2538ea1c9640d3763b15af668039d24172d063b42337b0c27796fc2be180c78d`다. 셋 모두 이 명세의 프로브가 띄운 판이다. 프로브는 nginx만 digest로 띄웠고 PostgreSQL과 TEI는 태그로 띄웠으며, 두 태그가 가리킨 digest는 개발 PC에서 `docker image inspect --format '{{.RepoDigests}}'`로 손으로 읽었다. 판을 바꾸는 티켓은 단독 compose 시험을 다시 지난다.
- [정함] 서버, 작업자, 마이그레이션 컨테이너는 `.env`를 통째로 받는다(`env_file`). 운영자는 설정 문서에 있는 `RAG_*` 설정을 compose를 고치지 않고 `.env`에 더한다. compose가 정하는 셋(`RAG_DATABASE_URL`, `RAG_DATA_DIR=/data`, `RAG_DEFAULT_EMBEDDING_URL=http://embedding:80`)은 compose의 `environment`가 덮어쓴다. 리랭커 끝점(`RAG_DEFAULT_RERANKER_URL`)은 compose가 정하지 않고, 리랭커를 켜는 설치가 `.env`에 `http://reranker:80`을 적는다. compose가 늘 그 값을 주면 리랭커를 띄우지 않은 설치도 리랭커 끝점을 갖게 된다. `.env`는 비밀 값이 들어 운영자만 읽게 둔다(`chmod 600`, agent-os 설치 안내와 같다).
- [정함] `.env`에서 운영자가 꼭 채우는 값은 `RAG_ALLOWED_HOSTS`(서버 이름. MCP 허용 호스트, ADR 0014)와 `POSTGRES_PASSWORD` 둘이다. 둘도 이미지의 두 값처럼 compose 파일이 `${이름:?문구}` 꼴로 읽어, 비어 있으면 컨테이너를 하나도 띄우지 않고 무엇이 없는지 적은 문구로 멈춘다(Compose 5.6.1에서 그 꼴의 작은 compose 파일로 `up -d --wait`를 쳐 종료 1과 문구를 보고, 컨테이너가 생기지 않은 것을 손으로 봤다). `POSTGRES_PASSWORD`는 PostgreSQL 서비스와 데이터베이스 주소에서, `RAG_ALLOWED_HOSTS`는 서버의 `environment`에서 그렇게 읽는다. 서버도 허용 호스트가 비면 기동을 거부하지만(ADR 0014), 그때는 앞의 컨테이너가 이미 뜬 뒤라 반쯤 뜬 설치가 남는다. 데이터베이스 주소는 compose가 그 비밀번호로 조립하므로, 설치 안내는 주소에 넣어도 깨지지 않는 16진수 비밀번호를 만드는 명령(`openssl rand -hex 24`)을 적는다.
- [정함] 볼륨은 둘이다. `postgres`(데이터베이스)와 `data`(서버, 작업자, 관리 명령이 함께 쓰는 파일 저장소)다. compose 파일의 최상위 `name:`은 `rag-engine`이고, 그래서 Docker에 생기는 볼륨 이름은 `rag-engine_postgres`와 `rag-engine_data`다. 이름을 두지 않으면 묶음을 푼 폴더 이름(`rag-engine-<번호>`)이 프로젝트 이름이 되어, 새 폴더에 풀어 띄운 설치가 빈 볼륨으로 뜬다(어림. agent-os의 단독 compose도 `name: agent-os`를 둔다). 단독 compose 시험은 `-p`로 프로젝트 이름을 덮는다. 모델은 볼륨이 아니라 묶음 안의 폴더 `models/embedding/`(리랭커는 `models/reranker/`)를 임베딩 서버의 `/data`에 붙인다. 폐쇄망에서 폴더를 통째로 복사해 옮기기 위해서다.
- [거절] 모델을 이름 있는 Docker 볼륨에 두는 것. 폐쇄망 설치가 볼륨 안으로 파일을 넣는 별도 명령을 쳐야 한다.
- [정함] 차례는 `postgres`가 건강해지면 `migrate`가 돌고, `migrate`가 성공으로 끝나면 `server`와 `worker`가 뜨고, `server`가 건강해지면 `proxy`가 뜬다(`depends_on`의 `service_healthy`와 `service_completed_successfully`). 프록시가 서버의 건강을 기다리므로 `docker compose up -d --wait`가 돌아오면 프록시가 바로 답한다. 시제품에서 그 명령이 돌아온 직후 프록시의 `/health`는 502 없이 0.1초에 200이었다(프로브 `up` 단계). `worker`는 `embedding`이 건강해질 때도 기다린다. 대기열에 작업이 남은 채 다시 띄우면 작업자가 모델을 올리는 동안의 임베딩 서버에 닿지 못해, 그 시도가 작업의 재시도 횟수(기본 6번)를 쓰기 때문이다(`src/rag_engine/app/job_failure.py`와 `retry_policy.py`를 읽었다). 시제품 compose의 `worker`는 `migrate`만 기다렸는데, `up --wait`는 헬스체크가 있는 임베딩 서버가 건강해질 때까지 어차피 기다리므로 이 차이가 위 0.1초에 닿지 않는다고 본다(어림). Docker 데몬이 다시 켜질 때는 compose가 아니라 재시작 정책이 컨테이너를 띄워 이 차례가 지켜지지 않을 수 있다(어림). 그때 먼저 뜬 작업자의 실패도 재시도 횟수를 쓴다. 횟수가 남은 작업은 기다림(30초에서 네 배씩) 뒤에 다시 돌지만, 마지막 시도였던 작업은 실패로 끝나 다시 넣기 전에는 돌아오지 않는다(`job_failure.py`를 읽었다). 또 모델을 처음 내려받는 시작이 띄우는 명령의 기다림(1800초)을 넘기면 작업자는 뜨지 않은 채 남으므로, 설치 안내는 그때 모델을 다 받은 뒤 같은 명령을 다시 치라고 적는다. 명세 검토가 손으로 봤다. 헬스체크가 늦게 서는 서비스를 다른 서비스가 기다리게 둔 작은 compose에서 `up -d --wait --wait-timeout 5`가 6초에 `timeout waiting for dependencies`로 끝났고, 기다리던 서비스는 40초 뒤에도 `created`로 남았으며, 같은 명령을 다시 치자 1초에 `running`이 됐다.
- [거절] agent-os처럼 프록시가 서버를 기다리지 않게 두는 것(그 저장소는 느리게 뜨는 위젯 때문에 그렇게 했다). 몇 초 만에 뜨는 뒷단과 함께 띄웠을 때 기다리지 않으면 `up --wait` 뒤에도 502가 5.4초 이어졌고, 건강해질 때까지 기다리면 502가 없었다(프로브 `sse` 단계 앞의 두 줄).
- [정함] 모든 서비스(마이그레이션 빼고)의 재시작 정책은 `unless-stopped`다. 시제품에서 서버 프로세스를 죽이자 컨테이너가 다시 떠 5.1초 뒤 프록시가 200을 냈다(프로브 `recover` 단계).
- [정함] compose의 기본 네트워크는 IPv6를 끈다(`enable_ipv6: false`). 프록시가 뒷단의 이름을 풀 때 IPv4 주소만 받게 하려는 것이고, 프록시 설정의 `ipv6=off`와 짝이다.
- [정함] 443은 `0.0.0.0:443:8443`으로 연다(agent-os의 단독 compose와 같은 꼴). 프록시 컨테이너 안에서는 root가 아니어서 1024 아래 포트를 열 수 없으므로 8443에서 받는다.
- [정함] 임베딩 서버와 리랭커는 TEI의 CPU 이미지(`cpu-1.9.4`)로 띄운다. 보증하는 환경이 GPU 없는 리눅스 x86-64 VM이고(아래 설치 안내 절), 이 기능의 수락이 말하는 깨끗한 VM과 단독 compose 시험이 도는 GitHub 러너에도 GPU가 없다. GPU 이미지로 바꾸는 설치는 이 기능이 시험하지 않고 설치 안내도 다루지 않는다.
- [이력] ADR 0010 본문의 "배포 대상만 GPU 이미지를 쓴다"가 위와 어긋나므로, ADR 0010에 이력 "단독 compose의 임베딩 서버와 리랭커는 CPU 이미지다"를 더하고 그 문장 뒤에 포인터를 단다.
- [정함] 임베딩 서버는 root가 아닌 사용자(uid·gid 10001)로 돌고, 루트 파일 시스템은 읽기 전용이며 `/tmp`만 tmpfs로 받는다. 모델 폴더는 쓸 수 있게 붙인다(첫 시작이 내려받는다). TEI 이미지의 기본 사용자는 root다. 시제품에서 모델이 든 볼륨을 붙이고 uid 10001로, 루트와 모델 볼륨을 모두 읽기 전용으로 띄우자 32초에 건강해졌다(프로브 `offline` 단계). 빈 볼륨을 uid 10001이 가질 때는 같은 꼴의 첫 시작이 모델을 내려받아(볼륨의 크기가 `du -sh`로 2.2GiB) 409초에 건강해졌고, 받은 파일은 uid 10001의 것이며 받은 리비전(모델 저장소의 커밋 해시. 같은 모델 이름이라도 리비전이 다르면 파일이 다르다)은 `offline` 단계에서 쓴 것과 같았다(프로브 `download` 단계). 리랭커(`BAAI/bge-reranker-v2-m3`, ADR 0010)도 같은 꼴로 띄운다. uid 10001, 읽기 전용 루트, `/tmp`의 tmpfs, 쓸 수 있게 붙인 `models/reranker/`, 아래의 30분 시작 유예다. 리랭커는 이 명세의 프로브가 띄우지 않았다.
- [정함] 그래서 설치 안내는 첫 시작 전에 모델 폴더를 만들어 uid 10001에게 주는 명령(`mkdir -p models/embedding`과 `sudo chown -R 10001:10001 models`)을 적는다. root가 가진 빈 폴더에서는 uid 10001의 임베딩 서버가 `Permission denied`로 내려받지 못해 `up --wait`가 6초 만에 종료 1로 돌아왔다(프로브 `download` 단계의 대조군). 그 서비스에는 재시작 정책이 있어 컨테이너는 멈춰 있지 않고 다시 뜨기를 되풀이할 것으로 본다(어림. 프로브 출력은 재시작 횟수를 적지 않는다). 명세 검토가 재시작 정책 없이 같은 꼴로 손으로 띄우니 3초에 종료 1이었다. 폴더를 만드는 명령까지 적는 것은 묶음에 `models/embedding/`이 없기 때문이다. git과 묶음을 짓는 도구는 빈 폴더를 담지 않고, 없는 바인드 원천 폴더는 Docker 데몬이 root의 것으로 만든다. 명세 검토가 손으로 봤다. `models`를 uid 10001에게 준 뒤 없는 `models/embedding`을 원천으로 얹어 uid 10001로 띄우자, 데몬이 그 폴더를 `0:0`, `755`로 만들었고 컨테이너의 쓰기가 `Permission denied`였다(Docker Desktop의 리눅스 VM 안 경로로 봤다).
- [정함] 첫 시작이 모델을 내려받는 시간을 견디게, 임베딩 서버와 리랭커의 헬스체크는 시작 유예(`start_period`)를 30분으로 두고, 설치 안내의 띄우는 명령은 `docker compose up -d --wait --wait-timeout 1800`이다. 개발 PC의 네트워크에서 내려받기가 409초였고, 느린 네트워크에서는 그보다 길다. 모델이 이미 든 두 번째 시작부터는 건강해지는 대로 명령이 돌아오므로 긴 기다림 시간이 손해가 아니다.
- [정함] 임베딩 서버가 올릴 모델의 리비전은 고정하지 않고, `HF_HUB_OFFLINE`도 두지 않는다. 모델 폴더에 모델이 들어 있으면 바깥으로 나가는 길이 없는 네트워크에서도 `HF_HUB_OFFLINE` 없이 떴다(프로브 `offline` 단계, 43초와 32초). 설치 안내는 시험한 리비전(`BAAI/bge-m3`의 `5617a9f61b028005a4858fdac845db406aefb181`)과, 받은 리비전을 모델 폴더의 `refs/main`에서 읽는 명령을 적는다.
- [거절] 리비전을 고정하는 것(`--revision`). TEI cpu-1.9.4는 리비전을 받으면 `HF_HUB_OFFLINE=1`이 있어도 허브에 이름을 물으러 나가, 바깥으로 나가는 길이 없는 네트워크에서는 폴더에 같은 리비전이 있어도 3초 만에 이름 풀기 실패로 멈췄고, 폴더에 없는 리비전을 준 대조군도 2~3초에 같은 오류로 멈췄다(프로브 `offline` 단계, `run_offline_out.txt`). 프로브의 모델 볼륨에 든 리비전(`refs/main`)이 고정한 값과 같다는 것은 프로브가 읽지 않고 이 세션이 그 볼륨을 읽기 전용으로 붙인 컨테이너에서 `refs/main`을 읽어 손으로 봤다. 고정하면 폐쇄망 설치와 인터넷이 잠깐 끊긴 동안의 재시작이 깨진다.
- [정함] 임베딩 서버의 로그 설정은 따로 두지 않는다. 수집과 검색을 지난 뒤 TEI 로그 26줄에서 질의와 문서의 글(한글 그대로와 유니코드 이스케이프 꼴 모두)이 하나도 나오지 않았고, 요청 줄은 시간만 적었다(프로브 `checks` 단계). 프로브가 본 것은 성공한 요청의 로그뿐이었고, 거절된 요청의 로그는 명세 검토가 손으로 봤다. 아래의 인자로 띄운 TEI에 표지 글을 담은 꼴이 틀린 본문(모르는 값, 틀린 타입)을 보내자 422였고, 빈 입력은 400이었다. 그 뒤 로그 25줄에 표지는 한글 그대로든 이스케이프 꼴이든 0번이었다. 422의 응답 본문은 받은 값을 되돌려 주지만, 그 본문은 요청을 보낸 쪽만 받고, 서버의 임베딩 어댑터는 거절된 요청의 오류에 상태 코드만 싣는다(`src/rag_engine/adapters/tei.py`의 응답 처리를 읽었다). 토큰 상한을 넘는 글로는 거절이 나지 않는다. `--max-batch-tokens 4096`이면 TEI가 기동할 때 상한을 넘는 입력을 자동으로 자른다고 경고하고, 상한을 넘는 글도 `/v1/embeddings`와 `/embed` 모두 200이었다(같은 손 확인). 단독 compose 시험은 꼴이 틀린 본문으로 거절된 뒤의 로그를 다시 본다(Testing Decisions). core 티켓 세션이 넘긴 물음(기능 계획)의 답이다.
- [정함] 메모리 예산은 기준 32GB, 최소 16GB로 설치 안내에 적는다(core가 넘긴 것). 임베딩 서버가 기동 직후 약 6.6GiB, 검색 부하 중 최대 7497MiB를 썼다(`compose.eval.yml`의 머리 주석). 그 수치는 `--max-batch-tokens 4096`으로 띄운 것이므로, 단독 compose의 임베딩 서버도 `compose.eval.yml`과 같은 인자(`--model-id BAAI/bge-m3 --port 80 --max-batch-tokens 4096`)로 띄운다. TEI 기본값 16384에서는 컨테이너 하나가 13.25GiB를 썼다(같은 주석. `docker stats`로 손으로 본 값이다). 리랭커의 메모리와 인자는 이 명세가 재지 않았고, 리랭커를 단독 compose에 싣는 티켓이 정해 설치 안내의 리랭커 절에 적는다.
- [정함] 프록시 컨테이너는 uid 101(nginx 이미지의 `nginx` 사용자)로 돌고, 루트를 읽기 전용으로, 모든 리눅스 권한을 떼고(`cap_drop: ALL`), 권한 상승을 막고(`no-new-privileges`), `/tmp`를 tmpfs로, init 프로세스를 켠다. 설정 폴더 `proxy/`와 인증서 폴더 `tls/`는 폴더째 읽기 전용으로 얹는다. 모두 agent-os의 단독 compose와 같다. 주 설정은 pid 파일과 임시 폴더를 `/tmp` 아래로 옮긴다(시제품 `proxy/nginx.conf`).

### 프록시

- [넘겨받음] 프록시가 TLS를 끝내고 MCP 경로, 수집 API, 관리 API를 경로로 갈라 서버에 넘긴다. 서버는 TLS를 하지 않는다. 인증서는 운영자가 파일로 두고, 시험 삼아 띄울 때 쓸 자체 서명 인증서를 만드는 명령을 설치 안내에 적는다(ADR 0020, ADR 0056 "TLS 인증서").
- [정함] 서버에 넘기는 경로는 넷이다. `= /mcp`(정확히 그 경로), `/api/v1/ingest/`와 `/api/v1/admin/`(그 아래 전부), `= /health`다. 나머지는 프록시가 404로 답한다. 빗금 없는 `/api/v1/ingest`와 `/api/v1/admin`도 그 경로 하나만 받는 설정(정확 일치 location, `= /api/v1/ingest`와 `= /api/v1/admin`. location은 nginx가 요청의 경로로 고르는 설정 덩어리다)으로 404를 준다. 빗금으로 끝나는 경로로 시작하는 요청을 모두 받는 설정(접두 location)만 두면 nginx가 빗금 없는 같은 경로에 빗금을 붙인 주소로 301을 돌려주는데, 그 주소에 컨테이너 안의 포트가 붙는다. 시제품과 같은 주 설정으로 띄운 nginx에서 `/api/v1/ingest`는 301에 `Location: http://rag.example.test:8443/api/v1/ingest/`였고, 정확 일치 404를 더하자 404가 되고 `/api/v1/ingest/documents`는 그대로 뒷단으로 넘어갔다(손으로 봤다. 시제품의 `proxy/nginx.conf`를 주 설정으로 얹어 `docker run --user 101:101 --tmpfs /tmp … nginx -c /etc/rag-engine/nginx.conf`로 띄운 nginx에, TLS 없이 `location /api/v1/ingest/`만 둔 사이트와 그 앞에 `location = /api/v1/ingest { return 404; }`를 더한 사이트를 두고, 두 경로에 `Host: rag.example.test`로 GET을 보냈다. 뒷단 자리에는 듣는 것이 없어 넘어간 요청은 502였다. 밖에서는 8443이 열려 있지 않다). 시제품에서 `/`, `/docs`, `/openapi.json`, `/redoc`, `/mcp/`, `/api/v1/other`가 모두 프록시의 404였다(프로브 `checks` 단계). API 문서 화면과 그 원본은 인증 없이 관리 API 전체의 모양을 보이므로 밖에 열지 않는다. API 문서의 판 칸은 서버 컨테이너 안에서 본다.
- [정함] TLS는 1.2와 1.3만 받는다(`ssl_protocols TLSv1.2 TLSv1.3`, agent-os와 같다). 암호 목록은 nginx 기본값을 쓴다. 시제품에서 1.0과 1.1로만 손을 내밀면 거부됐고 1.2와 1.3은 맺었다(프로브 `checks` 단계).
- [정함] 응답에는 HSTS 머리(`Strict-Transport-Security: max-age=31536000`. 브라우저에게 이 서버 이름으로는 한 해 동안 HTTPS로만 접속하라고 알린다)를 붙인다(agent-os와 같다). 80을 열지 않으므로 HTTP에서 HTTPS로 넘기는 응답은 없다.
- [사용자 선택] 접근 로그는 시각, 보낸 주소, 메서드, 경로(`$uri`, nginx가 정규화한 경로이고 질의 문자열이 없다), 상태 코드, 걸린 시간만 남긴다. 시제품의 로그 꼴에는 보낸 바이트(`$body_bytes_sent`)가 더 있었는데, 사용자가 고른 칸에 없어 뺀다. 그 칸은 질의 문자열과 상관이 없어 아래 측정은 그대로다. 요청을 처리하다 난 오류의 로그 줄은 nginx가 요청 줄을 질의 문자열째 싣기 때문에, 사이트 설정의 오류 로그는 버린다(`error_log /dev/null`). 시제품의 `site.conf`는 `crit` 이상만 남기는 설정으로 쟀는데, `crit` 줄(임시 파일 쓰기 실패 같은 것)에도 요청 줄이 실릴 수 있어 끈다. 그 줄은 재지 않았다. 프로세스의 일(시작, 설정 오류)은 주 설정의 오류 로그(`notice`)가 남긴다.
- [정함] 위 로그 꼴의 근거는 둘이다. 문서 키를 질의 문자열에 실은 GET을 보냈을 때, 이 꼴은 접근 로그에 그 키를 남기지 않았고 nginx 기본값은 남겼다. 서버가 멈춘 동안 같은 요청을 보냈을 때, 이 꼴은 오류 로그에도 그 키가 든 줄이 0개였고 nginx 기본값은 2개(그 가운데 `[error]` 줄 1개)였다(프로브 `checks`와 `recover` 단계). 다만 그 요청에 이 꼴은 504, nginx 기본값은 502로 답해 두 설정이 같은 오류를 로그에 남긴 것을 견준 것은 아니다. 제품이 사이트의 오류 로그를 버리는 결정(위 사용자 선택)은 이 비교에 기대지 않는다. 버린 로그에는 어느 오류에서도 줄이 없다. 문서 키가 질의 문자열에 실리는 경로는 둘이다. 관리 API의 문서 찾기(`GET /api/v1/admin/documents?key=`)와 수집 API의 문서 지우기(`DELETE /api/v1/ingest/documents?key=`)다.
- [거절] nginx 기본 오류 로그(`error` 이상)를 사이트에서도 쓰는 것. 서버가 멈춘 동안 문서 키가 오류 로그에 남는다(원칙 V).
- [정함] 서버에 넘기는 머리는 `Host`(받은 이름 그대로, `$host`), `X-Forwarded-For`(보낸 주소로 덮어쓴다), `X-Forwarded-Proto`(`https`)다. `$host`는 받은 머리에서 호스트 이름만 담는다(nginx 문서의 "host name". 포트를 붙인 `Host`로는 재지 않았다). 포트가 붙어 와도 서버의 허용 호스트 판정은 이름 그대로와 `이름:*`의 두 꼴을 모두 받으므로(ADR 0014) 판정이 갈리지 않는다. 시제품에서 허용한 이름의 POST `/mcp`는 200, 다른 이름은 421, 토큰이 없으면 401이었다(프로브 `checks` 단계).
- [정함] 서버는 `X-Forwarded-*`를 믿지 않는다. uvicorn은 믿을 프록시 주소를 환경 변수 `FORWARDED_ALLOW_IPS`로 받고, 주지 않으면 `127.0.0.1,::1`(같은 컨테이너 안의 주소)만 믿는다(uvicorn 0.54.0 `config.py`의 기본값). 단독 compose와 `.env.example`은 그 변수를 주지 않으므로, uvicorn은 다른 컨테이너인 프록시의 주소에서 온 그 머리를 무시한다. 지금 `src`에는 그 머리를 읽는 코드가 없고(ADR 0020 "명세가 재거나 정하는 것"), 머리를 넘기는 것은 관리자 페이지 같은 뒤의 기능이 보낸 주소나 원래의 scheme이 필요할 때를 위해서다. 그 기능이 머리를 믿게 할 때 믿을 주소를 정한다.
- [정함] 프록시는 올리는 본문의 크기를 막지 않고 모으지도 않는다(`client_max_body_size 0`, `proxy_request_buffering off`). 크기 상한은 서버 설정 `RAG_MAX_UPLOAD_MB` 하나가 판정한다. 시제품에서 20MB 올리기가 202였고, nginx 기본값(상한 1MB)은 2MB에서 413이었다(프로브 `checks` 단계).
- [정함] `/mcp`에서는 응답을 모으지 않고 온 대로 넘긴다(`proxy_buffering off`). 1초 간격으로 사건 다섯을 보내는 가짜 뒷단을 두고 재니, 이 설정은 `X-Accel-Buffering: no` 머리가 있든 없든 사건을 1초 간격으로 넘겼고, nginx 기본값은 그 머리가 있으면 온 대로, 없으면 다섯을 모아 4초 뒤에 한꺼번에 넘겼다(프로브 `sse` 단계). 지금의 서버는 이어 보내는 응답에 그 머리를 싣는다(mcp 2.3.0의 `mcp/server/_streamable_http_modern.py` 153줄과 sse-starlette 3.7.0의 `sse_starlette/sse.py` 333줄을 읽었다). nginx는 `X-Accel-*` 머리를 클라이언트에 넘기지 않아, 프록시 바깥에서 받은 `/mcp` 응답에는 그 머리가 없었다(프로브 `checks` 단계). 그러니 기본값으로도 지금은 모이지 않지만, SDK가 그 머리를 빼면 조용히 모이게 되므로 설정이 서버의 머리에 기대지 않게 한다. ADR 0020이 명세에 넘긴 측정(이어 보내는 응답이 프록시에서 묶이는지)의 답이다.
- [정함] 프록시는 뒷단의 이름을 Docker 내장 DNS(`127.0.0.11`)에서 5초마다 다시 푼다(`resolver 127.0.0.11 valid=5s ipv6=off`와 `upstream`의 `zone`과 `server server:8000 resolve`. nginx 1.27.3부터 무료판이 지원한다). 서버 컨테이너를 지우고 다시 만들어 주소가 바뀌어도(옛 주소는 다른 컨테이너가 차지하게 했다), 서버가 건강해진 때부터 502 없이 바로 200이었다. 대조군(이름을 시작할 때만 푸는 설정)은 같은 조건에서 60초 안에 회복하지 못했다(프로브 `recover` 단계).
- [정함] 서버를 다시 시작하는 동안에는 502가 난다. 프록시와 서버를 함께 다시 시작하면 9.3초, 멈춘 서버를 다시 켜면 6.2초였다(프로브 `recover` 단계). 설치 안내는 서버를 다시 시작하는 동안 약 10초 오류가 난다고 적는다. 또 서버에 닿지 못한 요청은 프록시 로그에 502·504 상태 코드로만 남고 까닭(연결 거부 같은 것)이 없으므로(위 로그의 사용자 선택), 까닭은 서버의 로그(`docker compose logs server`)와 Docker의 컨테이너 상태에서 찾으라고 적는다.
- [정함] 프록시가 뒷단의 답을 기다리는 시간은 nginx 기본값 60초(`proxy_read_timeout`) 그대로 둔다. 설치 안내는 검색의 시간 제한을 60초 넘게 올리는 설치(리랭커를 켜고 후보 수를 크게 올린 설치)가 이 값도 함께 올려야 한다고 적는다. 그때 무엇이 먼저 끊기는지는 재지 않은 어림이다.
- [정함] 설치 안내는 프록시 설정을 고친 뒤 `docker compose exec proxy nginx -t -c <주 설정>`으로 확인하고 `docker compose exec proxy nginx -s reload -c <주 설정>`으로 다시 읽게 한다. `<주 설정>`은 compose의 `proxy` 서비스가 `command`의 `-c`로 준 경로이고(시제품은 `/etc/rag-engine/nginx.conf`), 설정 폴더를 얹는 자리는 단독 compose를 짓는 티켓이 정한다. `-c`가 없으면 두 명령은 이미지의 기본 설정(`/etc/nginx/nginx.conf`)을 읽는다. 시제품과 같은 주 설정으로 uid 101로 띄운 nginx에서 `-c` 없는 `nginx -t`는 그 기본 설정을 검사하다 pid 자리(`/run/nginx.pid`)를 열지 못해 종료 1이었고, `-c` 없는 `nginx -s reload`도 같은 파일이 없어 종료 1이었다. `-c`를 주면 둘 다 지났고 nginx 기록에 다시 읽은 줄이 남았다(손으로 봤다. 위 301 확인과 같은 `docker run`으로 포트 없이 띄운 컨테이너에서 `docker exec <컨테이너> nginx -t`와 `docker exec <컨테이너> nginx -s reload`를 치고, 같은 둘에 `-c /etc/rag-engine/nginx.conf`를 주어 다시 쳤다). agent-os의 일지도 두 명령에 `-c`를 줘야 한다고 적었다(`2026-11-16-1447-standalone-compose-runs-real-images.md`의 "10이 받을 것").
- [정함] 인증서는 `tls/fullchain.pem`과 `tls/privkey.pem`이다(agent-os 설치 안내와 같은 이름이고, 설계 인터뷰에서 사용자가 고른 선택지의 설명이 이 이름을 들었다). 프록시가 uid 101로 돌아 키 파일을 읽어야 하므로, 설치 안내는 키 파일을 `root:101`, `0640`으로 두라고 적는다(agent-os 설치 안내와 같다).

### 배포 파일 묶음

- [정함] 묶음의 이름은 `rag-engine-<번호>.tar.gz`이고 GitHub 릴리스에 붙는다. ADR 0020 "옮기는 방식"은 묶음의 이름이 이 저장소의 값으로 바꿀 것이라고만 적고, 값은 이 명세가 agent-os의 꼴(ADR 0056 "판마다 나오는 것")에 이 저장소의 이름을 넣어 정했다.
- [정함] 묶음에 드는 것은 `compose.yaml`, `.env.example`, `proxy/nginx.conf`, `proxy/site.conf`, `tls/README.txt`(어떤 파일을 어떤 권한으로 두는지), `models/README.txt`(첫 시작이 내려받는다는 것과 폐쇄망에서 옮기는 법, 시험한 리비전), `README.md`(설치 안내)다. 묶음을 짓는 도구가 `deploy/standalone/`을 그대로 담고 `.env.example`의 표지만 채운다.
- [정함] PR 서식의 "새 환경 변수는 `.env.example`에 있다" 줄은 `deploy/standalone/.env.example`을 가리키게 고친다. 지금 저장소에는 `.env.example`이 없어 그 줄이 가리키는 파일이 없다. 운영자가 `.env`에 넣을 설정을 더한 PR은 그 파일에 주석 처리한 예시 줄을 더한다.
- [정함] 쓰는 곳이 없는 설정(`RAG_DELETED_RETENTION_DAYS`)은 `.env.example`에 넣지 않는다. 그 설정을 쓰는 기능이 넣는다.

### 설치 안내

- [넘겨받음] 보증하는 환경은 ADR 0056 "보증하는 환경"을 따른다. 리눅스 x86-64 VM의 Docker Engine과 Docker Compose다.
- [정함] 최소 판은 agent-os 설치 안내와 같은 Docker Engine 28.3.3, Docker Compose 2.20.2다. 두 제품을 한 기계에 두는 운영자가 판을 하나로 맞추게 하려는 것이다. Compose의 그 판부터 헬스체크의 `start_interval`을 받는다는 것과 Engine의 그 판을 고른 까닭(루프백에만 연 포트가 바깥에서 닿던 문제를 고친 판)은 agent-os 설치 안내가 적는다. 이 저장소의 단독 compose에는 루프백에만 여는 포트가 없다. 이 명세의 측정은 Engine 29.9.2와 Compose 5.6.1에서만 했고 최소 판에서는 재지 않았다. 이 저장소의 compose는 agent-os의 compose에 없는 조합을 쓴다. 한 번 돌고 끝나는 서비스(`migrate`)를 `service_completed_successfully`로 기다리게 두고 `up --wait`로 띄운다(agent-os의 compose에는 `service_completed_successfully`가 없다. 명세 검토가 grep으로 봤다). Compose 2.20.2가 이 조합에서 끝난 `migrate`를 실패로 보지 않는지와 그 판에 `--wait-timeout`이 있는지 모르므로, 단독 compose를 짓는 티켓이 그 판으로 띄워 본다. 안 되면 최소 판을 바꿀지 사용자에게 묻는다.
- [정함] 설치 안내는 묶음 안의 `README.md` 하나이고, 절은 다음 차례다. 보증하는 환경과 메모리, 묶음 풀기, `.env` 채우기, 인증서, 모델 폴더, 띄우기(`docker compose up -d --wait --wait-timeout 1800`), 첫 인증 토큰, 문서 넣기, MCP 클라이언트로 접속하기, 서비스와 이미지의 대응표, 리랭커 켜기, 프록시 설정 고치기, 볼륨과 지우면 안 되는 것, 폐쇄망 설치, Docker Hub 받기 제한, 업그레이드다. agent-os 설치 안내의 절을 이 저장소의 배치에 맞게 고친 것이다.
- [정함] 자체 서명 인증서를 만드는 명령은 프로브가 쓴 꼴(`openssl req -x509 -newkey rsa:2048 -nodes`, 서버 이름과 `localhost`, `127.0.0.1`을 대체 이름에 넣는다)이고, 유효 기간은 안내가 정한다. 자체 서명 인증서를 쓰면 MCP 클라이언트가 그 인증서를 믿게 해야 하고, 그 방법은 클라이언트마다 달라 안내가 적지 않는다(원칙 III).
- [정함] 첫 인증 토큰은 `docker compose exec server rag-engine bootstrap-token`으로 낸다. 문서 폴더는 `docker compose run --rm -v <폴더>:/import:ro worker rag-engine ingest /import --wait`로 넣는다. 둘 다 프로브의 `accept` 단계가 친 꼴이고, 그 단계에서 표본 문서가 들어가 검색됐다.
- [정함] MCP 클라이언트는 `https://<RAG_ALLOWED_HOSTS의 이름>/mcp`에 `Authorization: Bearer <토큰>` 머리로 접속한다. 프로브의 `accept` 단계가 공식 MCP SDK 클라이언트로 그렇게 접속해 도구 셋(`get_document`, `list_knowledge_bases`, `search`)을 보고 검색했다.
- [정함] 리랭커를 켜는 절은 넷을 적는다. 프로필로 띄우는 명령(`docker compose --profile reranker up -d --wait --wait-timeout 1800`. 리랭커도 첫 시작에 모델을 내려받는다), 모델 폴더 `models/reranker/`를 만들어 uid 10001에게 주는 명령, `.env`에 적는 `RAG_DEFAULT_RERANKER_URL=http://reranker:80`, 그리고 마이그레이션을 다시 돌리는 것이다. 기본 끝점의 주소는 데이터베이스의 레코드에 들어 있어 `migrate`가 다시 돌아야 바뀐다. 켜는 설치의 후보 수와 검색 시간 제한 안내는 ADR 0010 이력 2026-11-17이 적은 값을 옮긴다(기능 계획이 넘긴 것).
- [정함] 폐쇄망 설치의 절은 ADR 0056 "인터넷이 막힌 곳"과 agent-os 설치 안내의 꼴을 따른다. 인터넷이 되는 기계에서 이미지 다섯(서버, 작업자, nginx, PostgreSQL, TEI)을 받아 `docker save`로 파일 하나에 담고, 폐쇄망 기계에서 `docker load`로 싣는다. digest로 고정한 바깥 이미지는 실은 뒤 digest 참조가 남지 않을 수 있어, 안내는 실은 이미지에 로컬 이름을 다시 붙이고 `compose.override.yaml`로 그 이름을 쓰게 하는 길과, 받은 기계와 실은 기계에서 이미지 ID를 대조하는 명령을 적는다. 모델은 인터넷이 되는 기계에서 한 번 띄워 받은 `models/` 폴더를 통째로 옮긴다. 옮기는 것은 그 기계에서 설치 안내의 띄우는 명령(`docker compose up -d --wait --wait-timeout 1800`)이 성공으로 돌아와 임베딩 서버가 건강해진 뒤다. 내려받다 끊긴 폴더를 옮기면 폐쇄망에서 임베딩 서버가 빠진 파일을 받으러 나가다 이름 풀기 실패로 멈춰, 네트워크 문제처럼 보인다(빠진 파일을 받으러 나간다는 것은 `offline` 단계의 리비전 고정 실패와 같은 꼴로 미룬 어림이다). 안내의 명령은 그 티켓이 실제로 쳐 보고 적는다. 실은 뒤 digest 참조가 남는지도 그 티켓이 `docker save`와 `docker load` 뒤의 `RepoDigests`로 본다. 이 명세는 그 명령을 치지 않았다.
- [정함] Docker Hub 받기 제한(로그인하지 않은 받기의 시간당 횟수)에 걸리면 할 일(잠시 뒤 다시, 또는 `docker login`)을 적는다(agent-os 설치 안내와 같다).
- [정함] 업그레이드 절은 짧게 둔다. 새 릴리스 노트의 "업그레이드할 때 할 일"을 먼저 읽고, 새 묶음의 `compose.yaml`로 바꾸고 있던 `proxy/` 폴더는 두고 그 안을 비운 뒤 새 묶음의 `proxy/` 안 파일을 제자리로 복사하되(`find proxy -mindepth 1 -delete`와 `cp -r <새 묶음>/proxy/. proxy/`. 비우지 않으면 새 릴리스가 지우거나 이름을 바꾼 파일이 남는다), `.env`, `tls/`, `models/`, 폐쇄망 설치가 만든 `compose.override.yaml`은 남기고, `.env`의 `RAG_ENGINE_VERSION`을 새 번호로 바꾸고, `docker compose stop server worker`로 옛 서버와 작업자를 먼저 멈춘 뒤 `docker compose up -d --wait`를 친다. 바꾸기 전에 옛 `compose.yaml`과 `proxy/`를 다른 이름으로 복사해 둔다. 폴더째 옮기거나 새 폴더로 바꾸지 않는 것은, 도는 프록시가 처음 얹은 폴더를 계속 읽기 때문이다. 명세 검토가 손으로 봤다. 폴더째 읽기 전용으로 얹은 컨테이너에서, 폴더 안 파일을 제자리에서 덮어쓰면 컨테이너가 새 내용을 봤고, 폴더를 다른 이름으로 옮긴 뒤 새 폴더를 두면 컨테이너는 옛 내용을 계속 봤다(Docker Desktop의 리눅스 VM 안 경로를 `docker run -v <폴더>:<자리>:ro`로 얹었다). 폐쇄망 설치는 새 릴리스의 이미지도 폐쇄망 설치 절대로 옮겨 싣고, `compose.override.yaml`이 가리키는 로컬 이름을 새 묶음의 `compose.yaml`이 고정한 판에 맞춘다. 새 `proxy/`는 프록시가 다시 읽어야 먹으므로 `up` 뒤에 위 프록시 절의 `nginx -s reload -c <주 설정>`을 친다. compose는 얹은 파일만 바뀐 서비스를 다시 만들지 않는다고 본다(어림). 폴더 안을 비우고 다시 채운 파일을 도는 프록시가 보는지는 재지 않았다(어림. 04가 업그레이드를 손으로 칠 때 본다). 먼저 멈추는 것은 새 `migrate`가 도는 동안과 그 뒤 서버를 다시 만들 때까지 옛 코드가 새 스키마에 닿는 틈을 없애려는 것이다(compose가 서비스를 다시 만드는 차례는 재지 않았다). 스키마를 바꾸는 단계는 리비전 전부가 한 트랜잭션 안에서 돌아(마이그레이션 환경 파일이 `context.begin_transaction()` 하나로 감싸고 alembic의 기본값 `transaction_per_migration=False`를 바꾸지 않는 것을 읽었다) 그 단계가 실패하면 스키마가 그대로 남고, 그때는 남겨 둔 옛 `compose.yaml`을 제자리에 돌리고 옛 `proxy/`의 파일을 같은 길(안을 비우고 제자리 복사)로 돌린 뒤 `RAG_ENGINE_VERSION`을 옛 번호로 되돌려 `docker compose up -d --wait --remove-orphans`로 다시 띄울 수 있다. `--remove-orphans`는 새 compose에만 있던 서비스를 걷는다. 새 compose 파일은 옛 이미지가 모르는 설정이나 서비스를 담을 수 있어 번호만 되돌리면 옛 이미지가 새 배치로 뜬다. 그 밖의 실패에서 되돌리는 법은 backup-upgrade가 정한다. 프록시 설정을 고쳐 썼으면 새 묶음의 것과 견주어 고친 값을 새 파일에 다시 넣고, `nginx -s reload` 전에 위 프록시 절의 `nginx -t -c <주 설정>`으로 확인한다. 백업과 복원, 되돌리기는 backup-upgrade가 정하고, 그 전에는 마이그레이션이 든 릴리스의 노트가 PostgreSQL 볼륨을 백업하라고 적는다.
- [정함] 설치 안내의 필수 낱말과 다른 파일(compose, 프록시 설정, bake 설정)과의 정합은 agent-os의 `tests/tools/test_deploy_guide.py`를 옮긴 시험이 본다. 그 시험은 안내의 띄우는 명령, 인증서를 만드는 명령, 모델 폴더의 명령이 단독 compose 시험이 치는 것과 같은지도 본다. 시험은 안내대로 밟는다고 정했는데(Testing Decisions), 두 쪽을 대는 기계 검사가 없으면 한쪽만 고친 PR이 지난다.

### 릴리스 워크플로

- [넘겨받음] 릴리스 워크플로는 agent-os의 `release.yml`을 옮긴다. main 푸시(출시 PR과 핫픽스 PR의 병합)에서만 돌고(agent-os의 그 파일에 수동 실행 계기가 없다. 실패한 릴리스는 실패한 잡을 다시 돌려 잇는다), 잡은 둘이며 둘 다 GitHub 환경 `release`를 쓴다. 첫 잡이 번호를 계산하고 이미지를 짓고 시험하고 취약점을 점검한 뒤 로그인해 커밋 태그로 올린다. 둘째 잡이 번호 태그를 붙이고 GitHub 릴리스를 만들고 버전 태그를 단다. 시험과 점검을 모두 마친 뒤에 로그인하므로 시험이 도는 동안 러너에 자격 파일이 없다(ADR 0020 "agent-os가 미룬 결정 셋").
- [넘겨받음] 올리는 짓기는 같은 빌더가 캐시로 다시 짓는 것이라, 첫 잡은 올린 뒤 시험한 이미지와 올린 이미지가 같은지 견준다(US42). 견주는 값은 이미지 설정 파일의 해시다. 설정 파일은 레이어 목록을 담아 레이어나 설정(agent-os의 주석은 ENV만 다른 이미지도 갈린다고 적는다)이 다르면 해시가 갈리므로, 짓는 날의 판을 받는 `tini`의 층이 달라진 경우도 이 대조가 잡는다(설정이 레이어 목록 `rootfs.diff_ids`를 담는다. agent-os 명세가 OCI image-spec의 `config.md`와 대 보았다고 적는다). 거꾸로 올리는 짓기가 캐시를 타지 못하면 내용이 같아도 해시가 갈려 릴리스가 멈출 수 있다(어림). agent-os는 러너에서 올리는 짓기가 캐시를 타 같은 해시가 나온 것을 봤다(agent-os 일지 `2026-11-16-2249`). 시험한 쪽은 취약점 점검을 위해 `docker save`로 받은 파일에서, 올린 쪽은 커밋 태그로 레지스트리에 물은 linux/amd64 매니페스트의 `config.digest`에서 읽고, 다르면 번호 태그와 GitHub 릴리스 앞에서 실패한다(agent-os `release.yml`의 "시험한 이미지와 올린 이미지 대조" 단계를 읽었다). 해시를 꺼내는 판정은 아래 도구 시험의 `tests/tools/test_release_ci.py`가 본다.
- [넘겨받음] 지난 릴리스 뒤로 제품 변경이 없으면 번호를 계산하지 않고 성공으로 끝난다. 출시 후보의 GitHub 릴리스에도 GitHub 릴리스의 `prerelease` 칸(GitHub가 정식이 아닌 게시물에 붙이는 표시)을 켜지 않는다. 다시 돌린 릴리스는 앞 실행이 남긴 초안을 지운 뒤 새 초안을 만든다(ADR 0020 "agent-os가 미룬 결정 셋", agent-os의 실패한 릴리스를 다시 돌리는 절차).
- [정함] 바꿀 값은 이미지 둘(bake 대상 `server`, `worker`), 이미지 이름, 묶음 이름, 시험 단계다. 시험 단계는 agent-os의 Playwright 대신 이 저장소의 단독 compose 시험을 방금 지어 러너에 실은 이미지로 돌린다(아래 Testing Decisions). node, pnpm, Playwright 단계는 옮기지 않는다.
- [정함] 시험 단계의 임베딩 모델은 `eval-fast` 잡과 같은 캐시 키(`eval-tei-<모델>-<TEI 판>`)로 복원만 한 폴더를 쓰고(저장은 `eval-fast`가 맡는다. `ci.yml`의 단독 compose 시험 잡도 같다), 캐시가 없으면 임베딩 서버의 첫 시작이 내려받는다. 복원한 뒤에는 캐시가 있든 없든 그 폴더를 만들어 uid 10001에게 준다(설치 안내의 `mkdir -p`와 `sudo chown -R 10001:10001`과 같다). `eval-fast`는 캐시를 러너 사용자의 것으로 돌려 둔 뒤 저장하고(`ci.yml`의 저장 스텝 앞 주석), 캐시가 없을 때 남는 빈 폴더는 러너 사용자나 root의 것이라, 그대로 넘기면 uid 10001의 임베딩 서버가 내려받지 못한다고 본다(어림. 위 "단독 compose"의 모델 폴더 항목이 root가 가진 빈 폴더로 잰 것과 같은 꼴이다). 모델이 다 든 폴더에서 임베딩 서버가 그 폴더에 쓰는지는 재지 않았다. 캐시가 이 저장소의 어느 브랜치에서 만들어졌느냐에 따라 main의 실행이 그 캐시를 읽지 못할 수 있는데, 그래도 시험은 내려받는 시간만큼 길어질 뿐 깨지지 않는다.
- [넘겨받음] 취약점 점검은 ADR 0056 "취약점 점검"을 따른다. Grype 0.121.3(이미지 안의 패키지를 알려진 취약점 목록과 맞대는 도구)과 Syft 1.57.1(이미지에 든 소프트웨어 목록을 만드는 도구)을 digest로 고정해 쓰고, 이 저장소가 짓는 이미지 둘마다 소프트웨어 목록과 점검 결과를 GitHub 릴리스에 붙인다. 막는 기준도 agent-os와 같다. 바깥 이미지는 점검 대상이 아니다(ADR 0020 "이미지와 계정").
- [넘겨받음] search-eval이 구현되면 운영 의존성에 Anthropic SDK와 그 전이 의존 셋이 더해져 소프트웨어 목록과 점검 대상이 그만큼 는다(기능 계획이 넘긴 것). 이 기능은 그 의존성을 따로 다루지 않는다.

### 릴리스 노트

- [넘겨받음] 릴리스 노트의 절 차례는 agent-os를 따른다. 경고, 소개, 기능 소개, 업그레이드할 때 할 일, 새 기능, 고친 것, 그 밖의 변경이다. 원고 폴더의 꼴(기능 단락은 빈 줄 없는 한 단락이고 줄바꿈을 뺀 400자 이하, 소개 글 이름은 `X.Y.Z.md`)과 기능의 마지막 티켓이 단락을 빠뜨리면 막는 판정도 agent-os 노트 검사를 따른다.
- [정함] agent-os 노트의 절 "올릴 때 할 일"을 이 저장소에서는 "업그레이드할 때 할 일"로 부른다. 용어집이 그 일의 이름을 업그레이드로 바꿨기 때문이다(ADR 0020 이력 2026-11-18). 원고 폴더의 이름 `upgrade/`는 그대로다.
- [정함] "업그레이드할 때 할 일" 다음에 "계약의 판" 절을 더한다. 릴리스 워크플로가 지은 서버 이미지에서 `rag-engine --version`을 돌려 둘째 줄부터를 그대로 옮긴다. 어느 클라이언트와 맞는지는 릴리스 번호가 아니라 계약의 판이 알리기 때문이다(ADR 0020 "번호는 따로 센다", 원칙 III과 VII). 번호 도구는 그 줄들을 인자로 받아 노트에 싣는다.
- [이력] ADR 0020에 이력 "명세가 PR 서식의 칸과 릴리스 노트의 절 이름을 업그레이드로 맞췄다"를 더하고, "올릴 때 운영자가 손댈 것의 기준"의 노트 절 이름을 적은 문장 뒤와 "옮기는 방식"의 PR 서식 칸 이름을 적은 문장 뒤에 포인터를 단다.
- [넘겨받음] 첫 릴리스 `0.1.0-rc.1`에는 core와 search-eval이 함께 실리고, 그 릴리스의 소개 글(`intro/0.1.0.md`)이 두 기능을 설명한다(ADR 0020 "규칙 전에 끝난 기능"). 마이그레이션 셋(`0001`~`0003`)은 업그레이드할 앞 릴리스가 없어 느낌표 없이 실린다.

### PR 서식, 노트 검사, 검사 러너

- [정함] PR 서식에 칸 "업그레이드할 때 운영자가 손댈 것"을 더한다. agent-os의 칸 "올릴 때 운영자가 손댈 것"을 옮기며 이름을 용어집에 맞춘 것이고(기능 계획이 넘긴 물음의 답), 이 저장소의 세 항목(마이그레이션, 재색인, 계약의 앞자리)을 따로 묻는다.
- [넘겨받음] 노트 검사는 agent-os의 것을 옮긴다. 판정 (가)(제목과 느낌표와 업그레이드 원고의 짝), (나)(기능 단락의 빠뜨림), (다)(원고의 꼴)이고, 커밋 전 검사 러너(`tools/run_checks.py`의 `CHECKS`)의 항목, `ci.yml`의 `ticket` 잡의 스텝, 제목을 고칠 때만 도는 PR 제목 워크플로(필수 검사가 아니다)에서 돈다. 이 저장소에서 더하는 것은 위의 마이그레이션 판정 하나다.
- [정함] 기능이 아닌 폴더(노트 검사가 기능 단락을 요구하지 않는 `.scratch/` 아래 폴더)는 agent-os와 같이 `harness`와 `retro-queue`다.
- [넘겨받음] 리뷰 봇 프롬프트에 변경과 제목의 접두를 맞대는 줄을 더하는 일은 `claude-code-review.yml`을 고치는 PR이라 다른 파일과 함께 싣지 않는다(ADR 0016 "전환의 차례" 2, agent-os의 명세). 그 파일을 바꾼 PR은 리뷰 봇이 건너뛰고, 기록 밖의 파일을 함께 실으면 실패한다.

### ci.yml

- [넘겨받음] 단독 compose 시험 잡을 더한다. base가 main인 PR과 main 푸시에서만 시험하고, 그 밖(dev로 가는 PR, dev 푸시, 수동 실행)에서는 시험 스텝을 건너뛴 채 성공으로 끝난다(ADR 0020 "느린 시험이 도는 자리"). 조건은 잡의 첫 스텝(gate)이 정하고, 잡 자체는 늘 돌아 필수 검사 `verify`가 그 잡을 기다린다(agent-os의 `e2e-standalone` 잡과 같다).
- [정함] `image` 잡은 bake 설정으로 이미지 둘을 `APP_VERSION=0.0.1-rc.1`로 짓고, 서버 이미지를 띄워 `/health`를 보고(지금처럼 가짜 데이터베이스 주소로), 두 이미지에서 `rag-engine --version`의 첫 줄이 `rag-engine 0.0.1-rc.1`인지 본다. 모든 PR에서 그대로 돈다(ADR 0020). 저장소의 `version`(`0.0.0`)과 다른 번호로 짓는 것은, 번호를 코드에 `0.0.0`으로 적은 구현도 `0.0.0`으로 지은 이미지에서는 이 확인을 지나기 때문이다. 다른 번호로 확인하는 단독 compose 시험은 dev로 가는 PR에서 돌지 않는다.
- [정함] `ci.yml` 82줄의 주석("버전 태그를 붙여 내는 것은 release-image"류)은 워크플로를 옮기는 티켓이 릴리스 워크플로를 가리키게 고친다(기능 계획이 넘긴 것).

### 규약 문서와 낡은 문장

- [넘겨받음] 운영 문서(`docs/constitution/operations.md`)의 두 절(릴리스 노트 원고, 릴리스가 나는 차례와 실패한 릴리스를 다시 돌리는 절차), `docs/constitution/tech.md`의 레지스트리와 점검 도구의 행, `next-session`의 `merge.md`에서 릴리스를 기다리는 절, `docs/agents/issue-tracker.md`의 기능 단락 문장, 구현 스킬(`.claude/skills/implement/SKILL.md`)의 느낌표 문장을 agent-os에서 옮긴다(ADR 0020 "옮기는 방식"). 하네스의 말(릴리스한다, 제품 변경, 릴리스 노트 원고)의 정의는 운영 문서가 적는다(ADR 0020 "용어").
- [넘겨받음] 운영 문서와 `tech.md`를 고치는 티켓은 헌법 판을 올린다. 절을 더하면 minor, 문구만 고치면 patch다(헌법 거버넌스, ADR 0020 Consequences "헌법").
- [정함] 병합 절차를 옮기는 티켓은 `merge.md` "출시 PR"의 전제 확인에 사람 몫이 끝났는지 보는 줄을 더한다. Docker Hub 저장소 둘, 접근 토큰, 환경 `release`와 그 안의 비밀 값 둘과 변수 하나가 있는지는 `gh api`로 환경의 비밀 값 이름과 변수를 읽어 본다(값은 읽지 않는다). 그 절의 "이 저장소에서는 아직 출시 PR을 열어 본 적이 없어"도 고친다. 출시 PR 32와 62가 병합된 뒤로 사실이 아니다(기능 계획이 넘긴 것).
- [정함] 낡은 문장과 옛 경로를 고친다. 루트 Dockerfile 1줄의 주석은 파일이 `deploy/images/`로 옮겨지며 사라지고, `docs/constitution/operations.md` 8줄의 "버전 태그를 붙여 내는 것은 release-image다"는 운영 문서의 두 절을 옮기는 티켓이 새 절을 가리키게 고치고, `README.md` 5줄과 37~44줄(이미지를 짓고 띄우는 법)은 설치 안내를 싣는 티켓이 묶음의 설치 안내를 가리키게 고친다.
- [정함] 루트의 Dockerfile을 가리키는 자리는 Dockerfile을 옮기는 티켓(첫째 묶음)이 같은 PR에서 새 경로로 고친다. `.coderabbit.yaml` 72줄의 경로 지시(`path: "Dockerfile"`. 리뷰 봇이 그 파일에 붙이는 검토 지침)와 `README.md` 88줄의 `Dockerfile`, `README.md` 40줄의 `docker build -t rag-engine .`, `tools/search_eval.py` 독스트링 19줄의 `.dockerignore`이다. 40줄의 명령은 루트에 Dockerfile이 없어지는 순간 깨지므로 설치 안내를 싣는 티켓까지 기다리지 않고 bake 설정으로 짓는 명령으로 바꾼다.

### 사람 몫

- [넘겨받음] 사람 몫은 Docker Hub의 저장소 둘(`njh6803/rag-engine-server`, `njh6803/rag-engine-worker`), 접근 토큰, 배포 브랜치를 main 하나로 좁힌 GitHub 환경 `release`와 그 안의 비밀 값 둘(`DOCKERHUB_TOKEN`, `RELEASE_GH_TOKEN`)과 변수 하나(`DOCKERHUB_NAMESPACE`), squash 병합의 제목을 PR 제목으로 쓰는 저장소 설정이다. `RELEASE_GH_TOKEN`은 이 저장소 하나에 Contents와 Workflows의 읽기·쓰기만 준 세분 토큰이다. 비밀 값은 사용자가 직접 넣고 세션에 넘기지 않는다(ADR 0020 Consequences "사람 몫").
- [넘겨받음] squash 제목 설정은 PR 제목 검사를 옮기는 티켓을 병합하기 전에, 나머지는 릴리스 워크플로를 처음 main에 싣는 출시 PR을 병합하기 전에 끝나 있어야 한다. 차례대로면 그 PR은 이 기능의 출시 PR이다.

### 티켓을 나눌 때 함께 둘 것

- [넘겨받음] 릴리스 워크플로가 설치 안내와 배포 파일 묶음보다 먼저 main에 닿지 않게 한다(ADR 0020 "명세가 재거나 정하는 것").
- [정함] 릴리스 워크플로와 릴리스 설정 파일은 마지막 티켓이 함께 싣는다. 설정 파일만 먼저 들어가도 워크플로가 없어 릴리스는 나지 않지만, 둘을 함께 두면 첫 릴리스가 나는 병합이 하나로 정해진다.
- [정함] 함께 둘 것은 다음 여섯 묶음이다. 첫째, 이미지 둘과 번호가 보이는 자리(Dockerfile을 옮기는 것, bake 설정, `image` 잡, `--version`, API 문서와 MCP 서버 정보의 번호, `python-multipart` 선언). 둘째, 번호와 노트와 묶음을 짓는 도구와 그 시험. 묶음을 짓는 도구는 agent-os에서 번호와 노트의 도구와 한 파일(`tools/release.py`)이고, 셋째 묶음의 시험이 그 도구로 묶음을 짓기 때문에 함께 앞에 둔다. 셋째, 단독 compose와 프록시 설정과 단독 compose 시험과 `ci.yml`의 그 잡. 시험이 띄울 것과 띄우는 시험이 함께 있어야 둘이 같은 PR에서 서로를 확인한다. 넷째, 설치 안내와 묶음 안의 설명 파일과 안내의 정합 시험. 다섯째, 노트 검사와 PR 제목 워크플로, PR 서식의 칸, 마이그레이션 head가 하나인지 보는 시험. 이 묶음을 병합하기 전에 squash 제목 설정이 바뀌어 있어야 한다. 여섯째, 운영 문서의 두 절과 병합 절차와 `tech.md`와 `issue-tracker.md`와 구현 스킬의 문장. 리뷰 봇 프롬프트의 줄은 따로 티켓 하나다. 원고 폴더는 미리 두지 않고 첫 원고가 들 때 생긴다.
- [정함] 차례는 여섯째가 맨 앞이다. 헌법을 바꾸는 티켓은 그 기능의 첫 티켓이며 다른 티켓을 막는다(`docs/agents/issue-tracker.md`. 티켓 세션이 2026-11-18에 사용자에게 물어 정했다). 그 뒤 첫째와 둘째 → 셋째 → 넷째이고(compose가 이미지와 묶음 도구를, 안내가 compose를 쓴다), 다섯째는 둘째 뒤에(제품 변경의 경로 목록과 제목 읽기를 둘째의 도구에서 가져다 쓴다), 리뷰 봇 프롬프트는 여섯째 뒤에(느낌표의 기준이 운영 문서에 선다) 돈다. 릴리스 워크플로와 그것이 부르는 판정 도구와 그 시험, 릴리스 설정 파일, 이 기능의 기능 단락 원고, 첫 릴리스의 소개 글(`intro/0.1.0.md`)을 싣는 티켓이 모두의 뒤다. 판정 도구의 저장소 상태 시험이 compose와 설치 안내의 대응표를 읽으므로 그 둘보다 앞에 들어가면 빨갛다.

## Testing Decisions

좋은 시험은 바깥에서 보이는 동작만 본다. 이미지에서는 운영자가 치는 명령과 받는 응답이고, 도구에서는 입력 파일과 git 이력을 넣었을 때 나오는 번호와 노트와 판정이다. 컨테이너 안의 파일 배치나 도구의 내부 함수는 보지 않는다.

- [정함] 새 이음매는 단독 compose 시험 하나다. 배포 파일 묶음과 이미지 둘을 입력으로 받아, 운영자가 설치 안내대로 하는 일을 그대로 밟는다. 이 기능의 수락(깨끗한 VM에서 띄워 표본 문서를 넣고 MCP 클라이언트로 검색하고, 밖으로 열린 포트가 하나)이 이 시험의 몸통이다. 프로브의 `run.py`가 이 시험의 원형이다.
- [사용자 선택] 단독 compose 시험은 진짜 임베딩 서버(묶음의 TEI 이미지)로 띄운다. 가짜 임베딩 서버로 바꾸면 compose의 `embedding` 서비스를 시험이 고쳐 써야 해, 운영자가 받는 compose와 시험하는 compose가 갈린다.
- [정함] 단독 compose 시험은 pytest로 쓰고 기본 수집에서 뺀다. `uv run pytest`가 그 폴더를 모으지 않고(건너뛴 시험으로 세지 않는다. 원칙 I), 경로를 주어 칠 때만 돈다. 이미지와 임베딩 서버를 띄우는 데 몇 분이 걸리고 포트 443이 비어 있어야 하기 때문이다. 시험은 시작할 때 443이 비었는지 보고, 차 있으면 실패하며 까닭을 적는다(agent-os의 시험과 같다).
- [정함] 시험은 이미지를 환경 변수 둘(이름공간과 번호)로 받는다. 둘 다 있으면 그 이미지를 쓰고(릴리스 워크플로가 방금 지은 이미지), 없으면 bake 설정으로 직접 짓는다(이름공간 `rag-engine-test`, 번호 `0.1.0-rc.1`). 배포 파일 묶음도 환경 변수로 받을 수 있다. 있으면 그 묶음을 풀고(릴리스 워크플로가 올릴 묶음, 첫 릴리스 뒤 GitHub 릴리스에서 받은 묶음), 없으면 묶음을 짓는 도구로 짓는다. 모델 폴더는 환경 변수로 받고, 없으면 설치 안내의 명령대로 묶음 안에 `models/embedding/`을 만들어 uid 10001에게 주고 임베딩 서버의 첫 시작이 내려받게 한다. 개발 PC(Windows)의 Docker Desktop은 바인드 마운트의 소유를 흉내 내므로 이 단계의 소유 문제는 리눅스에서만 드러나고, 리눅스에서의 첫 확인은 출시 PR의 GitHub 러너다(Further Notes).
- [정함] 시험이 밟는 차례는 다음과 같다. 받은 묶음이나 도구로 지은 묶음을 임시 폴더에 풀고, `.env`를 채우고(허용 호스트는 `localhost`와 시험용 이름, 비밀번호는 무작위 16진수), 설치 안내의 명령으로 자체 서명 인증서를 만들고, 모델 폴더를 두고, 설치 안내의 띄우는 명령과 같은 `docker compose up -d --wait --wait-timeout 1800`을 친다(빈 모델 폴더면 첫 시작이 모델을 내려받으므로 그 기다림 시간이 그대로 쓰인다). 그 뒤 첫 인증 토큰을 내고, 표본 문서(저장소의 시험 표본)를 넣고, 공식 MCP SDK 클라이언트가 443으로 접속해 도구 목록과 검색 결과를 본다. 끝나면 로그를 남기고 볼륨째 내린다.
- [정함] 시험이 확인하는 것은 다음과 같다. 호스트에 열린 포트가 프록시의 443 하나다. 서버, 작업자, 프록시, 임베딩 서버의 1번 프로세스가 root가 아니다. 두 이미지의 `rag-engine --version` 첫 줄과 MCP 서버 정보의 번호가 넘긴 번호와 같다. 허용하지 않은 이름의 `/mcp`는 421, 토큰 없는 `/mcp`는 401, 허용 목록 밖 경로(`/docs` 포함)와 빗금 없는 `/api/v1/ingest`·`/api/v1/admin`은 301 없이 404다. 설치 안내의 `nginx -t -c`와 `nginx -s reload -c`가 종료 코드 0이다. MCP 검색 결과에 표본 문서의 기대한 문장이 든다. 클라이언트가 보안 수준을 낮춰(`SECLEVEL=0`) TLS 1.1만 내밀어도 맺지 못한다. 낮추지 않으면 OpenSSL 3 클라이언트가 스스로 1.1을 거부해 서버의 설정과 상관없이 이 확인을 지난다(프로브 `run.py`도 낮춰서 쟀다). 질의 문자열에 표지를 실은 요청 뒤 프록시 로그에 그 표지가 없고, 서버를 멈춘 동안 같은 요청을 보낸 뒤에도 없다(US16. 프로브에서는 응답이 504였고 표지가 든 줄이 0개였다). 수집과 검색을 지난 뒤 임베딩 서버의 로그에 질의와 표본 문서의 글이 없고, 시험이 compose 네트워크 안에서 임베딩 서버에 표지 글을 담은 꼴이 틀린 본문을 보내 422로 거절당한 뒤에도 그 글이 없다(거절 때의 로그는 프로브가 재지 않았고 명세 검토가 손으로 봤다. 위 "단독 compose"의 로그 항목). PostgreSQL의 로그에도 질의와 표본 문서의 글이 없다(이 명세가 재지 않은 자리다). 2MB 올리기가 202다. 옛 주소를 다른 컨테이너가 차지하게 한 채 서버 컨테이너를 지우고 다시 만든 뒤, 서버가 건강해지면 프록시가 15초 안에 200을 낸다(agent-os의 시험과 같은 문턱. 프로브에서는 0초였다). 옛 주소가 비어 있으면 새 컨테이너가 같은 주소를 받을 수 있어, 이름을 시작할 때만 푸는 설정도 이 확인을 지난다(프로브의 대조군도 옛 주소를 차지하게 해야 실패했다). 서버 프로세스를 죽이면 컨테이너가 다시 떠 프록시가 15초 안에 200을 낸다(US21. 프로브에서는 5.1초였다). 띄우는 명령이 돌아온 직후의 첫 `/health`가 502 없이 200이다(US7). 필수 값 하나를 비운 `.env`로 친 `docker compose config`가 종료 1이고 그 값의 이름을 적는다(US5). `docker compose --profile reranker config`가 종료 0이다(US26. 리랭커를 띄우지는 않는다).
- [정함] 시험은 실행마다 새로 만드는 자리만 쓴다. 상태와 인증서는 pytest가 그 실행에 주는 임시 폴더(`tmp_path`)에 두고, compose 프로젝트와 볼륨의 이름은 실행마다 무작위 꼬리를 붙여 짓고, 그 이름이 이미 있으면 다시 쓰지 않고 실패한다. 따로 띄우는 대조 스택은 본 스택과 다른 프로젝트 이름을 쓰고, 볼륨째 내리는 호출(`down -v`)은 그 호출이 띄운 프로젝트에만 친다. 설정을 바꿔 띄우는 대조 단계는 저마다 `finally`에서 자기가 띄운 것을 내리거나 원래 설정으로 되돌린다. 프로브의 `run.py`는 한 기계에서 손으로 차례대로 돌린 것이라 이를 지키지 않는다. 상태 파일과 인증서를 시스템 임시 폴더의 고정 이름에 두고 인증서가 있으면 기한을 보지 않고 다시 쓰며, `sse` 단계가 본 스택과 같은 compose 프로젝트를 쓰고, 오프라인과 내려받기 단계가 고정 이름의 볼륨을 만들고 지우며, 대조 설정을 되돌리는 호출 몇이 `finally` 밖에 있다(PR 67의 리뷰 봇이 짚었다).
- [정함] 단독 compose 시험이 도는 곳은 `ci.yml`의 새 잡(base가 main인 PR과 main 푸시)과 릴리스 워크플로의 시험 단계(올릴 이미지 자체로)다. 개발자는 개발 PC에서 경로를 주어 친다. 두 잡의 제한 시간(`timeout-minutes`)은 캐시가 없는 경우(이미지 짓기, 모델 내려받기, 1800초까지의 기다림)를 넘게 잡는다. agent-os의 값(단독 compose 시험 잡 20분, 짓는 잡 30분)을 그대로 옮기면 1800초의 기다림보다 잡이 먼저 끝난다.
- [정함] 도구의 시험은 agent-os의 시험 다섯을 옮겨 이 저장소의 값으로 고친다. 번호와 노트(`tests/tools/test_release.py`), 워크플로가 부르는 판정(`tests/tools/test_release_ci.py`), 노트 검사(`tests/tools/test_check_notes.py`), 릴리스 워크플로 파일의 꼴(`tests/tools/test_release_workflow.py`), 설치 안내의 정합(`tests/tools/test_deploy_guide.py`)이다. 더하는 경우는 셋이다. 마이그레이션 파일을 고친 PR의 느낌표 판정(더함, 고침, 지움, 옮김과 출시 PR의 면제), 노트의 "계약의 판" 절, `pyproject.toml`만 고친 변경이 제품 변경으로 세어지는 것이다. 선례는 이 저장소의 `tests/tools/` 아래 도구 시험이다.
- [정함] `test_release_ci.py`의 저장소 상태 시험(bake 설정의 저장소 이름이 compose의 `image:` 줄과 설치 안내의 대응표와 같은지)도 옮긴다. 이름 하나를 고치고 다른 자리를 빠뜨리면 릴리스가 나서야 드러나기 때문이다. agent-os의 그 시험은 e2e가 쓰는 compose 파일(`compose.fixtures.yaml`)과도 견주는데, 이 저장소의 단독 compose 시험은 묶음의 compose를 그대로 쓰므로 그 견줌은 뺀다. 저장소 상태 시험은 둘을 더 본다. 이미지를 짓는 파일의 `FROM`과 compose의 바깥 이미지 줄이 digest(`@sha256:`)로 고정됐는지(US53), 프록시 설정의 `/mcp` 자리가 `proxy_buffering off`를 두는지다(US40. 지금의 서버는 응답을 모으지 않게 하는 머리를 싣기 때문에 기능 시험으로는 그 설정의 유무가 갈리지 않는다).
- [정함] 번호가 보이는 자리의 시험은 제품 쪽 단위 시험이다. `rag-engine --version`이 필수 설정 없이 종료 코드 0으로 끝나고 첫 줄이 설치된 패키지의 번호이며 계약마다 한 줄씩 찍는지(선례 `tests/test_serve_command.py`와 같은 관리 명령 시험), FastAPI 앱의 판이 그 번호인지, MCP 초기화 응답의 `serverInfo.version`이 그 번호인지(선례 `tests/server/test_mcp_assembly.py`)를 본다. `serverInfo.version`은 `tests/contract/`의 계약 시험에 두지 않는다. 원칙 VII은 검색 도구의 형식을 MCP 클라이언트로 접속하는 계약 시험이 판정한다고 정하는데, 서버 정보의 번호는 MCP 표준의 칸에 싣는 값이라 검색 도구의 형식과 그 판을 바꾸지 않는다(위 번호가 보이는 자리의 사용자 선택). 이미지 안의 번호는 단독 compose 시험이 MCP SDK 클라이언트로 본다(위 확인 목록).
- [정함] 릴리스 워크플로 자체에는 자동 시험이 없다(agent-os와 같다). zizmor(GitHub Actions 워크플로 파일에서 비밀 값이 새거나 위험한 계기를 쓰는 자리를 찾는 검사 도구. 이 저장소의 커밋 전 검사가 이미 돌린다)가 워크플로를 감사하고, 워크플로가 부르는 판정은 위의 도구 시험이 본다. 첫 실제 실행은 이 기능의 출시 PR을 병합한 세션이 병합 절차의 "릴리스를 기다린다"대로 지켜본다.
- [정함] 수락은 두 자리에서 본다. 하나는 이 기능의 출시 PR에서 `ci.yml`의 단독 compose 시험 잡이 GitHub 러너(깨끗한 리눅스 VM)에서 초록인 것이다. 다른 하나는 첫 릴리스 뒤, GitHub 릴리스에서 받은 묶음과 Docker Hub에서 받은 이미지로 단독 compose 시험을 한 번 더 치는 것이다(이미지 환경 변수에 `njh6803`과 그 번호를 준다). 뒤의 것은 그 세션이 개발 PC에서 친다. 그 PC는 Docker Hub에 로그인해 있을 수 있으므로, 이미지는 빈 설정 폴더(`DOCKER_CONFIG`를 빈 임시 폴더로 준다)로 받아 계정 없이 받히는 것(US2)을 함께 보인다.

## Out of Scope

- 원천 폴더의 볼륨. source-sync가 서버 경로 원천을 더할 때 단독 compose에 그 볼륨과 설치 안내의 절을 더한다. source-sync의 `Blocked by`에 release-image가 있다.
- 관리자 페이지의 이미지와 프록시의 경로. admin이 이 명세의 규칙(이미지 이름, bake 대상, 경로 허용 목록, 단독 compose 시험)으로 더한다. admin은 source-sync를 기다리므로 이 기능 뒤에 돈다.
- 업그레이드 전 백업, 복원, 되돌리기의 절차. backup-upgrade가 정한다. 그 전에는 마이그레이션이 든 릴리스의 노트가 PostgreSQL 볼륨을 백업하라는 한 줄을 적는다. backup-upgrade는 source-sync를 기다리므로 이 기능 뒤에 돈다.
- 진단 묶음에 릴리스 번호를 싣는 것. diag-bundle이 `rag-engine --version`의 출력과 이미지의 OCI 라벨을 쓴다. diag-bundle은 source-sync를 기다리므로 이 기능 뒤에 돈다.
- 출시 후보 단계를 끝내는 것. release-0-1의 마지막 티켓이 릴리스 설정 파일의 `candidate_for` 줄을 지운다. release-0-1의 `Blocked by`에 release-image가 있다.
- 브라우저에서 부르는 MCP 요청. MCP SDK는 `Origin` 머리가 붙은 `/mcp` 요청을 막는 것으로 보이고(코드를 읽은 추정이고 재지 않았다), 브라우저 클라이언트를 열지는 이 기능이 정하지 않는다.
- 인증서를 자동으로 받는 것(ACME), ARM 이미지, 이미지 서명, Podman과 Kubernetes용 파일, GPU용 TEI 이미지를 기본으로 두는 것. 다른 제품의 compose가 이 이미지를 띄우는 배치도 정하지 않는다(ADR 0020).
- 이미지 안에서 검색 평가를 부르는 입구. admin이 연다(기능 계획이 넘긴 것).
- 수집 API가 올라오는 본문을 크기 상한에서 미리 끊는 것(`Content-Length`를 먼저 보거나 받는 바이트를 세는 것). 지금은 상한을 넘는 업로드도 끝까지 받아 임시 파일에 쓴 뒤 413으로 답하고(`src/rag_engine/server/ingest_api.py`를 읽었다), 이 기능은 서버 `/tmp`의 크기 상한으로 메모리만 막는다. 수집 API의 코드를 고치는 일이라 이미지와 배치를 정하는 이 기능 밖이다. 0.1을 내기 전에 할지는 release-0-1의 명세가 정한다(그 기능 계획에 넘겼다).

## Further Notes

- 이 명세의 측정은 모두 개발 PC의 Windows Docker Desktop(Docker 29.9.2, Compose 5.6.1)에서 쟀고, 리눅스 VM에서 잰 것이 아니다. 둘이 다를 수 있는 자리는 둘이다. 바인드 마운트의 파일 소유(Docker Desktop은 Windows 폴더의 소유를 흉내 낸다. 프로브는 모델을 이름 있는 볼륨으로 붙여 리눅스의 소유 규칙으로 쟀다)와 443 같은 낮은 포트를 여는 것이다. 단독 compose 시험이 GitHub 러너에서 처음 도는 PR이 리눅스에서의 첫 확인이다.
- 프로브의 `up` 단계는 단독 compose가 뜨는 데 121초가 걸렸다(커밋한 출력 `run_out.txt`의 실행). 모델이 이미 든 볼륨이었으므로 임베딩 서버가 모델을 메모리에 올리는 시간이 대부분이고, 그 기계에서 같이 돈 다른 컨테이너에 따라 다르다. 모델을 처음 내려받는 시작은 그 위에 내려받는 시간(개발 PC에서 409초)이 더해진다.
- nginx, TEI, PostgreSQL의 판을 바꾸는 티켓은 프로브 `standalone/run.py`의 단계 가운데 바뀐 이미지에 닿는 것(nginx면 `sse`, `checks`, `recover`, TEI면 `checks`, `offline`, `download`)을 다시 돌려 이 명세의 수치가 여전한지 본다.
- 첫 릴리스에서 지켜볼 것은 셋이다. 릴리스 워크플로가 eval 캐시를 읽는지(못 읽으면 시험 단계가 모델을 내려받는 시간만큼 길어진다), Docker Hub에 올린 두 이미지의 층이 한 벌로 저장되는지, GitHub 릴리스의 "계약의 판" 절이 `--version`의 줄과 같은지다.
