# 04: 설치 안내가 운영자를 묶음 풀기부터 MCP 검색과 업그레이드까지 이끈다

**What to build:** 배포 파일 묶음에 드는 한국어 설치 안내 `deploy/standalone/README.md` 한 편과, 묶음 안 두 폴더의 설명 `tls/README.txt`(어떤 파일을 어떤 권한으로 두는지)와 `models/README.txt`(첫 시작이 모델을 내려받는다는 것, 폐쇄망에서 옮기는 법, 시험한 리비전)가 선다. 운영자는 그 안내만 보고 깨끗한 리눅스 VM에서 묶음을 풀고, `.env`와 인증서와 모델 폴더를 두고, 띄우고, 첫 인증 토큰을 내고, 문서 폴더를 넣고, MCP 클라이언트로 검색한다. 리랭커 켜기, 프록시 설정 고치기, 폐쇄망 설치, Docker Hub 받기 제한, 업그레이드도 그 안내에 있다(스토리 3, 11, 23~28, 32, 37). 안내와 묶음의 다른 파일이 어긋나지 않는지는 agent-os의 `tests/tools/test_deploy_guide.py`를 옮긴 저장소 상태 시험이 본다.

안내에 적는 명령은 이 티켓이 실제로 쳐 본다. 명세가 "그 티켓이 실제로 쳐 보고 적는다"고 넘긴 것이 폐쇄망 설치의 명령이고, 그 밖의 명령도 프로브가 친 꼴을 옮기되 이 티켓이 한 번 더 친다.

근거는 명세 "설치 안내" 전부, "배포 파일 묶음"의 묶음에 드는 것, "단독 compose"의 `.env`·모델 폴더·`chown`·띄우는 명령·리비전·메모리 항목, "프록시"의 인증서 권한·설정을 고친 뒤·다시 시작하는 동안의 오류·기다리는 시간 항목, "이미지의 구성"의 `/tmp` 상한 항목, "규약 문서와 낡은 문장"의 `README.md` 항목이다.

**Blocked by:** 03 (단독 compose와 프록시 설정, 주 설정의 경로. 03이 02를 기다리므로 묶음을 짓는 도구도 그때 있다)

**Status:** ready-for-agent

- [ ] 시작할 때 agent-os의 변경을 본다. `git -C C:/project/agent fetch origin` 뒤에 `git -C C:/project/agent log b74a8adf2..origin/dev -- .github/workflows/release.yml tools/release.py tools/release_ci.py tools/check_notes.py deploy/ tests/tools/test_release.py tests/tools/test_release_ci.py tests/tools/test_release_workflow.py tests/tools/test_check_notes.py tests/tools/test_deploy_guide.py`가 비지 않으면 그 변경을 함께 옮길지 사용자에게 묻고 멈춘다(명세 "따르는 것과 옮기는 방식"). 두 명령 가운데 하나라도 오류로 끝나면 빈 출력으로 보지 않고 그 오류를 보고하고 멈춘다. 바뀐 파일이 이 티켓이 옮기는 파일이 아니면 묻지 않고 그 커밋을 Comments에 적고 잇는다. 사용자에게 물었으면 그 답과 본 agent-os 커밋을 Comments에 적는다. 기점이 `1aac0cf`가 아니라 `b74a8adf2`인 까닭은 명세 "따르는 것과 옮기는 방식"이 적는다. 옮길 것은 그 커밋의 `deploy/standalone/README.md`와 `tls/README.txt`, `tests/tools/test_deploy_guide.py`이고, agent-os 제품의 절(위젯, 관리 화면, SSH 포트 포워딩)은 옮기지 않는다.
- [ ] 안내의 절은 명세 "설치 안내"의 차례다. 보증하는 환경과 메모리(기준 32GB, 최소 16GB), 묶음 풀기, `.env` 채우기(`chmod 600 .env`, 비밀번호를 만드는 `openssl rand -hex 24`), 인증서(자체 서명 인증서를 만드는 명령과 키 파일의 `root:101`·`0640`), 모델 폴더(`mkdir -p models/embedding`과 `sudo chown -R 10001:10001 models`. 묶음에는 `models/embedding/`이 없고 없는 폴더는 Docker가 root의 것으로 만든다. 받은 리비전을 `refs/main`에서 읽는 명령, 시험한 리비전), 띄우기(`docker compose up -d --wait --wait-timeout 1800`과, 첫 시작이 그 기다림을 넘겼을 때 모델을 다 받은 뒤 같은 명령을 다시 치라는 것), 첫 인증 토큰, 문서 넣기, MCP 클라이언트로 접속하기, 서비스와 이미지의 대응표, 리랭커 켜기, 프록시 설정 고치기, 볼륨과 지우면 안 되는 것(`rag-engine_postgres`, `rag-engine_data`), 폐쇄망 설치, Docker Hub 받기 제한, 업그레이드다. 옮긴 글은 이 저장소의 이름(릴리스, 업그레이드 등)으로 쓴다.
- [ ] 명세가 안내에 적으라고 한 문장을 빠뜨리지 않는다. 서버 `/tmp`의 상한 1GiB와 `RAG_MAX_UPLOAD_MB`를 올리는 설치가 `.env`의 `RAG_ENGINE_SERVER_TMP_SIZE`도 함께 올려야 한다는 것(compose 파일을 고치면 업그레이드 때 사라진다), 서버를 다시 시작하는 동안 약 10초 오류가 난다는 것과 그 까닭을 서버 로그와 컨테이너 상태에서 찾으라는 것, 검색의 시간 제한을 60초 넘게 올리는 설치가 프록시의 `proxy_read_timeout`도 올려야 한다는 것, 자체 서명 인증서를 클라이언트가 믿게 하는 방법은 클라이언트마다 달라 적지 않는다는 것(원칙 III), 측정은 Engine 29.9.2와 Compose 5.6.1에서만 했고 최소 판(Engine 28.3.3, Compose 2.20.2)에서는 재지 않았다는 것이다. 마지막 문장은 03이 Compose 2.20.2로 띄워 본 결과(03의 Comments)가 있으면 그 결과대로 고친다.
- [ ] 프록시 설정을 고치는 절의 두 명령은 03이 정한 주 설정의 경로를 `-c`로 준다. 리랭커 켜기 절은 프로필로 띄우는 명령(`docker compose --profile reranker up -d --wait --wait-timeout 1800`), `models/reranker/`를 만들어 uid 10001에게 주는 명령, `.env`에 적는 `RAG_DEFAULT_RERANKER_URL=http://reranker:80`, `migrate`를 다시 돌리는 것, ADR 0010 이력 2026-11-17이 적은 후보 수와 검색 시간 제한, 03이 정한 리랭커의 메모리를 싣는다. 업그레이드 절은 명세 "설치 안내"의 업그레이드 항목의 차례(옛 `compose.yaml`과 `proxy/`를 다른 이름으로 복사, 새 `compose.yaml`로 바꾸고 있던 `proxy/` 폴더는 두고 그 안을 비운 뒤 새 `proxy/`의 파일을 제자리로 복사(`find proxy -mindepth 1 -delete`와 `cp -r <새 묶음>/proxy/. proxy/`), `.env`·`tls/`·`models/`·`compose.override.yaml`은 남김, `docker compose stop server worker`, `up`, 고쳐 쓴 프록시 설정을 견주어 새 파일에 다시 넣고 `nginx -t -c`로 확인하기, `nginx -s reload -c`, 스키마 단계가 실패했을 때 되돌리는 `--remove-orphans`)를 그대로 싣고, 폐쇄망 설치의 업그레이드(새 이미지를 옮겨 싣고 `compose.override.yaml`의 이름을 맞추는 것)와, 백업과 복원은 backup-upgrade가 정한다는 것을 적는다. 폴더째 바꾸면 도는 프록시가 새 설정을 보지 못한다는 까닭도 한 줄 적는다.
- [ ] 안내의 명령을 개발 PC의 단독 compose에서 실제로 쳐 보고, 친 명령과 결과를 Comments에 적는다. 자체 서명 인증서, 첫 인증 토큰(`docker compose exec server rag-engine bootstrap-token`), 문서 넣기(`docker compose run --rm -v <폴더>:/import:ro worker rag-engine ingest /import --wait`), 모델 폴더의 소유와 `refs/main` 읽기, 프록시의 `nginx -t -c`와 `nginx -s reload -c`, 리랭커를 켜는 명령, 업그레이드의 차례다. 업그레이드는 옛 묶음으로 띄운 설치에서 `proxy/site.conf`에 눈에 띄는 차이를 두고 옛 묶음에만 있는 파일 하나를 뺀 새 묶음으로 쳐서, 그 파일이 `proxy/`에 남지 않는지와, 안을 비우고 다시 채운 제자리 복사와 `nginx -s reload -c` 뒤에 프록시가 새 설정으로 답하는지 보고, compose가 얹은 파일만 바뀐 프록시를 다시 만들었는지(명세가 어림으로 둔 것)도 적는다.
- [ ] 폐쇄망 설치의 명령을 실제로 쳐 보고 적는다(명세 "설치 안내"의 폐쇄망 항목). 이미지 다섯을 `docker save`로 파일 하나에 담고 `docker load`로 싣는 것, digest로 고정한 바깥 이미지에 로컬 이름을 다시 붙이고 `compose.override.yaml`로 그 이름을 쓰게 하는 것, 받은 기계와 실은 기계에서 이미지 ID를 대조하는 것이다. 실은 뒤 digest 참조가 남는지(`docker image inspect`의 `RepoDigests`)를 보고, 남으면 로컬 이름을 다시 붙이는 길이 필요한지 다시 판단해 안내에 맞춘다(명세 "설치 안내"의 폐쇄망 항목). 인터넷이 되는 기계의 첫 시작은 안내의 띄우는 명령(`--wait-timeout 1800`)으로 친다. 개발 PC 한 대에서는 이미지를 지운 뒤 파일에서 싣는 것으로 실은 기계를 흉내 내고, 실은 이미지와 다른 폴더로 복사한 `models/`로 단독 compose가 떠서 검색되는지 본다. 흉내 낸 방법과 흉내 내지 못한 것(바깥으로 나가는 길이 정말 없는 기계)을 함께 적는다.
