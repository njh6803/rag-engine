# 03: 단독 compose가 프록시 뒤에 다섯 컨테이너를 띄우고, 시험이 운영자의 차례를 그대로 밟는다

**What to build:** `deploy/standalone/`에 단독 compose(이 서버만 따로 설치하는 구성. compose 파일 하나로 검색 서버, 작업자, 그리고 그 둘이 쓰는 서비스까지 함께 띄운다)의 `compose.yaml`, `.env.example`, 프록시 설정 `proxy/nginx.conf`와 `proxy/site.conf`가 선다. 운영자가 `.env`를 채우고 `tls/`에 인증서를 두고 `docker compose up -d --wait --wait-timeout 1800`을 치면 프록시(nginx), 검색 서버, 작업자, PostgreSQL, 임베딩 서버가 차례대로 뜨고(그 앞에 마이그레이션이 한 번 돈다), 밖으로 열린 포트는 프록시의 443 하나다(스토리 5~10, 12~22, 40).

단독 compose 시험이 이 차례를 그대로 밟는다. 01의 이미지 둘과 02의 도구로 지은 배포 파일 묶음을 받아, 진짜 임베딩 서버로 띄우고, 관리 명령으로 표본 문서를 넣고, 공식 MCP SDK 클라이언트로 443에 접속해 검색한다. `ci.yml`에 그 시험 잡을 더하되 base가 main인 PR과 main 푸시에서만 시험한다(스토리 42~45).

근거는 명세 "단독 compose", "프록시", "이미지의 구성"의 읽기 전용 루트·`/tmp`·헬스체크 항목, "배포 파일 묶음"의 `.env.example` 항목 둘, "ci.yml"의 단독 compose 시험 잡 항목, Testing Decisions의 단독 compose 시험 항목 전부다. 원형은 `.scratch/release-image/probes/standalone/`의 `run.py`와 시제품 compose·프록시 설정이고(같은 폴더 README 표), 명세가 든 수치는 그 프로브의 단계(`up`, `sse`, `checks`, `recover`, `offline`, `download`, `accept`)가 잰 것이다.

**Blocked by:** 01 (이미지 둘과 bake 설정), 02 (묶음을 짓는 도구)

### 단독 compose 시험

- [x] 실패하는 시험을 먼저 쓴다. 시험은 pytest로 쓰고 기본 수집에서 뺀다. `uv run pytest --collect-only -q`의 출력에 그 시험이 없고 건너뛴 시험으로도 세지 않으며(원칙 I), 경로를 주어 칠 때만 모이는 것을 손으로 보고 Comments에 적는다. 시험은 시작할 때 443이 비었는지 보고, 차 있으면 까닭을 적고 실패한다.
- [x] 시험은 이미지를 환경 변수 둘(이름공간과 번호)로 받고, 없으면 bake 설정으로 직접 짓는다(이름공간 `rag-engine-test`, 번호 `0.1.0-rc.1`). 배포 파일 묶음도 환경 변수로 받고, 없으면 02의 도구로 `deploy/standalone/`에서 짓는다. 모델 폴더도 환경 변수로 받고, 없으면 명세 "단독 compose"의 명령대로 풀어 둔 묶음 안에 `models/embedding/`을 만들어 uid 10001에게 주고 임베딩 서버의 첫 시작이 내려받게 한다. 묶음에는 그 폴더가 없다. 리눅스에서는 `sudo` 대신 같은 일을 하는 컨테이너(`chown`만 하는 것)를 써도 되고, Windows의 Docker Desktop은 바인드 마운트의 소유를 흉내 내므로 그 단계가 Windows에서 무엇을 하는지(또는 건너뛰는지) 시험의 독스트링에 적는다. 이 단계의 소유 문제는 리눅스 러너에서 처음 드러난다. 변수 이름은 이 티켓이 정하고 시험의 독스트링에 적는다. 08의 릴리스 워크플로가 그 이름으로 부른다. 04의 정합 시험이 안내의 명령과 대 볼 수 있게, 시험이 치는 띄우는 명령·인증서 명령·모델 폴더 명령은 한 자리(상수)에 둔다.
- [x] 시험이 밟는 차례와 확인하는 것은 명세 Testing Decisions의 두 항목("시험이 밟는 차례", "시험이 확인하는 것") 그대로다. 띄우는 명령은 설치 안내와 같은 `docker compose up -d --wait --wait-timeout 1800`이다. 확인 목록의 항목(빈 필수 값의 `docker compose config`, 띄운 직후의 첫 `/health`, 리랭커 프로필의 `config`, 서버 프로세스를 죽인 뒤와 서버 컨테이너를 다시 만든 뒤 15초 안의 200, PostgreSQL 로그를 포함한다)을 모두 단언으로 둔다. PostgreSQL 로그에 질의나 표본 문서의 글이 나오면 단언을 느슨하게 고치지 않고 멈춰 보고한다(원칙 V. 명세가 재지 않은 자리다).
- [x] 시험은 실행마다 새로 만드는 자리만 쓴다(명세 Testing Decisions의 그 항목). 상태와 인증서는 `tmp_path`에, compose 프로젝트와 볼륨의 이름은 실행마다 무작위 꼬리를 붙여 짓고 이미 있으면 실패하며, 대조 스택은 다른 프로젝트 이름을 쓰고, `down -v`는 그 호출이 띄운 프로젝트에만 친다. 설정을 바꿔 띄우는 대조 단계는 저마다 `finally`에서 되돌린다. 프로브 `run.py`가 이 규칙을 지키지 않은 자리(명세가 든 다섯)를 옮기지 않는다.
- [x] 시험이 부르는 외부 명령(docker, docker compose)에는 호출마다 시간 제한을 둔다. 띄우는 명령은 그 명령의 기다림(1800초)보다 긴 제한을 받는다.
- [x] 어떤 설정에서도 초록이 되는 단언이 둘 있었으므로 조건을 지킨다(명세 Testing Decisions). TLS 1.1 확인은 클라이언트의 보안 수준을 낮춰(`SECLEVEL=0`) 1.1을 내밀 수 있게 한 채 한다. 서버 컨테이너를 다시 만드는 확인은 옛 주소를 다른 컨테이너가 차지하게 한 채 한다(프로브 `run.py`의 `recover` 단계가 그렇게 했다).
- [x] 확인 목록이 어떤 설정에서도 초록인 단언이 아닌지 본다. 단언 가운데 적어도 둘(예: 프록시가 `/docs`를 넘기게 한 설정, 접근 로그에 `$request_uri`를 남기게 한 설정)을 일부러 깨뜨린 사본으로 시험이 빨개지는 것을 손으로 보고 Comments에 적는다. 깨뜨린 사본은 커밋하지 않는다.

### 명세가 재지 않은 것

- [x] 실제 서버의 `/mcp` 응답이 프록시를 지나 이어 보내는 꼴(`Content-Type: text/event-stream`)로 오는지와 `X-Accel-Buffering` 머리가 바깥에 없는지를, 단독 compose를 띄운 채 손으로 보고 명령과 함께 Comments에 적는다. 명세의 측정은 가짜 뒷단으로 했다(프로브 `sse` 단계). 지금 서버에 진행 알림처럼 사건을 여럿 보내는 응답이 없으면, 사건 사이가 모이지 않는다는 것은 가짜 뒷단 측정에 기댄다고 적는다(명세 "프록시"의 `/mcp` 항목).
- [x] 사이트 설정의 `error_log /dev/null`이 요청을 처리하다 난 오류(`crit` 줄을 포함한다)를 모두 받아, 주 설정의 오류 로그(`notice`)로 요청 줄이 새지 않는지를 nginx 문서의 `error_log` 지시어(쓸 수 있는 문맥과 아래 문맥으로 물려주는 규칙)를 원문으로 읽고 읽은 자리를 Comments에 적는다. 명세는 `crit` 줄을 재지 않았다(명세 "프록시"의 접근 로그 항목).
- [x] 임베딩 서버가 거절한 요청의 로그는 확인 목록의 단언(표지 글을 담은 꼴이 틀린 본문을 보낸 뒤 그 글이 로그에 없다)으로 다시 본다. 토큰 상한을 넘는 글은 `--max-batch-tokens 4096`에서 TEI가 잘라 200으로 답하므로 거절이 되지 않는다(명세 "단독 compose"의 로그 항목, 명세 검토의 손 확인). 거절이 실제로 났는지(422)도 함께 단언해, 거절되지 않은 요청으로 초록이 되지 않게 한다.

### CI
