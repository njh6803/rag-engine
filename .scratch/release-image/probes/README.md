# release-image 프로브

release-image 명세 세션(2026-11-17~18)에서 명세(`.scratch/release-image/spec.md`)와 ADR 0020 이력의 근거로 쓰려고 돌린 스크립트와 그 출력이다. 실행 명령은 각 스크립트의 독스트링에 있다. 측정은 모두 개발 PC의 Windows Docker Desktop에서 했고 리눅스 VM에서 한 것이 아니다(명세 Further Notes).

| 프로브 | 무엇을 재는지 | 어디가 근거로 드는지 | 다시 돌 때 필요한 것 | 잰 판 |
|---|---|---|---|---|
| `standalone/run.py` | 시제품 이미지 둘(`standalone/Dockerfile`)과 시제품 단독 compose(`standalone/compose.yml`, 프록시 설정 `standalone/proxy/`)를 실제로 띄워 잰다. 단계는 `build`(이미지의 번호, 사용자, 라벨, 크기, 함께 쓰는 층, 번호 없이 지으면 실패하는지), `sse`(가짜 뒷단 `standalone/sse_stub.py`로 프록시 설정 둘과 `X-Accel-Buffering` 머리의 유무마다 이어 보내는 응답이 닿는 시각, 프록시가 뒷단을 기다리는지에 따른 502), `up`, `accept`(첫 토큰, 표본 문서 수집, 공식 MCP SDK 클라이언트로 HTTPS 검색), `checks`(열린 포트, 컨테이너 사용자, 421·401·404, TLS 판, 접근 로그, 큰 파일 올리기, 임베딩 서버와 서버·작업자의 로그, 대조군 nginx 기본값 설정과 `/tmp` 없는 서버), `recover`(서버를 다른 주소로 다시 만들 때, 함께 다시 시작할 때, 프로세스가 죽을 때, 멈춘 동안의 오류 로그, 기다리는 조건 셋), `down`, `offline`(바깥으로 나가는 길이 없는 네트워크에서 임베딩 서버가 뜨는지를 `HF_HUB_OFFLINE`, uid 10001, 읽기 전용, 리비전 고정마다), `download`(생략하면 돌지 않는다. 빈 모델 볼륨에서 uid 10001의 첫 시작이 모델을 내려받는지와 root가 가진 볼륨의 대조군)다. 출력은 셋이다. `standalone/run_out.txt`는 `build`부터 `offline`까지 한 번에 돈 실행이고, 그 실행의 `offline`에는 리비전을 고정하고 `HF_HUB_OFFLINE=1`을 준 두 경우가 아직 없었다. `standalone/run_offline_out.txt`는 그 두 경우를 더한 뒤 `offline`만 다시 돈 실행이고, `standalone/run_download_out.txt`는 `download`만 돈 실행이다 | 명세 "이미지의 구성", "단독 compose", "프록시", "설치 안내", Testing Decisions, Further Notes. ADR 0020 이력 2026-11-18 "명세가 제품 변경의 목록과 번호가 보이는 자리를 넓혔다"는 이 프로브를 들지 않는다 | Docker Engine과 Compose, `openssl`, 저장소의 개발 의존성(`mcp`, `httpx2`). `BAAI/bge-m3`가 이미 든 Docker 볼륨(인자 `--models-volume`. 개발 PC에서는 `rag-latency-probe_tei-data`였다). 127.0.0.1의 빈 포트 하나. 바깥 네트워크는 바탕 이미지를 받을 때와 `download` 단계(약 2.3GB)에서만 쓴다. 임베딩 서버가 메모리 약 6.6GiB를 쓴다 | Docker 29.9.2, Compose 5.6.1(출력 첫 줄). nginx 1.30.6 alpine(`sha256:583b7f2f…c311`), `pgvector/pgvector:0.8.7-pg18-trixie`(`sha256:5895949d…bcd2`), TEI `cpu-1.9.4`(`sha256:2538ea1c…c78d`), `python:3.12-slim`과 `ghcr.io/astral-sh/uv:0.10.8`(태그로 받았고 digest는 읽지 않았다), mcp 2.3.0, sse-starlette 3.7.0, `BAAI/bge-m3` 리비전 `5617a9f61b028005a4858fdac845db406aefb181`. 읽을 때 주의할 것이 셋이다. 첫째, 세 출력은 스크립트에서 출력에 닿는 두 군데를 고치기 전에 돈 실행이다. 그때는 JSON이 아닌 응답 본문(nginx의 413 오류 페이지)을 줄바꿈째 찍어 `run_out.txt`의 413 줄 뒤에 HTML 세 줄이 따라 나왔고, 서버·작업자 로그 검사는 나온 값 자체를 찍었다(그 실행에서는 빈 목록이었다). 지금 스크립트는 본문을 한 줄로 접고, 토큰이 새도 출력에 실리지 않게 항목 이름만 찍는다. 그 HTML 세 줄 끝의 홀로 선 CR 셋(Windows 표준 출력이 본문의 CRLF를 CR CR LF로 바꿨다)은 줄 구분 문자 검사가 커밋을 막아 손으로 지웠고, 보이는 글자는 그대로다. 둘째, `checks`의 `x-accel-buffering None`은 서버가 그 머리를 보내지 않았다는 뜻이 아니다. nginx가 `X-Accel-*` 머리를 클라이언트에 넘기지 않는다(서버가 싣는다는 것은 명세 "프록시"가 코드를 읽어 적는다). 셋째, `run_download_out.txt`에서 받은 리비전과 소유자가 띄어쓰기 없이 붙어 나왔다(`5617a9f6…aefb181`과 `10001:10001`). 스크립트가 `refs/main` 뒤에 줄을 바꾸지 않아서이고, 다시 돌리면 7분(409초)과 내려받기 2.2GiB(볼륨의 `du -sh`)가 들어 고치지 않고 두었다 |
