# 01: 포트 둘: 진단용 검색 `diagnose_candidates`와 판정기 `RelevanceJudge`

**What to build:** 평가가 실제 검색과 같은 SQL 뼈대로 단계별 순위를 받을 수 있게 `VectorIndex`에 진단용 메서드를 더하고, LLM 관련성 판정기의 포트를 `domain`에 둔다. 이 기능의 첫 티켓이고 계약(포트)을 세워 다른 티켓을 막는다(명세 Further Notes의 순서 항목, ADR 0007 Consequences). 평가 도구도 Claude 어댑터도 아직 없으므로, PostgreSQL 어댑터의 시험이 이 티켓의 바깥 표면이다. 포트의 이름은 ADR 0007 이력 2026-11-13에 이미 들어 있다.

**Blocked by:** None (can start immediately)

**Status:** done

- [x] `domain`에 `SearchDiagnosis`(`is_current`와 줄의 목록)와 그 줄(`SearchHit`에 `ordinal`, `vector_rank`, `keyword_rank`, `fused_rank`를 더한 것)을 두고, `VectorIndex`에 `diagnose_candidates(SearchQuery, *, scan)`를 더한다. `scan`은 계획을 고르는 열거 `CandidateScan`(`INDEX`는 실제 검색과 같은 HNSW 색인 계획, `EXACT`는 정확 스캔)이다(명세 "진단용 검색과 단계". 불리언 `exact` 인자는 `CODING_STANDARDS.md`의 첫 판단 기준에 걸려 열거로 바꿨다). 줄은 벡터 후보와 키워드 후보의 합집합 전부이고(많아야 후보 수의 두 배), `fused_rank`는 그 합집합 안에서 RRF 점수 순으로 매긴 1부터의 순위다. RRF 점수가 같은 줄의 순서는 `search_candidates`와 같은 규칙으로 끊는다.
- [x] PostgreSQL 어댑터: 벡터 쪽과 키워드 쪽의 CTE, 필터와 그룹 집합의 조건, RRF 점수의 식을 짓는 함수를 하나로 두고 `search_candidates`와 `diagnose_candidates`가 함께 쓴다. 두 문장이 다른 곳은 합친 뒤의 자르기와 마지막 `SELECT`뿐이다. `SET LOCAL hnsw.ef_search`와 `hnsw.iterative_scan`도 같은 규칙으로 건다. `EXACT`이면 같은 트랜잭션에서 HNSW 색인을 쓰지 않는 계획(`SET LOCAL enable_indexscan = off` 같은)으로 같은 SQL 글을 돌린다(명세의 `[사용자 선택]` 정확 스캔 항목, ADR 0018 이력 2026-11-13 "평가는 후보를 정확 스캔으로 뽑고, 추론 기록의 해시가 바뀌면 승인을 받는다"). 그 계획 설정은 그 호출 밖으로 새지 않는다. `SET LOCAL`은 트랜잭션이 끝날 때까지 남으므로, 세이브포인트 안에서 돌리거나 호출 끝에 되돌려 같은 트랜잭션에서 뒤에 부른 호출이 HNSW 계획을 쓰게 한다. 06이 필터 질의에서 두 계획의 벡터 후보를 견주기 때문이다(PR #38 봇 첫 회차의 지적).
- [x] 어댑터 대조 시험: 같은 질의에서 `diagnose_candidates`(`INDEX`)의 `fused_rank`가 후보 수 이하인 줄이 `search_candidates`의 후보와 순서, 조각, RRF 점수까지 같다. 키워드가 빈 질의, 필터가 있는 질의, 벡터나 키워드 한쪽에만 든 조각이 있는 질의를 모두 본다. 선례는 `tests/adapters/test_vector_index_chunks.py`다.
- [x] 어댑터 시험: `EXACT`일 때의 계획에 판의 HNSW 부분 색인이 없고 `INDEX`일 때는 있다(EXPLAIN. 선례는 `tests/adapters/test_vector_index_chunks.py`의 계획 시험이고, 어댑터가 시험용으로 계획을 글로 내는 메서드를 두어 판의 HNSW 부분 색인 이름을 본다. 같은 트랜잭션의 `SET LOCAL`이 계획에 걸리게 짓는다). 같은 트랜잭션에서 `EXACT` 호출 뒤에 낸 `INDEX`의 계획과 `search_candidates`의 계획에도 그 색인이 있다. `EXACT` 결과의 `vector_rank`가 거리 순과 같다. 질의한 판이 현재 판이 아니게 되면 `is_current`가 거짓이다.
- [x] `domain`에 `RelevanceJudge` Protocol을 둔다. 메서드는 `judge(query, text)` 하나이고 관련 있으면 참을 돌려준다. 다시 해 볼 만한 실패는 `TransientFailure`, 그 밖은 `PermanentFailure`로 올린다는 것을 독스트링에 적는다(명세 "LLM 관련성 판정"). 시험 지원에 가짜 판정기를 둔다. Claude 구현은 12다.
- [x] 검사 넷이 초록이다.

## Comments

- 2026-11-13 구현에서 정한 것. 첫째, 계획을 고르는 인자는 불리언 `exact` 대신 열거 `CandidateScan`(`INDEX`, `EXACT`)이고 키워드 인자 `scan`이다(PR #38 봇 2회차가 넘긴 것). 메서드를 둘로 쪼개지 않은 것은 두 계획이 같은 SQL 글을 돌고 다른 것은 계획 설정뿐이라서다. 명세와 티켓 04, 06의 `exact` 서술을 같이 고쳤다. 둘째, 줄 `DiagnosedHit`은 `SearchHit`을 상속하지 않고 `hit` 칸으로 든다. 평가가 `dataclasses.replace`로 리랭크 점수를 붙이려면 `SearchHit`이 그대로 필요하고, 어댑터가 칸 열세 개를 되풀이해 적지 않아도 된다. 결과의 줄 목록 칸 이름은 `hits`다. 셋째, `EXACT`의 계획 설정은 `enable_indexscan`을 끄고 호출 끝에 끄기 전 값으로 되돌린다(세이브포인트는 쓰지 않았다. `SET LOCAL`은 세이브포인트를 해제해도 남는다). 몸통에서 데이터베이스 오류가 나면 트랜잭션이 되돌려지므로 되돌리기를 건너뛴다. 넷째, `EXPLAIN`용 `explain_diagnosis`는 `INDEX`에서만 순차 스캔을 끈다. `EXACT`는 실제 호출과 같은 설정으로 계획을 보려고 순차 스캔을 끄지 않는다(`EXACT`에서 둘 다 끄면 계획이 어떻게 바뀌는지는 정하지 않았다. 변이로 끄고 돌린 20행 표에서는 계획에 HNSW 색인이 들지 않았다). 그래서 `INDEX`의 계획을 본 뒤 같은 트랜잭션에서 `EXACT`의 계획을 보면 안 된다. 다섯째, 계획 시험(EXPLAIN)은 시험용 `explain_diagnosis`만 보므로, 실제 `diagnose_candidates`가 `scan`을 따르는지는 호출이 거는 `enable_indexscan` 설정을 감시하는 시험이 따로 본다. 여섯째, 같은 연결에서 두 계획을 다섯 번 넘게 번갈아 부르면 `EXACT`도 색인을 타는 결함을 CodeRabbit CLI가 짚었고(Major) 시험으로 재현했다(`pg_stat_user_indexes`의 `idx_scan`이 8이 아니라 11). psycopg가 같은 문장을 서버에 준비시킨 뒤 서버가 일반 계획을 쓰는데, 일반 계획은 `enable_indexscan`이 바뀌어도 다시 짜지 않는다. 그래서 `diagnosis_sql`이 글 앞에 `scan`을 적은 주석을 붙여 두 계획이 다른 문장으로 준비되게 했다. 이 시험은 변이로 주석을 지우면 빨강이다(변이 표 `first_round_trip_adapter_mutations.toml`).
