# 12: LLM 관련성 판정: Claude 판정기와 `judge`, 보고서의 LLM 숫자

**What to build:** 운영자가 판정기의 설정 셋(`RAG_JUDGE_URL`, `RAG_JUDGE_MODEL`, `RAG_JUDGE_API_KEY`)을 모두 두었을 때만 Claude 판정기가 조립되고(스토리 32), 개발자가 `judge --through <단계>`를 치면 마지막 단계의 상위 10개 조각과 질의의 쌍 가운데 판정 파일에 없는 것만 판정해 `judgments.jsonl`에 쌓는다(스토리 25, 30). `run`은 판정기를 부르지 않고 판정 파일만 읽어 LLM 숫자 둘과 빠진 정답 후보의 목록을 낸다(스토리 28, 29, 31). 키와 요청·응답의 본문은 로그와 표준 오류에 남지 않는다(스토리 33, 원칙 V).

**Blocked by:** 05 (전체 실행. `--through`가 두 단계를 받는다)

**Status:** ready-for-agent

- [ ] `anthropic>=2.8,<3`을 운영 의존성으로 선언하고, `pyproject.toml`의 import-linter forbidden 계약(`app`과 `domain`)에 `anthropic`을 더해 열일곱으로 만든다. 그 계약의 `name`(`sixteen`)과 그 위 주석의 "열여섯", `CLAUDE.md` 레이어 절의 "열여섯"을 같이 고친다(명세 Further Notes). 의존성을 더하므로 `docs/constitution/tech.md`를 읽고 필요하면 고친다.
- [ ] Claude 어댑터는 01의 `RelevanceJudge`를 구현한다(ADR 0019, 명세 "LLM 관련성 판정"). 판정기는 데이터베이스의 트랜잭션에 들 일이 없어 작업 단위 밖에서 부른다. 판정기에 보내는 글은 리랭커에 보내는 글과 같다. 지시문은 어댑터가 들고 판은 1부터의 정수다. 응답은 관련 여부 하나만 받는 구조화된 출력이고 그 모양은 실제 호출로 정한다. 연결 실패, 429, 5xx는 `TransientFailure`, 인증 실패와 읽을 수 없는 응답은 `PermanentFailure`이고, 실패의 메시지에는 SDK의 예외와 서버가 보낸 오류의 글을 옮기지 않는다(선례는 TEI 어댑터의 머리 독스트링이 적은 규칙이다). SDK가 예외와 디버그 로그에 무엇을 싣는지는 설치된 판의 소스를 읽어 확인하고 읽은 자리를 `## Comments`에 적는다.
- [ ] 설정 셋은 모두 기본값이 없다. 셋이 모두 있으면 조립하고, 일부만 있으면 조립하지 않고 빠진 설정의 이름을 알린다(값은 찍지 않는다). `judge`는 `RAG_JUDGE_MODEL`이 `config.json`의 `judge_model`과 다르거나 어댑터의 지시문 판이 `judge_prompt_version`과 다르면 아무것도 부르지 않고 종료 코드 1과 어긋난 둘의 이름을 낸다.
- [ ] `judge`(명세 "LLM 관련성 판정"): `--through`를 받고, 시작할 때 부를 건수와 비용의 어림을 찍으며 `--yes`가 없으면 부르지 않고 끝난다. 판정 하나마다 파일 끝에 줄을 덧붙이고, 동시 호출 넷, 일시 실패 재시도 셋, 끝나면 열쇠 순으로 정렬해 다시 쓴다. `--prune`은 지금의 모델과 지시문 판에 맞지 않는 줄을 지운다. 판정 파일의 쓰기는 02의 경로 판정을 거치고, 시작할 때 03의 데이터베이스 판정을 지난다. `judge`도 `--config <파일>`을 받는다(명세 "자리와 층"의 구성 항목). 06이 먼저 들어와 있으면 그 인자를 같이 쓰고, 아니면 06이 `judge`에 더한다.
- [ ] `judgments.jsonl`의 칸은 `query_sha256`, `text_sha256`, `relevant`, `model`, `prompt_version`, `judged_at`이고 글은 없다. 조회의 열쇠는 앞의 둘과 `model`, `prompt_version`이다.
- [ ] `run`의 `llm` 칸: 그 실행의 마지막 단계의 상위 10개 가운데 LLM이 관련 있다고 본 비율, 기대 근거에 닿은 조각을 LLM도 관련 있다고 본 비율, 판정 없음의 비율, 빠진 정답 후보의 목록(식별자로만)이다. 앞의 두 비율의 분모는 판정이 있는 조합만이고, 판정 없음의 비율은 판정 여부와 관계없이 상위 10개의 조합 전체가 분모다(PR #38 봇 첫 회차의 지적). 판정 파일이 없거나 맞는 줄이 하나도 없으면 `null`과 까닭이다.
- [ ] 새 시험 이음매: 시험이 띄우는 작은 ASGI 앱이 Messages API의 응답 모양을 흉내 내고 받은 요청을 기억하며, 실제 어댑터가 `RAG_JUDGE_URL`로 거기에 붙는다(선례 `tests/support/tei_stub.py`).
- [ ] 시험(명세 "판정의 시험"): 설정 셋이 모두 없으면 조립하지 않는다, 판정기의 설정도 판정 파일도 없으면 `run`이 `llm`을 `null`로 낸다, 판정기의 설정이 없어도 판정 파일이 있으면 `run`이 그 파일로 숫자를 낸다(스토리 31), 일부만 있으면 빠진 이름을 알린다, `--yes` 없이 건수와 비용만 찍고 가짜 끝점을 부르지 않는다, 끊긴 뒤 다시 돌리면 이미 받은 조합을 부르지 않는다(가짜 끝점의 요청 횟수), 질의의 글이나 지시문의 판이 바뀌면 옛 판정이 판정 없음으로 세어진다, 로그에 키와 요청·응답의 본문이 없고 가짜 끝점이 오류를 낸 때의 표준 오류에도 없다(선례 `tests/server/test_log_capture.py`, `test_request_logging.py`), 모델이나 지시문 판이 `config.json`과 다르면 `judge`가 부르지 않고 1이다, `--prune`이 맞지 않는 줄만 지운다, 판정 파일이 묶음 밖을 가리키는 링크이면 쓰지 않고 1이며 링크가 가리킨 파일이 그대로다, `judge`가 묶음 밖의 문서가 든 데이터베이스와 키는 묶음의 것인데 내용 해시가 다른 문서가 든 데이터베이스에서 가짜 끝점을 부르지 않고(요청 횟수가 0이다) 판정 파일을 쓰지 않으며 1을 낸다(원칙 V), `run`의 빠진 정답 후보가 기대 근거에 없는데 관련 있다고 본 조각을 식별자로 싣는다(스토리 29).
- [ ] 실제 Claude API를 한 번 부르는 확인(ADR 0019가 첫 구현 티켓에 맡겼다): 부를 건수와 비용을 사용자에게 보이고 **승인을 받은 뒤** 작은 표본으로 부른다. 어댑터 프로브의 꼴대로 돌지 않으면 멈추고 ADR 0019로 돌아온다. 결과를 프로브로 남긴다.
- [ ] ADR 0007 이력 2026-11-13이 판정기를 ADR 0003의 넷째 플러그인 자리가 아니라고 적을지(명세가 그 가름을 적었다) 사용자에게 묻고, 답을 `## Comments`에 적는다(명세 일지의 "다음").
- [ ] 검사 넷이 초록이다.
