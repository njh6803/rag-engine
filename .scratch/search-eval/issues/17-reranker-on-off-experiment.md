# 17: 리랭커 켬·끔 실험과 리랭커의 기본을 정하는 결정

**What to build:** 리랭크 뒤 줄과 합친 뒤 줄의 차, 리랭크를 넣은 후보 수의 효과를 실험해, core 16이 잰 CPU 리랭커의 지연과 함께 사용자에게 보이고 사용자가 리랭커의 기본을 정하는 길을 고르게 한다(명세 "전체 게이트와 리랭커"의 리랭커의 CPU 속도와 기본의 결정 항목, 스토리 26). 이 티켓에는 사용자의 선택을 기다리는 지점이 있다.

**Blocked by:** 14 (리랭크 기록. 명세는 그 티켓 뒤를 요구한다)

**Status:** done

## Comments

- 2026-11-17 (구현 세션, Sonnet 5.5 / high) 실험은 `.scratch/search-eval/probes/experiments/reranker/`에 있다. 티켓이 적은 `experiments/` 바로 아래가 아니라 하위 폴더를 쓴 까닭은 나란히 도는 티켓 16이 같은 폴더에 `chunking-candidates/`를 두기 때문이다. 표와 명령과 한계는 그 폴더의 `README.md`, 전체 표는 `summary.md`다.
  - 방법: 공공 문서 묶음을 스크래치로 복사해 후보 수 5, 10, 20, 50, 100마다 `run --through rerank --records write --tei-device gpu`와 `run --through fused --records read`를 돌렸다. `write`는 기록에 있는 쌍을 옮기고 없는 쌍만 GPU로 계산한다. 저장소의 `evals/public-docs/records/`는 건드리지 않았고 사본의 리랭크 점수는 커밋하지 않았다. 후보 수 50의 두 보고서는 커밋된 `baseline-fast.json`, `baseline-full.json`의 칸과 같았다.
  - 걸린 시간: 후보 수 100만 새로 계산이 필요했다. 4시간 43분 51초에 15,446쌍을 계산했다(평균 0.91쌍/초). 나머지는 기록만으로 1분 안에 끝났다. 티켓 14의 "2시간을 넘으면 멈춘다"는 리랭크 기록 만들기에 대한 것이라 이 실험에는 적용하지 않고 계속 돌렸고, 3시간을 넘길 전망은 중간 보고에서 알렸다.
  - 결과: 후보 50개 기준 상위 1 적중률이 끔 0.47~0.49, 켬 0.77, MRR이 끔 0.62~0.64, 켬 0.86. 후보 20개의 켠 줄은 거의 같고 후보 100개는 50개보다 낫지 않다(질문 하나가 0.65%p). 후보 5개와 10개는 기대 근거가 후보에 들지 못하는 질의가 늘어 재현율이 낮다. GPU 리랭크 호출은 후보 50개 29.4초, 후보 20개 11.6초(합성 글, 세 번, `rerank_latency_gpu_out.txt`). 실제 조각으로 돌린 후보 수 100 실행의 평균은 0.91쌍/초라 같은 환산으로는 후보 20개 약 22초, 후보 50개 약 55초다(느린 까닭은 재지 않았다. README 지연 절). core 16의 CPU 값은 후보 50개 130초, 후보 5개 15.3~17.0초다.
  - 사용자의 선택(2026-11-17, 채팅의 선택지 답): 리랭커의 기본은 "끄는 기본", 전체 게이트와 최소 점수는 "둘 다 유지". 보이고 고른 선택지는 끄는 기본 / 후보 수를 줄여 켜 둠 / ONNX 리랭커나 GPU 이미지 / 검색 시간 제한을 늘림이었다. 사용자의 자유 글은 없다.
  - 반영: 기본 설치는 리랭커를 켜지 않는다. `settings.py`의 `default_reranker_url`은 이미 `None`이 기본이었으므로 값은 바꾸지 않고, 그 사실을 시험(`test_필수_셋만_주면_나머지는_명세의_기본값이다`의 한 줄)과 주석으로 고정했다. ADR 0010 이력 2026-11-17(본문 포인터 포함, ADR 0007 본문의 컨테이너 수에도 포인터)과 ADR 0017·0018 이력, `tech.md`(헌법 판 1.3.3에서 1.3.4, patch), core 명세 넷(개요, 스토리 20, 설정, 지연 측정 문단), 이 기능의 명세, release-image 계획(리랭커 TEI를 compose 프로필로 두는 일의 받는 곳), 용어집, 티켓 20의 시작 전 확인 문장을 고쳤다. 사용자가 ADR 이력 초안을 보고 "승인"했다.
  - 모델을 바꾸는 길이 아니라서 `config.json`, 리랭크 기록, `baseline-full.json`은 그대로다. 숫자의 앞뒤 차이를 보일 일이 없다.
