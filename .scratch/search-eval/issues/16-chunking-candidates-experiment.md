# 16: 리랭커 없는 설정 실험: 조각 크기·겹침과 후보 수의 기본값

**What to build:** 리랭커 없이 할 수 있는 설정 실험을 로컬에서 돌려, 조각 크기와 겹침, 후보 수의 기본값을 바꿀지 사용자가 숫자로 정하게 한다(스토리 18, 26). 실험은 묶음의 `config.json`을 고치지 않고 `--config`로 준 다른 구성 파일과 `--records off`로 돌리고, 결과는 프로브로 커밋한다(명세 "설정 실험과 참고 측정"). 이 티켓에는 기본값의 승인을 기다리는 지점이 있다.

**Blocked by:** 06 (`--config`와 나눠 본 숫자), 11 (첫 기준 보고서. 기본 구성의 값을 대 본다)

**Status:** done

- [x] 구성: 조각 상한과 겹침 256·32, 512·64(기본), 512·128, 1024·128의 넷, 기본 청킹에서 후보 수 20, 50(기본), 100의 셋이다. 구성마다 `rag_eval` 머리의 새 데이터베이스에 색인해 빠른 실행의 보고서를 낸다. 조각 크기를 바꾼 구성의 임베딩은 로컬에서 새로 계산하고 커밋하지 않는다.
- [x] 보고서, 구성 파일, 돌린 명령, 장치와 걸린 시간을 `.scratch/search-eval/probes/experiments/`에 두고 프로브 README 표에 행을 더한다.
- [x] 판단용 숫자도 함께 정리한다. 키워드만 줄(`ts_rank`에 IDF가 없다는 판단과 토큰을 OR로 잇는 동작. 스토리 10), 필터 질의의 적중률과 HNSW 계획의 벡터 후보가 모자란 질의의 비율(좁은 필터의 정확 스캔 분기. 스토리 9)이다. 이 숫자로 무엇을 고칠지는 이 티켓에서 정하지 않는다(명세 Out of Scope).
- [x] 구성마다의 숫자를 한 표로 사용자에게 보이고 **멈춘다**. 사용자가 기본값을 바꾸기로 승인하면 이 PR에서 설정의 기본값, core 명세의 설정 절, 묶음의 `config.json`, 추론 기록, `baseline-fast.json`을 함께 고치고, 리랭크 기록이나 `baseline-full.json`이 이미 있으면 그것도 다시 만들어 승인을 받는다(명세 "설정 실험과 참고 측정", "CI 게이트와 기준 보고서"). 승인과 고른 값을 `## Comments`에 사용자의 글 그대로 적는다. 바꾸지 않기로 하면 그 판단만 적는다.
- [x] 검사 넷이 초록이다.

## Comments

- 2026-11-17 실험. 구성 여섯(조각 상한·겹침 256·32, 512·64, 512·128, 1024·128과 기본 청킹의 후보 수 20, 50, 100)을 GPU 임베딩 TEI(`turing-1.9.4`, GTX 1660 Ti)로 돌려 빠른 실행(`run --through fused --records off --config`)의 보고서를 `.scratch/search-eval/probes/experiments/chunking-candidates/`에 두었다. 명령, 장치, 걸린 시간, 표는 그 폴더의 `README.md`와 `summary.md`다. 합친 뒤 줄의 상위 5 적중률(사람 질의 / 키워드형 질의, %): 256·32 69.7 / 77.4, 512·64(기본) 83.2 / 80.6, 512·128 82.6 / 77.4, 1024·128 83.2 / 80.0, 후보 20 81.3 / 84.5, 후보 100 82.6 / 81.9. 질의 한 개가 0.65%p라 1~2개 차이는 우열을 말하지 않는다.
- 2026-11-17 기본 구성(`c512-64`)의 합친 뒤 줄은 커밋된 `baseline-fast.json`과 상위 1·3·5·10 적중률, MRR, 재현율, 놓친 질의의 수가 같다(nDCG@10만 최대 0.0002 다르다). 벡터만·키워드만 줄은 질의 1~2개씩 달랐다. 이 실험은 임베딩을 GPU에서 새로 계산했고 기준은 기록을 읽은 것이라, 그 차이로 본다(어림).
- 2026-11-17 판단용 숫자. 기본 구성의 키워드만 줄 상위 5 적중률은 사람 질의 49.7%, 키워드형 질의 58.7%이고 벡터만은 사람 질의 89.7%, 합친 뒤는 83.2%다. 필터가 붙은 질의는 사람 질의 목록에만 20개 있고(키워드형에는 없다), HNSW 계획의 벡터 후보가 모자란 질의는 여섯 구성 모두 0건이다. 이 숫자로 무엇을 고칠지는 정하지 않았다(명세 Out of Scope).
- 2026-11-17 1024·128은 도구의 코드 기본값(TEI 배치 32, 시간 제한 60초)에서 색인이 끝나지 않았다. 첫 시도 약 37분 동안 `job_finished` 줄 50개 가운데 30개가 성공이고 20개가 `embedding_unavailable`로 재대기열에 들어가(저장소 밖 로그를 손으로 센 값이다) 멈췄고, 원인(조각 1024 · 배치 32의 요청이 커서인지, 그 시각에 다른 세션이 GPU를 함께 써서인지)은 가르지 않았다. 그 구성만 커밋하지 않은 임시 변경(`settings.py`의 배치 8, 시간 제한 120초)으로 다시 돌린 뒤 되돌렸다. 나머지 다섯은 코드 기본값 그대로다. 조각 상한을 올리는 쪽을 고르면 `RAG_TEI_BATCH_SIZE`와 `RAG_TEI_TIMEOUT_SECONDS`를 함께 봐야 한다는 뜻이다.
- 2026-11-17 사용자에게 구성마다의 숫자를 한 표로 보이고 멈췄다. 사용자의 답: "유지". 조각 상한·겹침(512·64)과 후보 수(50)의 기본값을 바꾸지 않는다. 그래서 이 PR은 설정의 기본값, core 명세의 설정 절, 묶음의 `config.json`, 추론 기록, `baseline-fast.json`, `baseline-full.json`을 고치지 않는다. 후보 수의 효과는 리랭커를 넣은 실험(티켓 17)이 다시 본다.
- 2026-11-17 구성 `c512-64-k20`과 `c512-64-k100`은 데이터베이스를 새로 만들지 않고 `c512-64`의 색인을 그대로 써서 `run`만 돌렸다. 첫 항목의 "구성마다 새 데이터베이스"에서 벗어난 것이고, 임베딩 모델·차원·청킹이 같고 후보 수만 다른 구성은 같은 데이터베이스에서 돌린다는 `compose.eval.yml` 머리 주석의 길을 따랐다(조각 크기를 바꾼 네 구성은 모두 새 데이터베이스다).
