# search-eval 명세: 평가 세트로 검색의 적중률을 재고 기준 보고서보다 떨어지면 CI가 막는다

**Status:** ready-for-agent
**기능 계획:** `.scratch/search-eval/plan.md`
**근거:** ADR 0017, 0018, 0019와 ADR 0015 이력 2026-11-12, ADR 0018 이력 2026-11-13, ADR 0007 이력 2026-11-13, 설계 일지 `docs/journal/2026-11-12-2108-search-eval-design.md`(물은 것과 답, 합의 요약, `## 다음`), PR #27의 마지막 코멘트(봇 둘째 회차에서 명세로 넘긴 둘), `GLOSSARY.md`, 프로브 `.scratch/search-eval/probes/`(README 표), core 16의 프로브 `.scratch/core/probes/search-latency/`와 그 티켓의 일지 `docs/journal/2026-11-13-0615-search-latency-probe.md`(이 세션 도중인 2026-11-13에 dev에 병합되었다. PR #31). 설계 인터뷰는 하지 않았고(to-spec), 설계가 정하지 않았거나 측정이 전제를 바꾼 것 일곱을 2026-11-13에 사용자에게 물었다(테스트 이음매, 후보 목록을 확정하는 때, 묶음의 규모, 하락폭, 모델이 계산한 결과를 다루는 방식, 전체 게이트의 때, 리랭커의 기본을 정하는 때). 전체 게이트의 때는 GPU로 돌려 본 뒤 다시 물어 답이 바뀌었다("전체 게이트와 리랭커" 절). 티켓 세션(2026-11-13, 일지 `docs/journal/2026-11-13-1716-search-eval-tickets.md`)이 spec-reviewer의 명세 검토를 돌려, 그 지적과 사용자가 고른 넷(진단용 검색의 계획, 기록의 변조를 막는 길, 내용 해시에서 판정 칸을 빼는 것, ADR 0018 이력)을 반영했다. ADR 0018 이력 2026-11-13 둘("평가는 후보를 정확 스캔으로 뽑고, 추론 기록의 해시가 바뀌면 승인을 받는다", "푸시에서는 바뀐 경로를 보지 않고 빠른 게이트를 늘 돌린다")이 그 세션의 것이다.
**표시와 수:** 결정을 적은 항목마다 머리에 표시 하나를 단다. 사실만 적은 문단(Problem Statement, Solution, User Stories, Further Notes의 메모)에는 달지 않는다. `[넘겨받음]`은 설계(ADR, 일지의 합의 요약)가 정한 것을 옮긴 것, `[사용자 선택]`은 이 세션에서 사용자가 고른 것, `[정함]`은 이 명세가 정한 것, `[이력]`은 ADR에 이력을 더한 것, `[거절]`은 두지 않기로 한 것이다. 본문의 표시 수는 `[넘겨받음]` 17, `[사용자 선택]` 10, `[정함]` 82, `[이력]` 3, `[거절]` 8이다. 항목 여럿에 표시 하나를 함께 다는 방식은 쓰지 않았고, 수는 본문을 고칠 때마다 `grep`으로 다시 센다(to-spec 스킬 3단계).

이 명세는 `GLOSSARY.md`의 말만 쓴다. 코드 식별자, 설정 이름, 파일 이름, JSON 칸 이름은 영어 그대로다. 구현 파일의 경로는 적지 않고, 규칙 문서·ADR·테스트 선례의 경로와 이 기능이 새로 두는 재료의 자리만 적는다.

명세 안에서만 쓰는 말은 다음과 같다. **단계**는 검색 흐름에서 순위를 따로 재는 네 자리(벡터만, 키워드만, 합친 뒤, 리랭크 뒤)다. **닿는다**는 검색된 조각이 기대 근거의 자리를 담고 있다는 뜻이다(적중의 단위 절). **빠른 게이트**와 **전체 게이트**는 ADR 0018의 두 단이다. 빠른 게이트는 리랭커 없이 합친 뒤까지 재고, 전체 게이트는 리랭크 뒤까지 잰다. **빠른 실행**과 **전체 실행**은 그 둘이 돌리는 평가이고(`run --through fused`와 `run --through rerank`), 게이트 밖에서 손으로 돌려도 같은 이름으로 부른다. **묶음**은 평가 세트 하나가 든 폴더 전체(문서 파일, 문서 목록, 기대 근거, 질의 목록, 구성, 기록)다. ADR 0018이 "공공 문서 묶음"이라 부른 것이 그 하나이고, 용어집이 그룹의 Avoid로 든 "문서 묶음"과는 다른 것을 가리킨다. **유형 표지**는 질문에 미리 다는 낱말이고(답이 표에 있다 같은) **탈락 지점**은 놓친 질의가 검색 흐름의 어디에서 떨어졌는지를 가리키는 낱말이다. 둘 다 ADR 0018의 말이고 낱말의 목록은 평가 세트의 형식 절과 놓친 까닭 절에 있다. **하락폭**은 기준 보고서의 값에서 새 값을 뺀 차가 그보다 크면 게이트가 실패하는 크기다. **추론 기록**은 모델이 계산한 결과(임베딩 벡터, 리랭크 점수)를 글의 해시를 열쇠로 저장해 다시 쓰는 파일이다. **요청 지문**은 TEI 어댑터가 추론 요청에 싣는 것 가운데 글과 질의와 모델 이름을 뺀 것(끝점의 경로와 요청 매개변수)의 해시다(추론 기록 절). **판정 파일**은 LLM 관련성 판정의 결과를 저장해 다시 쓰는 파일이다.

## Problem Statement

검색 서버를 고치는 사람은 청킹, 임베딩 모델, 키워드 토큰, 리랭커, 검색 SQL을 바꿀 때마다 검색이 전보다 잘 찾는지 못 찾는지를 알 길이 없다. 운영 질문은 남기지 않으므로(ADR 0004) 실제 쓰임에서 품질을 읽을 수도 없다. core 명세는 조각 크기와 겹침, 후보 수, 리랭커의 효과, 품사 규칙, 좁은 필터의 정확 스캔, 시멘틱 청킹의 판정을 모두 search-eval이 숫자를 낸 뒤에 하기로 미뤘는데, 그 숫자를 낼 도구가 없다. 공개 시연을 보는 사람은 이 서버가 한국어 공공 문서를 얼마나 잘 찾는지 근거를 보고 싶어 한다. 검색 도구를 쓰는 클라이언트는 색인에 답이 없는 질의에도 관련 없는 조각을 `top_k`개 받고, 점수가 낮은 조각을 서버 쪽에서 거를 길이 없다.

## Solution

저장소에 공공 문서 묶음을 둔다. 법령과 행정규칙을 뼈대로 한 문서 40개 안팎과, 질문마다 찾아야 하는 자리(기대 근거), 그 자리를 겨냥한 질의 목록 둘(사람이 묻는 문장, 키워드형)이다. 개발자가 명령줄 도구로 묶음을 색인하고 평가를 돌리면, 질의 목록마다 단계별 적중률과 MRR, 재현율, nDCG가 든 보고서가 JSON과 Markdown으로 나온다. 보고서는 놓친 질문을 유형과 탈락 지점으로 나눠 세고, 저장된 LLM 관련성 판정이 있으면 참고 숫자를 함께 싣는다.

CI는 검색에 영향을 주는 PR마다 빠른 게이트를 돌려, 커밋해 둔 기준 보고서보다 상위 5 적중률이나 MRR이 정한 폭 넘게 떨어지면 실패한다. 모델이 계산한 결과는 추론 기록으로 저장소에 커밋해 CI가 다시 계산하지 않으므로, 같은 커밋의 평가는 어느 기계에서나 기록에 든 같은 벡터와 점수를 쓴다(합친 점수가 같은 조각끼리의 순서는 색인마다 달라질 수 있다. 진단용 검색과 단계 절). 리랭크 점수의 기록은 개발 PC의 GPU로 만들고, main으로 가는 PR의 전체 게이트가 그 기록으로 리랭크 뒤 줄을 본다. 리랭커가 CPU에서 느리다는 제품 쪽의 문제는 core 16이 재어 넘겼고, 이 기능의 리랭커 켬·끔 실험이 품질 숫자를 낸 뒤 사용자가 길을 고른다("전체 게이트와 리랭커" 절). 평가의 핵심은 제품 코드의 유스케이스라서, 관리자 페이지가 나중에 같은 평가를 화면으로 연다.

## User Stories

1. As a 개발자, I want 명령 하나로 묶음의 문서를 색인하고 싶다, so that 평가할 색인을 손으로 조립하지 않는다.
2. As a 개발자, I want 명령 하나로 평가를 돌려 보고서 파일을 받고 싶다, so that 검색을 고친 뒤 품질이 어떻게 달라졌는지 바로 본다.
3. As a 개발자, I want 보고서가 질의 목록마다 단계별 줄(벡터만, 키워드만, 합친 뒤, 리랭크 뒤)을 내기를 바란다, so that 품질이 어느 단계에서 얻어지고 잃는지 안다.
4. As a 개발자, I want 상위 1·3·5·10 적중률, MRR, 재현율, nDCG@10을 한 보고서에서 보고 싶다, so that 바깥의 수치와 나란히 읽는다.
5. As a 개발자, I want 사람이 묻는 문장과 키워드형 질의의 숫자를 따로 보고 싶다, so that 클라이언트의 모델이 지은 검색어에서 약한지 안다.
6. As a 개발자, I want 놓친 질문이 어느 단계에서 떨어졌는지(색인에 없음, 후보에 못 듦, 합치기에서 밀림, 리랭크에서 밀림) 보고 싶다, so that 고칠 자리를 좁힌다.
7. As a 개발자, I want 놓친 질문의 질의와 기대 근거 사이의 낱말 겹침을 보고 싶다, so that 낱말이 달라 놓친 것을 가린다.
8. As a 개발자, I want 표·그림·문서 여럿 같은 유형마다 적중률을 보고 싶다, so that 어느 유형의 문서에서 약한지 안다.
9. As a 개발자, I want 필터가 붙은 질의의 숫자를 따로 보고 싶다, so that 좁은 필터에서 정확 스캔 분기가 필요한지 판단한다.
10. As a 개발자, I want 키워드만 줄을 보고 싶다, so that `ts_rank`에 IDF가 없다는 판단과 토큰을 OR로 잇는 동작을 숫자로 본다.
11. As a 개발자, I want 평가가 실제 검색과 같은 SQL 뼈대로 재기를 바란다, so that 보고서의 숫자가 클라이언트가 받는 결과를 말한다.
12. As a 개발자, I want 검색에 영향을 주는 PR에서 CI가 기준 보고서 대비 하락을 막아 주기를 바란다, so that 모르는 사이에 검색 품질을 떨어뜨리지 않는다.
13. As a 개발자, I want 문서만 고친 PR에서는 빠른 게이트가 돌지 않고 필수 검사가 통과하기를 바란다, so that 무관한 PR이 느려지지 않는다.
14. As a 개발자, I want 게이트가 실패했을 때 어느 질의 목록의 어느 숫자가 얼마나 떨어졌는지 보고 싶다, so that 원인을 찾는다.
15. As a 개발자, I want CI가 올린 보고서를 산출물로 내려받고 싶다, so that 로컬에서 재현하지 않고도 숫자를 본다.
16. As a 개발자, I want 모델이 이미 계산한 글은 다시 계산하지 않기를 바란다, so that CPU만 있는 CI와 로컬에서 평가가 몇 분 안에 끝난다.
17. As a 개발자, I want 추론 기록에 없는 글이 많으면 CI가 까닭과 고치는 명령을 알려 주며 실패하기를 바란다, so that 몇 시간짜리 실행에 매달리지 않는다.
18. As a 개발자, I want 조각 크기와 겹침, 후보 수를 바꾼 구성으로 같은 평가를 돌리고 싶다, so that 기본값을 숫자로 정한다.
19. As a 개발자, I want 공개 데이터셋으로 참고 측정을 돌리고 싶다, so that 사람이 만든 질문으로 한 번 더 확인한다.
20. As a 개발자, I want 묶음의 형식이 틀렸거나 글귀가 문서에 없으면 평가 전에 오류로 알고 싶다, so that 세트의 실수를 검색의 실패로 세지 않는다.
21. As a 사용자(검수자), I want 에이전트가 쓴 질문과 기대 근거의 초안을 검수해 확정하고 싶다, so that 평가 세트를 믿을 수 있다.
22. As a 사용자, I want 묶음에 담을 문서의 후보 목록을 출처와 이용 조건과 함께 보고 확정하고 싶다, so that 저장소에 재배포해도 되는 문서만 든다.
23. As a 사용자, I want 기준 보고서를 바꾸는 커밋마다 숫자의 앞뒤 차이를 보고 승인하고 싶다, so that 품질 하락이 기준 갱신으로 묻히지 않는다.
24. As a 사용자, I want 기대 근거와 질의 목록을 고치는 변경도 숫자의 앞뒤 차이와 함께 승인하고 싶다, so that 세트를 고쳐 숫자를 맞추는 일이 없다.
25. As a 사용자, I want LLM API를 부르는 실행 전에 예상 건수와 비용을 보고 승인하고 싶다, so that 모르는 비용이 나가지 않는다.
26. As a 사용자, I want 조각 크기, 겹침, 후보 수의 기본값을 바꾸기 전에 실험 보고서를 보고 승인하고 싶다, so that 기본값이 근거 없이 바뀌지 않는다.
27. As a 사용자, I want 리랭크 점수의 분포를 보고 최소 점수를 구현할지 정하고 싶다, so that 통하지 않는 문턱을 계약에 넣지 않는다.
28. As a 개발자, I want LLM 관련성 판정의 숫자 둘(상위 10개의 관련 비율, 기대 근거에 닿은 조각의 일치 비율)을 보고서에서 보고 싶다, so that 기대 근거가 빠뜨린 관련 조각의 크기를 가늠한다.
29. As a 개발자, I want 기대 근거에 없는데 LLM이 관련 있다고 본 조각의 목록을 받고 싶다, so that 사용자가 확인한 것을 기대 근거에 더한다.
30. As a 개발자, I want 판정 실행이 끊겨도 이미 받은 판정을 다시 부르지 않고 이어 가기를 바란다, so that 같은 비용을 두 번 쓰지 않는다.
31. As a 개발자, I want CI가 키 없이 저장된 판정만으로 LLM 숫자를 내기를 바란다, so that CI에 비밀과 비용이 들지 않는다.
32. As a 운영자, I want 판정기가 끝점 주소, 모델, 키를 모두 설정했을 때만 조립되기를 바란다, so that 설정하지 않은 설치에서 문서 조각과 질문이 밖으로 나가지 않는다.
33. As a 운영자, I want 키와 판정 요청·응답의 본문이 로그에 남지 않기를 바란다, so that 비밀과 문서 내용이 새지 않는다.
34. As a MCP 클라이언트 개발자, I want `search`에 `min_score`를 주어 리랭크 점수가 낮은 조각을 빼고 싶다, so that 근거가 약한 조각이 모델의 입력에 쌓이지 않는다.
35. As a MCP 클라이언트 개발자, I want 거른 뒤 남은 조각이 없으면 오류가 아니라 빈 결과를 받고 싶다, so that 근거 없음과 고장을 가른다.
36. As a MCP 클라이언트 개발자, I want 리랭커가 없는 지식베이스에 `min_score`를 주면 `invalid_argument`를 받고 싶다, so that 걸러졌다고 잘못 믿지 않는다.
37. As a MCP 클라이언트 개발자, I want 결과의 `format_version`이 `1.1.0`인지로 서버가 `min_score`를 아는지 확인하고 싶다, so that 옛 서버가 인자를 조용히 버리는 경우를 가른다.
38. As a 운영자, I want 지식베이스에 최소 점수의 기본값을 두고 싶다, so that 클라이언트를 고칠 수 없는 설치에서도 낮은 점수의 조각을 거른다.
39. As a 공개 시연을 보는 사람, I want 공공 문서 묶음의 적중률 보고서를 저장소에서 읽고 싶다, so that 이 서버가 한국어 문서를 얼마나 잘 찾는지 근거로 본다.
40. As a admin을 설계하는 사람, I want 평가의 채점과 지표와 보고서가 명령줄 도구가 아니라 유스케이스에 있기를 바란다, so that 관리자 페이지가 핵심을 옮기지 않고 입구만 연다.

## Implementation Decisions

### 자리와 층

- [넘겨받음] 평가의 핵심(채점, 지표, 보고서)은 `app`의 유스케이스이고 포트만 부른다. 이번 입구는 저장소의 명령줄 도구이며 제품 이미지의 관리 명령으로는 내지 않는다. 관리자 페이지의 등록·실행·결과 화면, 관리 API, 저장 표는 admin이 받는다(ADR 0018).
- [정함] 놓친 까닭의 자동 분류와 기준 보고서와의 견줌도 같은 유스케이스에 둔다. admin이 평가를 화면으로 열 때 이 둘도 함께 쓰기 때문이다.
- [정함] 명령줄 도구는 `tools/search_eval.py`이고 `uv run python tools/search_eval.py <하위 명령>`으로 부른다. 인자 해석과 조립만 하고, 파일 형식의 읽기와 쓰기(묶음, 보고서, 추론 기록, 판정 파일)는 `adapters`에, 값과 계산은 `domain`과 `app`에 둔다. `tools/`는 이미지에 실리지 않는다(`.dockerignore`의 허용 목록을 읽었다). 그래서 평가를 부르는 입구는 admin이 열 때까지 이미지에 없다.
- [정함] 재료의 자리는 저장소 루트의 `evals/`다. 공공 문서 묶음은 `evals/public-docs/`이고, 그 안에 묶음의 머리 `eval-set.json`, 구성 `config.json`, 문서 파일 폴더 `documents/`, 문서 목록 `documents.json`, 기대 근거 `evidence.jsonl`, 질의 목록 `queries-human.jsonl`과 `queries-keyword.jsonl`, 추론 기록 폴더 `records/`, 판정 파일 `judgments.jsonl`, 사람 판정 `miss-review.jsonl`, 기준 보고서 `baseline-fast.json`과 `baseline-full.json`을 둔다. 평가 전용 compose는 루트의 `compose.eval.yml`이다. 새 최상위 폴더와 도구를 넣는 티켓이 `README.md`의 트리와 `.scratch/plan-head.md`의 목표 배치를 같이 고친다.
- [정함] 구성 `config.json`은 평가가 재는 색인과 검색의 설정을 적는 원천이고, 끝점 주소와 키는 들지 않는다. 칸은 `embedding_model`, `embedding_dimensions`, `reranker_model`, `chunking`(`strategy`, `max_tokens`, `overlap_tokens`), `search_candidates`, `tei_version`, `judge_model`, `judge_prompt_version`이다. `embedding_model`부터 `search_candidates`까지는 제품 설정 `RAG_DEFAULT_EMBEDDING_MODEL`, `RAG_DEFAULT_EMBEDDING_DIMENSIONS`, `RAG_DEFAULT_RERANKER_MODEL`, `RAG_DEFAULT_CHUNKING_STRATEGY`, `RAG_DEFAULT_CHUNK_TOKENS`, `RAG_DEFAULT_CHUNK_OVERLAP_TOKENS`, `RAG_SEARCH_CANDIDATES`에 대응한다. 공공 문서 묶음의 첫 값은 제품의 기본값(`BAAI/bge-m3`, 1024, `BAAI/bge-reranker-v2-m3`, `structure_first`, 512, 64, 50)이다(설정 코드를 읽었다). 도구는 이 값들을 환경 변수가 아니라 `config.json`에서만 읽고, 환경에서 받는 것은 데이터베이스 주소, 데이터 폴더, 임베딩 끝점, 리랭커 끝점(없어도 된다), 판정기의 설정 셋뿐이다(앞의 넷은 평가 전용 이름으로만 받는다. 아래 "평가 전용 데이터베이스" 항목). 그래서 묶음의 내용 해시가 같으면 재는 구성도 같다. 도구는 제품의 설정 객체를 환경 변수와 작업 폴더의 `.env`를 읽지 않게 지어, `config.json`과 위 환경 값에서 오지 않은 칸(파싱 한도, TEI 배치 크기 같은)은 코드의 기본값이 된다. 제품의 설정 객체는 `RAG_*` 환경 변수와 `.env`를 읽으므로(`src/rag_engine/adapters/settings.py`를 읽었다) 그대로 지으면 개발자의 `.env`가 파싱 한도를 바꿨을 때 같은 묶음이 다른 보고서를 내기 때문이다(티켓 세션의 명세 검토가 짚었다). `index`, `run`, `judge`는 `--config`로 다른 구성 파일을 받을 수 있고(설정 실험과 참고 측정 절), 주지 않으면 묶음의 `config.json`이다.
- [정함] 하위 명령은 여섯이다. `validate`는 묶음의 형식과 목록을 보고, `--indexed`를 주면 색인된 데이터베이스에서 글귀까지 본다. `index`는 데이터베이스를 준비하고 묶음의 문서를 수집해 작업을 끝까지 처리한다. `run`은 평가를 돌려 보고서를 쓰고, `--through fused`(빠른 실행. 합친 뒤까지)와 `--through rerank`(전체 실행. 리랭크 뒤까지) 가운데 하나를 반드시 받는다. `compare`는 보고서를 기준 보고서와 견줘 종료 코드로 답하고 `--gate fast`나 `--gate full`을 받는다. `judge`는 LLM을 불러 판정 파일을 채운다. `inspect`는 질의 목록의 이름과 기대 근거의 `id`를 받아 그 질의의 글, 기대 근거, 단계마다의 상위 조각의 글을 표준 출력에 찍는다(보고서 절). 종료 코드는 0(문제 없음), 1(묶음이나 색인의 오류, 게이트 실패), 2(잘못된 인자)다.
- [정함] `index`는 제품과 같은 길로 색인을 만든다. `config.json`의 값과 환경의 끝점으로 설정을 지어, 스키마와 기본 지식베이스를 제품의 `migrate` 명령과 같은 코드로 만든다(도구가 표나 행을 따로 짓지 않는다). 그 뒤 제품의 수집 유스케이스와 작업자의 한 번 돌기 입구로 문서를 수집해 작업을 끝까지 처리한다. 수집하는 것은 문서 목록에 든 파일이고, 파일의 해시가 목록과 같은지를 수집하기 전에 본다(평가 세트의 형식 절의 `validate` 항목). 기본 지식베이스가 이미 있는 데이터베이스에서는 그 현재 판의 요소가 `config.json`과 같을 때만 이어서 하고, 다르면 아무것도 쓰지 않고 종료 코드 1을 낸다. 제품의 `migrate`는 다시 돌 때 기본 지식베이스의 설정을 덮어쓰는데(core 명세 관리 명령 절), 평가 도구가 이미 쓰는 데이터베이스에서 판 전환을 일으키지 않게 하려는 것이다. 문서의 키는 `documents/` 기준 상대 경로(POSIX 구분자)이고 `ingest` 명령의 규칙과 같다. 문서 목록의 `updated_at`을 수집 요청의 갱신일로 넘긴다. 색인이 실패한 문서가 하나라도 있으면 종료 코드 1이다. 구성을 바꾼 실험은 데이터베이스를 새로 만들어 돌린다.
- [정함] 평가 전용 데이터베이스. 평가 도구는 평가를 위해 만든 데이터베이스에만 붙는다. 데이터베이스 주소, 데이터 폴더, 임베딩 끝점, 리랭커 끝점은 평가 전용 이름 `RAG_EVAL_DATABASE_URL`, `RAG_EVAL_DATA_DIR`, `RAG_EVAL_EMBEDDING_URL`, `RAG_EVAL_RERANKER_URL`로만 받고, 제품의 `RAG_DATABASE_URL`, `RAG_DATA_DIR`, `RAG_DEFAULT_*`와 작업 폴더의 `.env`는 읽지 않는다. 데이터베이스에 붙는 하위 명령(`index`, `run`, `judge`, `inspect`, `validate --indexed`)은 앞의 셋 가운데 빠진 것이 있으면 돌지 않고 빠진 이름을 알린다(값은 찍지 않는다). 제품의 설정 객체는 환경의 `RAG_*`와 작업 폴더의 `.env`를 읽으므로(`src/rag_engine/adapters/settings.py`를 읽었다) 도구가 그 객체를 환경에서 그대로 읽으면 개발자의 `.env`가 가리키는 데이터베이스에 붙는다. 시험이 전용 이름 `RAG_TEST_DATABASE_URL`을 쓰고 그 값을 `compose.test.yml`의 머리 주석이 적는 것과 같은 방식이며, 평가 전용 이름의 값은 `compose.eval.yml`의 머리 주석이 적는다. 데이터베이스의 이름도 본다. 데이터베이스에 붙는 하위 명령은 `RAG_EVAL_DATABASE_URL`이 가리키는 데이터베이스의 이름이 `rag_eval`로 시작하지 않거나 주소에서 이름을 읽을 수 없으면 접속하지 않고 종료 코드 1을 내며 그 규칙을 알린다(주소는 찍지 않는다). 변수의 이름이 평가 전용이어도 그 값에 제품의 데이터베이스 주소를 잘못 적는 실수는 남고, 아래의 문서 판정은 문서가 없거나 묶음과 같은 문서만 든 제품의 데이터베이스를 가르지 못하기 때문이다(PR #34 봇 둘째 회차의 지적). `compose.eval.yml`은 데이터베이스의 이름을 `rag_eval`로 두고, 실험마다 새로 만드는 데이터베이스와 시험이 만드는 데이터베이스도 그 머리로 이름을 짓는다. 선례는 시험이다. `compose.test.yml`의 데이터베이스는 `rag_test`이고 시험이 만드는 데이터베이스는 `rag_test_<난수>`다(`compose.test.yml`과 `tests/conftest.py`를 읽었다). 이름은 관례라 그 머리로 이름을 지은 제품의 데이터베이스까지 막지는 못한다. 막으려는 것은 주소를 잘못 적는 실수다. 그리고 `index`, `run`, `judge`는 시작할 때 데이터베이스가 이 묶음의 것인지를 본다. 데이터베이스에 든 문서 가운데 키가 묶음의 문서 목록에 없거나 내용 해시가 그 키의 `sha256`과 다른 것이 하나라도 있으면 아무것도 쓰지도 부르지도 않고 종료 코드 1을 낸다. 문서의 내용 해시는 수집이 원본 바이트에서 낸 sha256의 16진 소문자 글이므로(`src/rag_engine/app/ingest.py`를 읽었다) 문서 목록의 `sha256`도 같은 표기로 적어 글자 그대로 대 본다. 키만 보면 같은 키에 다른 내용이 든 데이터베이스가 지나가므로 내용까지 본다(PR #34 봇 첫 회차의 지적). 이 판정을 지난 데이터베이스의 문서는 모두 공개 묶음의 문서와 바이트가 같다. 데이터베이스에 묶음의 표지를 따로 적어 대 보는 길은 쓰지 않는다. 제품의 스키마에 평가만 쓰는 표를 더해야 하는데 위 항목이 도구가 표를 따로 짓지 않게 했고, 밖으로 나가는 것은 문서의 내용이라 내용 해시가 그것을 직접 가르기 때문이다. 문서가 하나도 없는 데이터베이스는 이 판정으로 가를 수 없어, 그런 데이터베이스에서는 이름의 판정과 위 항목의 요소 판정이 남는다. `index`는 이 판정과 위 항목의 요소 판정을 스키마를 올리기 전에 하며, 스키마가 없는 빈 데이터베이스는 지나가고 스키마의 판이 이 체크아웃이 올릴 판과 다른 데이터베이스는 거부한다(평가 데이터베이스는 새로 만들면 된다). 묶음에서 문서를 빼거나 문서 파일의 내용을 바꾼 뒤에도 데이터베이스를 새로 만든다. 까닭은 둘이다. `migrate`와 같은 코드는 스키마를 먼저 올리고 기본 지식베이스의 끝점과 리랭커 설정을 설정값으로 덮어쓰므로(`src/rag_engine/adapters/postgres/bootstrap.py`와 `src/rag_engine/app/default_records.py`를 읽었다) 평가용이 아닌 데이터베이스에 붙으면 그 설치의 검색을 바꾼다. 그리고 `judge`는 상위 조각의 글을 바깥의 LLM에 보내고 `index --records write`는 조각의 벡터를 공개 저장소에 커밋하는 파일에 쓰므로, 묶음 밖의 문서가 든 데이터베이스에서는 그 내용이 밖으로 나간다(원칙 V. 평가 세트를 공개 문서 묶음으로만 만든다는 것은 `docs/constitution/operations.md`의 설치처 정보 절이 정한다). 이 항목은 이 PR의 보안 리뷰가 낸 지적을 반영한 것이다.

### 진단용 검색과 단계

- [넘겨받음] `VectorIndex`에 진단용 메서드 하나를 더한다. 조각마다 벡터 순위, 키워드 순위, 합친 순위를 돌려주고 `search_candidates`와 같은 SQL 뼈대를 쓴다. 리랭크 점수는 평가 유스케이스가 실제 검색과 같은 `Reranker` 포트로 붙인다. MCP 도구로는 열지 않는다(ADR 0018).
- [정함] 메서드의 이름은 `diagnose_candidates`이고 `SearchQuery`와 키워드 인자 `scan`(아래 `[사용자 선택]` 항목)을 받아 `SearchDiagnosis`를 돌려준다. `SearchDiagnosis`는 `is_current`(질의한 판이 아직 현재 판인가)와 줄의 목록 `hits`이고, 줄 하나(`DiagnosedHit`)는 `SearchHit`(`hit`)에 `ordinal`(그 문서 안에서 조각의 순번. 조각 표에 있는 값이고 보고서가 조각을 가리키는 데 쓴다), `vector_rank`(없으면 `None`), `keyword_rank`(없으면 `None`), `fused_rank`를 더한 것이다. 줄은 벡터 후보와 키워드 후보의 합집합 전부이고(많아야 후보 수의 두 배), `fused_rank`는 그 합집합 안에서 RRF 점수 순으로 매긴 1부터의 순위다. `fused_rank`가 후보 수 이하인 줄이 `search_candidates`가 돌려주는 후보와 같다. RRF 점수가 같은 줄의 순서는 `search_candidates`와 같은 규칙으로 끊는다(지금은 조각의 id 순이다. 검색 SQL을 읽었다). 조각의 id는 색인할 때 새로 생기므로 점수가 같은 줄끼리의 순서는 색인마다 달라질 수 있고, 그것이 숫자를 얼마나 흔드는지는 실행 사이의 차를 재는 측정이 함께 본다(CI 게이트와 기준 보고서 절).
- [정함] 두 메서드가 같은 SQL 뼈대를 쓴다는 조건은 둘로 지킨다. 첫째, 벡터 쪽과 키워드 쪽의 CTE, 필터와 그룹 집합의 조건, RRF 점수의 식을 짓는 함수를 하나로 두고 두 문장이 그것을 함께 쓴다. 두 문장이 다른 곳은 합친 뒤의 자르기와 마지막 `SELECT`뿐이다. `SET LOCAL hnsw.ef_search`와 `hnsw.iterative_scan`도 같은 규칙으로 건다. 둘째, 어댑터 시험이 같은 질의에서 `diagnose_candidates`(아래 항목의 색인 스캔 `CandidateScan.INDEX`)의 `fused_rank`가 후보 수 이하인 줄이 `search_candidates`의 후보와 순서, 조각, RRF 점수까지 같은지 대 본다(키워드가 빈 질의, 필터가 있는 질의, 한쪽에만 든 조각이 있는 질의). 선례는 `tests/adapters/test_vector_index_chunks.py`다.
- [사용자 선택] 평가의 단계 순위는 정확 스캔으로 뽑은 후보로 낸다. `diagnose_candidates`는 계획을 고르는 열거 `CandidateScan`을 키워드 인자 `scan`으로 받는다(불리언 플래그 인자를 만들지 않는다는 `CODING_STANDARDS.md`의 첫 판단 기준을 따랐다). `INDEX`는 실제 검색과 같은 HNSW 색인 계획이고 `EXACT`는 정확 스캔이다. `EXACT`이면 같은 트랜잭션에서 HNSW 색인을 쓰지 않는 계획(`SET LOCAL enable_indexscan = off` 같은)으로 같은 SQL 글을 돌린다. 평가는 단계 순위를 낼 때 `scan=CandidateScan.EXACT`로 부른다. 어댑터 시험이 `EXACT`일 때의 계획에 판의 HNSW 색인이 없는 것을 EXPLAIN으로 본다(core 07이 검색 질의의 색인 사용을 EXPLAIN으로 본 것이 선례다). 까닭은 HNSW 색인이 지을 때마다 다른 후보를 낼 수 있어서다. 티켓 세션의 명세 검토가 테스트 PostgreSQL(pgvector 0.8.7)에 무작위 64차원 벡터 3,000개를 같은 순서로 넣은 표 둘을 짓고 질의 100개를 돌리자, 상위 50이 순서까지 견줘 다른 질의가 35개였다(프로브 `.scratch/search-eval/probes/repeat/hnsw_repeat.sql`로 손으로 봤다. 티켓 세션이 커밋하며 다시 돌린 출력 `hnsw_repeat_out.txt`에서는 27개였다. 집합 비교를 더해 한 번 더 돌린 출력 `hnsw_repeat_set_out.txt`에서는 순서로도 집합으로도 25개였고, 두 표의 상위 50이 함께 가진 후보는 최소 43개, 평균 49.55개였다. 실제 임베딩 벡터에서의 크기는 재지 않았다). 그러면 개발 PC의 색인으로 만든 리랭크 기록이 CI가 새로 지은 색인의 후보 쌍을 덮지 못해 전체 게이트가 코드와 무관하게 실패하고(전체 게이트의 모양 항목), 빠른 게이트의 실행 사이 흔들림도 커진다. 사용자가 2026-11-13 티켓 세션에서 세 선택지(평가만 정확 스캔으로 뽑기, CI가 빠진 쌍을 CPU 리랭커로 계산하기, 기록을 후보 수보다 넓게 만들기) 가운데 골랐다(ADR 0018 이력 2026-11-13 "평가는 후보를 정확 스캔으로 뽑고, 추론 기록의 해시가 바뀌면 승인을 받는다"). 값은 HNSW 근사로 잃는 몫이 단계의 숫자에 들지 않는 것이다. 그 몫은 필터가 붙은 질의에서만 따로 낸다(지표 절).
- [정함] 평가 유스케이스는 질의마다 실제 검색과 같은 준비를 한다. 현재 판에 적힌 모델·차원으로 질의를 임베딩하고, 같은 키워드 토크나이저로 토큰을 뽑고, 설정의 후보 수와 `CandidateScan.EXACT`로 `diagnose_candidates`를 한 번 부른다. 질의를 임베딩하는 끝점은 판에 적힌 것이 아니라 환경의 `RAG_EVAL_EMBEDDING_URL`이다. 판에 적힌 끝점은 `index`가 그때의 환경에서 적은 것이라, 로컬에서 TEI의 포트를 바꾼 뒤의 `run`이 옛 주소로 가지 않게 하려는 것이다. 현재 판의 모델이나 차원이 `config.json`과 다르면 평가하지 않고 종료 코드 1이다. 단계의 순위는 그 한 번의 결과에서 만든다. 벡터만은 `vector_rank` 순, 키워드만은 `keyword_rank` 순, 합친 뒤는 `fused_rank`가 후보 수 이하인 줄의 그 순위, 리랭크 뒤는 합친 뒤의 후보 전부를 리랭크한 점수 순(점수가 같으면 합친 순위 순)이다. 키워드 토큰이 빈 질의는 키워드만 단계에서 결과가 없는 것으로 센다. 후보 수는 `config.json`의 `search_candidates`이고, 리랭커의 모델 이름도 지식베이스가 아니라 `config.json`의 `reranker_model`에서 읽는다. 리랭커의 끝점 없이 만든 기본 지식베이스에는 리랭커 모델이 없기 때문이다(설정 코드를 읽었다).
- [정함] 평가는 검색 유스케이스를 부르지 않고 검색의 조각(판 고르기, 질의 임베딩, 리랭크)을 함께 쓴다. 검색 유스케이스는 `top_k`로 자른 결과만 돌려주어 단계의 순위를 주지 못하기 때문이다. 검색 유스케이스의 시간 제한(`RAG_SEARCH_TIMEOUT_SECONDS`)은 평가에 걸지 않는다. 평가가 재는 것은 품질이고, 지연은 core 16의 프로브(`.scratch/core/probes/search-latency/`)가 쟀다.
- [정함] 평가 도중 판이 전환되면(`is_current`가 거짓) 평가를 오류로 끝낸다. 평가는 고정된 색인 하나를 재는 일이라 다시 하지 않는다.

### 평가 세트의 형식

- [넘겨받음] 평가 세트는 기대 근거와 질의 목록으로 나눈다. 같은 기대 근거에 질의 목록을 여럿 붙일 수 있고, 저장소는 사람이 묻는 문장으로 쓴 질의 목록과 키워드형 질의 목록을 함께 가진다. 형식에 판 칸을 두되 원칙 VII의 계약 목록에는 아직 넣지 않는다(ADR 0018).
- [정함] 묶음의 머리 `eval-set.json`은 `format_version`(첫 판 `"1.0.0"`), `name`, `documents`(문서 목록 파일), `evidence`(기대 근거 파일), `query_lists`(배열. 하나는 `name`, `style`(`question` 또는 `keyword`), `file`)를 든다. 도구는 major가 다른 판의 묶음을 거부한다. 이 판은 머리, 구성, 문서 목록, 기대 근거, 질의 목록, 사람 판정 `miss-review.jsonl`, 판정 파일 `judgments.jsonl`의 형식을 덮는다. 추론 기록의 형식은 `records/records.json`의 `format_version`(첫 판 `"1.0.0"`)이 따로 덮는다(티켓 세션의 명세 검토가 짚었다).
- [정함] 기대 근거 파일은 JSON Lines이고 줄 하나가 질문 하나다. 칸은 `id`(묶음 안에서 유일한 문자열), `evidence`(하나 이상의 배열), `tags`(유형 표지의 배열, 비어도 된다)다. 기대 근거 하나는 종류가 둘이다. `{"kind": "passage", "document": <키>, "passage": <글귀>}`와 `{"kind": "page", "document": <키>, "page": <쪽 번호>}`다.
- [정함] 유형 표지의 낱말은 넷이다. `table`(답이 표에 있다), `figure`(답이 그림에 있다), `multi_document`(문서 여럿을 이어야 답한다), `no_context`(조각만 떼어 보면 무엇에 관한 글인지 알 수 없는 자리다)다. 넷 밖의 낱말은 `validate`가 거부한다. 공개 데이터셋의 그림 유형 문항은 `figure`로 표시한다.
- [정함] 질의 목록 파일은 JSON Lines이고 줄 하나가 질의 하나다. 칸은 `evidence_id`(기대 근거의 `id`), `query`(질의 글), 선택 칸 `filter`다. `filter`의 모양은 검색 도구의 `filter`와 같다(`groups`, `updated_after`, `updated_before`). 한 질의 목록 안에서 같은 `evidence_id`는 한 번만 나오고, 질의 목록이 모든 기대 근거를 덮을 필요는 없다.
- [정함] 날짜와 시각의 형식. 문서 목록의 `updated_at`은 `YYYY-MM-DD`이고, `index`와 `validate`는 `adapters`의 함수 하나로 그날 00:00 한국 표준시(`+09:00`)의 시각으로 바꾼다. 법령과 공공기관 문서의 공포일과 발행일이 한국의 날짜이기 때문이다. 질의의 `filter`에 든 `updated_after`와 `updated_before`는 오프셋이 있는 ISO 8601 시각이어야 하고(검색 도구의 필터가 받는 모양과 같다. `src/rag_engine/server/tool_models.py`를 읽었다) 오프셋이 없으면 세트의 오류다. 이 판(`"1.0.0"`)의 묶음에서 `filter`에 `groups`가 들면 세트의 오류다. `index`는 모든 문서를 기본 그룹에 넣으므로, 그룹 필터는 아무 문서에도 맞지 않거나 거르지 않는 것과 같아서다. 그룹을 만드는 길이 생겨 그룹 필터를 쓰는 묶음을 넣는 작업이 이 판정을 고친다(티켓 세션의 명세 검토가 짚었다).
- [넘겨받음] 질의에 필터를 적을 수 있게 형식을 연다. 좁은 필터를 판단할 숫자를 얻기 위해서다(일지 합의 요약의 가정 12).
- [정함] 공공 문서 묶음의 첫 판에서 필터가 붙은 질의는 갱신일 기간만 쓴다. v0에는 그룹을 만드는 길이 없어(core 명세가 admin에 넘겼다) 그룹 필터를 겨냥한 문서 배치를 만들 수 없기 때문이다. 필터가 붙은 질의는 사람 질문 목록에 20개 안팎을 둔다(어림. 질문 150개 가운데 일부에 기간을 붙인다).
- [정함] `validate`가 보는 것. 형식과 판, `id`와 `evidence_id`의 짝, 유형 표지의 낱말, 필터가 붙은 질의의 기대 근거가 그 필터를 지나는지, 머리와 문서 목록이 가리키는 경로가 묶음 폴더 안인지, 문서 목록의 모든 파일이 있고 해시가 맞는지, 목록에 없는 파일이 `documents/`에 없는지, 용량 상한, 추론 기록의 판과 크기와 요청 지문(추론 기록 절), 그리고 `--indexed`를 주었을 때는 묶음의 모든 문서가 그 데이터베이스에 색인되어 있는지와 글귀마다 그 문서의 본문에 들어 있는지다. 색인되지 않은 문서가 하나라도 있으면 실패한다. 인자로 가르는 까닭은, 데이터베이스가 있는지로 가르면 빈 데이터베이스나 다른 데이터베이스를 가리켰을 때 글귀 검사가 조용히 빠져 초록이 되기 때문이다(티켓 세션의 명세 검토가 짚었다). 필터의 판정은 이렇다. 기간 필터가 붙은 질의의 기대 근거가 가리키는 문서는 모두 그 기간 안이어야 한다. 문서 목록의 `updated_at`을 `index`가 수집에 넘기는 것과 같은 시각으로 바꿔 검색의 필터와 같은 비교로 본다(`updated_after`는 그 시각을 포함하고 `updated_before`는 포함하지 않는다. `src/rag_engine/domain/entities.py`의 `SearchFilter`와 `src/rag_engine/adapters/postgres/vector_index.py`의 조건을 읽었다). 기간 밖의 문서가 하나라도 있으면 세트의 오류다. 필터가 거른 문서의 조각은 검색에 나오지 않으므로 그 질의는 검색의 품질과 무관하게 놓친 것으로 세어지고, 정확 스캔 분기를 판단하는 필터 질의의 숫자(지표 절)를 낮춘다. 하나가 아니라 모두를 요구하는 까닭은 재현율과 nDCG의 분모가 기대 근거의 수이기 때문이다(PR #34 봇 셋째 회차의 지적). 묶음의 파일만으로 판정하므로 색인 없이 본다. 그룹 필터는 이 판에서 세트의 오류다(날짜와 시각의 형식 항목). 경로의 판정은 이렇다. 도구가 묶음에서 여는 파일은 읽을 때나 쓸 때나 풀린 경로가 묶음 폴더 안이어야 하고, 문서의 `key`는 `documents/` 안이어야 한다. 머리의 `documents`, `evidence`, `query_lists`의 `file`이 가리키는 파일과 이름이 정해진 파일(`config.json`, `records/`와 그 안의 기록 파일, `judgments.jsonl`, `miss-review.jsonl`, 기준 보고서)이 모두 든다. 절대 경로, `..`가 든 경로, 밖을 가리키는 링크(폴더가 링크인 경우도 든다)는 그 파일을 열기 전에 거부한다. 그래서 `index`, `run`, `judge`는 `records/`의 기록 파일이나 판정 파일이 묶음 밖을 가리키면 쓰지 않고 종료 코드 1을 내며, `validate`도 같은 판정을 한다. 읽는 파일만 판정하면 묶음에 든 링크 하나가 `--records write`나 `judge`의 쓰기를 묶음 밖의 파일로 보내는 길이 남는다(PR #34 봇 둘째 회차의 지적). 보고서를 쓰는 폴더와 `--config`로 준 구성 파일은 부르는 사람이 인자로 고른 자리라 이 판정의 대상이 아니다. 선례는 `ingest` 명령이 폴더 밖을 가리키는 링크를 거르는 것(`src/rag_engine/adapters/ingest_command.py`를 읽었다)과 `LocalBlobStore`가 키를 푼 경로가 데이터 폴더 밖이면 읽지도 쓰지도 않는 것이다(`src/rag_engine/adapters/blob_store.py`를 읽었다). `index`는 수집을 시작하기 전에, 스키마도 올리기 전에 문서 파일의 판정 셋(경로, 문서 목록의 모든 파일이 있고 해시가 맞는지, 목록에 없는 파일이 `documents/`에 없는지)을 하고, 하나라도 어긋나면 아무것도 쓰지 않고 종료 코드 1을 낸다. 수집에는 해시를 대 본 그 바이트를 넘긴다. `validate`를 따로 돌리지 않고 `index --records write`를 돌려도 문서 폴더에 잘못 놓인 파일의 벡터가 커밋하는 기록에 쓰이지 않게 하려는 것이다(PR #34 봇 둘째 회차의 지적). 이 형식을 읽는 코드는 `adapters`에 있어 admin이 설치처의 묶음에 다시 쓸 수 있고, 그때 묶음의 경로 칸이 서버의 다른 파일을 읽게 하는 길이 되지 않게 하려는 것이다(이 PR의 보안 리뷰가 낸 지적이다). 본문은 최신 파싱 결과에서 조각 글에 드는 블록의 글을 이은 것이다. 절을 가르는 제목 블록은 조각 글이 아니라 절 경로로만 가므로 뺀다(청킹 코드를 읽었다. 글이 조각 상한의 4분의 1을 넘는 제목 블록은 문단으로 다뤄져 본문에 든다). 글귀가 문서의 본문에 없으면 세트의 오류이고 검색의 실패로 세지 않는다.

### 적중의 단위

- [넘겨받음] 공공 문서 묶음은 문서와 원문 글귀로 적고, 그 문서의 조각 글에 그 글귀가 들어 있으면 닿은 것이다. 글귀가 조각의 경계에서 갈리면 놓친 것으로 센다. 공개 데이터셋은 문서와 쪽 번호로 본다. 조각 단위로 정답을 달지 않는 까닭은 청킹 설정을 바꾸면 조각의 경계가 달라지기 때문이다(ADR 0018).
- [정함] 글귀의 비교는 양쪽 글을 NFC로 정규화하고 공백류(공백, 탭, 줄바꿈)를 모두 지운 뒤 부분 문자열로 본다. PDF는 줄이 임의로 갈리고 파서마다 띄어쓰기가 달라, 공백을 살려 두면 같은 글이 다르게 읽힌다. 비교하는 조각의 글은 조각 글(`text`)이고 절 경로 줄은 넣지 않는다.
- [정함] 글귀는 파싱 결과의 본문 블록(문단, 표 같은)에서 옮긴 한 문장이나 구절이고 제목에서 옮기지 않는다. 제목은 조각 글에 들지 않아 닿을 수 없기 때문이다. 공백을 뺀 길이가 10자 이상 120자 이하다. 길수록 조각의 경계에서 갈리기 쉽고, 짧으면 다른 자리에도 나온다. 글귀가 그 문서 안에서 두 번 이상 나오면 `validate`가 경고한다(어느 자리에 닿아도 닿은 것으로 세기 때문이다).
- [정함] 쪽으로 적은 기대 근거는, 조각이 덮은 블록(`block_range`)의 쪽 번호 가운데 기대한 쪽이 있으면 닿은 것이다. 블록의 쪽 번호는 문서의 최신 파싱 결과에서 읽는다. 조각의 근거 위치에 실린 쪽은 첫 블록의 것뿐이라 두 쪽에 걸친 조각을 놓치기 때문이다.
- [정함] 기대 근거의 문서는 (원천, 키)의 키로 가리키고 조각의 문서가 그 문서일 때만 닿는다. 다른 문서에 같은 글귀가 있어도 닿은 것이 아니다.

### 지표

- [넘겨받음] 상위 1·3·5·10 적중률, MRR, 재현율, nDCG@10을 모두 계산한다. 기대 근거는 질문마다 하나 이상만 요구한다. 관련 문서를 빠짐없이 다는 방식은 나중으로 미루므로 재현율과 nDCG는 단 것만을 기준으로 한 값이다(ADR 0018).
- [정함] 지표의 정의. 상위 k 적중률은 상위 k개 안에 기대 근거 어느 하나에라도 닿은 조각이 있는 질의의 비율이다. MRR은 상위 10개 안에서 처음 닿은 조각의 순위의 역수(없으면 0)의 평균이다. 재현율은 상위 10개가 닿은 기대 근거의 수를 그 질문의 기대 근거의 수로 나눈 값의 평균이다. nDCG@10에서 기대 근거 하나는 처음 닿은 순위에서 한 번만 이득 1을 준다(겹침 때문에 같은 자리를 담은 조각이 여럿 나와도 한 번이다). 그래서 한 순위의 이득은 그 조각이 처음으로 닿은 기대 근거의 수이고, 대개 0이나 1이다. 이상적인 순위는 기대 근거의 수만큼(많아야 10) 맨 위부터 이득 1로 채운 것이다. 조각 하나가 기대 근거 둘에 처음 닿으면 값이 1을 넘을 수 있으므로 1에서 자른다. 잘리는 것은 이상적인 순위보다 좋은 결과뿐이다. 분모를 조각 하나가 주는 여러 이득까지 넣어 다시 정하지 않는 까닭은, 그러면 이상적인 순위가 색인의 조각 구성에 달려 청킹을 바꾼 실행끼리 값을 견줄 수 없게 되기 때문이다(지금의 분모는 기대 근거의 수에만 달려 있다). 잘려서 가려지는 양이 보이도록 보고서는 줄마다 nDCG가 잘린 질의의 수를 싣는다(PR #34 봇 첫 회차의 지적).
- [정함] 보고서의 줄은 질의 목록과 단계의 쌍마다 하나다. 유형 표지마다, 그리고 필터가 붙은 질의만으로도 같은 지표를 마지막 단계(빠른 실행은 합친 뒤, 전체 실행은 리랭크 뒤)에 대해 낸다. 질의 수가 0인 줄은 내지 않는다.
- [정함] 필터가 붙은 질의에는 숫자 하나를 더 낸다. HNSW 계획의 벡터 후보가 모자란 질의의 비율이다. 평가는 필터가 붙은 질의마다 `diagnose_candidates`를 `CandidateScan.INDEX`로 한 번 더 불러, 벡터 후보의 수가 후보 수와 정확 스캔의 벡터 후보 수 가운데 작은 것에 못 미친 질의를 센다. 정확 스캔도 필터를 지나는 조각이 후보 수보다 적으면 후보를 채우지 못하므로, 그 몫을 빼고 HNSW 때문에 모자란 것만 세려는 것이다. 좁은 필터에서 정확 스캔 분기가 필요한지는 이 비율과 필터 질의의 적중률로 판단한다(core 명세 "검색 흐름"의 거절 항목이 이 숫자를 기다린다). 이 숫자는 HNSW 색인을 지을 때마다 흔들릴 수 있어 게이트가 보지 않는다.

### 놓친 까닭

- [넘겨받음] 세 겹으로 본다. 질문에 미리 단 유형 표지, 진단용 검색이 알려 주는 탈락 지점과 낱말 겹침, 사람 판정이다. 사람 판정의 초벌은 Claude Code 세션이 하고 사용자가 확인한다(ADR 0018).
- [정함] 탈락 지점은 마지막 단계의 상위 10개에 닿은 조각이 없는 질의마다 하나를 붙인다. 아래 넷을 차례로 보아 처음 맞는 것이고, 닿는 조각 가운데 가장 멀리 간 것을 기준으로 삼는 셈이다. `no_matching_chunk`는 기대한 문서의 현재 판 조각 가운데 어느 것도 기대 근거에 닿지 않는 경우다(글귀가 조각의 경계에서 갈렸거나, 파싱이 그 글을 내지 못했거나, 문서가 색인되지 않았다). `not_in_candidates`는 닿는 조각이 색인에 있는데 어느 것도 벡터 후보에도 키워드 후보에도 들지 못한 경우다. `lost_in_fusion`은 닿는 조각이 어느 한쪽 후보에는 들었는데 합치기에서 밀린 경우다. 빠른 실행에서는 합친 순위가 10 안인 것이 없다는 뜻이고, 전체 실행에서는 합친 순위가 후보 수 안인 것이 없어 리랭커에 들어가지 못했다는 뜻이다. `lost_in_rerank`는 전체 실행에서만 나고, 닿는 조각이 리랭커에 들어갔는데 리랭크 뒤 순위가 10 밖인 경우다. 기대한 문서의 조각은 `VectorIndex.list_chunks`로 읽는다.
- [정함] 낱말 겹침은 글귀로 적은 기대 근거에만 낸다. 질의의 키워드 토큰 가운데 글귀의 키워드 토큰에 든 것의 비율이고, 같은 키워드 토크나이저를 쓴다. 질의에서 키워드 토큰이 하나도 나오지 않으면 분모가 0이라 값이 없다. 값이 없는 놓친 질의(쪽으로 적은 기대 근거의 질의, 키워드 토큰이 없는 질의)는 보고서에 `null`로 싣고 겹침이 0인 놓친 질의의 수에 넣지 않는다. 보고서는 그 밖의 놓친 질의마다 이 값을 싣고, 겹침이 0인 놓친 질의의 수를 따로 센다(분모가 0인 경우는 PR #34 봇 첫 회차의 지적으로 정했다).
- [정함] 사람 판정은 `miss-review.jsonl`에 줄 하나로 적는다. 칸은 `query_list`, `evidence_id`, `cause`, `confirmed`(사용자가 확인했는가)다. `cause`의 낱말은 다섯이다. `no_context`(조각에 문맥이 없어서), `table_or_figure`(표나 그림이어서), `vocabulary`(낱말이 달라서), `multi_document`(문서 여럿을 이어야 해서), `other`다. 보고서는 `confirmed`가 참인 줄만 까닭마다 센다. 색인 시점의 LLM 보강을 더할지는 `no_context`의 비율을 본 뒤 사용자가 정한다(기능 계획의 사용자가 넘긴 것 4).

### 보고서

- [넘겨받음] 보고서는 JSON과 Markdown 두 형식으로 낸다. 기준 보고서는 커밋하고 CI의 보고서는 산출물로 올린다(일지 합의 요약의 가정 4).
- [정함] `run`은 `report.json`과 `report.md`를 준 폴더에 쓴다. JSON이 원천이고 Markdown은 같은 값을 사람이 읽는 표로 옮긴 것이다. JSON의 칸은 `format_version`(첫 판 `"1.0.0"`), `eval_set`(이름, 판, 내용 해시, 문서·질문·질의의 수), `config`(쓴 구성), `index`(현재 판의 요소 넷과 조각 수), `stages`(잰 단계의 목록), `rows`(질의 목록과 단계마다의 지표와 nDCG가 잘린 질의의 수), `by_tag`, `filtered`, `misses`(놓친 질의마다 질의 목록 이름, 기대 근거의 `id`, 탈락 지점, 낱말 겹침. 값이 없으면 `null`), `miss_counts`, `human_causes`, `llm`(판정 숫자와 빠진 정답 후보의 목록. 없으면 `null`과 까닭), `score_distribution`(전체 실행에서만), `records`(추론 기록에서 읽은 수와 새로 계산한 수, 읽은 기록 파일마다의 sha256), `meta`(실행 시각과 커밋)다.
- [정함] 보고서에는 질의의 글과 조각의 글을 싣지 않고 식별자(질의 목록 이름, 기대 근거의 `id`, 문서의 키, 조각의 순번 `ordinal`)로 가리킨다. 이 유스케이스를 admin이 설치처의 평가에 다시 쓸 때 질문과 문서 내용이 보고서 파일로 번지지 않게 하기 위해서다(원칙 V). 빠진 정답 후보의 목록도 같은 식별자로 적는다. 글은 사람이 `inspect`로 열어 보고, `inspect`는 글을 표준 출력에만 찍고 파일로 쓰지 않는다. 조각의 순번은 같은 구성으로 색인한 데이터베이스에서만 같은 조각을 가리킨다.
- [정함] 묶음의 내용 해시는 머리, 문서 목록, 기대 근거, 질의 목록 파일의 바이트와 구성(바로 아래 항목이 정한 JSON)으로 계산한다. 문서 파일은 문서 목록의 해시로 대신한다. `meta` 칸은 견줌에서 뺀다.
- [사용자 선택] 구성은 내용 해시와 `compare`의 구성 비교에 파일의 바이트가 아니라 `judge_model`과 `judge_prompt_version`을 뺀 칸을 정렬한 JSON으로 들어간다. 두 칸은 검색의 숫자에 닿지 않는 참고 숫자(LLM 관련성 판정)의 열쇠인데, 넣으면 판정 모델이나 지시문의 판만 바꿔도 기준 보고서 둘이 모두 거부되어 승인과 전체 게이트의 수동 실행이 들기 때문이다. 티켓 세션의 명세 검토가 짚었고, 사용자가 2026-11-13에 두 선택지(두 칸을 뺀다, 그대로 두고 재료 티켓이 모든 칸을 처음부터 커밋한다) 가운데 골랐다.

### 공공 문서 묶음

- [넘겨받음] CI 게이트와 공개 시연은 직접 구성한 공공 문서 묶음(법령·행정규칙을 뼈대로 하고 공공누리 제1유형 일부)을 저장소에 커밋해 쓴다. 문서마다 출처, 이용 조건, 내려받은 날짜, 해시를 목록에 적고 용량 상한을 둔다. 후보 목록은 에이전트가 내고 사용자가 확정한다(ADR 0018).
- [사용자 선택] 규모는 문서 40개 안팎, 질문 150개 안팎, 문서 파일의 합 30MB 이하다. 사용자가 2026-11-13에 세 선택지(40·150·30MB, 20·80·15MB, 60·250·50MB) 가운데 골랐다. 질문 하나가 적중률 약 0.67%p다.
- [사용자 선택] 후보 목록은 이 명세가 아니라 재료를 넣는 티켓의 첫머리에서 확정한다. 그 티켓이 후보를 내려받아 이용 조건의 표시를 원문으로 확인하고 제품의 파서로 파싱해 본 뒤 목록을 사용자에게 보이고, 사용자가 확정한 것만 커밋한다. 사용자가 2026-11-13에 골랐다. 이 PR은 문서만 바꾸는 면제 PR이라 문서 파일을 실을 수 없고, 파서로 확인하는 일은 구현에 가깝다.
- [정함] 고르는 기준. 법령·행정규칙·고시(저작권법이 보호하지 않는 저작물)가 30개 안팎이고, 표와 그림이 많은 공공기관의 보고서·안내서 가운데 공공누리 제1유형 표시가 있는 것이 10개 안팎이다. 형식은 PDF, DOCX, HWPX 셋을 모두 담고 한 형식이 30개를 넘지 않는다. 제품의 파서가 글을 내지 못하는 문서(스캔본, HWP 5.0 바이너리)는 담지 않는다. 표가 든 문서가 10개 이상이고, 같은 주제를 다른 문서가 이어 다루는 짝(법률과 그 시행령 같은)이 5쌍 이상이다. 기본 구성으로 색인한 조각의 수가 3,000개 이하다(추론 기록 절의 상한).
- [정함] 문서 목록 `documents.json`의 칸은 문서마다 `key`(`documents/` 기준 상대 경로), `title`, `publisher`(낸 기관), `source_url`(내려받은 주소), `license`(이용 조건. `법령 등(저작권법 제7조)` 또는 `공공누리 제1유형`), `license_evidence`(그 표시를 확인한 자리. 문서 안의 쪽이나 내려받은 쪽의 주소), `downloaded_at`(날짜), `sha256`, `bytes`, `updated_at`(문서의 공포일이나 발행일. 필터 질의가 쓰는 갱신일. 공공누리 보고서 14개 가운데 10개는 파일에서 발행일을 확인하지 않아 공공데이터포털의 자료 기준일이다. 티켓 09 `## Comments`)다. 이용 조건은 원문의 표시로 확인한 것만 적는다(`docs/agents/issue-tracker.md`의 프로브와 근거 절).
- [넘겨받음] 질문과 기대 근거는 에이전트가 초안을 쓰고 사용자가 검수한다. 질문은 문서의 문장을 베끼지 않고 표현을 바꿔 묻는다. 키워드형 질의 목록도 같은 방법으로 만든다(ADR 0018).
- [정함] 질문의 배분. 유형 표지 `table`이 20개 이상, `multi_document`가 15개 이상, `no_context`가 15개 이상이다(유형별 숫자가 뜻을 가지려면 표본이 그만큼 필요하다. 어림). 문서 하나에 질문이 8개를 넘지 않는다. 키워드형 질의는 같은 질문을 명사 중심의 검색어 2~6낱말로 바꾼 것이고 문장으로 쓰지 않는다. 사용자의 검수는 질문과 글귀와 유형 표지를 한 표로 보고 하며, 검수한 날짜를 그 티켓의 `## Comments`에 적는다.

### 추론 기록

- [사용자 선택] 모델이 계산한 결과는 추론 기록으로 저장소에 커밋하고, 기록에 있는 글은 다시 계산하지 않는다. 사용자가 2026-11-13에 세 선택지(기록을 저장소에 커밋, CI 캐시에만 보관, 묶음을 줄여 매번 새로 계산) 가운데 골랐다. 까닭은 측정이다. TEI CPU 이미지(`cpu-1.9.4`, `BAAI/bge-m3`)를 코어 4개로 묶어 471토큰의 글을 배치 32로 임베딩하자 `--cpus=4`에서 배치마다 49.7~108.6초가 걸렸다(0.48개/s. 쟀다. 프로브 `.scratch/search-eval/probes/tei-cpu/embed_throughput.py`, 출력 `embed_throughput_out.txt`). `--cpuset-cpus=0-3`으로 다시 띄운 실행은 서버 로그에서 배치마다 56.4~93.8초였다(`embed_throughput_cpuset_server_log.txt`. 이 실행은 컨테이너가 도중에 죽어 프로브의 출력이 없다). 조각 3,000개면 약 100분이라(어림. 이 PC의 코어 4개로 잰 값이고, 둘째 실행 도중에는 다른 컨테이너가 함께 돌았다. Further Notes) PR마다 색인을 새로 만들 수 없다.
- [이력] ADR 0018 Consequences의 문장 "평가 전용 compose(PostgreSQL, 임베딩 TEI, 리랭커 TEI)가 release-image와 독립으로 서고, CI는 모델을 캐시한다"는 범위가 좁아진다. CI는 리랭커 TEI를 띄우지 않고 기록을 읽는다. ADR 0018 이력 2026-11-13 "모델이 계산한 결과는 로컬에서 만든 추론 기록으로 커밋하고, CI는 그 기록을 읽는다"와 본문 포인터가 그 변경이다. 같은 이력이 ADR 0010의 개발과 CI가 CPU 이미지를 쓴다는 문장에도 포인터를 단다. 리랭크 기록은 개발 PC의 GPU 이미지로 만들기 때문이다.
- [정함] 추론 기록은 `Embedder`와 `Reranker` 포트를 감싸는 어댑터 둘이다. 감싼 포트를 부르기 전에 기록을 보고, 없으면 감싼 포트를 불러 결과를 쓴다. 평가 도구의 조립만 이것을 쓰고 서버와 작업자의 조립은 쓰지 않는다. 토큰 세기(`count_tokens`, `special_token_count`, `token_spans`)는 기록하지 않고 감싼 포트로 그대로 넘긴다. 청킹이 묻는 글의 수가 많아 기록이 커지고, 토큰화는 임베딩에 견줘 가볍다고 보기 때문이다(프로브의 서버 로그에서 임베딩 요청 안의 토큰화 시간이 배치 32에 23~238ms였다. `/tokenize` 자체의 지연은 재지 않았다). 그래서 CI에도 임베딩 TEI는 뜬다.
- [정함] 열쇠는 모델 이름과 글에서 낸다. 임베딩은 `sha256(모델 이름, NUL, 글의 UTF-8 바이트)`이고, 리랭크는 `sha256(모델 이름, NUL, 질의, NUL, 글)`이다. 글은 감싼 포트가 받는 글 그대로다. 조각의 임베딩은 임베딩 서버에 보내는 글(줄인 절 경로를 붙인 글), 질의의 임베딩은 질의 글, 리랭크는 리랭커에 보내는 글(온전한 절 경로를 붙인 글)이다. 그래서 조각의 경계나 절 경로가 달라지면 새 열쇠이고, 모델을 바꾸면 모든 열쇠가 새것이다. 모델 이름은 `config.json`의 것이다.
- [정함] 기록 파일은 명령마다 주인이 하나다. 조각의 임베딩 `records/chunk-embeddings.keys`와 `.f32`는 `index`가, 질의의 임베딩 `records/query-embeddings.keys`와 `.f32`는 `run`이, 리랭크 점수 `records/rerank.jsonl`은 전체 실행의 `run`이 쓴다. `.keys`는 열쇠를 사전 순으로 한 줄에 하나씩, `.f32`는 같은 순서의 벡터를 float32 리틀 엔디언으로 이어 붙인 것, `rerank.jsonl`은 열쇠 순의 열쇠와 점수다. `records/records.json`은 기록 파일마다 모델 이름, 차원(임베딩), 수, 만든 TEI의 판과 장치(CPU 또는 GPU), 요청 지문(아래 항목)을 적는다. 정렬해 쓰므로 같은 내용은 같은 바이트다. 기록의 합은 20MB 이하이고 `validate`가 본다(조각 3,000개와 질의 300개의 1024차원 벡터가 약 13.5MB다. 계산이다).
- [정함] `index`와 `run`은 기록 방식 셋 가운데 하나로 돈다. `--records read`(기본)는 기록에 없는 글을 감싼 포트로 계산하되 기록 파일을 고치지 않는다. 새로 계산한 임베딩이 100개를 넘으면 계산을 멈추고 종료 코드 1을 내며, 어느 명령을 `--records write`로 다시 돌려 어느 파일을 커밋해야 하는지를 알린다. 감싼 포트가 없으면(리랭커의 끝점을 주지 않은 전체 실행) 기록에 없는 쌍 하나에도 같은 방식으로 실패한다. `--records write`는 상한 없이 계산하고, 그 명령이 주인인 기록 파일만 이번 실행이 쓴 열쇠 전부로 다시 쓴다. 다시 쓰는 것은 명령이 종료 코드 0으로 끝날 때뿐이고, 1로 끝나면(색인에 실패한 문서가 있다, 평가 도중 판이 바뀌었다) 주인 파일을 바이트 그대로 둔다. 실패한 문서의 열쇠가 기록에서 빠지지 않게 하려는 것이다(티켓 세션의 명세 검토가 짚었다). `index --records write`는 문서가 하나도 없는 데이터베이스에서만 돈다. 문서가 든 데이터베이스에서는 아무것도 쓰지 않고 종료 코드 1을 내며 데이터베이스를 새로 만들라고 알린다. 수집은 내용이 같은 문서를 다시 색인하지 않으므로(`unchanged`. `src/rag_engine/app/ingest.py`의 머리 독스트링을 읽었다) 이미 색인한 데이터베이스에서는 그 실행이 쓴 열쇠가 없거나 일부뿐이고, 그것으로 다시 쓰면 조각의 임베딩 기록이 비거나 줄어든다(PR #34 봇 셋째 회차의 지적). 끊긴 `index --records write`도 데이터베이스를 새로 만들어 다시 돌린다. `run`은 질의의 임베딩과 리랭크 점수를 실행마다 모두 청하므로 이 조건이 없다. `write`도 기록에 이미 있는 열쇠의 값은 다시 계산하지 않고 그대로 옮기며, 기록에 없는 글만 계산한다. 그래서 GPU가 있는 기계에서 전체 실행을 `write`로 돌려도 질의가 그대로면 `query-embeddings` 파일은 같은 바이트로 남고 `rerank.jsonl`만 달라진다. 값을 통째로 다시 계산해야 할 때(TEI의 판이나 모델의 개정, TEI 어댑터의 추론 동작을 바꾼 PR)는 그 기록 파일을 지운 뒤 `write`로 돌린다(조각의 임베딩 기록이면 데이터베이스도 새로 만든다). `records.json`에 적힌 그 파일의 TEI 판이 `config.json`의 `tei_version`과 다르면 `write`는 파일을 지우지 않았어도 옛 값을 옮기지 않고 다시 계산한다. 요청 지문에는 TEI의 판이 들지 않아, 판만 올리고 파일을 지우지 않은 채 `write`를 돌리면 옛 값이 새 판의 이름으로 남기 때문이다(PR #38 봇 첫 회차의 지적). 다른 명령의 파일은 건드리지 않으며, 빠른 실행의 `run`은 `rerank.jsonl`을 건드리지 않는다. `--records off`는 기록을 읽지도 쓰지도 않고 모두 감싼 포트로 계산한다(설정 실험용). CI는 `read`로만 돈다. 100개는 코어 4개에서 약 200초다(위 측정으로 어림).
- [정함] 기록에 든 값이 기준이다. TEI의 판이나 모델의 개정, TEI 어댑터가 추론 요청을 짓는 방식이나 서버가 돌려준 값을 다루는 방식이 바뀌어 값이 달라질 수 있는 변경은 그 PR이 기록 파일을 지우고 `write`로 다시 만들어 커밋해야 숫자에 드러난다. 그래서 TEI의 판을 올리는 PR은 기록을 다시 만든다는 것을 `compose.eval.yml`의 머리 주석과 `records.json`의 판 칸으로 알린다. `validate`는 `records.json`의 TEI 판과 `compose.eval.yml`의 이미지 태그(`cpu-`나 `turing-` 같은 장치 머리를 뗀 것)가 `config.json`의 `tei_version`과 다르면 실패한다. 같은 장치에서 다시 계산한 값이 기록과 얼마나 다른지는 이 세션이 재지 않았다(프로브를 돌리던 때에 다른 세션의 지연 측정이 같은 PC에서 돌고 있어서 CPU를 더 쓰지 않았다). 티켓 세션의 명세 검토가 같은 PC의 CPU 이미지(`cpu-1.9.4`, `--cpus=4 --max-batch-tokens 4096`)로 약 900자의 글 8개를 임베딩해 보니, 같은 묶음 두 번, 순서를 뒤집은 묶음, 둘로 나눈 묶음, 짧은 글을 섞은 묶음, 컨테이너를 다시 띄운 뒤에 돌려받은 값이 모두 같았다(JSON으로 받은 수를 `==`로 견줬다. 프로브 `.scratch/search-eval/probes/repeat/tei_repeat.py`로 손으로 봤다. 출력 `tei_repeat_out.txt`. 리랭커는 도중에 Docker가 내려가 재지 못했고, CI 러너의 CPU와 GPU는 재지 않았다). `read`가 기록에 없는 글을 그 자리에서 계산해 기록의 값과 섞어 쓰므로, 리랭크 기록을 만드는 티켓이 장치 사이의 차와 함께 잰다("전체 게이트와 리랭커" 절).
- [정함] TEI 어댑터의 변경이 기록에 가려지는 것을 막는 장치와 남는 한계다(PR #34 봇 첫 회차의 지적). 기록은 포트를 감싸므로 기록에 있는 글은 TEI 어댑터를 거치지 않는다. 어댑터가 요청을 짓는 방식이나 받은 값을 다루는 방식이 바뀌어도 열쇠는 그대로이고 평가는 옛 값을 읽는다. 요청 쪽은 기계가 본다. 지금 어댑터가 추론 요청에 싣는 것은 임베딩이 `/v1/embeddings`에 글과 모델 이름이고, 리랭크가 `/rerank`에 질의와 글, 그리고 `truncate`, `truncation_direction`, `raw_scores`, `return_text` 넷이다(`src/rag_engine/adapters/tei.py`를 읽었다). 요청 지문은 끝점의 경로와, 요청 본문에서 글과 질의와 모델 이름을 뺀 칸을 정렬한 JSON의 sha256이다. 어댑터는 그 경로와 칸을 임베딩과 리랭크마다 한 자리에 두고 요청을 그것으로 지으며, 어댑터의 시험이 실제로 보낸 요청이 그 자리의 값과 같은지를 본다. `write`는 그 명령이 주인인 기록 파일의 요청 지문을 `records.json`에 적고, 그 파일에 적혀 있던 요청 지문이 지금 것과 다르면 옛 값을 옮기지 않고 모두 다시 계산한다. `validate`는 `records.json`의 요청 지문이 이 체크아웃의 어댑터가 내는 것과 다르면 실패하며 어느 기록 파일을 다시 만들어야 하는지를 알린다. 요청 지문은 끝점 없이 읽으므로 리랭커를 띄우지 않는 CI도 리랭크의 것을 본다. 응답 쪽은 요청 지문이 보지 못한다. 서버가 돌려준 값을 다루는 코드(순번으로 입력 순서를 되살리기, 벡터를 옮기기)나 어댑터가 글을 보내기 전에 손대는 코드가 바뀌면 위 항목대로 사람이 기록을 다시 만들어야 숫자에 드러나고, 그 전에 그 코드의 회귀를 보는 것은 어댑터의 시험이다(`tests/adapters/test_tei_embedder.py`와 `tests/adapters/test_tei_reranker.py`에 요청 본문과 입력 순서를 보는 시험이 있다. 시험의 이름을 읽었다). 응답 쪽까지 기계가 보게 하는 길은 셋으로 본다. 빠른 게이트가 임베딩 기록의 표본을 CI의 임베딩 TEI로 다시 계산해 대 보는 길, 기록을 다시 만드는 `write`가 기록에 이미 있던 값의 표본을 다시 계산해 대 보는 길, 전체 게이트가 CI에 리랭커를 띄워 리랭크 기록의 표본을 다시 계산하는 길이다. 셋째 길은 CI가 리랭커를 띄우지 않는다는 ADR 0018 이력 2026-11-13의 결정을 바꾸고, 세 길 모두 다시 계산한 값과 기록의 차를 얼마까지 받을지가 리랭크 기록을 만드는 티켓의 측정("전체 게이트와 리랭커" 절)에 달려 있다. 사용자가 2026-11-13 티켓 세션에서 기록의 변조를 막는 길과 함께 이 셋을 보고 셋 모두 고르지 않았다(Further Notes). 그래서 응답 쪽의 회귀는 어댑터의 시험만 보고, 숫자에는 사람이 기록을 다시 만들 때 드러난다.
- [정함] 기록은 로컬에서 만든다. 임베딩 기록은 CPU로도 만들 수 있고(조각 3,000개에 약 100분. 위 어림), GPU가 있으면 GPU 이미지로 만든다(2026-11-14 티켓 09가 CPU 이미지로 `index`를 돌리자 제품의 TEI 시간 제한 60초에 걸려 첫 작업이 `embedding_unavailable`로 재대기열에 들어가 끝나지 않았다. 그래서 GPU 이미지로 돌렸다. 티켓 09 `## Comments`). 리랭크 기록은 GPU로만 만든다("전체 게이트와 리랭커" 절).

### CI 게이트와 기준 보고서

- [넘겨받음] 절대 문턱이 아니라 커밋한 기준 보고서 대비 하락폭으로 막는다. 질의 목록마다 상위 5 적중률과 MRR을 본다. 빠른 게이트는 합친 뒤 줄을, 전체 게이트는 리랭크 뒤 줄을 본다. 벡터만, 키워드만 줄은 보고서에만 싣는다. 빠른 게이트는 서버 코드, 의존성 목록, 평가 재료와 구성이 바뀐 PR에서만 돌고, 건너뛰면 `verify`는 통과로 센다. 게이트는 CI 전용이고 pre-commit 러너에는 넣지 않는다(ADR 0018). 푸시와 수동 실행에서도 늘 평가하는 것은 이 절의 아래 항목이 더했다(ADR 0018 이력 2026-11-13 "푸시에서는 바뀐 경로를 보지 않고 빠른 게이트를 늘 돌린다").
- [사용자 선택] 하락폭은 상위 5 적중률 2%p, MRR 0.02로 시작한다. 게이트를 넣는 티켓이 같은 커밋의 빠른 게이트를 CI에서 세 번 돌려 실행 사이의 차를 재고, 어느 숫자든 차가 질문 하나의 몫(상위 5 적중률 0.67%p)을 넘으면 멈춰 사용자에게 다시 묻는다. 넘지 않으면 이 값이 첫 기준 보고서의 승인과 함께 확정된다. 사용자가 2026-11-13에 두 선택지(2%p로 시작하고 흔들리면 다시 묻는다, 측정 뒤 명세를 고쳐 확정한다) 가운데 골랐다. 평가 도구가 없어 지금은 흔들림을 잴 수 없다.
- [정함] 기준 보고서는 실행의 종류마다 하나씩 파일 둘이다. `baseline-fast.json`은 빠른 실행의, `baseline-full.json`은 전체 실행의 `report.json`을 그대로 옮긴 것이다. 빠른 게이트는 앞의 것의 합친 뒤 줄과, 전체 게이트는 뒤의 것의 리랭크 뒤 줄과 견준다. 파일을 나누는 까닭은 dev로 가는 PR이 빠른 실행의 보고서만 만들 수 있기 때문이다. 하나로 두면 그 PR이 기준을 갈 때 리랭크 뒤 줄이 사라진다. 어느 줄을 어느 실행의 값으로 갱신하는지는 ADR 0018 Consequences가 명세에 맡긴 것이다.
- [정함] `compare`의 판정. `compare --gate fast`는 보고서를 `baseline-fast.json`과, `--gate full`은 `baseline-full.json`과 견준다. 질의 목록마다 그 게이트가 보는 줄을 찾아, 기준의 값에서 새 값을 뺀 것이 하락폭을 넘으면 실패다. 경계는 넘을 때만 실패다(정확히 2%p는 통과). 묶음의 내용 해시, 구성(판정 칸을 뺀 것. 보고서 절), 그 게이트가 읽는 기록 파일의 해시(아래 항목) 가운데 하나라도 기준 보고서의 것과 다르거나 기준 보고서가 없으면 숫자를 견주지 않고 실패하며, 무엇이 달라 기준 보고서를 갱신해야 하는지 알린다. 실패하면 질의 목록, 지표, 기준값, 새 값, 차를 표준 오류에 찍는다. 새 값이 기준보다 하락폭 넘게 높으면 통과하되 기준 보고서를 갱신하라고 알린다.
- [사용자 선택] 추론 기록의 변조는 기록 파일의 해시로 막는다. 보고서의 `records` 칸이 그 실행이 읽은 기록 파일마다 sha256을 싣고, `compare`는 그 게이트가 읽는 기록 파일(빠른 게이트는 조각과 질의의 임베딩 `.keys`와 `.f32`, 전체 게이트는 거기에 `rerank.jsonl`)의 해시가 기준 보고서의 것과 다르면 숫자를 견주지 않고 실패한다(위 항목). 그래서 기록을 다시 만드는 PR(청킹이나 모델을 바꾸는 PR, 출시 PR 앞에서 리랭크 기록을 맞추는 PR)은 기준 보고서의 갱신과 승인을 함께 거친다(아래 첫 기준 보고서와 갱신 항목). 손으로 고친 기록은 해시가 바뀌어 승인 없이는 게이트를 지나지 못한다. `read`가 기록에 없는 글을 그 자리에서 계산해도 기록 파일은 바뀌지 않으므로 해시도 그대로다. 사용자가 2026-11-13 티켓 세션에서 네 길(이 길, 빠른 게이트가 임베딩 기록의 표본을 다시 계산하기, `write`가 옛 값의 표본을 대 보기, 전체 게이트가 CI에 리랭커를 띄워 표본을 다시 계산하기) 가운데 이 길 하나를 골랐다(여럿을 고를 수 있었다. ADR 0018 이력 2026-11-13 "평가는 후보를 정확 스캔으로 뽑고, 추론 기록의 해시가 바뀌면 승인을 받는다"). 값은 기록을 다시 만드는 PR마다 승인이 하나 느는 것이다.
- [정함] 건너뛰기를 갈라 적는다(PR #27 봇 둘째 회차의 Minor 1). 결정은 ADR 0018의 것이다. 검색에 영향을 주지 않는 PR에서 빠른 게이트는 평가를 하지 않고, 그 PR의 필수 검사 `verify`는 초록이다. 지금의 동작은 다르다. `verify`는 `needs`의 결과가 모두 `success`일 때만 초록이라 건너뛴(`skipped`) 잡을 빨강으로 센다(`.github/workflows/ci.yml`의 verify 주석을 읽었다). 그래서 방법은 잡을 건너뛰지 않는 것이다. 빠른 게이트의 잡은 PR마다 늘 시작하고, 잡의 첫 스텝이 바뀐 경로를 보고 평가할지를 정하며, 평가하지 않으면 나머지 스텝을 스텝의 조건(`if`)으로 넘긴 채 잡이 성공으로 끝난다. `verify`의 판정 줄은 고치지 않고 `needs`에 잡 이름만 더한다.
- [정함] 빠른 게이트가 평가하는 경로의 목록. `src/`, `pyproject.toml`, `uv.lock`, `evals/`, `tools/search_eval.py`, `compose.eval.yml`, `.github/workflows/ci.yml`이다. 경로는 PR에서만 보고, base와 머리의 merge-base부터의 `git diff --name-only --no-renames`로 읽는다. 이름을 바꾼 파일은 옛 경로와 새 경로를 모두 판정한다. 이름 바꾸기 찾기가 켜져 있으면 `--name-only`가 새 경로만 내어, `src/`의 파일을 목록 밖으로 옮긴 PR이 평가를 건너뛸 수 있다(PR #38 봇 첫 회차의 지적. 시험이 이 경우를 본다). 푸시에서는 경로를 보지 않고 늘 평가한다(아래 항목). 목록과 판정은 `tools/`의 순수 함수로 두고 `tests/tools/`가 시험한다. 함수는 이벤트 셋을 받는다. PR이면 바뀐 경로로 정하고, 푸시와 수동 실행(`workflow_dispatch`)이면 늘 평가한다. PR에서 merge-base나 바뀐 경로를 읽지 못하면 평가한다(닫힘 쪽). 바뀐 것이 없다고 읽으면 조용히 초록이 되기 때문이다. 잡의 체크아웃은 merge-base를 구할 만큼 역사를 받는다(지금 `ticket` 잡만 `fetch-depth: 0`이다. `.github/workflows/ci.yml`을 읽었다. 이벤트와 읽지 못하는 경우는 티켓 세션의 명세 검토가 짚었다). 목록에서 빠진 경로의 변경은 PR에서는 평가되지 않고, 병합된 뒤 푸시의 빠른 게이트에서 잡힌다.
- [정함] 빠른 게이트는 PR(base가 dev든 main이든)과 dev·main 푸시에서 돈다. dev는 최신 기준을 강제하지 않아(`docs/constitution/operations.md` 브랜치와 병합) 병합된 결과가 PR에서 잰 것과 다를 수 있으므로 푸시에서도 잰다. main은 최신 기준을 강제하므로 main 푸시의 빠른 게이트는 PR이 잰 내용을 한 번 더 재는 것이다. 그래도 dev와 가르지 않는 까닭은 조건이 하나로 끝나고(푸시면 평가한다) main의 보호 설정이 바뀌어도 게이트가 조용히 비지 않기 때문이다. 같은 브랜치에 푸시가 이어지면 `ci.yml`의 `concurrency`(`cancel-in-progress: true`. 그 파일을 읽었다)가 앞 실행을 취소하므로 사이의 커밋은 재어지지 않고 마지막 머리만 재어진다. 그 동작은 고치지 않는다. 푸시에서 바뀐 경로를 보지 않는 까닭이 여기 있다. 앞 커밋부터의 차이로 평가할지를 정하면, 검색을 바꾼 푸시의 실행이 문서만 바꾼 다음 푸시에 취소될 때 마지막 머리가 평가 없이 초록으로 끝난다(PR #34 봇 셋째 회차의 지적). 값은 문서만 바꾼 병합의 푸시에서도 평가가 한 번 도는 CI 시간이다. 마지막 머리가 빨강이면 어느 병합이 숫자를 떨어뜨렸는지는 PR마다 올라온 산출물로 가른다. 설계는 PR만 말했고 푸시는 이 명세가 더한 것이다. ADR 0018 본문의 "PR에서만 돌고"는 같은 이력 2026-11-13의 포인터가 가린다.
- [정함] 빠른 게이트의 잡은 평가 전용 compose로 PostgreSQL과 임베딩 TEI를 띄우고, `validate`(파일 검사), `index`, `validate --indexed`(색인된 데이터베이스에서 글귀까지), `run --through fused`, `compare --gate fast`를 차례로 돈다. 보고서 둘은 성공이든 실패든 산출물로 올린다. 임베딩 TEI는 토큰 세기와 기록에 없는 글의 계산에 쓰고, 모델 파일은 CI 캐시에 둔다. 평가 전용 compose는 release-image의 단독 compose와 독립이다.
- [정함] 평가 전용 compose의 임베딩 TEI는 `--max-batch-tokens`를 4096으로 낮춰 띄운다(TEI의 기본은 16384다). core 16이 기본값에서 임베딩 컨테이너 하나가 13.25GiB를 점유하는 것을 `docker stats`로 봤고(손으로 본 값. `.scratch/core/probes/search-latency/compose.yml`의 머리 주석), 4096으로 띄운 그 프로브의 임베딩 컨테이너는 프로브를 시작할 때 6.625GiB, 검색 부하 중의 최대가 7,497MiB였다(프로브의 출력 `probe_out.txt`. 최대 메모리 줄의 앞 값이 임베딩이라는 것은 `probe.py`의 독스트링이 적는다). 이 세션이 기본값으로 띄운 임베딩 컨테이너도 메모리 부족으로 죽었다(Further Notes). CI 러너의 메모리는 이 세션이 확인하지 않았으므로, 게이트를 넣는 티켓이 그 값으로 러너에서 뜨는지를 실제 실행으로 보고 뜨지 않으면 더 낮춘다.
- [정함] 빠른 게이트의 시간 한도는 잡 전체 15분이고 `timeout-minutes`는 20이다(지금 `python`과 `image` 잡의 `timeout-minutes` 15에 맞춘 어림). 설계는 이 한도를 core 16의 측정으로 정하기로 했고(설계 일지 `## 다음`), core 16은 2026-11-13에 닫히며 그 값을 넘겼다. 그 값으로 대 보면 질의를 돌리는 몫은 작다. 리랭커 없는 `search`가 후보 50개에서 한 번에 서버 p95 421ms였으므로(동시 1건, n=4, 호스트 CPU 100%, 조각 91개의 색인. `.scratch/core/probes/search-latency/probe_out.txt`) 질의 300개면 2분쯤이고, 그 가운데 질의 임베딩(p95 373ms)은 평가가 기록에서 읽는다(어림. 평가는 한 질의에 단계 셋의 순위를 내므로 `search` 한 번과 같은 일이 아니다). 색인하는 몫은 그 측정으로 어림하지 못한다. 그 프로브의 표본은 문서 12개에 조각 91개이고 묶음은 문서 40개에 조각 3,000개까지이며, 작업자의 `parse_ms`가 문서마다 중앙값 5.8초로 파서만 잰 0.3초보다 훨씬 길었던 까닭을 core 16이 가르지 못했다(그 티켓의 일지 `docs/journal/2026-11-13-0615-search-latency-probe.md`). 그 측정은 CI 러너가 아니라 개발 PC의 값이기도 하다. 그래서 15분은 어림으로 남는다. 게이트를 넣는 티켓이 CI에서 걸린 시간을 재어 프로브 README에 적고, 15분을 넘으면 멈춰 사용자에게 다시 묻는다(ADR 0018 Consequences). 모델을 캐시에서 받아 띄우는 시간은 재지 않은 어림이다.
- [넘겨받음] 기준 보고서는 CI에서 만든 값을 커밋한다. 갱신 커밋은 사람이 승인한다. 게이트가 빨강일 때 에이전트는 기준 보고서를 스스로 갱신하지 않고 멈춰 보고한다. 기대 근거와 질의 목록의 수정, 기준 보고서의 갱신은 숫자의 앞뒤 차이를 보이고 사용자가 승인한 뒤에 한다(ADR 0018).
- [정함] 첫 기준 보고서와 갱신. `baseline-fast.json`은 빠른 게이트를 넣는 티켓이 만든다. 그 PR의 빠른 게이트는 기준 보고서가 없어 실패하므로, 올라온 산출물의 `report.json`을 `baseline-fast.json`으로 커밋해 다시 돌린다. `baseline-full.json`은 전체 게이트를 넣는 티켓이 그 브랜치의 수동 실행(`workflow_dispatch`)이 올린 산출물로 만든다. 갱신도 같다. 기록 파일의 해시가 달라 실패한 경우도 같다. 실패한 실행의 산출물을 내려받아 옛 값과 새 값의 표를 사용자에게 보이고, 승인을 받은 뒤 커밋한다. 승인은 그 PR의 티켓 `## Comments`에 사용자의 글 그대로 적는다.

### 전체 게이트와 리랭커

- [사용자 선택] 전체 게이트와 리랭크 점수에 기대는 일(리랭크 기록 만들기, 최소 점수의 분포 측정, 리랭커 켬·끔의 실험)은 core 16의 판정 내용에 묶지 않고 이 기능에서 하며, 리랭크 기록은 개발 PC의 GPU로 만든다. 사용자가 2026-11-13에 두 번 골랐다. 처음에는 CPU 측정을 보고 세 선택지(core 16의 판정 뒤로 미룬다, 지금 그대로 로컬에서 기록을 만든다, 전체 게이트를 이번 기능에서 뺀다) 가운데 미루는 쪽을 골랐다. 그 뒤 GPU로 돌릴 수 없느냐고 물었고, GPU로 띄워 본 결과를 본 뒤 세 선택지(이번 기능에서 GPU로 진행한다, 지금 드라이버를 올리고 바로 잰다, 처음 선택을 지킨다) 가운데 이번 기능에서 진행하는 쪽으로 바꿨다. core 16은 그 뒤 같은 날 닫혔고, 리랭커의 CPU 속도를 재기만 한 채 결정을 넘겼다(아래 "리랭커의 CPU 속도와 기본의 결정" 항목).
- [정함] CPU로는 리랭크 기록을 만들지 않는다. 까닭은 측정이다. 코어 4개만 보이는 TEI CPU 이미지에서 `BAAI/bge-reranker-v2-m3`는 질의와 조각 크기 글(임베딩 프로브가 471토큰으로 센 글과 같은 방식으로 만든 글이고, 쌍의 토큰 수는 재지 않았다)의 쌍 32개를 한 배치에 200.6~297.6초에 채점했다(0.12쌍/s. 쟀다. 프로브 `.scratch/search-eval/probes/tei-cpu/rerank_throughput.py`, 출력 `rerank_throughput_out.txt`). 그 모델 저장소에 ONNX 파일이 없어 TEI가 ORT 백엔드를 띄우지 못하고 Candle 백엔드로 돌았다(서버 로그 `rerank_throughput_server_log.txt`). 평가 한 번의 15,000쌍(질의 300, 후보 50)은 약 34시간이다(프로브의 어림). 코어를 묶지 않아도 결론은 같다. core 16의 프로브는 코어를 묶지 않은 같은 이미지에서 리랭크 32개 한 호출에 100.6초(글 하나에 3.14초)를 쟀고(`.scratch/core/probes/search-latency/probe_out.txt`), 호스트의 점유가 낮던 때에는 리랭크 4개 한 호출이 6.7초였다고 적는다(손으로 본 값. 그 티켓의 일지). 글 하나에 3.14초면 15,000쌍이 약 13시간이고 1.7초면 약 7시간이다(계산이다).
- [정함] 전체 게이트를 모든 PR에 돌리지 않는 까닭을 확정한다. ADR 0018이 그 안을 거부하며 적은 근거는 리랭커를 CPU로 돌리는 시간이 PR마다 든다는 어림이었고, core 16의 측정값을 보고 이 명세가 확정하기로 했다. 측정은 그 어림보다 크다. core 16이 잰 리랭커를 켠 `search`는 후보 50개에서 한 번에 130초였고(동시 1건, n=1. 같은 출력), 질의 300개면 약 11시간이다(계산이다). CPU로는 PR마다가 아니라 한 번도 돌리기 어렵다. 그리고 추론 기록을 쓰기로 한 지금은 CI가 리랭크를 계산하지 않으므로, 모든 PR에 돌리지 않는 까닭이 달라진다. 합친 뒤의 후보를 바꾸는 PR마다 GPU가 있는 기계에서 리랭크 기록을 다시 만들어 커밋해야 하기 때문이다. 결론(전체 게이트는 main으로 가는 PR에서 본다)은 같다.
- [정함] GPU의 처리량은 이 세션이 재지 못했고 리랭크 기록을 만드는 티켓이 잰다. 개발 PC의 GPU는 GTX 1660 Ti(VRAM 6GB)이고 이 명세를 쓸 때 드라이버는 560.94였다(`nvidia-smi`를 손으로 봤다. 같은 날 621.24로 올랐다는 것을 티켓 세션이 `nvidia-smi`로 손으로 봤다). TEI GPU 이미지(`turing-1.9.4`)는 그대로는 뜨지 않았다. `--gpus all`은 `cuda>=12.9` 요구로 거부됐고, 그 검사를 끄고 이미지의 상위 호환 라이브러리 폴더를 가린 뒤에야 GPU를 잡았으나 `CUDA_ERROR_UNSUPPORTED_PTX_VERSION`으로 모델을 올리지 못했다(손으로 봤다. 서버 로그 `.scratch/search-eval/probes/tei-cpu/gpu_turing_start_server_log.txt`, 띄운 방법은 프로브 README). 명세를 쓸 때는 설치된 드라이버가 이미지의 CUDA 12.9보다 낡은 것으로 보고, 그 티켓을 사용자가 드라이버를 올린 뒤로 미뤘다. 드라이버가 오른 지금, 그 티켓은 첫머리에 GPU 이미지가 우회 없이 뜨는지 보고, 띄운 방법과 임베딩·리랭크의 처리량을 프로브로 남긴다. 평가 한 번의 기록 만들기가 2시간을 넘으면 멈춰 사용자에게 다시 묻는다(2시간은 사용자가 고른 선택지에 적은 값이다).
- [정함] 값의 차를 같은 티켓이 대 본다. 같은 글 32개의 임베딩과 같은 쌍 32개의 리랭크 점수를 CPU 이미지로 두 번, GPU 이미지로 한 번 계산해, 벡터끼리의 코사인 유사도의 최솟값과 점수 차의 최댓값을 프로브로 남긴다(CPU 두 번은 같은 장치에서 다시 계산한 값의 차, CPU와 GPU는 장치 사이의 차다). 어느 쪽이든 코사인 유사도가 0.999 아래이거나 점수 차가 0.01을 넘으면 멈춰 사용자에게 다시 묻는다(두 문턱은 어림이다). CI가 기록에 없는 글을 CPU로 계산해 기록의 값과 섞어 쓰고, 제품의 기본 구성도 CPU이기 때문이다.
- [이력] ADR 0018 이력 2026-11-13(추론 기록 절의 것과 같은 이력)이 CI가 리랭커를 띄우지 않는다는 것과 GPU로 띄워 본 결과를 함께 적는다. 전체 게이트의 결정(main으로 가는 PR에서 리랭크 뒤 줄을 본다)은 바뀌지 않는다.
- [정함] 전체 게이트의 모양. `ci.yml`의 잡 하나이고 빠른 게이트와 같은 방법으로 늘 시작한다. base가 main인 PR과 수동 실행(`workflow_dispatch`)에서만 평가하고 그 밖에는 성공으로 끝난다. 잡의 차례는 빠른 게이트와 같고 `run --through rerank`와 `compare --gate full`만 다르다. 리랭커의 끝점을 주지 않으므로 리랭크 점수는 리랭크 기록에서만 읽고, 기록에 없는 쌍이 하나라도 있으면 실패한다(추론 기록 절의 `read`). main 푸시에서는 돌리지 않는다. main은 최신 기준을 강제해 PR의 머리가 곧 병합될 내용이기 때문이다(빠른 게이트가 main 푸시에서도 도는 까닭은 CI 게이트 절에 적었다). 수동 실행의 계기(`workflow_dispatch`)는 지금 `ci.yml`의 `on:`에 없다(그 파일을 읽었다). 빠른 게이트를 넣는 티켓이 그 계기를 함께 더해, 전체 게이트를 넣는 티켓보다 먼저 dev에 들어가게 한다. GitHub는 워크플로 파일이 기본 브랜치에 있어야 이 이벤트가 실행을 띄우고, 한 번 돈 워크플로는 API나 CLI로 다른 브랜치를 가리켜 띄울 수 있다고 적는다(공식 문서 `docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows`의 `workflow_dispatch` 절을 2026-11-13에 `curl`로 내려받아 읽었다). 계기가 기본 브랜치의 파일에는 없고 가리킨 브랜치의 파일에만 있을 때도 띄워지는지는 그 문서가 적지 않으므로, 계기를 먼저 dev에 넣어 그 경우를 피한다. 수동 실행은 `gh workflow run ci.yml --ref <브랜치>`로 띄운다. 수동 실행은 dev가 아닌 브랜치에서 띄운다. dev에서 띄우면 dev 푸시와 같은 `concurrency` 그룹(`ci-${{ github.ref }}`)이라 서로 취소하기 때문이다(`.github/workflows/ci.yml`을 읽었다). 수동 실행에서 다른 잡이 어떻게 끝나는지는 티켓 세션의 명세 검토가 코드로 읽었다. `ticket`은 PR이 아니면 한 줄을 찍고 지나가고(`tools/check_ticket.py`를 읽었다), `python`과 `image`는 이벤트 조건이 없어 끝까지 돈다(`ci.yml`을 읽었다). 계기가 dev에 들어간 뒤 전체 게이트를 넣는 티켓이 실제 실행으로 그것과 `verify`의 결과를 확인하고(계기를 더하는 티켓의 PR 안에서는 dev의 파일에 계기가 없어 위의 문서가 적지 않은 경우가 된다. PR #38 봇 첫 회차의 지적), 가를 일이 생기면 잡의 조건(`if`)이 아니라 스텝의 조건으로 가른다. 잡을 건너뛰면 `verify`가 빨강으로 세기 때문이다(CI 게이트 절의 건너뛰기 항목). dev는 이미 섰으므로(dev-branch 04, PR #28) ADR 0018 Consequences가 dev 전환 전의 구현에 두었던 수동 실행만의 갈래는 쓰지 않는다.
- [정함] dev와 main 사이에서 기록과 기준을 맞추는 절차. 합친 뒤의 후보를 바꾸는 변경(청킹, 임베딩, 검색 SQL, 후보 수)은 리랭크할 쌍을 바꾸고, 묶음을 고치는 변경은 내용 해시를 바꾼다. dev로 가는 PR은 빠른 게이트만 보므로 `rerank.jsonl`과 `baseline-full.json`을 맞추지 않고 병합된다. 그래서 dev에서 main으로 가는 출시 PR 앞에 맞추는 PR을 하나 둔다. GPU가 있는 기계에서 `run --through rerank --records write`로 `rerank.jsonl`을 다시 만들어 커밋하고, 그 브랜치의 수동 실행이 올린 보고서로 `baseline-full.json`을 견준다. `rerank.jsonl`을 다시 만들면 그 해시가 바뀌므로 `baseline-full.json`도 그 수동 실행의 보고서로 갈고, 그 갱신이 승인 절차를 따른다(CI 게이트 절의 기록 해시 항목). main에서 딴 핫픽스가 합친 뒤의 후보를 바꿀 때도 같다.
- [사용자 선택] 리랭커의 CPU 속도와 기본의 결정은 이 기능의 리랭커 켬·끔 실험 뒤에 사용자가 한다. 사용자가 2026-11-13에 세 선택지(리랭커 실험 뒤에 고른다, 지금 리랭커를 끄는 기본으로 바꾼다, 지금 ONNX와 GPU의 조사부터 한다) 가운데 골랐다. core 16(PR #31, 2026-11-13)은 CPU TEI 리랭커를 켠 `search`가 기본 검색 시간 제한(`RAG_SEARCH_TIMEOUT_SECONDS` 20초)을 지키기 어렵다는 것을 쟀다. 후보 5개에서 한 번에 15.5~17.3초(두 번 잰 값), 기본인 후보 50개에서 한 번에 130초(한 번 잰 값)였다(개발 PC. `.scratch/core/probes/search-latency/probe_out.txt`). 그 티켓은 길 셋(리랭커를 끄는 기본, ONNX 리랭커나 GPU 이미지, 검색 시간 제한을 늘리는 것) 가운데 어느 것도 고르지 않고 결정을 사용자와 이 기능에 넘겼다(그 티켓의 일지 `docs/journal/2026-11-13-0615-search-latency-probe.md`의 "다음"). 이 기능은 그 결정에 품질 쪽의 숫자를 댄다. 리랭커 켬·끔의 실험(설정 실험 절)이 리랭크 뒤 줄과 합친 뒤 줄의 차를 내면, 그 실험의 티켓이 그 보고서와 core 16의 지연을 함께 사용자에게 보이고 사용자가 길을 고른다. 그때까지 제품의 기본은 지금대로다. 고른 길이 ADR 0010(임베딩과 리랭커를 TEI 컨테이너로 둔다)이나 core 명세의 기본 구성에 닿으면 그 결정의 작업이 ADR의 이력과 명세를 고친다. 평가는 그 결정을 기다리지 않는다. 사용자의 둘째 선택대로 전체 게이트와 리랭크에 기대는 일은 GPU로 만든 기록으로 진행한다. 사용자가 리랭커의 모델을 바꾸는 길을 고르면 `config.json`과 리랭크 기록을 그 모델로 다시 만들고, 리랭커를 끄는 기본을 고르면 전체 게이트와 최소 점수를 어떻게 둘지를 같은 자리에서 함께 묻는다(ADR 0018과 0017의 전제가 달라진다). 이 기능은 기능 계획에서 core에 막혀 있었는데(`.scratch/search-eval/plan.md`의 `**Blocked by:**`), core는 core 16이 닫히며 끝났으므로(`.scratch/core/plan.md`의 `**끝:**` 줄) 이 기능의 티켓을 막는 다른 기능은 이제 없다.

### LLM 관련성 판정

- [넘겨받음] 판정기 포트는 `domain`의 Protocol이고 Claude 구현은 `adapters`에 둔다. 평가 유스케이스는 포트만 부르고 검색 유스케이스는 판정기를 받지 않는다. `app`과 `domain`의 import 금지 목록에 `anthropic`을 더한다. SDK는 `anthropic>=2.8,<3`을 운영 의존성으로 선언한다. 판정 모델은 설정값이고 `claude-opus-5-5`로 시작한다. 끝점 주소, 모델, 키 설정이 모두 있을 때만 판정기를 조립하고, 키와 판정 요청·응답의 본문은 로그에 남기지 않는다. 조각마다 관련 있음과 없음만 판정하고, API는 로컬 수동 실행에서만 부르며 판정 결과를 파일로 커밋한다. 파일에 없는 조합은 판정 없음으로 세어 그 비율을 보고서에 적는다. API를 부르는 실행은 예상 건수와 비용을 보이고 사용자가 승인한 뒤에 한다(ADR 0019).
- [정함] 포트의 이름은 `RelevanceJudge`이고 메서드는 `judge(query, text)` 하나이며 관련 있으면 참을 돌려준다. 쌍 하나에 호출 하나다. 실패는 `domain`의 기존 실패 둘로 올린다. 다시 해 볼 만한 것(연결 실패, 429, 5xx)은 `TransientFailure`, 그 밖(인증 실패, 읽을 수 없는 응답)은 `PermanentFailure`다. 실패의 메시지에는 SDK의 예외와 서버가 보낸 오류의 글을 옮기지 않고 이 저장소가 쓴 글만 싣는다. `judge`가 그 메시지를 표준 오류에 찍으므로 요청과 응답의 본문이 거기로 새지 않게 하려는 것이고, 선례는 TEI 어댑터다(`src/rag_engine/adapters/tei.py`의 머리 독스트링을 읽었다). 판정기에 보내는 글은 리랭커에 보내는 글과 같다(온전한 절 경로를 붙인 글). ADR 0007의 가름으로는 외부 서비스의 경계다. 다른 판정기 구현이 올 자리이고 이번 구현은 Claude 하나다. ADR 0003의 플러그인 자리 셋(커넥터, 변환, 파서)에 더하는 넷째 자리는 아니다. 판을 붙여 밖에 내는 인터페이스가 아니고 다른 구현도 이 저장소의 `adapters`에 둔다(PR #34 봇 첫 회차의 Nit). 데이터베이스의 트랜잭션에 들 일이 없어 작업 단위 밖에서 부른다.
- [이력] ADR 0007의 포트 열에 `RelevanceJudge`가 들고 `VectorIndex`에 `diagnose_candidates`가 든다. ADR 0007 이력 2026-11-13 "포트 열에 `RelevanceJudge`를 더하고 `VectorIndex`에 진단용 메서드 `diagnose_candidates`를 더한다"와 본문 포인터가 그 변경이다(PR #27 봇 둘째 회차의 Minor 2. 앞서 포트를 더할 때도 명세 세션이 이름을 이력에 적었다).
- [정함] 설정은 셋이고 모두 기본값이 없다. `RAG_JUDGE_URL`(끝점 주소), `RAG_JUDGE_MODEL`, `RAG_JUDGE_API_KEY`다. 셋이 모두 있으면 판정기를 조립하고, 일부만 있으면 조립하지 않고 무엇이 빠졌는지 설정 이름으로 알린다(값은 찍지 않는다). 판정 파일을 조회하는 열쇠의 모델과 지시문 판은 `config.json`의 `judge_model`(첫 값 `claude-opus-5-5`)과 `judge_prompt_version`이다. `run`은 이 둘만으로 판정 파일을 읽으므로 판정기의 설정이 없어도 된다. `judge`는 `RAG_JUDGE_MODEL`이 `judge_model`과 다르거나 어댑터가 든 지시문의 판이 `judge_prompt_version`과 다르면 아무것도 부르지 않고 종료 코드 1과 어긋난 둘의 이름을 낸다. 주소와 키는 사용자가 환경 변수에 둔다.
- [정함] 지시문은 Claude 어댑터가 들고 판은 1부터의 정수다. 지시문의 글을 고치면 판을 올린다. 응답은 관련 여부 하나만 받는 구조화된 출력으로 요청하고 그 모양은 구현 티켓이 실제 호출로 정한다.
- [정함] 판정 파일 `judgments.jsonl`은 줄 하나가 판정 하나다. 칸은 `query_sha256`(질의 글의 해시), `text_sha256`(판정기에 보낸 글의 해시), `relevant`, `model`, `prompt_version`, `judged_at`(날짜)이다. 조회의 열쇠는 앞의 둘과 `model`, `prompt_version` 넷이다. 그래서 질의의 글이 바뀌면 옛 판정은 새 글에 닿지 않고, 조각의 글이 바뀌어도 같으며, 판정 모델이나 지시문의 판이 바뀌면 옛 판정은 쓰이지 않고 모두 판정 없음이다. 파일에는 해시만 있고 글은 없다.
- [정함] 판정 모델이나 지시문의 판을 바꿔 쓰이지 않게 된 줄은 `judge --prune`이 지운다. 스스로 지우지 않는 까닭은 모델을 되돌릴 때 다시 쓸 수 있고, 지우는 일이 큰 diff라 사람이 고르게 하기 위해서다.
- [정함] `judge`도 `run`처럼 `--through`를 받고, 그 실행의 마지막 단계의 상위 10개 조각과 질의의 쌍 가운데 판정 파일에 없는 것만 부른다. `run`이 내는 LLM 숫자도 그 실행의 마지막 단계의 상위 10개로 센다. 시작할 때 부를 건수와 비용의 어림을 찍고 `--yes`가 없으면 부르지 않고 끝난다. 판정 하나를 받을 때마다 파일 끝에 줄을 덧붙이므로 끊긴 실행을 다시 돌리면 이미 받은 조합은 건너뛴다. 동시 호출은 넷이고 일시 실패는 세 번까지 다시 한다. 끝나면 파일을 열쇠 순으로 정렬해 다시 쓴다.
- [넘겨받음] 보고서에 숫자 둘을 싣는다. 상위 10개 조각 가운데 LLM이 관련 있다고 본 비율과, 기대 근거에 닿은 조각을 LLM도 관련 있다고 본 비율이다. 기대 근거에 없는데 LLM이 관련 있다고 본 조각은 빠진 정답 후보의 목록으로 따로 내고, 사용자가 확인한 것만 기대 근거에 더한다(ADR 0019).
- [정함] 두 비율의 분모는 판정이 있는 조합만이고, 판정 없음의 비율을 함께 낸다. 판정 없음의 비율은 판정 여부와 관계없이 상위 10개의 조합 전체가 분모다(PR #38 봇 첫 회차의 지적). `run`은 판정기를 부르지 않고 판정 파일만 읽는다. 판정 파일이 없거나 지금의 모델과 지시문 판에 맞는 줄이 하나도 없으면 `llm`은 `null`이고 까닭을 적는다.
- [정함] 판정의 정확도를 사람 표본과 맞춰 보는 일(ADR 0019 Consequences가 따로 필요하다고 적었다)은 첫 판정 실행의 티켓이 한다. 판정된 쌍 가운데 관련 있음 20개와 관련 없음 20개를 뽑아 `inspect`로 글을 보이고, 사용자가 LLM의 판정을 보지 않은 채 같은 가름을 한 뒤 일치한 수를 프로브 README에 적는다. 일치가 40개 가운데 32개에 못 미치면 지시문을 고칠지를 사용자에게 묻는다(표본의 크기와 문턱은 어림이다).
- [거절] 배치 API는 이번에 쓰지 않는다. 값은 절반이지만(ADR 0019의 어림) 이어 가기와 실패 처리가 따로 필요하다. 첫 실행의 비용을 본 뒤 정한다.

### 최소 점수

- [넘겨받음] 검색 도구에 선택 인자 `min_score`(0 이상 1 이하)를 두어 리랭크 점수가 그 값보다 낮은 조각을 뺀다. 리랭커가 없는 지식베이스에 주면 `invalid_argument`다. 남은 조각이 없으면 빈 결과를 정상 응답으로 낸다. 지식베이스마다 기본값을 둘 수 있고 요청 인자가 이긴다. 리랭커가 없는 지식베이스에 기본값을 설정하는 것도 거부한다. `format_version`은 `1.1.0`이 된다. 구현은 리랭크 점수의 분포를 본 사용자가 승인한 뒤에 하고, 승인 전에는 구현 티켓이 놓이지 않는다(ADR 0017, ADR 0015 이력 2026-11-12).
- [정함] 분포의 측정은 전체 실행의 보고서 `score_distribution`이 낸다. 합친 뒤의 후보 전부의 리랭크 점수를 기대 근거에 닿은 조각과 그렇지 않은 조각으로 갈라 0.05 폭의 구간마다 세고, 문턱 0.05부터 0.95까지 0.05 간격마다 상위 5 적중률과 상위 10 적중률, 결과가 비는 질의의 비율, 질의마다 남는 조각 수의 평균을 낸다. 전체 실행에 기대므로 리랭크 기록을 만든 뒤에 잰다.
- [정함] 승인을 적는 자리는 ADR 0017의 이력이다. 분포를 낸 티켓의 세션이 보고서를 사용자에게 보이고, 사용자가 구현을 승인하면 ADR 0017에 측정의 요약과 승인을 이력으로 더한다. 그 이력이 있어야 구현 티켓을 쓴다. 두 분포가 한 문턱으로 잘 갈리지 않으면 그렇다는 것을 함께 보이고 다시 묻는다(ADR 0017). 구현할지는 사용자의 답이 정하고, 사용자가 구현하지 않기로 하면 이력에 그 결과와 사용자의 판정을 적고 구현 티켓은 쓰지 않는다(분리와 승인의 우선은 PR #38 봇 첫 회차의 지적으로 정했다).
- [정함] 구현할 때의 모양. 거르는 자리는 리랭크 뒤, `top_k`로 자르기 앞이다. 범위 밖의 값은 `invalid_argument`다. 숫자가 아닌 값은 유스케이스에 닿기 전에 MCP SDK의 입력 검증이 거부하고(설계의 프로브에서 타입이 틀린 인자는 `isError`가 참이었다. 프로브 `.scratch/search-eval/probes/mcp-args/probe_unknown_args.py`), 그 모양은 기존 인자의 타입 오류와 같게 둔다. 지식베이스의 기본값은 지식베이스 행의 널 허용 칸이고(마이그레이션이 더한다) 색인 판의 요소가 아니다. 그 마이그레이션은 색인 판의 요소인 스키마 판(`SCHEMA_VERSION`)을 올리지 않는다. 올리면 모든 설치가 재색인 필요가 되는데 지식베이스 행에 칸을 더하는 것은 색인을 바꾸지 않기 때문이다. 마이그레이션 0002가 같은 선례다(`src/rag_engine/adapters/index_elements.py`의 `SCHEMA_VERSION`이 1이고 마이그레이션이 둘인 것을 읽었다. 티켓 세션의 명세 검토가 짚었다). 기본 지식베이스의 값은 `RAG_DEFAULT_MIN_SCORE`(기본 비움)로 받아 `migrate`가 쓴다. 계약 시험은 도구 목록의 inputSchema에 `min_score`가 있고 결과의 `format_version`이 `1.1.0`인 것을 본다(ADR 0015 이력이 inputSchema 시험을 이 티켓에 맡겼다).
- [정함] 기본값이 있는 지식베이스에서 리랭커를 빼는 설정 변경은 거부한다(ADR 0017 Consequences가 명세에 맡겼다). v0에서 그 길은 `migrate`뿐이다. `RAG_DEFAULT_RERANKER_URL`이 비었는데 `RAG_DEFAULT_MIN_SCORE`가 있으면 `migrate`는 아무것도 쓰지 않고 종료 코드 1과 두 설정의 이름을 낸다. 그래도 그런 상태의 행이 있으면(데이터베이스를 손으로 고친 경우) 검색은 거르지 않은 결과를 조용히 내지 않고 `search_unavailable`을 낸다. 지식베이스 설정을 고치는 관리 API가 생기면 같은 규칙을 422로 지킨다(admin).

### 설정 실험과 참고 측정

- [넘겨받음] 이 기능이 실험해 기본값을 정하는 것은 조각 크기와 겹침, 리랭커 켬·끔과 후보 수이고 기본값의 변경은 사용자 승인 뒤에 한다. 품사 규칙, 정확 스캔 분기, 시멘틱 청킹은 판단용 숫자만 보고서에 남긴다. 설정 실험은 로컬에서 수동으로 돌리고 결과는 프로브로 커밋한다(ADR 0018, 일지 합의 요약의 가정 3).
- [정함] 리랭커 없이 할 수 있는 실험을 먼저 한다. 조각 상한과 겹침은 256·32, 512·64(기본), 512·128, 1024·128의 넷이고, 후보 수는 20, 50(기본), 100의 셋이다(기본 청킹에서). 구성마다 새 데이터베이스에 색인해 빠른 실행의 보고서를 내고, 보고서와 돌린 명령을 `.scratch/search-eval/probes/experiments/`에 둔다. 실험은 묶음의 `config.json`을 고치지 않고 `--config`로 준 다른 구성 파일과 `--records off`로 돌린다. 조각 크기를 바꾼 구성의 임베딩은 로컬에서 새로 계산하며(CPU면 구성 하나에 한두 시간. 추론 기록 절의 측정으로 어림. GPU면 재지 않았다) 커밋하지 않는다. 리랭커 켬·끔과 리랭크를 넣은 후보 수의 효과는 리랭크 기록을 만드는 티켓 뒤의 실험이고, 실험 구성의 리랭크 점수도 GPU로 계산해 커밋하지 않는다. 리랭커 켬·끔의 보고서는 리랭커의 기본을 정하는 결정의 품질 쪽 근거다. 그 실험의 티켓이 보고서와 core 16이 잰 지연을 함께 사용자에게 보인다("전체 게이트와 리랭커" 절).
- [정함] 기본값을 바꾸기로 승인되면 그 티켓이 설정의 기본값, core 명세의 설정 절, 묶음의 구성, 추론 기록, 기준 보고서를 같은 PR에서 고친다. 기본값은 계약이 아니라 설정이라 ADR은 없다(core 명세 "설정" 절).
- [넘겨받음] 공개 데이터셋(allganize)은 로컬 참고 측정이고 PDF는 커밋하지 않는다(ADR 0018).
- [정함] 공개 데이터셋의 티켓은 원문(데이터셋의 카드와 라이선스 파일)으로 이용 조건을 확인해 프로브 README에 적고, 데이터셋을 내려받아 이 명세의 묶음 형식으로 바꾸는 스크립트를 `.scratch/search-eval/probes/`에 둔다. 저장소에는 스크립트와 보고서의 숫자만 커밋하고 PDF와 질문은 커밋하지 않는다. 데이터셋의 이름과 조건을 이 세션은 원문으로 확인하지 않았다.

## Testing Decisions

- [사용자 선택] 주 이음매는 명령줄 도구의 표면이다. 시험이 작은 묶음(문서 서너 개, 질문 대여섯 개)을 임시 폴더에 만들고 도구의 `main`을 인자와 함께 불러, 나온 보고서 파일과 종료 코드와 표준 오류의 글을 본다. 뒤에는 Docker의 실제 테스트 PostgreSQL과 TEI 스텁을 붙이고 Claude API는 가짜 끝점으로 대신한다. 사용자가 2026-11-13에 세 선택지(명령줄 도구 표면 + 실제 PostgreSQL + 스텁, 유스케이스 단위 + 가짜 포트, 전부 실물) 가운데 골랐다. core 명세의 주 이음매(바깥 표면 + 실제 PostgreSQL + TEI 스텁)와 같은 방식이다.
- [정함] 좋은 테스트는 바깥에서 보이는 행동만 본다. 묶음을 색인하고 평가를 돌려 보고서의 숫자를 보는 식이다. 유스케이스 안의 함수 호출이나 표의 행을 보지 않는다. 다만 "아무것도 쓰지 않는다"와 "스키마도 올리지 않는다"는 바깥에서 보이는 것으로 본다. 스키마의 판 표(alembic)가 없는지, 기존 관리 유스케이스로 읽은 문서와 지식베이스 설정이 그대로인지, 기록 파일과 판정 파일의 바이트가 그대로인지다(티켓 세션의 명세 검토가 짚었다). 지표의 정의는 손으로 계산할 수 있는 작은 묶음(기대 근거가 어느 순위에 나오는지 스텁의 결정적 벡터로 정해지는 것)으로 고정한다. 테스트 이름은 한국어 행동 명세이고 skip은 실패다(`CODING_STANDARDS.md`, `.claude/rules/tests.md`).
- [정함] 보조 이음매는 둘이다. PostgreSQL 어댑터의 `diagnose_candidates`(진단용 검색 절의 대조 시험)와, 기존 MCP 계약 시험(`tests/contract/`)에 더하는 `min_score`의 시험이다. 새 이음매는 가짜 Claude 끝점 하나다. 시험이 띄우는 작은 ASGI 앱이 Messages API의 응답 모양을 흉내 내고 받은 요청을 기억하며, 실제 Claude 어댑터가 끝점 주소 설정으로 거기에 붙는다. TEI 스텁(`tests/support/tei_stub.py`)과 같은 방식이다.
- [정함] 시험하는 행동. 표면 시험: `index` 뒤 `run`이 질의 목록마다 단계별 줄을 낸다, `run --through fused`의 보고서에는 리랭크 뒤 줄이 없고 `--through rerank`의 보고서에는 있다, 글귀가 조각의 경계에서 갈리면 놓친 것으로 세고 탈락 지점이 `no_matching_chunk`다, 닿는 조각이 후보에 들지 못한 질의와 합치기에서 밀린 질의와 리랭크에서 밀린 질의에 각각의 탈락 지점이 붙는다, 공백과 줄바꿈이 달라도 글귀가 닿는다, 다른 문서의 같은 글귀는 닿지 않는다, 쪽으로 적은 기대 근거가 두 쪽에 걸친 조각에 닿는다, 유형 표지와 필터 질의의 숫자가 따로 나온다, 키워드 토큰이 빈 질의가 키워드만 단계에서 놓친 것으로 세어지고 그 질의의 낱말 겹침이 `null`이며 겹침이 0인 수에 들지 않는다, 조각 하나가 기대 근거 둘에 닿아 nDCG가 잘린 질의가 그 줄의 잘린 수에 세어진다, 보고서에 질의의 글과 조각의 글이 없다, `validate`가 틀린 판·없는 문서·맞지 않는 해시·문서에 없는 글귀·모르는 유형 표지·묶음 폴더 밖을 가리키는 경로(절대 경로, `..`, 밖을 가리키는 링크)·기대 근거의 문서를 거르는 기간 필터가 붙은 질의(문서의 갱신일이 `updated_before`와 같으면 거부하고 `updated_after`와 같으면 받는다)를 까닭과 함께 거부한다, `compare`가 하락폭을 넘는 하락에서만 실패하고 묶음의 해시나 구성이 다르거나 기준 보고서가 없으면 견주지 않고 실패한다, `compare --gate fast`와 `--gate full`이 각자의 기준 보고서 파일과 줄을 본다, `index`가 현재 판의 요소가 구성과 다른 데이터베이스에서 아무것도 쓰지 않고 종료 코드 1을 낸다, 평가 전용 이름이 없으면 제품의 `RAG_DATABASE_URL`과 작업 폴더의 `.env`가 있어도 도구가 돌지 않고 빠진 이름을 알린다, `index`·`run`·`judge`가 묶음 밖의 문서가 든 데이터베이스와, 키는 묶음의 것인데 내용 해시가 다른 문서가 든 데이터베이스에서 아무것도 쓰지도 부르지도 않고 종료 코드 1을 낸다(`index`는 스키마도 올리지 않는다), 데이터베이스의 이름이 `rag_eval`로 시작하지 않는 주소에서는 도구가 접속하지 않고 종료 코드 1과 이름의 규칙을 낸다(닿지 않는 주소를 주어도 연결 오류가 아니라 그 규칙이 나오는 것으로 본다), `index`가 문서 목록과 해시가 다른 문서 파일이 있으면 `--records write`에서도 스키마를 올리지 않고 기록 파일을 쓰지 않으며 종료 코드 1을 낸다, `records/`나 그 안의 기록 파일이나 판정 파일이 묶음 밖을 가리키는 링크이면 `index`·`run`·`judge`가 쓰지 않고 종료 코드 1을 내며 링크가 가리킨 파일이 그대로이고 `validate`도 거부한다, `inspect`가 글을 표준 출력에만 찍는다. 티켓 세션의 명세 검토로 더한 것: `validate`가 문서 목록의 날짜를 그날 00:00 `+09:00`으로 바꿔 판정한다(경계 시험은 이 바꾸기를 거친 값으로 쓴다), 오프셋이 없는 필터 시각과 `groups`가 든 필터를 거부한다, `validate --indexed`가 색인되지 않은 문서가 있는 데이터베이스에서 실패한다, 작업 폴더의 `.env`에 `RAG_PARSE_MAX_PAGES=1`이 있어도 보고서가 같다, `diagnose_candidates`가 `CandidateScan.EXACT`일 때 HNSW 색인을 쓰지 않는다(EXPLAIN), `run`이 판에 적힌 끝점이 아니라 `RAG_EVAL_EMBEDDING_URL`로 질의를 임베딩한다.
- [정함] 덮는 스토리와 판정. 위 목록이 덮지 않은 스토리(9, 14, 18, 27, 28, 29)와 판정(TEI 판과 compose 태그가 다를 때, 용량 상한, 목록에 없는 파일, `judge`의 모델·지시문 판 불일치, `--prune`, 평가 도중 판이 바뀔 때)은 받는 티켓의 수용 기준이 시험으로 든다. 스토리 34~38(최소 점수의 동작)은 최소 점수의 구현 티켓이 받는다. 평가 도중 판이 바뀌는 시험은 질의 사이에 판을 바꿀 걸이가 지금 없어(티켓 세션의 명세 검토가 짚었다) 그 티켓이 걸이를 정한다.
- [정함] 추론 기록의 시험. 기록에 있는 글은 스텁을 부르지 않는다(스텁의 요청 횟수로 본다), `read`에서 기록에 없는 글이 상한을 넘으면 종료 코드 1과 안내가 나오고 기록 파일은 그대로다, 리랭커의 끝점 없이 돈 전체 실행은 기록에 없는 쌍이 하나만 있어도 실패한다, `write`가 그 명령이 주인인 파일만 다시 쓰고 다른 명령의 파일은 바이트 그대로 둔다(`index`와 빠른 실행의 `run` 뒤에 `rerank.jsonl`이 그대로다), `write`가 쓰이지 않은 열쇠를 자기 파일에서 지우고 같은 내용이면 같은 바이트를 쓴다, `index --records write`가 문서가 든 데이터베이스에서 기록 파일을 바이트 그대로 둔 채 종료 코드 1을 낸다, `off`가 기록을 읽지도 쓰지도 않는다, 모델 이름이 다르면 기록의 값을 쓰지 않는다, `validate`가 `records.json`의 요청 지문이 어댑터가 내는 것과 다르면 실패하고 다시 만들 기록 파일을 알린다, `write`가 요청 지문이 다른 기록 파일의 옛 값을 옮기지 않고 다시 계산한다(스텁의 요청 횟수로 본다), `write`로 돈 명령이 1로 끝나면 주인 파일이 바이트 그대로다, 보고서가 읽은 기록 파일의 해시를 싣고 `compare`가 그 해시가 기준 보고서와 다르면 숫자를 견주지 않고 실패한다. 어댑터의 시험(`tests/adapters/`)은 실제로 보낸 요청의 경로와 칸이 요청 지문의 원문과 같은지를 본다.
- [정함] 판정의 시험. 설정 셋이 모두 없으면 판정기를 조립하지 않는다, 판정기의 설정도 판정 파일도 없으면 `run`이 LLM 숫자를 `null`로 낸다, 판정기의 설정이 없어도 판정 파일이 있으면 `run`이 그 파일로 LLM 숫자를 낸다(스토리 31. 처음 문장은 설정이 없으면 `null`이라 적어 그 스토리와 어긋났다. 티켓 세션의 명세 검토가 짚었다), 일부만 있으면 빠진 설정의 이름을 알린다, `judge`가 `--yes` 없이 건수와 비용만 찍고 가짜 끝점을 부르지 않는다, 끊긴 뒤 다시 돌리면 이미 받은 조합을 부르지 않는다(가짜 끝점의 요청 횟수로 본다), 질의의 글이나 지시문의 판이 바뀌면 옛 판정이 판정 없음으로 세어진다, 로그에 키와 요청·응답의 본문이 없고 가짜 끝점이 오류를 낸 때의 표준 오류에도 없다(선례는 `tests/server/test_log_capture.py`와 `test_request_logging.py`).
- [정함] 저장소 상태의 시험. 커밋된 공공 문서 묶음이 `validate`의 파일 검사(형식, 해시, 용량, 기록의 판과 크기와 요청 지문)를 지나는지를 pytest가 본다. 지금 통과함을 재는 시험과 위반을 잡는 변이 시험을 하나씩 둔다(`.claude/rules/tests.md`). 색인이 필요한 검사(글귀가 전문에 있는지)와 평가는 pytest가 아니라 CI의 게이트가 본다. 실제 모델이 필요하기 때문이다.
- [정함] CI 게이트의 경로 판정은 `tests/tools/`가 순수 함수로 시험한다. 푸시와 수동 실행에서는 바뀐 경로와 무관하게 평가한다고 답하는 것과, PR에서 바뀐 경로를 읽지 못하면 평가한다고 답하는 것도 그 시험이 본다. 게이트 잡 자체는 워크플로의 실제 실행으로 확인한다. 게이트를 넣는 티켓이 평가하지 않는 PR(문서만 바꾼 커밋)에서 `verify`가 초록인 것과, 숫자를 일부러 떨어뜨린 커밋에서 빨강인 것을 실행 기록으로 남긴다(`CLAUDE.md` 작업 규약 3).
- [정함] 선례. 명령을 `main(argv)`로 부르는 시험 `tests/test_ingest_command.py`, 어댑터의 SQL 시험 `tests/adapters/test_vector_index_chunks.py`, 계약 시험 `tests/contract/test_search_tool.py`, TEI 스텁과 그 서버 `tests/support/tei_stub.py`·`tei_server.py`, 테스트가 만드는 문서 `tests/support/docx_files.py`·`hwpx_files.py`·`pdf_files.py`, 도구의 시험 `tests/tools/`.
- [정함] 재지 않은 채 구현 티켓으로 넘기는 측정은 다섯이고 모두 멈출 조건이 있다. 실제 Claude API 호출이 어댑터 프로브의 꼴대로 도는지(ADR 0019가 첫 구현 티켓에 맡겼다. 돌지 않으면 그 ADR로 돌아온다), 빠른 게이트의 CI 시간(15분을 넘으면 다시 묻는다), 실행 사이의 흔들림(질문 하나의 몫을 넘으면 다시 묻는다), GPU의 처리량(평가 한 번의 기록 만들기가 2시간을 넘으면 다시 묻는다), 다시 계산한 값의 차이(같은 장치에서 두 번, 그리고 CPU와 GPU 사이. 문턱을 넘으면 다시 묻는다)다. 앞의 셋은 평가 도구나 키가 있어야 잴 수 있고, GPU가 드는 측정은 NVIDIA 드라이버를 올려야 잴 수 있어 이 세션에서 재지 못했다. 같은 장치에서 두 번 계산하는 측정은 CPU만으로도 되지만, 프로브를 돌리던 때에 다른 세션의 지연 측정이 같은 PC에서 돌고 있어서 이 세션에서 돌리지 않았다. 티켓 세션의 명세 검토가 CPU 임베딩은 손으로 봤고(추론 기록 절), 리랭커와 장치 사이의 차는 리랭크 기록을 만드는 티켓이 프로브로 잰다.

## Out of Scope

- [거절] 관리자 페이지의 평가 화면, 그 관리 API, 평가 세트와 결과의 저장 표, 지식베이스마다 LLM으로 내보내기를 따로 허용하는 장치, 지식베이스의 최소 점수 기본값을 고치는 화면. admin이 받는다. `.scratch/admin/plan.md`에서 search-eval 설계가 넘긴 것을 적은 문단에 이미 있고, 그 기능의 `Blocked by`에 search-eval을 더할지는 admin의 설계 인터뷰가 정한다고 거기 적혀 있다. 이 명세가 더 넘기는 것은 하나다. 최소 점수의 기본값이 있는 지식베이스에서 리랭커를 빼는 설정 변경을 관리 API가 422로 거부해야 한다는 규칙이고(최소 점수 절), 같은 파일의 본문에 search-eval 명세가 넘긴 것으로 적었다.
- [거절] 리랭커의 CPU 속도를 푸는 길 가운데 실험 범위 밖의 것의 구현(ONNX가 있는 리랭커 모델로 바꾸기, GPU 이미지를 배포 구성에 넣기, 검색 시간 제한의 기본값을 늘리기). 이 기능은 그 결정에 품질 숫자를 대고 사용자에게 묻는 데까지 한다("전체 게이트와 리랭커" 절). 리랭커를 끄는 기본은 ADR 0018이 이 기능에 둔 실험(리랭커 켬·끔)의 기본값 변경이라 이 기능에서 하고, 나머지 길은 사용자가 고른 뒤에 받는 곳을 정한다. 받는 곳이 아직 없어 다른 기능의 계획에는 적지 않았다. 묻는 때는 이 명세의 그 절이 정해 두었고, 그 실험의 티켓이 받는다.
- [거절] 이미지에 실리는 SDK의 부품 목록과 취약점 스캔. release-image가 받는다. `.scratch/release-image/plan.md`에 이미 적혀 있다.
- [거절] 품사 규칙의 변경, 좁은 필터의 정확 스캔 분기, 시멘틱 청킹 전략, 키워드 엔진의 교체, 색인 시점의 LLM 문맥 부여. 이 기능은 판단용 숫자만 내고, 고칠지는 그 숫자를 본 뒤 별도 작업으로 정한다(ADR 0018).
- [거절] 관련 문서를 빠짐없이 다는 학술 방식의 정답, 네 등급의 관련성 판정, 다른 LLM 제공자와 로컬 모델의 판정기, CI에서의 API 호출(ADR 0018, 0019).
- [거절] 색인에 답이 없는 질의의 목록. 최소 점수의 효과를 직접 재려면 필요하지만 설계가 정한 측정(닿은 조각과 그렇지 않은 조각의 분포)에 들지 않는다. 분포가 판정을 내리기에 모자라면 그때 사용자에게 묻는다.
- [거절] 제품 이미지의 관리 명령으로 평가를 여는 것, MCP 도구로 진단용 검색을 여는 것(원칙 IV, ADR 0018).

## Further Notes

- 티켓의 순서에 관한 조건. 포트 둘(`VectorIndex.diagnose_candidates`, `RelevanceJudge`)을 더하는 티켓이 기능의 첫 티켓이다. ADR 0007 Consequences가 포트를 계약으로 보아 첫 티켓에 두기 때문이다. 헌법 파일인 `docs/constitution/operations.md`의 CI 절은 첫 티켓이 아니라 게이트를 넣는 티켓이 판 patch와 함께 고친다(ADR 0018 Consequences가 그 티켓에 두었다). `docs/agents/issue-tracker.md`가 헌법을 바꾸는 티켓을 첫 티켓으로 두는 규칙의 예외이고, 까닭은 그 문장이 게이트가 선 뒤의 동작을 적는 사실 문장이라 다른 티켓이 그 문구에 기대지 않기 때문이다(티켓 세션의 명세 검토가 짚었다). 계약을 바꾸는 티켓(최소 점수)은 기능의 첫 티켓이 아니다(ADR 0017이 둔 예외). 재료를 넣는 티켓과 게이트를 넣는 티켓은 사용자의 확정과 승인을 기다리는 지점이 있다(후보 목록, 질문의 검수, 첫 기준 보고서). 리랭크 기록을 만드는 티켓은 사용자가 NVIDIA 드라이버를 올린 뒤에 집을 수 있고(드라이버는 2026-11-13에 올랐다. 티켓 세션이 손으로 봤다), 전체 게이트, 점수 분포, 리랭커 실험은 그 티켓 뒤다. 최소 점수의 구현 티켓은 ADR 0017의 승인 이력이 생긴 뒤에 쓴다. 기능 계획의 `Blocked by`가 든 core는 2026-11-13에 끝났으므로(`.scratch/core/plan.md`의 `**끝:**` 줄) 이 기능의 티켓을 막는 다른 기능은 없고, 이 기능의 `끝` 줄은 사용자의 승인에 달려 있다(명세를 쓸 때는 드라이버 갱신도 기다렸다).
- 면제 PR이 고칠 수 없어 구현 티켓이 고치는 파일. `pyproject.toml`의 import 금지 목록(`anthropic`을 더해 열일곱)과 `CLAUDE.md`의 레이어 절이 적은 수는 Claude 판정기 어댑터와 SDK를 넣는 티켓이 고친다(판정기 포트를 넣는 첫 티켓은 SDK를 들이지 않는다). `docs/constitution/operations.md`의 CI 절(적중률이 기준치 아래로 떨어질 때라는 문장)과 `.github/workflows/ci.yml`의 머리 주석(느린 검사를 main PR에만 둘지를 설계에 미룬 문장)은 게이트를 넣는 티켓이 고친다(일지 `## 다음`).
- 공개 시연(`docs/PRD.md` 성공의 정의)의 "검색 적중률 보고서"는 빠른 실행의 보고서로 먼저 낼 수 있다. 리랭크 뒤 줄은 리랭크 기록을 만든 뒤의 전체 실행에서 더해진다.
- 이 세션이 잰 것은 프로브 `.scratch/search-eval/probes/tei-cpu/`의 둘이고, GPU 이미지는 띄워 보기만 했다(같은 폴더의 서버 로그). 두 측정 모두 이 PC(논리 코어 16)에서 컨테이너를 코어 4개로 묶은 것이다. 임베딩의 둘째 실행(`--cpuset-cpus=0-3`) 도중에는 리랭커 컨테이너가 모델을 내려받고 있었고 `docker stats`가 테스트 PostgreSQL 컨테이너를 CPU 156%로 냈다(손으로 봤다. 다른 세션의 pytest로 본다). 그 임베딩 컨테이너는 프로브가 끝나기 전에 죽었고 `docker inspect`의 `OOMKilled`가 참, 종료 코드가 137이었다(손으로 봤다). 그때까지의 배치 여섯은 서버 로그로 남겼다. 리랭크의 배치는 그 컨테이너가 죽은 뒤에 돌았다. 첫 임베딩 실행 때 무엇이 함께 돌았는지는 보지 않았다. 그래서 자릿수를 보는 값이고 CI 러너의 값이 아니다.
- 리랭커의 측정은 제품에도 닿는다. 이 세션의 프로브(코어 4개에서 쌍 하나에 약 8초)와 core 16의 프로브(리랭커를 켠 후보 50개의 검색 한 번에 130초, 한 번 잰 값)가 같은 것을 가리킨다. 리랭커를 켠 기본 구성은 CPU에서 검색 시간 제한 20초 안에 답하기 어렵다. 그 결정을 언제 누구에게 묻는지는 "전체 게이트와 리랭커" 절의 "리랭커의 CPU 속도와 기본의 결정" 항목이 정한다.
- core 16의 측정을 읽을 때의 한계. 개발 PC 한 대에서 설정마다 한 번씩 돌린 값이고(요청은 조합마다 1~16건), 호스트가 다른 작업과 CPU를 나눠 썼으며, TEI를 `--max-batch-tokens 4096`으로 띄우고 시간 제한을 측정용으로 늘린 실행이다(`.scratch/core/spec.md`의 Further Notes와 그 티켓의 일지). 이 명세는 그 값을 자릿수를 보는 데에만 쓴다.
- 명세를 처음 쓸 때는 추론 기록을 손으로 고친 변조를 게이트가 보지 못했다(명세 세션의 보안 리뷰가 낸 지적이다). 기록 파일이 묶음의 내용 해시에 들지 않고(보고서 절), 기록만 맞추는 커밋이 승인 대상이 아니었으며, CI는 기록에 있는 값을 다시 계산하지 않기 때문이다(추론 기록 절). 그래서 검색을 떨어뜨리는 변경과 함께 기록의 값을 고친 PR은 숫자를 지킨 채 게이트를 지날 수 있었고, 이진 파일의 차이는 사람이 읽을 수 없다. 이 명세는 처음에 그 길을 막지 않았고, 티켓 세션에서 사용자가 첫째 길(기록 해시의 승인)을 골라 지금은 기록 파일의 해시가 바뀌면 기준 갱신과 같은 승인을 받는다(CI 게이트 절의 기록 해시 항목, ADR 0018 이력 2026-11-13 "평가는 후보를 정확 스캔으로 뽑고, 추론 기록의 해시가 바뀌면 승인을 받는다"). 아래는 고르기 전의 기록이다. 막는 길은 둘로 본다. 보고서에 기록 파일마다의 해시를 싣고 `compare`가 그것이 기준 보고서의 것과 다르면 기준 갱신과 같은 승인을 받게 하는 길과, 빠른 게이트가 기록의 임베딩 일부를 CI에서 다시 계산해 대 보는 길이다. 앞의 길은 기록을 다시 만드는 PR마다 사용자의 승인을 늘리고 그 PR의 하락을 자동 판정이 아니라 사람이 보게 하며, 뒤의 길은 게이트의 시간을 늘리고 리랭크 기록은 보지 못한다. 승인 절차가 걸린 결정이라 이 명세가 정하지 않고, 티켓으로 쪼개는 세션이 빠른 게이트의 티켓을 쓰기 전에 사용자에게 묻는다(이 세션의 일지 `## 다음`). PR #34 봇 첫 회차의 지적(TEI 어댑터의 변경이 기록에 가려진다)도 같은 자리에서 난다. CI가 기록의 값을 다시 계산하지 않기 때문이다. 요청 쪽은 요청 지문이 보게 했고, 응답 쪽까지 보는 길 셋은 추론 기록 절이 적었으며 그 가운데 표본을 다시 계산하는 길은 변조도 함께 본다. 사용자에게 물을 때 그 셋을 위의 둘과 함께 보인다. 티켓 세션은 겹치는 길(빠른 게이트의 임베딩 표본)을 하나로 세어 네 길을 여럿 고를 수 있게 보였고, 사용자는 기록 해시의 승인 하나만 골랐다. 응답 쪽의 한계는 남는다(추론 기록 절).
- PR #27 봇 첫 회차에서 남겨 사용자가 정할 것(원칙 VII 아래나 헌법 README에 ADR 0015의 판 해석을 가리키는 포인터를 둘지)은 헌법의 개정이라 이 명세가 정하지 않는다(일지 `## 다음`).
