# search-eval: 평가 세트로 검색의 상위 k개 적중률을 재고, 기준치 아래로 떨어지면 CI가 실패한다
**슬라이스:** 2
**Blocked by:** core

평가 세트(질문과 기대 근거)로 상위 k개 적중률을 잰다. LLM 없이 검색만 재므로, 청킹, 임베딩 모델, 리랭커를 바꿀 때마다 돌려 검색 품질이 떨어지는 것을 잡는다. 공개 시연(core, search-eval, release-image)의 한 축이다.

core 명세(`.scratch/core/spec.md`, 2026-11-10)가 넘긴 것: 조각 상한과 겹침의 기본값(512·64 토큰)의 판정, 키워드로 넣는 품사 집합(명사·외국어·한자·숫자·어근. 토크나이저 규칙의 판은 색인 판의 요소라 바꾸면 재색인이다)의 재검토, 리랭커 켬·끔과 검색 후보 수(50)의 효과, 좁은 필터에서 정확 스캔 분기가 필요한지, 시멘틱 청킹 전략을 더할지.

dev-branch(ADR 0016, 2026-11-12)가 넘긴 것: 적중률 게이트를 CI에 더할 때, 그 잡을 main PR(출시 PR과 핫픽스 PR)과 main 푸시에서만 돌릴지 dev PR에서도 돌릴지 정한다. 지금은 main PR에만 도는 잡이 없어 dev PR과 main PR이 같은 잡을 돈다.

사용자가 넘긴 것(2026-11-10): 평가 항목 넷과 근거로 든 글 셋. 설계 인터뷰가 넣을지 판정한다. 아래 인용은 사용자의 글 그대로다(머리 줄만 이 문장으로 옮겼다). 항목 2가 따옴표로 든 문장은 ADR 0006 Consequences의 `ts_rank` 항목을 줄인 것이라 원문은 그 ADR에서 읽고, 항목 3의 위 첫째 제안은 이 계획 아래의 최소 점수 제안 문단이다. 근거로 든 글 셋은 웹 요약이라 근거가 아니다(`docs/agents/issue-tracker.md` 프로브와 근거 절).

> 1. 평가 질의를 두 종류로 잰다. 사람이 쓴 질문 그대로와, 클라이언트의 모델이 지은 검색어(키워드에 가까운 짧은 글)다. 이 저장소는 클라이언트를 모르므로, 평가 세트의 형식이 "질의 문자열 목록을 밖에서 받아 같은 기대 근거에 붙일 수 있다"까지만 정한다. 목록은 클라이언트 쪽이 만든다.
> 2. 적중률을 네 줄로 따로 낸다. 벡터만, 키워드만, 둘을 합친 것(RRF), 리랭크 뒤. ADR 0006 Consequences의 "`ts_rank`에는 IDF가 없어 BM25가 아니다. 모자라면 키워드 엔진만 바꾼다"를 판정할 숫자가 이 표다. 키워드 질의는 토큰을 OR로 잇는다는 것(core 명세 "키워드 토큰")도 함께 본다.
> 3. 최소 점수 임계값을 판정한다(위 첫째 제안이 받아들여졌을 때). 기대 근거인 조각과 아닌 조각의 리랭크 점수 분포, 임계값마다의 적중률과 빈 결과의 비율을 낸다.
> 4. 놓친 질문을 까닭으로 나눠 센다. 조각에 문맥이 없어서(절 경로를 붙여도 못 찾음), 표나 그림이어서, 낱말이 달라서, 문서 여럿을 이어야 해서. ADR 0003이 미룬 "청킹 뒤의 보강 자리"와 색인 시점의 LLM 문맥 부여를 더할지는 첫째 까닭의 비율을 보고 정한다. 사용자의 결정은 "색인 시점의 LLM 보강은 이 숫자를 본 뒤에 정한다"이다.
>
> 근거로 든 글(검색 요약으로만 봤고 원문을 읽지 않았다. 문서에 근거로 적기 전에 원문을 대 본다):
> - 단독으로 잰 검색 품질이 에이전트 루프 안의 쓸모를 늘 예측하지는 못한다: arXiv 2605.04018
> - 에이전트가 지은 하위 질의에서 BM25가 LLM 기반 검색기를 약 30% 앞섰다: arXiv 2602.05975
> - 문맥 부여 청킹의 검색 실패 감소 35%·49%·67%: Anthropic의 발표를 2차 인용(arXiv 2606.21676)으로 봤다

사용자가 넘긴 제안(2026-11-10): `search`에 최소 점수로 결과를 거르는 길을 둔다. core 티켓 세션이 core 명세에 두지 않고 이 기능에 통째로 넘겼다(사용자가 골랐다. core 명세 Out of Scope). 제안은 입력에 선택 인자 하나(이름은 설계가 정한다. 예: `min_score`)를 더하고 지식베이스 설정에 그 기본값 칸을 두는 것이다. 기본은 없음이고 없으면 지금처럼 거르지 않는다. 자리는 core 명세 검색 흐름의 다섯째(리랭크)와 여섯째(`top_k`개 자르기) 사이다. 제안의 까닭: 클라이언트의 모델이 검색어를 지어 부르는 쓰임에서는 점수가 낮은 조각도 모델의 입력에 쌓여 토큰이 늘고 근거 없는 답의 재료가 된다. 임계값은 리랭커 모델마다 점수 분포가 달라 리랭커 설정을 가진 서버 쪽에 두는 것이 맞고, 빈 결과는 클라이언트에게 근거가 없다는 것을 결정적으로 알린다. 설계 인터뷰가 정할 것 셋(사용자가 넘기기를 고르며 함께 넘긴 질문). 리랭커가 없는 지식베이스(`score`가 RRF 점수라 순위만 반영한다)에서 이 인자를 무시할지 `invalid_argument`로 거부할지, 거른 뒤 결과가 0개인 것을 오류가 아니라 빈 결과로 볼지, 그리고 계약의 판이다. 판은 열린 질문이다. ADR 0015는 결과 객체의 칸 추가를 minor로 정했을 뿐 입력 인자의 추가는 정하지 않았고, 원칙 VII은 칸을 더하는 것을 같은 판에서 한다고만 적는다. 그래서 입력 인자의 추가가 `format_version`에 드는 변경인지와 든다면 어느 자리를 올리는지를 정한다. 임계값의 값은 위 항목 3이 잰다.

수락: 공개 문서 묶음의 평가 세트로 적중률 보고서가 나오고, 정한 기준치 아래로 떨어지면 CI가 실패한다.
