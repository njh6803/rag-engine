# standalone-test-fills-image-namespace: 릴리스 워크플로의 단독 compose 시험이 시험용 이미지 이름으로 묶음을 띄우게 고친다(핫픽스)

**What to build:** release-image의 첫 릴리스(출시 PR 84의 병합 커밋 `24f814d`, 실행 https://github.com/njh6803/rag-engine/actions/runs/44716196490)가 `build` 잡의 `단독 compose 시험`에서 약 20초 만에 실패했다. `docker compose up -d --wait`이 종료 1로 끝났고 컨테이너 로그(`compose.log`)는 0바이트였다. 올릴 묶음은 `tools/release.py bundle --number … --namespace "$DOCKERHUB_NAMESPACE"`(Docker Hub 이름 `njh6803`)로 짓는데, 시험은 러너에 싣는 시험용 이미지를 `rag-engine-release-test/…`로 지어 `RAG_STANDALONE_NAMESPACE`로 넘긴다. 묶음 안의 `.env.example`은 `RAG_ENGINE_NAMESPACE=njh6803`이고 시험은 `.env`에서 `RAG_ALLOWED_HOSTS`와 `POSTGRES_PASSWORD` 두 칸만 채우므로, compose가 로컬에 없는 `njh6803/rag-engine-server:0.1.0-rc.1`을 Docker Hub에서 받으려다 실패한 것으로 읽힌다(러너의 stderr는 남지 않아 추정이다. 이 PC에서 같은 입력을 되풀이해 확인한 값은 Comments). 시험 앞쪽의 소유 바꾸기(`docker run`)는 시험이 받은 이름으로 이미지를 불러 통과한다. 환경 변수 없이 도는 경로(시험이 자기 이름공간으로 묶음을 직접 짓는 경로)는 묶음과 이미지의 이름공간이 같아 이 틈이 드러나지 않는다. 환경 변수를 주는 경로는 `ci.yml`이 환경 변수를 주지 않으므로 릴리스 워크플로의 이 실행이 처음이다. 고치는 곳은 `tests/standalone/test_standalone_compose.py`의 `stack` 픽스처다. `.env`에 `RAG_ENGINE_NAMESPACE`와 `RAG_ENGINE_VERSION`도 시험이 받은 이름공간과 번호로 덮어쓴다. 운영자는 이 두 칸을 고치지 않는다(`.env.example`에 묶음을 만든 릴리스의 값이 이미 적혀 있다). 시험이 운영자와 다르게 하는 일이 하나 느는 것이고, 모듈 독스트링이 그 일을 적는다. 묶음 바이트는 그대로라 시험한 묶음과 올릴 묶음이 같다는 약속은 유지된다. 같은 PR에서 실패한 명령의 stderr를 시험 실패 메시지에 싣는다. 이번에는 `run`이 stderr를 삼켜 로그만으로 까닭을 볼 수 없었다.

## Comments

- **고치기 전의 틈을 이 PC에서 되풀이했다.** 스크래치의 `repro_before.py`가 고치기 전 픽스처와 같게 `.env`의 두 칸만 채우고(`RAG_ENGINE_NAMESPACE=njh6803`, `RAG_ENGINE_VERSION=0.1.0-rc.1`이 그대로 남은 것을 출력으로 봤다) `docker compose -p rag-engine-e2e-repro up -d --wait --wait-timeout 60`을 쳤다. 종료 1이고 stderr가 `Error response from daemon: manifest for njh6803/rag-engine-server:0.1.0-rc.1 not found: manifest unknown: manifest unknown`이었다. 파이썬 시험에서 쓰는 `run`이 stderr를 삼켜 첫 릴리스 로그에는 이 문구가 없었다. 첫 릴리스의 실패 원인이 같다고 확정한 것은 아니고(러너의 stderr가 없다), 같은 입력에서 같은 자리가 같은 종료 코드로 멈췄다는 것까지다.
- **고친 뒤 환경 변수 경로로 돌렸다.** `RAG_STANDALONE_NAMESPACE=rag-engine-test`, `RAG_STANDALONE_VERSION=0.1.0-rc.1`, `RAG_STANDALONE_BUNDLE=<njh6803으로 지은 묶음>`, `RAG_STANDALONE_MODELS=<링크를 푼 bge-m3 복사본>`으로 `uv run pytest tests/standalone -q`. 처음 실행은 서버 건강 검사가 시간에 쫓겨 `up`이 실패했다(`dependency failed to start: container ... server-1 is unhealthy`, 이 PC에 다른 세션들이 시험을 돌리던 때다. 이 실패 문구를 읽을 수 있었던 것이 `run` 고침의 효과다). 같은 코드로 다시 돌린 실행은 `up`을 지나 `2 failed, 23 passed in 758.17s`였다. 실패 둘은 시간 문제였다: MCP 검색의 `ReadTimeout`(60초)과 서버 프로세스를 죽인 뒤 회복 20.8초(상한 15초). 그 두 시험만 다시 돌린 실행은 `2 passed, 23 deselected in 335.04s`였다. 이 PC의 CPU가 다른 세션 때문에 80%대였고(`wmic`로 84를 봤다), 전체를 한 번에 통과한 실행은 얻지 못했다. 앞 티켓 04의 같은 시험은 `25 passed in 206.86s`였다.
- **셀프 리뷰.** 표준 축과 명세 축을 sonnet에 맡겼다. 고친 것: `env_values`와 모듈 독스트링이 운영자와 같다거나 다르게 하는 일이 둘이라고 적던 것(거짓)을 셋째 차이로 고쳤다. 항상 참인 단언(`"3" in str(...)`)을 `"exit status 3"`으로 고쳤다. 픽스처가 옛 두 칸으로 되돌아가도 새 시험이 초록이던 틈을 `.env`를 쓰는 부분을 `write_env`로 빼고 그 함수로 시험해 닫았다. `release.py`의 표지 상수를 시험이 가져다 쓴다. 지금 코드 경로에 없는 옛 호출을 재던 시험을 지웠다. 남긴 것: 실패 메시지에 stdout 전체가 실려 토큰을 내는 호출이 실패하면 시험용 일회성 토큰이 로그에 남을 수 있다(영향 작음). 묶음 안 `.env.example`의 표지 치환 오류는 이제 이 시험이 아니라 `tests/tools/test_release.py`가 잡는다.
