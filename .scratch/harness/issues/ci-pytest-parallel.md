# ci-pytest-parallel: CI의 python 잡이 pytest를 나눠 돌려 제한 15분 안에 여유를 만든다

**What to build:** CI의 `python` 잡은 `uv run pytest -q`를 한 프로세스로 돌린다. 이 잡의 제한은 15분(`ci.yml`의 `timeout-minutes: 15`)이고 pytest 스텝만 13분 반 안팎이 걸려, 제한을 넘겨 취소된 실행이 이어졌다. GitHub의 실행 기록을 `gh run list`와 `gh run view`로 읽은 값은 다음과 같다(측정 스크립트는 없다).

| 머리 | 실행 | 잡 시간 | 결과 |
|---|---|---|---|
| `149e5eb`(PR #107의 첫 머리) | 첫 시도 | 14분 43초 | 통과 |
| `a427ad8`(일지 파일 하나만 바꾼 커밋) | 첫 시도 | 15분 15초 | 제한 초과로 취소, `verify` 실패 |
| `a427ad8` | 두 번째 시도 | 15분 16초 | 제한 초과로 취소, `verify` 실패 |
| `a427ad8` | 세 번째 시도(실패한 잡만 두 번 다시 돌림) | 14분 45초 | 통과 |
| `cc807a1`(`dev` 푸시) | 첫 시도 | 15분 제한에서 끊김(실행 전체 15분 13초) | 취소 |
| `6601a7c`(`dev` 푸시) | 첫 시도 | 15분 15초 | 제한 초과로 취소, `verify` 실패 |

그래서 `dev`의 마지막 푸시 실행 둘이 모두 빨강이다. 통과한 실행에도 제한까지 17초가량밖에 남지 않았다. 시험이 늘면 취소되는 실행이 늘어난다.

고치는 곳은 `.github/workflows/ci.yml`의 pytest 스텝 하나다. `uv run pytest -q`를 `uv run pytest -q -n auto`로 바꿔 러너의 CPU를 모두 써서 나눠 돌린다. 이 시험 묶음은 나눠 돌 수 있게 짜여 있다. `pytest-xdist`가 이미 개발 의존성에 있고(`pyproject.toml`), `tests/conftest.py`의 템플릿 데이터베이스는 작업자마다 한 번 만들며, 시험마다 무작위 이름으로 복제한 데이터베이스를 쓰므로 데이터가 부딪히지 않는다. 로컬 pre-commit의 검사 러너(`tools/run_checks.py`)는 이미 논리 CPU의 절반으로 나눠 돈다.

**뒤집는 결정.** `tools/run_checks.py`의 독스트링이 적은 "CI는 한 프로세스로 돈다. 그래서 테스트끼리 부딪혀서 나는 실패는 이 러너에서만 나고, CI의 빨강과 따로 읽는다"(agent-os ADR 0035에서 옮긴 결정)를 이 티켓이 뒤집는다. 같은 결정을 적은 `pyproject.toml`의 주석과 `tests/tools/test_run_checks.py`의 독스트링도 함께 고쳤다. 사용자가 2026-11-23에 세 길(병렬로 돌리기, 제한만 올리기, 잡 나누기) 가운데 병렬로 돌리기를 골랐고, 이어 이 결정을 뒤집는다는 것과 그 위험(아래 Comments)을 알린 뒤 세 갈래(러너처럼 CPU의 절반, CPU 전부, 옛 결정을 두고 제한만 올리기) 가운데 CPU 전부(`-n auto`)를 골랐다. ADR은 쓰지 않았다. `-n auto`를 지우면 되돌아가는 한 줄 설정이라 `domain-modeling`의 세 조건(되돌리기 어렵다, 맥락 없이는 놀랍다, 진짜 절충이다) 가운데 첫째가 빠진다. 이 결정은 이 티켓과 위 세 곳의 문장이 기록한다.

제한 시간 15분은 올리지 않는다. 나눠 돌린 시간이 나와야 값을 정할 수 있고, 제한을 먼저 올리면 느려진 것을 가린다.

## Comments

- **병합 전에 볼 것.** 나눠 돌린 시간은 이 PR의 CI에서만 알 수 있다. 이 PC에서는 CI 러너(리눅스, 공개 저장소의 표준 러너는 4 vCPU로 알려져 있으나 이 저장소에서 재지 않았다)의 CPU 수를 만들 수 없다. 이 PR의 `python` 잡 시간과 pytest 스텝 시간은 PR 본문에 적는다. 시간이 15분 안에서 줄지 않았거나 시험이 작업자 수 때문에 깨지면 이 티켓의 고침을 거두고 다른 길(작업자 수를 줄이기, 제한 올리기, 잡 나누기)을 사용자에게 다시 묻는다.
- **알고 고른 위험.** 부하에서만 지는 시험이 이미 대기열에 열려 있다(`.scratch/retro-queue/load-readtimeout-flake.md`, `load-sensitive-time-tests.md`. 전체 시험을 병렬로 돌릴 때 `ReadTimeout`과 시간 단언이 지고 홀로 돌리면 초록이었다고 적는다). CI가 병렬이 되면 이런 간헐 실패가 필수 검사 `verify`에 올라올 수 있다. `-n auto`는 PostgreSQL 서비스 컨테이너와 CPU를 나눠 쓰므로 러너의 절반만 쓰는 길보다 이 위험이 크다. 이 PR의 CI에서 그런 시험이 지면 상한을 넓히지 않고 어느 시험이 어떤 작업자 수에서 졌는지 먼저 적고, 작업자 수를 줄일지를 사용자에게 묻는다.
- **PR #107의 일지.** 병합된 일지의 "다음"과 "검증"에는 첫 시도의 14분 43초만 적혀 있고, 제한 초과로 취소된 두 시도(`a427ad8`)와 `dev` 푸시의 취소 둘은 없다. 이 티켓의 위 표가 그 기록을 대신한다.
