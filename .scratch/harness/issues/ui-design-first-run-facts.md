# ui-design-first-run-facts: 화면 그림 스킬을 이 저장소에서 처음 돌리며 본 것을 스킬에 옮긴다

**What to build:** 화면 그림 스킬(`.claude/skills/ui-design/SKILL.md`)은 agent-os에서 옮겨 온 뒤 이 저장소에서 돌려 본 적이 없었고, 끝 절 "재지 못한 것"은 처음 돌리는 세션(admin의 화면 그리기)에게 본 것과 막힌 자리를 그 절에 적으라고 했다. 그 세션(2026-11-26~27)이 본 것을 해당 단계로 옮기고, 이제 본 것을 그 절에서 지운다. admin의 화면을 옮기는 면제 PR(`docs/admin-screens`)에 함께 싣는 harness 티켓이다. 단계의 차례는 바꾸지 않는다. 끝 조건은 넷을 고친다(2의 읽는 파일 수, 7에 부품을 넣는 것, 6에서 거둔 확정을 세지 않는 것, 웹 편집 확인에서 커밋하지 않은 파일을 작업 트리와 맞대는 것). 절차에 더하는 것은 여덟이다. 5의 부품 떼기와 속성 화면, 5의 새 아티팩트 제목에 붙이는 저장소 이름, 5의 로컬 렌더 길, 6에서 확정한 화면을 고치게 할 때 메모의 확정을 거두는 것과 웹 편집 확인이 그 갈래를 작업 트리로 맞대는 것, 7의 부품 파일 표 줄과 그 줄을 화면 줄보다 먼저 쓰는 순서, 7의 셀프 리뷰가 옮긴 화면을 고치게 할 때의 길, 7의 다시 묻기에서 고침이 이어질 때 확정한 판에서 다시 받는 것, 웹 편집 확인에서 부품을 부르는 화면도 함께 보이는 것이다.

**admin에서 본 것.**
- 1(설치): 플러그인이 이미 켜져 있어 설치와 `/reload-plugins`는 돌지 않았다. 그래서 이 일만 "재지 못한 것"에 남는다.
- 2(계정): 경로 없이 읽은 디자인 시스템 아티팩트의 머리가 "owned by you"였다. 끝 조건이 "두 파일"이라 적었는데 읽는 파일은 셋이라 고친다.
- 5(그리기): 형식이 만들 때 내주는 `Main.dc.html`을 와이어프레임 쪽 아트보드로 썼다. 여러 화면이 함께 쓰는 부품 여섯을 따로 된 파일로 떼어 `dc-import`로 불렀고, 상태만 다른 화면은 속성을 둔 화면 하나를 다른 아트보드가 불러 그렸다. 이 둘을 5의 지시로 적는다.
- 5(렌더): 사람이 화면이 어긋났다며 고침을 청해, 원인을 찾으려고 스크래치패드에서 렌더했다(형식 지침은 사람이 청할 때만 렌더하라고 한다). 받은 화면 파일 곁에 형식의 고정 파일 `artifact-type/dc-runtime.js`를 `support.js`로, `project/ds/agent-os/`를 두니 내장 브라우저에서 그려졌다. 이 길을 5에 적고, "재지 못한 것"의 첫 항목을 저장소의 사본만으로 그려지는지로 좁힌다. 어긋남의 원인 하나는 그림이 디자인 시스템 README의 유틸리티 목록 밖 클래스 넷(`gap-6`, `grid`, `items-end`, `justify-end`)을 써 그 자리의 간격과 정렬이 빠진 것이었다. 사람이 고친 실수라 스킬에는 적지 않고, 자동 검사 후보로 회고에 넘긴다(`CLAUDE.md` 교정 루프).
- 5(아티팩트 찾기): 같은 계정의 Design 목록에 agent-os의 아티팩트(`portal-admin 화면 · screens-prompt.md`, `widget-login-state 화면 · settings-additions-prompt.md`)가 이 스킬과 같은 제목 꼴로 있었다. 이 저장소의 기능이 같은 slug와 프롬프트 파일 이름을 쓰면 제목으로 찾는 길이 남의 아티팩트를 잡으므로, 새 아티팩트의 제목 앞에 `rag-engine`을 붙인다(셀프 리뷰 명세 축이 냈다). admin의 아티팩트는 이 규칙 전에 만들어 시작 프롬프트의 `아티팩트:` 줄로 찾는다.
- 7(옮기기): 경로 56개를 받았고, 받은 파일은 스크래치패드의 `artifact-files\<아티팩트 id>\project\` 아래에 놓였다. 옮긴 56개가 받은 결과의 sha256과 모두 같았고(`sha256sum -c`로 손으로 봤다) CR이 든 파일이 없었다. 색인 `canvas.json`의 `boards`는 키가 파일 이름이고 값의 `page`가 쪽이었다.
- 7(표 채우기): 부품 파일에도 표 줄을 두었다. 웹 편집 확인이 표의 줄마다 맞대므로, 줄이 없으면 사람이 웹에서 부품을 고친 것을 놓친다. 이것을 스킬의 표 채우기에 적는다. `next-session` 결정표는 그릴 화면의 줄만 보므로, 부품 줄을 화면 줄보다 먼저 쓰게 하고 7의 끝 조건에 부품을 넣는다(셀프 리뷰 표준 축이 끊긴 갈래를 밟아 냈다).
- 7(커밋 전 셀프 리뷰): 셀프 리뷰가 옮긴 화면의 그림 셋(복구 중인 원천, "도는 중" 문구, 취소 창의 단추)을 고치게 했다. `design/`의 사본이 아니라 아티팩트를 고쳐 다시 받았고(넷의 sha256이 받은 결과 머리와 같았다, `sha256sum -c`로 손으로 봤다), 고친 화면을 다시 확정할지 사람에게 물었다. 사람은 고침을 두 번 요청한 뒤(열 가지와 "좀 더 예쁘게", 그다음 셋) 그 둘을 반영한 판을 확정했고, 그 판에서 56개를 모두 다시 받아 옮겼다(sha256이 받은 결과 머리와 모두 같았다, `sha256sum -c`로 손으로 봤다). 이 길과 다시 묻기에서 고침이 이어지는 길을 7에 적는다.
- 6(확정한 화면의 고침): 확정한 뒤 고침이 이어지는 도중에 끊기면, 새 세션은 README 줄이 다 있어 웹 편집 확인으로 가고 HEAD에 파일이 없어 알리기로 끝나며, 5도 메모의 옛 확정을 믿어 옛 사본이 커밋된다(두 번째 셀프 리뷰 표준 축이 끊긴 갈래를 밟아 냈다. admin에서 끊기지는 않았다). 확정한 화면을 고치게 하면 고치기 전에 메모의 확정을 거두며 사람이 청한 고침도 함께 적고(고치기 전에 끊기면 청한 고침을 잃는다고 명세 축이 냈다), 웹 편집 확인은 옮긴 뒤 커밋하지 않은 파일을 작업 트리와 맞대 6이나 7로 보내게 적는다.
- 웹 편집 확인: 부품 파일을 고치면 그 부품을 `dc-import`로 부르는 화면은 제 파일이 그대로라 sha256으로는 같다고 나온다. 바뀐 부품과 함께 부르는 화면도 사람에게 보이게 적는다(셀프 리뷰 명세 축이 냈다).

**이번에 바꾸지 않는 것.** "재지 못한 것"의 나머지 셋(옮긴 화면이 저장소의 사본만으로 그려지는지, 웹에서 고친 파일의 줄바꿈, 테마 메뉴)은 admin에서도 보지 못해 그대로 둔다.
