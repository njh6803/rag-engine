# crlf-from-script-edits: 스크래치 파이썬의 `write_text`와 stdout 리다이렉트가 Windows에서 저장소 파일 아홉을 CRLF로 바꿨고 `check_line_separators`는 설계상 CRLF를 보지 않는다

**상태:** 열림
**어디로:** `tools/check_line_separators.py`(`.gitattributes`가 `* text=auto eol=lf`인 저장소에서 CRLF를 어긋남으로 낸다. 독스트링이 CRLF를 보지 않는다고 적은 설계를 바꾸는 것이라 못 보는 것과 `tests/tools/`의 시험을 같이 고친다) 또는 `CLAUDE.md` 환경 함정 한 줄(저장소 파일을 스크립트로 쓸 때 `newline` 인자를 LF로 주거나 바이트로 쓴다. 검사 층이 더 높다)
**승인:** 자체 승인 2026-11-10, 9회차(더하는 것이라 다섯 번째에 반영한다. 5회차에 이르러 chore 배치 조건이다), 일지 2026-11-10-0118-core-spec.md, 2026-11-11-0615-core-07-first-search-round-trip.md, 2026-11-11-0929-core-get-document-text-window.md(3회차: 명세 치환 스크립트의 `write_text`가 `.scratch/core/spec.md`를 CRLF로 바꿨고 회고의 `git ls-files --eol`로야 보았다), 2026-11-11-1328-core-08-parsers-isolation.md(4회차: `tests/adapters/test_zip_guard.py`가 CRLF였고 `git add` 경고로야 알았다), 2026-11-14-1723-search-eval-05-full-run-rerank.md(5회차: 티켓 05를 고치는 `Path.write_text`가 파일을 CRLF로 바꿔 뒤이은 `git diff`의 `CRLF will be replaced by LF` 경고로야 알았다), 2026-11-14-1917-search-eval-06-miss-causes-and-breakdowns.md(6회차: 스크립트로 쓴 시험 파일 넷이 CRLF가 되어 `sed -i 's/\r$//'`로 되돌렸다), 2026-11-16-1341-search-eval-18-min-score-distribution.md(7회차: 티켓 18과 프로브 출력 `no_answer_scores_out.txt`가 `write_text`와 Windows 리다이렉트로 CRLF 74줄이 되어 셀프 리뷰가 잡았고 바이트 치환으로 LF로 되돌렸다), 2026-11-17-1033-search-eval-17-reranker-on-off.md(8회차: 프로브 출력 셋(`compare_with_baseline_out.txt`, `rerank_latency_gpu_out.txt`, `summary.md`)이 Windows 리다이렉트로 CRLF가 되어 `git add`의 `CRLF will be replaced by LF` 경고로야 알았고 `sed -i 's/\r$//'`로 되돌렸다), 2026-11-18-1634-release-image-spec.md(9회차), 2026-11-18-2135-release-image-tickets.md(10회차), 2026-11-20-0133-release-image-03-standalone-compose-behind-proxy.md(11회차: 새로 만든 시험 파일이 작업 사본에서 922줄 모두 CRLF였고 `git add`의 `CRLF will be replaced by LF` 경고로야 알았다. 쓴 도구는 가리지 못했다), ADR 불필요

명세 세션이 Bash heredoc의 `uv run python`으로 명세·일지·README·프로브를 고치며 `pathlib.Path.write_text`를 썼고 프로브 출력은 `>`로 받았다. Windows의 텍스트 모드가 LF를 CRLF로 바꿔 아홉 파일이 CRLF가 됐고, 손으로 친 `check_line_separators`는 0이었으며 `git add`의 `CRLF will be replaced by LF` 경고로야 알았다. 바이트 치환으로 LF로 되돌렸다. 커밋은 git이 정규화해 손상은 없었다.

같은 파일에서 날것 C0 제어 문자(BEL 등)를 막는 일은 `control-char-from-script-escape`가 센다. 반영할 때 한 chore로 묶는다.

11회차는 release-image 03 구현 세션이다. 새로 만든 `tests/standalone/test_standalone_compose.py`의 작업 사본이 922줄 모두 CRLF였고(인덱스는 LF), 커밋하려 `git add`를 칠 때 나온 경고로야 알았다. 같은 세션에서 만든 `deploy/standalone/compose.yaml`은 LF였다. 이 파일에 쓴 `tools/rewrap_comments.py`는 줄마다 `\r` 여부를 따로 적어 두고 `write_bytes`로 쓰므로(458~460행과 528행을 읽었다) 줄 끝을 새로 만들지 않는 것으로 읽었다. 코드를 읽어 본 것이고 돌려 본 것은 아니다. 어느 단계가 CRLF를 만들었는지는 가리지 못했다. 앞의 회차는 스크래치 스크립트의 `write_text`와 리다이렉트가 원인이었으나 이번은 원인을 모르므로, 처방은 쓴 도구와 관계없이 작업 사본의 CRLF를 알리는 검사(`tools/check_line_separators.py`)가 맞다. 손상은 없다(커밋은 git이 LF로 정규화했다). `sed -i s/\r$//`로 되돌렸다.
