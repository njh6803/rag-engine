# commit-msg-after-slow-checks: 커밋 메시지 타입 검사가 8분 걸리는 검사 러너 뒤에 돌아, 허용되지 않은 타입이 8분을 쓰고서야 막힌다

**상태:** 닫힘 (.scratch/harness/issues/commit-title-check-before-slow-checks.md, 2026-11-25, `hook_bash_commit_msg`가 `-m`, `cd`·`pushd` 뒤의 커밋, `-F -` heredoc, `-m "$(cat <<'EOF' …)"`까지 보고 같은 판정 스크립트로 제목을 먼저 대 본다. `echo … |`처럼 다른 명령이 만든 메시지와 변수·치환이 든 `-m` 값은 훅의 못 보는 것에 남았다)
**어디로:** `tools/` 의 PreToolUse 훅 하나(`git commit -m`의 제목 타입을 `tools/check_commit_msg.py`로 먼저 본다. 판정은 같은 모듈을 부른다)
**승인:** 자체 승인 2026-11-12, 7회차(더하는 것이라 다섯 번째에 반영한다), 일지 2026-11-12-1833-dev-review-bot-off.md, 2026-11-13-1324-code-review-transition-crossing.md, 2026-11-14-1438-search-eval-04-fast-run-report.md가 3회차다(제목이 80자로 72자 제한을 넘어 `pytest` 468초를 돈 뒤에야 막혔다. 명령은 `git commit -F <메시지 파일>`이었고 `hook_bash_commit_msg`가 있는데도 먼저 막지 못했다. 명령이 `cd <워크트리> &&`로 시작하는 복합 명령이었고 세션의 작업 폴더가 연결된 워크트리였다. 훅이 왜 지나갔는지는 진단하지 않았다), 2026-11-17-0304-search-eval-20-min-score-argument.md가 4회차다(제목이 75자로 72자 제한을 넘어 `parallel-checks`를 약 10분 돈 뒤에야 `commit-msg`가 막았고 50자로 줄여 한 번 더 약 10분을 돌았다. 이번 명령은 `git commit -m`이었다. `hook_bash_commit_msg`는 `-F <파일>`만 판정하고 `-m`의 메시지는 독스트링의 "못 보는 것"에 이미 적혀 있어, 이번에 훅이 지나간 것은 훅의 버그가 아니라 설계된 사각이다. 3회차의 지나감은 `cd`가 앞선 명령이면 보지 않는다는 독스트링의 다른 사각으로 설명된다. 두 사각 모두 이 항목이 처방하는 `-m`·`cd` 복합 명령까지 보는 앞당긴 판정이 따로 필요하다는 근거다), 2026-11-18-1817-glossary-harness-small-names.md가 5회차다(제목이 73자로 72자 제한을 넘어 `parallel-checks`를 약 6.5분 돈 뒤에야 `commit-msg`가 막았다. 명령은 `git commit -m`이라 4회차와 같은 설계된 사각이다. 막힌 뒤 제목을 줄이지 않고 같은 제목으로 한 번 더 커밋을 띄워 중간에 멈췄다), 2026-11-19-0202-glossary-constitution-version-names.md가 6회차다(제목이 79자로 72자 제한을 넘어 `parallel-checks`를 434초 돈 뒤에야 `commit-msg`가 막았다. 명령은 `git commit -m`이라 4·5회차와 같은 설계된 사각이다), 2026-11-19-2318-glossary-contract-version-review-bot.md가 7회차다(앞 PR 78의 일지 커밋 제목이 75자로 72자 제한을 넘어 `parallel-checks`를 약 617초 돈 뒤에야 `commit-msg`가 막았다. 명령은 `git commit -m`이라 같은 설계된 사각이다), 2026-11-20-2034-source-sync-design.md가 8회차다(제목이 76자로 72자 제한을 넘었다. 명령은 메시지를 표준 입력으로 넘기는 `git commit -F -`였고, `hook_bash_commit_msg`의 독스트링이 못 보는 것에 적은 또 하나의 설계된 사각이다. pre-commit의 pytest가 1291.93초 뒤 다른 까닭으로 실패해 `commit-msg` 단계에는 닿지 않았고, 기다리는 동안 `tools/check_commit_msg.py`를 손으로 돌려 찾았다), 2026-11-21-1404-implement-journal-before-review.md가 9회차다(제목이 96자, 이어 73자로 72자 제한을 넘어 `parallel-checks`를 각각 약 15분(915.8초, 1033초) 돈 뒤에야 `commit-msg`가 막았다. 명령은 `git commit -m`이라 4~7회차와 같은 설계된 사각이다), ADR 불필요

`ci:` 타입으로 커밋했더니 pre-commit의 `parallel-checks`가 480초를 돈 뒤에야 `commit-msg` 훅(`.pre-commit-config.yaml`의 `commit-msg` 단계)이 "타입은 feat, fix, docs, style, refactor, test, chore, perf"라며 막았다. `commit-msg` 단계는 `pre-commit` 단계 뒤에 도는 것이 pre-commit의 순서라 훅 설정만으로 앞당길 수 없다. 메시지는 `-m`에 이미 있어 명령을 칠 때 값싸게 볼 수 있다.
