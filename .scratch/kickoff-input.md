# rag-engine 계획 (제안)

상태: 제안. 2026-11-05 작성, 2026-11-06 저장소 이름과 행 이름을 고치고 수집 파이프라인과 원천, 동기화, 관리자 페이지 메뉴 초안을 더하고, 공개 시연에 맞춰 release-image를 core 바로 뒤로 당김. 저장소 `rag-engine`은 아직 만들지 않았다. 이 문서는 agent-os의 킥오프 런북(`KICKOFF.md`)으로 새 저장소를 시작할 때의 입력이다. 킥오프의 어느 단계에서 이 문서의 어느 절을 쓰는지는 바로 아래 절에 있다. 경계는 agent-os의 ADR 0048(`docs/adr/0048-document-search-server-lives-in-another-repository.md`, accepted)이 정한다. 이 저장소의 날짜는 9절 PRD 초안의 성공의 정의에 있다.

rag-engine은 MCP를 쓰는 어떤 클라이언트에서도 쓸 수 있는 독립된 설치형 문서 검색 서버(지식베이스)다. 여러 원천에서 문서를 수집하고 색인해서 검색까지 맡고, 답을 생성하지는 않는다. agent-os의 참조 에이전트 doc-qa가 이 서버를 쓰지만, 그 사실은 agent-os 쪽만 안다. 이 저장소의 코드와 계획은 agent-os의 코드나 행에 기대지 않는다.

## 킥오프에서 이 문서를 쓰는 법

새 저장소는 agent-os 저장소의 킥오프 런북(`KICKOFF.md`와 `kickoff/`)으로 시작한다. 킥오프가 저장소, 스킬, `CLAUDE.md`, 이슈 트래커, PRD와 헌법, 골격과 검증 명령, 첫 PR까지 만든다. 그래서 저장소의 뼈대를 따로 만드는 행은 두지 않고, 이 문서는 각 단계에 넣을 입력이 된다.

| 킥오프 단계 | 이 문서에서 쓰는 곳 | 정하는 것 |
|---|---|---|
| 준비 | 아래 "준비의 답" | 무엇을 만드나, 주인과 이름, 공개 여부 |
| 1단계 | 없음 | 워크트리를 쓸지(agent-os는 쓴다) |
| 4단계 | 6절의 행 표 | 이슈 트래커(agent-os와 같은 로컬 마크다운)와 `.scratch/plan.md` 첫 판. 첫 판의 행은 6절의 표다 |
| 5단계 | 9절(PRD 초안), 10절(헌법 인터뷰의 입력), 2~4절 | `docs/PRD.md`, 헌법 세 파일, 첫 ADR |
| 7단계 | 10절의 "스캐폴딩의 종료 조건" | 골격과 검증 명령 |
| 9단계(킥오프 뒤 첫 기능) | 6절의 core | core의 설계 인터뷰부터 |
| 킥오프 뒤 | 4, 5, 7, 8절 | 각 행의 설계 인터뷰 입력. 저장소 안에서 어디에 둘지는 그 저장소의 문서 위치 규약대로 정한다 |

### 준비의 답

- **무엇을 만드나:** MCP를 쓰는 어떤 클라이언트에서도 쓸 수 있는 설치형 문서 검색 서버(지식베이스)다. 여러 원천에서 문서를 수집하고 색인해서, 근거 위치와 갱신일이 붙은 검색 결과를 MCP 읽기 도구로 돌려준다.
- **주인과 이름:** `njh6803`, `rag-engine`.
- **공개 여부:** 공개. agent-os와 같은 공개 저장소로 둔다.

## 1. 맡는 것과 아는 것

- **맡는 것:** 원천에서의 문서 수집과 동기화, 파싱, 청킹, 임베딩, 색인, 검색, 관리 API(REST), 관리자 페이지. 그리고 자기 이미지와 단독 설치, 색인과 원본 문서의 백업과 판 올림, 진단, 검색 평가.
- **여는 통로:** 클라이언트에게는 MCP(Streamable HTTP)의 읽기 도구를 열고, 문서 담당자에게는 관리 API와 관리자 페이지를 연다. 다른 시스템에게는 수집 API를 연다. MCP는 통로 가운데 하나이고, 이 서버의 정체가 아니다.
- **아는 것:** MCP 표준과, MCP `_meta`에 실린 주체의 범용 형식.
- **내는 것:** 판을 붙인 컨테이너 이미지, 판을 붙인 검색 도구의 형식, 판을 붙인 수집 API와 커넥터 인터페이스.
- **모르는 것:** 어떤 클라이언트가 이 서버를 쓰는지, 답을 어떻게 만드는지.

## 2. 계약: 검색 도구의 형식

클라이언트는 이 형식에 기댄다. 칸을 더하는 것은 같은 판에서 하고, 칸을 지우거나 뜻을 바꾸면 판을 올린다. 이 저장소에는 MCP 클라이언트로 접속해 이 형식을 확인하는 계약 시험을 둔다. 형식의 원천은 이 저장소의 계약 문서이고, agent-os의 ADR 0048에 적힌 형식은 그 출발점(v1)이다.

| 쪽 | 칸 | 뜻 |
|---|---|---|
| 입력 | 질문 | 검색할 글 |
| 입력 | 개수 | 돌려줄 조각의 수 |
| 입력 | 필터 | 문서 묶음, 기간 같은 조건(선택) |
| 출력 | 조각 | 질문에 맞는 문서의 일부 |
| 출력 | 문서 경로, 쪽, 위치 | 답에 출처로 적을 근거 위치 |
| 출력 | 갱신일 | 문서의 갱신일. 클라이언트가 답의 출처에 함께 적는다 |
| 출력 | 점수 | 검색 점수 |

조각에는 갱신일 말고도 시행일과 접근 그룹을 담을 칸을 처음부터 둔다. 기준선에서는 갱신일만 출력하고 나머지는 채우기만 하지만, doc-permission과 doc-freshness가 쓴다. 색인 형식을 나중에 바꾸면 설치된 문서를 모두 다시 색인해야 하기 때문이다. doc-freshness는 출력에 "오래됨" 칸을 더한다(같은 판 안의 칸 추가).

## 3. 데이터베이스

이 절은 rag-engine이 자기 데이터를 담는 데이터베이스다. 문서를 가져오는 원천으로서의 데이터베이스는 4절에서 다룬다.

- 이 서버는 자기 데이터베이스를 쓰고, 연결 문자열 하나만 받는다. 다른 서비스의 데이터베이스를 읽지 않고, 마이그레이션은 이 저장소가 한다.
- 단독 compose는 자기 PostgreSQL을 함께 띄운다. 설치 환경에 이미 PostgreSQL이 있으면 연결 문자열만 바꿔 그쪽에 붙인다.
- 벡터 저장소로 pgvector를 고르면 이 데이터베이스에 확장을 설치한다. 별도 벡터 DB를 고를지는 core의 설계 인터뷰가 정한다.

## 4. 수집 파이프라인과 커넥터

### 파이프라인

수집은 원천마다 같은 순서를 따른다: 원천(커넥터) → 변환(선택) → 파싱 → 청킹 → 색인. 원천마다 설정 파일로 각 단계를 정하고, 플러그인을 끼우는 자리는 커넥터, 변환, 파서 셋이다. 세 자리의 인터페이스에는 판을 붙인다. 원천이 설치 환경마다 다르고 계속 늘어나므로, 제품은 범용 단계와 인터페이스를 내고 설치 환경마다 다른 것은 플러그인이 맡는다.

### 원천의 틀

모든 수집 경로를 "원천" 하나의 틀로 다룬다. 원천은 종류(커넥터), 연결 정보, 범위, 실행 일정, 접근 그룹의 기본값, 변환 단계를 가진다. 원천에서 가져온 문서는 원천 안에서 바뀌지 않는 ID(파일 경로, 기본 키)와 내용 해시로 식별한다.

### 커넥터

커넥터 인터페이스는 목록 가져오기, 바뀐 것 가져오기, 문서 하나 읽기, 원천의 ID 목록 내기로 이루어진다.

| 커넥터 | 방식 | 판 |
|---|---|---|
| 업로드 | 관리자 페이지에서 사람이 넣는다 | 0.1, 내장 |
| 서버 경로 | 서버에 마운트한 폴더(NFS, SMB 공유 포함)를 주기적으로 가져온다 | 0.1, 내장 |
| 수집 API | 다른 시스템이 문서를 보낸다(넣기, 고치기, 지우기) | 0.1, 내장 |
| SQL | 데이터베이스에 든 글을 질의로 가져온다 | 1.0(db-source), 내장 |
| 객체 저장소(S3 호환) | 주기적으로 가져온다 | 요구가 생기면 |
| 사내 시스템(위키, 문서관리시스템, 그룹웨어 등) | 가져오고, 권한도 함께 가져온다 | 요구가 생기면 시스템마다 하나씩 |

수집 API는 마지막 통로다. 커넥터가 없는 원천이라도, 설치 환경이 그 원천에서 문서를 꺼내 수집 API로 보내는 작은 스크립트를 쓰면 붙일 수 있다. 그래서 커넥터를 미리 많이 만들지 않는다.

### 변환 플러그인

변환 플러그인은 커넥터가 읽은 것(행 하나, 파일 하나)을 받아 문서들을 돌려주는 코드다. 설치 환경마다 다른 규칙을 맡는다. 예를 들면 본문에 섞인 HTML이나 서식의 정리, 문서관리시스템의 API로만 내려받을 수 있는 첨부, 암호화되어 저장된 첨부의 복호화, 행 하나를 여러 문서로 나누기다.

- 변환 플러그인은 제품 저장소가 아니라 설치처의 비공개 저장소에 둔다. 제품은 인터페이스와 예시 하나만 낸다. 그래야 설치처의 정보가 공개 저장소에 들어가지 않고, 제품은 범용으로 남는다.
- 지금 두는 자리는 문서 단계(파싱 전) 하나다. 조각 단계에서 조각마다 메타데이터나 요약을 보강하는 자리는 필요해질 때 더한다.

### SQL 커넥터: 세 층

DBMS마다, 또는 설치처마다 SQL 커넥터를 새로 만들지 않는다. 데이터베이스의 차이를 세 층으로 나눠 흡수하고, 코드로 만드는 것은 셋째 층만이다.

| 층 | 흡수하는 것 | 어떻게 |
|---|---|---|
| 1. 드라이버 | DBMS의 차이 | 연결 문자열과 드라이버 파일 |
| 2. 질의와 매핑 | 여러 표의 조합, 코드표 변환, 조건, 여러 본문 칼럼, 여러 메타데이터 칼럼, 첨부 칼럼 | 운영자가 쓰는 SELECT와 매핑 설정 |
| 3. 변환 플러그인 | 질의와 설정으로 안 되는 설치처별 규칙 | 코드(위의 변환 플러그인) |

운영자가 질의를 직접 쓰므로, 표 조합(JOIN), 코드표 변환, 칼럼 합치기, "게시 상태인 글만" 같은 조건은 대부분 SQL 안에서 끝난다. 표가 크거나 질의가 무거우면 설치 환경이 수집 전용 뷰나 표를 만든다. 매핑 설정은 질의 결과의 칼럼을 문서의 어느 자리에 넣을지만 정한다.

- **ID:** 칼럼 하나, 또는 여러 칼럼을 이어 붙인 복합 키다. ID가 없으면 고친 행이 새 문서가 되므로 반드시 정한다.
- **본문:** 여러 칼럼을 템플릿으로 합친다(예: "제목: {title}" 다음 줄에 "{body}").
- **메타데이터:** 칼럼마다 이름과 형식(문자, 숫자, 날짜)을 준다. 검색 필터와 doc-freshness, doc-permission이 이 값을 쓴다.
- **증분의 기준:** 단조 증가하는 칼럼(rowversion, 시퀀스)이 가장 안전하다. 갱신 시각 칼럼을 쓰면 같은 시각에 바뀐 행이나 늦게 커밋된 행을 놓치지 않도록, 앞 실행과 겹치는 구간을 두고 읽는다. 기준 칼럼이 없으면 매번 전체를 읽는다.
- **삭제:** 삭제 표시 칼럼을 쓰거나, 정리 작업으로 원천의 ID 목록과 대조한다. 큰 표는 대조를 매 실행마다 하지 않고 따로 정한 주기로 한다.
- **첨부:** 첨부 칼럼마다 종류를 정한다.

  | 첨부 칼럼에 든 것 | 가져오는 방법 | 맡는 층 |
  |---|---|---|
  | 파일 경로(공유 폴더) | 서버 경로 커넥터와 같은 읽기로 가져온다(폴더를 마운트) | 매핑 설정 |
  | URL(사내 시스템) | 인증 정보를 붙여 HTTP로 내려받는다 | 매핑 설정 |
  | BLOB(파일 자체가 DB에 있음) | 드라이버로 읽는다 | 매핑 설정 |
  | 다른 표의 ID(1:N 첨부) | 첨부 표를 읽는 자식 질의를 하나 더 둔다 | 매핑 설정 |
  | 문서관리시스템의 ID | 그 시스템의 API로 내려받는다 | 변환 플러그인 |

  첨부는 행의 자식 문서로 둔다. 첨부는 행의 메타데이터와 접근 그룹을 물려받고, 행이 지워지면 함께 지운다. 행은 그대로인데 첨부만 바뀌는 경우를 잡도록 첨부에도 갱신 시각이나 해시를 따로 둔다.

### DBMS와 드라이버

- 흔한 DBMS(PostgreSQL, MySQL과 MariaDB, MS SQL Server, Oracle)의 드라이버는 미리 확인해 둔다. 드라이버 라이브러리가 기본으로 지원하지 않는 DBMS(Tibero, CUBRID 등)는 ODBC로 붙이는 길을 확인한다.
- 라이선스상 이미지에 넣을 수 없는 드라이버는 설치 환경이 파일로 넣는다(볼륨으로 마운트). 드라이버마다 재배포 조건을 확인해 설치 안내에 적는다.
- 문서로 다루기 어려운 저장소(문서형 DB, 검색 엔진 등)는 SQL 커넥터로 무리하게 붙이지 않고, 필요하면 커넥터 플러그인을 따로 만든다.

### 구조화 데이터는 넣지 않는다

매출이나 재고처럼 숫자가 자주 바뀌고 합계가 필요한 데이터를 조각으로 잘라 색인하면, 낡은 숫자로 답하거나 합계를 틀린다. SQL 커넥터는 데이터베이스에 든 글(공지, FAQ, 게시판, 규정 본문 등)에 한정한다. 구조화 데이터는 클라이언트 쪽의 Text-to-SQL(질문을 SQL로 바꿔 읽기 전용으로 실행하는 도구. MCP 서버 등)로 다루고, 이 서버의 범위에 넣지 않는다.

### 동기화의 규칙

- **실행:** 지금 동기화(수동), 주기 실행(cron), 수집 API의 즉시 반영의 세 가지다.
- **증분과 전체:** 평소에는 바뀐 것만 가져온다. 파일은 수정 시각과 내용 해시로, SQL은 갱신 시각 칼럼으로 가린다. 전체 재색인은 청킹이나 임베딩 설정을 바꿨을 때만 따로 돌린다.
- **삭제 반영:** 원천에 더는 없는 문서를 색인에서 지우는 정리 작업을 처음부터 둔다. 원천의 ID 목록과 색인의 목록을 대조하고, SQL은 삭제 표시 칼럼도 쓸 수 있다. 정리가 없으면 지운 문서가 계속 검색되어 낡은 답이 나오고, 권한이 바뀐 문서라면 유출이 된다.
- **겹침 방지:** 같은 원천의 작업은 한 번에 하나만 돈다. 수집 API로 넣은 문서와 주기 동기화가 같은 문서를 서로 덮어쓰지 않게, 문서마다 어느 원천의 것인지 하나로 정한다.
- **시간대와 부하:** 수집은 임베딩 때문에 GPU나 CPU를 쓰고 원천에도 부하를 준다. 원천마다 실행 시간대(예: 야간)와 동시 처리 수를 정한다.
- **실패:** 재시도와 대기 시간을 두고, 원천마다 마지막 실행, 다음 실행, 가져온 수, 건너뛴 수, 실패 사유를 작업 기록으로 남긴다.
- **수집 정책:** 지원 형식, 크기 상한, 제외할 경로와 패턴(임시 파일, 개인 폴더 등)을 원천마다 정한다. 암호가 걸린 파일과 스캔본은 실패가 아니라 "건너뜀"으로 표시한다.
- **연결 정보:** 데이터베이스 비밀번호와 API 토큰은 암호화해서 저장하고, 저장한 뒤에는 다시 보여 주지 않는다. 진단 묶음과 로그에도 싣지 않는다.
- **메타데이터:** 제목, 작성 부서, 갱신일, 시행일을 원천의 어떤 값에서 가져올지 커넥터마다 정한다. doc-freshness와 doc-permission이 이 값을 쓴다.

| 현황 | 첫 화면. 문서 수, 조각 수, 수집 대기와 실패 건수, 원천마다의 마지막 동기화, 색인 판, 최근 검색 지연 |
| 원천 | 원천 목록, 종류, 일정, 마지막 실행과 다음 실행, 지금 동기화, 작업 기록(가져온 수, 건너뛴 수, 실패 사유), 실패한 작업의 재시도 |

### 넣지 않을 것

- 답 생성 설정(프롬프트, LLM 모델): 클라이언트(agent-os의 doc-qa 등)가 맡는다.
- 대화 기록, 질문 기록, 답에 대한 오류 신고: 클라이언트가 맡는다. 운영자는 클라이언트 쪽에서 신고된 답과 인용 문서를 보고, 문서는 이 관리자 페이지에서 고친다.
- 검색된 질문의 내용: 질문에는 민감한 내용이 들어갈 수 있으므로 이 서버는 질문 내용을 남기지 않고 지연 시간만 남긴다.

## 6. 행

`plan.md` 표의 열(슬라이스, 기능, 내용, Blocked by, Status)에 맞췄다. 킥오프 4단계가 이 표로 `.scratch/plan.md` 첫 판을 만들고, 킥오프 뒤의 첫 기능은 core다.

core 다음은 release-image와 search-eval이다. 판을 고정한 이미지가 있어야 클라이언트가 실제 서버로 시험할 수 있고, 공개 문서 묶음을 넣은 공개 시연을 동기화와 관리자 페이지보다 먼저 열 수 있기 때문이다. 공개 시연은 관리 명령으로 문서를 한 번 넣고 동기화를 쓰지 않으므로, core, search-eval, release-image 셋이면 된다. 그래서 source-sync는 release-image 뒤에 서고, 뒤에 오는 행은 release-image가 정한 판 태그와 단독 compose의 규칙으로 자기 몫(source-sync는 원천 폴더의 볼륨, admin은 관리자 페이지의 이미지)을 더한다. backup-upgrade와 diag-bundle은 원천 설정과 동기화 기록을 다루므로 source-sync 뒤에 선다.

| 2 | diag-bundle | 진단 묶음 명령. 판, 색인 상태(문서 수, 조각 수), 원천마다의 마지막 동기화와 실패, 최근 검색 지연을 한 파일로 묶는다. 원본 문서의 내용, 연결 정보, 비밀 값은 싣지 않는다. 수락: 일부러 깨뜨린 설치(데이터베이스 꺼짐, 색인 없음, 임베딩 모델 파일 없음, 원천 폴더 없음)에서 묶음만 보고 원인을 가를 수 있다 | source-sync | todo |
| 3 | hwp-binary | HWP 5.0 바이너리 파싱(표 포함). 국내 기관 문서에는 HWPX가 아닌 옛 바이너리 형식이 여전히 많다. 상용 파서를 연동하거나 오픈소스 파서를 쓰되, 설치형 재배포 라이선스를 먼저 확인한다. 표의 구조(행과 열)를 조각에 어떻게 담을지도 함께 정한다. 수락: 표가 든 HWP 5.0 표본 문서를 수집하면 본문과 표의 칸이 검색에 나오고, 쪽과 위치가 근거로 실린다 | admin | todo |
| 3 | doc-permission | 문서 묶음별 접근 그룹으로 검색을 거른다. 실행의 주체는 MCP 요청의 `_meta`로 받는다. 그 형식은 MCP의 `_meta`에 주체를 싣는 범용 형식이고, 이 서버의 계약 문서에 적는다. 주체에서 그룹을 찾는 길(요청에 그룹이 실려 오는지, 이 서버의 사용자와 그룹 표인지)은 설계 인터뷰가 정한다. 문서의 접근 그룹을 어디서 정할지도 같은 인터뷰가 고른다: 모두 공개, 관리자가 묶음이나 원천에 지정, 원천의 권한(공유 폴더의 ACL 등)을 가져오기다. 원천의 권한을 가져오면 원천에서 권한이 바뀐 뒤 반영되기까지 시간차가 생기므로, 그 반영 주기도 정한다. 검색 결과의 조각에는 접근 그룹 칸이 실리므로, 클라이언트도 같은 권한을 답과 기록에 쓸 수 있다. 주체가 오지 않은 요청은 거부한다(기본은 닫힘). 시험은 `_meta`에 주체를 실어 보내는 시험용 MCP 클라이언트로 한다. 수락: 그룹이 다른 주체 둘이 같은 질문을 하면 각자 볼 수 있는 문서의 조각만 나오고, 주체가 없는 요청은 거부되는 계약 시험이 통과한다 | admin | todo |
| 3 | doc-freshness | 문서의 최신성. 관리자 페이지에서 문서의 갱신일과 시행일을 보고 고치며, 운영자가 정한 기한보다 오래된 문서를 목록으로 보여 준다. 검색 결과의 조각에 "오래됨" 칸을 더해, 클라이언트가 답에 경고를 붙일 수 있게 한다. 답에 대한 오류 신고는 이 서버가 받지 않는다. 신고는 클라이언트의 일이고, 운영자는 신고된 답이 인용한 문서를 이 관리자 페이지에서 고친다. 수락: 기한이 지난 표본 문서가 목록에 나오고, 그 문서의 조각이 검색 결과에서 오래됨으로 표시된다 | admin | todo |
| 3 | db-source | SQL 커넥터. 4절의 "SQL 커넥터: 세 층"대로 짓는다. 연결 문자열로 드라이버를 고르고, 운영자가 적은 질의와 매핑 설정(ID, 본문 템플릿, 메타데이터 칼럼과 형식, 증분의 기준, 삭제, 첨부 칼럼과 자식 질의)으로 데이터베이스에 든 글과 그 첨부를 문서로 가져온다. 원천에는 읽기 전용 계정으로 붙는다. 변환 플러그인의 예시 하나(본문의 HTML 정리)를 함께 낸다. 재배포할 수 없는 드라이버는 설치 환경이 볼륨으로 넣는 절차를 안내에 적는다. 관리자 페이지에 질의 결과 몇 행이 어떤 문서와 첨부가 되는지 미리 보는 화면을 둔다. 구조화 데이터는 이 커넥터로 가져오지 않는다(4절). 수락: 본문 칼럼 여럿, 메타데이터 칼럼 여럿, 1:N 첨부 표(첨부는 파일 경로)를 가진 표본 게시판을 PostgreSQL과 다른 DBMS 하나에서 원천으로 수집하고, 행과 첨부를 더하고 고치고 지우면 다음 실행 뒤 검색 결과가 따라 바뀌며, 변환 플러그인 예시를 켜면 본문의 HTML이 정리된 채 색인된다 | source-sync | todo |
| 3 | change-log | 관리 변경 기록. 누가 언제 문서를 올리고 지웠는지, 원천과 설정과 접근 그룹을 바꿨는지 남기고, 관리자 페이지에서 조회하고 파일로 내보낸다. 질문 내용과 연결 정보는 남기지 않는다. 수락: 문서 업로드, 삭제, 원천 변경이 누가 언제 했는지와 함께 기록에 나오고, 내보낸 파일을 다시 읽으면 같은 기록이 나온다 | admin | todo |

## 7. 설계 인터뷰에서 먼저 볼 기술 위험

1. **상주 서버의 동시성과 수집 작업자.** 한 서버가 여러 요청을 동시에 받는다. 수집 도중에 들어오는 검색을 어떻게 다룰지(새 색인을 다 만든 뒤 한 번에 바꾸는 방식 등)와, 대량 수집 중에도 검색이 느려지지 않게 수집 작업자를 어떻게 나눌지를 먼저 정한다.
2. **삭제 반영의 누락.** 정리 작업을 나중에 넣으면 그 전에 원천에서 지운 문서가 색인에 계속 남는다. 그래서 source-sync의 첫 판부터 정리 작업을 둔다.
3. **문서 파서의 품질과 라이선스.** 국내 문서는 HWP, HWPX, 표가 많은 PDF가 흔하고, 파싱 품질이 답변 품질을 거의 결정한다. 설치형으로 배포하므로 파서와 임베딩 모델의 라이선스(특히 GPL과 AGPL 계열)를 재배포 기준으로 확인한다. HWP 5.0 바이너리는 기준선에서 빼지만 hwp-binary가 곧 이어지므로, 파서 후보를 고를 때 HWP 바이너리 지원 여부와 그 라이선스도 함께 본다. 한국 문서를 Markdown으로 바꾸는 공개 도구(`chrisryugj/kordoc` 등)도 후보로 보되, 라이선스를 먼저 확인한다.
4. **DB 드라이버와 첨부 칼럼.** DBMS 드라이버마다 재배포 조건이 다르고, 드라이버 라이브러리가 지원하지 않는 DBMS도 있다. db-source 전에 대상 DBMS별로 드라이버, 재배포 조건, ODBC 대안을 표로 정리한다. 행에 든 첨부(파일 경로, URL, BLOB)를 가져오는 방식은 참고할 만한 공개 설계가 드물어 직접 정해야 하므로, 첨부의 변경 감지와 함께 삭제의 연쇄를 설계 인터뷰에서 먼저 본다.
5. **벡터 저장소와 한국어 키워드 검색.** PostgreSQL의 기본 전문 검색에는 한국어 형태소 분석이 없다. 그래서 pgvector를 고르고 키워드 검색을 섞으려면 pg_bigm이나 PGroonga 같은 확장이 필요할 것으로 본다. 확장을 쓰면 설치 환경의 PostgreSQL에 붙일 때 그 확장이 있어야 하므로, 단독 PostgreSQL과 설치 환경 PostgreSQL 두 경우를 함께 본다.
6. **색인 형식의 변경 비용.** 조각의 칸을 나중에 바꾸면 설치된 문서를 모두 다시 색인해야 한다. 그래서 갱신일, 시행일, 접근 그룹 칸을 처음부터 둔다(2절). 색인 형식에 판을 붙이고, backup-upgrade의 판 올림이 다시 색인이 필요한지 알 수 있게 한다.
7. **첫 대량 적재 시간.** 문서 수만 건을 처음 넣을 때 걸리는 시간은 임베딩 처리량이 정한다. 대상 사양에서 이 시간을 재서 설치 안내에 적고, 적재를 멈췄다가 이어 갈 수 있게 한다.

## 8. 개발 환경

- 임베딩과 리랭커는 개발하는 동안 로컬 PC(CPU나 GTX 1660 Ti)에서 돌린다. 수억 파라미터급 모델이므로 개발용 문서 양에는 충분하다.
- 동시 요청의 검색 지연과 첫 대량 적재 시간처럼 대상 사양에서 재야 하는 값은 클라우드 GPU를 몇 시간 빌려 잰다. 선택지와 데이터 규칙은 agent-os 저장소의 일지 `docs/journal/2026-11-06-02-doc-qa-direction.md`에 있는 "설계 인터뷰 입력" 절의 GPU 환경을 따른다. 요금은 조사 시점의 기록이므로 쓰기 전에 다시 확인한다.

## 9. PRD 초안

킥오프 5단계의 `docs/PRD.md` 초안이다. 킥오프가 요구하는 네 가지(누구의 어떤 문제, 무엇을 만들고 안 만드나, 성공의 정의, 스펙이 충돌할 때의 우선순위)에 맞췄다.

```markdown
# rag-engine PRD

## 누구의 어떤 문제
- **문서 담당자와 운영자.** 조직의 문서를 에이전트가 근거로 쓸 수 있게 모으고 최신으로 유지해야 하지만, 문서를 밖으로 보낼 수 없어 외부의 지식베이스 서비스를 쓸 수 없다.
- **에이전트를 만드는 개발자.** 근거 위치가 붙은 검색 결과를 표준(MCP)으로 받고 싶다. 특정 에이전트 런타임에 묶이고 싶지 않다.

## 무엇을 만드나
- 설치형 문서 검색 서버. 원천(업로드, 서버 경로, 수집 API, SQL)에서 문서를 수집하고, 파싱, 청킹, 임베딩, 색인, 검색을 한다.
- 통로는 셋이다. 클라이언트에게 MCP 읽기 도구, 문서 담당자에게 관리 API와 관리자 페이지, 다른 시스템에게 수집 API.

## 무엇을 안 만드나
- 답 생성(LLM 호출), 대화 기록, 답에 대한 오류 신고. 클라이언트의 몫이다.
- 구조화 데이터의 Text-to-SQL. 클라이언트 쪽 도구의 몫이다.
- 스캔본 OCR(나중에 연동한다)과 외부 웹 수집.
- 멀티테넌시. 설치 하나가 조직 하나다.

## 성공의 정의
- 공개 시연(2027-01 초): core, search-eval, release-image만으로, 공개 문서 묶음을 넣은 서버가 판을 고정한 이미지로 돌고 그 묶음의 검색 적중률 보고서를 함께 낸다.
- 0.1(2027-03 초 무렵): 폐쇄망 VM에 단독 compose로 설치되고, 업로드와 서버 경로로 PDF, DOCX, HWPX를 수집해, MCP 클라이언트가 근거 위치와 갱신일이 붙은 조각을 받는다. 원천에서 지운 문서는 다음 동기화 뒤 검색되지 않는다. 검색 적중률 보고서가 CI에서 돈다.
- 1.0(2027년 상반기, 어림): HWP 5.0 바이너리, 문서 권한에 따른 검색(주체가 없으면 거부), 최신성 표시, SQL 원천, 관리 변경 기록.

## 스펙이 충돌할 때의 우선순위
1. 권한과 비밀: 볼 수 없는 문서의 조각을 내지 않고, 질문 내용과 연결 정보를 남기지 않는다.
2. 원천과의 일치: 원천에서 지운 문서는 검색되지 않는다.
3. 계약의 판: 검색 도구 형식, 수집 API, 플러그인 인터페이스를 판 없이 깨지 않는다.
4. 검색 품질.
5. 기능의 폭.
```

## 10. 헌법 인터뷰의 입력

킥오프 5단계는 헌법 세 파일(`principles.md`, `tech.md`, `operations.md`)을 빈 칸 없이 채우고, 되돌리기 어렵고 진짜 대안이 있었던 결정을 ADR로 남긴다. 아래는 그 인터뷰에 가져갈 후보다. 정하는 것은 인터뷰다.

### 원칙 후보

| 원칙 | 근거 |
|---|---|
| 클라이언트를 모른다. MCP 표준과 판을 붙인 계약으로만 연다 | 1절, agent-os ADR 0048 |
| MCP로는 읽기만 연다. 쓰기는 관리 API와 수집 API로만 한다 | 2절, core |
| 권한은 기본이 닫힘이고, 질문 내용, 연결 정보, 원본 문서의 내용을 로그와 진단에 남기지 않는다 | 4절, 5절, doc-permission |
| 원천이 진실이다. 색인은 원천의 사본이고, 원천에서 지운 것은 색인에서도 지운다 | 4절의 동기화 규칙 |
| 계약에는 판을 붙인다. 검색 도구 형식, 수집 API, 커넥터·변환·파서 인터페이스, 색인 형식이 대상이다 | 2절, 4절 |

### 스택에서 정할 것

| 항목 | 정할 것 | 메모 |
|---|---|---|
| 언어 | 파이썬을 먼저 본다 | 파서, 임베딩, DB 드라이버의 생태계가 넓고, 킥오프가 복사하는 하네스(훅, 검사)도 파이썬이다 |
| 패키지 관리 | uv | agent-os와 같다 |
| HTTP 서버와 MCP SDK | 같은 프로세스에서 REST와 `/mcp`를 여는 조합 | MCP는 Streamable HTTP |
| 데이터베이스 | PostgreSQL | 3절 |
| 벡터 저장소 | pgvector와 별도 벡터 DB 가운데 | 킥오프에서 고르기 어려우면 "core 설계 인터뷰에서 정하고, 그때 ADR과 함께 `tech.md`를 고친다"로 결정한다 |
| 작업 대기열 | 수집 작업자를 검색 서버와 나누는 방식 | core의 설계 인터뷰와 함께 |
| 관리자 페이지 | 화면 스택 | agent-os의 `web/`과 같은 pnpm과 Next를 쓸지, 서버가 그리는 단순한 화면으로 할지 |

### 운영에서 정할 것

- 검증 명령(테스트, 린트, 타입체크)과 CI.
- 계약 시험을 처음부터 CI에 둔다. MCP 클라이언트로 접속해 검색 도구의 형식을 확인하는 시험이다.
- 이미지 빌드를 CI에 둔다.
- 설치처의 정보(주소, 계정, 설치처별 변환 플러그인)는 이 저장소에 넣지 않고, 설치처의 비공개 저장소에 둔다.

### 첫날 ADR 후보

- MCP로는 읽기 도구만 열고, 쓰기는 관리 API와 수집 API로 나눈다.
- 이 서버는 자기 데이터베이스를 쓰고 연결 문자열 하나만 받는다.
- 수집 파이프라인에 플러그인 자리 셋(커넥터, 변환, 파서)을 두고, 설치처별 변환 플러그인은 설치처의 비공개 저장소에 둔다.
- 질문 내용을 남기지 않고 지연 시간만 남긴다.

### 스캐폴딩의 종료 조건

킥오프 7단계의 종료 조건(테스트, 린트, 타입체크 명령이 실제로 통과한다)에 더해, 빈 HTTP 서버의 `/health`를 시험하는 테스트가 통과하고 컨테이너 이미지가 CI에서 지어진다.
