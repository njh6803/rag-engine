# 02: 리뷰 봇이 dev→main 출시 PR을 건너뛴다

**What to build:** agent-os ADR 0043 Consequences "티켓 검사와 봇"대로 `.github/workflows/claude-code-review.yml`의 리뷰 잡이 출시 PR(같은 저장소의 머리 브랜치 `dev`, base `main`)에서는 돌지 않게 한다. agent-os 티켓 2(`dev-review-bot-off`, #536)의 조건식과 "확인한 근거" 절의 여섯 경우를 옮긴다. 건너뛴 잡은 필수 검사가 아니다(`tools/protection.json`의 필수 검사는 `verify` 하나).

**기본 브랜치가 dev로 옮겨진 뒤의 갈래도 정한다**(ADR 0016 Consequences "리뷰 봇 두 갈래"의 앞의 것). 이 파일의 머리 주석대로라면 액션은 PR의 워크플로 파일을 기본 브랜치의 것과 견주고, 다르면 리뷰를 건너뛴다(설계 세션은 재 보지 않았다). 기본 브랜치가 dev이면 dev에서 이 파일이 바뀌고 아직 출시되지 않은 동안 main을 머리로 둔 PR이 건너뛰어지고, 뒤 스텝의 코멘트 0개 가드가 그 PR을 빨갛게 한다(그 PR은 이 파일을 바꾸지 않았으므로 코멘트를 센다). 그런 PR은 main에서 딴 핫픽스 PR과 되돌려 합치기 PR(머리 `main`, base `dev`)이다. 되돌려 합치기 PR에서 리뷰 잡이 돌아야 하는지도 함께 정한다(agent-os의 조건식은 그 PR을 건너뛰지 않는다). 가드가 그 경우를 가려 지나게 할지, 알려진 빨강으로 두고 운영 문서에 적을지(03에 넘긴다. 03은 이 티켓이 병합된 뒤에 병합한다) 정하고 근거를 적는다.

이 파일을 바꾼 PR은 봇이 건너뛰고, 기록(일지·대기열·티켓·하네스 탐침) 밖의 파일을 함께 실으면 가드가 실패한다. 그래서 이 티켓은 따로 PR이고 다른 워크플로나 도구를 건드리지 않는다. 그 PR의 보안·버그·성능 몫은 PR 직전 리뷰(CodeRabbit CLI나 대체 둘)가, 유지보수성·경계 몫은 셀프 리뷰가 맡는다(`docs/constitution/operations.md` 리뷰 파이프라인).

**Blocked by:** 없음 (01·03과 나란히 돈다)

**Status:** done

## 확인한 근거 (2026-11-12)

### 건너뛰는 조건

임시 PR이 아니라 식을 읽어 따졌다(코드 읽기). 잡의 `if`는 `!draft && !(머리 저장소 == 이 저장소 && 머리 브랜치 == 'dev' && base == 'main')`이고, `git show origin/dev:.github/workflows/claude-code-review.yml`(agent-os)의 같은 파일의 식과 글자가 같다(손으로 대 봤다). 아래 표는 그 식을 워크플로 파일에서 읽어 파이썬 식으로 옮겨 경우마다 넣은 결과다. 명령은 `uv run python -I <스크래치패드>/eval_if.py .github/workflows/claude-code-review.yml`이고 기대와 다르면 종료 코드 1로 끝나는데 0으로 끝났다(손으로 돌렸다. 스크립트는 세션 스크래치패드에 있고 커밋한 프로브가 아니다). 파이썬 식은 GitHub의 식 평가기와 다르므로 이것은 읽어 따진 결과를 한 번 더 거른 어림이지 GitHub에서 잰 값이 아니다. 실제 dev→main PR에서 건너뛰는 모습은 dev가 서고 첫 출시 PR이 열릴 때 처음 본다.

| 머리 브랜치 → base | 머리 저장소 | 결과 |
|---|---|---|
| `dev` → `main` | 이 저장소 | 건너뛴다 |
| `hotfix/x` → `main` | 이 저장소 | 돈다 |
| `feature/01-a` → `dev` | 이 저장소 | 돈다 |
| `chore/a` → `dev` | 이 저장소 | 돈다 |
| `docs/a` → `dev` | 이 저장소 | 돈다 |
| `dev` → `main` | 포크 | 돈다(포크의 `dev`는 건너뛰지 않는다) |
| `main` → `dev`(되돌려 합치기) | 이 저장소 | 돈다 |
| `feature/01-a` → `main`(기본 브랜치 전환 전) | 이 저장소 | 돈다 |

초안 PR은 머리와 base에 상관없이 건너뛴다(기존 조건). 코멘트 0개 가드는 같은 잡의 스텝이라 잡과 함께 건너뛴다. 건너뛴 잡은 필수 검사가 아니다(`tools/protection.json`의 필수 검사는 `verify` 하나, 파일을 읽었다).

### 되돌려 합치기 PR(머리 `main`, base `dev`)은 건너뛰지 않는다

agent-os와 같이 조건에 갈래를 더하지 않는다. 그 PR이 싣는 핫픽스는 hotfix PR에서 이미 리뷰를 받았지만, 충돌을 푼 줄은 이 PR에서 처음 생기는 코드다. 조건식이 이 PR을 건너뛰면 가드도 함께 건너뛰어 코드를 실은 PR이 어떤 봇 리뷰도 없이 초록으로 병합된다. 돌리는 값은 요약 코멘트 하나이고, diff가 핫픽스 몫으로 작아 크지 않다. 출시 PR을 끄는 근거(내용 전부가 티켓 PR마다 리뷰를 받았다)가 이 PR에는 충돌 해결의 몫만큼 성립하지 않는다.

### 기본 브랜치가 dev인 동안의 갈래: 알려진 빨강으로 두고, 가드는 풀지 않는다

- **액션 로그의 경고 문구.** 액션 `anthropics/claude-code-action@58985842…`(v1.0.244)의 `src/github/token.ts`를 그 커밋 주소(`raw.githubusercontent.com`)에서 내려받아 읽었다(원문 5111바이트, 코드 읽기). 앱 토큰 교환(`https://api.anthropic.com/api/github/github-app-token-exchange`로 OIDC 토큰을 보낸다. 120~123행)이 실패했을 때 오류 코드가 `workflow_not_found_on_default_branch`이거나(24~26·38~44행) 401 응답의 메시지에 `workflow validation failed`가 있으면(46~53행) `Skipping action due to workflow validation: …` 경고를 찍고 `WorkflowValidationSkipError`를 던진다(125~136행). 안내 문구(133행)는 워크플로를 바꾼 PR에서 예상되는 일이라고 적는다. 이 경고가 이 파일 머리 주석이 근거로 든 agent-os PR #3·#6의 문구와 같은지는 그 저장소의 로그를 다시 보지 않았다. 이 파일에는 파일끼리 견주는 코드가 없고 서버가 판정한 오류 코드만 있다. 그래서 "서버가 기본 브랜치의 파일과 견준다"는 오류 코드 이름과 안내 문구에서 읽은 추론이고, 이 저장소에서 재지 않았다.
- **어느 PR이 걸리는가(어림).** 이 갈래가 생기는 때는 dev와 main의 이 파일이 달라진 때다. 04가 dev를 main에서 따는 순간 두 파일은 같다. 그 뒤 dev에서 이 파일을 바꾸고(액션 판을 올리는 일 등) 아직 출시하지 않았거나, main의 핫픽스가 이 파일을 바꾸고 아직 되돌려 합치지 않았으면 다르다. `pull_request` 이벤트는 병합 결과 커밋의 워크플로를 쓴다고 알고 있어(GitHub 동작에 대한 기억, 이 저장소에서 보지 않았다) 파일이 다를 때 걸리는 쪽은 base가 `main`인 PR(hotfix PR)로 좁혀진다. 되돌려 합치기 PR은 핫픽스가 이 파일을 바꾸지 않았다면 병합 결과가 dev의 파일이라 기본 브랜치와 같아 돌 것이다. 핫픽스가 이 파일을 바꾼 경우의 되돌려 합치기 PR은 이 추정이 맞지 않으니 첫 핫픽스에서 본다.
- **결정.** 가드를 고쳐 이 경우를 지나게 하지 않는다. 가드가 지나가도록 거르는 길은 둘인데 둘 다 쓰지 않는다. (a) 코멘트가 없어도 기본 브랜치의 파일과 다르면 지난다: 코드를 실은 hotfix PR이 리뷰 없이 초록이 되어 가드가 막으려던 초록 착시를 되살린다. (b) (a)에 기록 밖 파일 검사를 붙인다: hotfix는 코드를 싣는 PR이라 거의 늘 걸리고 이익이 없다. 빨강은 리뷰가 없었다는 사실이며 필수 검사가 아니라서 병합을 막지 않는다. 대신 가드의 오류 메시지에 이 경우일 수 있다는 것과 리뷰를 대신하는 길을 적었고(어림이라 "일 수 있다"로 적었다), 머리 주석에도 같은 내용을 적었다. 이 오류 메시지 고침은 수용 기준이 요구한 것이 아니라 결정을 읽는 이에게 전하려고 더했다. 동작은 그대로다. 코멘트가 없는 다른 원인(턴 상한 초과 등)에도 같은 문구가 붙으므로 "일 수 있다"로만 적었다.
- **03에 넘긴다.** `docs/constitution/operations.md`의 리뷰 파이프라인에 적을 줄: (1) dev→main 출시 PR은 리뷰 봇이 건너뛴다. (2) 기본 브랜치가 dev인 동안 dev의 `claude-code-review.yml`이 아직 출시되지 않았으면 base가 `main`인 hotfix PR의 Claude Code Review가 액션의 워크플로 검증으로 건너뛰어져 가드가 빨개질 수 있다. 알려진 빨강이며 필수 검사가 아니고 그 PR의 리뷰는 PR 직전 리뷰와 셀프 리뷰가 대신한다. (3) 되돌려 합치기 PR은 봇이 돈다. 그리고 ADR 0016 Consequences "리뷰 봇 두 갈래"를 이 결정과 위 근거의 종류(코드를 읽은 추론, 서버 쪽 비교는 보지 못함)로 고쳐 `## 이력`에 적는다. 이 PR은 `docs/adr/` 파일이 기록 밖이라 싣지 못해 03이 맡는다. 고칠 때 그 문장이 main을 머리로 둔 PR(핫픽스 PR, 되돌려 합치기 PR)이 모두 리뷰를 건너뛴다고 적은 것도 이 결정(건너뛸 수 있는 것은 base가 main인 hotfix PR이고 되돌려 합치기 PR은 돈다)에 맞춘다. 운영 문서 "리뷰 파이프라인"의 24행 "Claude Code Review 워크플로가 함께 돈다"도 출시 PR에서는 맞지 않게 되므로 (1)과 함께 고친다. 03 티켓 파일에는 이 몫을 수용 기준으로 더하지 않았다. 03은 다른 세션이 나란히 고치는 중이라 이 PR이 그 파일을 건드리면 충돌한다. 03 티켓 11행("02가 넘긴 것")과 이 절이 받는 쪽이고, 다음 지시문의 "이어받을 상태"에도 적는다.

### 이 PR의 리뷰

이 PR은 `claude-code-review.yml`을 바꿔 봇이 건너뛴다. 보안·버그·성능 몫은 PR 직전 리뷰(CodeRabbit CLI나 대체 둘)가, 유지보수성·경계 몫은 셀프 리뷰(`/code-review`)가 맡는다. 결과는 PR 본문에 적는다.
