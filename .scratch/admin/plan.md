# admin: 관리자 페이지 v0. 현황, 원천, 문서, 검색 시험 화면에서 문서를 올리고 지우며 잘 찾아지는지 확인한다
**슬라이스:** 2
**Blocked by:** source-sync

킥오프 입력 5절의 "제품 0.1에서 화면으로 만들 것"(현황, 원천, 문서, 검색 시험)을 만든다. 문서를 제때 올리고 지울 수단이 없으면 색인이 낡은 문서로 답하기 때문이다. core와 source-sync의 관리 API 위에 서고, MCP 도구로는 열지 않는다. 사내 로그인(OIDC)으로 할지, 운영자 계정 하나로 시작할지는 설계 인터뷰가 정한다. 화면의 디자인은 이 저장소가 스스로 정한다. 관리자 페이지의 이미지를 release-image의 판 태그 규칙에 더하고, 단독 compose에서는 같은 포트의 경로 하나로 연다. 설계 인터뷰의 입력은 킥오프 입력 5절이다.

core 명세(`.scratch/core/spec.md`, 2026-11-10)가 넘긴 것: 그룹과 지식베이스의 생성·수정·삭제 관리 API(core는 지식베이스의 목록·조회·재색인 시작만 두고, 기본 그룹과 기본 지식베이스는 `migrate` 명령이 설정값으로 만든다), 화면이 요구하는 문서·작업 목록 조회의 확장(core의 목록은 상태 필터와 커서 페이지만 둔다). `migrate`는 다시 돌 때마다 기본 지식베이스의 설정을 환경 변수 `RAG_DEFAULT_*`의 값으로 덮어쓴다(core 명세 관리 명령 절). 관리 API로 지식베이스 설정을 고치는 길을 열면 다음 `migrate`가 그 값을 되돌리므로, 둘의 우선순위는 이 기능의 설계 인터뷰가 정한다.

search-eval 설계(ADR 0017, 0018, 0019, 2026-11-12)가 넘긴 것: 검색 평가를 관리자 페이지에서 등록하고 실행하고 결과를 보는 화면과 그 관리 API, 평가 세트와 결과를 두는 저장 표. 평가의 핵심(채점, 지표, 보고서)은 search-eval이 `app`의 유스케이스로 두고 저장소의 명령줄 도구로만 열므로, 제품 이미지 안에서 평가를 부르는 입구는 이 기능이 처음 연다. 그 입구가 열릴 때 LLM 관련성 판정도 함께 열린다. search-eval이 구현된 뒤에는 판정기와 SDK가 이미지에 실려 있고 기본은 꺼짐이다(끝점 주소, 모델, 키 설정이 모두 있어야 조립된다). 설계 인터뷰가 정할 것은 넷이다. 첫째는 순서다. 평가 화면과 그 관리 API는 search-eval의 평가 유스케이스가 구현된 뒤에야 만들 수 있는데, 지금 이 기능의 `Blocked by`에는 search-eval이 없고 수락에도 평가 항목이 없다. search-eval을 `Blocked by`에 더할지, 평가 화면을 이 기능의 뒤 티켓이나 다른 기능으로 뗄지를 정한다. 나머지 셋은 지식베이스마다 조각과 질문을 LLM 쪽으로 내보내도 되는지 따로 허용하는 장치, 설치처의 평가 세트와 판정 결과를 어디에 어떻게 남길지(설치처의 질문과 문서 내용이라 원칙 V의 대상이다), 그리고 최소 점수가 구현되면 지식베이스의 그 기본값을 관리자 페이지에서 고치게 할지다(ADR 0017. 최소 점수는 점수 분포를 본 뒤 사용자가 승인할 때만 구현하고, 리랭커가 없는 지식베이스에는 기본값을 둘 수 없다).

search-eval 명세(`.scratch/search-eval/spec.md`, 2026-11-13)가 넘긴 것: 최소 점수가 구현된 뒤에 지식베이스 설정을 고치는 관리 API를 열면, 최소 점수의 기본값이 있는 지식베이스에서 리랭커를 빼는 변경과 리랭커가 없는 지식베이스에 기본값을 두는 변경을 422로 거부한다(명세의 "최소 점수" 절, ADR 0017). v0에서는 그 길이 `migrate`뿐이라 search-eval이 `migrate`에서 같은 규칙을 지킨다.

수락: 브라우저에서 표본 문서를 올려 상태가 바뀌는 것을 보고, 문서의 조각 목록을 열어 보며, 원천의 지금 동기화와 작업 기록이 보이고, 검색 시험의 결과가 같은 질문에 대한 MCP 검색 결과와 같으며, 문서를 지운 뒤에는 그 문서의 조각이 검색에 나오지 않는 e2e가 통과한다.
