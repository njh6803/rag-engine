# rag-engine PRD

## 누구의 어떤 문제
- **문서 담당자와 운영자.** 조직의 문서를 에이전트가 근거로 쓸 수 있게 모으고 최신으로 유지해야 하지만, 문서를 밖으로 보낼 수 없어 외부의 지식베이스 서비스를 쓸 수 없다.
- **에이전트를 만드는 개발자.** 근거 위치가 붙은 검색 결과를 표준(MCP)으로 받고 싶다. 특정 에이전트 런타임에 묶이고 싶지 않다.

## 무엇을 만드나
- 설치형 문서 검색 서버. 원천(업로드, 서버 경로, 수집 API, SQL)에서 문서를 수집하고, 파싱, 청킹, 임베딩, 색인, 검색을 한다.
- 통로는 셋이다. 클라이언트에게 MCP 읽기 도구, 문서 담당자에게 관리 API와 관리자 페이지, 다른 시스템에게 수집 API.

## 무엇을 안 만드나
- 답 생성(LLM 호출), 대화 기록, 답에 대한 오류 신고. 클라이언트의 몫이다.
- 구조화 데이터의 Text-to-SQL. 클라이언트 쪽 도구의 몫이다.
- 스캔본 OCR(나중에 연동한다)과 외부 웹 수집.
- 멀티테넌시. 설치 하나가 조직 하나다.

## 성공의 정의
- 공개 시연(2027-01 초): core, search-eval, release-image만으로, 공개 문서 묶음을 넣은 서버가 판을 고정한 이미지로 돌고 그 묶음의 검색 적중률 보고서를 함께 낸다.
- 0.1(2027-03 초 무렵): 폐쇄망 VM에 단독 compose로 설치되고, 업로드와 서버 경로로 PDF, DOCX, HWPX를 수집해, MCP 클라이언트가 근거 위치와 갱신일이 붙은 조각을 받는다. 원천에서 지운 문서는 다음 동기화 뒤 검색되지 않는다. 검색 적중률 보고서가 CI에서 돈다.
- 1.0(2027년 상반기, 어림): HWP 5.0 바이너리, 문서 권한에 따른 검색(주체가 없으면 거부), 최신성 표시, SQL 원천, 관리 변경 기록.

## 스펙이 충돌할 때의 우선순위
1. 권한과 비밀: 볼 수 없는 문서의 조각을 내지 않고, 질문 내용과 연결 정보를 남기지 않는다.
2. 원천과의 일치: 원천에서 지운 문서는 검색되지 않는다.
3. 계약의 판: 검색 도구 형식, 수집 API, 플러그인 인터페이스를 판 없이 깨지 않는다.
4. 검색 품질.
5. 기능의 폭.
