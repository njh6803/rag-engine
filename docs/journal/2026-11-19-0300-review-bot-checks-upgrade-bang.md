# release-image 07: 리뷰 봇이 PR의 변경과 제목의 느낌표가 맞는지 본다 · 2026-11-19

release-image 티켓 여덟 가운데 07(`07-review-bot-checks-upgrade-bang`)을 구현한 세션의 기록이다. 시작 프롬프트는 `/implement .scratch/release-image/issues/07-review-bot-checks-upgrade-bang.md`이고 브랜치는 `feature/07-review-bot-checks-upgrade-bang`, 작업은 워크트리 `07-review-bot-checks-upgrade-bang`에서 했다. 모델은 Sonnet 5.5 / high다. 01, 02와 나란히 연 세 세션 가운데 셋째다.

## 한 일

- `.github/workflows/claude-code-review.yml`의 리뷰 프롬프트 3단계 끝에 한 가지를 더했다. PR 제목 접두의 느낌표가 변경과 맞는지 `docs/constitution/operations.md`의 "느낌표의 기준"으로 보라는 줄이다. 기준은 프롬프트에 다시 적지 않고 그 절을 가리키기만 한다. 업그레이드할 때 손댈 것이 있는데 느낌표가 없거나, 없는데 붙었으면 [Major]로 짚는다. 마이그레이션 파일과 업그레이드 원고의 짝은 노트 검사가 보므로, 재색인이 필요해지는 변경과 계약의 판에서 앞자리를 올리는 변경처럼 기계가 알아보지 못하는 것을 diff에서 찾게 했다. 출시 PR과 운영에서 개발로 합치기 PR은 같은 문서를 따라 면제한다.
- 4단계의 범위 문장 "위 두 축뿐이다"를 "위 두 축과 제목 접두의 느낌표뿐이다"로 맞췄다. 그대로 두면 새 줄과 범위 문장이 서로 어긋난다.
- 티켓의 상태를 `in-progress`로 시작해 `done`으로 닫았다.

## 확인한 것

- `uv run python tools/plan_table.py`를 돌린 뒤 `git status`에 `.scratch/plan.md`가 나타나지 않았다. 티켓 상태를 바꿔도 전체 계획 표는 바뀌지 않으므로 가드에 걸리지 않는다.
- `zizmor`(`--offline --strict-collection --config .github/zizmor.yml .`)는 "No findings"였다.
- 이 PR은 워크플로 파일, 티켓 파일, 일지만 싣는다. 워크플로를 바꾼 PR이라 리뷰 봇은 건너뛰고, 셀프 리뷰와 PR 직전 리뷰가 이 변경의 유일한 리뷰다.

- 검사 러너(`uv run python tools/run_checks.py`)는 종료 0이었다. `ruff check`와 `ruff format --check`도 통과했다.

## 셀프 리뷰

표준 축과 명세 축을 나란히 돌렸다. 둘이 같이 낸 Major는 하나였다. 프롬프트가 "같은 문서가 면제로 정한다"고 썼지만, 운영 문서 41행이 면제하는 것은 노트 검사뿐이고 리뷰 봇의 판단을 면제한다는 문장은 없다. 봇이 1단계에서 `title,body`만 읽어 머리와 base 브랜치를 알 수 없다는 점도 같이 나왔다.

고친 것(프롬프트 원문):

- 1단계가 `gh pr view $PR --json title,body,headRefName,baseRefName`를 읽는다.
- 기준을 "느낌표의 기준"과 그 다음 단락 "보는 자리" 둘로 가리킨다. 면제는 머리가 main이고 base가 dev인 합치기 PR만 `headRefName`과 `baseRefName`으로 가려 적용하고, 출시 PR은 이 잡이 돌지 않는다고 적었다.
- "그런 것이 없는데"를 "기준에 드는 변경이 없는데"로 바꾸고 마이그레이션이 든 변경도 든다고 적었다. 마이그레이션만 든 올바른 `feat!:` PR에 거짓 [Major]가 나지 않게 하려는 것이다.
- 맞을 때 적는 줄을 "제목 접두: 맞음"으로 못박고 "지적 없음"의 두 줄과 별개로 더한다고 적었다. 다음 PR에서 이 줄이 나오는지 눈으로 찾을 글자가 된다.

남긴 것과 이유:

- 운영 문서가 봇 판단의 면제를 따로 적지 않는다. 이 PR은 운영 문서를 싣지 못하므로(워크플로 가드), 면제를 "보는 자리"의 노트 검사 면제와 같은 까닭으로 읽은 것이 이 프롬프트의 해석이다. 운영 문서에 그 한 문장을 더할지는 사용자가 정한다.
- `on.pull_request.types`에 `edited`가 없어, 제목을 고쳐도 봇이 다시 돌지 않고 틀린 [Major] 코멘트가 남는다. `ticket` 잡과 같은 구조이고 운영 문서가 적은 대로 제목을 고친 뒤 푸시를 한 번 더 하면 새 제목으로 돈다. 이 워크플로의 트리거는 이 티켓의 범위 밖이라 건드리지 않았다.
- 노트 검사(05)가 들어오기 전에는 마이그레이션 파일 PR의 접두를 기계가 보지 않는다. 고친 프롬프트는 마이그레이션도 접두와 맞대므로 그 사이를 봇이 메운다.
- Nit(앞자리 풀이, 일지의 낱말 풀이)는 운영 문서의 낱말을 따른 것이라 남긴다.

## PR 직전 리뷰

`coderabbit-review`를 돌렸다. CLI 0.7.5가 `Seat: not assigned`(Free)에서도 끝까지 돌았고 지적은 0건이다. 밀 주장 넷(절 이름과 면제, 합치기 PR과 출시 PR의 분기, 허용 도구 `gh pr view:*`, YAML과 zizmor)은 모두 맞았다. 나열 밖에서 Minor 하나와 Nit 둘이 나왔다.

- [Minor] 운영 문서 41행이 "07이 `claude-code-review.yml`에 더한다"고 미래형으로 적었다. 이 PR이 병합되면 낡은 문장이 된다. 이 PR은 운영 문서를 싣지 못하므로(워크플로 가드) 남긴다. 다음 절의 후속 PR이 맡는다.
- [Nit] 워크플로 머리 주석이 여전히 "담당은 유지보수성·경계"뿐이다. 동작에 영향이 없어 남긴다.
- [Nit] 합치기 PR의 면제 판단이 머리·base 브랜치 이름만 본다. 포크의 `main` 브랜치에서 dev로 내는 PR도 면제로 읽히지만, 잃는 것이 봇의 조언 한 줄이라 남긴다. `isCrossRepository`를 함께 읽게 하면 닫힌다.

## 회고

일지의 "다음" 절을 쓴 계기로 `retro` 스킬을 돌렸다. 후보는 넷이고 승인 0, 넘김 0, 기각 넷이다.

1. **기각.** 훅이 agent-os 저장소로 `cd`하는 명령을 막았다. 이미 있는 가드가 그 자리에서 막았고, `git -C`로 바로 풀었다.
2. **기각.** 훅이 `zizmor` 출력을 파이프로 줄인 명령에 경고했다. 이미 있는 훅이 그 자리에서 알렸고, 종료 코드가 필요한 판정은 뒤의 검사 러너로 다시 본다.
3. **기각.** 티켓의 마지막 체크박스("검사 넷이 초록이다")를 러너 결과가 나오기 전에 체크했다. 러너가 실패하면 되돌릴 것이고 잃은 것이 없다. 사건 없이 위험만 떠올린 것이다.
4. **기각.** 프롬프트에 별도 3-1단계를 처음 넣었다가 4단계의 "위 두 축뿐이다"와 어긋남을 스스로 보고 3단계 안으로 합쳤다. 병합 전에 이 세션이 잡았고 남은 비용이 없다.

만료는 `uv run python tools/queue_open_rows.py`의 "만료할 항목"이 (없음)이라 닫을 것이 없었다. 문턱을 지난 새 훅·검사가 없어 `tools/hook_report.py`는 돌리지 않았다.

## 다음

이 PR이 병합된 뒤 따로 고칠 것이 하나 있다. `docs/constitution/operations.md` 41행의 "리뷰 봇이 변경과 제목의 접두를 맞대는 줄은 release-image의 07이 더한다"를 현재형으로 고치고, 봇 판단의 면제(합치기 PR)를 그 단락에 한 문장으로 적는다. 헌법 문서를 고치는 일이라 사용자 승인을 받아야 하고, 이 PR의 워크플로 가드가 허용하는 경로 밖이다. 해당 문장을 걷는 일은 release-image의 마지막 티켓이 하거나, 그 전에 작은 chore로 낼 수 있다. 05가 같은 단락의 PR 서식과 노트 검사 문장을 걷을 때 함께 고치는 길이 가장 싸다.

병합한 세션은 다음으로 열리는 티켓 PR의 세션에 다음 한 가지를 넘긴다. 그 PR에서 리뷰 봇이 느낌표를 판정하는 줄(맞다는 한 줄, 또는 [Major] 지적)을 내는지 보고, 일지에 적는다. 이 줄이 실제로 도는지는 이 PR에서 확인할 수 없고, 아직 보지 않았다.
