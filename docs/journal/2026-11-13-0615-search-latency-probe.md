# search-latency-probe: 대상 사양에서 검색 지연을 재고 기본값을 정한다 · 2026-11-13

`next-session`이 낸 지시문으로 다른 세션이 연 세션의 기록이다(Sonnet 5.5). 시작 프롬프트는 `/implement .scratch/core/issues/16-search-latency-probe.md`이고, 브랜치는 `feature/16-search-latency-probe`, 작업은 워크트리 `16-search-latency-probe-f30c20`에서 했다. 이번 요청 범위는 "PR과 병합까지"다. 이 티켓이 기능 `core`의 마지막 티켓이다. 준비, 한 것, 잰 값과 판정, 셀프 리뷰, 회고, 검증, 다음을 차례로 둔다.

- 티켓의 `Status:`를 `ready-for-agent`에서 `in-progress`로 바꿨다(첫 편집).

## 한 것

- `.scratch/core/probes/search-latency/`에 프로브 셋과 출력을 더했다. `probe.py`는 기계 사양, 수집, 파싱 한도, TEI 직접 호출, `/mcp` `search` 동시 부하를 순서대로 재고 사람이 읽는 보고를 낸다. `corpus.py`는 규칙으로 한국어 PDF·DOCX·HWPX 표본과 질의를 짓는다. `compose.yml`은 TEI 컨테이너 둘이다. 출력은 `probe_out.txt`다.
- 프로브 README에 행 셋을 더했다. 명세 Further Notes의 "어림으로 남긴 것" 문장에 이번에 잰 결과와 아직 어림인 것(백오프 밑수 30초, 리눅스 `RLIMIT_AS`로의 환산)을 적었다.
- 기본값(`RAG_SEARCH_CANDIDATES` 50, `RAG_TEI_BATCH_SIZE` 32)은 바꾸지 않았다. 그래서 `settings.py`와 명세 설정 절은 고치지 않았다. 까닭은 아래 "잰 값과 판정"이다.

## 잰 값과 판정

기계는 Ryzen 7 3700X(16스레드), 메모리 31.9GiB, Docker Desktop VM 16 CPU·15.6GiB다. 호스트가 다른 세션의 작업과 CPU를 나눠 써서 보고의 호스트 CPU 평균이 90~100%였다. 같은 호출의 시간이 실행마다 크게 달랐다(리랭크 1개 호출이 저장한 실행에서 40초, 저장하지 않은 실행에서 3.4초와 68초). 아래는 `probe_out.txt`의 값이다.

- 표본 12개(PDF·DOCX·HWPX 각 4개, 6장), 조각 91개, 토큰 3.4만. 수집은 277초, 작업 12개가 모두 `succeeded`였다.
- 파싱: 표본 12개는 0.3초 이하, 최대 작업 집합 102MiB다. 한도 근처 PDF(1000쪽, 5.5MiB)는 65초, 1475MiB, 글 2.36MiB다. 한도 넷(1000쪽, 300초, 2GiB, 64MiB)이 표본을 막지 않는다. 다만 이 메모리는 Windows의 작업 집합이고 리눅스 `RLIMIT_AS`는 가상 메모리라, 2GiB 한도와의 여유는 어림으로 남는다.
- TEI 직접: 임베딩 한 호출의 처리량이 16개 296 토큰/s, 32개 290 토큰/s로 2% 안이다. 32개 한 호출은 53.2초라 기본 `RAG_TEI_TIMEOUT_SECONDS`(60초)에 가깝다. 리랭크는 32개 한 호출이 100.6초로 60초를 넘었다(1개 40.0초, 8개 41.6초).
- 검색 부하, 리랭커 없음(후보 50): 동시 1건 p95 421ms, 4건 p95 1.05초, 8건 p95 3.2초, 오류 0. 단계는 임베딩이 거의 전부다.
- 검색 부하, 리랭커 있음: 후보 5개가 단건 15.5~17.3초(20초 안), 동시 4건 p95 281초(네 건 모두 20초 초과)였다. 후보 10개와 50개는 동시 1건만 재어 94초와 130초다. 시간은 거의 모두 `rerank_ms`이고 임베딩은 0.1~0.8초, SQL은 0.01~0.16초다. 리랭커의 TEI 로그가 `model.onnx` 없음과 `model.safetensors` 내려받기를 찍는다(느린 까닭이 candle 폴백이라는 것은 추정이다).
- 설정과 크기마다 한 번씩만 쟀다. 같은 호출이 실행마다 크게 흔들렸으므로(리랭크 1개 호출 40초, 저장하지 않은 실행의 3.4초와 68초) 수는 이 실행의 값이다.

**판정.**
- `RAG_TEI_BATCH_SIZE`: 첫 전체 실행 전에 적은 기준(16과 32의 임베딩 처리량이 10% 안이면 32)대로 32를 둔다. 296과 290 토큰/s로 2% 안이다. 이 기준은 임베딩만 보았다. 같은 실행에서 리랭크 32개 한 호출은 100.6초로 `RAG_TEI_TIMEOUT_SECONDS`(60초)를 넘었고 임베딩 32개 한 호출은 53.2초로 한도에 가까웠다. 그래도 바꾸지 않은 까닭은 둘이다. 리랭크가 쓰이는 검색은 어차피 20초를 넘어 배치 크기로 구해지지 않고, 수집은 임베딩만 쓰며 한 호출 53.2초는 이 개발 PC의 100% 점유 때 값이다. 대상 기계에서 다시 재어야 한다.
- `RAG_SEARCH_CANDIDATES`: 기준(동시 4건 p95가 10초 이하이고 오류 없는 가장 큰 값)은 리랭커 유무를 가르지 않고 적었다. 글자 그대로 적용하면 리랭커 없이 후보 50, 동시 4건 p95 1.05초가 통과해 50을 둔다. 기본 구성은 리랭커가 켜진 것이라 기준을 그 구성에 걸어 다시 읽으면(이 한정은 결과를 본 뒤 더했다) 잰 조합(후보 5·10·50)이 모두 못 맞춘다. 두 읽기가 같은 결론이라 기본값 50을 그대로 둔다. 후보 4 이하와 후보 10·50의 동시 4건은 재지 않았다. 후보 5에서 이미 단건이 한도에 닿으므로 후보를 줄여서는 풀리지 않을 것이라는 것은 추론이고, 후보 수를 줄이는 것은 재현율을 깎는 일이라 search-eval의 몫이다.
- 남은 결정(사용자와 search-eval의 몫): CPU TEI 리랭커로는 기본 검색 시간 제한 20초를 지키기 어렵다. 길은 셋이다. 리랭커를 끄는 기본(이 경우 후보 50에서 동시 8건 p95 3.2초), ONNX 리랭커나 GPU 이미지, 검색 시간 제한을 늘리는 것이다. 이 프로브는 어느 길도 고르지 않는다.

**어림으로 남는 것.** 백오프 밑수 30초는 재지 않았다. 파싱 한도 중 메모리 2GiB는 Windows 작업 집합(1475MiB)만 재어 리눅스 `RLIMIT_AS`(가상 메모리)와 같은 값이 아니라 확인하지 못했다. 작업자 로그의 `parse_ms`는 원본 읽기부터 파싱 결과 저장까지의 한 구간이라(`index_document.py`) `RAG_PARSE_TIMEOUT_SECONDS`가 세는 구간보다 넓다. 표본 12개에서 최대 11.9초이고, 표본마다 파서만 잰 0.3초와의 20~40배 차이는 원인을 가르지 않았다. 1000쪽 PDF에서 조각 수에 비례해 늘어나는 저장 몫은 재지 못했다. 임베딩 16과 32의 처리량이 2% 안이라는 판정은 `--max-batch-tokens 4096`(조각 약 490토큰이 한 배치에 8개쯤)이 8개 이상을 평평하게 만들어 둘을 못 가른 것일 수 있다. 기본 16384에서는 재지 못했다.
