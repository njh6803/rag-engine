# source-sync 04: 서버 경로 커넥터 · 2026-11-22

source-sync 티켓을 나란히 여는 지시문으로 연 세션의 기록이다(Sonnet 5.5 / high). 시작 프롬프트는 `/implement .scratch/source-sync/issues/04-server-path-connector.md`이고, 브랜치는 `feature/04-server-path-connector`, 작업은 워크트리 `04-server-path-connector`에서 했다. 요청 범위는 PR과 병합까지다.

## 준비

- 주 체크아웃이 아니라 `EnterWorktree`로 새 워크트리에 먼저 들어가 브랜치를 바꿨다. `tidy-checkouts`는 묶음의 첫 세션이 도는 것이라 이 세션은 돌리지 않았다.
- 01 일지의 "다음"이 시킨 대로 명세 144·148·149행을 겨냥해 읽었다. 144행(키의 역슬래시 규칙)은 이 티켓의 일이고 구현했다. 148행(폴더를 정하는 요청의 차례)과 149행(폴더 확인의 10초 한도)은 06의 일이라 이 티켓에서는 짓지 않았다. 06이 쓸 것은 티켓 04 끝의 "구현 메모"와 06 티켓의 폴더 확인 항목에 적었다.
- 이 세션의 대화는 구현 도중 한 번 요약으로 줄었다.

## 지은 것

**커넥터.** `adapters/connectors/server_path.py`의 `ServerPathConnector`와 만드는 함수 `create_server_path_connector`다. `pyproject.toml`의 entry point 그룹 `rag_engine.connectors`에 `server_path`로 등록했다. 부모 폴더는 `RAG_SOURCES_DIR`(없으면 `/sources`)에서, 업로드 상한은 `RAG_MAX_UPLOAD_MB`(없거나 틀리면 100)에서 만드는 함수가 커넥터를 만들 때 한 번 읽는다. 이미 만든 커넥터는 환경 변수를 다시 읽지 않는다. 만드는 함수는 설정의 모양만 보고 파일 시스템을 부르지 않는다.

- **확인과 열기는 한 동작이다.** `NOFOLLOW_OPEN_AVAILABLE`이 참인 운영체제(제품 이미지의 리눅스)에서는 부모 폴더를 연 자리에서 토막마다 `O_NOFOLLOW`와 연 폴더 기준의 열기로 내려가고, 마지막 토막은 `O_NONBLOCK`을 더해 연 뒤 연 파일로 보통 파일인지 본다. 목록도 연 폴더에서 `os.scandir(fd)`로 읽는다. 이 열기가 없는 개발 기계(Windows)에서는 토막마다 `lstat`으로 확인한 뒤 여는 길로 돈다.
- **키와 설정의 거름.** 키의 빈 토막, `.`, `..`, NUL, 앞의 `/`는 파일 시스템을 부르지 않고 `rejected`다. 역슬래시는 운영체제가 구분자로 읽을 때(Windows)만 거절하고 리눅스에서는 보통 글자다. 설정 `folder`는 같은 거름에 더해 역슬래시를 어디서나 거절하고, 끝의 `/` 하나를 뗀다.
- **목록.** 끝까지 걸어 보통 파일을 낸다. 키는 디스크의 이름 그대로이고 변경 확인값은 `"{mtime_ns}:{size}"`다. 심볼릭 링크, 보통 파일이 아닌 것, UTF-8로 쓸 수 없는 이름은 내지 않고 목록을 끝낸 뒤 개수만 로그 한 줄로 남긴다. 하위 폴더를 읽지 못하면 그 폴더를 빼지 않고 목록 전체를 `unreadable`로 실패시킨다. 걷는 일은 `_Walk`가 명시적인 더미로 한다(깊은 폴더에서 재귀 한도에 걸리지 않게 한다).
- **받기.** 바이트와 확장자로 정한 MIME(`SUPPORTED_EXTENSIONS`)과 수정 시각을 낸다. `fetch`는 `fstat`의 크기가 상한을 넘으면 읽지 않고 `too_large`로 알리고, 크기가 상한 이하여도 상한보다 한 바이트 더 읽다가 넘으면 멈춘다(확인한 뒤 자란 파일을 잡는다).
- **스레드.** 파일 시스템을 부르는 일은 호출마다 새로 띄운 daemon 스레드 하나에서 한다. 이벤트 루프의 기본 풀도, 호출끼리 나눠 쓰는 풀도 쓰지 않는다. 결과는 `call_soon_threadsafe`로 루프에 넘기고, 루프가 이미 닫혔으면 버린다(`_post_to_loop`).
- **예외에 경로를 싣지 않는다.** 예외는 `except` 블록 밖에서 올려 `__context__`와 `__cause__`에 경로가 실리지 않게 했고, `OSError`는 `unreadable`로 바꾼다.

시험은 `tests/adapters/test_server_path_connector.py`(72개)다. 실제 파일 시스템과 실제 심볼릭 링크로 한다.

## 이 세션이 정한 것

- **쌍점은 Windows에서 거절한다.** 명세는 역슬래시만 운영체제에 따라 거절하라고 적었다. 드라이브 이름이 앞에 붙은 `C:밖의파일.pdf`는 Windows에서 부모 폴더 밖을 가리킬 수 있어, 구현은 쌍점도 같은 때에 거절한다. 리눅스에서는 보통 글자다. 명세의 한 줄을 이에 맞출지는 06이 정한다(티켓 04의 구현 메모).
- **`folder`의 `a//`와 `a//b`는 `invalid_config`다.** 명세는 "끝의 `/`는 뗀다"만 적었고 겹친 `/`는 정하지 않았다. 하나만 떼고 나머지 빈 토막은 거절한다.
- **UTF-8로 쓸 수 없는 글자는 설정에서는 `invalid_config`, 키에서는 `rejected`다.** `list()`가 이런 이름을 키로 내지 않으므로 키가 될 수 없는 값이다.
- **상한은 `os.environ`에서만 읽는다.** `.env`를 읽으려면 파일 시스템을 불러야 하는데 만드는 함수는 부르지 않는다. 서버와 작업자가 `.env`로 상한을 정하는 설치에서는 이 커넥터가 기본값 100을 쓸 수 있다. 모듈 독스트링과 티켓 메모에 적었다.
- **같은 이름의 entry point가 둘이면 먼저 찾은 것을 쓰는 01의 결정은 건드리지 않았다.**

## 겪은 것

- 테스트 코드에 `# pyright: ignore`를 썼다가(원칙 II) `loop.run_in_executor`를 바꿔 끼우는 `_forbid_default_pool`로 바꿨다. `# noqa: ANN202`와 `os.scandir[str]` 표기(실행 때 TypeError)도 같은 식으로 일반 함수 한 쌍으로 바꿨다.
- 메서드 이름 `list`가 클래스 안에서 내장 `list`를 가려 주석의 타입이 틀어졌다. 걷는 코드를 모듈 수준 함수로 빼냈고, 셀프 리뷰 뒤에 그것을 `_Walk` 클래스로 다시 묶었다.
- 린트 `too-many-statements-in-try-clause`(5개 이하)에 걸려 반복의 한 걸음을 따로 함수로 나눴다.
- `os.mkfifo`가 Windows 플랫폼에서는 없어 pyright가 알 수 없다고 했다. `sys.platform == "win32"`로 가른 `_make_fifo` 도우미 안에 넣어 두 플랫폼에서 깨끗하게 했다.
- 편집기의 pyright 진단은 리팩터링 도중과 직후에 낡은 오류를 자주 띄웠다. 판정은 명령줄 `uv run pyright`로 했다.
- 한글은 ruff가 폭 2로 세어 주석이 줄 길이(100)를 자주 넘었다. `tools/rewrap_comments.py`와 `ruff format`으로 고쳤다.
- 맨 `python3`을 부른 명령을 훅이 막았다(환경 함정). 그 명령은 통째로 돌지 않았고, 메모를 다시 더했다.

## 검증

브랜치는 `feature/04-server-path-connector`였고 `tools/sibling_overlap.py`는 번호 겹침 없음이었다. `README.md`만 형제 워크트리(`glossary-release-number-names`)와 함께 고친 파일이다.

- **개발 PC(Windows).** 커넥터 시험 72개가 초록이다. `uv run ruff check .`, `uv run ruff format --check .`, `uv run pyright`(0건), `uv run lint-imports`, `uv run python tools/check_type_escapes.py`도 초록이다. 이 PC의 초록은 리눅스 길이 돈다는 증거가 아니다(`.claude/rules/tests.md`).
- **리눅스(제품 작업자 이미지 `rag-engine-test/rag-engine-worker:0.1.0-rc.1`).** 저장소를 읽기 전용으로 붙이고 같은 시험을 돌렸다. 71개가 초록이고 하나가 빨강이다. 빨강은 entry point 시험이다. 이미지에 설치된 패키지 정보가 새 entry point를 모르기 때문이고, 이 PC에서는 초록이다. 실제 `O_NOFOLLOW` 길로 도는 경쟁, FIFO, 링크 시험이 이 길에서 돈다.
- **변이.** 리눅스 컨테이너 안의 사본에 변이 여섯을 넣고 시험이 빨개지는지 봤다. 모두 빨개졌다. (1) 링크를 따르지 않는 열기가 없다고 하는 변이는 상수 시험이 확정적으로 잡고, 경쟁 시험은 다섯 번 가운데 네 번 잡았다. (2) `O_NONBLOCK`을 뺀 변이는 FIFO 시험이 시간 초과로 잡는다. (3) 파일 열기의 `O_NOFOLLOW`를 뺀 변이는 링크 시험이, (4) 폴더 열기의 `O_NOFOLLOW`를 뺀 변이는 원천 폴더 링크 시험이 잡는다. (5) 크기 확인을 뺀 변이는 `too_large` 시험이, (6) 한 바이트 더 읽기를 뺀 변이는 읽는 도중 자란 파일 시험이 잡는다. 경쟁 시험은 우연에 기대므로 한 번에 못 잡을 수 있다. 고친 코드에서는 밖의 내용이 나올 길이 없어 거짓 빨강은 없다.
- **전체 검사 러너(`tools/run_checks.py`).** 리팩터링 전의 첫 판은 초록이었다. 리팩터링 뒤 첫 판은 같은 시간에 컨테이너 시험과 변이를 돌리던 중이었고, xdist 작업자 둘이 "node down"으로 죽고 시험 셋이 실패한 채 한도 4200초까지 멈춰 있다가 끝났다. 실패한 시험의 이름은 한도에서 끊긴 출력에 남지 않았다. 다른 부하 없이 다시 돌린 판은 전부 초록이다(`test-db`, `check-ticket`, `check-notes`, `lint-imports`, `zizmor`, `check-instructions`, `check-type-escapes`, `pyright`, `pyright-linux`, `run-hooks`, `pytest` 847.5초). 첫 판의 실패가 부하 때문이라는 것은 이 재실행이 초록이라는 것으로 짐작한 것이고, 실패한 시험을 따로 확인한 것은 아니다.

- **CodeRabbit 지적을 고친 뒤(`scan()`의 리스트 누적).** `ruff check`, `ruff format`, `pyright`가 초록이고 커넥터 시험 72개가 이 PC에서 초록이다. 리눅스 이미지에서는 71개 초록과 위와 같은 entry point 시험 하나의 빨강이다. 전체 검사 러너는 이 수정을 담은 커밋의 pre-commit이 돈다.

## 셀프 리뷰

`/code-review`를 고정점 `origin/dev`로 돌렸다(표준 축은 sonnet·high). 범위는 이 브랜치의 고친 추적 파일(`README.md`, `pyproject.toml`, 티켓 04)과 미추적 파일 셋(커넥터 모듈, 시험, 일지)이다. 티켓 06의 한 줄은 리뷰 뒤에 더했다. 주장 검증 대상은 모듈 독스트링의 "확인과 열기는 한 동작", 스레드 하나의 약속, 로그에 이름이 안 실린다는 말이었다.

### 판정과 반영

두 축의 지적을 근거를 열어 가려 읽고 판정했다. 서브에이전트의 보고는 모델의 출력이라 지적으로만 썼다.

**고친 것.**
- 걷는 코드가 출력 인자(`counts`)를 받아 바꾸던 모양을 `_Walk` 클래스로 고쳤다(`counts`는 `run()`이 낸다). 더미는 `_Frame`(폴더, 키 앞머리, 남은 항목)을 쌓는다. 항목의 변경 확인값은 `_Entry.change_marker`가 만든다.
- 스레드에서 이벤트 루프로 일을 넘기던 닫힌 루프 처리 두 벌이 같은 모양이라 모듈 수준 `_post_to_loop`로 합쳤다.
- `_kind_of`와 `_entry_of`를 나눠 항목 종류와 항목 값을 따로 만들게 했다.
- UTF-8로 쓸 수 없는 `folder`와 키를 거절하게 했고, Windows의 쌍점도 같이 거절하게 했다. 시험 셋을 더했다.
- 시험: Windows 길의 경쟁 시험이 `os.lstat`를 실제로 부르는지 단언한다(확인한 뒤 여는 길임을 본다). 읽는 도중 자란 파일의 `too_large` 시험을 더했다(`fstat`가 크기 0을 답하게 바꿔 끼운다). 거짓 이름이던 `test_링크를_따르지_않는_열기는_리눅스에만_있다`를 `..._Windows_밖에서만_쓸_수_있다`로 고쳤다.
- `pyproject.toml`의 주석이 ADR 0012를 서버 경로 커넥터의 근거로 적었다. ADR 0012는 그룹과 인터페이스를 정하고 서버 경로 커넥터를 첫 구현으로 두는 것은 ADR 0021이라 둘을 나눠 적었다.
- 모듈 독스트링과 주석의 줄 길이를 감았다.

**남긴 것과 이유.**
- 실패 사유를 `ConnectorError`로 바꾸는 같은 모양이 네 군데에 있다(Duplicated Code 후보). 냄새 기준선이 스스로 판단 항목이라고 하는 것이고 동작에 영향이 없어 이 PR에서는 묶지 않았다.
- `_mime_of`와 `domain/media_types`의 확장자 표의 관계에 대한 지적도 같은 이유로 남겼다. 표 자체는 새로 만들지 않고 이미 있는 것을 읽는다.
- `_call_in_thread`는 모듈 안의 비공개 이름이다. 05(커넥터 호출 장치)와 06이 같은 규칙의 스레드 호출을 필요로 하면 그때 공개할지 정한다.
- 상한을 `.env`에서 읽지 않는 것은 결정으로 적었다(위).
- 같은 이름의 entry point가 둘일 때의 동작은 01의 결정 그대로다.

**주장 검증 세 가지.** 모듈 독스트링의 "확인과 열기는 한 동작", 스레드 하나의 약속, 로그에 이름이 실리지 않는다는 말은 각각 시험이 닿는다. 앞의 둘은 위 변이가 시험을 빨갛게 만들었고(변이 1에서 4), 스레드는 기본 풀 금지와 스레드 공유 금지 시험이, 로그는 `test_목록의_로그에는_폴더와_파일_이름을_싣지_않는다`가 본다.

**PR 직전 리뷰에 밀 주장.** 방금 새로 쓴 사실 문장은 다음 둘이다. 이 문서 "검증"의 "경쟁 시험은 다섯 번 가운데 네 번 잡았다"와 모듈 독스트링의 "Windows에서는 토막마다 `lstat`으로 확인한 뒤 여는 길로 돌고 그 틈을 닫지 못한다".

## PR 직전 리뷰

### `/security-review`(본 세션이 모듈 전체를 읽고 본 판)

지적 없음이다. 본 것은 다음과 같다. 서브 작업으로 나누지 않고 이 세션이 `server_path.py` 전체를 읽었다.

- 리눅스 길: 부모 폴더만 링크를 따라 연다(운영자가 정한 값이다). 그 아래는 토막마다 `O_NOFOLLOW`와 연 폴더 기준의 열기로 내려가고, 키와 설정의 토막은 열기 전에 빈 토막, `.`, `..`, NUL, 앞의 `/`를 거절한다. 토막 안에 `/`가 없어 한 번의 열기가 두 칸을 건너뛸 수 없다.
- 마지막 파일은 `O_NOFOLLOW|O_NONBLOCK`으로 열고 연 기술자로 보통 파일인지 본다. 기술자에는 `O_CLOEXEC`가 붙는다. 링크가 아닌 하드 링크는 파일 시스템 위에서 보통 파일과 구별되지 않으므로 이 커넥터의 몫이 아니다(원천 폴더에 쓸 수 있는 쪽이 이미 가진 권한이다).
- Windows 길은 확인한 뒤 여는 틈이 있다. 이것은 명세가 적은 대가이고 제품은 리눅스 이미지다.
- 로그에는 개수만 싣고 예외는 `except` 밖에서 올려 경로가 사슬에 남지 않는다. 환경 변수는 신뢰한다.

### CodeRabbit CLI(`coderabbit-review`)

`coderabbit review --agent --base origin/dev --committed`가 끝까지 돌았고(`review_completed`, 종료 코드 0, CLI 0.7.5, `Plan: Free`, `Seat: not assigned`) 지적은 아홉 건이었다. 대상은 커밋 `a517a38`의 일곱 파일이다. 서브에이전트의 보고는 모델 출력이라 지적으로만 쓰고 근거를 코드에서 열어 판정했다. 보고 끝의 대체 둘(`/security-review`, `bug-perf-review`)을 돌리라는 줄은 CLI가 끝까지 돌지 못한 길의 몫이라 이번에는 해당하지 않는다. `/security-review`는 위처럼 따로 돌렸다.

**고친 것.**
- `scan()` 둘(`_FdDirectory`, `_PathDirectory`)이 항목마다 튜플을 통째로 다시 만들어 한 폴더의 복사량이 항목 수의 제곱으로 늘었다(CLI는 Major, 이 세션은 Minor로 봤다. 정확성이 아니라 규모의 문제다). 지역 리스트에 더하고 끝에 튜플로 돌려주게 했다. 정렬과 사라진 항목을 건너뛰는 동작은 그대로다.
- 일지 "지은 것"의 "호출마다 읽는다"는 코드와 달랐다. 두 값은 `create_server_path_connector`가 커넥터를 만들 때 한 번 읽는다. 일지를 고쳤다.

**남긴 것과 이유.**
- 경쟁 시험의 `assert contents`(한 번은 정상으로 읽혔어야 한다)가 스케줄 운에 달렸다는 지적: 거짓 초록이 아니라 거짓 빨강 쪽 위험이고, 바꿔치기가 도는 1500번 가운데 정상 폴더 상태가 한 번도 걸리지 않으려면 바꿔치기 스레드가 그 시간 내내 굶어야 한다. 이 시험이 보려는 것(경쟁이 실제로 있었는데 밖의 내용이 없다)을 지키는 단언이라 그대로 둔다. 리눅스 CI에서 빨개지면 그때 고친다.
- `list()`를 닫아도 파일을 내지 않는 폴더만 남으면 걷는 스레드가 끝까지 돈다는 지적(Minor): 스레드는 daemon이고 걷기는 유한하다. 끊긴 공유 폴더에서 막힌 호출은 신호를 봐도 풀리지 않는다. 05(커넥터 호출 장치)가 버려진 호출을 다룬다.
- 큐의 상한이 없다는 지적(보류, Minor): 항목은 작은 값이고 소비 속도는 07이 정한다. 07이 소비를 빨리 못 하면 그때 상한을 더한다.
- `check()`가 폴더를 열고 닫기만 해서, 읽기 권한은 있고 탐색 권한이 없는 폴더에서는 `check()`가 통과하고 `list()`가 `unreadable`이라는 지적(CLI는 Major, 보류, Minor): 명세가 `check()`에 요구하는 것은 원천 폴더를 읽을 수 있는지이고, 이 티켓의 수용 기준은 폴더를 여는 호출이 오류를 내게 바꿔 끼우는 장면을 본다. 실패해도 `list()`가 `unreadable`로 알린다. 폴더 확인을 짓는 06이 `check()`의 깊이를 함께 정한다.
- `.env` 지적(보류, Minor)은 위 "이 세션이 정한 것"의 결정이다. 서버가 받은 바이트의 크기를 한 번 더 보므로 상한이 뚫리지는 않는다. 단독 compose가 이 값을 환경 변수로 넘기는지는 15가 본다.

**오탐.** Windows 길의 확인한 뒤 여는 틈(CLI는 Critical)은 명세 145행이 알고 적은 대가이고 시험이 어느 길로 도는지 못 박는다. `fetch`가 읽은 시점의 변경 확인값을 돌려줘야 한다는 지적(CLI는 Major)은 `FetchedItem`에 그 칸이 없는 01의 계약이고, 목록과 받기 사이에 파일이 바뀌어도 저장된 값이 옛 값이라 다음 동기화가 다시 읽으므로 누락되지 않는다.
