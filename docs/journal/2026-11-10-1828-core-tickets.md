## 명세 검토

spec-reviewer 서브에이전트를 백그라운드로 돌렸다(명세의 HEAD be99f63). 검토는 명세와 저장소를 고치지 않았고, 근거를 [코드 읽기], [손으로 봄], [어림]으로 갈라 적었다. [손으로 봄]은 스크래치패드의 임시 스크립트 셋(MCP Context에서 ASGI scope 읽기, PostgreSQL의 DDL 잠금과 NUL·부분 유일 색인의 예외, `DROP INDEX CONCURRENTLY`와 uuid6 값의 수용)이다. 보고의 끝 셈은 blocker 3 · should-fix 16 · nit 8이다. should-fix의 번호는 S1~S17이고 S6은 없다. nit은 N1~N4와 번호 없는 넷이다.

체크리스트 일곱의 판정: 계약 영향은 부분 충족(B3), 원칙 위반(III·IV·VI)은 없음, ADR 충돌은 ADR 0008 본문(S7)과 `[이력]` 항목에 섞인 문장(N3), 경로 실재는 지적 없음, 비목표 침범은 source-sync 계획의 첫 문단(S16), 테스트는 덮이지 않은 스토리(S12)와 잴 수 없는 시험(S13), 자리표시자는 지금 잴 수 있던 미룬 측정 둘(S15, N1). 질문 둘에는 열어 둔 결정이 계약에 박힌다, 티켓 사이에서 계약이 조용히 무효가 되는 자리가 열이다(S14)라고 답했다.

지적과 반영. 명세의 권한 안의 것은 이 세션이 추천안으로 정해 반영했고, 사용자 승인이 필요한 것(ADR 이력, 용어집, 범위)은 아래 `## 물은 것과 답`에서 물었다.

- B1(명세 일지의 교차 Minor X5): 같은 문서에 대기 작업이 있을 때 수집이 작업을 넣으면 부분 유일 색인에 걸려 500이 난다. 수집은 대기 작업을 `INSERT … ON CONFLICT … DO UPDATE` 한 문장으로 다시 쓰고(`run_after`를 지금으로, 요청 ID를 이번 것으로, 시도 횟수는 그대로), 일시 실패를 다시 예약하는 작업 단위는 같은 문서에 다른 대기 작업이 있으면 `failed`로 끝내고 문서 쪽을 쓰지 않는다고 정했다.
- B2: 파서 인터페이스가 바이트와 MIME만 받아 쪽 수 초과와 암호를 누가 내는지 정해지지 않았다. `interface_version` `"1.0.0"`, 한도 값 객체(`max_pages`), 인터페이스 예외 둘(`encrypted_document`, `too_many_pages`), 그 밖은 `parse_failed`로 정하고, 글 크기와 U+0000 지우기는 자식 프로세스의 실행기에 두었다.
- B3: 형식 1.0.0 칸의 뜻. `page`는 1부터, `block_range`는 0부터 센 `[first, last]`(양 끝 포함), `updated_after`는 포함·`updated_before`는 제외·오프셋 필수, `document_count`는 지워지지 않은 문서 수, `groups`의 없는 그룹 이름은 오류 없이 아무것에도 맞지 않는다.
- S1: 절 경로 줄만으로 상한을 넘는 조각. 청킹 규칙 일곱째(경로 줄은 상한의 4분의 1 안, 넘치면 바깥 제목부터 뺌, 그보다 긴 제목 블록은 문단, 경로가 비면 경로 줄 없음, `location.section`은 온전한 경로)와 글 짓기 함수 하나로 정했다.
- S2: 실패 분류. 오류 번역 항목(데이터베이스의 일시 실패는 SQLSTATE `08` 갈래·`40001`·`40P01`·`57P01`~`57P03`, `DataError`·`IntegrityError`는 일시가 아님, 갈래 밖은 `internal_error`로 재시도 소진처럼 끝냄, 메시지를 옮기지 않음)을 두었다.
- S3: 물러난 판의 일반 `DROP INDEX`가 모든 지식베이스의 검색을 막는다. 트랜잭션 밖의 `DROP INDEX CONCURRENTLY IF EXISTS`와 묶음 삭제로 정했다.
- S4(X8): 둘째 단계가 읽은 판이 넷째 단계 전에 정리되면 빈 결과를 성공으로 낸다. 넷째 단계의 SQL이 그 판이 아직 `current`인지 같이 읽고, 아니면 둘째 단계부터 한 번 다시, 다시 해도 아니면 `search_unavailable`이다.
- S5(X6): `migrate`의 기본 레코드 보장이 잠금 규칙 밖이었다. 색인 판 행을 쓰는 작업 단위는 모두 지식베이스 행을 `FOR UPDATE`로 잠근 뒤 쓰고, `migrate`는 행이 없으면 만든 뒤 잠근다.
- S7: Kiwi를 올리면 청킹부터 다시 한다는 결정이 ADR 0008 본문을 거짓으로 만든다. 사용자 승인으로 ADR 0008에 이력과 포인터를 달았다. 검토는 ADR 0006 26행도 들었지만 그 문장은 글자 그대로 여전히 참이라 포인터를 달지 않았다(`.claude/rules/adr.md`의 달지 않는 것).
- S8: 범위 밖 지식베이스에 `forbidden`을 내면 그 존재가 드러난다. `knowledge_base_not_found`로 바꾸고 도구 오류 코드에서 `forbidden`을 뺐다.

- S10, S11: 첫 티켓의 완료 조건과 계약 티켓의 목록. 계약 티켓 항목에 다섯 층(server와 worker는 독립 형제), forbidden 계약(uuid6만 허용), 문서 넷(`CLAUDE.md`, `.scratch/plan-head.md`와 `plan_table`, `README.md` 트리, `.claude/rules/server.md`), 검색 도구 형식과 수집 API의 모델을 넣었다. 모양이 없는 Transform은 처음 구현하는 source-sync가 정한다.

## 사용자가 넘긴 것

명세 검토가 도는 동안 사용자가 agent-os 쪽 세션에서 정리한 글을 붙여 넣었다. 첫째 메시지(원문 그대로):

> 사용자: 사용자가 넘긴 제안 하나를 spec-reviewer의 지적과 함께 판정한다(2026-11-10, agent-os 쪽 세션에서 정리).
>
> 제안: 검색 도구 `search`에 최소 점수로 결과를 거르는 길을 둔다.
> - 입력에 선택 인자 하나(이름은 명세가 정한다. 예: `min_score`)를 더하고, 지식베이스 설정에 그 기본값 칸을 둔다. 기본은 없음이고 없으면 지금 명세와 같이 거르지 않는다.
> - 자리는 명세 "검색 흐름"의 다섯째(리랭크)와 여섯째(top_k개 자르기) 사이다.
> - 값은 core가 정하지 않는다. search-eval이 리랭크 점수의 분포를 재고 정한다.
>
> 왜: 클라이언트의 모델이 검색어를 지어 부르는 쓰임(agentic 검색)에서는 점수가 낮은 조각도 모델의 입력에 쌓여 토큰이 늘고 근거 없는 답의 재료가 된다. 임계값은 리랭커 모델마다 점수 분포가 달라 리랭커 설정을 가진 서버 쪽에 두는 것이 맞고, 빈 결과는 클라이언트에게 "근거 없음"을 결정적으로 알린다.
>
> 명세가 정할 것:
> 1. 리랭커가 없는 지식베이스에서는 `score`가 RRF 점수라(명세 "검색 흐름"의 점수 항목) 순위만 반영한다. 그때 이 인자를 무시할지 `invalid_argument`로 거부할지.
> 2. 거른 뒤 결과가 0개인 것은 오류가 아니라 빈 결과인지.
> 3. 계약의 판. 첫 판(`format_version` 1.0.0)이 나가기 전이라 지금 넣으면 판을 올리지 않아도 되는지, 입력 인자의 추가가 형식의 판에 드는 변경인지.
>
> 고를 수 있는 길: (가) 인자와 설정 칸의 자리만 core 명세에 두고 값은 search-eval로 넘긴다. (나) core에는 두지 않고 search-eval의 기능 계획에 통째로 넘긴다. 정리한 쪽의 추천은 (가)다. 첫 판 뒤에 입력 인자를 더하면 계약의 판을 올려야 해서 지금이 싸다. 다만 core의 범위가 늘어나므로 공개 시연 일정과 견줘 판정한다.
>
> 함께 정해진 것(명세를 바꾸지 않는다): 질의 시점에 LLM을 쓰는 것(질의 재작성, LLM 리랭크)은 두지 않는다. 검색어는 클라이언트가 짓는다.

이어 둘째 메시지(원문 그대로. [첫째]는 첫째 메시지의 제안과 같은 글이다):

> 사용자: 사용자가 넘긴 것 둘이다(2026-11-10, agent-os 쪽 세션에서 정리). 첫째는 이 세션이 spec-reviewer의 지적과 함께 판정하고, 둘째는 판정하지 않고 옮겨 적기만 한다.
>
> [첫째] 이 세션이 판정할 제안: 검색 도구 `search`에 최소 점수로 결과를 거르는 길을 둔다.
> - 입력에 선택 인자 하나(이름은 명세가 정한다. 예: `min_score`)를 더하고, 지식베이스 설정에 그 기본값 칸을 둔다. 기본은 없음이고 없으면 지금 명세와 같이 거르지 않는다.
> - 자리는 명세 "검색 흐름"의 다섯째(리랭크)와 여섯째(top_k개 자르기) 사이다.
> - 값은 core가 정하지 않는다. search-eval이 리랭크 점수의 분포를 재고 정한다.
>
> 왜: 클라이언트의 모델이 검색어를 지어 부르는 쓰임(agentic 검색)에서는 점수가 낮은 조각도 모델의 입력에 쌓여 토큰이 늘고 근거 없는 답의 재료가 된다. 임계값은 리랭커 모델마다 점수 분포가 달라 리랭커 설정을 가진 서버 쪽에 두는 것이 맞고, 빈 결과는 클라이언트에게 "근거 없음"을 결정적으로 알린다.
>
> 명세가 정할 것:
> 1. 리랭커가 없는 지식베이스에서는 `score`가 RRF 점수라(명세 "검색 흐름"의 점수 항목) 순위만 반영한다. 그때 이 인자를 무시할지 `invalid_argument`로 거부할지.
> 2. 거른 뒤 결과가 0개인 것은 오류가 아니라 빈 결과인지.
> 3. 계약의 판. 첫 판(`format_version` 1.0.0)이 나가기 전이라 지금 넣으면 판을 올리지 않아도 되는지, 입력 인자의 추가가 형식의 판에 드는 변경인지.
>
> 고를 수 있는 길: (가) 인자와 설정 칸의 자리만 core 명세에 두고 값은 search-eval로 넘긴다. (나) core에는 두지 않고 search-eval의 기능 계획에 통째로 넘긴다. 정리한 쪽의 추천은 (가)다. 첫 판 뒤에 입력 인자를 더하면 계약의 판을 올려야 해서 지금이 싸다. 다만 core의 범위가 늘어나므로 공개 시연 일정과 견줘 판정한다.
>
> 함께 정해진 것(명세를 바꾸지 않는다): 질의 시점에 LLM을 쓰는 것(질의 재작성, LLM 리랭크)은 두지 않는다. 검색어는 클라이언트가 짓는다.
>
> [둘째] 옮겨 적기만 할 것: 아래는 search-eval의 설계 인터뷰가 읽을 입력이다. `.scratch/search-eval/plan.md` 본문의 "core 명세가 넘긴 것" 문단 뒤에 "사용자가 넘긴 것(2026-11-10)"으로 옮겨 적고 같은 PR에 싣는다.
>
> 사용자가 넘긴 평가 항목 넷. 설계 인터뷰가 넣을지 판정한다.
> 1. 평가 질의를 두 종류로 잰다. 사람이 쓴 질문 그대로와, 클라이언트의 모델이 지은 검색어(키워드에 가까운 짧은 글)다. 이 저장소는 클라이언트를 모르므로, 평가 세트의 형식이 "질의 문자열 목록을 밖에서 받아 같은 기대 근거에 붙일 수 있다"까지만 정한다. 목록은 클라이언트 쪽이 만든다.
> 2. 적중률을 네 줄로 따로 낸다. 벡터만, 키워드만, 둘을 합친 것(RRF), 리랭크 뒤. ADR 0006 Consequences의 "`ts_rank`에는 IDF가 없어 BM25가 아니다. 모자라면 키워드 엔진만 바꾼다"를 판정할 숫자가 이 표다. 키워드 질의는 토큰을 OR로 잇는다는 것(core 명세 "키워드 토큰")도 함께 본다.
> 3. 최소 점수 임계값을 판정한다(위 첫째 제안이 받아들여졌을 때). 기대 근거인 조각과 아닌 조각의 리랭크 점수 분포, 임계값마다의 적중률과 빈 결과의 비율을 낸다.
> 4. 놓친 질문을 까닭으로 나눠 센다. 조각에 문맥이 없어서(절 경로를 붙여도 못 찾음), 표나 그림이어서, 낱말이 달라서, 문서 여럿을 이어야 해서. ADR 0003이 미룬 "청킹 뒤의 보강 자리"와 색인 시점의 LLM 문맥 부여를 더할지는 첫째 까닭의 비율을 보고 정한다. 사용자의 결정은 "색인 시점의 LLM 보강은 이 숫자를 본 뒤에 정한다"이다.
>
> 근거로 든 글(검색 요약으로만 봤고 원문을 읽지 않았다. 문서에 근거로 적기 전에 원문을 대 본다):
> - 단독으로 잰 검색 품질이 에이전트 루프 안의 쓸모를 늘 예측하지는 못한다: arXiv 2605.04018
> - 에이전트가 지은 하위 질의에서 BM25가 LLM 기반 검색기를 약 30% 앞섰다: arXiv 2602.05975
> - 문맥 부여 청킹의 검색 실패 감소 35%·49%·67%: Anthropic의 발표를 2차 인용(arXiv 2606.21676)으로 봤다

[첫째]의 판정은 (나)로 추천했고 사용자가 골랐다(아래 질문 3). 추천의 근거는 넷이다. ADR 0015와 원칙 VII은 칸을 더하는 것을 minor로 정해 기본값이 "거르지 않음"인 선택 인자는 1.0.0 뒤에 1.1.0으로 더해도 기존 클라이언트를 깨지 않는다(정리한 쪽이 (가)를 추천한 근거, 곧 첫 판 뒤에는 판을 올려야 한다는 것은 major일 때만 선다). 리랭커가 없는 지식베이스의 점수는 RRF라 임계값의 뜻이 없고, 제대로 풀려면 점수의 종류를 내는 칸까지 필요하다. 지식베이스의 기본값 칸은 v0에 지식베이스를 고치는 관리 API가 없어 `RAG_DEFAULT_*`와 `migrate`의 길을 새로 내야 하는데 core 안에는 그 값을 쓰는 곳이 없다. 공개 시연의 묶음이 core, search-eval, release-image라 search-eval이 더해도 바깥 클라이언트가 1.0.0을 보기 전이다. 명세 Out of Scope의 search-eval 줄과 search-eval 계획 본문의 "사용자가 넘긴 제안(2026-11-10)" 문단에 세 질문과 함께 넘겼다.

"함께 정해진 것"(질의 시점에 LLM을 쓰지 않는다. 검색어는 클라이언트가 짓는다)은 명세를 바꾸지 않는다고 했으므로 명세에 적지 않고 이 일지에만 남긴다. 지금 명세의 검색 흐름에도 질의 재작성과 LLM 리랭크는 없다.

[둘째]는 판정하지 않고 `.scratch/search-eval/plan.md` 본문의 "core 명세가 넘긴 것" 문단 뒤에 "사용자가 넘긴 것(2026-11-10)"으로 옮겨 적었다. 근거로 든 글 셋은 사용자의 말대로 원문을 읽지 않은 웹 요약이라 근거가 아니라는 표시와 함께 옮겼다(`docs/agents/issue-tracker.md` 프로브와 근거 절). 항목과 글은 사용자의 글 그대로 `>` 인용으로 두고, 평가 항목 3의 위 첫째 제안이 그 계획 안의 최소 점수 제안 문단이라는 것은 인용 밖의 메모로 적었다(셀프 리뷰 반영 뒤의 모양. 처음에는 인용 안의 글을 고쳐 적었다).

## 물은 것과 답

명세 검토의 지적과 사용자가 넘긴 제안을 대 본 뒤, 사용자 승인이 필요한 넷을 한 화면으로 물었다. 넷 다 추천안을 골랐다.

- 질문 1(글 그대로): 명세는 Kiwi(kiwipiepy나 그 모델)를 올리면 청킹의 문장 경계도 바뀌므로 청킹부터 다시 한다고 정했습니다. 이 결정은 ADR 0008 본문("토크나이저만 바뀌면 키워드 열만 다시 만들고 임베딩은 그대로", "작업이 문서의 판을 들고 간다")을 거짓으로 만듭니다. 어떻게 할까요? (선택지 2: ADR 0008 이력을 단다, Kiwi 아닌 문장 분리기)

> 사용자: "ADR 0008 이력을 단다 (Recommended)" — 설명: 명세의 결정을 그대로 두고 ADR 0008에 이력 하나와 본문 포인터 둘을 답니다. Kiwi를 올리는 일은 이미지 업그레이드 때나 생기는 드문 일이고, 그때 청킹·임베딩을 다시 하는 비용을 받아들이는 대신 한국어 문장 경계의 품질을 지킵니다. ADR 0006 26행은 글자 그대로는 여전히 참이라 포인터를 달지 않습니다.

- 질문 2(글 그대로): 명세가 쓰는 판의 상태 말(현재 판, 건설 중인 판, 물러난 판, 살아 있는 판)을 용어집에 올릴까요? 함께 용어집의 관리 API 항목이 삭제를 관리 API의 쓰기로 적은 것(명세와 설계는 삭제를 수집 API의 DELETE에 둠)도 고칩니다. (선택지 2: 넷을 올리고 항목도 고침, 명세 안에서만 정의)

> 사용자: "넷을 올리고 항목도 고침 (Recommended)" — 설명: 관리 API가 이 상태를 내보이고 티켓 제목과 시험 이름이 쓰는 말이라 용어집에 둡니다. 대상 판, 복사 칸, 세대, 올린 세대는 동시성 장치의 말이라 명세 안에서 한 번씩 정의합니다. 관리 API·수집 API 항목은 삭제를 수집 API 쪽으로 옮겨 적습니다.

- 질문 3(글 그대로): 검색 도구 search에 최소 점수(min_score)로 결과를 거르는 제안을 어디에 둘까요? ADR 0015는 칸 추가를 minor로 정해, 1.0.0 뒤에 더해도 기존 클라이언트를 깨지 않고 1.1.0으로 올리면 됩니다. (선택지 2: (나) search-eval로 통째로, (가) core에 자리만 둔다)

> 사용자: "(나) search-eval로 통째로 (Recommended)" — 설명: 제안과 세 질문(리랭커 없는 지식베이스에서의 뜻, 빈 결과, 판)을 search-eval 계획 본문에 넘깁니다. 리랭커가 없을 때 점수가 RRF라 임계값이 뜻이 없고, 이를 제대로 풀려면 점수 종류를 내는 칸까지 필요해 값을 재는 쪽이 모양까지 정하는 편이 맞습니다. core의 범위가 늘지 않습니다.

- 질문 4(글 그대로): 명세는 to-tickets가 '검사 러너와 CI가 테스트 PostgreSQL을 띄우는' 하네스 티켓도 함께 쓴다고 적었습니다. 그런데 docs/ 브랜치 PR에 done이 아닌 harness 티켓을 넣으면 CI ticket 잡이 막고, harness 티켓 파일은 받는 세션이 쓰는 것이 규약입니다. 이 티켓을 어디에 둘까요? (선택지 2: core 티켓 01로 쓴다, chore 세션이 harness로 쓴다)

> 사용자: "core 티켓 01로 쓴다 (Recommended)" — 설명: 명세가 정한 일이라 '기능에 드는' 일이고, 그래서 core 디렉터리의 첫 티켓(.scratch/core/issues/01-…, 브랜치 feature/01-…)으로 이 PR에 씁니다. 수용 기준이 지금 고정되고 Blocked by가 실제 파일을 가리킵니다. 명세와 plan-head의 '하네스 티켓' 문구를 고칩니다.

첫째와 둘째의 답대로 `domain-modeling` 스킬을 부른 뒤 ADR 0008에 이력 하나(Kiwi를 올리면 청킹부터 다시 하고, 작업은 색인 판을 들고 가지 않는다)와 포인터 둘을 달고, `GLOSSARY.md`에 현재 판, 건설 중인 판, 물러난 판, 살아 있는 판을 더하며 관리 API·수집 API 항목의 삭제 자리를 고쳤다.

넷째의 답은 설계 일지가 하네스 티켓으로 적은 일을 core 01로 옮긴다. 그래서 그 말을 쓰던 자리를 함께 고쳤다. 명세(테스트 데이터베이스 절, Further Notes), `.scratch/plan-head.md`(순서 절, 목표 배치의 `compose.test.yml` 줄), `.scratch/core/plan.md`다. `docs/constitution/tech.md`의 테스트 칸도 처음에는 문구를 고치고 판을 1.1.2로 올렸으나, 셀프 리뷰가 넷째 답의 설명이 허락한 것은 명세와 plan-head의 문구까지라고 짚어 되돌렸다. 고칠 문구의 제안은 core 01이 받는다(`## 셀프 리뷰`의 반영). `.claude/skills/next-session/directive.md`의 "하네스 티켓"은 하네스 기능의 티켓을 뜻하는 일반 말이라 그대로 두었다.

## 명세에 반영한 것

위 지적의 반영과 사용자의 답을 명세 한 번의 편집으로 실었다(스크래치패드의 치환 스크립트, 바꾼 자리 마흔일곱). 머리의 근거 줄에 티켓 세션과 이 일지를 적고, 표시 수를 main의 `[넘겨받음]` 21, `[사용자 선택]` 3, `[정함]` 95, `[이력]` 2, `[거절]` 7에서 20, 4, 103, 2, 7로 고쳤다(머리 줄을 뺀 본문을 `grep -o`로 다시 셌다). `[넘겨받음]` 하나가 `[사용자 선택]`이 된 것은 Further Notes의 하네스 티켓 줄이 사용자가 고른 core 01 줄로 바뀐 것이다. 새 `[정함]` 여덟은 계약 티켓이 정하는 것, 판의 HNSW 색인을 만들고 지우는 때(`[이력]` 항목에서 가른 것), 대기 작업 재사용(B1), 오류 번역, 색인 판 행의 잠금, 로거, 더하는 시험, 시간에 기대는 시험의 설정이다. 최소 점수 제안을 search-eval로 넘긴 것은 Out of Scope의 search-eval 줄에 사용자가 골랐다는 문장으로 더했다.

기능 계획 다섯의 본문도 고쳤다. core(티켓 세션이 한 일과 첫 티켓·계약 티켓의 차례), source-sync(S16), admin(`migrate`가 기본 지식베이스 설정을 덮는 것과 admin의 수정 API의 앞뒤), search-eval(사용자가 넘긴 것 둘), release-image(TEI 컨테이너의 로그).

- `pg-ddl/ddl_locks.py`(A~F): 0행에 맞는 부분 색인 만들기가 조각 20만 행에서 0.16~0.19초(검토는 0.08~0.11초로 적었다. 같은 PC, 다른 때다), `CREATE INDEX`는 INSERT를 막고 SELECT를 막지 않음, 일반 `DROP INDEX`는 줄 선 뒤의 SELECT까지 막음, 글 칸의 NUL은 `DataError`이고 jsonb의 NUL은 `22P05`, 둘째 대기 작업은 `23505`.
- `pg-ddl/drop_concurrently.py`(G1, G2): `CONCURRENTLY`는 줄을 서도 새 SELECT를 막지 않고 트랜잭션 안에서는 `25001`.
- `uuid/probe_sqlalchemy.py`(H): uuid6 값이 pydantic `UUID` 칸과 SQLAlchemy `sa.Uuid` 열에 변환 없이 든다. `uv run --with`가 greenlet 휠에서 os error 32로 실패해 임시 venv로 돌렸다(ADR 0011과 같은 우회).
- 결과는 검토가 손으로 본 것과 같았다. pg-ddl의 psycopg `LiteralString` 오류와 uuid의 isinstance·이벤트 루프 정책 경고는 pyright에 남는다고 README에 적었다.
