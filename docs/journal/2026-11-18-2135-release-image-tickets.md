# release-image 티켓: 명세 검토를 반영하고 티켓 여덟으로 나눈다 · 2026-11-18

release-image 명세 PR(#67)이 병합된 뒤 주 체크아웃 세션이 낸 지시문으로 연 세션의 기록이다. 시작 프롬프트는 `/to-tickets .scratch/release-image/spec.md`이고, 브랜치는 `docs/release-image-tickets`, 작업은 워크트리 `release-image-tickets`에서 했다. 모델은 Opus 5.5 / xhigh다. 컨텍스트가 한 번 압축됐다. 준비, 사용자가 넘긴 것, 명세 검토, 명세에 반영한 것, 티켓, 물은 것과 답, 사람 몫, 셀프 리뷰, PR 직전 리뷰, 회고, 다음을 차례로 둔다.

## 준비

- 지시문대로 주 체크아웃에서 `tidy-checkouts`를 먼저 돌았다. 루트는 dev였고 `git fetch origin` 뒤 `origin/dev`(`df9ff50`)보다 7커밋 뒤처져 있었지만, 추적하지 않는 파일 둘(`.scratch_li.log`, `.scratch_pyr.log`)이 있어 깨끗하지 않았다. 스킬의 "루트 브랜치인데 깨끗하지 않다" 갈래대로 당기지 않고 두었다. 누가 그 파일을 만들었는지는 보지 않았다.
- `judge`는 지울 것을 내지 않았다. 남긴 것은 작업 디렉터리를 쥔 프로세스가 있는 워크트리(`05-full-run-rerank`, `13-first-judge-run` 등)와 바뀐 파일이 있는 워크트리(`10-public-docs-questions`)였다. `empty-trash`는 휴지통의 `15-full-gate-ci~~.venv`와 `16-chunking-candidates-experiment~~.venv`를 지우지 못하고 종료 1로 끝났다. 두 폴더의 `.pyd`를 다른 `python.exe`가 올리고 있었다. 지시문대로 보고만 하고 기다리지 않았다.
- 주 체크아웃에서 브랜치를 따지 않고 `EnterWorktree(name: release-image-tickets)`로 새 워크트리에 들어가, 그 안에서 `git switch -c docs/release-image-tickets origin/dev`로 바꿨다. 그 명령이 upstream을 `origin/dev`로 잡아 `git branch --unset-upstream`으로 풀고, `EnterWorktree`가 만든 `worktree-release-image-tickets` 브랜치는 지웠다.
- agent-os(`C:\project\agent`)는 읽기만 했다. 훅과 워크트리 가드가 그 저장소로의 `cd`와 변수·반복이 든 git 명령을 막아, `git -C C:/project/agent show 1aac0cf:<경로>`를 파일 하나마다 따로 쳐 스크래치에 받았다.

## 명세 검토

`spec-reviewer` 서브에이전트에게 명세를 넘기고, 특히 볼 자리로 지시문이 든 셋(시험한 이미지와 올린 이미지 대조 줄, 시험이 띄우는 명령, diag-bundle 계획 7줄)을 줬다. 기준은 `df9ff50`이다. 검토는 blocker 1, should-fix 14, nit 12를 냈다. 측정은 모두 저장소 밖 임시 스크립트로 개발 PC(Docker Desktop 29.9.2, Compose 5.6.1, TEI `cpu-1.9.4`)에서 했고, 커밋한 프로브가 아니다. 그래서 명세에 옮길 때는 "명세 검토가 손으로 봤다"와 그 명령의 꼴로 적었다(`docs/agents/issue-tracker.md` 프로브와 근거). 셋째 항목(diag-bundle 7줄)은 프로브 출력과 맞았고 표현 둘만 고칠 만하다고 했다. 첫째 항목(대조 줄)도 맞았고, 어림 표시의 자리만 옮기라고 했다.

가른 결과는 다음과 같다. 명세의 사실이 틀렸거나 정하지 않은 것은 명세에서 고쳤고, 아직 잴 수 없는 것은 그 자리를 맡은 티켓의 수락 기준으로 넘겼다.

- **blocker. 묶음의 차례가 서지 않는다.** 둘째 묶음(단독 compose)의 시험이 셋째 묶음(설치 안내와 묶음 도구)의 도구로 묶음을 짓고, 그 도구는 agent-os에서 넷째 묶음의 번호·노트 도구와 한 파일(`tools/release.py`)이다. 묶음 도구를 번호·노트와 함께 앞으로 올리고(티켓 02), 넷째를 도구(02)와 검사(05)로 나눴다. 명세 "티켓을 나눌 때 함께 둘 것"을 여섯 묶음과 그 차례로 고쳐 썼다.
- **should-fix 14.** 모두 받았다. 명세에서 고친 것은 아래 "명세에 반영한 것"이고, 티켓에 넘긴 것은 Compose 2.20.2에서 띄워 보기(03), 리랭커의 인자와 메모리(03), 업그레이드를 실제로 쳐 보기(04), 잡 제한 시간(03, 08)이다. `tools/release_ci.py`와 그 시험, `intro/0.1.0.md`는 어느 묶음에도 없어 마지막 티켓(08)에 뒀다.
- **nit 12.** 열한 개를 고쳤다. `docker save`/`load` 뒤의 `RepoDigests`는 "지금 잴 수 있다"는 지적이었는데, 이 세션은 재지 않고 04의 폐쇄망 확인에 넘겼다. 개발 PC의 이미지를 지우고 다시 실어야 해, 다른 세션이 쓰는 이미지를 건드릴 수 있어서다. 명세에도 "이 명세는 그 명령을 치지 않았다"고 적었다. 셀프 리뷰의 명세 축이 nit 둘의 빈틈을 더 찾아 셀프 리뷰에서 고쳤다. nit 10의 뒷절반(노트 검사가 구현 스킬의 문장보다 먼저 강제될 수 있다)은 06을 첫 티켓으로 바꿔 풀었고, nit 1(Dockerfile을 옮길 때 고칠 자리)은 티켓 01에만 있던 `tools/search_eval.py` 19줄을 명세 255줄의 목록에도 넣었다.
- 검토가 확인하지 못했다고 한 것 가운데 PostgreSQL의 로그는 단독 compose 시험의 확인 목록에 더했다(03. 나오면 멈추고 보고한다). bind 원천 폴더를 누가 만드는지, Docker가 지운 컨테이너의 주소를 바로 다시 주는지는 시험의 조건(모델 폴더를 안내대로 만들기, 옛 주소를 차지한 채 다시 만들기)으로 비켜 갔다. agent-os의 `origin/dev`가 낡았을 수 있다는 것은 명세와 티켓의 확인 명령 앞에 받아 오기(`git -C C:/project/agent fetch origin`. 처음에는 역슬래시 경로로 적었다가 셀프 리뷰가 Git Bash에서 깨진다고 짚어 고쳤다)를 두어 막았다.

## 명세에 반영한 것

`.scratch/release-image/spec.md`에서 고친 것이다. 표시 수는 `[넘겨받음]` 30→29, `[정함]` 96→97이고 나머지는 그대로다(묶음 이름 줄을 `[정함]`으로 바꿨다). 서두의 수를 맞췄다.

- 따르는 것: agent-os 변경 확인 앞에 받아 오기를 둔다.
- 이미지의 구성: 서버 `/tmp`의 크기를 `.env`의 `RAG_ENGINE_SERVER_TMP_SIZE`(비면 `1g`)로 바꿀 수 있게 했다. compose 파일을 고치게 하면 업그레이드가 그 고침을 지운다.
- 단독 compose:
  - compose가 덮어쓰는 환경 변수는 셋이고, 리랭커 끝점은 켜는 설치가 `.env`에 적는다(compose가 늘 주면 리랭커 없는 설치도 끝점을 갖는다. 설정은 빈 값을 None으로 읽는다).
  - 최상위 `name: rag-engine`으로 볼륨 이름(`rag-engine_postgres`, `rag-engine_data`)을 정했다.
  - 기다림을 넘긴 `up` 뒤에 같은 명령을 다시 치는 것은 검토의 손 확인으로 바꿨다.
  - 리랭커(`BAAI/bge-reranker-v2-m3`)도 임베딩 서버와 같은 꼴로 띄우고 30분 유예를 준다.
  - 모델 폴더는 `mkdir -p models/embedding`을 `chown` 앞에 둔다. 묶음에 그 폴더가 없고, 없는 바인드 원천은 데몬이 root의 것으로 만든다(검토의 손 확인).
  - root가 가진 폴더의 대조군은 멈춘 것이 아니라 다시 뜨기를 되풀이한 것으로 고쳤다.
  - 임베딩 서버의 로그 항목: 거절된 요청은 꼴이 틀린 본문(422)과 빈 입력(400)이고, 그 뒤 로그에 표지가 0번이었다(검토의 손 확인). 토큰 상한을 넘는 글은 `--max-batch-tokens 4096`에서 TEI가 잘라 200이라 거절이 되지 않는다. 어댑터는 거절의 오류에 상태 코드만 싣는다(`src/rag_engine/adapters/tei.py`를 읽었다).
  - 메모리 항목: 임베딩 서버를 `compose.eval.yml`과 같은 `--max-batch-tokens 4096`으로 띄운다. 메모리 예산의 수치가 그 인자에서 잰 것이다.
- 배포 파일 묶음: 묶음 이름은 `[정함]`이다(ADR 0020은 바꿀 값이라고만 적는다).
- 설치 안내:
  - 최소 판 Compose 2.20.2가 이 저장소의 조합(`service_completed_successfully`와 `up --wait`)을 받는지는 모르므로 03이 재 본다.
  - 리랭커 절의 명령에 `--wait-timeout 1800`과 폴더·`.env` 줄을 더했다.
  - 폐쇄망 절의 첫 시작을 띄우는 명령과 같게 맞췄고, `RepoDigests`는 04가 본다.
  - 업그레이드 절: `proxy/`는 폴더째 바꾸지 않고 제자리로 복사한다. 도는 프록시는 처음 얹은 폴더를 계속 읽는다(검토의 손 확인). `compose.override.yaml`은 남긴다.
  - 정합 시험은 안내의 명령과 시험의 명령을 대 본다.
- 릴리스 워크플로: 대조 줄의 어림을 캐시를 못 타는 쪽(멈춤)으로 옮겼다.
- 리뷰 봇 항목의 인용을 ADR 0016 "전환의 차례" 2로 바로잡았다.
- ci.yml: `image` 잡은 저장소의 `0.0.0`과 다른 `0.0.1-rc.1`로 짓는다. `0.0.0`으로 지으면 번호를 코드에 적은 구현도 지난다.
- 티켓을 나눌 때 함께 둘 것: 여섯 묶음과 차례로 고쳐 썼다(위 blocker).
- Testing Decisions:
  - 모델 폴더는 안내대로 만든다.
  - 늘 초록이던 확인 둘에 조건을 붙였다. TLS 1.1은 `SECLEVEL=0`으로 내밀고, 서버를 다시 만드는 확인은 옛 주소를 차지한 채 한다.
  - 거절 요청을 422로 바꿨다.
  - PostgreSQL 로그, US5·7·21·26의 확인을 더했다.
  - 두 잡의 제한 시간은 1800초 기다림을 넘게 잡는다.
  - 저장소 상태 시험에서 이 저장소에 없는 e2e compose와의 견줌을 뺐고, digest 고정(US53)과 `proxy_buffering off`(US40)를 더했다.
  - 수락의 둘째는 빈 `DOCKER_CONFIG`로 받는다(US2).

`.scratch/diag-bundle/plan.md` 7줄도 고쳤다. 쓸 수 없는 빈 폴더는 다시 뜨기를 되풀이한다는 것, "재지 않았다"의 범위를 바깥 길이 없는 내부 네트워크에서 uid 10001이 가진 빈 폴더를 `HF_HUB_OFFLINE` 없이 띄운 경우로 좁힌 것, 그 경우를 검토가 손으로 봐 2초에 이름 풀기 실패였다는 것이다.

- 4는 오탐이다. 명세 141줄이 상한을 넘는 업로드도 끝까지 쓰인다는 것과 미리 끊는 것은 이 기능이 바꾸지 않는다는 것을 이미 적는다.

## 회고

일지의 "다음" 절을 쓴 계기로 retro 스킬을 돌렸다. 후보는 여섯이고 승인 둘, 넘김 하나, 기각 셋이다.

1. **승인(회차로 센다).** 명세 검토(`spec-reviewer`)의 보고를 받은 턴에 일지나 파일로 옮기지 않아, 컨텍스트가 압축된 뒤 세션 기록(JSONL)에서 꺼냈다. 꺼내는 데 호출이 여러 번 든 사건이 있고, 같은 실수를 세는 열린 항목이 있다. 대기열 `review-report-journal-lag`의 7회차로 더하고, 반영할 자리에 `.claude/agents/spec-reviewer.md`를 넣으라는 단락을 붙였다. 회차가 5 이상이라 이미 chore 배치 조건이다.
2. **승인(새 항목).** 스크래치 파이썬의 문자열에 `C:\project\agent`를 raw가 아닌 꼴로 넣어 티켓 06에 BEL(U+0007)이 들어갔다. 세션이 스스로 찾아 고쳤다. 층은 검사(`tools/check_line_separators.py`가 날것 C0 제어 문자를 막는다)이고 PR 하나로 되돌릴 수 있다. 더하는 것이라 대기열 `control-char-from-script-escape`의 1회차로 두고, 같은 도구를 대상으로 하는 `crlf-from-script-edits`와 서로 가리키게 했다. 그 도구가 BEL을 놓치는 것은 손으로 봤다. BEL 한 글자를 넣은 스크래치 `.md`는 종료 0, U+2028을 넣은 대조 파일은 종료 1이었다(`uv run python tools/check_line_separators.py <파일>`).
3. **넘김(사람 몫).** 주 체크아웃 루트의 추적하지 않는 파일 둘(`.scratch_li.log` 963바이트, `.scratch_pyr.log` 37바이트, 둘 다 2026-11-12 13:57에 생겼고 내용은 경계 검사와 타입 검사의 출력이다. 크기와 시각은 `ls -la`로, 내용은 `head -c`로 앞부분을 봤다)이 그날부터 `tidy-checkouts`의 당기기를 막았다. 다른 일지 열한 개가 그 파일을 적었지만 대기열 항목은 없었다. 워크트리 세션은 다른 체크아웃을 바꾸지 않으므로 사용자에게 한 번 물었다. 사용자의 답은 다음과 같다.

   > 승인할테니 너가 지금 지워

   이 세션이 두 파일을 `rm`으로 지웠고, 지운 뒤 루트에 `scratch_`로 시작하는 파일이 0개인 것을 봤다. 워크트리 가드가 주 체크아웃을 가리키는 `git -C`를 막아서 지우기 전에 `git status`를 다시 치지 못했다. 그래서 세션 처음의 정리가 두 파일을 추적하지 않는 파일(`??`)로 보인 것을 근거로 삼았다. 저장소의 변경이 아니어서 티켓 줄은 없고, 이 세션에서 끝냈으므로 대기열 항목도 쓰지 않았다. 누가 만든 파일인지는 여전히 모른다.
4. **기각.** `git switch -c docs/release-image-tickets origin/dev`(`next-session` `merge.md` 5의 명령 꼴)가 upstream을 `origin/dev`로 잡아 `--unset-upstream`으로 풀었다. 풀기 전에 깨진 것이 없어 사건이 없다.
5. **기각.** agent-os로의 `cd`와 변수·반복이 든 git 명령을 훅과 워크트리 가드가 막아 파일마다 따로 받았다. 이미 있는 가드가 그 자리에서 막은 것이다.
6. **기각.** Read 도구의 토큰 한도, 도구 사이 글의 언어 경고, `empty-trash`의 종료 1은 이미 있는 도구와 훅이 그 자리에서 알렸다.

회고를 마친 뒤 셀프 리뷰 동안 둘이 더 나와 같은 판정으로 더했다. 후보는 모두 여덟이고 승인 넷, 넘김 하나, 기각 셋이다.

7. **승인(회차로 센다).** 티켓 여덟이 CRLF였다. 티켓을 고친 스크래치 파이썬의 쓰기가 남긴 것이고, 셀프 리뷰 표준 축이 잡았다. git이 저장할 때 LF로 바꾸므로 손상은 없다. 같은 처방(`tools/check_line_separators.py`가 CRLF를 낸다)을 든 열린 항목 `crlf-from-script-edits`의 10회차로 더했다.
8. **승인(회차로 센다).** 셀프 리뷰를 반영하는 스크래치 스크립트를 `uv run python -I`로 돌리자 출력이 cp949로 깨졌고, `-X utf8`을 붙여 다시 돌렸다. 잃은 것은 없다(스크립트가 바꿈이 어긋나면 아무것도 쓰지 않게 해 두었다). 열린 항목 `python-i-utf8`의 6회차로 더했다.

만료는 `uv run python tools/queue_open_rows.py`의 "만료할 항목"이 (없음)이었다. 두 출력에 모두 든 항목만 닫으므로 `--ref origin/dev`로 다시 돌려도 닫을 것이 없어 치지 않았다. 문턱을 지난 새 훅·검사가 없어 `tools/hook_report.py`도 돌리지 않았다.
