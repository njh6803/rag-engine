# admin 화면: 관리자 페이지 v0의 화면을 명세 전에 그린다 · 2026-11-26~27

`ui-design-skill-port`를 병합한 뒤 `next-session`이 낸 지시문으로 연 세션의 기록이다(Opus 5.5 / xhigh). 시작 프롬프트는 `/ui-design admin`이고, 브랜치는 `docs/admin-screens`, 작업은 워크트리 `admin-screens`에서 했다. 화면은 Design 아티팩트 https://claude.ai/artifact/DYxhpWUJyyU2qF2d9WMhd2 에 그렸다. 옮긴 화면(`.scratch/admin/design/**`)은 면제 모양이지만, 같은 PR이 화면 그림 스킬(`.claude/skills/ui-design/SKILL.md`)도 고쳐서 harness 티켓 `.scratch/harness/issues/ui-design-first-run-facts.md`를 함께 싣는다("스킬에 옮긴 것"). 준비, 사용자가 넘긴 것, 조사, 방향, 이름, 고르기, 그리기, 옮기기, 반영한 것을 차례로 두고, 그 뒤의 절은 일이 일어난 차례대로 덧붙인다.

## 준비

- 주 체크아웃(dev)에서 시작해 세션 제목을 바꾸고 지시문대로 `tidy-checkouts`를 먼저 돌렸다. 루트의 dev를 `3c0d8ad`에서 `b6021ee`까지 당겼다. 체크아웃되지 않은 브랜치 `worktree-ui-design-skill-port`를 지웠다. 병합된 워크트리 `admin-design`은 쉬는 세션(`docs/admin-design`)이 쥐고 있어 `end-holders`로 그 세션의 `claude.exe`(pid 37352)와 `cmd.exe`(pid 11296)를 끈 뒤, 워크트리와 브랜치 `docs/admin-design`을 지웠다. 휴지통(`.claude/worktrees/.tidy-trash/`)에는 `admin-design~~.venv` 등이 남았다. `charset_normalizer`의 `.pyd`에서 액세스가 거부되었고, 도구가 쥔 프로세스를 찾지 못했다. 그 밖의 워크트리(`05-full-run-rerank`, `13-first-judge-run` 등은 쥔 프로세스, `10-public-docs-questions`는 바뀐 파일)는 도구가 남겼고 보고만 했다.
- `EnterWorktree`(name `admin-screens`)로 들어가 `git switch -c docs/admin-screens origin/dev`로 브랜치를 땄다. 그때 `HEAD`는 `b6021ee`였다. Docker는 29.9.2로 떠 있었다.
- 스킬 1단계: `claude plugin list`에서 `frontend-design@claude-plugins-official` 1.1.1이 user 범위로 `enabled`였다. 설치와 `/reload-plugins`는 돌지 않았다.
- 스킬 2단계: 디자인 시스템 아티팩트를 `paths` 없이 읽은 머리가 "owned by you"였다. 판은 `1795631875-90df`다. 이어 `project/README.md`, `project/tokens.json`, `project/guidelines/web-design.md`를 읽었다.
- 근거 문서: ADR 0024~0027, `.scratch/admin/plan.md`, `docs/agents/issue-tracker.md`의 화면 디자인 절, 앞 일지(`2026-11-26-1805-ui-design-skill-port.md`)의 "다음", agent-os의 `.scratch/admin-login/design/README.md`와 `screens-prompt.md`, `GLOSSARY.md`, 킥오프 입력 5절을 읽었다.

## 조사

사람이 줄 참고가 없다고 해서(아래 "방향"의 호출 1) 서브에이전트 둘에게 웹 조사를 맡겼다. 두 보고는 세션 기록에 있고 `uv run python tools/extract_asks.py agents <세션 기록>`으로 꺼낼 수 있다. 보고가 제품마다 적은 읽은 정도를 옮긴다.

- **원천·동기화·토큰 쪽**(에이전트 1): Airbyte(공식 저장소 `airbytehq/airbyte-platform` main `63d665f`의 `airbyte-webapp/src/` 아래 소스와 문서), Onyx(공식 저장소 소스와 문서), Fivetran(공식 문서. 소스는 닫혀 있다). 세 제품 모두 갈무리를 보지 못했다. Fivetran 문서의 이미지 주소는 앱 안 브라우저에서 사이트로 가는 것이 막혔다. 토큰을 한 번만 보이는 모양은 GitHub 문서로 보탰다.
- **문서·검색 시험·대시보드 쪽**(에이전트 2): Dify(`langgenius/dify` main `df053963e4`의 소스와 docs.dify.ai 문서, 갈무리 둘), RAGFlow(`infiniflow/ragflow` main `ae15da0ae8`의 소스와 저장소 문서, 갈무리 넷), Algolia(공식 문서와 보관된 옛 문서, 옛 문서의 갈무리 둘. 지원 문서는 403으로 막혔다), Meilisearch Cloud(공식 문서, 갈무리 다섯). 넷째 제품은 Kibana 대신 Meilisearch로 바꿨다고 보고가 적었다. RAGFlow는 갈무리의 "Enable" 열이 지금 소스에는 없다는 판 차이도 적었다.

갈무리가 없는 화면은 소스의 배치 속성과 문서 글로 판단했다. 공통 규칙과 갈래, 가져오지 않을 것은 시작 프롬프트 `.scratch/admin/design/screens-prompt.md`의 "참고 디자인"에 옮겼다.

바로잡음: 아래 호출 3의 질문 글은 "갈무리(스크린숏)는 RAGFlow와 Meilisearch 것만 봤습니다"라고 적었다. 보고를 보면 Dify(둘)와 Algolia(옛 문서의 둘)의 갈무리도 봤다. 사용자에게 보인 글이라 아래 인용은 그대로 두고 여기 적는다. 시작 프롬프트의 "참고 디자인"은 처음부터 네 제품의 갈무리 수를 바르게 적었다. 고른 방향은 이 문장에 기대지 않는다.

## 방향

질문은 `AskUserQuestion`으로 올렸다. 질문 글과 선택지의 라벨·설명은 `uv run python tools/extract_asks.py asks <세션 기록>`으로 꺼내 글자 그대로 옮겼고, 미리보기(글자로 그린 배치)는 옮기지 않았다. 사용자가 고른 것은 `> 사용자:` 줄에 적는다.

**호출 1 (참고 디자인).** "rag-engine 관리자 페이지의 새 화면(현황, 원천, 문서, 검색 시험, 토큰)을 그릴 때 배치를 참고할 디자인이 있나요? 색·글꼴·틀은 agent-os 디자인 시스템과 agent-os 관리 화면을 그대로 쓰고, 참고는 새 화면의 배치와 문구에만 씁니다."

- "없다, 찾아 달라 (Recommended)": 같은 분야(검색·색인 서버의 관리 화면, 설치형 운영 도구)에서 디자인으로 이름난 제품 셋~다섯을 웹에서 찾아 공통 규칙을 뽑고, 출처와 함께 보여 드린 뒤 방향을 고르시게 합니다.
- "있다, 적어 주겠다": 제품 이름, 주소, 화면 갈무리 가운데 아는 것을 다음 메시지(또는 '기타' 칸)에 적어 주시면 거기서 규칙을 뽑습니다. 셋보다 적으면 웹에서 채웁니다.

> 사용자: "없다, 찾아 달라 (Recommended)"

**호출 2 (문구 말투).** 조사가 도는 동안 물었다. "관리자 페이지 화면에 뜨는 문구(제목, 설명, 알림, 확인 창)를 어떤 말투로 쓸까요? agent-os 관리 화면은 "로그인하지 못했다"처럼 -다로 끝나고, 이 저장소의 ADR 0024는 동기화 취소 확인 창 문구를 "이미 반영된 문서는 그대로 남습니다"처럼 -습니다로 적어 두었습니다."

- "-습니다 (Recommended)": "로그인하지 못했습니다", "동기화를 취소합니다"처럼 씁니다. ADR 0024가 적은 확인 창 문구와 그대로 맞고, 국내 관리 화면에서 흔한 말투입니다. agent-os 화면과는 말투가 달라집니다.
- "-다 (agent-os와 같게)": "로그인하지 못했다", "동기화를 취소한다"처럼 씁니다. agent-os에서 확정한 로그인·계정 화면 문구를 글자 그대로 옮길 수 있습니다. ADR 0024의 확인 창 문구는 "그대로 남는다"로 바꿔 쓰게 됩니다.

> 사용자: "-습니다 (Recommended)"

**호출 3 (질문 넷).** 두 조사를 합쳐 올렸다.

질문 1 (참고 방향). "관리자 페이지 그림의 바탕으로 어느 방향을 삼을까요? 참고로 일곱 제품(Dify, RAGFlow, Algolia, Meilisearch, Airbyte, Onyx, Fivetran)의 화면 코드와 문서를 읽었고, 갈무리(스크린숏)는 RAGFlow와 Meilisearch 것만 봤습니다."

- "공통 규칙 + 갈래별 안 (Recommended)": 아래 인용의 설명.
- "Onyx를 가깝게 따름": 같은 '문서 검색 서버의 관리 화면'이라 가장 가깝습니다. 원천은 종류별로 묶은 카드 줄이고, 줄을 펼치면 최근 실행이, 옆 패널에는 기록이 뜹니다. 현황은 따로 된 상태 화면입니다. 화면마다 안을 하나만 그립니다.
- "Airbyte·Fivetran을 따름": 데이터를 옮기는 도구의 화면입니다. 원천은 표로 보이고, 상세 화면 머리 오른쪽에 일정·지금 동기화·일시 중지가 한 줄로 섭니다. 동기화 기록은 따로 된 탭에 시간 순으로 쌓입니다. 문서와 검색 시험 화면은 Dify·RAGFlow를 따릅니다.

> 사용자: "공통 규칙 + 갈래별 안 (Recommended)" — 설명: 셋 이상이 함께 쓴 규칙을 바탕에 둡니다. 추가 단추는 목록 오른쪽 위, 상태는 색과 아이콘·글자를 함께 쓰고, 원천이나 문서를 누르면 따로 된 상세 화면으로 갑니다. 검색 결과 위에는 결과 수와 걸린 시간, 점수는 숫자로 보입니다. 제품마다 갈린 배치(목록 모양, 기록 자리, 원문과 조각의 배치)는 안으로 나눠 그립니다.

질문 1의 "갈무리는 RAGFlow와 Meilisearch 것만"은 틀렸다(위 "조사"의 바로잡음).

> 사용자: "현황·원천·문서·검색 시험 (Recommended)" — 설명: 킥오프가 0.1 화면으로 적은 넷입니다. 로그인, 비밀번호 정하기, 계정, 내 비밀번호 바꾸기는 agent-os에서 이미 고르고 확정한 화면을 이 제품의 이름과 메뉴로 옮깁니다. 토큰도 계정 화면과 같은 표·⋯ 메뉴·확인 창 모양으로 한 안만 그립니다.

질문 3 (와이어프레임). "배치만 회색 상자로 먼저 보는 와이어프레임 차례를 둘까요?"

- "와이어프레임 먼저": 아래 인용의 설명.

> 사용자: "와이어프레임 먼저" — 설명: 안 셋을 회색 상자로 그려 배치만 고르신 뒤, 고른 안만 완성 화면으로 그립니다. 배치를 더 가볍게 견줄 수 있지만 고르는 차례가 한 번 늘어납니다.

질문 4 (넣지 않을 것). "참고 제품에는 있지만 rag-engine 화면에는 넣지 않으려는 것들입니다. 이대로 뺄까요? (① 질문 기록과 검색 횟수 ② 조각 고치기·더하기·끄기 ③ 검색 시험에서 MCP 검색 도구에 없는 칸 ④ 가져오는 원천의 문서를 지우는 메뉴 ⑤ 요금제·체험판 표시와 로고·브랜드 색 ⑥ 그룹 단위 권한)"

- "모두 뺀다 (Recommended)": 아래 인용의 설명.
- "검색 시험은 질문과 지식베이스만": 위 여섯을 빼는 것은 같고, 검색 시험에서 결과 수·갱신일·최소 점수 칸까지 뺍니다. 화면은 가장 단순해지지만, MCP 클라이언트가 그 칸을 넣었을 때의 결과는 화면에서 시험해 볼 수 없습니다.

> 사용자: "모두 뺀다 (Recommended)" — 설명: ①은 질문 내용을 남기지 않는다는 원칙 V 때문에, ④는 가져온 문서는 원천에서 지워야 하기 때문에(원칙 VI) 뺍니다. ⑥은 역할이 admin과 reader 둘뿐이라 뺍니다. 검색 시험의 칸은 MCP 검색 도구와 같게 질문, 지식베이스, 결과 수, 갱신일 범위, 최소 점수만 둡니다.

이 답으로 시작 프롬프트 `screens-prompt.md`를 썼고, 스킬 4단계대로 `frontend-design` 스킬을 브리프(시작 프롬프트와 저장소 규칙)와 함께 불렀다. 그 스킬이 권한 것과 저장소 규칙이 부딪친 일곱 자리(색, 글꼴, 고정폭 글자, 숫자 칸, 움직임, 갈무리로 다듬기, 첫 화면의 히어로)는 `frontend-design-conflicts.md`에 적었고, 모두 저장소 규칙을 따랐다.

## 이름

와이어프레임 열둘을 올리고 안을 고르는 질문(아래 "고르기"의 호출 4)을 올렸을 때, 사용자는 답하는 대신 메시지를 보냈다. 그 메시지들과 그 뒤에 바꾼 이름을 차례로 적는다.

> 사용자: "현황이 대시보드야? 원천은 지식베이스야?"

현황은 흔히 대시보드라고 부르는 첫 화면이 맞고, 원천은 지식베이스가 아니라고 답했다(원천은 문서를 가져오는 곳이고, 지식베이스는 그 문서로 만든 검색용 색인이다).

> 사용자: "대시보드로 하면 안되나?"

바꿀 수 있다고 답했다. 용어집이 피하라고 적은 것은 관리자 페이지 전체를 대시보드로 부르는 일이었고, 그 까닭이 "현황 화면 하나만 뜻하는 말로 읽힌다"여서 첫 화면 하나의 이름으로 쓰는 것과 부딪치지 않는다.

> 사용자: "색인 판도 색인 버전으로 하는게 맞지 않아? 그리고 원천의 종류는 데이터베이스, 폴더 경로, 파일, 수집 API 등이 되어이야하는거 아닌가?"

둘 다 맞다고 답했다. 색인 판을 색인 버전으로 바꾸는 일은 사용자가 2026-11-19에 이미 골랐는데(일지 `2026-11-19-0025-glossary-ask-remaining-names.md`), 이 세션이 그 결정을 확인하지 않고 옛 이름으로 그렸다. 용어집의 판 항목은 그 이름 바꾸기를 맡은 형제 브랜치(`glossary-release-number-names`)가 고치므로 이 PR은 화면과 시작 프롬프트에서만 "색인 버전"으로 적는다.

> 사용자: "바꾸고, 원천도 원천 데이터로 바꾸는건 어때?"

이름 셋(현황은 대시보드, 색인 판은 화면에서 색인 버전, 원천의 종류는 서버 폴더·데이터베이스·수집 API·파일 올리기)을 바꾸고, "원천 데이터"는 문서가 있는 곳이 아니라 문서의 내용으로 읽혀 권하지 않는다고 답했다. `domain-modeling` 스킬을 불러 용어집과 ADR을 고쳤다(아래 "반영한 것").

> 사용자: "원천 그대로"

그래서 "원천"은 그대로 두고, 용어집 원천 항목의 피할 말에 "원천 데이터"를 더했다.

완성 화면을 그린 뒤 확정을 묻자(아래 "고르기"의 호출 7) 사용자가 이름 둘을 더 바꾸자고 하고 갱신일을 물었다.

> 사용자: "상태를 도는중 말고 실행중? 이나 색인중?으로 바꾸고 반영됨은 그냥 성공? 으로 바꾸는게 어때? 그리고 검색 시험에서 갱신일은 뭐야?"

**호출 8 (질문 셋).**

질문 1 (도는 중). "원천 목록의 "마지막 동기화" 칸에 적힌 "12분째 도는 중"을 무엇으로 바꿀까요? 같은 원천의 상태 배지와 대시보드는 이미 "동기화 중"으로 적혀 있습니다."

- "동기화 중 (Recommended)": 아래 인용의 설명.
- "실행 중": 흔히 보는 말입니다. 배지의 "동기화 중"까지 "실행 중"으로 바꿔야 말이 하나가 됩니다.
- "색인 중": 동기화는 폴더 목록을 읽고 지운 파일을 빼는 일도 하는데, 이 말은 그 일을 빼고 좁게 읽힙니다. 문서 상태의 "수집 중"과도 헷갈립니다.

> 사용자: "동기화 중 (Recommended)" — 설명: "12분째 동기화 중"이 됩니다. 배지와 같은 말이라 한 상태를 한 말로 읽습니다.

질문 2 (반영됨). "문서 상태 배지의 "반영됨"(문서가 지금 검색 색인에 들어가 검색되는 상태)을 무엇으로 바꿀까요? 바꾸면 용어집의 색인 상태 값과 문서 목록, 문서 화면, 대시보드의 같은 말을 함께 고칩니다."

- "성공 (Recommended)": 아래 인용의 설명.
- "색인됨": 지금 색인에 들어 있어 검색된다는 뜻이 그대로 보입니다. "실패"와의 짝은 "성공"보다 덜 맞습니다.
- "반영됨 그대로": 용어집과 화면을 바꾸지 않습니다.

> 사용자: "성공 (Recommended)" — 설명: "실패"와 짝이 맞아 가장 쉽게 읽힙니다. 다만 "지금 검색에 들어 있다"보다 "처리가 잘 끝났다"로 읽혀서, 문서 화면의 줄은 "default 색인 버전 3에 들어갔습니다"처럼 풀어 씁니다. 동기화 기록의 "끝남"은 실패한 문서가 섞여도 끝난 동기화라 그대로 둡니다.

화면에는 "default 색인 버전 3에서 검색됩니다"로 적었다. 설명의 "들어갔습니다"와 글자는 다르고 뜻은 같다.

질문 3 (갱신일). "검색 시험의 조건 칸과 문서 목록의 "갱신"(문서가 마지막으로 고쳐진 날. 서버 폴더는 파일의 수정 시각, 수집 API는 보낸 시스템이 넘긴 값)을 어떻게 할까요?"

- "이름 두고 풀이 달기 (Recommended)": 검색 시험의 갱신일 칸 아래에 흐린 줄 "문서가 마지막으로 고쳐진 날입니다. 서버 폴더는 파일의 수정 시각입니다."를 달고, 용어집에 갱신일 항목을 더합니다. PRD, MCP 검색 결과 설명, 릴리스 노트가 이미 쓰는 말이라 이름은 그대로 둡니다.
- "수정일로 바꾸기": 윈도 탐색기의 "수정한 날짜"와 같아 바로 읽힙니다. 다만 PRD, 명세, 릴리스 노트의 갱신일까지 저장소 전체를 바꾸어야 하고, PRD를 고치는 일은 따로 승인을 받아야 합니다.

> 사용자: "이름 두고 풀이 달기 (Recommended)로 하는데 이게 검색 조건에 있는 이유가 뭐야?"

검색 조건에 둔 까닭은 MCP 검색 도구가 같은 조건을 받기 때문이라고 답했다. core 명세의 사용자 이야기 17이 "그룹과 갱신일 기간으로 결과를 거를 수 있기를… 특정 부서나 최근 문서만"을 적고, 검색 시험은 MCP 검색 도구와 같은 칸을 둔다(호출 3의 질문 4). 값은 서버 폴더가 파일의 수정 시각으로 채우고(source-sync 명세 153줄), 수집 API는 보내는 쪽이 `updated_at`으로 넘긴다(core 명세 125줄). 그래서 화면의 풀이 줄에 "MCP 클라이언트가 최근 문서만 찾을 때 넣는 조건과 같습니다."를 더했다.

- "B: 조각 목록과 정보 열": 넓은 왼쪽에 '조각 86'과 '파싱 결과' 탭, 오른쪽 좁은 열에 문서 정보와 동작이 섭니다. 파싱 결과와 조각을 한꺼번에 보지는 못합니다.
- "C: 목록 위 오른쪽 패널": 목록에서 줄을 누르면 오른쪽에 패널이 겹쳐 열립니다. 실패 사유와 다시 수집을 빨리 보지만, 조각을 크게 보려면 문서 화면으로 가야 합니다.

선택지에 없는 답을 사용자가 직접 썼다. 원본을 어떻게 보일지는 호출 6으로 다시 물었다.

질문 4 (검색 시험). "검색 시험 화면은 어느 안으로 완성할까요? 질문 칸, 조건, 결과를 어떻게 놓는지가 다릅니다."

- "B: 위 검색칸과 조건 열 (Recommended)": 아래 인용의 설명.
- "A: 반반": 왼쪽 절반에 여러 줄 질문과 조건, 오른쪽 절반에 결과 카드가 섭니다. 결과 폭이 좁아 조각 글이 길게 접힙니다.
- "C: 결과 표": 결과를 표(순위, 점수, 문서, 근거 위치, 조각 첫 줄)로 모으고 줄을 펼쳐 전체 글을 봅니다. 점수를 견주기 쉽지만 글을 읽으려면 줄마다 펼쳐야 합니다.

> 사용자: "B: 위 검색칸과 조건 열 (Recommended)" — 설명: 맨 위에 한 줄 질문 칸, 왼쪽 좁은 열에 조건, 오른쪽 넓은 자리에 결과 카드가 섭니다. 조각 글이 넓은 폭으로 읽힙니다.

**호출 6 (문서 원본).** "문서 화면에서 원본 문서를 어떻게 보일까요? 지금 관리 API에는 원본을 내주는 요청이 없어서, 원본을 보이려면 그 요청을 하나 더하고 ADR 0024에 이력을 달아야 합니다. 올린 문서는 서버가 보관한 원본을 쓰고, 서버 폴더의 문서는 그 폴더에서 읽어 옵니다."

- "두 칸에 원본 탭 (Recommended)": 아래 인용의 설명.
