# source-sync 설계: 원천의 갈래와 동기화의 실행을 정한다 · 2026-11-20

release-image의 마지막 티켓(08)을 병합한 세션이 낸 지시문으로 연 세션의 기록이다(Fable 5.2 / xhigh). 시작 프롬프트는 `/grill-with-docs source-sync`이고, 브랜치는 `docs/source-sync`(설계를 쓰는 면제 PR), 작업은 워크트리 `source-sync`에서 했다. 준비, 사용자가 넘긴 것, 확인한 것, 물은 것과 답, 반영한 것을 차례로 두고, 그 뒤의 절은 일이 일어난 차례대로 덧붙인다.

## 준비

- 주 체크아웃(dev)에서 시작해 세션 제목을 바꾸고 `EnterWorktree`로 `source-sync`에 들어갔다. 브랜치는 `git switch -c docs/source-sync --no-track origin/dev`로 새로 땄다. 선례(release-image 설계 일지)는 앱이 만든 브랜치의 이름을 `git branch -m`으로 바꿨는데 이 세션은 새 브랜치를 따서, 앱이 만든 `worktree-source-sync` 브랜치가 로컬에 남았다(`git branch --list`). 원격에는 없고 병합된 브랜치를 치우는 `tidy-checkouts`가 받는다.
- 워크트리는 3cd84f5에서 섰고, 인터뷰 도중 `git fetch origin` 뒤 `git merge --ff-only origin/dev`로 5de36b6까지 빨리 감았다(`git reflog`).
- `grill-with-docs`가 `grilling`과 `domain-modeling`을 불렀다.
- `uv run python tools/sibling_overlap.py`는 가상 환경을 처음 만드느라 120초 제한을 넘겨 배경으로 넘어갔고, 끝난 뒤 출력 파일로 봤다. 종료 0이고 ADR 번호 겹침이 없으며, 형제의 헌법 버전 최고는 1.5.6이다(열린 PR 87). 그래서 이 PR은 헌법 문서를 고치지 않는다("반영한 것").

## 확인한 것

사실은 서브에이전트 둘이 나란히 찾았고, 보고가 붙인 근거의 종류를 괄호에 옮긴다. 이 세션이 직접 읽은 것은 "이 세션이 읽었다"로 적는다. 줄 번호는 3cd84f5 기준이다.

### 지금 코드 (서브에이전트 보고 1. 코드만 읽었고 손으로 친 명령은 `git log --oneline -1` 하나다)

- **원천 표.** 칸은 `id`, `name`(유일), `kind` 셋이고 제약은 `CHECK (kind IN ('push'))` 하나다. 설정, 일정, 연결 정보, 만든 시각 같은 칸은 없다(코드를 읽었다: 마이그레이션 `0001` 57~63줄, `src/rag_engine/adapters/postgres/tables.py` 41~48줄). 도메인의 `SourceKind`도 값이 `PUSH` 하나다(`src/rag_engine/domain/entities.py` 22~25줄). 기본 원천 `default`는 `migrate`가 만든다(`src/rag_engine/app/default_records.py` 24, 58줄).
- **문서 표.** `UNIQUE(source_id, key)`이고 상태는 `received`, `parsed`, `failed` 셋이다. 내용 해시 칸은 `content_hash`(원본 바이트의 sha256), 임시 삭제 시각은 `deleted_at`, 완전히 지운 표시는 `purged_at`이다. 원천 쪽 변경 확인값을 두는 칸은 없다(코드를 읽었다: `0001` 124~149줄, `src/rag_engine/app/ingest.py` 182줄).
- **삭제 보관함과 삭제 기록.** 보관함은 조각 단위의 `archived_chunks` 표다. 삭제 기록의 표는 따로 없고 `purged_at`이 채워진 문서 행이 그 노릇을 한다. `src` 아래에서 `purged_at`을 채우는 코드는 없다(`purged_at=[a-z]`로 Grep했다). 시험 지원 코드의 주석이 "core에는 정리 작업이 없어" 시험이 SQL로 직접 쓴다고 적는다(`tests/support/pipeline.py` 169, 183줄).
- **작업 표.** `document_id`가 `NOT NULL`이라 문서에 매이지 않은 작업(원천 동기화)을 지금 모양으로는 넣을 수 없다. 작업 종류는 `index_document` 하나이고 `process_job`은 종류로 가르지 않는다(코드를 읽었다: `0001` 191~217줄, `src/rag_engine/worker/processing.py` 198~217줄).
- **플러그인 인터페이스.** 파서는 있다(`src/rag_engine/domain/parsing.py`, `PARSER_INTERFACE_VERSION = "1.0.0"`, entry point 그룹 `rag_engine.parsers`, 인터페이스 버전의 앞자리가 다르면 `parser_rejected`를 남기고 뺀다). 커넥터와 변환의 Protocol은 없고, `src/rag_engine/domain/ports.py` 8~9줄의 주석이 "처음 쓰는 source-sync가 만든다"고 적는다(`[Tt]ransform|[Cc]onnector`로 `src`를 Grep해 그 주석만 나왔다).
- **수집 유스케이스.** `ingest_document`는 원천을 늘 `get_source(DEFAULT_NAME)`으로 읽는다(`src/rag_engine/app/ingest.py` 167줄). 요청의 칸은 `filename`, `data`, `key`, `group`, `metadata`, `updated_at`이고 원천을 고를 길이 없다. 같은 (원천, 키)가 다시 들어오면 묘비 다시 쓰기, 되살림, 내용 바뀜, 그룹 바뀜, 실패 뒤 다시 넣기, 그대로의 차례로 가른다(326~348줄). 건너뛰는 판단은 원본 바이트를 받아 sha256을 계산한 뒤에만 한다.
- **변환 자리.** 코드에 없다. 원본을 읽은 바로 다음 줄이 파싱이다(`src/rag_engine/app/index_document.py` 209~211줄). 자리 표시도 없다.
- **삭제 유스케이스.** `delete_document`도 원천이 `DEFAULT_NAME`으로 고정이다. `deleted_at`을 쓰고 조각을 보관함으로 옮기며 원본은 지우지 않는다(`src/rag_engine/app/delete_document.py` 25~48줄). 보관함을 비우는 유스케이스는 없다.
- **작업자.** 꺼내는 질의는 `ORDER BY run_after, id LIMIT 1 FOR UPDATE SKIP LOCKED`다(`src/rag_engine/adapters/postgres/job_queue.py` 153~182줄). LISTEN/NOTIFY와 폴링(`RAG_WORKER_POLL_SECONDS`, 기본 5)을 함께 쓴다. 동시 처리 수는 `RAG_WORKER_CONCURRENCY`(기본 2), 재시도는 최대 6번에 대기 시간이 `30초 × 4^(시도−1)`이고 상한이 3600초다(`src/rag_engine/app/retry_policy.py` 11~37줄, `src/rag_engine/adapters/settings.py` 67~71줄). 정해진 때에 무엇을 돌리는 장치는 없다(`cron|periodic|scheduler|interval`로 Grep했고 worker 모듈 넷을 읽었다).
- **REST 경로와 인증.** 접두는 `/api/v1`이다. `/health`만 인증 밖이고, `reader` 토큰으로 `/mcp` 밖을 부르면 403이라 REST 경로는 모두 `admin` 토큰 전용이다(`src/rag_engine/server/auth.py` 57~73줄). 수집 API는 multipart로 `file`, `key`, `group`, `metadata`, `updated_at`을 받고 삭제는 같은 경로의 DELETE에 `key` 쿼리다(`src/rag_engine/server/ingest_api.py` 46~79줄). 원천을 만들거나 고치는 관리 API는 없고, `Catalog` 포트의 원천 메서드는 `add_source`, `get_source`, `get_source_by_id` 셋이다(`src/rag_engine/domain/ports.py` 138~150줄).
- **관리 명령.** `serve`, `migrate`, `worker`, `bootstrap-token`, `ingest` 다섯이다. `ingest <경로>`는 폴더를 재귀로 걸어 확장자가 `.pdf`, `.docx`, `.hwpx`인 파일만 넣고, `resolve()`한 경로가 폴더 밖이면 거르며, 키는 폴더 기준 상대 경로다. 지워진 파일을 반영하는 단계는 없고 파일의 수정 시각을 쓰지 않는다(`src/rag_engine/adapters/ingest_command.py` 75~87, 126~133줄).
- **설정.** `RAG_DELETED_RETENTION_DAYS`(기본 30)는 정의만 있고 읽어 쓰는 실행 코드가 없다(`src/rag_engine/adapters/settings.py` 47줄).
- **파일 저장소.** 원본은 `RAG_DATA_DIR/blobs/<문서 UUID>/<원본 UUID>`에 둔다. 지우지 못한 원본은 `orphan_blob_left`를 남기고 고아로 둔다(`src/rag_engine/app/ingest.py` 218~231, 583~592줄). 고아 원본을 훑어 찾는 코드는 없다.
- **파서의 실패 분류.** 암호가 걸린 PDF는 `EncryptedDocumentError`가 `encrypted_document`(영구 실패)로 바뀌고, ZIP 계열(DOCX, HWPX)은 부모 프로세스의 사전 검사가 같은 코드로 판정한다(`src/rag_engine/adapters/parsers/pdf_parser.py` 51~58줄, `runner.py` 108~109줄, `zip_guard.py` 3~5줄). 글자가 없는 스캔본은 예외 없이 빈 목록이 되어 조각 0개로 색인 상태 `indexed`가 될 것으로 본다(보고는 어림이라고 적었다. 청커가 빈 블록에 빈 목록을 내는지는 그 보고가 읽지 않았다). "건너뜀"에 해당하는 상태나 오류 코드는 없다.
- **단독 compose.** 서버와 작업자는 이름 붙은 볼륨 `data:/data` 하나만 붙이고 둘 다 `read_only: true`다. 호스트 폴더를 서버나 작업자에 붙이는 줄은 없다(`deploy/standalone/compose.yaml` 143~144, 164~165줄). compose가 정하는 값은 `RAG_DATABASE_URL`, `RAG_DATA_DIR=/data`, `RAG_DEFAULT_EMBEDDING_URL=http://embedding:80`이다(23~26줄).
- **비밀 값.** 데이터베이스에 드는 비밀은 인증 토큰의 sha256 해시 하나다. 연결 정보를 암호화하는 코드와 그것을 담을 칸은 없다. `cryptography`는 직접 의존이 아니고 `uv.lock`에 50.0.2가 전이 의존으로 들어 있다(`pdfplumber` → `pdfminer-six`, `mcp` → `pyjwt[crypto]`).

### 선례와 라이브러리 (서브에이전트 보고 2. 웹 검색 요약만으로 쓴 문장은 없고, 요약에서 본 것은 원문을 받아 대 본 것만 적었다고 보고했다)

- **cron 표현식 라이브러리 셋.**
  - cronsim 2.8(2026-11-05 등록). BSD(GitHub 표시는 BSD-3-Clause)이고, 의존 패키지가 없으며, 파이썬 3.11 이상을 요구한다. 휠에 `cronsim/py.typed`가 있다(손: 휠을 메모리로 받아 파일 목록을 읽었다). 소유자는 개인 계정 `cuu508`이고 앞선 출시가 2.7(2025-10-21), 2.6(2024-12-04)이라 한 해에 한 번꼴이다. 2.0부터 `zoneinfo`와 함께 쓰게 설계됐고 일광 절약 시간 전환은 Debian cron과 같게 처리한다. 다섯 칸과 여섯 칸 표현식을 받고 틀린 표현식에는 `CronSimError`를 낸다(원문: `https://pypi.org/pypi/cronsim/json`, `https://raw.githubusercontent.com/cuu508/cronsim/2.8/README.md`와 `CHANGELOG.md`, `https://api.github.com/repos/cuu508/cronsim`).
  - croniter 7.0.0(PyPI 등록 2026-11-09). MIT이고 휠에 `py.typed`도 `.pyi`도 없다(손: 휠 파일 목록). 따로 내는 `types-croniter`는 6.2.4용까지만 있다. 6.0.0(2024-12-17)의 README가 유지 관리 종료를 선언했고, 6.1.0(2026-03-14)부터 `pallets-eco/croniter`로 옮겨 다시 나온다. 7.0.0은 유효하던 표현식의 뜻이 바뀌는 출시다(원문: `https://pypi.org/pypi/croniter/json`, 6.0.0과 6.1.0의 PyPI JSON, `https://raw.githubusercontent.com/pallets-eco/croniter/7.0.0/CHANGELOG.rst`).
  - APScheduler 3.11.3(2026-06-28). MIT이고 휠에 타입 정보가 없으며 `types-apscheduler`도 PyPI에 없다. `CronTrigger.from_crontab`은 다섯 칸만 받고 요일 숫자 0이 월요일이라 원래 crontab(0이 일요일)과 어긋난다고 소스의 경고가 적는다. 4.0은 시험판이다(원문: `https://pypi.org/pypi/apscheduler/json`, `https://raw.githubusercontent.com/agronholm/apscheduler/3.11.3/src/apscheduler/triggers/cron/__init__.py` 123~153줄).
- **이 저장소의 의존성과 경계.** `pyproject.toml`과 `uv.lock`에 `croniter`, `cronsim`, `apscheduler`는 없다(손: 대소문자 무시 Grep 0건). import-linter의 forbidden 계약은 `domain`과 `app`이 서드파티 열일곱을 import하지 못하게 막고(`pyproject.toml` 141~166줄), 같은 자리의 주석이 "목록에 없는 서드파티(uuid6)는 막지 않는다"고 적는다. 그래서 `cronsim`은 목록에 더하지 않는 한 이 계약이 막지 않는다(어림: 계약 문구에서 끌어낸 해석이고 `lint-imports`를 돌려 보지 않았다).
- **다른 제품의 일정.** Elastic 커넥터와 Amazon Kendra는 cron 표현식을 받는다. Onyx("Refresh Every" 기본 30분, 없어진 문서를 지우는 "Prune Every" 기본 7일), Azure AI Search(간격 5분~24시간과 시작 시각), RAGFlow(새로 고침 간격)는 간격을 받는다. Amazon Bedrock Knowledge Bases는 수동이 기본이고 관리형 커넥터는 매일, 매주, 매월 가운데 고른다(원문: `https://docs.onyx.app/admins/connectors/overview.md`와 Onyx 저장소의 `app_configs.py`, Elastic 8.19의 `update-connector-scheduling-api`, Microsoft Learn `search-howto-schedule-indexers`, AWS 문서 `kendra/latest/APIReference/API_CreateDataSource.html`와 `bedrock/latest/userguide/kb-managed-sync.html`, `https://ragflow.io/docs/add_data_source/add_to_knowledge_base_and_sync`). Onyx의 가지치기 기본을 웹 검색 요약은 30일이라고 했으나 원문과 달라 보고가 채택하지 않았다.
- **대량 삭제를 막는 장치.** rclone bisync는 `--max-delete`가 백분율이고 기본이 50%이며, 넘으면 아무것도 바꾸지 않고 멈춘다. 한쪽 목록이 비어 있으면 실패하고, `--check-access`는 양쪽에 표식 파일이 보이는지 먼저 본다. Unison의 `confirmbigdel`(기본 켜짐)은 복제본 전체가 지워진 것처럼 보이면 확인을 받고 무인 모드에서는 멈추며, `mountpoint`는 적은 경로가 없으면 멈춘다. Microsoft Entra Connect는 한 번에 삭제 500건을 넘기지 못하게 하고, Algolia Crawler는 레코드가 지난번보다 10% 넘게 줄면 게시를 막는다. rsync `--max-delete`는 한도를 넘는 삭제를 건너뛴다(원문: rclone 저장소의 `docs/content/bisync.md`, Unison 저장소의 `src/globals.ml` 232~240줄과 `src/update.ml` 1261~1269줄, `MicrosoftDocs/entra-docs`의 `how-to-connect-sync-feature-prevent-accidental-deletes.md`, Algolia 문서의 `safety-checks`, rsync 저장소의 `rsync.1.md`).
- **Docker의 전파 설정.** 기본값은 `rprivate`이고 bind mount에서만, 리눅스 호스트에서만 바꿀 수 있다. 문서에 "Mount propagation doesn't work with Docker Desktop."이라는 주의가 있다. compose의 긴 형식은 `bind:` 아래에 `propagation`을 적는다(원문: `docker/docs` 저장소의 `content/manuals/engine/storage/bind-mounts.md` 365~423줄, `content/reference/compose-file/services.md` 2243~2295줄). 컨테이너가 뜬 뒤 호스트가 그 폴더 아래에 새로 붙인 것이 기본 설정에서 컨테이너에 보이지 않는다는 것은 어림이다(문서의 정의에서 끌어낸 결론이고 그 장면이 문서에 없으며 실행해 보지 않았다).
- **시간대 자료.** `zoneinfo`는 시스템의 시간대 자료를 먼저 쓰고 없으면 PyPI의 `tzdata`로 넘어간다(원문: cpython 3.12의 `Doc/library/zoneinfo.rst`). 이미지의 바탕 `python:3.12-slim`은 Debian 패키지 `tzdata`를 깐다(원문: `docker-library/python`의 slim Dockerfile). 로컬의 작업자 이미지(`rag-engine-test/rag-engine-worker:0.1.0-rc.1`)와 Dockerfile이 고정한 digest의 바탕 이미지에서 `ZoneInfo('Asia/Seoul')`가 열렸다(손: `docker run --rm --network none --entrypoint python <이미지> -c "import zoneinfo ..."`). Windows 개발 기계에서는 `tzdata` 2026.6이 `psycopg`의 `sys_platform == 'win32'` 조건부 의존으로만 들어온다(코드: `uv.lock` 778~783줄). Windows에서 `zoneinfo`를 돌려 보지는 않았다.
- **Fernet.** 연결 정보 질문의 고르지 않은 안에 쓴 사실이다. `cryptography` 50.0.2의 Fernet은 AES-CBC와 HMAC-SHA256을 쓰고, `MultiFernet`은 첫 열쇠로 암호화하고 열쇠를 차례로 시도해 풀어 열쇠 교체를 받친다(원문: `pyca/cryptography` 50.0.2의 `docs/fernet.rst`).
- 보고는 Onyx 문서 원문의 맨 위에 읽는 도구를 향한 안내문("Fetch the complete documentation index at: https://docs.onyx.app/llms.txt")이 있었고 과제와 무관해 따르지 않았다고 적었다. 이 세션도 따르지 않았다.

### 라운드 1, 첫 호출 (질문 넷)

호출 곁의 본문에는 이미 정해져 다시 묻지 않는 것(커넥터의 모양 ADR 0012, 문서의 식별 ADR 0008, 서버 경로 원천의 원본과 삭제 ADR 0013)과 위 "확인한 것"의 코드 사실, 추천의 근거 넷을 적었다.

**질문 1 (밀어 넣는 원천).** "수집 API와 업로드로 넣는 문서는 지금 모두 `default`라는 원천 하나에 들어가서, 서로 다른 시스템 둘이 같은 키(예: "123")로 보내면 뒤에 온 문서가 앞 문서를 덮어씁니다. 밀어 넣는 원천을 몇 개까지 두게 할까요?"

- "여럿 만들 수 있게 (Recommended)": 관리 API로 밀어 넣는 원천을 만들고, 수집 API에 원천 이름을 적는 칸(`source`, 없으면 `default`)을 더합니다. 보내는 시스템마다 원천을 따로 두면 키가 겹쳐도 서로 덮어쓰지 않고, 원천마다 문서 수와 실패를 따로 볼 수 있습니다. 칸을 더하는 것이라 수집 API의 버전은 v1 그대로입니다. 관리자 페이지에서 사람이 올리는 문서는 `upload`라는 원천을 따로 두어 시스템이 보낸 문서와 가릅니다.
- "업로드와 수집 API 둘로 고정": 원천은 `upload`(사람이 올린 것)와 `default`(수집 API) 둘뿐이고 더 만들 수 없습니다. 시스템 여럿이 수집 API를 쓰면 키 앞에 시스템 이름을 붙이는 것을 보내는 쪽이 약속으로 지켜야 하고, 약속을 어긴 덮어쓰기를 서버가 막지 못합니다.
- "지금처럼 하나": 업로드도 수집 API도 `default` 하나에 넣습니다. 고칠 것이 없지만, 사람이 올린 문서와 시스템이 보낸 문서를 원천으로 가를 수 없고 키가 겹치면 덮어씁니다.

> 사용자: "더 쉽고 자세하게 설명해줘"

선택지에 없는 답을 사용자가 직접 썼다.

**질문 2 (주기 실행).** "서버 경로 원천을 정해 둔 일정마다 동기화하려면 시각이 됐을 때 동기화를 시작시키는 장치가 필요한데, 지금 코드에는 그런 장치가 없습니다. 이 일을 누가 맡게 할까요?"

- "작업자가 맡는다 (Recommended)": 원천마다 '다음 실행 시각'을 데이터베이스에 적어 두고, 작업자가 대기열을 살필 때(지금 5초마다) 시각이 지난 원천의 동기화 작업을 넣습니다. 컨테이너가 늘지 않고, 작업자가 여럿이어도 데이터베이스의 행 잠금으로 한 번만 넣습니다. 작업자가 꺼져 있으면 일정도 멈추지만, 그때는 수집 자체가 돌지 않습니다. 다음 실행 시각을 서버가 알기 때문에 관리자 페이지가 보여 줄 수 있습니다.
- "일정 전용 컨테이너": 일정만 맡는 프로세스를 따로 띄웁니다. 역할은 분명하지만 단독 compose의 기본 컨테이너가 다섯에서 여섯으로 늘고, 그 컨테이너만 죽으면 수집은 멀쩡한데 일정만 조용히 멈춥니다.
- "서버 밖의 cron": 서버에는 '지금 동기화' 관리 API만 두고, 운영자가 설치한 기계의 cron(정해진 시각에 명령을 실행해 주는 운영체제 기능)에 그 API를 부르는 줄을 등록합니다. 서버 코드는 가장 적지만 일정을 관리자 페이지에서 볼 수도 고칠 수도 없고, 설치할 때 운영자가 손으로 할 일이 늘어납니다.

> 사용자: "관리자 페이지에서 스케줄러를 등록"

선택지에 없는 답을 사용자가 직접 썼다.

**질문 3 (건너뜀).** "암호가 걸린 파일은 지금 '실패'로 기록되고, 글자가 없는 스캔본은 조각 0개인 '성공'으로 기록됩니다. 킥오프 입력은 이 둘을 실패가 아니라 '건너뜀'으로 보여 주라고 했는데, 건너뜀을 어떻게 남길까요?"

- "문서 상태에 건너뜀을 더한다 (Recommended)": 아래 인용의 설명.
- "저장은 그대로, 보여 줄 때만 가른다": 데이터베이스에는 지금처럼 실패와 오류 코드로 남기고, 관리 API가 암호 문서의 오류 코드를 '건너뜀'으로 묶어 보여 줍니다. 표를 고치지 않지만, 같은 내용을 다시 넣으면 매번 다시 파싱해 다시 실패하고, 스캔본은 계속 성공으로 보입니다.
- "걸러진 파일까지 모두 문서로": 첫째 안에 더해, 수집 정책에 걸린 파일도 '건너뜀' 문서로 남깁니다. 어떤 파일이 왜 빠졌는지 파일마다 보이지만, 임시 파일이나 지원하지 않는 형식까지 문서 표에 쌓여 문서 수와 목록이 흐려집니다.

> 사용자: "문서 상태에 건너뜀을 더한다 (Recommended)" — 설명: 문서의 상태 값에 '건너뜀'과 사유(암호, 글자 없음)를 더합니다. 관리 API의 문서 목록에서 실패와 따로 세고, 같은 내용을 다시 넣어도 다시 파싱하지 않습니다(파일이 바뀌면 다시 봅니다). 수집 정책에 걸린 파일(지원하지 않는 형식, 크기 상한 초과, 제외 패턴)은 문서로 만들지 않고 동기화 기록에 사유별 개수만 남깁니다. 문서 상태는 MCP 검색 도구의 출력에 없는 값이라 검색 도구의 계약은 바뀌지 않습니다.

**질문 4 (변환의 모양).** "변환은 설치처가 자기 규칙(본문에 섞인 HTML 정리, 암호화된 첨부 풀기 같은 것)을 끼워 넣는 플러그인 자리이고, 한번 내면 버전을 올려야만 모양을 바꿀 수 있습니다. 변환이 문서 하나를 받아 무엇을 돌려주게 할까요?"

- "문서 하나를 하나로 (Recommended)": 원본 내용과 메타데이터를 받아 고친 것 하나를 돌려주거나 '이 문서는 넣지 않는다'고 답합니다. 파싱 직전에 파서와 같은 격리된 자식 프로세스에서 돌아, 설치처 코드에도 시간과 메모리 한도가 걸립니다. 저장해 두는 원본은 받은 그대로라, 변환을 고친 뒤에는 원천에서 다시 받지 않고 다시 파싱만 하면 됩니다. 문서 하나를 여럿으로 나누는 일(행에 딸린 첨부)은 그것을 처음 쓰는 SQL 원천(db-source)의 설계가 부모·자식 문서와 함께 정하고, 그때 메서드를 더합니다(더하는 것은 같은 major 버전에서 됩니다).
- "처음부터 하나를 여럿으로": 변환이 문서 목록을 돌려줍니다. 자식 문서의 키를 짓는 규칙, 부모가 지워질 때 자식을 지우는 규칙, 문서 표의 부모 칸을 지금 정해야 합니다. 쓰는 곳(SQL 원천) 없이 정한 모양이 1.0에서 맞지 않으면 인터페이스의 major 버전을 올려야 합니다.
- "이번에는 짓지 않는다": 아래 인용의 설명.

> 사용자: "이번에는 짓지 않는다" — 설명: 변환 인터페이스를 SQL 원천(db-source) 기능으로 넘기고 0.1에는 변환 자리를 두지 않습니다. 0.1에서 설치처가 자기 규칙을 끼울 길은 고친 문서를 수집 API로 직접 보내는 것뿐이고, 기능 계획의 범위(커넥터와 변환의 인터페이스를 짓는다)를 고쳐야 합니다.

추천과 다른 답이다. 추천은 "문서 하나를 하나로 (Recommended)"였다.

### 라운드 1, 둘째 호출 (질문 넷)

첫 호출의 답 가운데 둘("더 쉽고 자세하게 설명해줘", "관리자 페이지에서 스케줄러를 등록")은 선택지에 없는 답이라 설명을 보태 다시 물었다. 밀어 넣는 원천은 낱말 둘(원천, 키)을 풀고, 그룹웨어와 위키가 같은 키 "123"을 보내는 장면에서 세 선택지가 어떻게 달라지는지를 표(준비, 보내는 프로그램, 두 "123", 원천 목록 화면, 위키 연동을 끊을 때, 사람이 올린 파일)로 견줬다. 일정의 답은 운영자가 관리자 페이지에서 일정을 등록하고 고치며 서버가 그 일정을 데이터베이스에 보관한다는 뜻으로 받아들인다고 적고("서버 밖의 cron" 안은 빠진다), 남은 결정 하나(등록한 시각이 됐을 때 그것을 알아채고 동기화를 시작시키는 프로그램을 어디에 둘지)를 물었다. 화면은 admin이 만들고 이 기능은 그 화면이 부를 관리 API를 만든다고 적었다. 원천 삭제와 되살리기는 이 호출에서 처음 물었다.

**질문 5 (밀어 넣는 원천).** "그룹웨어와 위키처럼 서로 다른 시스템이 같은 키(예: "123")로 문서를 보내면 지금은 뒤에 온 문서가 앞 문서를 덮어씁니다. 밖에서 문서를 보내 주는 곳(밀어 넣는 원천)을 어떻게 나눌까요?"

- "시스템마다 원천을 따로 (Recommended)": 아래 인용의 설명.
- "업로드와 수집 API 둘로 고정": 원천은 `upload`(사람이 올린 것)와 `default`(수집 API로 온 것) 둘뿐이고 더 만들 수 없습니다. 시스템 여럿이 보낼 때는 키를 `groupware/123`처럼 짓는 것을 보내는 쪽이 약속으로 지켜야 하고, 한쪽이 어기면 덮어쓰기를 서버가 막지 못합니다. 연동 하나를 끊을 때는 그 시스템의 문서를 키로 골라서 지워야 합니다.
- "지금처럼 하나": 사람이 올린 파일도, 프로그램이 보낸 문서도 모두 `default` 하나에 들어갑니다. 고칠 것이 없지만, 키가 겹치면 덮어쓰고, 누가 넣은 문서인지 원천으로 가를 수 없습니다.

> 사용자: "시스템마다 원천을 따로 (Recommended)" — 설명: 운영자가 `groupware`, `wiki`처럼 원천을 만들고, 보내는 프로그램은 수집 API에 원천 이름 칸(`source`)을 적어 보냅니다. 같은 키 "123"이어도 원천이 다르면 서로 다른 문서로 남고, 원천마다 문서 수와 실패를 따로 보며, 연동을 끊을 때는 그 원천만 지우면 됩니다. 원천 이름을 적지 않으면 지금처럼 `default`에 들어가므로 지금 쓰는 방법은 그대로이고, 칸을 더하는 것이라 수집 API의 버전도 v1 그대로입니다. 사람이 관리자 페이지에서 올리는 파일은 `upload` 원천에 따로 모읍니다.

**질문 6 (일정을 돌리는 쪽).** "일정은 관리자 페이지에서 등록하고 서버가 데이터베이스에 보관하는 것으로 이해했습니다. 등록해 둔 시각(예: 매일 새벽 2시)이 됐을 때 그것을 알아채고 동기화를 실제로 시작시키는 프로그램은 어디에 둘까요?"

- "작업자 안에 둔다 (Recommended)": 아래 인용의 설명.
- "일정 전용 컨테이너를 더한다": 일정만 맡는 프로그램을 따로 띄웁니다. 역할은 분명하지만 단독 compose의 기본 컨테이너가 다섯에서 여섯으로 늘고 내려받을 이미지도 하나 늘며, 그 컨테이너만 죽으면 문서 처리는 멀쩡한데 일정만 조용히 멈춥니다.

> 사용자: "작업자 안에 둔다 (Recommended)" — 설명: 문서를 처리하는 작업자 프로그램이 5초마다 데이터베이스를 살필 때, 등록된 시각이 지난 원천이 있는지도 함께 보고 동기화를 시작시킵니다. 컨테이너가 늘지 않고, 작업자를 여럿 띄워도 데이터베이스의 행 잠금 덕분에 같은 일정이 한 번만 시작됩니다. 작업자가 꺼져 있으면 일정도 멈추지만, 그때는 문서 처리 자체가 되지 않으므로 따로 잃는 것이 없습니다.

**질문 7 (원천 삭제).** "관리 API로 원천 하나를 지울 때, 그 원천에서 들어온 문서들을 어떻게 할까요?"

- "문서도 함께 임시 삭제 (Recommended)": 아래 인용의 설명.
- "문서가 남아 있으면 거부": 문서가 하나라도 있는 원천은 지울 수 없고, 운영자가 문서를 먼저 지워야 합니다. 실수로 수만 건이 한 번에 검색에서 빠지는 일은 막지만, 서버 경로 원천은 문서를 지울 길이 원천 폴더를 비우는 것뿐이라 지우는 절차가 길어집니다.
- "원천만 지우고 문서는 남김": 문서는 검색에 그대로 남습니다. 그 뒤로는 원천에서 고치거나 지워도 반영할 길이 없는 문서가 되어 낡은 내용이 계속 검색되므로, 헌법 원칙 VI와 어긋납니다.

> 사용자: "문서도 함께 임시 삭제 (Recommended)" — 설명: 원천을 지우는 순간 그 원천의 문서가 모두 검색에서 빠지고, 보관 기간(기본 30일)이 지나면 문서와 원천을 완전히 지웁니다. 헌법 원칙 VI(원천에서 지운 문서는 색인에서도 지운다)를 원천 단위로 그대로 적용한 것입니다. 잠깐 쉬게 하려는 것이면 지우지 않고 쓰도록 '멈춤'(동기화만 끄고 문서는 검색에 남김)을 따로 둡니다.

**질문 8 (되살리기).** "지운 문서는 보관 기간 동안 되살릴 수 있게 보관해 두는데, 지금은 같은 키로 문서를 다시 넣어야만 되살아납니다. 관리 API에 '되살리기'를 어디까지 열까요?"

- "밀어 넣은 문서만 되살린다 (Recommended)": 아래 인용의 설명.
- "모든 문서를 되살린다": 서버 경로 원천의 문서도 API로 되살립니다. 다만 원천 폴더에 그 파일이 없으면 다음 동기화 때 다시 지워지므로, 되살린 문서가 일정에 따라 다시 사라지는 일이 생깁니다.
- "되살리는 API를 두지 않는다": 지금처럼 같은 키로 다시 넣을 때만 되살아납니다. 만들 것이 없지만, 실수로 지운 사람이 원본 파일을 다시 갖고 있어야 합니다.

> 사용자: "밀어 넣은 문서만 되살린다 (Recommended)" — 설명: 업로드와 수집 API로 넣었다가 지운 문서는 보관 기간 안에 관리 API 호출 하나로 되살립니다. 보관해 둔 조각을 되돌리고, 그사이 색인 판이 바뀌었으면 보관해 둔 원본으로 다시 색인합니다. 서버 경로처럼 서버가 가져오는 원천의 문서는 API로 되살리지 않고, 원천 폴더에 파일을 되돌려 놓으면 다음 동기화가 되살립니다. 원천에 없는 문서를 API로 되살려도 다음 동기화가 다시 지우기 때문입니다.

### 라운드 2, 첫 호출 (질문 넷)

서브에이전트 보고 2가 온 뒤에 올렸다. 호출 곁의 본문에는 cron 표현식의 풀이와 다른 제품이 일정을 받는 방식의 표, 라이브러리 후보 셋의 견줌, 대량 삭제 사고의 장면(서버 기계가 다시 켜진 뒤 공유 폴더가 붙지 않으면 컨테이너 안에서 빈 폴더로 보인다)과 다른 도구의 장치 두 갈래, 연결 정보와 폴더 붙이기의 풀이를 적었다.

**질문 9 (일정 적는 법).** "관리자 페이지에서 등록한 일정(예: 매일 새벽 2시, 30분마다)을 서버가 어떤 모양으로 받아 보관하고 계산할까요? 화면에서 어떻게 고르게 할지는 다음 기능(admin)이 정하고, 여기서는 서버가 보관하는 모양을 정합니다."

- "cron 표현식 (Recommended)": 아래 인용의 설명.
- "간격만": 'N분마다'와 선택 항목인 첫 시작 시각만 받습니다(Onyx, Azure AI Search, RAGFlow가 이 방식). 새 의존성이 없고 가장 단순하지만 '평일에만', '매달 1일에' 같은 일정을 적을 수 없고, 매일 새벽 2시는 '24시간마다, 첫 시작 02:00'으로 돌려 적어야 합니다.
- "매일·매주·간격 가운데 고르기": '매일 몇 시', '매주 무슨 요일 몇 시', 'N분마다' 세 가지 꼴을 우리가 정한 모양으로 받습니다(Amazon Bedrock의 관리형 커넥터가 매일·매주·매월 가운데 고르는 방식). 새 의존성이 없고 흔한 경우를 덮지만, 다음 실행 시각 계산을 직접 만들어 시험해야 하고 세 꼴 밖의 일정이 필요해지면 모양을 다시 넓혀야 합니다.

> 사용자: "cron 표현식 (Recommended)" — 설명: `0 2 * * *`(매일 02:00), `0 2 * * 1-5`(평일 02:00), `*/30 * * * *`(30분마다)처럼 다섯 칸으로 적는 표기를 관리 API가 받아 보관합니다. 조사한 제품 가운데 Elastic 커넥터와 Amazon Kendra가 이 방식이고, '평일 밤에만' 같은 조건을 그대로 적을 수 있습니다. 관리자 페이지는 '매일·매주·N분마다'를 고르면 표현식으로 바꿔 저장하게 만들 수 있습니다. 표현식 계산에는 cronsim 2.8(BSD 라이선스, 무료, 다른 패키지에 기대지 않음, 타입 정보 포함)을 새 의존성으로 들입니다. 치르는 값은 개인이 한 해에 한 번꼴로 내는 작은 라이브러리에 기대는 것이고, 계산하는 자리를 포트 뒤에 두어 나중에 다른 라이브러리로 바꿀 수 있게 합니다.

**질문 10 (대량 삭제).** "서버 경로 원천의 공유 폴더가 서버 기계에 붙지 않은 채로 동기화가 돌면, 서버에는 빈 폴더로 보여서 '파일이 전부 지워졌다'고 읽고 그 원천의 문서를 모두 검색에서 뺄 수 있습니다. 이런 사고에 어떤 안전장치를 둘까요?"

- "빈 목록이면 지우지 않는다 (Recommended)": 아래 인용의 설명.
- "비율 한도도 둔다": 첫째 안에 더해, 한 번의 동기화가 그 원천 문서의 절반 넘게 지우려 하면 삭제를 보류하고 운영자가 승인해야 반영합니다(Microsoft Entra Connect의 500건 한도, rclone bisync의 50% 한도와 같은 방식). 일부만 붙은 폴더까지 잡지만, 정말로 지운 문서가 승인 전까지 계속 검색되어 헌법 원칙 VI와 PRD의 우선순위 2(원천에서 지운 문서는 검색되지 않는다)가 미뤄지고, 승인하는 관리 API와 보류 상태가 늘어납니다.
- "안전장치를 두지 않는다": 목록대로 지웁니다. 폴더가 붙지 않으면 그 원천의 문서가 모두 검색에서 빠졌다가, 폴더가 다시 붙은 뒤의 동기화에서 되살아납니다. 만들 것이 없지만 그사이 검색 결과가 비어 보입니다.

> 사용자: "빈 목록이면 지우지 않는다 (Recommended)" — 설명: 원천 폴더가 없거나, 목록이 0건인데 색인에는 그 원천의 문서가 있으면 삭제를 반영하지 않고 그 동기화를 실패(사유: 원천을 읽을 수 없음)로 기록합니다. 공유 폴더가 붙지 않은 가장 흔한 사고를 잡습니다(rclone bisync와 Unison에 같은 종류의 장치가 있습니다). 일부만 줄어든 경우는 목록대로 지우되, 지운 문서는 보관 기간(기본 30일) 동안 남아 있어 내용이 같은 파일이 돌아오면 다음 동기화가 임베딩을 다시 하지 않고 되살립니다. 운영자가 정말로 폴더를 비운 것이면 '지금 동기화'에 '빈 목록도 반영'을 켜서 돌립니다.

**질문 11 (연결 정보).** "킥오프 입력은 원천의 연결 정보(데이터베이스 비밀번호, API 토큰)를 암호화해 보관하라고 했는데, 0.1에 들어가는 서버 경로 원천에는 비밀번호가 필요 없고 처음 쓰는 곳은 1.0의 SQL 원천입니다. 연결 정보를 보관하는 장치를 언제, 어떻게 지을까요?"

- "SQL 원천 기능에서 짓는다 (Recommended)": 아래 인용의 설명.
- "지금 암호화 보관을 짓는다": 원천 설정에 쓰기 전용 비밀 칸을 두고(저장한 뒤에는 다시 보여 주지 않음) 데이터베이스에 암호화해 넣습니다. 암호화는 이미 다른 패키지를 따라 들어와 있는 cryptography 패키지의 Fernet(AES 암호화와 위변조 검사, 열쇠 교체 지원)을 쓰고, 열쇠는 운영자가 설치할 때 만들어 비밀 파일로 둡니다. 열쇠를 잃으면 저장한 비밀을 모두 다시 넣어야 하므로 운영자가 열쇠를 따로 백업해야 하는데, 0.1에는 이 장치를 쓰는 내장 원천이 없습니다.
- "데이터베이스에 두지 않는다": 원천 설정에는 비밀의 이름만 적고 값은 `.env`나 비밀 파일에 둡니다. 암호화와 열쇠 관리가 필요 없지만, 관리자 페이지에서 비밀번호를 넣거나 바꿀 수 없고 운영자가 서버의 파일을 고친 뒤 다시 띄워야 합니다. 킥오프 입력의 '암호화해서 저장'과 다른 방향입니다.

> 사용자: "SQL 원천 기능에서 짓는다 (Recommended)" — 설명: 이번 기능의 원천 설정에는 비밀 값을 넣는 칸을 두지 않습니다. 암호화 방법과 열쇠 관리는 그것을 처음 쓰는 SQL 원천(db-source)의 설계가 정합니다. 0.1의 운영자는 암호화 열쇠를 만들고 백업할 일이 없습니다. 설치처가 직접 만든 커넥터에 토큰이 필요하면 0.1에서는 그 커넥터가 환경 변수나 비밀 파일에서 읽습니다. 기능 계획의 범위(연결 정보의 암호화 보관)를 db-source로 옮겨 적어야 합니다.

**질문 12 (폴더 붙이기).** "서버 경로 원천을 쓰려면 서버 기계의 문서 폴더를 서버와 작업자 컨테이너 안에서 보이게(읽기 전용으로) 붙여야 합니다. 단독 compose에서 폴더를 어떻게 붙이게 할까요?"

- "부모 폴더 하나를 붙인다 (Recommended)": 아래 인용의 설명.
- "원천 폴더마다 compose에 줄을 더한다": 운영자가 compose 덮어쓰기 파일에 폴더마다 붙이는 줄을 적고 서버와 작업자를 다시 띄웁니다. 폴더가 서버 기계의 여러 곳에 흩어져 있어도 그대로 붙일 수 있지만, 원천을 더할 때마다 파일을 고치고 다시 띄워야 하며, 어떤 경로든 붙일 수 있어 경계가 운영자의 주의에 달립니다.

> 사용자: "부모 폴더 하나를 붙인다 (Recommended)" — 설명: 운영자가 `.env`에 서버 기계의 폴더 하나를 적으면 그 폴더가 컨테이너의 `/sources`에 읽기 전용으로 붙고, 원천을 만들 때는 그 아래 하위 폴더 이름만 적습니다(예: `규정집`). 서버는 `/sources` 밖의 경로를 원천으로 받지 않으므로 관리 API를 잘못 써도 컨테이너의 다른 파일을 읽게 만들 수 없습니다. 원천을 더할 때 compose 파일을 고치지 않습니다. 공유 폴더(NFS, SMB)는 운영자가 서버 기계에서 그 부모 폴더 아래에 붙입니다. 다만 컨테이너가 뜬 뒤에 새로 붙인 공유 폴더는 Docker의 기본 설정에서 컨테이너에 보이지 않을 것으로 봅니다(Docker 문서의 정의에서 끌어낸 어림이고 재 보지 않았습니다). 전파 설정으로 풀리는지는 명세가 재고, 풀리지 않으면 '공유 폴더를 붙인 뒤 서버와 작업자를 다시 띄운다'를 설치 안내에 적습니다.

### 라운드 2, 둘째 호출 (질문 둘)

올리기 전에 선택지의 사실을 코드에 대 봤다(위 "이 세션이 직접 본 것"의 첫 두 줄). 호출 곁의 본문에는 토큰 역할 둘이 할 수 있는 일의 표와, 작업자가 먼저 들어온 작업부터 꺼내므로 규정집 폴더 3만 건의 첫 동기화 뒤에 수집 API로 보낸 공지 1건이 줄을 선다는 것(기능 계획의 수락 "수집 API로 보낸 문서가 바로 검색된다"와 부딪친다), 단독 compose에서 검색과 수집이 임베딩 컨테이너 하나를 같이 쓴다는 것(얼마나 느려지는지는 재지 않은 어림)을 적었다.

**질문 13 (수집 토큰).** "그룹웨어 같은 다른 시스템이 문서를 보내려면 지금은 모든 일을 할 수 있는 관리 토큰을 그 시스템에 넣어 줘야 합니다. 문서를 보내는 일만 할 수 있는 토큰(수집 전용 토큰)을 이번에 둘까요?"

- "원천 하나에 묶인 수집 토큰 (Recommended)": 토큰 역할에 '수집'(`ingest`)을 더합니다. 운영자가 발급할 때 원천 하나를 고르고, 그 토큰은 수집 API로 그 원천에 문서를 넣고 지우는 일만 할 수 있습니다. 관리 API와 MCP 검색을 부르면 403으로 거부됩니다. 그룹웨어에 준 토큰이 새어도 위키 원천의 문서나 토큰 발급, 재색인에는 닿지 못합니다. 토큰이 원천을 정하므로 보내는 프로그램은 원천 이름을 적지 않아도 되고, 토큰의 원천과 다른 이름을 적으면 거부합니다. 한 시스템이 원천 둘에 보내야 하면 토큰을 둘 발급합니다. 관리 토큰은 지금처럼 수집 API도 부를 수 있습니다. 토큰에 원천 칸이 늘고, 토큰 결정을 적은 ADR 0014에 이력을 더합니다.
- "수집 전용 역할만 더한다": '수집' 역할의 토큰은 수집 API만 부를 수 있지만 어느 원천에든 넣고 지울 수 있습니다. 토큰에 원천 칸을 두지 않아 만들 것이 조금 적습니다. 그 대신 그룹웨어에 준 토큰으로 위키 원천의 문서를 덮어쓰거나 지울 수 있습니다.
- "지금처럼 관리 토큰으로": 아래 인용의 설명.

> 사용자: "지금처럼 관리 토큰으로" — 설명: 새 역할을 두지 않습니다. 0.1에서는 문서를 보내는 시스템에 관리 토큰을 넣어 줘야 하고, 그 토큰이 새면 토큰 발급과 모든 문서의 삭제까지 열립니다. 수집 전용 토큰은 관리자 페이지 기능(admin)의 설계로 넘깁니다.

추천과 다른 답이다. 추천은 "원천 하나에 묶인 수집 토큰 (Recommended)"였다.

**질문 14 (부하 조절).** "큰 폴더를 처음 동기화하면 문서 수만 건의 처리가 몇 시간씩 이어질 수 있습니다. 그동안 다른 원천의 문서가 뒤에 줄을 서고, 낮에는 검색이 느려질 수 있습니다. 원천마다 무엇을 조절할 수 있게 할까요?"

- "원천마다 동시 처리 수만 (Recommended)": 언제 시작할지는 일정이 정하고(밤에 돌리려면 `0 2 * * *`), 시작한 동기화는 끝날 때까지 돕니다. 원천마다 '한 번에 처리할 문서 수'(기본 1)를 두어 한 원천이 작업자의 자리를 모두 차지하지 못하게 합니다. 그래서 3만 건짜리 동기화가 도는 중에도 수집 API로 보낸 문서는 남은 자리에서 바로 처리됩니다. 첫 동기화가 낮까지 이어져 검색이 느려지면(느려지는 정도는 재 보지 않은 어림입니다) 운영자가 그 원천을 '멈춤'으로 두었다가 밤에 풉니다. 멈추면 그 원천의 남은 문서 처리도 멈추고, 풀면 이어서 합니다.
- "허용 시간대도 둔다": 첫째 안에 더해, 원천마다 허용 시간대(예: 22:00~06:00)를 적을 수 있습니다. 그 시간 밖에서는 그 원천의 문서 처리를 서버가 스스로 멈췄다가 다음 허용 시간대에 이어서 합니다. 운영자가 손으로 멈출 필요가 없습니다. 그 대신 새로 더하거나 고친 문서가 다음 허용 시간대까지 검색에 반영되지 않고(지운 문서는 시간대와 상관없이 바로 뺍니다), '허용 시간대를 기다리는 중'이라는 상태와 시간대 계산, 그 시험이 늘어납니다.
- "둘 다 두지 않는다": 아래 인용의 설명.

> 사용자: "둘 다 두지 않는다" — 설명: 일정만 두고, 부하는 작업자 전체의 동시 처리 수 설정 하나(지금 기본 2)로 조절합니다. 만들 것이 가장 적습니다. 그 대신 큰 동기화가 도는 동안 수집 API로 보낸 문서가 그 뒤에 줄을 서서, 몇 시간 뒤에야 검색될 수 있습니다.

추천과 다른 답이다. 추천은 "원천마다 동시 처리 수만 (Recommended)"였다.

### 라운드 3 (이름 셋과 합의 확인)

호출 곁의 본문에 둘째 라운드에서 정해진 것과 따라오는 것(토큰 결정 ADR 0014는 그대로이고 수집 전용 토큰은 admin 계획에 넘긴다, 기능 계획의 범위에서 "시간대와 동시 처리 수"를 빼고 수락의 "바로 검색된다"는 대기열에 밀린 작업이 없을 때의 이야기로 읽는다), 이름을 정할 세 가지, 그리고 "묻지 않고 기본으로 둔 것" 열네 가지를 적었다. 그 열네 가지가 합의 확인 질문의 요약이라 글자 그대로 옮긴다.

앞의 열두 결정에서 따라 나오거나, 이미 있는 결정(ADR, core 명세)을 그대로 이은 것입니다. 번호로 고칠 줄을 짚어 주실 수 있습니다.

1. **동기화의 차례.** 원천의 목록을 받고, 색인과 대 보고, 새 문서와 바뀐 문서를 넣고, 목록에 없는 문서를 임시 삭제하고, 결과를 기록합니다. 동기화 한 번도 작업 대기열의 작업 하나로 돕니다. 데이터베이스 구조가 바뀌므로 그 PR의 제목에는 느낌표가 붙습니다.
2. **겹침 방지.** 같은 원천의 동기화는 한 번에 하나만 돕니다. 앞 동기화가 돌고 있으면 일정이 온 회차는 건너뛰어 기록에 남기고, "지금 동기화" 요청은 거부합니다.
3. **바뀐 파일 가리기.** 파일의 수정 시각과 크기가 그대로면 파일을 읽지 않습니다. 달라졌으면 읽어서 내용을 비교하고, 내용이 같으면 다시 색인하지 않습니다. 파일을 옮기거나 이름을 바꾸면 옛 문서를 지우고 새 문서를 넣은 것으로 봅니다.
4. **그룹.** 서버가 읽어 오는 원천은 만들 때 그룹 하나를 정하고, 그 원천의 문서는 모두 그 그룹에 속합니다. 밀어 넣는 원천은 지금처럼 요청마다 그룹을 적습니다(적지 않으면 기본 그룹).
5. **원천의 주인.** 수집 API로는 밀어 넣는 원천의 문서만 넣고 지울 수 있습니다. 서버가 읽어 오는 원천에 보내면 거부합니다.
6. **쉬게 하기.** 서버가 읽어 오는 원천에만 있습니다. 쉬는 동안에는 일정이 와도 동기화를 시작하지 않습니다. 이미 대기열에 들어간 문서는 끝까지 처리하고, 문서는 검색에 남습니다.
7. **일정의 시간대.** 설치 전체에 하나인 설정으로 읽고, 기본값은 한국 시간(`Asia/Seoul`)입니다. 기본을 UTC로 두면 `0 2 * * *`가 한국 시간 오전 11시에 돌기 때문입니다.
8. **놓친 일정.** 작업자가 꺼져 있어 시각을 놓쳤으면, 다시 켜졌을 때 놓친 횟수만큼이 아니라 한 번만 돌립니다.
9. **보관 기간이 지난 것 지우기.** 작업자가 하루에 한 번 돌립니다. 보관 기간(기본 30일)이 지난 문서와 지운 원천을 완전히 지우고, 어느 문서도 가리키지 않는 원본 파일을 치웁니다.
10. **실패.** 문서 하나의 실패는 지금 규칙(최대 6번, 간격을 늘려 가며 다시 시도) 그대로입니다. 목록을 받지 못한 동기화는 실패로 기록하고 다음 일정에 다시 합니다.
11. **동기화 기록.** 동기화 한 번마다 시작과 끝, 무엇이 시작시켰는지(일정, 손으로), 결과와 실패 사유, 개수(더함, 바뀜, 지움, 그대로, 사유별 건너뜀, 실패)를 남깁니다. 킥오프 입력의 "작업 기록"은 "동기화 기록"으로 부릅니다. 용어집의 "작업"이 대기열의 작업 하나를 뜻해서 겹치기 때문입니다.
12. **수집 정책의 기본값.** 지원 형식(PDF, DOCX, HWPX) 밖의 파일, 크기 상한을 넘는 파일, 제외 패턴에 맞는 파일은 문서로 만들지 않고 개수만 셉니다. 기본 제외는 숨김 파일과 폴더, 오피스 임시 파일(`~$`로 시작)입니다. 심볼릭 링크(다른 파일을 가리키는 바로 가기)는 따라가지 않아 원천 폴더 밖의 파일을 읽지 않습니다. 갱신일은 파일의 수정 시각으로 채웁니다.
13. **관리 API와 관리 명령.** 관리 API에 원천 만들기, 보기, 고치기, 지우기, 쉬게 하기와 다시 시작, 지금 동기화, 동기화 기록 보기, 연결 확인, 밀어 넣은 문서 되살리기를 더합니다. 수집 API에는 원천 이름 칸(`source`)을 더하고 버전은 v1 그대로입니다. 관리 명령은 더하지 않습니다.
14. **넘기거나 빼는 것.** 변환 인터페이스와 연결 정보 암호화는 SQL 원천(db-source)으로, 수집 전용 토큰은 관리자 페이지(admin)로 넘깁니다. 원천별 실행 시간대와 동시 처리 수는 짓지 않고 기능 계획의 범위에서 뺍니다.

**질문 15 (정리 작업).** "'정리 작업'이라는 이름이 지금 두 가지 일(원천에서 사라진 문서를 검색에서 빼는 일, 지운 지 30일이 넘은 문서를 완전히 지우는 일)에 함께 쓰이고 있습니다. 이 이름을 어느 일에 붙일까요?"

- "완전히 지우는 일에만 붙인다 (Recommended)": 아래 인용의 설명.
- "사라진 문서를 빼는 일에 붙인다": 킥오프 입력의 뜻을 살려 '정리 작업'을 원천에서 사라진 문서를 검색에서 빼는 일로 부르고, 보관 기간이 지난 것을 완전히 지우는 일에는 '비우기' 같은 새 이름을 붙입니다. ADR 0013과 core 명세가 '정리 작업'을 다른 뜻으로 쓴 문장마다 이름이 바뀌었다는 이력을 달아야 합니다.

> 사용자: "완전히 지우는 일에만 붙인다 (Recommended)" — 설명: '정리 작업'은 임시 삭제한 지 보관 기간(기본 30일)이 지난 문서와 원천을 완전히 지우고, 어느 문서도 가리키지 않는 원본 파일을 치우는 일만 가리킵니다. ADR 0013과 core 명세가 이미 이 뜻으로 쓰고 있어 고칠 문서가 없습니다. 원천에서 사라진 문서를 검색에서 빼는 일은 동기화의 한 단계이고 '삭제 반영'이라고 부릅니다(용어집의 동기화 풀이에 이미 들어 있습니다). backup-upgrade 계획의 '정리 작업을 한 번 돌려 삭제를 다시 반영한다'는 '동기화를 한 번 돌려'로 고치고, 킥오프 입력은 인터뷰의 입력 기록이라 그대로 둡니다.

**질문 16 (원천 갈래).** "원천은 문서가 들어오는 방식에 따라 두 갈래로 나뉩니다. 다른 시스템이나 사람이 문서를 보내 주는 원천(업로드, 수집 API)과 서버가 일정에 따라 스스로 읽어 오는 원천(서버 경로, 나중의 SQL)을 각각 뭐라고 부를까요?"

- "밀어 넣는 원천, 가져오는 원천 (Recommended)": 아래 인용의 설명.
- "받는 원천, 읽어 오는 원천": 서버의 처지에서 쓴 말입니다. 보내 주는 쪽은 '받는 원천', 서버가 읽어 오는 쪽은 '읽어 오는 원천'으로 부릅니다. ADR 0008과 0012의 '밀어 넣는 원천'에 이름이 바뀌었다는 이력을 달아야 합니다.
- "밀어 넣는 원천, 커넥터 원천": 읽어 오는 쪽을 커넥터가 있다는 사실로 부릅니다. 짧지만, 용어집이 원천을 '커넥터'라고 부르지 말라고 적어 둔 것(커넥터는 원천을 읽는 플러그인의 이름)과 헷갈릴 수 있습니다.

> 사용자: "밀어 넣는 원천, 가져오는 원천 (Recommended)" — 설명: 보내 주는 쪽은 '밀어 넣는 원천', 서버가 읽어 오는 쪽은 '가져오는 원천'으로 부릅니다. 앞의 이름은 ADR 0008과 0012가, 뒤의 이름은 ADR 0002가 이미 쓰고 있고, 용어집의 수집 API 풀이('이 서버가 다른 시스템을 불러 문서를 가져오는 쪽은 커넥터다')와도 같은 낱말이라 고칠 문서가 없습니다. 용어집에 두 이름을 항목으로 더합니다.

## 반영한 것

- **용어집(`GLOSSARY.md`).** 새 항목 아홉(밀어 넣는 원천, 가져오는 원천, 삭제 반영, 일정, 일시 중지, 동기화 기록, 수집 정책, 건너뜀, 정리 작업)을 더하고, "원천", "키", "그룹", "동기화", "되살림", "수집 API"의 풀이를 두 갈래에 맞게 고쳤다.
- **ADR 0021(새로 씀).** 원천의 갈래, 문서의 주인(수집 API는 밀어 넣는 원천만, 그룹, 원천 삭제, 되살리기), 서버 경로 원천의 폴더, 짓지 않는 것 셋(변환 인터페이스, 연결 정보의 암호화 보관, 수집 전용 토큰).
- **ADR 0022(새로 씀).** 동기화의 차례, 일정(cron 표현식, 작업자, 시간대, 놓친 일정, cronsim), 지키는 것(겹침 방지, 목록이 비면 지우지 않는다, 일시 중지), 부하를 조절하는 장치를 두지 않는 것, 남기는 것(건너뜀, 수집 정책, 동기화 기록, 실패), 정리 작업.
- **ADR을 둘로 나눈 까닭.** 앞의 것은 원천이 무엇이고 문서의 주인이 누구인지(데이터 모델과 권한의 경계)이고, 뒤의 것은 동기화가 언제 어떻게 도는지(실행)다. 뒤의 결정을 바꿀 때 앞의 것을 함께 열지 않게 했다. 헌법 거버넌스의 "ADR은 결정 단위로 하나"에 맞춘 판단이고 사용자에게 승인 화면에서 보인다.

- **Minor · ADR 0022 64줄** "동기화 한 번이 끝났다고 보는 때". 넘김은 맞다. 다만 "넣은 문서의 처리가 모두 끝날 때"로 정하면 재시도(최대 6번, 간격 상한 1시간) [코드] 동안 일정 회차가 건너뛰고 "지금 동기화"가 거부된다. 방향: "삭제 반영이 임베딩 뒤에 묶이지 않고, 죽은 동기화가 겹침 판정을 영영 잡지 않는다"를 조건으로 붙여 넘긴다.

### 3. 명세에 넘길 물음 (결함은 아니고 명세가 정할 세부)
- `default`와 `upload`를 지울 수 있는지, 지운 뒤 `migrate`가 다시 만드는지. 이름이 유일 제약이라 보관 기간 동안 `migrate`가 조용히 지나가면, `source`를 적지 않은 수집이 지운 원천으로 간다.
- 수집 API의 삭제 요청에도 `source` 칸을 두는지.
- 정리 작업과 되살림이 같은 문서에서 겹칠 때(문서 행을 잠그고 `deleted_at`을 다시 본다).
- 정리 작업이 `/sources`의 파일(서버 경로 원천의 "원본")을 지우지 않게 하는 것.
- 일시 중지한 순간 대기 중이거나 도는 동기화 작업, 일시 중지한 원천의 "지금 동기화", 다시 시작 직후의 놓친 일정, 일정을 고친 직후의 다음 실행 시각.
- 일정 확인이 작업자의 자리가 모두 바쁠 때도 도는지. 지금 작업자는 꺼낼 작업이 없을 때만 5초를 기다린다(`src/rag_engine/worker/service.py`) [코드].
- 목록 도중 읽기 오류(하위 폴더 권한, 네트워크 끊김)를 부분 목록이 아니라 실패로 보는 것.
- 빈 목록 판정이 수집 정책을 적용하기 전인지 뒤인지.
- 수집 정책을 커넥터와 서버 가운데 어디서 적용하는지(커넥터 인터페이스 1.0에 닿는다).
- 원천 삭제를 작업 단위 하나로 할지 대기열 작업으로 할지(문서 수만 건).
- 겹치는 폴더를 가리키는 원천 둘, 그리고 `ingest <경로>`로 `default`에 넣어 둔 폴더를 서버 경로 원천으로 옮길 때 생기는 중복.
- `.env`에 폴더를 적지 않았을 때의 `/sources`.
- 자유 형식 커넥터 설정에 든 비밀이 관리 API 보기, 진단 묶음, 백업에 평문으로 남는 것(원칙 V).
- 여섯 칸(초가 든) cron 표현식의 거부. cronsim README는 초 칸이 든 여섯 칸도 받는다고 적는다 [웹 요약].

### 리뷰가 연 결정 셋 (질문 19~21)

Major 넷 가운데 셋은 고치는 방법이 결정의 방향이나 관리 API가 알려 주는 값에 닿아, 고치기 전에 `AskUserQuestion`으로 물었다(`code-review` 6단계 3). 명세 축 M1이 질문 19, 명세 축 M3이 질문 20, 표준 축 Major 1이 질문 21이다. 질문 글과 선택지의 라벨·설명을 글자 그대로 옮긴다. 세 답 모두 추천안이다.

**질문 19 (지운 원천).** "원천(예: wiki)을 지운 뒤 보관 기간(기본 30일) 안에 실수였다는 것을 알았을 때, 지운 원천을 되돌릴 길을 둘까요? 어느 쪽을 고르셔도 지운 원천은 그 순간부터 새 문서, 문서 되살리기, 동기화를 받지 않습니다."

- "원천 되살리기를 둔다 (Recommended)": 아래 인용의 설명.
- "되돌리는 길을 두지 않는다": 지운 원천은 되돌릴 수 없습니다. 실수로 지웠으면 원천을 새로 만들어 문서를 다시 보내거나 다시 동기화해야 하고, 임베딩을 처음부터 다시 합니다(수만 건이면 몇 시간이 걸릴 수 있다는 것은 재지 않은 어림입니다). 보관해 둔 30일치 조각은 쓰이지 않고 기간이 지나면 지워집니다. 만들 것이 가장 적습니다.

> 사용자: "원천 되살리기를 둔다 (Recommended)" — 설명: 관리 API 호출 하나로 지운 원천을 보관 기간 안에 되돌립니다. 원천과 함께 지워졌던 문서가 같이 검색에 돌아오고, 그사이 색인 판이 바뀌지 않았으면 임베딩을 다시 하지 않습니다. 가져오는 원천은 되돌린 뒤의 동기화가 그사이 폴더에서 바뀐 것을 다시 맞춥니다. 관리 API가 하나 늘고, 원천과 함께 지워진 문서와 그 전에 따로 지운 문서를 가르는 표시를 남겨야 합니다.

**질문 20 (꺼내는 순서).** "큰 폴더의 첫 동기화가 문서 수만 건을 대기열에 넣으면, 그 뒤에 온 다른 원천의 동기화와 '지금 동기화'도 같은 줄 뒤에 서고, 그동안 그 원천에서 지운 문서가 검색에 계속 나옵니다. 작업자가 작업을 꺼내는 순서를 어떻게 할까요?"

- "동기화와 정리 작업을 먼저 꺼낸다 (Recommended)": 아래 인용의 설명.
- "지금 순서 그대로 둔다": 모든 작업을 먼저 들어온 순서대로 꺼냅니다. 고칠 것이 없습니다. 그 대신 큰 동기화가 넣은 문서의 처리가 끝날 때까지 다른 원천의 동기화와 '지금 동기화', 정리 작업이 기다리고, 그동안 원천에서 지운 문서가 계속 검색됩니다(몇 시간이 될 수 있다는 것은 재지 않은 어림입니다). 이 점을 ADR에 치르는 값으로 적습니다.

> 사용자: "동기화와 정리 작업을 먼저 꺼낸다 (Recommended)" — 설명: 작업자가 문서 한 건을 색인하는 작업보다 동기화 작업(목록을 받아 대 보고 지운 문서를 빼는 일)과 정리 작업을 먼저 꺼냅니다. 큰 동기화가 돌고 있어도 다른 원천에서 지운 문서는 그 원천의 일정이 오면 곧 검색에서 빠지고, '지금 동기화'도 곧 돕니다. 새로 넣는 문서의 색인은 질문 14에서 고르신 대로 들어온 순서대로 줄을 섭니다. 꺼내는 순서에 규칙 하나가 늘어납니다.

**질문 21 (관리 API).** "문서 상태에 '건너뜀'을 더하면 관리 API의 문서 조회에서 암호가 걸린 파일이 '실패'가 아니라 '건너뜀'으로 나와 '실패'의 뜻이 좁아집니다. 관리 API 코드의 규칙은 '뜻을 바꾸면 경로를 v2로 올린다'인데, 관리 API의 버전을 어떻게 할까요?"

- "v1 그대로 두고 값을 더한다 (Recommended)": 아래 인용의 설명.
- "v2로 올린다": 문서 조회를 /api/v2/admin으로 새로 열어 규칙을 글자 그대로 지킵니다. 쓰는 쪽이 없는 지금 v1과 v2 두 경로를 함께 두거나 v1을 지우는 일이 생기고, 관리 API의 다른 경로(작업 조회, 토큰)를 어느 버전에 둘지도 정해야 합니다.

> 사용자: "v1 그대로 두고 값을 더한다 (Recommended)" — 설명: 경로는 /api/v1/admin 그대로이고 문서 상태에 '건너뜀' 값 하나가 늡니다. 릴리스 태그가 아직 하나도 없고(첫 정식 판이 나기 전입니다) 이 API를 쓸 관리자 페이지도 이 기능 뒤에 만들기 때문에, 옛 뜻에 기대는 쓰는 쪽이 없습니다. ADR에 '정식으로 낸 판이 없어 같은 v1에서 바꾼다'는 까닭을 적습니다. 이미 있는 문서(암호가 걸려 실패로 남은 것, 글자가 없어 조각이 0개인 것)를 건너뜀으로 옮길지는 명세가 정합니다.

**고친 것 (명세 축).**

- M1(지운 원천으로 들어오는 문서와 되살림). 질문 19의 답대로 ADR 0021 "문서의 주인"에 불릿 둘("지운 원천은 아무것도 받지 않는다", "지운 원천은 보관 기간 안에 관리 API로 되살린다")을 더했다. Considered Options에 고르지 않은 안을, Consequences의 관리 API 목록에 "지운 원천 되살리기"를, 명세 목록에 셋(지운 원천의 이름을 적은 수집 요청의 오류 코드, 원천을 지우는 순간의 작업을 거두는 방법, 표시의 모양)을 더했다. 용어집 "되살림"의 풀이를 지운 원천까지 넓혔다.
- M2(삭제 기록이 원천 삭제를 막는다). ADR 0022 "정리 작업" 끝에 지운 원천에 딸린 삭제 기록은 원천과 함께 지운다는 문장과 까닭을 적고, ADR 0021의 원천 삭제 불릿에 괄호로 받았으며, ADR 0013 8줄에 `(바뀜: ADR 0022)`를 달았다. 질문 7에서 고른 설명 "문서와 원천을 완전히 지웁니다"에서 따라 나온 것으로 보아 따로 묻지 않았고, 승인 화면에서 보인다.

- (a) 둘. ADR 0022 "시작시키는 쪽"과 Consequences에 다음 실행 시각을 적어 두고 원천 보기가 보여 준다는 것을 넣었고, 데이터베이스 변경 목록에 원천 표의 칸(일정, 다음 실행 시각, 일시 중지, 제외 패턴)을 더했다. ADR 0021 Consequences는 갈래 칸(`kind`)이 이미 있어 받는 값만 는다고 고쳤다.
- (c) 다섯. 넷(건너뜀과 파서 버전, 실패한 문서의 재시도, 동기화가 끝났다고 보는 때, 방금 쓴 원본)은 ADR 0022 Consequences 끝의 "명세가 정하되 지켜야 하는 조건"으로 받았다. 방향을 ADR이 정하지 않으면 명세가 틀린 쪽으로 정해도 막을 문장이 없어서 조건으로 적었다. 개수 목록은 건너뜀과 수집 정책에 걸린 파일을 따로 세게 갈랐다.
- Nit 다섯. 수락의 인용, 계획의 "넷", 계획의 옛 표현 셋("주기 실행", "다음 주기 실행 뒤", "같은 원천의 작업이 겹쳐"), ADR 0021의 일시 중지 문장(가져오는 원천에만 있다는 괄호), ADR 0022 겹침 방지의 "건너뛰어"(문서 상태의 건너뜀과 헷갈려 "시작하지 않고"로)를 고쳤다.
- "명세에 넘길 물음" 열넷. 둘은 ADR 0022 Consequences에 적었다(작업자의 자리가 모두 바쁠 때의 일정 확인은 명세 목록에, 목록 도중의 읽기 오류는 조건에). 나머지 열둘은 아래 "남긴 것"대로 받는 쪽에 적었다.

**남긴 것과 이유.**

- 표준 축 Minor 2(ADR 0012 21줄의 포인터). 달지 않았다. "주기와 병렬은 source-sync가 정한다"는 이 설계가 정한 뒤에도 글자 그대로 참이고, `.claude/rules/adr.md`는 그런 문장에 달지 않는다고 적는다. ADR 0013 25줄은 "명세가 정한다"고 적은 것을 ADR이 정해 주체가 달라졌으므로 달았다. ADR 0003 8줄도 달지 않았다. 그 줄은 변환을 "선택"으로 적고 언제 짓는지 적지 않는다. 명세 축도 ADR 0003과 0012에는 포인터가 필요 없다고 봤다. 표준 축이 함께 든 ADR 0007은 변환을 드는 줄이 이력(44줄)뿐이고 지난 이력은 기록이다.

- 명세 축 (b)(`upload` 원천을 `migrate`가 만들어 둔다). 질문 5에서 고른 설명은 "`upload` 원천에 따로 모읍니다"까지이고 누가 만드는지는 이 세션이 정했다. ADR의 문장은 그대로 두고 승인 화면에서 세션이 정한 것으로 따로 보인다.
- 명세에 넘긴 물음 열둘. 받는 쪽인 `.scratch/source-sync/plan.md` 본문의 "설계의 셀프 리뷰 … 가 명세에 넘긴 물음" 문단에 적었다. 그 기능의 명세가 이 계획을 입력으로 읽고, 넘기는 쪽과 받는 쪽이 같은 기능이라 받는 쪽이 먼저 도는 일이 없다. 여섯 칸짜리 일정 표현식을 일정 계산 라이브러리가 받는다는 것은 리뷰어의 웹 요약이라 그렇게 적어 넘겼다.
- 두 축이 대조하지 못했다고 적은 것(Kendra, Azure AI Search, RAGFlow 문서의 글자 대조와 큰 동기화 뒤의 지연 시간). 앞의 것은 "확인한 것"에 서브에이전트가 받아 본 것으로 적혀 있고 ADR은 그 제품들을 Considered Options의 예로만 든다. 뒤의 것은 ADR이 재지 않은 어림이라고 적는다.

**다시 돌린 명령.** `uv run python tools/check_adr_pointers.py`와 `uv run python tools/plan_table.py --check`가 출력 없이 끝났다. 바뀐 파일을 인자로 준 `uv run python tools/check_quotes.py`는 "인용 대조 경고 23건(파일 10개(그중 전체를 본 것 3개)에서 인용 61건 중)"으로 끝났고, 스물셋 모두 이 일지의 질문 글(세션 기록에서 옮긴 것)과 Onyx 문서의 인용이다. ADR 둘과 용어집, 계획에는 경고가 없다. 이 검사는 경고만 하고 막지 않는다. 손으로 치는 검사 다섯은 커밋이 부르는 pre-commit의 결과로 갈음하고, 결과는 "검증" 절에 적는다.

원인은 이 변경이 아니라 개발 기계의 메모리로 봤다. 이 변경은 마크다운 열한 파일뿐이고, 실패한 일곱은 모두 시간 안에 끝나야 하는 시험이거나 프로세스를 새로 띄우는 시험이며, 둘은 운영체제가 메모리를 내주지 못했다는 오류를 그대로 냈다. 22시 10분에 손으로 보니 물리 메모리 31.9GB 가운데 여유가 1.2GB, 가상 메모리 한도 127.9GB 가운데 여유가 16.3GB였고, 검사를 돌리는 python 프로세스는 모두 다른 워크트리 세션의 것이었다(`Get-CimInstance Win32_OperatingSystem`과 `Win32_Process`를 손으로 봤다). 22시 27분에도 여유는 12.6GB였고 그런 프로세스가 스물둘이었다. 시험을 고치거나 건너뛰지 않았고 다른 세션의 프로세스도 건드리지 않았다. 메모리가 풀리기를 기다렸다가 같은 커밋을 그대로 다시 시도한다.

**기다림.** 첫 대기(최대 25분, 검사 프로세스가 0이거나 여유가 35GB 이상이면 끝남)는 한도를 채우고 22시 35분에 "여유 커밋 메모리 6GB, 검사 중인 python 프로세스 22개"로 끝났다. 22시 36분에 다시 보니 여유 10.5GB, 검사 프로세스 스물여덟(다른 워크트리 다섯과 agent 저장소, 주 체크아웃)이었다. 프로세스 이름으로 묶어 본 차지한 메모리는 claude 49개 26.2GB, python 104개 16.6GB, vmmem 15.1GB, node 156개 13.9GB, oracle 10.0GB였다(`Get-Process`를 손으로 봤다). 검사가 모두 끝나도 여유가 35GB까지 오르지는 않을 것으로 어림해, 둘째 대기는 조건을 "검사 프로세스 여섯 이하이고 여유 20GB 이상"으로, 한도를 40분으로 바꿔 걸었다. 그 상태에서 커밋을 치면 같은 실패가 되풀이될 것으로 보아 치지 않았다. `tools/run_checks.py`의 독스트링은 세션 둘이 같은 시각에 커밋하면 시간에 기댄 사례가 빨개질 수 있다고 적고 잠금은 두지 않았다고 적는다.

**커밋 메시지의 제목.** 기다리는 동안 `uv run python tools/check_commit_msg.py <메시지 파일>`을 손으로 돌려 보니 처음 제목이 "제목 76자 > 72자"로 걸렸다. 첫 시도는 pre-commit에서 끝나 이 검사(commit-msg 단계)까지 가지 못했으므로, pytest가 통과했더라도 21분 뒤에 여기서 실패했을 것이다. 제목을 `docs: 원천을 둘로 가르고 동기화는 작업자가 cron 일정으로 돌린다 (source-sync 설계, ADR 0021·0022)`(72자)로 줄였고 검사가 출력 없이 끝났다. 메시지는 파일로 두고 `git commit -F <파일>`로 친다.

**사용자가 pytest를 건너뛰고 커밋하게 했다.** 둘째 대기를 건 뒤 두 길을 표로 보이고 물었다. 물음은 "여유가 생길 때까지 기다릴까요, pytest를 건너뛰고 커밋해 CI 판정에 맡길까요?"이고, 단추는 "계속 기다린다"(이 세션이 첫 자리에 둔 것)와 "pytest 건너뛰고 커밋"이었다. 표에 적은 둘째 길의 설명은 이렇다. `SKIP=pytest git commit`으로 pytest만 빼고 나머지 검사는 그대로 돌린다. 5분 안팎이 걸린다. 리뷰 반영 뒤의 변경은 로컬 pytest를 거치지 않고 판정은 CI의 `verify`가 한다. 같은 수정 시각과 크기를 가진 내용 변경은 동기화가 감지하지 못합니다.

14행의 변경 확인 조건은 수정 시각과 크기입니다. 파일 내용을 바꾸면서 두 값을 원래대로 유지하면 동기화는 파일을 읽지 않고, 이전 색인이 그대로 남습니다. 파일의 수정 시각을 바꾸면 다음 동기화가 내용을 다시 읽으므로 이 상황은 우회할 수 있습니다. 하지만 ADR에는 이 한계가 적혀 있지 않고, 운영자가 전체 내용 검사를 요청하는 방법도 없습니다.

### 판정과 반영 (PR 봇 리뷰 첫 회차)

지적마다 그 줄과 근거를 먼저 열었다. 연 것은 아래와 같다.

- `.scratch/backup-upgrade/plan.md` 5줄과 7줄. 7줄은 밀어 넣는 원천에서 백업 뒤에 지운 문서가 "복원한 뒤에 동기화를 돌려도 다시 지워지지 않는다"고 적는데, 5줄은 원천의 갈래를 가르지 않고 동기화를 한 번 돌리면 삭제가 다시 반영된다고 적었다.
- ADR 0022 "지키는 것"의 "목록이 비면 지우지 않는다" 불릿. 실패로 기록하는 조건은 "원천 폴더가 없거나, 목록이 0건인데 색인에는 그 원천의 문서가 있으면"이고, "빈 목록도 반영"은 "운영자가 정말로 폴더를 비운 것이면" 쓰는 길로만 적혀 있다.
- ADR 0021 "원천의 갈래"와 Considered Options의 첫 줄("밀어 넣는 원천을 업로드와 수집 API 둘로 고정하거나, 지금처럼 하나로 둔다."를 고르지 않았다고 적는다), 용어집의 수집 API 풀이, ADR 0008 10줄과 ADR 0012 10줄.
- ADR 0013 26줄, `.scratch/core/spec.md` "삭제, 되살림, 묘비" 절의 되살림 항목(227줄), `.claude/rules/adr.md`의 포인터 규칙.
- ADR 0022 14줄, ADR 0012 10줄("변경 표지(수정 시각과 크기, etag 같은 것)가 같으면 받기를 건너뛰고, 다르면 받아 내용 해시로 다시 확인한다"), 이 일지의 합의 요약 3번.

**고친 것 넷.**

- 1번(backup-upgrade 계획 5줄). 지적이 맞다. 5줄을 "복원한 뒤에는 가져오는 원천마다 동기화를 한 번 돌려 그 원천에서 지운 것을 다시 반영한다(밀어 넣는 원천에서 지운 문서는 동기화로 다시 지워지지 않는다. 아래 문단)"로 좁혔고, 7줄에 위 문단을 좁혀 적었다는 문장을 더했다. 7줄의 괄호가 밀어 넣는 원천의 예로 수집 API와 업로드를 나란히 든 것도 3번과 같은 까닭으로 "수집 API나 업로드로 문서를 받은 원천"으로 풀었다.
- 2번(source-sync 계획 10줄). 지적이 맞다. PR 직전 리뷰를 반영하며 쓴 대목이 "빈 목록도 반영"을 폴더가 사라진 경우와 비어 있는 경우 모두의 운영자 길로 적었는데, ADR 0022는 폴더를 정말로 비운 경우만 적었다. 그 대목을 고쳐 ADR 0022가 폴더가 없는 경우를 정하지 않았다는 것과, 명세가 두 경우를 갈라 정할 것 셋(폴더가 없을 때에도 통하게 할지, 통하지 않게 하면 그때 운영자가 할 일, 되살리기의 응답이나 설치 안내가 그 길을 알려 주는지)을 적었다. ADR 0022는 고치지 않았다. 폴더가 없을 때의 동작은 인터뷰가 묻지 않은 결정이라 이 세션이 ADR에 정해 적을 수 없고, 명세가 통하게 정하면 그 ADR의 이력에 적는다.
- 3번(ADR 0008 10줄). 지적이 맞다. ADR 0021은 밀어 넣는 원천을 운영자가 시스템마다 만드는 이름 붙은 원천으로 정했고 수집 API는 그 원천의 이름을 받아 문서를 넣는 통로다. "업로드와 수집 API는 커넥터가 아니라 밀어 넣는 원천 종류이고"만 읽으면 밀어 넣는 원천이 그 둘로 정해진 것으로 알게 된다. 그 문장 끝에 `(바뀜: ADR 0021)`을 달았다. 같은 문장이 ADR 0012 10줄에도 있어 거기에도 달았다. 지적은 ADR 0008만 짚었고, ADR 0012 쪽은 `밀어 넣는 원천 종류`로 저장소의 마크다운을 Grep해 찾았다. 같은 Grep에 걸린 `.scratch/core/spec.md` 84줄은 두었다. 포인터 규칙은 ADR 본문의 것이고, 그 명세는 밀어 넣는 원천이 `default` 하나뿐이던 core의 것이다. source-sync 계획 12줄의 괄호도 업로드와 수집 API를 밀어 넣는 원천이라고 적고 있어 "업로드와 수집 API는 커넥터가 아니고, 그 둘로 들어온 문서는 밀어 넣는 원천에 속한다"로 고쳤다.
- 5번(ADR 0022 14줄). 한계가 적혀 있지 않다는 지적은 맞다. 변경 확인값이 같으면 읽지 않는다는 방식 자체는 ADR 0012가 2026-11-09에 정했고 합의 요약 3번으로 사용자가 확인한 것이라 바꾸지 않았다. 그 방식이 치르는 값과 지금 쓸 수 있는 우회만 14줄 문단에 세 문장으로 더했다. 원천의 파일을 모두 다시 읽게 하는 길을 둘지는 새 기능을 고르는 일이라 정하지 않고 명세에 넘겼다. 받는 쪽은 source-sync 계획에 새로 둔 문단 "PR 봇 리뷰 … 가 명세에 넘긴 것"이다. 승인 뒤에 더한 글이라 그 문단에 그렇게 적었고 사용자에게 원문과 함께 알린다.

**보류한 것 하나.**

- 4번(ADR 0013 26줄). 포인터를 달지 않았다. 그 문장은 "같은 (원천, 키)가 보관 기간 안에 다시 들어오면 새 문서가 아니라 되살림인지는 명세가 정한다(어림: 되살린 뒤 갱신으로 처리)"이고, core 명세가 2026-11-10에 그 어림대로 정했다("되살림은 같은 (원천, 키)가 `deleted_at`은 있고 `purged_at`은 없는 문서로 다시 들어올 때다(ADR 0013이 어림으로 적은 방향 그대로)"). 명세가 정한다고 적었고 명세가 정했으니 문장은 글자 그대로 여전히 참이다. ADR 0022의 문장은 그렇게 정해진 되살림이 동기화로 돌아온 파일에도 그대로 쓰인다는 것이고 26줄을 바꾸지 않는다. `.claude/rules/adr.md`는 "사실을 더하기만 해 본문이 글자 그대로 여전히 참인 것"에는 포인터를 달지 않는다고 적는다. `(바뀜: ADR 0022)`를 달면 ADR 0022가 그 문장을 바꾼 것으로 읽힌다. 같은 ADR의 25줄에 포인터 둘이 달린 것과는 경우가 다르다. 25줄이 명세에 맡긴 둘(되살리는 관리 API, 정리 작업의 주기)은 명세가 아니라 ADR 0021과 0022가 정했다. 이 까닭은 PR의 그 코멘트에 답글로 남긴다.

## 회고

`retro` 스킬로 돌렸다. 근거는 이 일지와 이 세션이다. 후보 열하나를 냈고 판정은 승인 여덟(이미 있는 항목에 회차를 더한 것 다섯, 새 항목 셋), 기각 셋이다. 넘긴 것이 없어 사용자에게 묻지 않았다. 만료할 항목은 이 워크트리의 대기열과 `--ref origin/dev`의 대기열 두 출력에 모두 없었다. CodeRabbit의 첫 리뷰를 반영한 뒤 후보 셋을 더 냈고(아래 12~14), 그것까지 합치면 후보 열넷에 승인 열(회차를 더한 것 여섯, 새 항목 넷), 기각 넷이다.

**승인: 이미 있는 항목에 회차를 더한 것.** 다섯 모두 열린 항목이 이미 처방한 사건이라 회차로 센다(retro 4단계의 회차로 세는 것).

1. 문서만 바꾼 커밋의 pre-commit이 전체 pytest를 돌았다. 대기열 `docs-only-commit-full-pytest`가 10회차가 됐다(회고 때는 9회차로 적었다. 병합 전에 dev를 다시 합칠 때 PR #91이 같은 항목에 9회차를 먼저 적어 두어 이 사건을 10회차로 옮겼다). 사건: 마크다운 열한 파일만 바꾼 첫 커밋 시도가 pytest를 1291.93초 돌고 다른 세션들의 부하로 실패했다. 같은 날 문서를 읽는 시험 일곱 파일만 돌린 것은 238.70초에 398개가 통과했다. 그 일곱은 이 세션이 고른 것이고, 그 항목이 남길 시험의 목록은 반영하는 chore가 정한다.
2. 커밋 메시지의 제목 길이를 pre-commit보다 먼저 막지 못했다. 대기열 `commit-msg-after-slow-checks`가 8회차가 됐다. 사건: 첫 커밋의 명령은 메시지를 표준 입력으로 넘기는 `git commit -F -`였고 제목은 76자였다. `tools/hook_bash_commit_msg.py`의 독스트링은 그 꼴을 못 보는 것에 적는다. pytest가 먼저 실패해 commit-msg 단계에는 닿지 않았고, 기다리는 동안 `tools/check_commit_msg.py`를 손으로 돌려 찾았다.
3. 이름을 바꾼 PR이 병합된 뒤에도 이 브랜치의 새 글이 옛 낱말을 쓰고 있었다. 대기열 `renamed-term-reintroduced-by-parallel-pr`이 2회차가 됐다. 사건: PR 87이 릴리스의 뜻으로 쓰던 "판"을 버렸는데, 그 전에 쓴 ADR 0022 초안의 두 곳이 그 낱말을 쓰고 있었다. 승인 뒤 기준 브랜치를 받아 온 이 세션이 스스로 훑어 바꿨고 dev에는 들어가지 않았다. 검사가 잡은 것이 아니라 세션이 PR 87의 제목을 보고 알아챈 것이다.
4. 리뷰 보고를 받은 턴에 일지로 옮기지 못했다. 대기열 `review-report-journal-lag`가 10회차가 됐다. 사건: 셀프 리뷰 표준 축의 보고와 PR 직전 리뷰의 보고가 각각 온 직후에 컨텍스트가 압축되어, 세션 기록에서 스크립트로 꺼내 글자 그대로 옮겼다. 명세 축의 보고는 받은 턴에 옮겼다. 잃은 판정은 없다. 앞의 회차들과 달리 옮기기를 미룬 것이 아니라 보고가 온 턴에 압축이 끼어든 것이라, 받은 턴에 옮기라는 문장만으로는 닿지 않는다. 그 관찰을 항목의 본문에 적었다.
5. 세션 기록에서 질문과 보고를 꺼내는 스크립트를 또 새로 썼다. 대기열 `extract-asks-tool`이 7회차가 됐다. 사건: 인터뷰 질문의 글과 선택지 설명을 옮기려고 스크래치패드에 추출 스크립트 하나를, 서브에이전트의 보고와 브리프를 꺼내려고 넷을 새로 썼다.

**승인: 새 항목.**

6. 여러 세션이 같은 시각에 검사를 돌려 개발 기계의 가상 메모리가 바닥났다. 새 항목 `concurrent-checks-exhaust-memory`, 1회차. 사건: 첫 커밋 시도의 실패 일곱 가운데 다섯은 시간 한도가 아니라 프로세스를 띄우지 못한 것이고(둘은 `WinError 1455`와 `VirtualProtect failed`를 그대로 냈다), 40분쯤 기다려도 풀리지 않아 사용자가 pytest를 건너뛰게 했다. 승인의 세 조건: 사건이 있고, 층은 도구(검사 러너가 pytest를 띄우기 전에 여유 메모리와 다른 검사 프로세스의 수를 읽어 알린다)이며, PR 하나로 되돌릴 수 있다. 막지 않고 알리는 것이라 가드레일을 느슨하게 하지 않는다. 더하는 것이라 다섯 번째나 손상 전에는 회차만 센다. 커밋이 만들어지지 않았을 뿐 잃은 작업이 없어 손상이 아니다. 코드를 바꾼 커밋도 같은 부하에서 같은 실패를 낼 것이라 1번의 항목과 따로 두고, 두 항목이 서로 가리키게 했다.
7. ADR의 승인을 PR 직전 리뷰보다 먼저 받아, 승인받은 글이 병합 전에 바뀌었다. 새 항목 `adr-approval-before-pre-pr-review`, 1회차. 사건: 승인 뒤에 돈 `coderabbit-review`가 서버 경로 원천의 경계 규칙을 Major로 냈고, 승인받은 ADR 0021의 문단에 세 문장을 더했다. 사용자에게 그 세 문장을 원문과 함께 알렸다. 세 조건: 사건이 있고, 층은 지침(설계 세션이 PR 직전 리뷰를 승인 화면 앞에 돌린다는 한 줄)이며, PR 하나로 되돌릴 수 있다. 사용자에게 확인받는 단계를 빼는 것이 아니라 리뷰의 차례를 앞으로 옮기는 것이라 넘기지 않았다. 더하는 것이라 회차만 센다. 같은 결과(승인받은 글과 병합되는 글이 달라진다)를 다른 원인으로 다루는 `adr-draft-drops-option-conditions`와 서로 가리키게 했다.
8. 한도에 걸렸던 헤드에 CodeRabbit 리뷰를 다시 요청하면 `tools/wait_ci.py`가 리뷰가 시작되기 전에 통과로 끝난다. 새 항목 `wait-ci-stale-review-state-on-rerequest`, 1회차. 사건은 위 "PR 봇 리뷰" 절에 있다. 도구의 버그를 고치는 것이라 사건 하나로 반영하는 종류다. 이 PR은 설계 문서만 담고, 도구와 그 시험을 고쳐 실으면 PR의 범위가 넓어지므로 이 세션에서 반영하지 않고 대기열에 두었다.

**기각.**

9. 설계 인터뷰가 상태가 바뀌는 자리의 교차를 밟지 않아, 셀프 리뷰 명세 축이 Major 셋을 냈고 질문 셋(19~21)을 다시 물었다. 그 교차는 `code-review`의 명세 축 브리프 (d)가 보게 한 기준이고 리뷰가 잡았다. 리뷰가 잡도록 둔 기준을 리뷰가 잡은 사건은 회차로 세지 않고(retro 4단계), 검사로 옮길 수 없으며 표준에 더할 새 판단 기준도 아니다. 닫힌 `spec-review-transition-crossing`이 그 줄을 더한 뒤로 이 꼴의 결함이 PR 봇이 아니라 셀프 리뷰에서 나왔다.
10. 사용자가 추천과 다른 답을 셋 골랐다(질문 4, 13, 14). 셋 모두 0.1에서 쓰는 곳이 아직 없는 장치(변환 인터페이스, 수집 전용 토큰, 원천마다의 부하 조절)를 짓지 않는 쪽이다. 선택지 설명의 전제가 틀려 바로잡힌 것이 아니라 범위를 고른 것이어서, 실수나 비용인 사건이 없다. `grilling-premise-check`의 회차로도 세지 않는다.
11. CI와 CodeRabbit을 기다리던 배경 대기가 세션이 끝나며 끝 줄 없이 멈췄다. 세션이 끝난 뒤의 일이라 저장소의 도구가 막을 층이 없다. `tools/wait_ci.py`의 독스트링이 못 보는 것에 "세션이 꺼진 뒤의 완료"를 재지 않았다고 적어 두었고, 이번에 본 것은 8번 항목의 본문에 관측으로 적었다.

**일지에만 남기는 것.**

- 부하에서만 빨간 시간 시험의 새 사례 둘(`tests/app/test_job_lease.py`의 5초 상한, `tests/test_serve_command.py`의 30초 기한). 이 종류는 닫힌 `token-expiry-test-load-margin`이 받아들여 닫은 것이라(일지 `2026-11-14-2150-release-image-after-agent-os.md`의 회고 8번이 그렇게 적는다), 대기열 항목에 회차를 더하지 않고 여기에만 적는다(retro 5단계). 다시 열지는 사용자가 정하는데, 이 세션에 실린 에이전트 메모에는 사용자가 2026-11-15에 다시 열지 않기로 답했다고 적혀 있다. 그 답의 원문은 저장소의 일지에서 찾지 못했다.
- 첫 대기의 조건(검사 프로세스가 0이거나 여유가 35GB 이상)은 그날의 기계에서 채워지기 어려운 값이어서 25분을 한도까지 썼다. 한 번의 어림이 빗나간 것이다.
- CodeRabbit은 PR의 첫 요청에서 한도에 걸렸다. PR 직전에 CLI로 한 번 돌린 것과 PR의 한도가 같은 것인지는 알 수 없다(CLI는 `Plan: Free`, PR의 요약 코멘트는 `Plan: Advanced`라고 적는다).

**봇 리뷰 첫 회차 뒤에 더한 후보.** 사건은 위 "판정과 반영 (PR 봇 리뷰 첫 회차)"에 있다. 같은 일을 다룬 항목은 `uv run python tools/queue_open_rows.py --search`에 낱말을 바꿔 가며 세 번 찾았다.

12. 승인(회차). 새 ADR이 낱말의 갈래를 바꿨는데, 그 낱말을 옛 갈래로 적은 다른 ADR의 문장을 찾지 않았다. 대기열 `decision-word-residue`가 8회차가 됐다. 사건: ADR 0021이 수집 API를 밀어 넣는 원천의 종류에서 그 원천에 문서를 넣는 통로로 바꿨는데, ADR 0008 10줄과 ADR 0012 10줄의 같은 문장에 포인터가 없었다(3번 지적). 그 항목은 결정이 말의 뜻을 바꿨을 때 그 말을 `docs/adr/`까지 grep하지 않은 사건을 세고, 이번 사건이 그 꼴이다. 열린 항목이 이미 처방한 사건이라 회차로 센다. 포인터를 빠뜨린 다른 사건을 세는 `adr-rename-history-pointer-gap`(용어집이 이름을 바꾼 이력의 표시)과 `adr-body-rewrite-vs-pointer`(포인터 대신 본문을 고쳐 쓴 것)는 꼴이 달라 잇지 않았다.
13. 승인(새 항목). 리뷰를 반영하며 기능 계획에 쓴 문장이 ADR이 정한 것보다 넓었다. 새 항목 `review-fix-sentence-overstates-adr`, 1회차. 사건: PR 직전 리뷰의 Minor를 명세에 넘기며 "빈 목록도 반영"을 폴더가 사라진 경우의 운영자 길로도 적었는데, ADR 0022는 폴더를 정말로 비운 경우만 적었다(2번 지적). `code-review` 6단계 1의 "근거를 끝까지 열고 쓴다"를 어긴 것이고, 그 대목은 "고치며 새로 쓴 사실 문장" 19번에도 앞 절까지만 올랐다. 구현 때 실리는 지침을 어겨 다음 층의 리뷰가 잡은 사건이라 회차로 세고, 같은 일을 다룬 항목이 없어 새 항목이다. 층은 지침이다(문장이 근거보다 넓은지는 검사가 판정할 수 없다). 더하는 것이라 회차만 센다. backup-upgrade 계획의 1번 지적은 리뷰 반영이 아니라 산출물을 처음 쓸 때 난 것이라 회차로 세지 않고 그 항목의 본문에 곁들여 적었다.
14. 기각. ADR 0022가 변경 확인값 방식이 치르는 값을 적지 않았다(5번 지적). 그 방식은 ADR 0012가 이미 정한 것을 이은 기본값이라 인터뷰가 선택지로 묻지 않았고, 값을 적지 않은 것을 봇 리뷰가 잡아 병합 전에 더했다. 검사로 옮길 수 없고, ADR이 고른 방식의 값을 적는다는 것은 이 저장소의 ADR이 이미 따르는 관행이라 표준에 더할 새 판단 기준도 아니다.
