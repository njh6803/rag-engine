# search-eval 14: GPU 리랭크 기록과 장치 사이의 값 차 · 2026-11-15

티켓 `.scratch/search-eval/issues/14-gpu-rerank-records.md`를 구현한 기록이다. 브랜치는 `feature/14-gpu-rerank-records`다. `next-session` 지시문이 연 새 세션(Sonnet 5.5 / high)이 `EnterWorktree`로 워크트리 `14-gpu-rerank-records`에 들어와 이어 갔다. 티켓이 멈추라고 한 지점(기록 만들기가 2시간을 넘길 때)에서 사용자에게 물었고, 사용자가 "끝까지 돌린다"를 골랐다. 값의 차는 문턱을 넘지 않아 멈추지 않았다.

## 한 것

- 티켓 10이 보류한 `labr-01`의 사람 질문 문구를 "수습을 시작한 날부터 3개월 동안은"으로 고치고(사용자가 검수해 확정한 문구라 PR 본문에서 알렸다) `run --through fused --records write --tei-device gpu`로 질의 임베딩 기록을 다시 만들었다. 310개 가운데 키 하나만 바뀌고 309개는 바이트까지 같았다. 리랭크 기록의 키가 질의 글을 담으므로 이 순서를 리랭크 기록보다 앞에 뒀다.
- GPU 이미지(`turing-1.9.4`)가 우회 없이 `--gpus all`과 compose의 GPU 예약만으로 임베딩 TEI와 리랭커 TEI 둘 다 떴다(드라이버 621.24, GTX 1660 Ti). 띄운 방법은 프로브 `tei-gpu/compose-gpu.yml`이고 서버 로그를 남겼다.
- 처리량은 임베딩 1.60개/초, 리랭크 1.58쌍/초였다. 15,000쌍의 어림은 158분이라 2시간을 넘었다.
- 값의 차(프로브 `tei-gpu/device_diff.py`, 글 32개와 쌍 32개). 임베딩은 CPU 두 번이 완전히 같았고 GPU 두 번은 같지 않았다(코사인 최솟값 0.99998, 최대 절대 차 6.6e-4). CPU와 GPU 사이는 코사인 최솟값 0.999937이다. 리랭크 점수는 각 장치의 두 번이 같았고 CPU와 GPU 사이의 최대 차가 3.2e-4였다. 문턱(코사인 0.999, 점수 차 0.01) 안이다.
- 리랭크 기록 `records/rerank.jsonl`(15,476쌍)을 GPU로 만들었다. 16:10:09에 시작해 19:34:20에 끝났고 3시간 24분 11초(약 1.26쌍/초)가 걸렸다. `records.json`의 세 항목이 모두 `device: gpu`, `tei_version: 1.9.4`다. `records/` 전체는 약 11.8MB다.
- TEI를 모두 멈추고 리랭커 끝점 없이 `run --through rerank --records read`를 돌려 종료 코드 0과 새로 계산 0을 확인했다. 지표는 기록을 쓴 실행과 같았다(리랭크 뒤 적중률@1 0.774, MRR 0.861, nDCG@10 0.876).
- 저장소 상태 시험(`tests/tools/test_search_eval_public_docs.py`)의 기록 파일 목록에 `rerank.jsonl`을 더했고 루트 `README.md`의 `evals/` 줄을 고쳤다.

## 정한 것

- 2시간을 넘길 전망일 때 티켓대로 멈춰 물었고 사용자가 끝까지 돌리기를 골랐다. 시작 직후 어림은 약 2.7~3.1시간이었고 실제는 3시간 24분이었다. 처리량 프로브(1.58쌍/초)보다 느린 1.26쌍/초가 나온 까닭은 재지 않았다.
- 장치가 섞인 항목은 없다. 조각과 질의 임베딩은 티켓 10이 GPU로 만들었고 이 티켓이 새로 계산한 것은 질의 하나와 리랭크 점수뿐이라 07이 남긴 한계(CPU 값에 `gpu`를 적는 일)에 걸리지 않았다.
- 손으로 센 수치(GPU 점수 분포, 최대 차 쌍의 점수, VRAM)는 프로브 README와 티켓 Comments에 "손으로 봤다"를 붙였다. 값 JSON은 커밋하지 않았다.
- 티켓 19가 먼저 병합돼(PR #52) `probes/README.md`가 충돌했다. 양쪽이 같은 표 끝에 행을 더한 것이라 두 쪽 행을 모두 남기고 dev를 이 브랜치에 합쳤다.

## 검증

- `validate evals/public-docs`가 `문제 없음`이다. `uv run python tools/run_checks.py`가 종료 코드 0이다(pytest 579초). 합치기 커밋의 pre-commit도 통과했다.
- 값의 차 프로브는 CPU 컨테이너를 내렸다 올리는 일을 손으로 했다. 출력은 이름표만 갖는다.

- 이 반영이 새로 쓴 사실 문장(PR 직전 리뷰가 겨냥할 것): 프로브 README의 `device_diff.py` 행과 `compose-gpu.yml` 행의 손으로 센 수치 괄호, 티켓 Comments의 값의 차 항목과 리랭크 기록 항목.

## 회고

후보 넷을 내고 승인 1, 기각 3, 넘김 0이다. 새로 쓴 대기열 항목은 없고 회차를 더한 항목이 하나다. 만료할 항목은 없었다(`queue_open_rows.py`가 `origin/dev` 기준과 이 워크트리 기준 모두 만료 없음).

- 승인. 근거를 적은 문장이 출력이 가르지 못하는 사실을 담았다. 프로브 README 행과 티켓 Comments가 출력에 없는 수치(GPU 점수 분포, 최대 차의 쌍의 점수, VRAM)를 "손으로 봤다" 없이 적었고, 프로브 독스트링의 "158개 순환"과 "약 900자"는 `build`를 불러 재니 155개와 716~1211자였다. 재지 않은 "`compare`의 허용 오차로 흡수된다"와 "요청 평균 약 19초"도 적었다. 셀프 리뷰 두 축이 잡았다. 열린 항목 `measured-claim-beyond-probe`가 이미 처방한 사건이라 8회차를 더했다(`.scratch/retro-queue/measured-claim-beyond-probe.md`. 이 항목은 이미 5회차를 넘어 chore 계기다). 이번에는 프로브 README와 독스트링과 티켓 Comments에서 났고 처방의 자리인 `to-spec`이 이 셋에 닿지 않는다는 것을 그 항목 본문에 적었다.
- 기각. 전체 `pre-commit`이 이 브랜치의 두 커밋에서 각각 약 10분을 돌아 커밋 명령이 Bash의 600초 상한에서 백그라운드로 넘어갔다. 첫 커밋은 시험 파일 한 줄을 고쳤고 둘째는 dev의 `src`를 합친 병합 커밋이라 문서만 바뀐 커밋이 아니다. 열린 항목 `docs-only-commit-full-pytest`의 대상이 아니고 게이트가 설계대로 돈 것이다.
- 기각. `run --through rerank --records read`가 임베딩 끝점 환경 변수(`RAG_EVAL_EMBEDDING_URL`)를 요구해 처음 한 번 종료 코드 1로 끝났다. `eval_environment.py`의 `REQUIRED_ENV`가 데이터베이스에 붙는 하위 명령 모두에 이 이름을 요구한다고 적은 의도된 설계이고 결함이 아니다. 티켓 15의 CI 잡이 알아야 할 사실이라 아래 "다음"에 적었다.
- 기각. 스크래치 스크립트와 프로브(`.scratch`)의 pyright 진단이 대화에 새 진단으로 올라왔다. 게이트가 보지 않는 파일의 소음이고 판단을 바꾼 것이 없다(앞 세션 일지의 같은 기각과 같다).

## 다음

- 이 PR이 병합되면 티켓 14는 끝이다. `.scratch/search-eval/plan.md`의 `끝` 줄은 아직 없다. 열린 티켓은 11, 13, 15, 16, 17, 18이다. 11(빠른 게이트의 CI, PR #51)은 다른 세션이 맡아 돌고 있다. 14가 끝나면 17(리랭커 켬·끔 실험)과 18(최소 점수 분포 측정)이 막힌 것이 없어 나란히 돈다. 15는 11을, 13과 16은 11의 기준 보고서를 기다린다.
- 18은 `run --through rerank`의 보고서 `score_distribution`이 이 기록으로 읽힌다. 리랭커 끝점 없이 `--records read`로 돌 수 있다(임베딩 끝점 환경 변수는 `read`에서도 필수다).
- 티켓 15의 CI 잡이 읽는 기록으로 돌 때 알아 둘 것: `run --records read`는 리랭커 끝점 없이 돌지만 임베딩 끝점 환경 변수(`RAG_EVAL_EMBEDDING_URL`)는 데이터베이스에 붙는 모든 하위 명령이 요구한다(`eval_environment.py`의 `REQUIRED_ENV`). TEI를 띄우지 않는 CI라도 이 이름에 값(주소)을 줘야 한다. `read` 모드는 그 주소를 부르지 않는다는 것은 TEI를 멈추고 돌려 확인했다.
- 기록을 다시 만들면 GPU 임베딩이 비트까지 같지 않아 값이 조금씩 달라지고, 그러면 `compare`가 기록 해시 불일치로 실패해 기준 보고서를 새로 만들어야 한다. 기록은 가능한 한 다시 만들지 않는다. 다시 만들 일이 생기면 약 3시간 반(리랭크)과 35분(조각 임베딩)이 든다.
- GPU 평가용 컨테이너와 DB 볼륨은 지웠다. 모델 캐시 볼륨 `search-eval-tei-probe-data`는 남겼다. 같은 compose(`probes/tei-gpu/compose-gpu.yml`)로 다시 띄운다.
