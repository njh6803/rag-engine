# admin 설계: 관리자 페이지 v0의 범위, 로그인, 화면 스택을 정한다 · 2026-11-26

source-sync의 마지막 티켓과 하네스 티켓들을 병합한 뒤 `next-session`이 낸 지시문으로 연 세션의 기록이다(Fable 5.2 / xhigh). 시작 프롬프트는 `/grill-with-docs admin 기능의 설계 인터뷰를 한다. .scratch/admin/plan.md가 넘겨받은 일을 모아 두었다`이고, 브랜치는 `docs/admin-design`(설계를 쓰는 면제 PR), 작업은 워크트리 `admin-design`에서 했다. 준비, 사용자가 넘긴 것, 확인한 것, 물은 것과 답, 합의 요약, 반영한 것을 차례로 두고, 그 뒤의 절은 일이 일어난 차례대로 덧붙인다.

## 준비

- 주 체크아웃(dev)에서 시작해 세션 제목을 `docs/admin-design`으로 바꿨다.
- 지시문대로 `tidy-checkouts`를 먼저 돌렸다. 주 체크아웃의 dev를 `61847dd`에서 `5d5651c`까지 당겼다(`git merge --ff-only --no-overwrite-ignore origin/dev`). 병합된 워크트리 `14-daily-cleanup`과 그 브랜치, 체크아웃되지 않은 브랜치 `worktree-review-report-to-journal-on-receipt`를 지웠다. `14-daily-cleanup`은 쉬는 세션 하나가 쥐고 있어 `end-holders`로 그 세션의 프로세스를 끝낸 뒤 지웠다. 사람에게 넘긴 것은 둘이고 보고만 했다. 워크트리 `14-reindex-version-switch`는 병합된 PR의 머리와 로컬 브랜치의 끝이 달라 도구가 지우지 않았다. 휴지통(`.claude/worktrees/.tidy-trash/`)은 `python.exe`(pid 41268)가 옛 가상 환경의 파일을 쥐고 있어 비우지 못했다.
- `EnterWorktree`(name `admin-design`)로 들어가 `git switch -c docs/admin-design`으로 브랜치를 땄다. 그때 `HEAD`는 `origin/dev`와 같은 `5d5651c`였다.
- `grill-with-docs`가 `grilling`과 `domain-modeling`을 불렀다.
- `uv run python tools/sibling_overlap.py`는 120초 제한을 넘겨 배경으로 넘어갔고 끝난 뒤 출력 파일로 봤다. ADR 번호 겹침이 없고 형제의 헌법 버전 최고는 1.5.9다. 그래서 이 PR의 ADR은 0024부터 쓰고, 헌법 버전은 1.5.10으로 올린다("반영한 것").

## 확인한 것

사실은 서브에이전트 다섯이 찾았다. 앞의 셋은 첫 라운드 전에 나란히 돌았고, 뒤의 둘은 첫 라운드의 답이 연 가지를 찾았다. 보고가 붙인 근거의 종류를 괄호에 옮기고, 이 세션이 직접 읽은 것은 "이 세션이 읽었다"로 적는다.

### 서브에이전트 보고 1~3 (원문이 세션 기록에 없다)

보고 셋(이 저장소의 지금 코드, agent-os의 관리 화면과 로그인 선례, 화면 기술과 로그인 후보의 웹 조사)은 `uv run python tools/extract_asks.py agents <세션 기록>`이 "보고가 기록에 없다"로 냈다. 브리프는 기록에 있고 보고의 원문만 없다. 아래는 이 세션이 보고를 받은 직후 사용자에게 적어 보인 글에서 옮긴 것이고, 보고가 사실마다 붙인 근거 표시는 원문이 없어 옮기지 못했다. 선택지의 설명에 넣은 사실 가운데 이 세션이 다시 대 본 것은 "이 세션이 직접 본 것"에 따로 적는다.

- **지금 코드에 없는 것.** 화면 코드, 계정·로그인·쿠키를 다루는 코드, 검색을 부르는 REST 경로, 문서의 조각 목록을 내는 경로, 문서 하나를 다시 시도하는 길, 도는 동기화를 취소하는 길, 그룹을 다루는 경로 전부, 지식베이스를 만들고 고치는 길, 원천 폴더의 목록을 내는 길이 없다. 인증은 `Authorization: Bearer` 토큰 하나다.
- **지금 코드에 있는 것.** 원천을 만들고 고치고 지우고 되살리는 요청, 연결 확인, 일시 중지와 다시 시작, 지금 동기화, 동기화 기록 조회는 source-sync가 관리 API로 지었다. 인증 토큰의 발급, 목록, 회수도 관리 API에 있다. 프록시가 443에서 TLS를 끝낸다.
- **검색에 걸린 시간.** 검색 한 번마다 로그 한 줄에 걸린 시간만 찍히고 어디에도 모이지 않는다.
- **search-eval은 끝났다**(2026-11-17). 기능 계획이 걱정한 순서 문제(평가 화면은 search-eval 구현 뒤에야 지을 수 있다)는 사라졌다.
- **agent-os의 선례.** 관리 화면은 pnpm 워크스페이스의 Next 앱이고 별도 이미지의 Node 서버가 낸다. 로그인은 PostgreSQL에 둔 계정과 쿠키 속의 짧은 JWT와 갱신용 번호다. 위젯 관리 화면을 설계할 때 사용자는 "서버가 HTML을 직접 그리기"와 "화면을 파일로 지어 백엔드가 함께 내기"를 고르지 않았다.
- **다른 설치형 제품의 로그인.** 조사한 아홉 가운데 Grafana, Portainer, Open WebUI, Dify, RAGFlow, Onyx는 계정 로그인이고, Qdrant와 Meilisearch의 관리 화면은 브라우저가 API 열쇠를 든다. 관리 토큰으로 로그인해 쿠키로 유지하는 제품은 없었다.
- **채택도와 라이선스.** npm 주간 내려받기는 React 2.7억, Vite 2.9억, Next 0.9억, htmx 52만이고 Stack Overflow 2026 조사에서 쓴다는 응답은 React 41.5%, Next 20.6%, htmx 5.4%다. React, Vite, Next는 MIT, Jinja2는 BSD, htmx는 0BSD, argon2-cffi는 MIT, Authlib은 BSD다. 이 세션은 첫 라운드의 본문에 "수치는 2026-11-26에 npm과 Stack Overflow 2026 조사의 원문을 받아 대 본 값"이라고 적었다.

### 서브에이전트 보고 4 (그룹·지식베이스와 평가 코드. 읽기만 했고 근거는 코드, 문서, 어림 셋으로 갈랐다)

- **그룹과 지식베이스는 지울 수 없게 지어져 있다.** 두 표를 가리키는 외래 키에 지울 때의 동작이 없어 가리키는 행이 있으면 지우기가 실패하고, 지우는 코드도 없다(코드: `src/rag_engine/adapters/postgres/tables.py` 73~118줄과 그 밖의 표 정의). `Catalog` 포트에는 그룹의 목록·고치기·지우기, 지식베이스의 지우기·이름 바꾸기, 지식베이스에서 그룹 빼기가 없다(코드: `src/rag_engine/domain/ports.py` 148~293줄).
- **`migrate`가 덮는 칸.** 기본 지식베이스의 임베딩 끝점·모델·차원, 리랭커 끝점·모델, 청킹 셋, 최소 점수를 설정값과 다르면 덮는다. 이름, 설명, 기본 여부, 현재 색인 판 참조는 덮지 않는다(코드: `src/rag_engine/app/default_records.py` 46~94줄). 단독 compose에서는 `migrate` 서비스가 서버 앞에서 한 번 돈다(코드: `deploy/standalone/compose.yaml` 120~122줄).
- **지식베이스마다 다른 임베딩 서버를 부르게 조립되어 있다.** 끝점과 모델은 지식베이스와 색인 판의 칸이고, 서버와 작업자는 색인 판에 적힌 값마다 임베더를 만들어 돌려쓴다(코드: `src/rag_engine/adapters/tei.py` 358~417줄).
- **원천의 그룹을 바꾸는 코드는 없다.** 가져오는 원천은 만들 때만 그룹을 정하고 고치기는 설정, 제외 패턴, 일정만 받는다(코드: `src/rag_engine/app/pull_sources.py` 189~251줄).
- **읽기용 인증 토큰의 지식베이스 범위는 외래 키가 아닌 배열이다**(코드: `tables.py` 352줄).
- **평가 유스케이스는 기본 지식베이스에 박혀 있다.** 지식베이스의 이름을 인자로 받지 않고 기본 원천의 문서 키로 기대 근거를 찾는다(코드: `src/rag_engine/app/eval_run.py` 22, 459~481줄).
- **평가의 명령줄 입구는 평가 전용 데이터베이스에만 붙는다.** 데이터베이스 이름이 `rag_eval`로 시작하지 않으면 접속 전에 거부하고(코드: `src/rag_engine/adapters/eval_environment.py` 85~112줄), 데이터베이스에 묶음 밖의 문서가 한 건이라도 있으면 색인, 실행, 판정을 거부한다(코드: `src/rag_engine/app/check_eval_database.py` 33~88줄). `tools/`는 이미지에 실리지 않는다(문서: `.scratch/search-eval/spec.md` 71줄).
- **LLM으로 나가는 것은 질의 글 전체와 조각 글 전체다**(코드: `src/rag_engine/adapters/claude_judge.py` 77~123줄). 판정 파일과 추론 기록에는 글 없이 해시만 남는다.
- **걸린 시간의 기록.** 공공 문서 묶음(문서 46개, 질의 310개)에서 리랭크 점수를 처음 계산한 실행은 개발 PC의 GPU로 3시간 24분 11초였고(문서: `.scratch/search-eval/issues/14-gpu-rerank-records.md` 27줄), CPU에서 리랭커를 켠 후보 50개 검색 한 번은 130초였다(문서: `.scratch/search-eval/issues/17-reranker-on-off-experiment.md` 11, 20줄).
- **`/docs`와 `/openapi.json`은 관리 토큰이 있어야 열린다.** 첫 보고가 어림으로 남겼던 것을 이 보고가 확인했다.
- 보고는 과제 문구의 전제 둘이 실제와 다르다고 먼저 적었다. 판정 결과는 `records/`가 아니라 묶음 루트의 `judgments.jsonl`에 쌓이고, `.scratch/search-eval/plan.md`에는 admin을 든 문장이 없다(넘긴 글은 `.scratch/admin/plan.md`와 search-eval 명세, ADR 0018에 있다).

### 서브에이전트 보고 5 (agent-os의 웹 워크스페이스. 읽기만 했다)

- **부품 패키지.** 부품은 열하나다. atoms 일곱(`AccountStatusBadge`, `Button`, `Card`, `Icon`, `IconButton`, `Progress`, `StatusBadge`)과 molecules 넷(`Alert`, `Markdown`, `Switch`, `TextField`)이다(코드를 읽었다: agent-os `web/packages/ui/src/index.ts` 5~32줄). 그 패키지는 agent-os의 다른 패키지나 앱을 가져다 쓰지 않는다(Grep 결과와 그 패키지의 `package.json` 25~50줄을 읽었다). 파일은 `node_modules`를 빼고 644개이고 그중 554개가 사진 비교의 정답 PNG다(find와 wc로 셌다). 보고는 부품 열하나 가운데 본문을 끝까지 읽은 것이 `TextField`와 `Alert`뿐이라고 적었다.
- **사진 비교.** 버전을 고정한 Playwright Docker 이미지 안에서만 돌고 `maxDiffPixels: 0`이다(코드를 읽었다: agent-os `web/packages/ui/visual/playwright.config.ts` 13~18, 35~38줄).
- **CI에 걸린 시간.** 2026-11-24 기록에서 실행 40개의 최소·중앙·최대(분)는 web 3.3·4.5·5.7, e2e 1.2·1.6·8.5, visual 5.7·7.5·8.3이다(문서를 읽었다: agent-os `.scratch/harness/probes/README.md`).
- **타입 우회 금지.** ESLint 설정이 `any`, 타입 단언, `!`, `@ts-ignore`, `@ts-nocheck`를 막고 줄마다 규칙을 끄는 주석도 막는다(코드를 읽었다: agent-os `web/eslint.config.mjs`).

### 이 세션이 직접 본 것

- **agent-os의 ADR 셋.** ADR 0062(계정 로그인. 통째로 읽으면 한도에 걸려 나눠 읽었고, 압축 뒤 1~30줄을 다시 읽었다), ADR 0020(원칙 III을 TypeScript로 넓힌다), ADR 0021(웹 워크스페이스의 스택)을 읽었다. ADR 0062의 결정은 그 저장소에서도 문서에만 있고 코드는 없다. (바로잡음: 이 문장은 틀렸다. 코드를 보지 않고 썼고 셀프 리뷰의 두 축이 잡았다. agent-os는 그 결정을 기능 `admin-login`으로 짓는 중이고, 2026-11-26에 티켓 열넷 가운데 셋이 끝나 계정 표, 비밀번호 해시, 요청 출처 검사, 시스템 관리자 명령의 코드가 있다. 아래 "셀프 리뷰"의 "판정".)
- **agent-os의 버전.** `web/package.json`에서 `pnpm@11.24.0`, Node `>=24 <25`, Storybook `^10.6.1`, Vitest `^5.0.2`, Playwright `^1.63.0`, openapi-typescript `^7.13.0`을 읽었다.
- **npm 레지스트리(2026-11-26에 조회했다).** typescript-eslint 8.74.0이 요구하는 TypeScript는 `>=4.8.4 <6.1.0`, openapi-typescript 7.13.0은 `^5.x`이고, TypeScript의 최신은 7.0.2다. 공개 부품 라이브러리의 주간 내려받기(2026-11-18~24, npm 통계 API)는 Radix 약 2,900만, MUI 약 1,500만, Ant Design 약 540만, Mantine 약 380만이다.
- **agent-os의 관리 화면에 없는 부품.** `web/apps/admin/components`에서 `<dialog`, `<table`, `<select`, `type="file"`을 찾았다. 표를 쓰는 화면은 하나이고 대화 상자, 선택 목록, 파일 올리기를 쓰는 곳은 없다.

**질문 1 (평가 화면).** "검색 평가(평가 세트를 등록하고 돌려서 적중률을 보는 일)를 관리자 페이지에서 하는 화면을 이번 v0에 넣을까요? 킥오프가 정한 0.1 화면 넷(현황, 원천, 문서, 검색 시험)과 이 기능의 수락 기준에는 평가 화면이 없고, 지금 평가는 개발자가 명령으로만 돌립니다."

- "v0에서 빼고 새 기능으로 (Recommended)": 이번 v0는 화면 넷만 짓습니다. 평가를 등록하고 돌리고 결과를 보는 화면과 그 관리 API, 결과를 담을 표는 새 기능 하나로 떼어 0.1 정식 릴리스 뒤(1.0 묶음)에 둡니다. 함께 넘어가는 결정은 넷입니다: 지식베이스마다 문서를 LLM 쪽으로 내보내도 되는지 허용하는 장치, 평가 세트와 판정 결과를 어디에 얼마나 보관할지, 최소 점수 기본값을 화면에서 고치기, 화면을 짓는 순서. 0.1에서 평가는 지금처럼 개발 도구와 CI로만 돕니다.
- "관리 API와 표만 이번에": 평가를 등록·실행하고 결과를 조회하는 관리 API와 결과 표를 이번에 짓고, 화면은 새 기능으로 넘깁니다. 0.1에서 명령줄로 평가를 돌릴 수 있게 되지만, 문서를 LLM 쪽으로 내보내는 허용 장치와 평가 세트 보관(원본 문서의 내용을 남기지 않는다는 원칙에 닿습니다)을 이번 설계에서 정해야 해서 인터뷰와 명세가 그만큼 길어집니다.

**질문 3 (로그인).** "사람이 브라우저로 관리자 페이지에 들어올 때 무엇으로 확인할까요? 지금 서버는 요청마다 인증 토큰(비밀 문자열)만 확인하고, 계정·로그인·쿠키를 다루는 코드는 없습니다. 어느 쪽을 고르든 MCP 클라이언트와 문서를 보내는 시스템 같은 프로그램은 지금처럼 인증 토큰을 씁니다."

- "운영자 계정으로 로그인 (Recommended)": 아래 인용의 설명.
- "관리 토큰으로 로그인, 쿠키로 유지": 계정을 두지 않습니다. 로그인 화면에 관리 토큰을 한 번 붙여 넣으면 서버가 확인하고 쿠키를 내려 줍니다. 계정 표와 비밀번호 처리가 없어 계정 방식보다 작지만, 쿠키 유지와 위조 요청 막기는 똑같이 지어야 합니다. 문서 담당자마다 관리 토큰(토큰 발급과 원천 삭제까지 되는 열쇠)을 하나씩 발급해 줘야 하고, "누가"는 토큰 이름으로만 구분합니다. 조사한 설치형 제품 아홉 가운데 이 방식은 없었습니다.
- "관리 토큰을 브라우저가 든다": 서버는 거의 바꾸지 않습니다. 화면에 관리 토큰을 붙여 넣으면 브라우저가 들고 있다가 요청마다 보냅니다. Qdrant와 Meilisearch의 관리 화면이 이 방식입니다. 토큰을 탭의 메모리에만 두면(Meilisearch) 새로 고칠 때마다 다시 붙여 넣어야 하고, 브라우저 저장소에 두면(Qdrant) 화면에 끼어든 스크립트 하나가 토큰을 읽어 갈 수 있어서 보안 권고(OWASP)가 하지 말라고 적는 방식입니다.
- "사내 통합 로그인(OIDC)에 맡긴다": 설치처의 통합 로그인 서버(Keycloak, AD FS 등)로 보내 확인합니다. 비밀번호를 이 제품이 다루지 않습니다. 설치처마다 그런 서버가 있어야 해서 폐쇄망의 깨끗한 VM 하나에 설치하는 0.1의 장면과 맞지 않습니다. Grafana, Open WebUI, Onyx는 계정 로그인을 기본으로 두고 통합 로그인을 덧붙이는 식으로 제공합니다. 라이브러리(Authlib, BSD)가 하나 더 듭니다.

> 사용자: "운영자 계정으로 로그인 (Recommended)" — 설명: 이름과 비밀번호로 로그인합니다. 계정은 제품의 PostgreSQL에 두고, 첫 계정은 서버에서 치는 명령으로 만듭니다. 로그인 상태는 화면의 스크립트가 읽지 못하는 쿠키로 유지합니다. agent-os에서 고르신 방향과 같고, Grafana·Portainer·Open WebUI·Dify 같은 설치형 제품도 이 방식입니다. 치르는 값: 계정 표, 비밀번호 해시 라이브러리(argon2-cffi, MIT), 틀린 비밀번호 잠금, 로그인 유지, 위조 요청 막기를 새로 지어 이 기능이 그만큼 커집니다. 사람마다 계정이 있어서 뒤에 올 변경 기록("누가 지웠는지")과 역할 나누기의 바탕이 됩니다.

**질문 4 (화면 기술).** "관리자 페이지 화면을 어떤 기술로 만들까요? 지금 저장소에는 화면 코드가 없고, 설치 구성은 프록시(nginx)가 443 포트 하나로 받아 경로에 따라 파이썬 서버로 넘기는 모양입니다. 헌법의 스택 문서는 후보로 "pnpm과 Next의 웹 워크스페이스, 또는 서버가 그리는 단순한 화면"을 적어 두었습니다."

- "파일로 지어 내보낸다 (React + Vite) (Recommended)": 화면을 React와 TypeScript로 만들고 Vite로 HTML·JS 파일 묶음으로 짓습니다. 설치된 서버에서는 Node가 돌지 않고 파일을 내보내기만 합니다(무엇이 내보낼지, 곧 작은 웹 서버 컨테이너를 따로 둘지 파이썬 서버가 함께 낼지는 다음 라운드에 여쭙니다). agent-os의 도구(React, TypeScript, ESLint, Vitest, Playwright, OpenAPI에서 타입 만들기) 대부분을 그대로 쓰고 Next만 빠져서, 주소 처리 라이브러리를 따로 고릅니다. React와 Vite 모두 MIT이고 npm 주간 내려받기가 각각 2.7억, 2.9억 회입니다. agent-os에서는 이와 가까운 안("React 화면을 파일로 지어 백엔드가 함께 내기")을 고르지 않고 Next를 고르셨습니다.
- "Node 서버가 낸다 (Next + pnpm, agent-os와 같게)": 아래 인용의 설명.
- "파이썬 서버가 그린다 (Jinja2 + htmx)": 화면도 지금의 파이썬 서버가 HTML로 만들어 냅니다. Node가 빌드에도 실행에도 필요 없고 이미지와 컨테이너가 늘지 않습니다. 치르는 값: 템플릿 안의 코드는 타입 검사가 보지 못하고(어림), 조각 목록 넘겨 보기나 올리기 진행 표시 같은 움직임은 손이 더 가며, agent-os와 도구가 완전히 달라집니다. htmx를 쓴다는 응답은 5.4%입니다(React 41.5%, Stack Overflow 2026 조사). Jinja2는 BSD, htmx는 0BSD입니다. agent-os에서는 "서버가 HTML을 직접 그리기"를 고르지 않으셨습니다.

> 사용자: "Node 서버가 낸다 (Next + pnpm, agent-os와 같게)" — 설명: agent-os 관리 화면과 같은 도구 구성을 그대로 옮깁니다. 설정과 규칙을 베껴 올 수 있어 시작이 빠르고 두 저장소가 같은 모양이 됩니다. 설치된 서버에 Node 서버 컨테이너가 하나 더 돌아서 메모리가 더 들고(어림), Next와 Node의 보안 패치를 릴리스마다 따라가야 합니다. 릴리스 이미지가 둘에서 셋으로, 기본 컨테이너가 다섯에서 여섯으로 늡니다. Next를 파일로만 내보내는 길도 있지만 /documents/<문서 번호>처럼 번호가 들어가는 주소를 쓸 수 없는 제약이 있습니다(Next 문서). Next는 MIT, 주간 0.9억 회입니다.

### 라운드 1, 둘째 호출 (질문 넷)

앞의 답이 범위를 가장 크게 골라 열린 가지(평가의 세부, 그룹·지식베이스의 세부, 기능을 나눌지)에 넣을 사실은 서브에이전트 4에게 맡기고, 그 답과 서로 기대지 않는 넷을 먼저 올렸다. 호출 곁의 본문에는 질문마다 쓴 사실(원천의 관리 API는 이미 있다, 일시 중지는 다음 일정만 막는다, 문서 하나만 다시 돌리는 요청은 없다, 검색에 걸린 시간은 로그에만 있다)을 적었다.

**질문 5 (원천 화면).** "원천 화면에서 운영자가 어디까지 할 수 있게 할까요? 원천을 만들고, 고치고(폴더, 제외 패턴, 일정), 지우고 되살리고, 연결을 확인하고, 일시 중지하는 관리 API는 이미 지어져 있어서 화면만 더하면 됩니다. 킥오프가 적은 원천 화면은 목록, 일정, 마지막·다음 실행, 지금 동기화, 동기화 기록 보기까지입니다."

- "화면에서 다 한다 (Recommended)": 아래 인용의 설명.
- "보고 돌리는 것만": 목록, 일정, 마지막·다음 실행, 동기화 기록 보기와 지금 동기화, 일시 중지·다시 시작만 화면에 둡니다(킥오프의 원천 화면 정의). 원천 만들기·고치기·지우기는 지금처럼 명령줄에서 관리 API를 부릅니다. 원천은 설치할 때 한두 번 만드는 것이라는 판단입니다. 일정을 고르는 화면과 폴더를 고르는 화면은 짓지 않게 됩니다.
- "보고 돌리기에 일정 고치기만": '보고 돌리는 것만'에 일정 고치기를 더합니다. 원천 만들기, 폴더 고치기, 지우기는 명령줄로 남습니다. 운영 중에 가장 자주 손대는 것이 일정이라는 판단입니다.

> 사용자: "화면에서 다 한다 (Recommended)" — 설명: 목록과 동기화 기록 보기, 지금 동기화, 일시 중지·다시 시작에 더해 가져오는 원천 만들기(그룹 고르기 포함), 폴더·제외 패턴·일정 고치기, 연결 확인, 지우기·되살리기까지 화면에서 합니다. 운영자가 명령줄에서 관리 API를 직접 부를 일이 없어집니다. 원천 화면에 입력 폼과 확인 창이 늘어 티켓이 한둘 더 듭니다(어림). 폴더를 화면에서 어떻게 고르게 할지와 일정을 어떻게 고르게 할지는 다음 라운드에 여쭙니다.

**질문 6 (동기화 멈춤).** "돌고 있는 동기화만 멈추는 요청과 화면의 '멈추기' 단추를 둘까요? 지금 도는 동기화를 멈추는 길은 그 원천을 지웠다가 되살리는 것뿐이고(ADR 0023), 그동안 그 원천의 문서가 검색에서 빠집니다. 일시 중지는 다음 일정을 막을 뿐 이미 도는 동기화는 멈추지 않습니다."

- "멈추기 요청과 단추를 둔다 (Recommended)": 원천과 문서는 건드리지 않고 그 동기화만 멈추는 관리 API 하나를 더하고, 원천 화면의 도는 동기화 옆에 '멈추기'를 둡니다. 작업자는 동기화 도중 주기적으로 멈춤 표시를 보고 끝내며(지금 원천의 지움 표시를 보는 간격은 기본 200초입니다), 동기화 기록에는 '운영자가 멈춤'이라는 사유가 새로 남습니다. 멈추기 전에 반영한 문서는 그대로 두고, 원천에서 사라진 문서를 지우는 단계는 하지 않습니다. 화면에 '지금 동기화' 단추가 생기면 잘못 누른 동기화(특히 전부 다시 읽기)를 되돌릴 길이 필요해진다는 판단입니다.
- "이번에는 두지 않는다": 관리 API와 사유 코드를 늘리지 않습니다. 잘못 건 동기화는 끝나기를 기다리고, 꼭 멈춰야 하면 지금처럼 원천을 지웠다가 되살립니다. 0.1의 커넥터는 폴더를 훑는 서버 경로 하나라서 동기화는 언젠가 끝납니다. 멈추기 요청은 끝없는 목록을 낼 수 있는 SQL 원천 기능(db-source, 1.0)으로 넘깁니다.

> 사용자: "멈추기 요청과 단추를 둔다 (Recommended).
> 근데 멈추기 말고 다른 용어로 하자.
> 중지, 정지, 취소 등 추천해줘"

선택지에 없는 답을 사용자가 직접 썼다. 첫 선택지를 고르면서 이름을 다시 추천해 달라고 한 것이라, 이름은 질문 13으로 다시 올렸다. 위 선택지의 설명에 든 "멈추기", "멈춤 표시", "운영자가 멈춤"은 질문 13의 답에 따라 "취소"로 읽는다.

**질문 7 (다시 수집).** "실패했거나 건너뛴 문서 하나만 다시 수집하게 하는 요청과 문서 화면의 '다시 수집' 단추를 둘까요? 지금은 문서 하나만 다시 돌리는 요청이 없습니다. 킥오프가 적은 문서 화면에는 '다시 수집'이 들어 있고, source-sync 명세가 이 요청을 이 기능으로 넘겼습니다."

- "문서 하나 다시 수집을 둔다 (Recommended)": 아래 인용의 설명.
- "이번에는 두지 않는다": 문서 화면은 실패 사유와 건너뛴 사유만 보여 줍니다. 올린 문서는 같은 파일을 다시 올리고, 가져온 문서는 원천 화면에서 '전부 다시 읽기'로 그 원천 전체를 동기화합니다. 관리 API가 늘지 않습니다.

> 사용자: "문서 하나 다시 수집을 둔다 (Recommended)" — 설명: 관리 API 하나와 문서 화면의 단추를 더합니다. 올린 문서는 서버가 보관해 둔 원본으로, 가져온 문서는 원천 폴더에서 그 파일만 다시 읽어 파싱부터 다시 합니다. 파서나 임베딩 서버가 잠깐 멈춰서 실패한 문서 몇 건을 살릴 때 원천 전체를 다시 읽지 않아도 됩니다.

**질문 8 (검색 지연).** "현황 화면의 '최근 검색 지연'에 쓸 값을 어디에 모을까요? 지금 검색에 걸린 시간은 로그 줄에만 찍히고 어디에도 모이지 않습니다. 진단 묶음 명령(diag-bundle, 아직 설계 전)도 같은 값을 실어야 합니다. 어느 쪽을 고르든 질문의 내용은 남기지 않고 걸린 시간만 남깁니다(ADR 0004)."

- "데이터베이스 표에 걸린 시간만 적는다 (Recommended)": 아래 인용의 설명.
- "서버 메모리에 최근 것만 둔다": 서버 프로세스가 최근 몇백 건을 메모리에 들고 있다가 현황 화면에 냅니다. 표가 늘지 않습니다. 서버를 다시 띄우면 비고, 진단 묶음 명령은 다른 프로세스라서 이 값을 읽지 못해 그 기능이 다른 길을 찾아야 합니다.
- "v0 현황에서는 뺀다": 현황 화면에 검색 지연을 싣지 않고 로그에만 둡니다. 어디에 모을지는 진단 묶음 기능의 설계가 정하고, 현황 화면에는 그 뒤에 붙입니다. 킥오프가 적은 현황 화면의 항목 하나가 빠집니다.

> 사용자: "데이터베이스 표에 걸린 시간만 적는다 (Recommended)" — 설명: 검색 한 번마다 시각과 걸린 시간(전체, 임베딩, SQL, 리랭커)만 표에 한 줄 적고, 정해 둔 기간이 지난 줄은 지웁니다. 서버를 다시 띄워도 남고, 서버와 따로 도는 진단 묶음 명령도 같은 표를 읽을 수 있습니다. 검색마다 쓰기 한 번이 늘고, 표 하나와 오래된 줄을 지우는 일이 늡니다. 보관 기간과 화면에 보일 값(가운데값, 느린 쪽 값 등)은 명세가 정합니다.

### 라운드 2, 첫 호출 (질문 넷)

호출 곁의 본문에는 서브에이전트 4가 찾은 사실(평가 코드는 평가 전용 데이터베이스에서만 돈다, CPU에서 리랭커를 켠 검색 한 번이 130초였다, LLM 판정은 질의와 조각의 글 전체를 보낸다, 그룹과 지식베이스는 지울 수 없게 지어져 있다), 낯선 말의 풀이 셋(Argon2id, 짧은 서명 값과 갱신용 번호, 출처 표시 `Sec-Fetch-Site`), 추천의 근거를 적었다.

**질문 9 (기능 나누기).** "v0의 범위가 로그인과 계정, 화면 넷(현황, 원천, 문서, 검색 시험), 그룹·지식베이스 관리, 평가 화면으로 커졌습니다. 이 일을 기능(명세와 티켓을 따로 갖는 작업 단위) 하나로 둘까요, 나눌까요? 어느 쪽을 고르든 모두 0.1 정식 릴리스에 들어갑니다."

- "셋으로 나눈다 (Recommended)": 아래 인용의 설명.
- "둘로 나눈다": admin에 그룹·지식베이스 관리까지 넣고, 평가 화면만 새 기능으로 떼어 0.1 정식 릴리스를 막는 기능으로 올립니다. 그룹·지식베이스의 세부(지울 때 그 안의 문서 처리, 화면에서 고친 설정과 .env의 우선순위, 재색인)는 이번 인터뷰에서 정하고, 평가 화면의 세부는 그 기능의 설계 인터뷰에서 정합니다.
- "하나로 두고 이번에 모두 정한다": admin 하나에 전부 담고, 이번 인터뷰에서 평가와 그룹·지식베이스의 세부까지 정합니다. 명세 하나에 화면이 일곱쯤 들어가고 티켓이 스무 개를 넘습니다(어림). 인터뷰가 이 세션에서 여러 라운드 더 이어집니다.

> 사용자: "셋으로 나눈다 (Recommended)" — 설명: admin(로그인과 계정, 화면의 틀과 이미지, 화면 넷과 그 API)과 새 기능 둘(그룹·지식베이스 관리, 평가 화면)로 나눕니다. 셋 모두 0.1 정식 릴리스를 막는 기능으로 전체 계획에 올립니다. 이번 인터뷰는 admin을 끝까지 정하고, 새 기능 둘은 넘겨받은 일을 각자의 계획으로 옮겨 각자의 설계 인터뷰에서 세부를 정합니다. 명세와 리뷰의 단위가 작아지고, 화면 넷을 먼저 지어 쓰면서 뒤의 둘을 설계할 수 있습니다. 평가 화면은 정할 것이 특히 많습니다: 지금 평가 코드는 평가 전용 데이터베이스와 기본 지식베이스에서만 돌게 지어져 있고(코드를 읽었습니다), CPU에서 리랭커를 켠 검색 한 번이 130초였습니다(search-eval 티켓 17의 기록).

**질문 10 (로그인 세부).** "운영자 계정 로그인의 세부를 agent-os에서 정하신 것(agent-os ADR 0062)과 같게 둘까요? agent-os에서도 이 결정은 아직 문서에만 있고 코드는 없어서, 옮겨 오는 것은 코드가 아니라 결정입니다."

- "agent-os와 같게 옮긴다 (Recommended)": 아래 인용의 설명.
- "줄여서 옮긴다": 비밀번호 규칙, 저장 방식, 잠금, 로그인 유지, 위조 요청 막기는 agent-os와 같게 둡니다. 다만 계정은 단계 없이 모두 같은 권한이고, 계정 만들기와 비밀번호 다시 정하기는 서버 명령으로만 합니다. 화면에는 로그인, 로그아웃, 내 비밀번호 바꾸기만 둡니다. 계정 관리 화면과 비밀번호 링크가 빠져 티켓이 줄지만, 문서 담당자를 한 명 늘릴 때마다 서버에 들어갈 수 있는 사람이 명령을 쳐야 합니다.
- "하나씩 다시 정한다": 계정의 단계, 비밀번호 규칙, 로그인 유지 방식, 잠금을 이 인터뷰에서 하나씩 여쭙니다. agent-os에서 이틀에 걸쳐 정하신 것을 다시 묻게 되고, 두 제품의 로그인이 달라질 수 있습니다.

> 사용자: "agent-os와 같게 옮긴다 (Recommended)" — 설명: 계정은 시스템 관리자 하나(지울 수 없음)와 관리자 여럿이고, 역할 나누기는 0.1 뒤로 둡니다. 첫 계정은 서버 명령으로 만들고, 그 뒤 계정은 화면에서 만들어 '비밀번호 정하는 링크'(한 번만, 24시간)를 건넵니다. 계정은 지우지 않고 '쓰지 않음'으로 돌립니다. 비밀번호는 8~128자에 대문자·숫자·특수문자를 요구하고, 저장은 Argon2id(보안 권고 OWASP의 최소 설정과 같은 값)로 합니다. 5번 연속 틀리면 1분 잠그고 두 배씩 늘려 최대 1시간까지 잠급니다. 로그인 유지는 쿠키 속 짧은 서명 값(기본 5분)과 서버가 기억하는 갱신용 번호로 하고, 쉬는 시간 기본 30분·총 8시간을 운영자가 설정합니다. 위조 요청은 브라우저가 붙이는 출처 표시(Sec-Fetch-Site)로 막습니다. 로그인 기록은 데이터베이스에 남기고 그 화면은 뒤로 둡니다. 2단계 인증과 통합 로그인은 0.1에 없습니다. 계정 관리 화면이 하나 늘어납니다. agent-os와 달라지는 점은 인증 토큰이 프로그램용으로 남는다는 것 하나입니다.

이 설명의 끝 문장("달라지는 점은 … 하나입니다")은 그때의 사실이다. 뒤의 질문 19에서 여는 주소를 물었고 답도 agent-os와 같은 쪽이어서, 달라지는 점은 여전히 인증 토큰과 그것에서 따라 나오는 것(자격마다 열리는 것, 공개 계정을 옮기지 않는 것)뿐이다(ADR 0025 "이 저장소에서 다른 것").

바로잡음: 질문 10의 글이 적은 "agent-os에서도 이 결정은 아직 문서에만 있고 코드는 없어서"는 틀렸다. 사용자에게 보인 글이라 위 인용은 그대로 두고 여기에 적는다. agent-os는 2026-11-26에 그 결정의 티켓 열넷 가운데 셋을 지어 두었다(아래 "셀프 리뷰"의 "판정"). 고른 선택지의 설명은 이 문장에 기대지 않지만, ADR 초안의 승인 질문에서 사용자에게 바로잡아 알린다.

**질문 11 (토큰 화면).** "인증 토큰(MCP 클라이언트와 프로그램이 쓰는 비밀 문자열)을 발급하고 회수하는 화면을 v0에 둘까요? 발급·목록·회수 관리 API는 이미 있어서 화면만 더하면 됩니다. 킥오프는 0.1에서 이 일을 화면 없이 하기로 적었습니다."

- "화면에 둔다 (Recommended)": 아래 인용의 설명.
- "0.1에서는 명령줄로": 화면을 두지 않습니다(킥오프의 0.1 범위). 토큰은 지금처럼 서버 명령(첫 토큰)과 관리 API 호출로 발급하고 회수합니다. 설치 안내가 그 명령을 적습니다.

> 사용자: "화면에 둔다 (Recommended)" — 설명: 토큰 목록(이름, 역할, 만료, 지식베이스 범위), 발급(값은 발급 직후 한 번만 보여 줍니다), 회수를 화면에서 합니다. MCP 클라이언트를 붙일 때마다 명령줄에서 관리 API를 부르지 않아도 됩니다. 원천 화면에서 "화면에서 다 한다"를 고르신 것과 같은 방향입니다. 화면이 하나 늘어납니다.

**질문 12 (수집 토큰).** "문서를 보내는 일만 할 수 있는 토큰(수집 전용 토큰)을 이번에 둘까요? source-sync 설계에서 "지금처럼 관리 토큰으로"를 고르시고 이 기능으로 넘기신 결정입니다. 그 뒤로 달라진 것은 사람이 로그인으로 들어오게 된다는 점뿐이고, 0.1에 문서를 보내 올 다른 시스템은 아직 정해진 것이 없습니다."

- "이번에도 두지 않는다 (Recommended)": 아래 인용의 설명.
- "수집만 되는 토큰을 원천 하나에 묶는다": 토큰 역할에 '수집'을 더합니다. 발급할 때 원천 하나를 고르고, 그 토큰은 수집 API로 그 원천에 문서를 넣고 지우는 일만 할 수 있습니다. 다른 원천, 관리 API, 검색을 부르면 거부됩니다. 토큰에 원천 칸이 늘고, 토큰 결정을 적은 ADR 0014에 이력을 더합니다.
- "수집만 되는 역할만 더한다": '수집' 역할의 토큰은 수집 API만 부를 수 있지만 어느 원천에든 넣고 지울 수 있습니다. 만들 것이 조금 적은 대신, 한 시스템에 준 토큰으로 다른 원천의 문서를 덮어쓰거나 지울 수 있습니다.

> 사용자: "이번에도 두지 않는다 (Recommended)" — 설명: 새 역할을 두지 않습니다. 문서를 보내는 시스템을 붙이는 설치처는 그 시스템에 관리 토큰을 넣어 줘야 하고, 그 토큰이 새면 토큰 발급과 모든 문서의 삭제까지 열립니다. 수집 전용 토큰은 접근 권한 기능(doc-permission, 1.0)의 계획으로 넘깁니다. 나중에 더해도 이미 발급한 토큰은 그대로 쓰입니다(역할 값 하나가 늘어나는 변경입니다).

### 라운드 2, 둘째 호출 (질문 둘)

호출 곁의 본문에는 이름 후보 넷을 용어집의 "일시 중지"와 나란히 놓은 표와 "취소"를 추천하는 까닭 셋, 폴더에 관해 확인한 사실(지금은 하위 폴더 이름을 글자로 적고, 그 아래의 폴더를 알려 주는 API는 없다)을 적었다.

**질문 13 (동기화 용어).** "돌고 있는 동기화 한 번을 운영자가 끝내는 일을 무엇이라고 부를까요? 화면 단추, 관리 API, 동기화 기록의 사유에 같은 말을 씁니다. 용어집에는 이미 '일시 중지'(다음 일정을 꺼 두는 것이고, 되돌리는 일은 '다시 시작')가 있어서 그 말과 헷갈리지 않아야 합니다."

- "취소 (Recommended)": 아래 인용의 설명.
- "중단": 단추는 '동기화 중단', 기록에는 '중단됨'으로 남습니다. 하던 데서 끊는다는 뜻이라 이미 반영된 문서를 되돌린다는 오해가 없습니다. 다만 같은 화면에 '일시 중지' 단추와 나란히 놓이면 두 말이 비슷해 헷갈릴 수 있습니다.
- "중지": 단추는 '동기화 중지', 기록에는 '중지됨'으로 남습니다. '일시 중지'와 낱말이 겹쳐서, 일정을 꺼 두는 것과 도는 동기화를 끝내는 것을 가르기가 넷 가운데 가장 어렵습니다.
- "정지": 단추는 '동기화 정지', 기록에는 '정지됨'으로 남습니다. '일시 중지'와 글자는 덜 겹치지만, 멈춰 세웠다가 다시 켤 수 있는 상태처럼 읽혀서 이어 하기가 되는 것으로 오해할 수 있습니다.

> 사용자: "취소 (Recommended)" — 설명: 단추는 '동기화 취소', 동기화 기록에는 '취소됨'으로 남습니다. '일시 중지'와 글자가 겹치지 않고, 이어 하지 못하며 새로 돌려야 한다는 뜻이 담깁니다. ADR 0023이 이미 "도는 동기화를 취소하는 요청"이라고 적었고, GitHub Actions와 Airbyte 같은 도구도 도는 작업을 끝내는 일을 cancel이라고 부릅니다(어림: 기억에 기댄 것이고 이번에 원문을 받아 보지는 않았습니다). 조심할 점: '취소'가 이미 반영된 문서까지 되돌린다는 뜻으로 읽힐 수 있어서, 확인 창에 "이미 반영된 문서는 그대로 남습니다"를 적습니다.

**질문 14 (폴더 고르기).** "가져오는 원천을 만들거나 고칠 때 읽을 폴더를 화면에서 어떻게 정하게 할까요? 지금은 설치할 때 붙여 둔 부모 폴더 아래의 하위 폴더 이름(예: 규정집)을 글자로 적고, 그 아래에 어떤 폴더가 있는지 알려 주는 API는 없습니다."

- "목록에서 눌러 고른다 (Recommended)": 아래 인용의 설명.
- "글자로 적고 연결 확인으로 본다": 폴더 이름을 입력 칸에 적고, 이미 있는 '연결 확인'으로 읽히는지 봅니다. 관리 API가 늘지 않습니다. 틀린 이름은 확인에서 "읽을 수 없음"으로 알게 되고, 어떤 폴더가 있는지는 서버 기계에서 따로 봐야 합니다.

> 사용자: "목록에서 눌러 고른다 (Recommended)" — 설명: 붙여 둔 부모 폴더 아래의 폴더 목록을 주는 관리 API 하나를 더하고, 화면에서 폴더를 눌러 내려가며 고릅니다. 이름을 손으로 적지 않아 오타가 없고, 어떤 폴더가 있는지 서버에 들어가 보지 않아도 됩니다. 폴더 이름이 화면에 보이게 되며(파일 이름과 내용은 내지 않습니다), 끊긴 공유 폴더에서 목록이 돌아오지 않는 경우에는 연결 확인과 같은 10초 한도를 겁니다. 관리 API 경로 하나가 늡니다.

### 라운드 3 (질문 넷)

"Node 서버가 낸다 (agent-os와 같게)"가 연 가지다. 호출 곁의 본문에는 확인한 사실(agent-os의 부품은 열하나이고 이 화면에 필요한 부품의 절반쯤이 없다, 공개 부품 라이브러리의 채택도, agent-os의 화면 검사에 걸린 시간, TypeScript가 5.9에 묶이는 까닭)과 처음 나오는 말의 풀이 넷(동작만 주는 부품, 부품 진열장 Storybook, 화면 사진 비교, 타입 단언)을 적었다.

**질문 15 (화면 부품).** "화면에 쓰는 부품(단추, 표, 대화 상자 등)을 어디서 가져올까요?"

- "agent-os 것을 복사하고 없는 것은 직접 짓는다 (Recommended)": 아래 인용의 설명.
- "agent-os 것을 복사하고, 까다로운 부품만 공개 부품(Radix)을 쓴다": 위와 같되 대화 상자, 선택 목록, 잠깐 뜨는 알림처럼 키보드 조작과 화면 낭독기 대응이 까다로운 부품은 '동작만 주고 모양은 없는' 공개 부품 Radix(MIT, 주간 내려받기 약 2,900만)에 우리 모양을 입힙니다. 직접 짓는 양이 줄고 선택 목록을 브라우저 기본보다 자유롭게 꾸밀 수 있습니다. 대신 바깥 패키지가 하나 늘어 판을 따라가야 하고, agent-os와 부품의 구현이 갈립니다. agent-os는 2026-09-28에 Radix가 따라오는 shadcn을 고르지 않았는데, 그 까닭은 위젯과 부품을 나눠 써야 했기 때문이고 이 저장소에는 위젯이 없습니다.
- "공개 라이브러리 하나를 통째로 쓴다 (Ant Design 또는 Mantine)": 표, 폼, 파일 올리기, 대화 상자, 알림이 모두 들어 있는 라이브러리 하나를 씁니다. 둘 다 MIT이고 주간 내려받기는 Ant Design 약 540만, Mantine 약 380만입니다(MUI는 약 1,500만이지만 표의 여러 기능이 유료판에 있다는 웹 조사 보고가 있어 후보에서 뺐습니다). 셋 가운데 가장 빨리 짓습니다. 대신 화면 모양이 agent-os와 달라지고, 색과 간격을 그 라이브러리의 방식으로 정해야 하며, 큰 판이 오를 때마다 바뀐 부분을 따라가야 합니다. 둘 가운데 어느 것을 쓸지는 고르신 뒤 다시 여쭙니다.

> 사용자: "agent-os 것을 복사하고 없는 것은 직접 짓는다 (Recommended)" — 설명: agent-os의 색·글꼴·간격 값과 부품 열하나(단추, 카드, 입력 칸, 스위치, 알림 띠, 상태 표시 등)를 이 저장소의 web/ 아래로 복사합니다. 표, 선택 목록, 체크 상자, 대화 상자, 파일 올리기, 잠깐 뜨는 알림, 페이지 넘김은 agent-os에 없어서 직접 짓되, 브라우저가 기본으로 주는 요소(대화 상자 <dialog>, 선택 목록 <select>, 표 <table>, 파일 입력)에 같은 모양을 입힙니다. 두 제품의 화면이 같은 모양이 되고, 새로 드는 바깥 패키지는 Tailwind와 아이콘(lucide)뿐입니다. 대신 부품 일곱 안팎을 직접 짓고 시험해야 하고, 복사본이라 agent-os가 고친 것이 저절로 따라오지 않습니다. agent-os 관리 화면에는 대화 상자·선택 목록·파일 올리기를 쓰는 곳이 아직 없어 본뜰 구현이 없습니다.

바로잡음: 고른 설명의 "새로 드는 바깥 패키지는 Tailwind와 아이콘(lucide)뿐입니다"는 틀렸다. agent-os의 부품 패키지(`web/packages/ui/package.json`)가 직접 의존하는 바깥 패키지는 여섯이고, 통째로 복사하면 react-markdown, remark-gfm, 글꼴을 싣는 `@fontsource` 패키지 둘이 함께 든다(아래 "셀프 리뷰"의 "판정"). 고른 선택지의 설명이 기술 조건을 틀리게 적은 것이라, `grilling`의 "옮길 때"대로 ADR 초안의 승인 질문에서 바로잡아 확인받는다.

**질문 16 (화면 검사).** "화면 쪽 자동 검사를 어디까지 둘까요?"

- "실제 서버에 대고 도는 브라우저 시험까지 (Recommended)": 린트, 타입 검사, 부품 단위 시험, 서버 계약에서 만든 코드가 최신인지 보는 검사를 커밋 훅과 CI에 두고, 브라우저가 실제 서버와 데이터베이스에 로그인해 화면을 눌러 보는 시험(Playwright)을 CI에 둡니다. CI에 잡 둘이 늘고 필수 검사 verify가 그 결과를 모읍니다(agent-os의 2026-11-24 중앙값은 4.5분과 1.6분). 부품 진열장(Storybook)과 화면 사진 비교는 0.1 뒤로 미룹니다. 그래서 화면 모양이 뜻하지 않게 달라진 것은 자동으로 잡지 못합니다.
- "부품 진열장(Storybook)까지": 위에 더해 부품과 화면의 상태마다 견본을 두고, 그 견본을 실제 브라우저에서 띄워 보는 시험을 돌립니다. 빈 목록, 오류, 긴 글 같은 상태를 서버 없이 눈으로 볼 수 있습니다. 대신 Storybook 묶음이 의존성에 들고 화면마다 견본을 함께 써야 합니다. 화면 사진 비교는 미룹니다.
- "화면 사진 비교까지 전부 (agent-os와 같게)": 아래 인용의 설명.

> 사용자: "화면 사진 비교까지 전부 (agent-os와 같게)" — 설명: 위 둘에 더해 견본마다 화면 사진을 찍어 저장소의 정답 사진과 한 점도 다르지 않은지 봅니다. 모양이 뜻하지 않게 바뀐 것을 잡습니다. 대신 CI에 긴 잡이 하나 더 늘고(agent-os 중앙값 7.5분), 정답 사진을 저장소에 커밋하며(agent-os는 554장), 모양을 일부러 고칠 때마다 정답 사진을 다시 찍어야 합니다.

추천과 다른 답이다.

**질문 17 (타입 원칙).** "타입 검사를 피해 가지 못하게 하는 헌법 원칙 II를 화면 코드(TypeScript)에도 걸까요?"

- "원칙 II를 TypeScript까지 넓힌다 (Recommended)": 아래 인용의 설명.
- "헌법은 그대로 두고 린트 설정에만 둔다": 린터는 같은 다섯 가지를 똑같이 막지만 헌법 원칙이 아닙니다. 그래서 그 설정을 느슨하게 고치는 일이 헌법 개정(ADR과 승인)이 아니라 보통 변경이 됩니다. 헌법 버전의 큰 자리는 오르지 않습니다.
- "TypeScript의 기본 엄격 검사만 켠다": 새 규칙을 두지 않습니다. 기본 엄격 검사는 any와 as를 막지 않아, 서버 계약에서 만든 타입을 as 하나로 덮어도 검사가 지나갑니다.

> 사용자: "원칙 II를 TypeScript까지 넓힌다 (Recommended)" — 설명: 화면 코드에서도 타입 검사를 끄는 다섯 가지(any, 타입 단언 as, 값이 있다고 우기는 !, @ts-ignore, @ts-nocheck)를 쓰지 못합니다(as const는 됩니다. @ts-expect-error는 타입 시험 파일에서만 씁니다). 판정은 린터(typescript-eslint)가 하고, 줄마다 규칙을 끄는 주석도 막습니다. 헌법 원칙의 문장이 바뀌므로 헌법 버전이 1.5.9에서 2.0.0이 되고, 개정은 판정하는 린터가 서는 날인 web 뼈대 티켓이 합니다(이번 설계 PR은 ADR에 결정만 적습니다). TypeScript는 5.9에 묶입니다. agent-os와 같습니다.

**질문 18 (화면 그림).** "명세를 쓰기 전에 화면 그림을 그려 확인받을까요?"

### 라운드 4 (질문 둘)

질문 18의 답이 연 가지(옮길 하네스의 크기)와, "agent-os와 같게"라는 답이 조용히 갈리지 않게 확인할 것 하나다. 호출 곁의 본문에는 agent-os의 그림 스킬이 기대는 것 넷, 스킬을 옮기는 일은 설계 PR에 넣을 수 없어 다음 세션의 하네스 티켓이 한다는 것과 그래서 생기는 차례(이번 설계 PR, 스킬 옮기기, admin 화면 그림, admin 명세), 관리자 페이지의 주소에 관한 사실(지금 프록시는 443 하나만 열고, ADR 0020과 기능 계획은 "같은 포트의 경로 하나"로 적었으며, agent-os는 관리 화면을 다른 포트 8443에 두었다)을 적었다.

**질문 19 (디자인 원천).** "화면 그림을 그릴 때 어떤 디자인 시스템을 붙일까요? (옮길 하네스의 크기가 여기서 갈립니다)"

- "agent-os의 디자인 시스템 아티팩트를 그대로 붙인다 (Recommended)": 아래 인용의 설명.
- "이 저장소의 디자인 시스템 아티팩트를 따로 만들고 동기화 도구까지 옮긴다": 이 저장소의 부품 복사본(web/packages/ui)을 원천으로 하는 디자인 시스템 아티팩트를 새로 만들고, 둘을 맞추는 도구(agent-os의 web/tools/sync-design-system, 파일 서른 개 이상)와 그 스킬까지 옮깁니다. 새로 짓는 부품도 아티팩트에 실려 그림이 실제 코드와 같아집니다. 대신 부품 복사본이 먼저 있어야 해서 '명세 전에 그림'의 차례가 바뀝니다. web 뼈대와 부품 복사를 admin 명세보다 먼저 지어야 하고(그 일을 맡는 기능이나 티켓이 앞에 섭니다), 옮길 하네스가 크게 늘어납니다.

> 사용자: "agent-os의 디자인 시스템 아티팩트를 그대로 붙인다 (Recommended)" — 설명: 그림 스킬과 그 계기 셋(디자인 폴더에 쓸 때 알리는 훅, 다음 세션 결정표의 '화면 디자인' 줄, 트래커 문서의 화면 디자인 절)만 옮깁니다. 그릴 때는 agent-os가 관리하는 디자인 시스템 아티팩트를 읽기만 해서 붙이고, 코드와 아티팩트를 맞추는 동기화 도구는 옮기지 않습니다. 이 저장소가 새로 짓는 부품(표, 대화 상자 등)은 그 아티팩트에 없으므로 그림 안에 직접 그립니다. 하네스 PR 하나로 끝나고, admin 화면 그림은 web/ 코드가 생기기 전에도 그릴 수 있습니다. 대신 이 저장소의 부품 복사본이 원본과 달라져도 그림은 agent-os 쪽 모양을 따르고, 웹에서 고친 디자인 값(색, 간격)을 이 저장소의 코드로 들이는 길은 없습니다. 그림 자체를 웹에서 고친 것을 다시 들이는 길은 스킬에 그대로 있습니다.

**질문 20 (여는 주소).** "관리자 페이지를 어느 주소로 열까요?"

- "지금 포트의 /admin/ 아래로 연다 (Recommended)": 주소는 https://<서버>/admin/이고 밖으로 여는 포트는 지금처럼 443 하나입니다(ADR 0020과 admin 기능 계획이 이미 이렇게 적었습니다). 운영자가 방화벽에 열 포트가 늘지 않습니다. 대신 MCP 클라이언트가 닿는 곳이면 로그인 화면에도 닿습니다. 로그인 화면에 닿을 수 있는 주소 범위를 프록시 설정으로 좁히는 장치를 둘지는 명세가 정합니다. agent-os가 다른 포트를 쓴 까닭은 같은 서버에 방문자용 페이지가 있어서였고, 이 서버에는 브라우저로 여는 다른 페이지가 없습니다.
- "다른 포트로 연다 (agent-os와 같게, 기본 8443)": 아래 인용의 설명.

> 사용자: "다른 포트로 연다 (agent-os와 같게, 기본 8443)" — 설명: 관리자 페이지와 로그인 경로를 443이 아닌 포트에 둡니다. 운영자가 방화벽 규칙 하나로 관리자 페이지에 닿는 주소를 좁힐 수 있습니다. 대신 밖으로 여는 포트가 둘이 되어 ADR 0020의 '포트 하나'와 설치 안내, compose 파일이 바뀝니다. 프로그램이 쓰는 관리 API와 수집 API는 443에 그대로 남으므로, 좁혀지는 것은 화면과 로그인뿐입니다.

### 나. 묻지 않고 기본으로 둔 것

**기능 나누기**

- 나-1. 새 기능의 이름은 `group-kb`(그룹·지식베이스 관리)와 `eval-screen`(평가 화면)입니다. 둘 다 슬라이스 2이고, `group-kb`는 admin 뒤에, `eval-screen`은 `group-kb` 뒤에 섭니다. 평가 화면이 뒤인 까닭은 지식베이스마다 두는 설정(LLM으로 내보내기 허용, 최소 점수 기본값)이 지식베이스 설정 화면에 붙기 때문입니다.
- 나-2. `group-kb`가 넘겨받는 일은 그룹·지식베이스의 만들기·고치기·지우기, 준비 명령(migrate)이 화면에서 고친 설정을 덮어쓰는 문제, 가져오는 원천의 그룹 바꾸기, 최소 점수 규칙(422 거부), 검색 시험의 그룹 거르기입니다. `eval-screen`이 넘겨받는 일은 평가의 등록·실행·결과 화면과 그 API와 저장 표, 평가 세트와 판정 결과의 보관 방법입니다.
- 나-3. 0.1의 날짜 문구(2027-03 초 무렵)는 PRD가 원천이라 이번에 고치지 않습니다.

**admin의 화면과 API**

- 나-4. 화면은 로그인, 비밀번호 정하기(링크로 여는 화면), 현황, 원천(동기화 기록 포함), 문서(조각 목록과 파일 올리기 포함), 검색 시험, 토큰, 계정(시스템 관리자에게만 보임), 내 비밀번호 바꾸기입니다.
- 나-5. 새로 생기는 관리 API는 동기화 취소, 문서 하나 다시 수집, 원천 폴더 목록, 검색 시험, 현황 집계, 문서의 조각 목록이고, 문서와 동기화 기록의 목록 조회를 넓힙니다. 경로와 칸의 이름은 명세가 정합니다.
- 나-6. 검색 시험은 MCP 검색과 같은 코드를 부르고, 질문은 저장하지 않으며, 그룹으로 거르지 않습니다.
- 나-7. 화면에서 지울 수 있는 문서는 밀어 넣는 원천의 문서뿐입니다. 가져오는 원천의 문서는 원천에서 지워야 합니다(원칙 VI).
- 나-8. 화면은 주기적으로 다시 읽어 갱신하고, 화면 언어는 한국어 하나이며, 일정은 "매일, 매주, N분마다" 틀로 고르거나 다섯 칸을 직접 적습니다.
- 나-9. 토큰 화면은 이미 있는 관리 API(발급, 목록, 회수)를 그대로 씁니다.

**로그인(agent-os의 결정에서 따라오는 세부)**

- 나-10. 권한은 이렇게 둡니다. 시스템 관리자는 모든 일과 계정 관리를 하고, 관리자는 계정 관리만 빼고 모든 일(토큰 발급과 회수 포함)과 자기 비밀번호 바꾸기를 합니다. 계정 관리 경로는 로그인한 시스템 관리자만 부를 수 있고 인증 토큰으로는 열리지 않습니다.
- 나-11. 인증 토큰(관리용과 읽기용)과 `bootstrap-token` 명령은 그대로 남습니다. 로그인한 계정은 관리 API와 수집 API(파일 올리기)를 부를 수 있고, MCP는 인증 토큰으로만 열립니다.
- 나-12. 첫 계정은 새 서버 명령으로 만들고 비밀번호는 입력으로 받습니다. 계정이 하나도 없을 때 로그인 화면은 그 명령을 안내만 합니다.
- 나-13. 로그인 없이 열리는 경로는 로그인, 갱신, 링크로 비밀번호 정하기, 첫 계정이 있는지 확인하기 넷이 늘어납니다. 헌법 원칙 V의 문장("인증 없는 요청을 거부한다")은 고치지 않고, ADR에 이 넷을 닫힌 목록으로 적습니다.
- 나-14. 서명 키는 데이터베이스에 두고 바꾸는 서버 명령을 둡니다. 계정 이름은 영문 소문자·숫자·`.`·`_`·`-`로 3~32자이고, 메일 주소와 실명은 받지 않습니다. 로그인 실패 문구는 하나로 통일합니다.
- 나-15. 로그인 기록은 데이터베이스에 남기고 보는 화면은 0.1 뒤로 미룹니다. 접속 주소(IP)를 남길지는 명세가 정합니다(서버는 지금 프록시가 넘기는 주소를 믿지 않습니다).
- 나-16. 0.1에 넣지 않는 것은 2단계 인증, 사내 통합 로그인, 역할 만들기, 메일 발송, 흔한 비밀번호 검사입니다.
- 나-17. 새 의존성은 비밀번호 해시용 `argon2-cffi`(MIT)입니다.

**관리 포트**

- 나-18. 관리 포트(기본 8443)에서는 주소의 첫 화면이 곧 관리자 페이지이고, 화면이 부르는 API와 로그인 경로도 그 포트에서 열립니다. 443의 허용 경로(MCP, 수집 API, 관리 API, `/health`)는 그대로이고, 443에서는 쿠키 로그인을 받지 않습니다.
- 나-19. 관리 포트는 기본으로 열려 있고, 운영자가 번호를 바꾸거나 닫을 수 있습니다(agent-os와 같게). 인증서는 443과 같은 것을 씁니다.

**화면 스택**

- 나-20. agent-os의 구성을 옮깁니다. `web/` 아래 pnpm 워크스페이스, Node 24, TypeScript 5.9, Next 16, React 19, Tailwind 4, lucide 아이콘, SWR, 서버 계약에서 만든 API 코드(만든 결과를 커밋하고 최신인지 검사), ESLint와 Prettier, Vitest, Playwright, Storybook, 사진 비교입니다. 이 저장소에는 서버 계약 파일(`openapi.json`)이 아직 커밋돼 있지 않아서, web 뼈대 티켓이 그것부터 내보냅니다.
- 나-21. agent-os의 부품 묶음은 테마와 밀도까지 통째로 복사하고, 복사한 agent-os 커밋을 적어 둡니다.
- 나-22. 이미지는 `njh6803/rag-engine-admin`이고 Docker Hub 저장소를 하나 더 만드는 사람 몫이 생깁니다. 릴리스 이미지가 둘에서 셋으로, 기본 컨테이너가 다섯에서 여섯으로 늡니다.
- 나-23. 헌법 원칙 II의 문장을 고쳐 버전을 2.0.0으로 올리는 일은 린터가 서는 web 뼈대 티켓이 합니다. 이번 설계 PR은 스택 문서의 "관리자 페이지" 칸만 채우고 버전을 1.5.9에서 1.5.10으로 올립니다(문구 수정).

**화면 그림 절차**

- 나-24. 그림 스킬을 옮기는 일은 다음 세션이 하네스 티켓으로 합니다. 옮기는 것은 스킬, 디자인 폴더에 쓸 때 알리는 훅, 다음 세션 결정표의 "화면 디자인" 줄, 트래커 문서의 화면 디자인 절입니다. 디자인 시스템 동기화 도구와 그 스킬은 옮기지 않습니다.
- 나-25. admin, `group-kb`, `eval-screen`의 기능 계획에 "명세 전에 화면을 그린다"를 적습니다. 화면이 없는 기능(백업, 진단 묶음)은 이 단계가 없습니다.
- 나-26. 차례는 이번 설계 PR, 스킬 옮기기, admin 화면 그림, admin 명세, 티켓, 구현입니다. 스킬을 옮기기 전에는 결정표에 "화면 디자인" 줄이 없으므로, 이 세션이 내는 다음 지시문이 스킬 옮기기를 가리키게 하고 admin 기능 계획에도 그 차례를 적어 둡니다.

**다른 기능에 넘겨 적는 것**

- 나-27. 백업 기능(backup-upgrade)의 계획에는 "계정, 서명 키, 로그인 기록, 검색 지연 표가 데이터베이스에 있고 백업에 서명 키가 함께 담긴다"를 적습니다. 진단 묶음(diag-bundle)의 계획에는 "검색 지연 표를 읽는다"를 적습니다.

### 합의 요약과 달라진 것 (승인 때 알린다)

초안을 쓰면서 합의 요약의 글자와 달라진 것이다. ADR 초안의 승인 질문에서 사용자에게 알린다.

1. **ADR 0017은 포인터가 아니라 이력으로 적었다.** 요약은 ADR 0017 63줄에 "바뀜" 표시를 단다고 적었다. 그 줄은 본문이 아니라 지난 이력 항목(2026-11-17) 안이고, 지난 이력 항목은 기록이라 포인터를 달지 않는다(`.claude/rules/adr.md`). 그래서 새 이력 항목을 더했다.
2. **요약의 목록에 없던 문장 셋에 포인터를 달았다.** ADR 0020 19줄(첫 정식 릴리스를 막는 기능이 admin, backup-upgrade, diag-bundle이라는 문장. 기능 둘이 더해진다)과 ADR 0020 14줄의 두 문장(제품 변경으로 세는 것의 목록, "`web`과 `plugins`는 이 저장소에 없다")이다. ADR 0007 10줄에는 요약이 든 기본 컨테이너의 수에 더해 "프로세스와 이미지는 서버와 작업자 둘" 쪽 문장에도 달았다.
3. **제품 변경의 경로에 `web/`을 더한다**(ADR 0026 "제품 변경의 범위"). 화면만 고친 변경도 릴리스가 나야 운영자에게 닿는다. 요약에 없던 결정이다.
4. **접근 그룹을 쓰는 설치의 검색 시험을 doc-permission에 넘겼다**(ADR 0024 "이번에 짓지 않는 것"). 그 설치는 요청자가 없는 검색을 거부하는데 검색 시험은 요청자를 싣지 않는다. 요약에 없던 넘김이다.
5. **용어집의 풀이를 다듬었다.** 검색 시험의 "질문"을 용어집의 말 "질의"로 맞추고 검색 평가와 가르는 문장을 붙였다. 관리자 페이지와 관리자 항목에는 두 "관리자"를 가르는 문장을, 운영자 계정에는 인증 토큰과 가르는 문장을 붙였다. 다시 수집은 재색인의 풀이(색인 판이 바뀐 지식베이스의 조각을 다시 만드는 일)에 맞춰 가르는 문장을 고쳤다.
6. **ADR 0025에 문장 둘을 더했다.** 관리 포트를 닫으면 서버 기계 자신(`127.0.0.1`)에서만 열린다는 것(agent-os ADR 0062의 문장을 옮겼다)과, 짧은 JWT를 무엇으로 서명하고 검증할지는 명세가 정한다는 것이다.
7. **기능 계획에 요약보다 자세히 적은 것.** backup-upgrade에는 갱신용 번호와 비밀번호 링크, 복원하면 계정과 비밀번호가 백업한 때로 돌아간다는 것을, diag-bundle에는 싣지 않을 비밀 값과 로그인 기록을 실을지의 물음을, release-0-1에는 폐쇄망으로 옮길 이미지가 하나 는다는 것을 적었다. group-kb와 eval-screen의 수락은 "설계 인터뷰가 다듬는다"로 표시한 어림이다. admin에는 "구현 티켓이 고칠 곳"의 목록을, group-kb와 eval-screen에는 "이 기능의 티켓이 고칠 주석"을 적었다(아래 "옛 말 잔존").

아래는 셀프 리뷰를 반영하며 더 달라진 것이다(근거는 아래 "셀프 리뷰"의 "판정").

8. **바로잡음: agent-os에 로그인 코드가 있다.** 질문 10의 글과 ADR 0025 초안은 "agent-os에서도 이 결정은 문서에만 있고 코드는 없다"고 적었으나 틀렸다. ADR 0025는 그 저장소가 티켓 열넷 가운데 셋을 지었다고 고쳐 적고, 그 코드를 본뜰지는 명세가 정한다고 적었다.
9. **바로잡음: 부품을 복사하면 바깥 패키지 여섯이 함께 든다.** 질문 15에서 고르신 선택지의 설명은 "Tailwind와 아이콘(lucide)뿐"이라고 적었으나 틀렸다. react-markdown, remark-gfm, 글꼴 패키지 둘이 더 든다. ADR 0026은 여섯을 적고, 라이선스 확인을 web 뼈대 티켓에 맡기며, 복사한 패키지의 이름을 이 저장소의 이름으로 바꾼다고 적었다.
10. **ADR 0025에 agent-os ADR 0062의 세부 일곱을 더했다.** 줄여 옮기다 빠진 것이다(다시 해시하기, 잠긴 동안 비밀번호를 견주지 않기, 링크의 주소를 화면이 조립하기, 비밀번호를 정한 뒤 자동 로그인하지 않고 잠금을 풀며 다른 로그인을 끊기, '쓰지 않음' 때 갱신용 번호 지우기, 시스템 관리자 자신은 대상이 아닌 것, 서명 키를 바꿔도 로그인이 이어지는 것). 줄여 적은 문장이 그 ADR과 다르면 그 ADR의 문장을 따른다는 조항도 넣었다.
11. **화면이 부르는 API가 서버에 닿는 길을 명세로 넘겼다.** 초안은 "프록시가 API와 로그인 요청을 파이썬 서버로 바로 넘긴다"고 적었는데, 합의 요약에 없고 agent-os(관리 화면이 받아 서버로 넘겨 준다)와도 다른 것을 이 세션이 근거 없이 정해 적은 문장이었다. 두 길과 고를 때 볼 것 둘을 적고 명세가 정하게 했다.
12. **ADR 0025에 "옮기지 않고 이 저장소가 따로 정하는 것" 셋을 적었다.** agent-os의 층 배치(이 저장소는 ADR 0007의 층 규칙을 따른다), 로그인 경로의 `Host` 검사, 서명 키를 만드는 때다. 로그인 없이 열리는 경로의 닫힌 목록이 파이썬 서버의 경로를 다루는 것이고, 관리자 페이지 컨테이너가 내는 화면 파일은 그 목록의 대상이 아니라는 문장도 더했다. admin 계획의 수락 끝 문장을 거기에 맞춰 고쳤다.
13. **ADR 0024에 더한 것.** 요약 나-5는 "문서와 동기화 기록의 목록 조회를 넓힙니다"라고 적었는데 core가 넘긴 것은 문서 목록과 작업 목록이었다. 작업 목록을 되살려 적었다. 원천을 만드는 화면에 그룹을 고르는 칸을 둔다는 것(질문 5의 설명), 동기화 기록에 '취소됨'으로 보인다는 것(질문 13의 설명), 명세가 정할 겹치는 경우 여섯도 더했다.
14. **ADR 0026의 Zustand.** agent-os의 스택에는 상태 보관 라이브러리 Zustand가 있는데, 초안은 "쓰는 곳이 생길 때 들인다"고 적었다. 요약 나-20의 목록에 없던 미룸이다.
15. **ADR 0027에 판정자의 세부를 더했다.** 타입 정보를 읽는 규칙(`no-unsafe-*`), `@ts-expect-error`에 설명을 붙이는 것, 타입 선언 파일도 판정 범위인 것, agent-os에서 만든 코드의 `any` 한 자리를 `unknown`으로 바꿨다는 것이다.
16. **`.scratch/plan-head.md`의 "하네스 기능" 절에 그림 스킬 옮기기를 올렸다.** 결정표만 보면 admin이 명세 쓰기로 가기 때문이다. admin 계획의 "차례"에는 그 티켓이 끝났는지 가르는 표지와 티켓이 지킬 것 둘을 적었다.
17. **여쭐 것: 진단 묶음과 백업을 admin 뒤로 세울지.** 두 기능의 계획에 admin이 짓는 표를 읽거나 담는다고 적었는데, 두 기능의 `Blocked by`에는 admin이 없어 admin보다 먼저 지어질 수 있다. 차례를 바꾸는 일이라 고치기 전에 승인 질문에서 여쭌다. 답은 "진단 묶음만 admin 뒤로 세운다"였다(아래 "승인").

### 판정

요약: 표준 축은 Major 2, Minor 5, Nit 5이고 가장 큰 것은 agent-os에 코드가 없다는 틀린 문장이다. 명세 축은 Major 2, Minor 12, Nit 2이고 가장 큰 것은 넘긴 일을 받는 기능이 넘기는 기능보다 먼저 지어질 수 있다는 것이다. 지적마다 근거를 이 세션이 직접 확인한 뒤 정했다. 아래에서 "표"는 표준 축, "명"은 명세 축의 번호다.

**고친 것**

- **표-Major 1, 명-2 (agent-os에 코드가 없다는 문장).** agent-os의 `.scratch/admin-login/issues/`에서 상태 줄을 봤다. 01, 02, 08이 `done`이고 나머지 열하나는 `ready-for-agent`다. `src/agent_os/http/`에 `accounts.py`, `passwords.py`, `origin.py`가 있다. 그 체크아웃의 reflog는 2026-11-26 00:17, 04:16, 14:42에 당긴 것을 보여, 이 세션이 시작한 15:34에 그 코드가 이미 있었다. 체크아웃이 뒤처진 것이 아니라 이 세션이 코드를 보지 않고 쓴 문장이다. **고친 것**

## 회고

`retro`를 돌렸다. 근거는 이 일지와 이 세션이다. 후보는 여덟이고 승인 넷, 기각 넷이며 사용자에게 넘긴 것은 없다. 승인한 넷은 모두 대기열에 회차로 두고 이 세션에서 반영한 것은 없어, harness 티켓은 쓰지 않았다. 세션이 길어 컨텍스트가 여러 번 압축됐으므로, 압축 전에 난 일 가운데 일지에 적히지 않은 것은 이 회고가 보지 못한다.

**승인**

1. **질문의 글, 선택지의 설명, ADR 초안에 넣은 사실 셋을 근거에 대 보지 않았다.** 질문 10의 글은 agent-os에도 운영자 계정 로그인의 코드가 없다고 적었고, 질문 15에서 고른 선택지의 설명은 화면 부품을 복사할 때 드는 바깥 패키지가 둘뿐이라고 적었다. 둘 다 그 저장소의 티켓 상태와 `web/packages/ui/package.json`에 대 보지 않은 문장이었고, 셀프 리뷰 두 축이 Major로 냈으며 뒤의 것은 승인 화면에서 다시 여쭸다. ADR 0025 초안은 agent-os ADR 0062의 19줄을 옮기며 그 문장 바로 뒤에 달린 `(바뀜: 이력 2026-11-24 …)` 포인터를 따라가지 않아 이력이 바꾼 옛 문장을 옮겼고, PR 직전 리뷰의 주장 대조가 잡았다(회고에서 그 19줄을 다시 열어 포인터가 달려 있던 것을 봤다). 판정은 회차로 세는 승인이다. `grilling`의 "올리기 전"은 설명에 넣는 사실을 지금 코드에 대 보라고 적는, 인터뷰 때 실리는 지침이고 그것을 어겨 리뷰가 잡았다. 대기열 grilling-premise-check에 더해 9회차가 됐다. 회차 5를 넘은 항목이라 다음 하네스 chore 배치가 고른다.
2. **PR 직전 리뷰의 지적을 오탐으로 닫았다가 PR 봇이 같은 자리를 다시 냈다.** 위 "PR 봇 회차"의 지적 1이다. CLI가 Major로 짚은 것을 서브에이전트와 이 세션이 계획에 이미 적혀 있다는 이유로 닫았고, 지적이 든 경우(두 기능이 함께 끝난다)를 계획의 문장대로 밟아 보지 않았다. 판정은 승인이다. 사건이 있고, 검사가 가를 수 없는 판단이라 지침의 층(리뷰 서브에이전트의 트리아지 기준과 `code-review` 6단계 2)이며, PR 하나로 되돌릴 수 있다. 더하는 것이라 다섯 번째에 반영한다. 닫은 지적을 PR 봇이 다시 낸 꼴은 대기열 triage-write-path-without-repro와 같지만 그 항목의 처방(파일을 옮겨 쓰는 경로를 재현한다)은 문서의 차례 규칙에 맞지 않아, 새 항목 대기열 triage-dismissed-crossing(1회차)을 쓰고 두 항목이 서로 가리키게 했다.

**기각**

5. **일지에 적은 수 둘이 틀렸다.** 계약의 경로 수를 근거 없이 적었고, 인용 경고 가운데 질문과 라벨의 수를 하나 적게 셌다. 둘 다 커밋 전에 Grep으로 다시 세어 고쳤다. 검사로 옮길 수 없고, 지침으로 적으면 이미 하는 일을 되풀이하는 문장이 된다.

7. **계획 둘이 파일 없이 코드를 읽었다고 적었다.** group-kb와 eval-screen 계획의 문단이다. 위 "검증"에 적은 대로 커밋 전에 `git grep`으로 찾아 근거 파일을 적었다. #124가 들인 근거 규칙이 실린 채로 스스로 찾은 것이고 리뷰가 잡은 사건이 아니라 회차로 세지 않는다.
8. **압축 뒤에 다시 읽은 것.** agent-os ADR 0062의 앞 30줄을 다시 읽었고("확인한 것"), 봇 1회차의 코멘트를 `gh api`로 다시 받아 위 절을 썼다. 보고와 판정은 받은 턴에 일지로 옮겨 두어 일지를 요약에서 다시 짓지는 않았다. 잃은 것이 없어 사건으로 세지 않는다.

- PR 직전 리뷰의 서브에이전트가 파일 넷을 대 보지 못했다. 보고에 까닭이 없어 대기열 coderabbit-review-turn-limit와 같은 원인인지 알 수 없고, 회차로 세지 않는다.

- **backup-upgrade도 시작할 수 있다.** 명세도 설계 줄도 없어 다음 단계는 설계 인터뷰다. admin과 나란히 가고, 백업 안내와 시험을 누가 맞추는지는 두 계획과 release-0-1 계획에 적었다(위 "PR 봇 회차"). 이 세션은 그 지시문을 따로 내지 않고 `.scratch/plan.md`의 프론티어로 가리킨다.
