## 확인한 것

- **임베딩의 CPU 처리량**(쟀다. `.scratch/search-eval/probes/tei-cpu/embed_throughput.py`, 출력 `embed_throughput_out.txt`): TEI `cpu-1.9.4`와 `BAAI/bge-m3`를 `--cpus=4`로 띄워, 936자(471토큰)의 글 192개를 배치 32로 401.3초에 임베딩했다(0.48개/s, 배치마다 49.7~108.6초). 질의 하나의 중앙값은 536ms다. `--cpuset-cpus=0-3`으로 다시 띄운 실행은 컨테이너가 메모리 부족으로 죽어 서버 로그의 배치 여섯(`total_time` 56.4~93.8초)만 남겼다(`embed_throughput_cpuset_server_log.txt`). 다른 세션의 시험이 같은 PC에서 돌아 자릿수를 보는 값이다.
- **리랭커의 CPU 처리량**(쟀다. `rerank_throughput.py`, 출력 `rerank_throughput_out.txt`, 서버 로그 `rerank_throughput_server_log.txt`): 같은 이미지와 `BAAI/bge-reranker-v2-m3`를 `--cpuset-cpus=4-7`로 띄워, 쌍 96개를 배치 32로 785.5초에 채점했다(0.12쌍/s, 배치마다 200.6~297.6초). 서버 로그는 그 모델 저장소의 ONNX 파일 넷이 404이고 ORT 백엔드가 뜨지 못해 Candle 백엔드가 CPU로 돌았다고 적는다.
- **GPU 이미지**(손으로 봤다. 프로브 README의 문단, 서버 로그 `gpu_turing_start_server_log.txt`): 이 PC의 GPU는 GTX 1660 Ti(6144MiB), 드라이버 560.94다. TEI `turing-1.9.4`는 `--gpus all`에서 `cuda>=12.9` 요구로 거부됐고, 그 검사를 끄면 이미지의 상위 호환 `libcuda`가 올라가 `CUDA_ERROR_NO_DEVICE`로 CPU로 떨어졌으며, 그 폴더를 가리면 `Starting Bert model on Cuda`까지 간 뒤 `CUDA_ERROR_UNSUPPORTED_PTX_VERSION`으로 끝났다. GPU의 처리량은 재지 못했다.
- **검색의 코드**(코드를 읽었다): `src/rag_engine/app/search.py`의 유스케이스는 `VectorIndex.search_candidates`를 부른 뒤 리랭크하고 `top_k`로 자른다. 리랭커에 보내는 글은 `compose_index_text`가 절 경로를 붙인 글이다. 수집 요청에는 갱신일 칸이 있고, `.dockerignore`의 허용 목록은 `pyproject.toml`, `uv.lock`, `README.md`, `src/`다.
- **CI**(코드를 읽었다): `.github/workflows/ci.yml`의 `verify`는 `needs`의 결과가 모두 `success`일 때만 초록이다. 잡의 `timeout-minutes`는 15, 15, 5, 5다.
- **core 16**(읽었다): `.scratch/core/issues/16-search-latency-probe.md`의 `Status:`는 `ready-for-agent`다. 검증 명령을 돌릴 때 `docker ps`에 `rag-latency-probe-reranker-1`과 `rag-latency-probe-embedding-1`이 떠 있었다. 다른 세션이 그 티켓을 돌리는 중으로 보인다(손으로 봤다).

### 사용자의 물음과 셋째 호출

명세 본문과 ADR 이력 초안을 쓴 뒤 사용자가 물었다. "위에 2개 질문 GPU로 도리면 안돼?" 로컬에서는 GPU로 돌릴 수 있고 그러면 여섯째 질문의 답이 달라질 수 있으나, 무료 CI 러너에는 GPU가 없어 다섯째(추론 기록)는 그대로 필요하다고 답했다. GPU 러너가 공개 저장소에서도 유료라는 것은 기억으로 말했고 원문으로 확인하지 않았다고 함께 적었다. 이어 GPU 이미지를 띄워 봤고(위 "확인한 것"), 드라이버를 올려야 돈다는 결과와 함께 다시 물었다.

7. **전체 게이트(다시).** "GPU로 리랭크 기록을 만들 수 있게 되면(드라이버 업데이트 필요), 전체 게이트(리랭크 뒤 줄을 보는 게이트)와 리랭크 관련 측정을 언제 진행할까요?"
   - 이번 기능에서 GPU로 진행 (Recommended): "core 16을 기다리지 않습니다. 명세에 '리랭크 기록은 로컬 GPU로 만든다'고 적고, 그 티켓의 첫 단계가 GPU 처리량을 잽니다(기록 만들기가 2시간을 넘으면 멈추고 다시 여쭙니다). 드라이버 업데이트는 그 티켓 전에 사용자께서 해 주시면 됩니다. 리랭커가 CPU에서 느린 문제는 core 16이 따로 판정합니다."
   - 지금 드라이버를 올리고 바로 측정: "사용자께서 지금 NVIDIA 드라이버를 최신으로 올려 주시면, 이 세션에서 GPU 처리량을 재고 그 숫자를 명세의 근거로 적습니다. 가장 확실하지만 명세 작업이 드라이버 업데이트를 기다립니다. 다른 세션이 Docker를 쓰는 중이면 잠시 끊길 수 있습니다."
   - 기존 선택 유지 (core 16 뒤): "앞에서 고르신 대로 전체 게이트와 리랭크 관련 측정을 core 16의 판정 뒤로 미룹니다. 명세와 ADR 이력 초안을 고치지 않아도 됩니다. GPU는 나중에 그 티켓에서 다시 검토합니다."
   - 답: 이번 기능에서 GPU로 진행 (Recommended).

### 다섯째 호출(core 16의 병합 뒤, 리랭커 결정의 때와 고친 이력의 승인)

넷째 호출의 승인을 받은 뒤 커밋 직전에 core 16이 dev에 병합된 것을 알았다(아래 "core 16의 병합과 다시 맞춘 것"). 승인받은 ADR 0018 이력의 문장이 사실과 달라져 다시 물었다.

1. [리랭커 결정] "core 16(검색 지연 측정)이 오늘 닫히면서 'CPU에서 리랭커를 켜면 검색 한 번에 130초가 걸려 20초 제한을 넘는다'는 측정과 함께, 해결 방법의 선택을 사용자와 search-eval에 넘겼습니다. 이 결정을 언제 내리시겠습니까?"
   - 리랭커 실험 뒤에 고름 (Recommended): "search-eval의 리랭커 켬·끔 실험이 '리랭커가 적중률을 몇 %p 올리는지'를 낸 뒤, 그 숫자와 core 16의 지연을 나란히 보고 세 길(리랭커를 끄는 기본, ONNX 리랭커나 GPU 이미지, 시간 제한 늘리기) 가운데 고르십니다. 그때까지 제품의 기본값은 그대로 둡니다. 지금은 리랭커의 품질 기여를 모르기 때문에 숫자 없이 고르면 되돌릴 가능성이 있고, 아직 배포된 이미지가 없어 기다리는 비용이 작습니다. 실험은 NVIDIA 드라이버 업데이트 뒤에 가능합니다."
   - 지금 리랭커 끔을 기본으로: "기본 구성에서 리랭커를 바로 끕니다(리랭커 없이는 동시 8건의 p95가 3.2초였습니다). CPU만 있는 설치처에서도 검색이 제한 시간 안에 답하게 됩니다. 대신 품질 숫자 없이 정하는 것이고, core의 기본값과 명세를 고치는 별도 티켓이 필요하며, 최소 점수 기능(리랭커가 있어야 동작)과 전체 게이트의 전제를 다시 여쭤야 합니다."
   - 지금 ONNX·GPU 조사부터: "리랭커를 지키는 방향으로, ONNX 파일이 있는 다른 리랭커 모델이나 GPU 이미지가 20초 안에 들어오는지 재는 조사 티켓을 search-eval 앞에 둡니다. 리랭커를 유지할 수 있는지 일찍 알게 되지만, 평가 도구가 아직 없어 모델을 바꿨을 때의 품질 변화는 잴 수 없고 search-eval의 시작이 그만큼 늦어집니다."
   - 답: 리랭커 실험 뒤에 고름 (Recommended).
2. [ADR 0018] "앞서 승인하신 ADR 0018 이력 가운데 core 16에 관한 문장이 사실과 달라져 고쳤습니다. 고친 내용을 승인하시겠습니까? (1) '리랭커의 CPU 속도는 core 16이 판정한다'를 'core 16은 재기만 하고 넘겼고, 위 질문에서 고르신 때에 사용자가 고른다'로. (2) 'search-eval 티켓은 core 16이 닫힌 뒤에 집는다'를 'core가 오늘 끝나 더 막는 것이 없다'로. (3) 새로 더한 둘: 전체 게이트를 모든 PR에 돌리지 않는 까닭의 확정, 평가용 임베딩 컨테이너를 메모리 설정을 낮춰 띄운다."
   - 승인 (Recommended): "(3)의 첫째는 설계가 '어림이니 core 16의 측정을 보고 명세가 확정한다'고 남겨 둔 숙제입니다. 측정으로는 CPU 리랭크가 평가 한 번에 11~34시간이라 PR마다 돌릴 수 없고, 추론 기록을 쓰는 지금은 'PR마다 GPU로 리랭크 기록을 다시 만들어야 해서'가 까닭이 됩니다. 결론(전체 게이트는 main으로 가는 PR에서만)은 그대로입니다. 둘째는 core 16이 기본 설정에서 임베딩 컨테이너가 13GiB를 점유하는 것을 본 데 따른 것입니다. 위 질문에서 첫째가 아닌 답을 고르시면 (1)의 문장만 그 답에 맞게 고칩니다."
   - 보류: "이력을 확정하지 않고 PR을 열지 않은 채 멈춥니다. 어느 문장을 바꾸고 싶으신지 알려 주시면 명세와 이력을 고친 뒤 다시 여쭙니다."
   - 답: 승인 (Recommended).

## 명세가 정한 것

명세의 서두가 표시와 수를 든다. 설계가 정하지 않아 이 세션이 정한 것 가운데 무게가 있는 것만 적는다.

- 명령줄 도구는 `tools/search_eval.py`이고 하위 명령은 `validate`, `index`, `run`, `compare`, `judge`, `inspect`다. 재료의 자리는 저장소 루트의 `evals/public-docs/`, 평가 전용 compose는 `compose.eval.yml`이다. 평가가 재는 구성은 묶음의 `config.json`이 원천이고, `run --through fused|rerank`가 빠른 실행과 전체 실행을 가른다.
- 진단용 메서드는 `VectorIndex.diagnose_candidates`, 판정기 포트는 `RelevanceJudge`다(ADR 0007 이력).
- 기대 근거는 글귀(`passage`)와 쪽(`page`) 두 종류이고, 글귀는 NFC 정규화와 공백 제거 뒤의 부분 문자열로 견준다.
- 빠른 게이트의 잡은 건너뛰지 않고 늘 시작하며, 첫 스텝이 바뀐 경로를 보아 평가하지 않을 때는 성공으로 끝난다. 그래서 `verify`의 판정은 고치지 않는다(PR #27 봇 둘째 회차가 넘긴 첫째). PR만이 아니라 dev와 main의 푸시에서도 돈다.
- 모델이 계산한 결과는 추론 기록으로 커밋하고, 리랭크 기록은 GPU로 만든다(ADR 0018 이력). 기록 파일은 명령마다 주인이 하나이고(`index`는 조각의 임베딩, `run`은 질의의 임베딩, 전체 실행의 `run`은 리랭크 점수) `--records write`는 자기 파일만 다시 쓴다.
- 기준 보고서는 `baseline-fast.json`과 `baseline-full.json` 둘이다. 리랭크 기록과 `baseline-full.json`은 dev에서 main으로 가는 출시 PR 앞에서 맞춘다.
- 재지 않은 채 구현 티켓으로 넘긴 측정은 다섯이고 모두 멈출 조건이 있다(명세 Testing Decisions의 마지막 항목).
- 리랭커의 CPU 속도를 푸는 길(리랭커를 끄는 기본, ONNX 리랭커나 GPU 이미지, 검색 시간 제한 늘리기)은 이 기능의 리랭커 켬·끔 실험 뒤에 사용자가 고른다(다섯째 호출의 답). 그 실험의 티켓이 보고서와 core 16의 지연을 함께 보인다.
- 평가 전용 compose의 임베딩 TEI는 `--max-batch-tokens 4096`으로 띄운다(core 16이 기본값에서 본 메모리 점유에 따른 것).

### Major와 처리

1. 기능 계획의 `Blocked by: core`와 명세의 "core 16을 기다리지 않는다"가 어긋난다. core에서 열린 티켓은 core 16뿐이라 그것이 먼저 닫힌다. 고쳤다. 사용자의 선택이 바꾼 것은 순서가 아니라 조건(core 16의 판정이 무엇이든 GPU 기록으로 진행한다)이라고 적었고, 리랭커 켬·끔 보고서는 core 16이 닫힌 뒤에 나오므로 그 판정을 다시 볼 근거라고 고쳤다(명세, ADR 0018 이력, core 계획).
2. 기준 보고서가 하나면 dev로 가는 PR이 기준을 갈 때 리랭크 뒤 줄을 만들 수 없다. 고쳤다. `baseline-fast.json`과 `baseline-full.json`으로 나누고 `compare --gate fast|full`이 각자의 파일을 본다.
3. `--records write`가 이번 실행이 읽지 않은 열쇠를 지워 다른 명령의 기록(GPU로 만든 리랭크 기록)을 지운다. 고쳤다. 기록 파일을 종류별로 나누고 명령이 자기 파일만 다시 쓴다. 실험용 `--records off`를 더했다.
4. `config.json`의 칸이 없고 빠른 실행과 전체 실행을 가르는 길이 없다. 고쳤다. 칸을 적고, `index`가 그 값으로 제품의 `migrate`와 같은 코드로 데이터베이스를 준비하며, `run --through fused|rerank`가 실행을 가른다.
5. ADR 0018 본문의 "빠른 게이트는 …PR에서만 돌고, 건너뛰면 `verify`는 통과로 센다"에 포인터가 없다. 고쳤다. 포인터를 달고 이력에 푸시 실행과 잡이 늘 시작한다는 것을 적었다.

### Minor·Nit 가운데 고친 것

- 탈락 지점 `lost_in_fusion`과 `lost_in_rerank`가 전체 실행에서 겹쳤다. 넷을 차례로 보아 처음 맞는 것으로 정하고, `not_indexed`는 경계에서 갈린 경우까지 담으므로 `no_matching_chunk`로 이름을 바꿨다.
- nDCG에서 조각 하나가 기대 근거 둘에 처음 닿는 경우가 비어 있었다. 이득을 처음 닿은 기대 근거의 수로 하고 값은 1에서 자른다.
- 보고서가 조각을 "순번"으로 가리키는데 `SearchHit`에 그 칸이 없다. 진단용 검색의 줄이 `ordinal`을 싣게 했고, 글을 여는 하위 명령 `inspect`를 더했다.
- 제목 블록은 조각 글에 들지 않는다. `validate`의 견줌 대상을 본문으로 좁히고 글귀를 제목에서 옮기지 않는다고 적었다.
- RRF 점수가 같은 줄의 순서가 색인마다 달라질 수 있다. 진단용 검색 절에 적고 Solution의 "같은 재료" 문장을 고쳤다.
- 판정 모델의 원천이 둘이었다. 열쇠는 `config.json`이고 `judge`는 환경의 모델이나 어댑터의 지시문 판이 그것과 다르면 부르지 않는다. `judge`의 대상은 `--through`로 정한다.
- 최소 점수의 "숫자가 아닌 값은 `invalid_argument`"는 설계의 프로브와 어긋났다. 타입이 틀린 인자는 MCP SDK의 입력 검증이 거부한다고 고쳤다.
- ADR 0019 Consequences의 사람 표본 대조가 명세에 없었다. 첫 판정 실행의 티켓에 표본 40쌍으로 두었다.
- 임베딩 글과 리랭크 글을 "색인 글" 하나로 적은 곳을 갈랐다. 열쇠 절이 조각의 임베딩(줄인 절 경로), 질의, 리랭크(온전한 절 경로)를 따로 적는다.
- 글자 그대로가 아닌 따옴표 인용 넷을 따옴표 없는 서술로 바꾸거나 원문으로 고쳤다.
- 근거 표기를 맞췄다. 임베딩의 배치 시간은 `--cpus=4`의 49.7~108.6초와 `--cpuset-cpus=0-3` 서버 로그의 56.4~93.8초로 갈라 적고, 471토큰은 임베딩 프로브만 잰 값이라고 리랭크 쪽 문장을 고쳤으며, 토큰화 23~238ms는 임베딩 요청 안의 값이라고 적었다. 측정 중에 함께 돈 것과 `OOMKilled`는 세션 기록의 `docker stats`와 `docker inspect` 출력으로 확인해 손으로 봤다고 표지를 달았다. 프로브 README의 "임베딩 컨테이너와 같은 때에 돌았다"는 틀려서 고쳤다(리랭크의 배치는 임베딩 컨테이너가 죽은 뒤에 돌았다).
- GPU 이미지가 "GPU를 잡았으나"는 우회 둘(요구 검사 끄기, 상위 호환 라이브러리 폴더 가리기)을 거친 것임을 드러냈다.
- ADR 0007 이력의 "둘 다 이름은 명세에 맡겼다"는 ADR의 말이 아니어서 고쳤고, 외부 서비스의 경계와 작업 단위 밖이라는 가름은 명세의 LLM 관련성 판정 절에 적었다.
- ADR 0010의 개발과 CI가 CPU 이미지를 쓴다는 문장에 포인터를 달았다.
- admin 계획의 본문에 최소 점수와 리랭커의 422 규칙을 적었다.
- 서두의 "명세 안에서만 쓰는 말 여섯"은 수가 틀렸고 유형 표지, 탈락 지점, 하락폭의 뜻이 없었다. 수를 빼고 뜻을 더했으며, 다른 뜻으로 쓴 "단계"(잡의 스텝, 티켓의 첫머리)와 "묶음"(줄의 목록)을 다른 말로 바꿨다.
- 같은 장치에서 다시 계산한 값이 같다고 단정한 문장을 지우고, 리랭크 기록을 만드는 티켓이 CPU 두 번과 GPU 한 번으로 재게 했다.
- 게이트 잡의 차례에서 글귀 검사가 색인 뒤에야 가능한 것을 반영했다(반영하다 스스로 찾았다).

### 남긴 것과 이유

- 프로브 스크립트 둘의 겹치는 코드와 `argv[2]`로 받는 조건 문자열: 판단 사항이다. 프로브는 한 번 돌리고 근거로 남기는 스크립트라 함께 쓰는 모듈로 묶지 않는다.
- `tools/search_eval.py`라는 경로를 명세가 적은 것: 명세 서두의 예외(이 기능이 새로 두는 재료의 자리)에 든다.
- core 16의 티켓 파일에는 리랭커의 CPU 판정을 적지 않았다. 다른 세션이 지금 그 티켓을 돌리는 것으로 보여(`docker ps`에 `rag-latency-probe-*` 컨테이너가 있었다. 손으로 봤다) 같은 파일을 두 브랜치가 고치면 병합이 부딪힌다. core 계획의 본문에만 적고 사용자에게 알린다. (그 뒤 core 16이 병합되어 이 넘김 자체가 없어졌다. 아래 "core 16의 병합과 다시 맞춘 것".)
- 같은 장치에서 두 번 계산한 값의 차는 CPU만으로 잴 수 있으나 재지 않았다. 다른 세션의 지연 측정이 같은 PC에서 돌아 그 측정을 흔들기 때문이다. 리랭크 기록을 만드는 티켓에 넘겼다. core 16이 끝난 뒤에도 이 세션에서 재지 않았다. 명세가 CPU와 GPU 사이의 차와 한 프로브로 재게 했고, GPU는 드라이버를 올려야 돈다.
- 설계에 없이 이 명세가 정한 것 가운데 사용자에게 따로 보일 것 넷: 빠른 게이트의 dev·main 푸시 실행, 손으로 고친 지식베이스 행에서의 `search_unavailable`, 미리 다는 유형 표지 `no_context`, 사람 표본 40쌍의 대조. ADR 이력의 승인을 물을 때와 마지막 보고에서 알린다.

## 보안 리뷰(내장 `/security-review`, 커밋 d6bf762)

PR 직전 리뷰 때 돌리지 않기로 한 판단을 바로잡았다. PR 서식의 체크리스트와 `docs/constitution/operations.md` 리뷰 파이프라인은 CLI가 돌지 않을 때 보안 축을 내장 `/security-review`가 본다고 정하고, 서식은 문서만 바뀐 PR도 면제가 아니라고 적는다. 커밋 뒤에 돌렸다. `git rev-parse --abbrev-ref origin/HEAD`가 `origin/dev`이고 `git merge-base --is-ancestor origin/dev HEAD`가 0이라 범위는 커밋 하나다.

그 명령은 문서 파일의 지적을 내지 않게 되어 있다(제외 목록). 그래서 취약점을 찾는 하위 작업에 갈래 둘을 맡겼다. 갈래 A는 그 명령의 기준 그대로의 취약점이고, 갈래 B는 명세를 글자 그대로 구현하면 취약점이 되는 설계의 공백이다. 하위 작업은 Read, Grep, Glob만 썼고 호출은 67번이었다. 보고는 바뀐 파일 14개를 작업 트리에서 끝까지 읽었다고 적는다.

갈래 A는 없다. 서버 로그 셋, 스크립트 출력 둘, 이 일지를 줄 단위로 읽어 토큰, 키, 비밀번호, 이메일, 내부 주소가 없다고 보고했고, 프로브 스크립트 둘은 표준 라이브러리로 CLI 인자의 주소에 요청을 보내 응답을 JSON으로 읽을 뿐이라고 보고했다. 본 세션도 같은 패턴을 Grep으로 찾았고 일치가 없었다. 그 명령의 둘째 단계(취약점마다 거짓 양성을 거르는 하위 작업)는 거를 것이 없어 띄우지 않았다.

갈래 B의 지적과 판정은 다음과 같다. 보고가 든 코드는 본 세션이 다시 열어 확인했다.

1. Major, 유효, 고쳤다. 평가 도구가 평가용이 아닌 데이터베이스에 붙는 것을 막는 장치가 현재 판의 요소 비교뿐이다. 명세가 데이터베이스 주소의 이름을 가르지 않고 `migrate`와 같은 코드를 쓰라고만 해서, 제품의 설정 객체를 그대로 쓰면 개발자의 `.env`가 가리키는 데이터베이스에 붙는다. 그러면 기본 지식베이스의 끝점과 리랭커 설정이 덮이고, `judge`가 묶음 밖 문서의 조각을 바깥의 LLM에 보내며, `index --records write`가 그 조각의 벡터를 공개 저장소에 커밋할 파일에 쓴다. → 명세 "자리와 층"에 "평가 전용 데이터베이스" 항목을 더했다. 평가 전용 이름 넷(`RAG_EVAL_DATABASE_URL`, `RAG_EVAL_DATA_DIR`, `RAG_EVAL_EMBEDDING_URL`, `RAG_EVAL_RERANKER_URL`)으로만 받고 제품의 이름과 `.env`는 읽지 않으며, `index`·`run`·`judge`는 묶음의 문서 목록에 없는 키의 문서가 하나라도 있으면 아무것도 쓰지도 부르지도 않고 종료 코드 1을 낸다. 판정은 스키마를 올리기 전에 한다. 보고가 권한 조건 가운데 기본 지식베이스의 끝점과 리랭커 설정이 같아야 한다는 것은 넣지 않았다. 빠른 실행 뒤에 리랭커 끝점을 주고 다시 도는 정상 경로를 막고, 그 조건이 지키려던 것(빈 운영 데이터베이스)은 전용 이름이 막는다. Testing Decisions의 표면 시험에 둘을 더했다.
2. Minor, 유효, 고쳤다. 묶음의 머리와 문서 목록의 경로 칸에 폴더 밖을 가리키지 못하게 하는 규칙이 없다. 지금은 넘는 경계가 없으나 이 형식을 읽는 코드는 `adapters`에 있어 admin이 설치처의 묶음에 다시 쓸 수 있다. → 명세 "평가 세트의 형식"의 `validate` 항목에 경로의 판정을 더했고(절대 경로, `..`, 밖을 가리키는 링크를 읽기 전에 거부하고 `index`도 같다) Testing Decisions의 거부 목록에 더했다.

`retro`를 이 일지의 다음 절을 쓴 때의 계기로 돌렸다. 후보는 열하나이고 승인 여섯, 기각 다섯, 넘김 0이다. 승인한 여섯 가운데 넷은 열린 항목에 회차를 더했고 둘은 새 항목이다. 여섯 모두 더하는 것이라 이 세션에서 반영한 것은 없다. 만료할 항목도 없었다(`uv run python tools/queue_open_rows.py`와, `git fetch origin` 뒤에 `--ref origin/dev`를 붙인 실행이 같은 출력을 냈다).

TEI 어댑터의 요청이나 응답 처리가 바뀌어도 옛 기록이 읽힌다는 지적이다. 맞다. 요청 쪽은 고쳤다. 끝점의 경로와 요청 매개변수의 해시(요청 지문)를 `records.json`에 적고 `validate`가 어댑터의 것과 대 보며, `write`는 지문이 다른 기록의 옛 값을 옮기지 않는다. 기록을 다시 만드는 조건에 어댑터의 추론 동작을 더했다. 응답 쪽(받은 값을 다루는 코드)은 요청 지문이 보지 못한다고 명세에 적었고, 그것까지 기계가 보게 하는 길 셋을 적어 사용자에게 넘겼다.
  5. CodeRabbit Major, ADR 0018 이력의 "전체 게이트는 리랭크 점수를 기록에서만 읽어 CI가 리랭커를 띄우지 않는다". 리랭커 어댑터의 회귀를 보는 경로를 정하라는 지적이다. ADR은 고치지 않았다. 사용자가 승인한 이력이고 결정은 그대로다. 경로는 명세가 정했다(4의 요청 지문, 다시 만드는 조건, 어댑터의 시험). CI에 리랭커를 띄워 표본을 다시 계산하는 길은 그 이력의 결정을 바꾸므로 정하지 않고 사용자가 고를 선택지에 넣었다.
  6. claude-review Nit, `RelevanceJudge`가 ADR 0003의 플러그인 자리가 아니라는 한 줄. 명세의 포트 항목에 더했다. 같은 표현이 있는 ADR 0007 이력은 사용자가 승인한 글이라 고치지 않았다.
- 고치며 새로 쓴 사실 문장과 근거. 문서의 내용 해시가 원본 바이트의 sha256을 16진 소문자로 적은 글이라는 것은 `src/rag_engine/app/ingest.py`의 `hashlib.sha256(request.data).hexdigest()`를 읽었다. TEI 어댑터가 추론 요청에 싣는 경로와 칸은 `src/rag_engine/adapters/tei.py`의 `embed`와 `rerank`를 읽었다. 어댑터의 시험이 요청 본문과 입력 순서를 본다는 것은 `tests/adapters/test_tei_reranker.py`의 요청 본문 단언과 두 시험 파일의 시험 이름을 읽었다. nDCG에서 잘리는 것이 이상적인 순위보다 좋은 결과뿐이라는 것은 정의에서 나온다(값이 1을 넘는다는 것이 곧 그 뜻이다). 리랭커의 CPU 처리량은 이 세션의 프로브가 잰 값이다.
- 명세의 표시 수는 17·7·79·3·8이다(`[정함]`이 하나 늘었다). `uv run python tools/check_adr_pointers.py`는 종료 0이다. 명세 안에서만 쓰는 말에 "요청 지문"을 더했다.
