# core 명세 고침: get_document 전문 창과 제목 표시 · 2026-11-11

사용자가 agent-os의 base-agent 명세가 rag-engine에 넘긴 글(둘)을 붙여 넣어 판정을 맡긴 세션의 기록이다. 지시문 없이 연 세션(Fable 5.1)이고, 브랜치는 `docs/get-document-text-window`(티켓 없는 면제 PR. 명세를 고치는 일), 작업은 워크트리 `get-document-text-window`에서 했다. 준비, 사용자가 넘긴 것, 판정과 근거, 물은 것과 답, 명세에 반영한 것, 티켓 09에 넘긴 것, agent-os에 넘길 글, 셀프 리뷰, 회고, 검증, 다음을 차례로 둔다.

## 준비

- 읽은 것: core 명세(`.scratch/core/spec.md`)의 설정·파싱의 격리와 자원 한도·청킹·검색 흐름·MCP 도구·Testing Decisions 절, 티켓 09(`.scratch/core/issues/09-search-complete-tools.md`), main의 `src/rag_engine/server/tool_models.py`·`search_tool.py`, `src/rag_engine/adapters/parsers/docx_parser.py`, `tests/server/test_tool_models.py`, ADR 0001·0015, `docs/agents/issue-tracker.md`, 직전 티켓 세션 일지(`2026-11-10-1828-core-tickets.md`)의 "사용자가 넘긴 것"과 "물은 것과 답"(사용자가 넘긴 글을 판정하는 선례), agent-os 저장소의 base-agent 명세(`C:\project\agent\.claude\worktrees\base-agent-spec\.scratch\base-agent\spec.md`)에서 `get_document`를 쓰는 자리(승인 뒤에만 부르는 전문 읽기, 출처에 절의 제목을 적는 규칙, 가짜 검색 서버가 둔 전문의 세 모양, rag-engine에 넘긴 문단).
- 코드를 읽은 사실 둘. 첫째, 티켓 09 워크트리(`.claude/worktrees/search-complete-tools`)의 미커밋 `src/rag_engine/app/read_documents.py`의 `_text`는 `"\n\n".join(block.text for block in content.blocks)`라 제목 블록도 문단과 같은 글로 잇는다. 둘째, main의 DOCX 파서는 `Heading N` 스타일을 수준이 있는 제목 블록으로 내고, 명세의 파서 블록 규칙은 PDF가 제목 블록을 내지 않는다고 적었다(PDF·HWPX 파서는 티켓 08이 다른 세션에서 구현 중이다).
- `get_document` 도구는 main에 등록되지 않았다(출력 모델 `DocumentOutput`만 있다). 티켓 09가 다른 세션([feature/09-search-complete-tools])에서 구현 중이다. 그래서 형식의 판 1.0.0은 어느 클라이언트에도 아직 나가지 않은 모양이다.
- 클라이언트의 상한을 보려고 Claude Code 공식 문서 `https://code.claude.com/docs/en/mcp.md`를 2026-11-11에 `curl`로 내려받아(157,100바이트) grep했다. 원문의 두 문장은 아래 인용이다. `anthropic/maxResultSizeChars`는 한 클라이언트의 `_meta` 키라 원칙 III대로 기대지 않는다.
  > Claude Code displays a warning when MCP tool output exceeds 10,000 tokens and limits output to 25,000 tokens by default.
  >
  > for a tool that doesn't declare `anthropic/maxResultSizeChars`, Claude Code saves a successful result with no image content to a file once it's longer than 50,000 characters, whatever its token count.
- 훅의 안내대로 `EnterWorktree`로 워크트리에 들어가 브랜치를 `docs/get-document-text-window`로 바꾸고 세션 제목을 그 이름으로 바꿨다.

## 사용자가 넘긴 것

원문 그대로:

> agent-os의 base-agent 명세가 넘기는 것(2026-11-10, agent-os의 .scratch/base-agent/spec.md).
>
> 1. get_document의 전문 크기에 끝이 필요하다.
>    지금 명세의 get_document는 include_text가 참이면 전문 전체를 text 하나로 돌려주고, 크기를 묶는 설정이나 잘렸다는 표지가 없다.
>    agent-os의 기본 에이전트 assistant는 이 도구를 질문한 사람의 승인 뒤에 부르고, 결과는 통째로 모델의 입력에 들어간다.
>    긴 문서 하나가 실행 하나의 입력 토큰을 크게 늘리는데, agent-os 쪽에서 그것을 묶는 장치(토큰 합 상한)는 아직 없다.
>    판정해 줄 것: (가) 전문의 최대 크기 설정과 잘렸다는 표지(예: truncated)를 둘지, (나) 나눠 읽는 인자(예: offset과 limit)를 둘지, (다) 둘 다 두지 않을지.
>    형식의 판이 바뀌면 agent-os의 가짜 검색 서버가 따라 고친다(agent-os ADR 0048).
>
> 2. 전문에 절의 제목이 드는지를 명세에 적어 달라.
>    assistant의 스킬은 전문에서 가져온 근거의 출처에 "그 내용이 든 절의 제목"을 적고, 전문에 절의 제목이 없으면 "전문"이라고 적는다.
>    지금 명세는 text가 "파싱한 블록의 글을 빈 줄로 이은 것"이라고만 적어, 제목 블록이 그 글에 드는지 알 수 없다.
>    agent-os는 두 모양을 모두 가짜 서버로 재 두었고, 실제 이미지가 나오면 한 번 돌려 확인한다.

## 판정과 근거

1번은 (가)와 (나)를 한 장치로 합친 "창으로 읽기"를 추천했고 사용자가 골랐다. 근거는 넷이다.

- 원칙 III(클라이언트를 모른다). 서버는 임베딩 모델의 토크나이저로만 토큰을 셀 수 있고 그것은 클라이언트 모델의 토큰이 아니라, 크기는 글자(유니코드 코드 포인트)로 잰다. 상한의 값도 클라이언트마다 달라야 하므로 서버 설정은 기본값이자 상한이고 클라이언트가 호출마다 낮출 수 있어야 한다.
- 클라이언트의 상한은 이미 있다. 위 Claude Code 문서의 문장대로 한 클라이언트는 도구 출력을 25,000토큰에서 묶고 50,000자를 넘는 글 결과를 파일로 저장한다. 묶지 않은 전문은 그 클라이언트에서 결과 그대로 모델에 닿지 않는다.
- (가)만 두면 상한 너머는 어느 클라이언트도 영영 읽지 못해 스토리 21(조각만으로 모자랄 때 문맥을 더 읽는다)이 긴 문서에서 서지 않는다. (나)만 두면 인자를 주지 않은 호출이 지금처럼 전문 전체를 낸다.
- 자르는 자리와 다음 자리는 서버만 셈한다. 블록 경계(빈 줄)에서 잘라 표의 행과 제목이 반으로 나뉘지 않게 하고, 클라이언트는 받은 `next_offset`을 그대로 돌려주기만 하므로 코드 포인트와 UTF-16 단위의 차이를 셈하지 않는다. `next_offset`이 null이면 끝이라 잘림 표지를 겸한다.

2번은 코드를 읽은 사실로 답했다. 전문에는 제목 블록이 들고(DOCX·HWPX), PDF는 파서가 제목 블록을 내지 않아 없다. 표시 없이 섞으면 읽는 쪽이 어느 줄이 제목인지 짐작해야 하므로, 제목 블록을 `#`을 수준만큼 붙인 한 줄(ATX 제목 모양)로 내기를 추천했고 사용자가 골랐다. 블록 배열로 내는 안은 쪽 번호까지 낼 수 있지만 블록마다 JSON 칸이 붙어 토큰이 늘고 창의 규칙을 블록 단위로 다시 정해야 해서 추천하지 않았다.

판은 1.0.0 그대로다. `get_document`가 아직 나가지 않았으므로 칸을 더해도 깨지는 클라이언트가 없고, 1.0.0의 모양을 지금 정하는 것이다. 기본값 20,000자는 어림이다(한국어에서 글자 하나가 토큰 하나에 가까운 토크나이저에서도 25,000토큰 안에 들게 잡았다. 값은 설정이라 운영자가 바꾼다).

## 물은 것과 답

사용자 승인이 필요한 셋을 한 화면으로 물었다. 셋 다 추천안을 골랐다.

- 질문 1(글 그대로): get_document의 전문(text) 크기를 어떻게 묶을까요? get_document는 아직 나가지 않았고(티켓 09가 구현 중), 지금 구현은 블록 글을 빈 줄로 이어 전부 돌려줍니다. (선택지 4: 창으로 읽기, (가) 상한과 표지만, (나) offset·limit만, (다) 둘 다 두지 않음)

> 사용자: "창으로 읽기 (Recommended)" — 설명: (가)와 (나)를 한 장치로 합칩니다. 입력에 max_chars(기본·상한은 서버 설정 RAG_DOCUMENT_TEXT_MAX_CHARS, 어림 20,000자)와 offset을 두고, 출력에 전체 길이 text_length와 다음 자리 next_offset을 둡니다. next_offset이 null이면 끝이라 잘림 표지를 겸합니다. 자르는 자리는 블록 경계(빈 줄)이고, 블록 하나가 창보다 길 때만 글자에서 자릅니다. 근거: 클라이언트를 모르므로(원칙 III) 서버가 토큰을 셀 수 없어 글자로 재고, Claude Code 공식 문서(원문을 내려받아 대 봤습니다)는 MCP 도구 출력을 기본 25,000토큰으로 묶고 50,000자를 넘는 글 결과는 모델에 주지 않고 파일로 빼돌립니다. 상한만 두면(가) 상한 너머는 영영 못 읽습니다. (미리보기: 입력 `{"include_text": true, "max_chars": 8000, "offset": 0}`, 출력 발췌 `"text": "# 제1장 총칙\n\n## 제1조 목적\n\n…", "text_length": 23410, "next_offset": 7960`, 마지막 창 `"next_offset": null`)

- 질문 2(글 그대로): 전문에 절의 제목이 드는지를 어떻게 적을까요? 코드를 읽은 사실: 지금 구현은 제목 블록도 문단과 똑같은 글로 잇습니다. DOCX·HWPX 파서는 제목 블록을 내고, PDF 파서는 내지 않아 PDF 전문에는 제목이 없습니다. (선택지 3: # 표시를 붙여 낸다, 표시 없이 그대로, 블록 배열로 낸다)

> 사용자: "# 표시를 붙여 낸다 (Recommended)" — 설명: 제목 블록을 수준만큼 #을 앞에 붙인 한 줄(ATX 제목 모양)로 내고, 문단과 표는 지금처럼 냅니다. 읽는 쪽이 제목을 가려낼 수 있고 토큰은 거의 늘지 않습니다. 명세에는 '전문에 제목 블록이 든다. PDF는 파서가 제목을 내지 않아 없다'를 적습니다. 검색 결과 text가 절 경로를 빼고 location.section에 따로 싣는 것과 다르지만, 전문은 한 줄기 글이라 구조를 안에 둘 수밖에 없습니다.

- 질문 3(글 그대로): 어디에, 언제 반영할까요? get_document는 티켓 09가 다른 세션에서 구현 중이고 아직 main에 없습니다. (선택지 2: 지금 명세를 고치고 09에 알림, 09는 그대로 두고 뒤 티켓이 1.1.0)

## 명세에 반영한 것

스크래치패드의 치환 스크립트 하나로 다섯 자리를 고쳤다(바꿀 자리가 정확히 한 번씩 있는지 단언한다).

- 머리의 근거 줄에 이 세션의 반영 한 문장을 더했다. 표시 수 줄은 본문(7행부터)을 `grep -o`로 다시 센 값으로 고쳤다. 세니 `[정함]`은 고치기 전에도 104였는데 머리는 103이라고 적혀 있었다(직전 세션이 하나를 더하고 세지 않은 것으로 본다. 어림). 이번 값은 `[넘겨받음]` 20, `[사용자 선택]` 6, `[정함]` 104, `[이력]` 3, `[거절]` 7이다.
- "설정" 절 검색의 설정 항목에 `RAG_DOCUMENT_TEXT_MAX_CHARS`(20000)를 더했다(셀프 리뷰 뒤 항목의 머리를 "검색과 문서 조회의 설정"으로 고쳤다).
- "MCP 도구" 절의 `get_document` 항목을 새 모양으로 고쳤다. 입력 `offset`·`max_chars`, 출력 `text_length`·`text`·`next_offset`, 전문의 정의(블록 글을 빈 줄로 잇되 제목 블록은 `#` 줄), 형식마다 제목이 드는지, `include_text`가 아닐 때와 파싱 결과가 없을 때의 null, 범위 밖 인자의 `invalid_argument`다.
- 그 뒤에 `[사용자 선택]` 항목 하나를 더했다. 창을 자르는 규칙(창의 끝은 `offset + max_chars` 이하의 마지막 블록 경계의 시작이고 없으면 `offset + max_chars`, `next_offset`은 창의 끝, 창들을 이어 붙이면 전문과 글자 그대로 같음. 셀프 리뷰 뒤의 모양), 글자로 재는 까닭, 거절한 안 둘, 근거(Claude Code 문서의 원문), 기본값이 어림이라는 것, 판이 1.0.0 그대로라는 것이다.
- Testing Decisions의 HTTP 시험 목록에 창의 사례(마지막 블록 경계에서 잘림, 이어 읽은 글이 전문과 같음, 긴 블록의 글자 자르기, 마지막 창의 null, `include_text` 없이도 `text_length`, 범위 밖 인자)와 제목 표시의 사례(DOCX의 `#` 줄, PDF에 `#` 줄 없음)를 더했다.

바꾸지 않은 것. ADR 0001(읽기 도구만), 0008, 0015(판의 규칙)의 본문 문장은 이 변경으로 거짓이 되지 않아 이력도 포인터도 달지 않았다. `GLOSSARY.md`에 새 용어는 없다. `src/`와 `tests/`는 면제 PR이라 고치지 않고 티켓 09가 구현한다. `.scratch/plan.md`는 티켓 상태가 바뀌지 않아 돌리지 않았다.

## 티켓 09에 넘긴 것

## agent-os에 넘길 글

> 1. 전문 크기: (가)와 (나)를 한 장치로 합쳤다. `get_document` 입력에 `offset`(정수, 0 이상, 기본 0)과 `max_chars`(정수, 1 이상, 기본·상한은 서버 설정 `RAG_DOCUMENT_TEXT_MAX_CHARS`, 기본 20,000자)가 들고, 출력에 `text_length`(전문 전체의 길이. 유니코드 코드 포인트 수. `include_text`와 상관없이 낸다), `text`(`offset`부터 시작하는 창), `next_offset`(다음 창의 `offset`. 전문이 이 창에서 끝났으면 null)이 든다. 따로 `truncated` 칸은 없고 `next_offset`이 null이 아닌 것이 잘림 표지다. 창의 끝은 `offset + max_chars` 이하에 있는 마지막 블록 경계(빈 줄)의 시작이고, 없으면(남은 블록 하나가 창보다 길다) `offset + max_chars`다. `next_offset`은 `offset`에 `text`의 길이를 더한 값이라 다음 창은 빈 줄로 시작할 수 있고, 창들을 이어 붙이면 전문과 글자 그대로 같다(창 사이에 문서가 바뀌지 않았을 때. 받는 쪽이 알 수 있는 신호는 창마다 실리는 `updated_at`이다). 범위 밖 `max_chars`, 음수 `offset`, 전문 길이보다 큰 `offset`은 `invalid_argument`이고, 길이와 같은 `offset`은 빈 `text`와 null `next_offset`이다. 파싱 결과가 없으면 셋 다 null이다(지금과 같다).
> 2. 절의 제목: 전문에는 제목 블록이 들고, 제목 블록은 `#`을 수준만큼 앞에 붙이고 공백 하나를 둔 한 줄이다(`# 제1장 총칙`, `## 제1조 목적`). 문단과 표(행마다 한 줄, 칸은 ` | `)는 그대로다. DOCX와 HWPX의 전문에는 제목이 들고, PDF 파서는 제목 블록을 내지 않아 PDF의 전문에는 제목이 없다. 그래서 가짜 서버의 세 모양(제목이 든 것, 제목 없이 글만 이은 것, null)은 그대로 쓰되 제목이 든 모양은 `#` 줄로 바꾼다.
> 3. 판: 1.0.0 그대로다. `get_document`는 아직 어느 클라이언트에도 나가지 않았고(rag-engine 티켓 09가 구현 중), 이 모양이 1.0.0이다. 가짜 검색 서버는 위 칸을 따른다.
> 4. 참고: `text_length`는 `include_text`가 거짓이어도 오므로, 승인 카드에 전문의 길이를 보여 주고 싶으면 승인 전 호출에서 읽을 수 있다. 상한 20,000자는 어림이고 설정이다.

기각.
- 판정 명령(`check_quotes`, `check_ticket`)을 `cut`·`tail`에 파이프해 종료 코드를 가렸다. 계기 훅 `hook_bash_gate_pipe`가 두 번 알렸고 파이프 없이 로그 파일로 다시 돌렸다. 조건은 이미 있는 훅이 그 자리에서 알린 것. 대기열 gate-pipe-read-status는 이 훅의 거짓 양성을 고치는 항목이라 이 사건(진짜 양성)을 잇지 않았다.
- 셀프 리뷰의 지적 셋(명세 축 Major의 이어 붙이기 반례, 표준 축의 전문 창이라는 말에 정의가 없음, 파서 절이라는 포인터가 절 이름이 아님). 리뷰가 잡도록 둔 기준이고 어긴 구현 지침이 없다(명세 안에서만 쓰는 말의 규칙은 명세 머리에만 있고 `.claude/`와 `docs/agents/`에는 없다). 검사로 옮길 수 없고 새 판단 기준도 아니다.
- Bash 훅 셋(다른 체크아웃으로 `cd`, 복합 git 명령, 40줄 넘는 heredoc)이 그 자리에서 막았고 안내대로 바꿨다(경로 인자, 단순 git 명령, Write 도구로 쓴 스크립트).

일지에만.
- 명세 치환을 적용하던 중 앱이 종료되어 재시작했다. 파일은 디스크에 있었고 리뷰 보고는 이미 일지에 있어 잃은 것은 없다(대기열 review-report-journal-lag의 처방을 지킨 꼴). 재시작 뒤 셋째 스크립트의 적용 여부를 grep으로 다시 확인한 비용만 들었다. 저장소의 처방은 없다.
- 제품의 예열도 같은 멈춤을 낸다. 실제 서버가 기동 직후 Kiwi 적재가 GIL을 쥐는 동안 요청에 답하지 못한다(`asyncio.to_thread`가 막지 못한다. 앱 lifespan의 그 길은 프로브 `.scratch/harness/probes/kiwi_warmup_stall/server_first_request.py`의 원인 재현 갈래가, 스레드 적재 중의 멈춤은 `gil_stall.py`가 쟀다). 에이전트의 실수가 아니라 제품의 동작이라 처방 없이 다음 절에 둔다.
