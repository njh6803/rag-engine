# release-image 명세: main이 움직이면 CI가 릴리스하고, 운영자는 단독 compose로 다섯 컨테이너를 띄운다 · 2026-11-18

release-image 설계 PR(#64, ADR 0020)과 쉬운 말 PR(#65)이 병합된 뒤 주 체크아웃 세션이 낸 지시문으로 연 세션의 기록이다. 시작 프롬프트는 `/to-spec release-image`이고, 브랜치는 `docs/release-image-spec`(명세 PR), 작업은 워크트리 `release-image-spec`에서 했다. 세션은 Fable 5.2 / xhigh로 시작했고 도중에 사용자가 `/model claude-opus-5-5`로 바꿨다. 컨텍스트가 세 번 압축됐다. 준비, 사용자가 넘긴 것, 확인한 것, 물은 것과 답, 반영한 것, 셀프 리뷰, 승인, 검증, 회고, 다음을 차례로 둔다.

## 준비

- 지시문대로 주 체크아웃에서 `tidy-checkouts`를 먼저 돌았다. 루트(dev)를 `fe6d7ab..e7eeab6`으로 당겼고(fast-forward), 병합된 로컬 브랜치 `docs/release-image`를 지웠다. 나머지 워크트리는 도구가 낸 이유(바뀐 파일이 있다, 앱의 표지가 있다, 병합된 PR이 없다, 쥔 프로세스가 있다)로 남겼다.
- 브랜치 `docs/release-image-spec`의 워크트리를 전날 중단된 같은 제목의 옛 세션이 잠그고 있었다. 브랜치에는 커밋이 없고 추적하지 않는 프로브 폴더(`.scratch/release-image/probes/standalone`)만 있었다. 사용자에게 물어("물은 것과 답"의 첫 질문) 잠금만 풀고 그 워크트리에 들어갔다. 옛 세션의 프로세스는 끄지 않았다.
- 브랜치에 커밋이 없어 지시문대로 `origin/dev`(`e7eeab6`)로 당긴 뒤 썼다. 명세 리뷰의 base도 그 커밋이다.
- agent-os(`C:\project\agent`)는 읽기만 했다. 옮길 원본으로 삼은 커밋은 그 저장소 origin/dev의 `1aac0cf`다(명세 "따르는 것과 옮기는 방식").

## 확인한 것

사실의 근거는 명세의 각 항목이 괄호에 적고, 잰 것은 프로브(`.scratch/release-image/probes/`, 표는 그 `README.md`)가 다시 낸다. 여기에는 명세가 답해야 했던 목록과 큰 줄기만 적는다.

- **ADR 0020이 명세에 넘긴 것.** Consequences "명세가 재거나 정하는 것"이 열셋이고(제품 변경의 경로 목록, 이미지를 둘로 가르는 Dockerfile, 이미지 안에 번호를 넣는 방법, 바깥 이미지의 판 고정, 프록시가 넘기는 경로와 MCP 응답의 흐름, 프록시가 서버에 넘기는 머리, 프록시 접근 로그가 남기는 것, 프록시가 받는 TLS의 가장 낮은 판, 단독 compose 시험이 지나는 것, 마이그레이션 파일을 알아보는 PR 제목 검사, 임베딩 서버의 로그가 입력 글을 남기는지, 임베딩 모델 파일의 폐쇄망 반입, 티켓을 나누는 순서), ADR이 어림으로 남긴 것이 셋이다(MCP 응답이 프록시에서 묶이지 않는지, squash 제목 설정이 커밋 하나인 PR에서 어떻게 동작하는지, 느린 시험이 main 병합 때 두 워크플로에서 도는지). ADR 0020 전문을 읽었다.
- **시제품으로 잰 것.** 프로브 `standalone/run.py`가 시제품 이미지 둘과 시제품 단독 compose를 개발 PC의 Windows Docker Desktop에서 띄워 쟀다. 이미지 둘은 524MB이고 층 8개가 같았다. 모델이 이미 든 볼륨으로 단독 compose가 뜨는 데 마지막 실행에서 121초였다(`run_out.txt`의 `up` 줄). 질문 1의 설명에 적은 "33~181초"는 커밋한 출력 어디에도 없는 값이다(아래 "셀프 리뷰"에서 다룬다). 가짜 뒷단의 이어 보내는 응답은 `/mcp`의 버퍼링을 끈 프록시 설정에서 머리 `X-Accel-Buffering`의 유무와 상관없이 온 대로 닿았고, 버퍼링을 끄지 않은 대조군 설정에서는 그 머리가 있으면 온 대로, 없으면 4초 뒤에 한꺼번에 닿았다. nginx 기본 로그는 물음표 뒤의 문서 키를 남겼고, 고른 로그 형식과 오류 줄 끔에서는 남지 않았다. 임베딩 서버(TEI cpu-1.9.4)는 uid 10001과 읽기 전용 루트에서 떴고, 모델 리비전을 고정하면 바깥 길이 없는 네트워크에서 3초 만에 종료 1로 끝났으며, 빈 모델 폴더를 10001이 가지면 첫 시작에 2.2GiB(볼륨의 `du -sh`)를 409초에 내려받았고 root가 가진 폴더에서는 6초 만에 `Permission denied`로 멈췄다(출력 `run_out.txt`, `run_offline_out.txt`, `run_download_out.txt`).
- **squash 제목 설정은 재지 못했다.** 프로브 `squash_title/run.py`가 이 저장소의 병합된 티켓 PR 59개 가운데 커밋이 하나인 것이 0개이고, agent-os의 셋도 PR 제목과 커밋 제목이 같아 설정의 동작을 가를 표본이 없음을 보였다.
- **제품 변경의 경로.** `origin/dev`의 병합이 아닌 커밋 60개 가운데 `src`·`pyproject.toml`·`uv.lock`을 고친 것이 29개이고, `pyproject.toml`을 고친 9개는 모두 `uv.lock`도 고쳤다. 그 가운데 8개는 `src`도 고쳤고, 나머지 하나(`87e981c`)는 개발 의존성만 더했다(`git rev-list`와 `git diff-tree`로 손으로 셌다. ADR 0020 이력 2026-11-18의 첫째 항목).
- **코드를 읽어 확인한 것.** 서버가 싣는 `X-Accel-Buffering: no`는 mcp 2.3.0 `mcp/server/_streamable_http_modern.py:153`과 sse-starlette 3.7.0 `sse_starlette/sse.py:333`이다. uvicorn 0.54.0은 믿을 프록시 주소를 `FORWARDED_ALLOW_IPS`로 받고 기본값이 `127.0.0.1,::1`이다(`uvicorn/config.py:363`). 이 세션이 그 미들웨어를 스크래치 스크립트로 불러 보니 172.18.0.5에서 온 `X-Forwarded-For`는 무시되고 127.0.0.1에서 온 것만 반영됐다(손으로 봤다. 저장소의 프로브는 아니다).

## 물은 것과 답

질문은 `AskUserQuestion`으로 올렸다. 질문 글과 선택지의 라벨·설명을 글자 그대로 옮기고, 사용자가 고른 것은 `> 사용자:` 줄에 적는다. 설명은 이 세션이 쓴 글이다.

### 워크트리 잠금

**질문.** "docs/release-image-spec 브랜치의 워크트리(.claude/worktrees/release-image-spec)를 어제 중단된 같은 제목의 옛 세션(claude.exe pid 28816, 마지막 활동 11-17 20:37)이 아직 잠그고 있어서 들어갈 수 없습니다. 브랜치에는 커밋이 없고, 커밋되지 않은 .scratch/release-image/probes/standalone 폴더만 남아 있습니다. 어떻게 진행할까요?"

- "잠금을 풀고 잇는다 (Recommended)": 제가 git worktree unlock으로 옛 세션의 잠금만 풀고 그 워크트리에 들어가 명세를 씁니다. 옛 세션의 프로세스는 끄지 않으므로, 그 세션을 다시 깨우면 같은 폴더를 두 세션이 쓰게 됩니다.
- "새 워크트리에서 쓴다": 옛 워크트리와 브랜치는 그대로 두고, 새 워크트리에서 docs/release-image-spec-2 브랜치를 origin/dev로부터 따서 명세를 씁니다. 옛 워크트리와 브랜치는 정리되지 않고 남습니다.
- "내가 옛 세션을 닫겠다": 사용자가 앱에서 옛 세션(docs/release-image-spec, 11-17)을 직접 보관하거나 종료한 뒤 알려 주시면, 그때 다시 들어가기를 시도합니다.

> 사용자: "잠금을 풀고 잇는다 (Recommended)"

### 명세의 결정 넷 (한 호출)

**질문 1 (시험 방식).** "release-image의 시험을 네 자리에 두려고 합니다. (1) 릴리스 번호·노트·배포 파일 묶음을 만드는 도구는 임시 git 저장소로 돌려 보는 시험, (2) 실제 이미지를 지어 설치용 compose로 띄운 뒤 HTTPS 포트 밖에서 문서를 넣고 MCP로 검색해 보는 시험(main으로 가는 PR, main 푸시, 릴리스 워크플로에서만 돕니다), (3) `rag-engine --version` 같은 번호 표시는 기존 명령 시험에 추가, (4) 워크플로 파일 자체는 자동 시험 없이 zizmor 검사. 이 가운데 (2)에서 임베딩 서버를 어떻게 띄울까요?"

- "진짜 임베딩 서버로 띄운다 (Recommended)": 운영자가 받는 compose 파일을 바꾸지 않고 그대로 띄워, 검색 결과에 기대한 문장이 나오는지까지 봅니다. 모델 파일(bge-m3)은 검색 평가 잡이 이미 쓰는 CI 캐시에서 꺼냅니다. 제 PC에서는 전체가 뜨는 데 33~181초 걸렸습니다. main으로 가는 PR과 main 푸시에서만 돌아 평소 티켓 PR은 느려지지 않습니다.
- "임베딩 서버만 가짜로 바꾼다": 몇십 초 만에 끝나지만, compose 파일의 임베딩 서버 항목(이미지 판, 시작 인자, 모델 폴더)이 한 번도 시험되지 않은 채 릴리스됩니다. 검색 결과도 가짜 벡터 기준으로만 확인합니다.

> 사용자: "진짜 임베딩 서버로 띄운다 (Recommended)"

**질문 2 (이미지 내용).** "서버 이미지와 작업자 이미지의 내용물을 어떻게 할까요? 지금 코드는 시작 파일 하나가 서버와 작업자를 모두 불러오고, 의존성도 한 묶음입니다. (이미지 이름을 둘로 내는 것은 ADR 0007대로 그대로입니다.)"

- "같은 내용물, 시작 명령만 다르게 (Recommended)": 제품 코드의 구조를 건드리지 않습니다. 시제품으로 재 보니 둘 다 524MB이고 층 8개가 모두 같아, 하나를 받으면 다른 하나는 거의 추가로 받지 않습니다. 이름이 처음부터 둘이라 나중에 내용물을 갈라도 운영자의 설치 파일은 바뀌지 않습니다. 취약점 점검 결과는 두 이미지에서 같게 나옵니다.
- "내용물도 가른다": 서버 이미지에서 문서 파서를, 작업자 이미지에서 웹 서버 쪽을 빼서 각각 작아지고 취약점 점검 대상이 줄어듭니다. 대신 제품 코드의 시작 파일과 의존성 묶음을 먼저 갈라야 해서 티켓이 2~3개 늘고, 얼마나 작아지는지는 아직 재지 않았습니다.

> 사용자: "같은 내용물, 시작 명령만 다르게 (Recommended)"

**질문 3 (MCP 번호).** "MCP 클라이언트가 접속할 때 서버가 알려 주는 정보(serverInfo)의 판 칸에 릴리스 번호를 넣을까요? 지금은 빈 문자열이고, ADR 0020은 번호가 보이는 자리로 `rag-engine --version`과 API 문서 둘만 적었습니다."

- "넣는다 (Recommended)": 클라이언트의 화면이나 로그에 `rag-engine 0.1.0-rc.1`처럼 보여 어느 릴리스에 붙었는지 바로 압니다. MCP 표준에 원래 있는 칸이라 특정 클라이언트에 기대지 않고, 검색 도구의 형식(판 1.1.0)은 바뀌지 않습니다. ADR 0020에 이력 한 줄을 더하고 따로 승인을 받겠습니다.
- "넣지 않는다": ADR 0020 그대로 두 자리만 채웁니다. MCP로만 접속하는 쪽은 서버의 릴리스 번호를 알 수 없고, 필요해지면 나중에 더할 수 있습니다.

> 사용자: "넣는다 (Recommended)"

**질문 4 (프록시 로그).** "프록시(nginx)의 로그에 무엇을 남길까요? 문서를 지우거나 찾는 요청은 문서 키(기본값은 파일 이름)가 주소의 물음표 뒤에 실립니다. 서버 자체는 이 값을 로그에 남기지 않습니다."

> 3. 첫 내려받기가 끊긴 `models/embedding/`을 폐쇄망으로 옮기는 경우다. `refs/main`을 읽는 확인(169줄)은 덜 받은 폴더에서도 지난다(어림). 옮긴 뒤에는 이름 풀기 실패로 멈춰 네트워크 문제처럼 보인다.
>
> **확인한 주장**
> - ADR 0020 "명세가 재거나 정하는 것" 13항목에 모두 답이 있고, 사용자 답 넷이 `[사용자 선택]`으로 실렸다.
> - 옛 이름은 대응 문단과 인용에만 남았다. diff는 용어집, 헌법, 기존 이력을 고치지 않았다. 새 포인터의 제목은 `###` 줄과 같다.
> - Blocked by: source-sync와 release-0-1은 release-image를 바로 기다리고, 나머지 셋은 source-sync를 거쳐 기다린다.
> - 프로브 수치가 출력과 맞는다. `.venv`의 세 줄, agent-os의 nginx digest·8443·15초·400자·노트 차례가 맞고, `uvicorn.run`이 `forwarded_allow_ips`를 넘기지 않는다. 커밋 60개와 pyproject 9개라는 셈도 맞다.
>
> **대조하지 못한 주장**
> - Compose 2.20.2에서 한 번 돌고 끝나는 `migrate`와 `up --wait`가 함께 성공하는지.
> - 리눅스 바인드 마운트의 소유.
> - 실제 MCP 응답의 흐름(가짜 뒷단만 쟀다).
> - 쓰기 가능한 모델 폴더에서 리비전을 고정한 경우(고정한 경우는 모두 읽기 전용 모델 볼륨이었다).
> - TLS를 거부한 것이 설정 때문인지(nginx 1.30의 기본값과 견준 대조군이 없다).
> - agent-os의 292개는 쪽 수가 제한된 표본이고, 친 명령이 기록되지 않았다.

요지: 두 축 모두 Critical은 없다. 표준 축의 강한 위반 8개와 명세 축의 (a)~(d) 17개는 대부분 같은 뿌리(손으로 본 것이나 읽은 것을 잰 것처럼 적은 문장, agent-os에서 옮긴 수를 넘겨받은 것으로 단 표시, 사용자 답의 조건 빠짐)다. 겹친 지적은 pyproject 셈, bake 변수, 59초다.

### 판정과 반영

지적마다 근거(코드, 프로브 출력, agent-os 파일, 실행)를 먼저 대 보고 고쳤다. 줄 번호는 반영 뒤의 명세 줄이다.

- **pyproject 셈(표준 1, 명세 c3).** 맞다. `87e981c`는 `src`를 고치지 않았다(`git diff-tree`). 명세 103·105줄과 ADR 0020 이력 첫째 문단을, 9개 모두 `uv.lock`도 고쳤고 그 가운데 `87e981c` 하나는 `src`를 고치지 않았으나 잠금 파일 때문에 이미 제품 변경이라는 뜻으로 고치고 기점을 커밋 `e7eeab6`으로 적었다. 이 일지 "확인한 것"의 같은 문장도 고쳤다.
- **bake 변수(표준 2, 명세 c2).** 맞다. 127줄을 agent-os의 다섯으로 고쳤다.
- **바탕 이미지의 digest(표준 3).** 맞다. 134줄을, BuildKit이 받아 지었지만 받은 이미지가 이미지 저장소에 남지 않아 digest를 읽지 않았다는 뜻으로 고쳤다(`docker image inspect`가 없는 이미지라고 답했다).
- **바깥 이미지의 digest(표준 4).** 맞다. 155줄에 nginx만 digest로 띄웠고 나머지 둘은 손으로 읽었다고 적었다.
- **59초(표준 5, 명세 c6).** 맞다. 297줄에서 지우고 커밋한 출력의 121초만 남겼다. 질문 1의 설명에 적은 "33~181초"도 커밋한 출력에 없는 값이고, 이 세션은 그 값이 어디서 왔는지 다시 대 보지 못했다. 그 답은 운영자가 받는 compose를 그대로 시험하는지를 가른 선택이고 시험은 main으로 가는 PR에서만 돌아 시간이 판단을 바꾸지 않는다고 보아 다시 묻지 않고, 사용자에게 알린다.
- **리비전 고정의 거절 근거(표준 6).** 맞다. 171줄에 폴더에 없는 리비전을 준 대조군도 똑같이 멈췄다는 것과, 프로브 볼륨의 `refs/main`이 고정한 값과 같다는 것은 프로브가 아니라 이 세션이 손으로 봤다는 것을 적었다.
- **프로브 compose의 주석(표준 7).** 맞다. `standalone/compose.yml` 41~44줄을 "502를 낸 것은 depends_on을 뗀 대조군뿐이었다(sse 5.4초, recover 1.0초)"로 고쳤다.
- **질의 문자열에 키가 실리는 경로(표준 8).** 맞다. 183줄에 관리 API 하나와 수집 API 하나로 고쳤다.
- **판단 항목(표준).** 1MiB 경계는 starlette 1.10.0 `formparsers.py`의 `spool_max_size`를 읽은 근거와 "언저리는 재지 않았다"를 더했다(139줄). `$host`는 nginx 문서의 "host name"을 들고 포트가 붙은 꼴은 재지 않았다고 적었다(185줄). 남긴 것과 이유.

- 186~189줄의 프록시 항목이 한 항목에 사실이 여럿이라 무겁다(표준 Nit). 항목마다 근거가 다른 측정이라 쪼개면 표시와 근거가 흩어진다. 읽기 문제이고 사실은 맞아 남긴다.
- 줄 번호 참조(`ci.yml` 82줄, operations.md 8줄, README 5·37~44·40·88줄, `.coderabbit.yaml` 72줄)가 낡기 쉽다(표준 Nit). 그 줄을 고치는 티켓이 이 명세를 읽고 바로 고치므로 지금 맞는 것으로 충분하다.
- 두 축이 대조하지 못한 것(리눅스 VM, Compose 2.20.2, 실제 MCP 응답의 흐름, nginx 기본 TLS 대조군, 쓰기 가능한 볼륨의 리비전 고정)은 명세가 이미 어림이나 측정 범위로 적었고, 첫 확인은 GitHub 러너에서 단독 compose 시험이 처음 도는 PR이다(Further Notes).

### 새로 쓴 사실 문장 (PR 직전 리뷰에 밀 주장)

반영으로 새로 쓴 문장이다. PR 직전 리뷰의 브리프에 그대로 넘긴다.

1. 명세 103줄: "커밋 `e7eeab6`까지의 병합이 아닌 커밋 60개 가운데 `pyproject.toml`을 고친 것은 9개이고, 9개 모두 `uv.lock`도 고쳤다. 8개는 `src`도 고쳤고, 나머지 하나(`87e981c`, core 01)는 개발 의존성에 테스트 데이터베이스 드라이버를 더한 커밋이라 `pyproject.toml`과 `uv.lock`만 고쳤다." ADR 0020 이력 첫째 문단도 같은 셈이다. 이 일지 "확인한 것"의 "29개"(세 경로 가운데 하나라도 고친 커밋)는 `git rev-list --no-merges --count e7eeab6 -- src pyproject.toml uv.lock`으로 다시 셌다.
2. 명세 119줄: alembic의 head가 둘이면 `command.upgrade(config, "head")`가 "Multiple head revisions are present"로 실패한다.
3. 명세 127줄: agent-os bake 설정의 변수는 `NAMESPACE`, `TAG`, `VERSION`, `REVISION`, `SOURCE` 다섯이다.
4. 명세 134줄: BuildKit이 받은 바탕 이미지는 `docker image inspect`가 없는 이미지라고 답했다.
5. 명세 136줄: `tini`는 바탕 이미지의 Debian 패키지 저장소에서 짓는 날의 판을 받는다(agent-os와 같다).
6. 명세 139줄: starlette 1.10.0 `formparsers.py`의 `spool_max_size = 1024 * 1024`.
7. 명세 144줄과 ADR 0020 이력: 서버 정보는 MCP 표준의 칸이고 검색 도구의 형식과 그 판(1.1.0)은 바뀌지 않는다.
8. 명세 155줄: 프로브는 nginx만 digest로 띄웠고 PostgreSQL과 TEI의 digest는 `docker image inspect --format '{{.RepoDigests}}'`로 손으로 읽었다.
9. 명세 157줄: `${이름:?문구}`의 값이 비면 Compose 5.6.1의 `up -d --wait`가 종료 1과 문구를 내고 컨테이너를 만들지 않는다. `POSTGRES_PASSWORD`는 PostgreSQL 서비스와 데이터베이스 주소에서, `RAG_ALLOWED_HOSTS`는 서버의 `environment`에서 읽는다.
10. 명세 171줄: 폴더에 없는 리비전을 준 대조군도 3초 만에 똑같이 멈췄고, 프로브 볼륨의 `refs/main`이 고정한 값과 같다는 것은 손으로 봤다.
11. 명세 183줄: 문서 키가 질의 문자열에 실리는 경로는 `GET /api/v1/admin/documents?key=`와 `DELETE /api/v1/ingest/documents?key=` 둘이다.
12. 명세 185줄: `$host`는 nginx 문서의 "host name"이고, ADR 0014의 허용 호스트 판정은 이름 그대로와 `이름:*`를 받는다.
13. 명세 186줄: uvicorn 0.54.0은 `FORWARDED_ALLOW_IPS`가 없으면 `127.0.0.1,::1`만 믿는다.
14. 명세 190줄: 서버에 닿지 못한 요청은 프록시 로그에 502·504로만 남는다.
15. 명세 205줄: agent-os 설치 안내의 최소 판은 Engine 28.3.3, Compose 2.20.2다.
16. 명세 213줄: 마이그레이션 환경 파일이 `context.begin_transaction()` 하나로 감싸고 `transaction_per_migration=False`를 바꾸지 않아 스키마 단계가 한 트랜잭션이다.
17. 명세 218줄: agent-os `release.yml`의 계기는 main 푸시뿐이다.
18. 명세 252줄: `.coderabbit.yaml` 72줄은 `path: "Dockerfile"`이고 `README.md` 40줄은 `docker build -t rag-engine .`, 88줄은 `Dockerfile`을 든다.
19. 명세 275줄: 프로브에서 서버가 멈춘 동안 표지를 실은 요청의 응답은 504였고 프록시 로그에 표지가 든 줄이 0개였다.
20. 프로브 `standalone/compose.yml` 41~44줄: 502를 낸 것은 depends_on을 뗀 대조군뿐이었다(sse 5.4초, recover 1.0초).
21. 프로브 `squash_title/run.py` 독스트링: agent-os는 `--pages 3`으로 최근에 닫힌 PR 300개를 읽었다.
22. diag-bundle 계획: uid 10001이 가진 빈 폴더는 바깥 길이 있으면 첫 시작이 모델을 내려받아 뜬다.

다시 돌린 명령: `uv run python tools/check_adr_pointers.py`가 출력 없이 끝났다. 손으로 치는 다섯(테스트, 린트, 포맷 검사, 타입체크, import 경계)은 커밋이 부르는 pre-commit으로 갈음하고, 결과는 아래 "검증"에 적는다.

## PR 직전 리뷰

### 보안 훅의 지적

첫 커밋의 pre-commit이 도는 동안 플러그인의 자동 보안 리뷰가 프로브 `standalone/run.py`를 짚었다. 요지는 다음과 같다(글자 그대로가 아니라 줄였다). 단계 사이의 상태 파일 `state.json`(프로브용 데이터베이스 비밀번호와 발급한 토큰)을 시스템 임시 폴더에 기본 권한으로 쓰므로, 폴더는 0700, 파일은 0600으로 만들고 링크를 따라가지 말라는 것이다(MEDIUM).

- 고친 것: `save_state`가 리눅스에서는 `os.open(…, O_NOFOLLOW, 0o600)`과 `os.fchmod(…, 0o600)`으로 쓴다. 독스트링 머리도 그렇게 고쳤다. 고친 함수를 스크래치 스크립트로 불러 보니 Windows에서 쓰고 덮어쓰기가 됐고 권한은 `0o666`으로 보였다. Windows는 권한 비트를 쓰지 않고 사용자마다 따로 있는 임시 폴더의 권한을 따르므로, 독스트링에 그렇게 적었다. 리눅스 갈래는 돌려 보지 않았다.
- 남긴 것: 작업 폴더와 인증서 폴더는 좁히지 않았다. 프록시 컨테이너(uid 101)가 인증서 폴더를 바인드 마운트로 읽어야 해서, 리눅스에서 0700으로 좁히면 프로브의 프록시가 키를 읽지 못한다. 그 키는 7일짜리 시험용 자체 서명 인증서의 것이다.

### coderabbit-review

서브에이전트가 `coderabbit review --agent --include-untracked --base origin/dev`를 끝까지 돌렸다(`review_completed`, CLI 0.7.5, `auth status`는 `Plan: Free`, `Seat: not assigned`). CLI 지적은 4건이고 서브에이전트 판정은 유효 1, 보류 3, 오탐 0이다. 보고의 요지는 다음과 같다(글자 그대로가 아니라 줄였다).

1. [Minor, 유효] `standalone/run.py`의 서버·작업자 로그 검사가 나온 값 자체를 `leaked` 목록으로 찍는다. 토큰이 새면 그 원문이 커밋하는 출력에 실린다. 지금 출력은 빈 목록이다.
2. [Nit, 보류] 토큰 없는 POST `/mcp`를 본문과 Accept 없이 보낸다. 인증 미들웨어가 본문을 읽기 전에 401을 내므로(`.claude/rules/server.md`) 결론은 맞고, 정상 요청과 짝지은 대조가 아닐 뿐이다.
3. [Minor, 보류] 프록시 `site.conf`의 `error_log … crit`도 요청 줄을 질의 문자열째 싣는다. 임시 파일 쓰기 실패 같은 `crit` 줄에도 실릴 수 있는데, 프로브는 "서버가 멈춘 동안"의 오류만 쟀다. 명세는 `crit`을 문서 키가 남지 않는 보장으로 읽히게 썼다.
4. [Minor, 보류] 임베딩 서버(TEI) 로그에 입력 글이 남지 않는다는 근거가 성공한 요청 26줄뿐이다. 명세가 이미 그렇게 적었지만 "로그 설정은 따로 두지 않는다"는 결정이 원칙 V에 걸린 채 그 빈틈 위에 서 있다.

일지 사실 문장 22개는 서브에이전트가 대 보았다. 어긋난 것은 둘이다. 명세 171줄은 고치기 전에 대조군도 똑같이 멈췄다고 적었는데 대조군이 2초였고(`run_offline_out.txt` 7줄), 명세 167줄이 고치기 전에 uid 10001과 읽기 전용 루트로 32초라고 적은 줄은 루트와 모델 볼륨을 모두 읽기 전용으로 띄운 경우다(같은 파일 5줄). 다시 보지 못한 것은 커밋하지 않은 스크래치 실험(2번 alembic head 둘, 9번 `${이름:?문구}`)과 열어 보지 않은 것(7번, 10번)이다. 서브에이전트는 10번에서 빈 볼륨 대조군(10줄)도 같은 오류로 끝나 "리비전을 주면 허브에 나간다"를 가를 수 없다고 적었는데, 5줄(리비전 없음, 32초에 뜸)과 6줄(리비전 고정, 3초에 멈춤)은 리비전 하나만 달라서 이 프로브가 가른다. 보안 축에서는 출력 파일과 일지에 비밀 값이 없었다.

### 커밋 훅이 막은 것

첫 커밋의 pre-commit에서 줄 구분 문자 검사(`check-line-separators`와 그 pytest)가 `standalone/run_out.txt` 54~56줄의 홀로 선 CR 셋으로 빨강이었다. nginx 413 오류 페이지 본문의 CRLF를 스크립트가 그대로 찍었고, Windows 표준 출력이 줄바꿈마다 CR을 더해 CR CR LF가 됐다. 나머지 검사와 pytest 4562개는 초록이었다. 고친 것은 둘이다.

## dev 합치기

용어 PR(`chore/glossary-release-names`, 2026-11-18 08:30 UTC 병합)이 dev에 오른 뒤 `git merge --no-ff --no-commit origin/dev`로 합쳤다. 기능 계획 셋(admin, release-0-1, source-sync)은 저절로 합쳐졌고, ADR 0020은 두 곳이 충돌했다.

- 본문: 이 브랜치가 포인터를 단 두 줄("제품 판의 번호가 보이는 자리", "옮기는 방식")과 dev가 포인터를 단 "용어" 줄이 붙어 있어 충돌했다. 셋 모두 각자의 포인터를 살렸다.
- 이력: 같은 자리 뒤에 양쪽이 이력을 더했다. dev의 이력 "용어집이 제품 판의 이름을 릴리스로 바꿨다"를 앞에, 이 브랜치의 이력 둘을 뒤에 두었다.

합친 뒤 병합 전 상태를 적은 문장을 고쳤다. 사용자가 승인한 이력 두 곳도 결정이 아닌 이 문장만 바꿨다.

- ADR 0010 이력: "릴리스" 뒤의 괄호(지금 용어집의 제품 판)를 지웠다. 용어집이 이제 릴리스를 정의한다.

2. **고른 선택지의 조건을 명세가 빠뜨리거나 느슨하게 적었다.** 사건: 선택지 설명의 조건 넷을 빠뜨리거나 받는 자리 하나에만 적었고, 설명에 없던 로그 칸과 설명보다 센 문장을 더했다(셀프 리뷰 명세 축). 오류 줄을 끈다는 답을 `crit` 이상을 남기는 설정으로 적었다(PR 직전 리뷰). 조건: 같은 꼴을 처방한 열린 항목이 있어 회차로 센다. 간 자리: `adr-draft-drops-option-conditions`, 2회차. 처방의 자리가 `grill-with-docs` 산출물 단계라 이번 단계(`to-spec`)에는 닿지 않는다. 반영할 때 `to-spec`의 질문 뒤 단계에도 같은 줄을 둘지 본다. 대기열 항목에는 retro 5단계대로 회차와 이 일지 이름만 더했고, 사건의 서술은 이 절이 원천이다.
3. **스크립트와 Windows 리다이렉트가 저장소 파일 다섯을 CRLF로 바꿨다.** 사건: ADR 0020은 합치기 충돌을 푼 스크래치 스크립트의 `write_text`가, 프로브 출력 넷은 Windows 리다이렉트가 CRLF로 만들었다. 합치기 커밋에서 git 경고를 보고도 두었다가 이 회고의 `git ls-files --eol`로 다섯을 찾아 바이트 치환으로 LF로 되돌렸다. 저장소에는 git이 LF로 정규화해 넣어 손상은 없다(되돌린 파일의 `git hash-object`가 색인의 blob과 같았다). 조건: 열린 항목이 처방한 사건이다. 간 자리: `crlf-from-script-edits`, 9회차.
4. **셀프 리뷰 보고를 받은 턴에 일지로 옮기지 않았다.** 사건: 컨텍스트가 압축된 뒤 세션 기록에서 서브에이전트 보고를 꺼내는 스크래치 스크립트로 두 보고를 찾아 옮겼다. 잃은 판정은 없다. 조건: `code-review` 6단계 끝의 지침을 어긴 사건이다. 간 자리: `review-report-journal-lag`, 6회차.
5. **선택 화면과 지시문을 옮기는 추출 스크립트를 또 썼다.** 사건: 일지의 "사용자가 넘긴 것"과 "물은 것과 답"을 글자 그대로 옮기려고 스크래치패드에 스크립트 둘(`extract_questions.py`, `extract_first_user.py`)을 새로 썼다. 조건: 열린 항목이 처방한 사건이다. 간 자리: `extract-asks-tool`, 5회차. 다섯 번째라 반영할 문턱에 닿았지만 이 PR은 명세를 싣는 면제 PR이라 반영은 하네스 chore에 둔다(`measured-claim-beyond-probe`의 5회차도 같게 했다). 더하는 것이 훅이나 검사가 아니라 도구여서 `tools/hook_report.py`는 돌리지 않았다.
6. **1초짜리 검사가 7분짜리 검사 러너 뒤에 막았다.** 사건: 첫 커밋 시도에서 pytest가 433.9초를 돈 뒤에야 `line separators`가 홀로 선 CR로 막았다(pre-commit 출력을 읽었다). 조건: 열린 항목의 어디로 줄이 `line separators`를 앞당길 훅으로 든다. 간 자리: `precommit-mutations-after-tests`, 6회차.
7. **문서만 바꾼 커밋도 전체 pytest를 돌았다.** 사건: `.scratch`와 `docs` 아래 파일만 바꾼 커밋 시도 셋의 pytest가 433.9초, 448.2초, 440.3초였다(pre-commit 출력을 읽었다). 조건: 게이트를 좁히는 것이라 처음에 넘겼고, 사용자가 2026-11-13에 대기열에 두기로 한 항목이다. 이번에는 회차만 더하고, 반영과 ADR 필요 여부는 chore가 정한다. 간 자리: `docs-only-commit-full-pytest`, 6회차.

### 기각

8. **홀로 선 CR.** 첫 커밋에서 `check-line-separators`가 막았다. 이미 있는 검사가 그 자리에서 막은 것이다. 그 시도가 쓴 시간은 6에, CRLF는 3에 셌다.
9. **인용 대조 경고 17건.** `check-quotes`가 알렸고, 줄여 옮기며 따옴표를 단 자리는 합치기 커밋에서 고쳤다. 이미 있는 검사가 알린 것이다. 그대로 둔 11건은 사용자에게 보인 글의 인용이라 저장소에 원문이 없고, 글자는 고치지 않았다.
10. **프로브 상태 파일의 권한.** 플러그인의 자동 보안 리뷰가 짚었고 고쳤다. 이미 있는 리뷰가 그 자리에서 알린 것이다.
11. **가드에 막힌 호출 둘.** 여러 경로를 묶은 Grep의 중괄호 glob이 `.env`를 막는 훅에, mkdir와 printf를 이은 Bash가 권한 거부에 막혔다. 가드가 그 자리에서 막았고, 다른 꼴로 다시 쳐 비용은 재시도 한 번씩이었다.
12. **dev를 합친 뒤 낡은 병합 전 문장.** 지시문이 정한 합치기 자리에서 고쳤다. 정해진 자리에서 처리되어 사건이 아니다.
13. **옛 세션이 잠근 워크트리.** 사용자에게 물어 잠금만 풀었다. 같은 폴더를 두 세션이 쓸 수 있는 일이라 묻는 것이 맞는 동작이었고, 바꿀 것이 없다.
14. **CodeRabbit 서브에이전트의 오독.** 오프라인 프로브의 두 줄이 리비전 하나만 다르다는 것을 놓쳤고, 트리아지가 `run.py`의 `pinned`로 반박했다. 리뷰의 지적을 근거로 가르는 것이 정해진 처리다.

### 만료와 대기열

`uv run python tools/queue_open_rows.py`와, `git fetch origin` 뒤 `--ref origin/dev`를 붙인 실행이 모두 만료할 항목이 없다고 냈다. 두 출력의 회차 5 이상 목록이 같아, 다른 PR이 이 항목들에 회차를 더하지 않았다. 이 회고로 회차 5 이상인 열린 항목은 `extract-asks-tool`이 늘어 열둘이다.

## 봇 첫 회차 (PR 67, 헤드 `6ce1682`)

CI는 모두 초록이었다(`verify`, `python`, `image`, `ticket`, `eval-fast`, `eval-full`, `claude-review`, CodeRabbit). 지적은 26개다. CodeRabbit이 줄 코멘트 8개(Major)와 리뷰 본문의 Minor 16개를, claude-review가 Minor 1개와 Nit 1개를 냈다. 첫 회차라 Minor·Nit까지 하나씩 판정했다. 고친 것 16, 받는 쪽(명세 Testing Decisions)에 적은 것 7, 보류 3이다. compose.yml 95는 고친 것으로 세고, 그 지적의 나머지 둘은 보류 목록에 함께 적었다.

### 고친 것

- **작업자가 임베딩 서버를 기다리지 않는다**(compose.yml 119~121). 명세 단독 compose의 차례 줄에 `worker`가 `embedding`의 `service_healthy`도 기다린다고 더했다. 근거는 임베딩 서버에 닿지 못한 시도도 재시도 횟수를 쓴다는 것이다(`job_failure.py`, `retry_policy.py`, 설정 기본값 6번과 30초). 데몬이 다시 켜질 때는 이 차례가 지켜지지 않을 수 있다는 것은 어림으로 적었다.
- **서버 `/tmp`에 크기 상한이 없다**(compose.yml 95). 명세에 1GiB 상한을 새 `[정함]`으로 더했다. 같은 지적의 나머지 둘은 보류다(아래).
- **업그레이드가 실패할 때 옛 배포 파일이 없다**(spec 213). 바꾸기 전에 옛 `compose.yaml`과 `proxy/`를 남기고, 스키마 단계가 실패하면 그 둘과 옛 번호를 함께 돌린다고 고쳤다.
- **빗금 없는 `/api/v1/ingest`·`/api/v1/admin`**(site.conf 49, admin 계획 13). 시제품과 같은 주 설정으로 띄운 nginx에서 손으로 봤다. 접두 location만 있으면 301에 `Location: http://rag.example.test:8443/api/v1/ingest/`였고, 정확 일치 404를 더하자 404가 되고 하위 경로는 그대로 넘어갔다. 명세 프록시의 경로 줄과 Testing Decisions의 확인 목록에 더했고, admin 계획 13줄에 관리자 페이지의 경로를 더할 때도 같게 하라고 적었다.
- **`nginx -t`와 reload가 시작 설정을 보지 않는다**(spec 192). 손으로 봤다. `-c` 없는 `nginx -t`는 이미지의 기본 설정을 검사하다 `/run/nginx.pid`를 열지 못해 종료 1, `-c` 없는 reload도 같은 파일이 없어 종료 1이었고, `-c /etc/rag-engine/nginx.conf`를 주면 둘 다 지났으며 nginx 기록에 다시 읽은 줄이 남았다. 명세 192줄을 `-c <주 설정>`으로 고치고 확인 목록에 두 명령의 종료 코드 0을 더했다.
- **오류 로그 비교가 다른 오류를 견줬다**(run.py 743~745). 커밋한 출력에서 서버가 멈춘 동안 이 꼴은 504, nginx 기본값은 502였다(`run_out.txt` 70~71줄). 명세 183줄에 그 사실과, 오류 로그를 버리는 결정이 이 비교에 기대지 않는다는 것을 더했다. 프로브 스크립트는 고치지 않았다.
- **squash 제목을 사람이 바꿀 수 있다**(spec 121). 병합하는 쪽이 제목을 주지 않는다는 새 `[정함]`을 더했다. `merge.md`의 squash 병합 명령에 `--subject`가 없는 것을 읽었다.
- **리비전과 소유자가 붙어 찍혔다**(run.py 895~896). `run_download_out.txt` 2줄에서 `5617a9f…aefb181`과 `10001:10001`이 한 값이었다. 스크립트의 `refs/main` 뒤에 `echo`를 넣고, 독스트링과 프로브 README에 커밋한 출력은 고치기 전의 실행이라고 적었다. 출력은 다시 내지 않았다(내려받기 409초와 2.2GiB). 명세 167줄의 사실(받은 리비전이 offline 단계의 것과 같다)은 붙은 값의 앞 40자로 그대로다.
- **squash 프로브의 못 보는 것**(squash_title 14, 53~54). 한 후보와 같아도 설정을 따른 증거가 아니라는 것과, squash가 아닌 병합도 가르지 못한다는 것(merge 커밋은 "둘 다 아니다"로, 커밋이 하나인 PR의 rebase 병합은 "커밋 제목을 따랐다"로 센다)을 독스트링에 더했다. 커밋한 출력은 견준 표본이 0개라 셈이 바뀌지 않아 코드는 고치지 않았다.
- **`compose.hfoffline.yml` 주석**(1줄). 그 변수가 바깥 길을 막는 것처럼 읽혀, 변수의 유무를 견주는 덮어쓰기이고 길을 막는 것은 `compose.offline.yml`의 내부 네트워크라고 고쳤다.
- **diag-bundle 계획의 OCI 라벨**(7줄). version은 릴리스 번호, revision은 지은 커밋이라고 갈랐다.
- **ADR 0010 이력 2026-11-18의 지연 수치**(46줄). 15.3~17.0초는 리랭크 호출이고 검색 전체는 15.5~17.3초, 동시 4건의 검색 전체 p95는 281초라고 고쳤다(`.scratch/core/probes/search-latency/probe_out.txt` 74·77·82줄). 사용자가 승인한 이력의 사실을 바로잡은 것이고 결정은 바뀌지 않았다. 마무리 보고에서 사용자에게 알린다.
- **`serverInfo.version`을 계약 시험에 두지 않는 까닭**(claude-review Minor). 명세 Testing Decisions의 확인 목록 다음 줄에, 원칙 VII은 검색 도구의 형식을 MCP 클라이언트로 접속하는 계약 시험이 판정한다고 정하고 서버 정보의 번호는 그 형식과 판을 바꾸지 않는다고 적었다.
- **근거 줄의 로컬 경로**(claude-review Nit). 명세 5줄에 GitHub 저장소 `njh6803/agent-os`를 함께 적었다. 92줄의 `git -C C:\project\agent` 명령은 개발 PC에서 치는 명령이라 그대로 두었다.

### 받는 쪽에 적은 것

프로브 `run.py`의 지적 일곱(69 상태 폴더, 611 대조 설정 복원, 798~799 고정 볼륨 이름, 154~155 인증서 재사용, 342 `up`이 `try` 밖, 351 `sse`가 본 스택과 같은 프로젝트, 846~849 오프라인 정리)은 맞는 지적이지만, 한 기계에서 손으로 차례대로 돌린 프로브라 커밋한 측정값에는 닿지 않는다. 이 성질을 지켜야 하는 것은 프로브를 원형으로 삼을 단독 compose 시험이라, 명세 Testing Decisions에 한 줄을 더했다(실행마다 새로 만드는 자리, 무작위 꼬리의 프로젝트와 볼륨 이름, 대조 단계마다 `finally`). 그 시험은 둘째 묶음의 티켓이 쓴다. 69는 공유 임시 폴더라는 보안 지적이기도 한데, 커밋한 실행은 사용자마다 따로 있는 Windows 임시 폴더에서 돌았다(독스트링이 적는다).

### 새로 쓴 사실 문장 (다음 층에 밀 주장)

자리는 명세의 절과 줄의 머리로 적는다. 줄 번호는 편집마다 밀린다.

- 명세 프록시의 경로 넷 줄: "시제품과 같은 주 설정으로 띄운 nginx에서 `/api/v1/ingest`는 301에 `Location: http://rag.example.test:8443/api/v1/ingest/`였고, 정확 일치 404를 더하자 404가 되고 `/api/v1/ingest/documents`는 그대로 뒷단으로 넘어갔다." 괄호에 친 `docker run`과 두 사이트 설정, 넘어간 요청이 502였다는 것을 적었다.
- 명세 프록시의 `nginx -t` 줄: "시제품과 같은 주 설정으로 uid 101로 띄운 nginx에서 `-c` 없는 `nginx -t`는 그 기본 설정을 검사하다 pid 자리(`/run/nginx.pid`)를 열지 못해 종료 1이었고, `-c` 없는 `nginx -s reload`도 같은 파일이 없어 종료 1이었다. `-c`를 주면 둘 다 지났고 nginx 기록에 다시 읽은 줄이 남았다." 괄호에 친 `docker exec` 명령 넷을 적었다.
- 명세 프록시의 "위 로그 꼴의 근거는 둘이다" 줄: "다만 그 요청에 이 꼴은 504, nginx 기본값은 502로 답해 두 설정이 같은 오류를 로그에 남긴 것을 견준 것은 아니다."
- 명세 단독 compose의 "차례는" 줄: "그 시도가 작업의 재시도 횟수(기본 6번)를 쓰기 때문이다", "마지막 시도였던 작업은 실패로 끝나 다시 넣기 전에는 돌아오지 않는다", "모델을 처음 내려받는 시작이 띄우는 명령의 기다림(1800초)을 넘기면 작업자는 뜨지 않은 채 남으므로". 셀프 리뷰 표준 축의 지적으로 더한 "이 차이가 위 0.1초에 닿지 않는다고 본다(어림)"도 든다.
- 명세 이미지의 구성의 "서버의 `/tmp`에는" 줄: "크기 상한(`RAG_MAX_UPLOAD_MB`, 기본 100MB)을 넘는 업로드도 수집 API가 크기를 보기 전에 끝까지 그 자리에 쓰인다". 같은 사실을 명세 Out of Scope와 release-0-1 계획에도 적었다.
- 명세 번호와 느낌표의 "병합하는 쪽은" 줄: "이 저장소의 병합 절차(`next-session`의 `merge.md` 병합 명령 `gh pr merge <번호> --squash --match-head-commit <HEAD>`)는 제목을 주지 않으므로 설정의 PR 제목을 쓴다."
- ADR 0010 46줄: "질의 임베딩과 데이터베이스 검색을 더한 서버의 검색 전체는 15.5~17.3초였다", "같은 프로브의 동시 4건은 검색 전체의 p95가 281초였다."
- `run.py` 독스트링과 프로브 README: 커밋한 `run_download_out.txt`는 `echo`를 넣기 전의 실행이라 앞의 40자가 리비전이다.
- `squash_title/run.py` 독스트링: merge 커밋은 "둘 다 아니다"로, 커밋이 하나인 PR의 rebase 병합은 커밋 제목을 따른 것으로 센다는 문장(코드를 읽었다). 처음에는 squash가 아닌 병합이 모두 대개 "둘 다 아니다"로 세어진다고 썼고, 셀프 리뷰 표준 축이 rebase 반례를 잡아 고쳤다.

## 셀프 리뷰 (봇 첫 회차 반영)

`code-review`를 고정점 `6ce1682`(PR 67의 헤드)로 돌렸다. 범위는 커밋하지 않은 작업 트리 변경이고, 처음 본 범위는 파일 16개, 커밋 0개, 미추적 0개다. 반영하며 release-0-1 계획을 더 고쳐 커밋에는 17개가 실린다. 명세는 사용자 요청으로 두었다. 요구는 위 "봇 첫 회차" 절의 판정대로 고친 것과 받는 쪽에 적은 것이 그대로 반영됐는지, 그리고 retro 5단계대로 대기열 일곱에 회차를 더한 것이다. `uv run python tools/sibling_overlap.py`는 형제 워크트리 `glossary-harness-small-names`(PR #68)가 `measured-claim-beyond-probe.md`를 함께 고친다고 알렸다. 그 브랜치가 먼저 병합되면 이 항목의 승인 줄을 합칠 때 두 회차를 함께 남긴다.

### 표준 축

지적 넷을 모두 고쳤다.

- squash 프로브 독스트링이 squash가 아닌 병합을 모두 "둘 다 아니다"로 센다고 닫았는데, 커밋이 하나인 PR의 rebase 병합은 "커밋 제목을 따랐다"로 세어지는 반례가 있다. 두 갈래를 나눠 적었다.
- 명세 단독 compose의 차례 줄이 시제품의 0.1초 측정을 새 차례(작업자가 임베딩 서버도 기다린다)의 근거처럼 읽혔다. 측정은 프록시와 서버의 차례에 대한 것이고, 작업자의 차이가 그 값에 닿지 않는다는 것은 어림이라고 갈랐다.
- 프록시 경로 줄의 "정확 일치 location"에 풀이가 없었다. location이 무엇인지 처음 나오는 자리에 풀이를 붙였다.
- 일지의 새로 쓴 사실 문장 목록이 명세 줄 번호로 자리를 적어 편집마다 밀렸다. 절 이름과 줄의 머리로 바꿨다.

### 명세 축

지적 열을 판정했다. 모두 고쳤고, 5는 사용자에게 확인받는 일로 남았다.

1. 받는 쪽에 적은 Testing Decisions 줄에 프로브 `run.py` 351(`sse` 단계가 본 스택과 같은 프로젝트를 `down -v`로 내린다)의 요지가 빠졌다. "따로 띄우는 대조 스택은 본 스택과 다른 프로젝트 이름을 쓰고, 볼륨째 내리는 호출(`down -v`)은 그 호출이 띄운 프로젝트에만 친다"를 더했다.
2. compose.yml 95 보류의 근거 "원칙 VII의 계약인 수집 API"가 틀렸다. 원칙 VII은 판을 붙이는 규칙이지 이 기능 밖이라는 근거가 아니다. 근거를 "수집 API의 코드를 고치는 일이라 이미지와 배치를 정하는 이 기능 밖"으로 바꾸고, 받는 쪽을 release-0-1 기능 계획(0.1을 내기 전에 할지 그 명세가 정한다)과 명세 Out of Scope에 적었다. PR 코멘트 초안도 같게 고쳤다.
3. 위 "고친 것"의 squash 항목이 고치기 전 독스트링을 서술했다. 지금 독스트링에 맞췄다.
4. 대기열 일곱의 승인 줄과 본문에 사건 서술을 길게 더했다. retro 5단계는 기존 항목에 회차 수와 일지 파일명만 더하게 한다. 일곱 모두 회차와 파일명만 남기고, `adr-draft-drops-option-conditions`와 `review-report-journal-lag`에 더한 본문 문단을 걷었다. `precommit-mutations-after-tests`에 적은 "pytest 안의 줄 구분 문자 시험도 같은 자리로 빨갰다"는 근거가 없는 문장이라 함께 사라졌다. 처방의 자리에 대한 메모는 위 회고 2번에 옮겼다.
5. ADR 0010 이력의 수치 정정은 사용자가 승인한 이력의 문장을 바꾼 것이라 병합 전에 확인받아야 한다. "다음"의 "병합은 묻지 않는다"를 고치고, 커밋 뒤 앞뒤 문장을 보이고 묻는다.
6. Testing Decisions의 `serverInfo.version` 줄이 "그 시험은 원칙 VII이 말하는 검색 도구의 형식을 판정하고"로 닫혀, 그 시험이 다른 것도 볼 수 있다는 반례가 섰다. 원칙 VII이 정하는 것(검색 도구의 형식을 MCP 클라이언트로 접속하는 계약 시험이 판정한다)을 그대로 옮기는 꼴로 바꿨다.
7. 명세의 "손으로 봤다" 둘(빗금 없는 경로의 301, `nginx -t`와 reload의 `-c`)에 친 명령이 없었다(`docs/agents/issue-tracker.md` 26줄). 괄호에 `docker run`, 두 사이트 설정, `docker exec` 명령 넷을 적었다. 일지의 `/tmp` 인용은 명세의 글자와 다르게 마침표를 붙였던 것을 맞췄다.
8. 차례 줄의 "그때 먼저 뜬 작업자의 실패는 재시도의 기다림이 받는다"가 거짓이다. 마지막 시도였던 작업은 기다림 없이 실패로 끝난다(`job_failure.py`를 읽었다). 횟수가 남은 작업과 마지막 시도였던 작업을 갈라 적었다.
9. 모델을 처음 내려받는 시작이 띄우는 명령의 기다림(1800초)을 넘기면 작업자가 뜨지 않은 채 남는 갈래가 빠졌다. 설치 안내가 그때 같은 명령을 다시 치라고 적는다고 더했다(어림).
10. 업그레이드 절의 셋이 빠졌다. 옛 파일을 옮기지 않고 복사해 두는 것(어림), 되돌릴 때 `--remove-orphans`, 새 `proxy/`를 먹이는 `nginx -s reload -c <주 설정>`(어림)을 더했다.

PR 67(base dev)은 명세 커밋 `84aa85c`와 dev 합치기 `6ce1682`를 싣고 열려 있고, 이 일지의 회고와 봇 첫 회차의 반영과 다음은 셋째 커밋으로 간다. 봇 첫 회차는 위 절대로 판정했다. 둘째 회차부터는 Critical·Major만 고치고, 남긴 것은 PR 코멘트에 이유를 적는다. ADR 이력 셋은 사용자가 승인했지만, 봇 첫 회차에서 ADR 0010 이력의 지연 수치를 바로잡았으므로 병합 전에 고친 앞뒤 문장을 사용자에게 보이고 확인받는다. 거절하면 그 줄을 되돌린다. base가 dev인 PR이라 `merge.md`의 워크트리에서 병합할 때 1~4로 squash 병합한다. 이 PR은 끝 줄을 적지 않아 출시 PR의 계기가 아니다. 주 체크아웃 미갱신: 루트는 dev(`git worktree list`의 첫 줄. `6957194`에 있어 `origin/dev`의 `bc31442`보다 뒤처져 있고, 이 세션은 당기지 않는다).

병합 뒤의 다음 단계는 release-image의 티켓이다. `spec.md`가 있고 `issues/`가 없다. 먼저 `spec-reviewer` 서브에이전트로 명세를 검토하고, 그 뒤 `/to-tickets .scratch/release-image/spec.md`를 친다. 새 세션에서 연다(Opus 5.5 / xhigh, Docker가 켜진 로컬 세션).

티켓의 입력은 명세의 Implementation Decisions "티켓을 나눌 때 함께 둘 것"이다. 다섯 묶음과 그 차례(첫째 → 둘째 → 셋째, 넷째와 다섯째와 리뷰 봇 프롬프트는 첫째와 나란히, 릴리스 워크플로와 릴리스 설정 파일을 싣는 티켓이 모두의 뒤)를 거기서 읽는다. 명세가 재지 않았다고 적은 것(리눅스 VM, Compose 2.20.2, 실제 MCP 응답의 흐름, 프록시의 `crit` 줄, 임베딩 서버가 거절한 요청의 로그, 바탕 이미지 둘의 digest)은 그 자리를 맡는 티켓의 수용 기준으로 옮긴다.

사람 몫은 사용자에게 다시 알릴 일이다(명세 "사람 몫"). Docker Hub의 저장소 둘과 접근 토큰, 배포 브랜치를 main 하나로 좁힌 GitHub 환경 `release`와 그 안의 비밀 값 둘(`DOCKERHUB_TOKEN`, `RELEASE_GH_TOKEN`)과 변수 `DOCKERHUB_NAMESPACE`는 릴리스 워크플로를 처음 main에 싣는 출시 PR을 병합하기 전에 끝나 있어야 한다. squash 병합의 제목을 PR 제목으로 쓰는 저장소 설정은 PR 제목 검사를 옮기는 티켓(넷째 묶음)을 병합하기 전에 바꾼다. 비밀 값은 사용자가 직접 넣고 세션에 넘기지 않는다.
