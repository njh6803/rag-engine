# source-sync 명세: 원천을 지우는 요청은 지움 표시만 세우고 문서는 작업자가 50건씩 옮기며, 전파 설정은 compose에 넣지 않는다 · 2026-11-21

source-sync 설계 PR(#89, ADR 0021·0022)이 병합된 뒤 그 세션이 낸 지시문으로 연 세션의 기록이다. 시작 프롬프트는 `/to-spec source-sync`이고, 브랜치는 `docs/source-sync-spec`(명세 PR), 작업은 워크트리 `source-sync-spec`에서 했다. 세션은 Fable 5.2 / xhigh로 돌았고, 컨텍스트가 여러 번 압축됐다(셀프 리뷰의 반영을 마친 시점에 세션 기록의 압축 요약이 여덟 개다. 기록 파일에서 `"isCompactSummary":true`를 Grep으로 세었다). 준비, 사용자가 넘긴 것, 확인한 것, 물은 것과 답, 반영한 것, 셀프 리뷰, 승인, PR 직전 리뷰, 검증, 회고, 다음을 차례로 둔다.

## 준비

- 지시문대로 주 체크아웃에서 `tidy-checkouts`를 먼저 돌았다. 루트(dev)를 `3cd84f5`에서 `2c6f2c0`(`origin/dev`와 같은 커밋)으로 당겼다. 병합된 로컬 브랜치 여섯(`chore/glossary-release-number-names`, `chore/glossary-standalone-pan-names`, `feature/08-ci-releases-from-main`, `hotfix/standalone-test-fills-image-namespace`, `worktree-glossary-release-number-names`, `worktree-source-sync`)을 지웠다. 병합된 워크트리 넷(`02-tools-compute-release-number-notes-bundle`, `04-install-guide-walks-operator`, `05-notes-check-guards-upgrade-bang`, `glossary-constitution-version-names`)은 한 시간 넘게 쉬던 세션의 프로세스를 도구로 끝낸 뒤 지웠다. 그 세션들은 사이드바에 남아 있다.
- 도구가 `끝낸다`로 낸 다섯 가운데 `06-release-docs-and-merge-procedure`는 끝내지 않았다. 사용자가 사이드바에 고정해 둔 세션이어서 이 세션의 판단으로 프로세스를 끄지 않았고, 보고에 그렇게 적었다. 다음 정리 때 다시 후보로 나온다.
- 남긴 것은 도구가 낸 이유대로다. `14-reindex-version-switch`는 병합된 PR의 머리 커밋과 브랜치 끝이 달라 도구가 사람에게 넘겼다. `05-full-run-rerank`, `13-first-judge-run`, `to-spec-grep-probe-output`은 다른 프로세스가 작업 폴더로 쥐고 있었다. `glossary-release-number-names`, `glossary-root-branch-merge-back`, `release-image`는 잠금을 건 세션의 프로세스가 살아 있었다. `source-sync`는 그 브랜치를 맡은 세션이 돌고 있었다. `08-ci-releases-from-main`과 `release-search-eval`은 병합된 PR이 없었고, `10-public-docs-questions`에는 바뀐 파일이 있었다. 앱이 만든 워크트리 둘(`16-search-latency-probe-f30c20`, `relaxed-grothendieck-e892b9`)은 앱의 정리에 맡겼다. 휴지통에는 `.venv` 폴더 21개가 남았다(다른 프로세스가 `.pyd` 파일을 쥐고 있었다).
- 지시문대로 주 체크아웃에서 브랜치를 따지 않고 `EnterWorktree`(name `source-sync-spec`)로 새 워크트리에 들어갔다. 워크트리의 시작 커밋이 `origin/dev`(`2c6f2c0`)와 같은 것을 본 뒤 거기서 브랜치 `docs/source-sync-spec`으로 바꿨다. 명세 리뷰의 base도 그 커밋이다.
- 프로브는 개발 PC에서 돌았다. `cron-expr`는 그 PC의 Python 3.12.10에서 바로 돌렸고, 나머지 셋은 Windows Docker Desktop(엔진 29.9.2, WSL2 커널 6.18.58.1)에 띄운 컨테이너를 상대로 돌렸다. 프로브용 PostgreSQL 컨테이너(`rag-probe-sync-pg`)는 측정이 끝난 뒤 내렸다.

## 확인한 것

사실의 근거는 명세의 각 항목이 괄호에 적고, 잰 것은 프로브(`.scratch/source-sync/probes/`, 표는 그 `README.md`)가 다시 낸다. 여기에는 명세가 답해야 했던 목록과 큰 줄기만 적는다. 탐색에 서브에이전트를 쓰지 않았고 아래는 모두 이 세션이 직접 읽거나 돌린 것이다.

- **명세가 답해야 했던 것.** ADR 0021 Consequences의 "명세가 재거나 정하는 것" 여섯(전파 설정으로 나중에 붙인 공유 폴더가 보이는지, 만든 뒤 바꿀 수 있는 설정, 지운 원천의 이름을 다시 쓸 수 있는지, 없거나 지운 원천을 적은 수집 요청의 오류 코드, 원천을 지우는 순간의 작업을 거두는 방법, 원천과 함께 지워진 문서를 가르는 표시), ADR 0022가 본문과 Consequences에서 명세에 넘긴 것(시간대 설정의 이름, 동기화 기록의 보관, 정리 작업이 도는 시각, 꺼내는 순서를 가르는 방법, 일정 확인이 자리와 따로 도는지, 목록을 만든 뒤 바뀐 파일, "모두 다시 읽기"를 둘지, 지킬 조건 여럿), 기능 계획의 세 문단(설계의 셀프 리뷰, PR 직전 리뷰, PR 봇 리뷰가 넘긴 물음), core 명세와 release-image 명세가 넘긴 것이다.
- **지시문이 짚은 글 둘.** ADR 0022 "동기화의 차례"에 승인 뒤 더해진 문장과 기능 계획의 "PR 봇 리뷰가 명세에 넘긴 것" 문단은 CodeRabbit이 보지 않은 글이라고 지시문이 알렸다. 둘 다 명세의 입력으로 읽었다. 앞의 것은 명세의 "동기화의 차례" 절이 옮겼고 그 절의 결정과 글자 그대로 맞았다. 뒤의 것(변경 확인값이 같아도 모두 다시 읽는 길)은 사용자에게 물어 정했다("물은 것과 답"의 둘째 질문).
- **읽은 문서.** 설계 일지, 기능 계획 다섯(source-sync와 이 기능을 기다리는 admin, db-source, diag-bundle, backup-upgrade), ADR 0008·0009·0012·0013·0020·0021·0022, core 명세의 수집·삭제·되살림·잠금·시험 절, release-image 명세의 단독 compose와 설치 안내 절, 용어집, `docs/agents/issue-tracker.md`의 프로브와 근거 절, `docs/constitution/operations.md`, 킥오프 입력 4절이다.
- **읽은 코드.** `domain`의 엔티티, 포트, 오류 코드, `app`의 수집, 문서 삭제, 문서 색인, 기본 레코드, `adapters`의 표 정의, 작업 대기열, 벡터 색인, 파일 저장소, 설정, `ingest` 명령, `server`의 수집 API와 관리 API와 그 모델, Problem Details, `worker`의 조립과 작업 처리, 단독 compose와 `.env.example`과 설치 안내다. 명세에 "코드를 읽었다"고 적은 사실은 여기서 나왔다. 원본 경로는 수집 요청마다 새 이름으로 짓고, 수집은 원본을 먼저 쓴 뒤 문서 행을 적으며, 파일 저장소에는 열거가 없고, 후보 조각을 뽑는 질의는 조각 표만 읽고, 작업자는 꺼낼 작업이 없을 때만 주기를 기다리며, 관리 API의 목록은 `limit`와 `after`로 넘기고, 문서 응답에는 원천 이름이 이미 실린다.
- **프로브 넷.** 실행 명령과 버전은 프로브 폴더의 `README.md`에 있다. 아래의 수는 셀프 리뷰 뒤에 프로브를 보강해 다시 돌린 출력의 것이다(`schedule-once`와 `mount-propagation`을 다시 돌렸고, 시간은 돌릴 때마다 달라 앞 실행의 값과 다르다). `schedule-once`는 PR 직전 리뷰 뒤에 한 번 더 고쳐 돌렸고 아래의 수는 그 마지막 출력의 것이다("PR 직전 리뷰"의 판정).
  - `cron-expr`: cronsim 2.8은 여섯 칸 표현식을 오류 없이 받아 첫 칸을 초로 읽었다. 일곱 칸, 네 칸, 빈 글, `@daily`는 `Wrong number of fields`로 거부했고, 값이 틀린 표현식과 2월 31일은 표현식을 만들 때 예외를 올렸다(프로브가 예외가 난 단계를 찍는다). 설계에서는 리뷰어의 웹 요약이던 것을 쟀다. 명세의 규칙(칸이 다섯일 때만 넘긴다)을 쓴 함수가 pyright strict를 지났다.
  - `schedule-once`: 연결 여덟이 원천 40개의 일정을 25회차 동안 동시에 확인했을 때 원천 행 잠금(`FOR UPDATE SKIP LOCKED`)은 원천 하나마다 커밋하는 모양(A)과 시각이 지난 원천을 트랜잭션 하나에서 모두 잡는 명세의 모양(A2) 모두 작업 1000건(기대 1000건)을 넣었고, 잠금 없는 대조는 4028건을 넣었다(틈을 2ms 둔 쪽은 4728건). 원천마다 종류마다 대기·실행 중 작업을 하나로 묶는 부분 유일 색인은 동시에 넣기 50회차에서 회차마다 하나만 받았다. 원천도 문서도 가리키지 않는 정리 작업 둘은 빈 값끼리 같은 값으로 보는 색인(`NULLS NOT DISTINCT`)에서만 둘째가 거부됐다. 색인 작업 10만 건이 대기 중일 때 꺼내는 질의의 가운데값은 지금 질의 78.7ms, 종류를 정렬에 넣은 질의 192.8ms, 색인 작업이 아닌 것만 먼저 묻는 질의 1.6ms였다. 겹치면 넣지 않는 문장에서 색인의 조건을 바인드 값으로 적은 꼴은 11번째 실행에 `InvalidColumnReference`(42P10)로 실패했다(D3).
  - `source-delete`: 문서 1만 건과 조각 10만 개인 원천을 한 트랜잭션에서 삭제 보관함으로 옮기면 커밋 전까지 16.12초가 걸렸고 그동안 그 원천의 문서 행 하나를 `FOR UPDATE`로 잠그려던 다른 연결이 막혔다. 한 트랜잭션에서 되살리면 756.69초였다. 문서 500건씩 나누면 삭제는 전체 15.50초(묶음 가운데값 0.62초), 되살리기는 전체 794.88초(묶음 가운데값 39.41초)였다. 묶음을 50건으로 줄여 한 번 더 쟀더니(`probe_out_batch50.txt`) 삭제는 전체 16.83초(가운데값 0.08초), 되살리기는 전체 760.94초(가운데값 3.58초)였다. 묶음을 줄여도 전체 시간이 거의 같아(삭제는 1.33초 늘었고 되살리기는 33.94초 줄었다) 둘 다 50건으로 정했다.
  - `mount-propagation`: 기본 설정으로 띄운 컨테이너에는 뜬 뒤에 붙인 폴더가 보이지 않았고 `rslave`로 띄운 컨테이너에는 보였다. 서버 기계의 루트가 shared가 아니면 `rslave`로 컨테이너가 뜨지 않았고, 읽기 전용으로 붙였는데도 나중에 전해진 폴더에는 쓰기가 됐다. `docker restart`로 다시 띄운 컨테이너에는 그 폴더가 보였고 쓰기는 막혔다. Docker Desktop에서 `rslave`를 적어 띄워도 오류는 나지 않았다. 셀프 리뷰 뒤에 두 단계를 더 쟀다. 단독 compose가 붙일 모양에서 `docker compose restart server worker`로 다시 띄워도 결과가 같았고(9단계), 설치 폴더에 `sources/`가 없을 때는 Docker가 그 폴더를 root의 것으로 만들고 컨테이너가 떴다(10단계).
- **명세를 쓰다 뒤늦게 본 것.** ADR 0013 본문의 "검색 표에 산 것만 두어 검색 SQL에 삭제 필터가 없고"가 원천 삭제의 결정(검색이 지운 원천의 조각을 뺀다)으로 거짓이 된다는 것을 "원천 삭제와 되살리기" 절을 쓰던 중에 알았다. 그 전까지는 이력을 더할 ADR이 0021 하나라고 보고 있었다.
- **재지 않은 것.** 실제 NFS·SMB 공유 폴더에서의 동작, 배포판 리눅스 서버의 커널에서의 동작, 권한 비트가 Windows와 root에서 읽기를 막지 못한다는 것, 원천 행의 공유 잠금으로 세운 순서가 실제로 멈춤 없이 도는지, 제품이 쓰는 잠금(`FOR NO KEY UPDATE`)이 원천 삭제의 긴 트랜잭션에 막히는지, 되살리기가 느린 까닭이 어느 색인인지는 재지 않았다. 명세에 어림이나 "시험이 판정한다"로 적었다. 처음에는 `docker compose restart`도 재지 않은 것이었으나 셀프 리뷰 뒤에 쟀다(위 9단계).

## 물은 것과 답

질문은 `AskUserQuestion` 한 호출로 셋을 올렸다. 질문 글과 선택지의 라벨·설명을 글자 그대로 옮기고, 사용자가 고른 것은 `> 사용자:` 줄에 적는다. 설명은 이 세션이 쓴 글이다. 셋째 질문의 설명은 "전달 설정"이라고 적었는데 명세와 ADR이 쓰는 말은 "전파 설정"이다.

**질문 1 (시험 방식).** source-sync 명세(서버 폴더를 일정에 따라 읽어 와 색인하는 기능)의 자동 시험을 어떤 방식으로 걸까요? 지금 core 기능은 서버를 실제 HTTP 요청으로 부르고 실제 테스트 PostgreSQL을 쓰는 방식으로 시험합니다.

- 지금 방식 그대로 (Recommended): 서버를 HTTP 요청으로 부르고 실제 테스트 PostgreSQL을 씁니다. 원천 폴더는 시험마다 만드는 임시 폴더로 바꾸고, 일정은 시계를 기다리지 않고 '지금 시각'을 직접 넣어 한 번 돌립니다. 여기에 폴더 읽기(바로 가기 링크, 한글 이름), 일정 계산, 작업 대기열, 설치처가 만든 커넥터 흉내를 작은 시험으로 따로 보고, 실제 컨테이너를 띄우는 단독 compose 시험에는 '폴더를 붙여 동기화가 한 번 도는 장면' 하나만 더합니다.
- 컨테이너 시험을 넓게: 위 방식에 더해, 실제 컨테이너를 띄운 단독 compose 시험에서 전 과정(원천 만들기, 동기화, 폴더에서 파일을 지운 뒤 검색에서 빠지는 것, 원천 삭제와 되살리기)을 확인합니다. 실제 설치와 가장 가깝지만 컨테이너를 띄우는 시간만큼 CI가 느려집니다.
- 컨테이너 시험 없이: 컨테이너에 폴더를 붙이는 장면은 자동 시험에서 빼고 손으로 확인합니다. CI는 빨라지지만 compose 파일에 폴더를 잘못 붙인 실수를 자동 시험이 잡지 못합니다.

> 사용자: 지금 방식 그대로 (Recommended)

**질문 2 (다시 읽기).** '지금 동기화'에 '모두 다시 읽기' 옵션을 둘까요? 보통 동기화는 파일의 수정 시각과 크기가 그대로면 그 파일을 열어 보지 않습니다. 이 옵션을 켜면 폴더의 모든 파일을 다시 읽어 내용을 대 보고, 실패했거나 건너뛴 문서(암호 걸린 파일, 글자 없는 파일)도 다시 시도합니다.

- 옵션을 둔다 (Recommended): 수정 시각은 그대로인데 내용만 바뀐 파일이나, 파서를 고친 뒤 다시 봐야 하는 실패·건너뜀 문서를 운영자가 원천 하나만 골라 다시 처리할 수 있습니다. 폴더가 크면 모든 파일을 읽느라 그 동기화가 오래 걸립니다. 임베딩 서버가 꺼져서 실패한 문서는 이 옵션 없이도 다음 동기화가 저절로 다시 시도합니다.
- 두지 않는다: 옵션이 하나 줄어 단순해집니다. 대신 그런 파일을 다시 처리하려면 운영자가 파일을 다시 저장해 수정 시각을 바꾸거나, 지식베이스 전체를 재색인(모든 문서의 임베딩을 다시 계산)해야 합니다. 문서 하나씩 다시 시도시키는 기능은 뒤의 관리자 페이지(admin) 기능에서 만들 예정입니다.

> 사용자: 옵션을 둔다 (Recommended)

**질문 3 (공유 폴더).** 서버를 띄운 뒤에 서버 기계에 새로 붙인 공유 폴더(NAS 등)를 컨테이너가 보게 하는 방법을 어떻게 할까요? 재 보니 기본 설정에서는 나중에 붙인 폴더가 컨테이너에 보이지 않았고, 서버와 작업자를 다시 띄우면(docker compose restart server worker) 보였습니다.

- 설치 안내에 '다시 띄우기'를 적는다 (Recommended): compose 파일은 그대로 둡니다. 설치 안내에 '공유 폴더는 서버를 띄우기 전에 붙이고, 나중에 붙였거나 떼었다 다시 붙였으면 서버와 작업자를 다시 띄운다'를 적습니다. 운영자가 명령을 한 번 더 쳐야 하지만, 폴더가 항상 읽기 전용으로 지켜집니다.
- 자동으로 보이게 한다 (rslave 설정): compose 파일에 전달 설정(rslave)을 넣어, 나중에 붙인 폴더가 다시 띄우지 않아도 보이게 합니다. 대신 재 본 결과 두 가지 문제가 있었습니다. 서버 기계의 설정이 맞지 않으면(루트가 shared가 아니면) 컨테이너가 아예 뜨지 않았고, 나중에 전달된 폴더는 읽기 전용이 풀려 컨테이너에서 쓰기가 됐습니다.
- .env에서 고르게 한다: 기본은 첫째 안처럼 두고, 운영자가 .env에 한 줄을 적으면 둘째 안처럼 동작하게 합니다. 고를 수 있지만 설정 변수 하나와 그 안내(둘째 안의 두 가지 문제 설명)가 늘어납니다.

> 사용자: 설치 안내에 '다시 띄우기'를 적는다 (Recommended)

셋째 질문의 글에는 고쳐 읽을 곳이 하나 있다. "서버와 작업자를 다시 띄우면(docker compose restart server worker) 보였습니다"라고 적었으나 질문을 올린 때에 프로브가 잰 명령은 `docker restart`였다. compose 명령은 셀프 리뷰 뒤에 프로브의 9단계로 쟀고 결과가 같았다. 그래서 사용자가 고른 선택지의 근거는 그대로 선다.

### 명세 축 보고

대상: `.scratch/source-sync/spec.md`와 ADR 0013·0021의 새 이력, 기능 계획 다섯의 새 문단. 파일은 고치지 않았다. 줄 번호는 명세(spec.md)의 줄이다.

요약: Critical 하나(D1), Major 여섯(C1, C2, D2, D4, D6과 C1·C2의 결과인 D3·D5), 나머지는 Minor와 Nit이다. 범위 밖 동작은 찾지 못했다.

- **C4 [Minor]** 453줄 "ADR 본문을 바꾼 곳은 둘 … ADR 0012와 ADR 0022의 본문은 … 글자 그대로 맞아": ADR 0012 10줄 "같으면 받기를 건너뛰고"는 174줄("모두 다시 읽기")에서 참이 아닌데 그 ADR에 위임 문장도 포인터도 없다. 94줄 "새 포트는 넷이다"도 ADR 0007의 포트 열을 넓히는데 이력이 없다(앞선 명세들은 포트를 더할 때마다, 세 번 이력을 달았다).

#### (d) 전이의 교차와 실패 뒤에 남는 상태

**D1 [Critical: 데이터 유실. 창은 좁다] 원천을 되살리는 요청부터 그 작업이 끝나기까지 × 정리 작업 첫째 단계.**
되살리는 요청은 지움 표시를 바로 걷고, 문서는 작업이 50건씩 되살린다(1만 건에 760초를 쟀다). 보관 기간이 끝나기 직전에 되살렸는데 작업이 느리거나 실패해 새벽 3시를 넘기면, 아직 지운 시각과 "원천과 함께 지워짐" 표시가 남은 문서는 원천의 표시가 걷혀 "지운 원천의 문서"가 아니므로 첫째 단계가 기간 지난 문서로 완전히 지운다. 실패한 되살리기를 다시 잇는 다섯째 단계는 같은 정리 작업에서 첫째 단계 뒤에 돈다. 밀어 넣는 원천은 원본과 조각을 잃고 되살릴 길이 없다(첫째 단계가 그 표시가 남은 문서를 건너뛰면 막힌다).

**D2 [Major] 원천 삭제 작업의 실패 × 되살리는 요청(그 사이에 돈 색인 작업과 재색인).**
지우는 요청과 되살리는 요청을 막는 가드(265줄)는 원천 삭제 작업이 대기 중이거나 실행 중일 때만 선다. 삭제 작업이 재시도를 다 쓰고 실패한 뒤, 다음 정리 작업이 다시 잇기 전에 되살리면, 표시가 선 동안 "아무것도 쓰지 않고 성공으로 끝난" 색인 작업(258줄)의 문서 가운데 삭제 작업이 옮기지 못한 것은 살아 있고 색인 상태가 `pending`인데 색인 작업이 없다. 되살리기 작업은 표시가 있는 문서만 보고, 동기화의 재투입(231줄)은 실패 코드만 본다. 그때 건설 중인 판이 있으면(표시가 선 동안 시작한 재색인이 그 문서를 살아 있는 문서로 세는지도 적히지 않았다) 그 `pending` 하나가 판 전환을 영영 막는다.

**D3 [Major] 정리 작업 둘째 단계 × 끝난 색인 작업 행(C1의 결과).**
보관 기간이 지난 원천의 문서 행을 지우는 순간 그 문서를 가리키는 색인 작업 행 때문에 실패한다. 정리 작업은 날마다 같은 자리에서 실패하므로 그 원천은 지워지지 않고 이름도 풀리지 않는다. 둘째 뒤에 오는 셋째(주인 없는 원본), 넷째(동기화 기록), 다섯째(멈춘 삭제와 되살리기 잇기)도 돌지 못한다. 416줄의 장면이 구현 때 잡겠지만, 그때 골라야 할 답(작업 행을 지운다, 외래 키를 바꾼다)이 명세에 없다.

**D4 [Major] 원천 되살리기 작업 × 수집 API의 삭제 요청, 동기화의 삭제 반영.**
되살리기 작업이 아직 닿지 않은 문서는 지워진 문서라, 그 키를 지우라는 수집 API 요청은 이미 지운 문서로 보고 204로 지나간다. 조금 뒤 되살리기 작업이 그 문서를 검색에 되돌린다. 밀어 넣는 원천에는 이것을 바로잡을 동기화가 없어 클라이언트가 지운 문서가 계속 검색된다(원칙 VI). 가져오는 원천도 같은 꼴이다. 되살리기 도중에 돈 동기화의 삭제 반영은 "지워지지 않은 문서"만 보므로, 파일이 없어진 문서가 다음 동기화까지 검색에 남는다.

**D5 [Major] 동기화의 갱신(색인이 돌기 전) × 원천 삭제 → 되살리기(C2의 결과).**
동기화가 문서 내용을 바꾸고 색인 작업이 돌기 전에 원천을 지우면, 삭제 작업이 옛 내용의 조각을 보관함으로 옮기고 대기 중인 색인 작업을 지운다. 되살리기가 262줄에 적힌 단계대로(해시를 보지 않고) 돌면 옛 내용의 조각이 `indexed`로 돌아온다. 다음 동기화는 변경 확인값이 같아 그 문서를 읽지 않고 색인 상태도 실패가 아니라서, 옛 내용이 계속 검색된다. core의 조건을 글자 그대로 옮기면 생기지 않는다.

**D6 [Major] 정리 작업 다섯째 단계 × 되살리는 요청.**
다섯째 단계가 "표시가 선 원천에 지워지지 않은 문서가 남았다"를 읽은 직후에 되살리는 요청이 표시를 걷으면, 표시가 없는 원천에 원천 삭제 작업이 들어간다. 원천 삭제 작업과 되살리기 작업이 묶음마다 원천 행을 잠그고 표시를 다시 본다는 문장은 없다(정리 둘째 단계에만 있다, 282줄). 그대로 지으면 되살린 원천의 살아 있는 문서를 삭제 작업이 다시 지우고, 두 작업이 같은 원천을 서로 반대로 옮긴다.

**D7 [Minor] 색인 작업의 `source_changed` × 다음 동기화의 "내용 같음"(C3의 결과).**
색인 작업이 읽는 순간에만 파일이 달랐다가(복사 도중, 잠깐 없어짐) 같은 내용으로 돌아오면, 다음 동기화는 확인값만 다시 적고 색인 상태는 `failed`와 `source_changed`로 남는다. 운영자가 "모두 다시 읽기"나 재색인을 돌리기 전에는 저절로 풀리지 않는다. 길은 있으므로 ADR 0022의 조건은 지켜진다.

**D8 [Minor] 원천 되살리기 작업의 실패 × 지우는 요청.**
D2와 같은 가드의 빈틈이다. 되살리기 작업이 실패로 끝난 뒤의 지우는 요청은 받아들여져, 265줄이 막겠다고 한 "문서마다 지운 시각이 갈리는" 상태가 생긴다(앞서 지워진 문서는 옛 시각, 새로 옮기는 문서는 새 시각). 그 뒤 다시 되살리면 옛 시각의 문서가 D1의 길로 먼저 지워질 수 있다.

**D9 [Minor] 기한을 잃은 동기화 시도 × 새 시도.**
끊긴 공유 폴더에서 멈춘 시도는 기한이 지나 버려지고 다른 작업자가 처음부터 다시 돈다(181줄). 멈췄던 스레드가 뒤늦게 돌아왔을 때 문서마다의 작업 단위가 자기 작업 행(작업자, 시도 횟수)을 다시 본다는 문장이 원천 단위 작업에는 없다. 없으면 옛 시도가 옛 후보 목록으로 삭제 반영을 해 새 시도가 넣은 문서를 지우고, 동기화 기록의 개수도 두 시도가 섞어 쓴다. 다음 동기화가 되살리므로 끝내 맞춰지기는 한다.

**D10 [Minor] 건너뜀을 쓰는 색인 작업 × 건설 중인 판의 마지막 `pending`.**
건너뜀 문서의 색인 상태를 `indexed`로 쓴 색인 작업(241줄)이 전환 검사를 한다는 문장이 없다. 재색인의 마지막 문서가 건너뜀이면 그 뒤에 끝날 문서가 없어 판 전환이 일어나지 않는다. 판정하는 장면도 없다(A3).

**D11 [Nit] 지움 표시가 선 원천 × 문서 수를 세는 자리.**
252줄은 `search`, `get_document`, 관리 API의 문서 조회만 든다. `list_knowledge_bases`의 문서 수(`count_live_documents`)와 문서의 조각 수가 표시가 선 원천을 빼는지는 적히지 않아, 삭제 작업이 끝날 때까지 수가 검색과 어긋날 수 있다.

**밟아 보고 문제없다고 본 교차**
- 동기화 도중의 삭제 → 되살리기: 작업 단위마다 표시를 다시 보고(178줄) core의 되살림으로 맞춰진다.
- 일정 확인 × 지우는 요청, "지금 동기화" × 일정 확인: 부분 유일 색인과 원천 행 잠금으로 하나만 들어간다.
- 정리 둘째 단계 도중의 작업자 죽음: `source_retention_expired`(266줄)와 묶음마다의 재확인으로 이어진다.
- 정리 첫째 단계 × 문서 되살리기: 문서 행 잠금 뒤 다시 본다(280줄).
- 방금 쓴 원본 × 정리 셋째 단계: 24시간 유예.
- 재색인과 "모두 다시 읽기"가 같은 문서에 작업을 넣는 경우: core의 대기 작업 유일 규칙으로 하나다.

**관찰(지적 아님)**: 수집과 동기화가 원천 행을 공유 잠금으로 쥔 순간의 일정 확인은 그 원천을 건너뛴다(`SKIP LOCKED`). 그 주기만 늦어진다. 긴 동기화 둘이 기본 동시 처리 2를 모두 차지하면 다른 원천의 동기화와 색인이 기다린다.

#### 맞게 확인한 것

- 프로브 출력의 수 전부(cron C·D·E, schedule-once A·B·D1~D3·E1·E2·F, source-delete의 시간 열여섯, mount 0·2~8)가 명세의 수와 같다.
- ADR 0021의 "명세가 재거나 정하는 것" 여섯, ADR 0022가 넘긴 일곱과 조건 다섯에 답이 있고, 조건 인용 셋은 글자 그대로다.
- 기능 계획의 PR 직전 리뷰 다섯, PR 봇 하나, core와 release-image가 넘긴 것에 답이 있다. 셀프 리뷰 물음은 A1·A2 둘만 빠졌다.
- 수락 넷 가운데 셋은 장면으로 판정된다(403~405, 410, 411·425·427줄). 나머지 하나가 A4다.
- Out of Scope 넷이 받는 기능 계획(admin, db-source, diag-bundle, backup-upgrade)에 적혔고, 네 계획의 `**Blocked by:**`에 source-sync가 있다.
- 사용자 선택 셋이 일지의 선택지 원문과 같다.
- ADR 0013·0021의 포인터와 이력 제목이 글자 그대로 맞는다.
- 코드 주장: 검색의 후보 질의가 조각 표만 읽는다, 꺼내는 질의가 프로브와 같다, 원본을 먼저 쓴다, 원본 경로를 수집마다 새로 짓는다, `kind`가 `push`뿐이다, 요청 ID 칸을 비울 수 없다, 제목 규칙, 설정 기본값, 작업 코드와 Problem Details 코드의 개수.
- 설치 안내: 절 번호(3, 6, 11, 14), compose가 정하는 값 셋, 3-3의 "Docker가 root의 폴더로 만든다"(377줄의 근거).
- release-image 명세 149줄에 "계약마다 한 줄씩" 목록이 있다(135줄의 근거). ADR 0020 15줄이 볼륨을 바꾸는 변경을 못박은 셋 밖으로 둔다(377줄과 맞는다).
- ADR 0009(정리와 재색인도 같은 대기열)와 맞는다.
- 원칙 IV(MCP 도구를 더하지 않는다)와 원칙 V(예외 글, 키, 폴더 이름을 응답·기록·로그에 싣지 않는다)를 어긴 자리는 찾지 못했다. 설정에 든 비밀이 원천 보기에 보이는 한계는 450줄이 스스로 밝힌다.

#### 대조하지 못한 것

- ADR 0008과 ADR 0015의 원문.
- `cron-expr/probe.py`, `mount-propagation`의 `probe.sh`와 `inner.sh`가 출력의 항목을 실제로 재는지(출력만 봤다).
- `worker/service.py`의 "꺼낼 작업이 없을 때만 주기를 기다린다"(209줄), 수집 API가 바이트 머리로 형식을 가리는 코드(159줄), `ingest` 명령의 시험이 링크를 실제로 만드는지(423줄).
- `.env.example`의 지금 내용, 문서 응답에 원천 이름이 실리는지.
- 원천 행 공유 잠금을 앞에 둔 잠금 순서가 멈춤 없이 도는지(명세도 재지 않았고 428줄의 시험에 맡겼다).
- 이미 지운 문서를 또 지우는 요청이 204라는 것(D4의 전제)은 `app/delete_document.py`를 읽은 기억에 기대며 이번에 다시 열어 보지 않았다.
- 일지의 "준비" 절(대조할 원천이 없다).

### 판정

두 보고의 지적을 근거(명세의 줄, 코드, 프로브 출력)와 대 보고 판정했다. 고친 것은 모두 커밋 전에 고쳤고, 남긴 것에는 이유를 적는다. ADR에 닿는 고침은 "승인"에서 사용자에게 보였다.

**명세 축**

- D1 [Critical] 고쳤다. 지적대로다. 되살리는 요청이 지움 표시를 걷은 뒤에도 원천과 함께 지워졌다는 표시가 남은 문서는 지운 시각이 그대로여서, 정리 작업의 첫째 단계가 기간이 지난 문서로 보고 완전히 지울 수 있었다. 첫째 단계가 그 표시가 없는 문서만 지우게 했고, 표시가 있는 문서는 원천을 따르게 했다(지운 원천의 것은 둘째 단계가 원천과 함께 지우고, 되살린 원천의 것은 원천 되살리기 작업이 되살린다). C7(지운 원천에 든 따로 지운 문서의 보관 기간이 두 줄에서 어긋난 것)도 이 고침으로 풀린다. 그런 문서는 표시가 없으므로 첫째 단계가 그 문서를 지운 날부터 세어 지운다.
- C1·D3 [Major] 고쳤다. 작업 표가 문서를 가리키는 외래 키에는 지울 때의 동작이 없다(`src/rag_engine/adapters/postgres/tables.py` 215행을 읽었다. 문서를 가리키는 외래 키는 파싱 결과, 색인 상태, 조각과 보관 조각, 작업 표에 있다). 정리 작업의 둘째 단계가 문서 행을 지우기 전에 그 문서를 가리키는 작업 행을 끝난 것까지 지우게 했고, Out of Scope의 "끝난 작업 행을 지우는 일"을 그에 맞췄다.
- C2·D5 [Major] 고쳤다. 원천 되살리기와 문서 되살리기에 core 명세 227행의 조건(대상 판의 조각이면서 만든 내용 해시가 문서의 내용 해시와 같은 것만 되돌린다)과 되돌릴 조각이 없는 경우 둘(그사이 판이 바뀌었다, 지우기 전에 바뀐 내용이 아직 색인되지 않았다)을 옮겨 적었다.
- D2 [Major] 고쳤다. 원천 되살리기 작업이 표시가 있는 문서를 되살린 뒤, 그 원천의 지워지지 않은 문서 가운데 색인이 멈춘 문서(대상 판 가운데 색인 상태가 `indexed`도 `failed`도 아닌 판이 있는데 색인 작업이 대기 중도 실행 중도 아닌 문서)에 색인 작업을 넣게 했다. 처음에는 `pending`인 문서만 잡으려 했으나, core 명세 143행이 재색인을 시작한 뒤에 든 문서는 건설 중인 판에 색인 상태 행이 없다고 적어 상태 행이 없는 판도 조건에 넣었다. 그 단계에서 작업이 실패해도 다시 이어지게, 정리 작업의 다섯째 단계가 다시 넣는 조건에 "그 원천의 마지막 원천 되살리기 작업이 실패로 끝났다"를 더했다. 지움 표시가 선 동안 시작한 재색인이 아직 옮기지 않은 문서를 어떻게 세는지도 적었다(재색인의 시작은 문서 행으로 센다. `src/rag_engine/domain/ports.py`의 `list_live_document_ids` 독스트링을 읽었다).
- D4 [Major] 고쳤다. 전제(이미 지운 문서를 지우는 요청은 아무것도 바꾸지 않는다)는 `src/rag_engine/app/delete_document.py` 36~37행을 다시 열어 확인했다. 수집 API의 삭제 요청과 동기화의 삭제 반영이 지워져 있는데 원천과 함께 지워졌다는 표시가 남은 문서를 만나면, 그 표시를 지우고 지운 시각을 그 순간으로 고치게 했다. 그 문서는 따로 지운 문서가 되어 원천 되살리기 작업이 되살리지 않는다.
- D6 [Major] 고쳤다. 원천 삭제 작업과 원천 되살리기 작업이 묶음마다 원천 행을 잡고 지움 표시를 다시 보게 했다(삭제 작업은 표시가 서 있을 때만, 되살리기 작업은 표시가 없을 때만 일한다). 정리 작업의 다섯째 단계는 원천마다 원천 행을 잠근 작업 단위에서 조건을 보고 넣게 했다.
- D8 [Minor] 고쳤다. D1의 고침(표시가 있는 문서의 보관 기간은 원천의 지운 시각으로 센다)으로 해가 없어진다. 지우는 요청과 되살리는 요청을 막는 까닭을 적은 문장을 그에 맞췄다.
- D7·C3 [Minor] 고쳤다. 동기화가 색인 작업을 다시 넣는 대상을 "내용이 바뀌지 않은 문서"(확인값이 같아 읽지 않은 것과 읽어 보니 같은 것)로 넓히고 다시 넣는 코드에 `source_changed`를 더했다.
- D9 [Minor] 고쳤다. 원천 단위 작업과 정리 작업이 쓰는 작업 단위도 core 명세의 작업 행 조건(작업자와 시도 횟수가 꺼낼 때의 값 그대로인지 보고 아니면 그 시도를 버린다)을 따르게 했다.
- D10·A3 [Minor] 고쳤다. 건너뜀을 쓴 색인 작업도 전환 검사를 한다고 적었고, Testing Decisions에 장면 둘(건너뜀 문서가 마지막에 끝나도 판이 전환된다, 파서가 바뀐 뒤의 재색인이 건너뜀 문서를 다시 본다)을 더했다.
- D11 [Nit] 고쳤다. 문서 수를 세는 자리는 지움 표시를 보지 않는다는 것을 치르는 값으로 적었다(`count_live_documents`를 부르는 자리 둘을 Grep으로 봤다).
- A1 [Minor] 고쳤다(표준 축 Major 4와 같은 지적이다). `ingest <경로>`로 `default`에 넣은 폴더를 서버 경로 원천으로 옮길 때의 중복에 답을 적었다. 서버는 원천이 다른 같은 내용을 합치지 않고, 옮기는 절차를 설치 안내가 적는다.
- A2 [Minor] 고쳤다. 원천의 설정이 데이터베이스에 그대로 들어 백업에 실린다는 것을 Out of Scope의 backup-upgrade 항목과 그 기능 계획에 더했다.
- A4 [Minor] 고쳤다. 수집 API 장면의 기대에 "넣은 문서가 검색에 나온다"를 더했다.
- C4 [Minor] 고쳤다. ADR 0012 본문의 "같으면 받기를 건너뛰고"가 "모두 다시 읽기"에서 참이 아니고, ADR 0007 본문의 포트 열에 새 포트가 든다. 두 ADR에 2026-11-21 이력과 포인터를 더했다. 그러려고 명세가 새 포트의 이름(`ConnectorRegistry`, `ScheduleCalculator`, `SyncRecordStore`)을 정했다. 앞선 명세 셋이 포트를 더할 때마다 이름을 정해 ADR 0007의 이력에 적은 선례를 따랐다.
- C5 [Minor] 고쳤다. 프로브가 문서 행을 `FOR UPDATE`로 한 번 잠가 본 것이고 제품은 `FOR NO KEY UPDATE`로 잠근다(`src/rag_engine/adapters/postgres/document_store.py` 238행을 읽었다). 명세와 ADR 0013 이력에 잰 것과 어림을 갈라 적었다.
- C6 [Minor] 고쳤다. 느린 까닭이 벡터 색인이라는 것은 어림으로 적었고(GIN 색인과 가르는 대조를 하지 않았다), 78.1초는 조각을 채운 표에 지은 시간이라고 고쳤다(`source-delete/probe.py` 157~174행). 일정 확인의 모양은 프로브에 A2를 더해 다시 쟀다.
- C8 [Nit] 고쳤다. `'0 0 31 2 *'`가 든 절을 E로, uid 10001의 출처를 `compose.yaml`의 머리 주석으로, 커넥터 인터페이스 버전의 값을 파서와 같은 꼴(`1.0.0`)로 고쳤다.

**반영하다 더 정한 것**

판정을 명세에 옮기다가 셋을 더 정했다. 리뷰가 낸 지적이 아니라 이 세션이 고침의 귀결을 따라가다 본 것이다.

- 동기화의 빈 목록 판정이 되살린 원천에서 원천 되살리기 작업을 기다리는 문서도 있는 문서로 세게 했다. D4의 고침으로 삭제 반영이 그런 문서의 표시를 지우게 됐다. 그래서 폴더가 붙지 않은 채 되살린 직후에 동기화가 돌면, 지워지지 않은 문서가 하나도 없어 빈 목록 판정을 지나고 그 문서를 모두 따로 지운 문서로 만들 수 있었다.

## PR 직전 리뷰

셀프 리뷰의 반영을 마친 작업 트리(커밋 전)를 `coderabbit-review` 서브에이전트로 한 번 더 봤다. ADR 이력의 승인은 이 리뷰를 반영한 뒤에 받는다. 앞선 설계 세션에서 승인을 먼저 받았다가 이 리뷰가 낸 지적으로 승인받은 글이 병합 전에 바뀌었기 때문이다(대기열 `adr-approval-before-pre-pr-review`). CLI가 도는 리뷰에는 밀 주장을 넘기는 길이 없어(`code-review` 6단계 1), 위 "반영으로 새로 쓴 사실 문장"의 목록은 브리프에 싣지 못했다. 브리프에는 대상 파일, 프로브가 재지 않는 것을 쟀다고 적은 자리와 사실 문장이 코드나 프로브 출력과 어긋나는 자리와 상태 전이의 논리 결함을 문서 변경이어도 유효한 지적으로 다뤄 달라는 것을 적었다. 보고는 받은 그대로 옮기고 머리 줄의 단계만 낮췄다. 보고가 가리키는 줄 번호는 리뷰 때의 것이다.

### 보고

### 판정과 반영 (PR 직전 리뷰)

지적마다 명세의 줄과 코드를 열어 보고 판정했다. Major 셋은 모두 고쳤다.

- **Major 1(확인과 열기 사이의 경쟁) 고쳤다.** 지적대로다. 명세는 토막마다 링크인지 본다고만 적었고 확인과 열기를 묶지 않았다. ADR 0021이 링크를 따라가지 않기로 한 까닭(컨테이너 안의 다른 파일을 문서로 색인해 검색으로 읽어 내는 길)이 이 틈으로 다시 열린다. "서버 경로 커넥터와 원천 폴더" 절에 항목 하나를 더했다. 부모 폴더를 연 자리에서 토막마다 링크를 따르지 않는 열기로 내려가고, 마지막에 연 파일로 보통 파일인지 본 뒤 거기서 읽는다. 목록도 같다. 이 열기가 어디에 있는지는 손으로 봤다. `python -c "import os, sys; print(sys.version.split()[0], sys.platform, hasattr(os,'O_NOFOLLOW'), os.open in os.supports_dir_fd, os.scandir in os.supports_fd)"`를 개발 PC에 지어져 있던 서버 이미지(`docker run --rm --entrypoint python rag-engine-test/rag-engine-server:0.1.0-rc.1 -c …`)에서 돌리니 `3.12.16 linux True True True`였고, 개발 PC에서 `uv run python -c …`로 돌리니 `3.12.10 win32 False False False`였다. 그 이미지를 어느 커밋에서 지었는지는 보지 않았다. 그래서 그 열기가 없는 운영체제에서는 확인한 뒤 여는 길로 돌고 틈을 닫지 못한다고 적었고, 파서의 메모리 상한이 같은 꼴이라는 선례를 들었다(`tests/adapters/test_parse_runner.py` 112~119행을 읽었다. 한도보다 많이 잡는 파서가 리눅스에서는 `parse_memory_exceeded`이고 윈도에서는 걸리지 않는다고 시험이 운영체제마다 기대를 적는다). Testing Decisions의 커넥터 시험에 링크로 바꿔치는 경쟁 하나를 더했다. ADR 0021의 본문은 거짓이 되지 않는다(링크를 따라가지 않는다는 결정을 여는 순간까지 지키게 한 것이다).
- **Major 2(겹침 확인의 동시 요청) 고쳤다.** 지적대로다. 폴더의 겹침은 실제 폴더를 봐야 알 수 있어 유일 색인으로 받칠 수 없고, 명세에는 요청끼리 차례를 세우는 장치가 없었다. 같은 절에 항목 하나를 더했다. 겹침 확인과 저장을 작업 단위 하나에서 하고, 폴더를 정하는 요청 셋(만들기, 폴더 고치기, 되살리기)이 그 작업 단위에서 맨 먼저 트랜잭션 수준 자문 잠금 하나를 잡는다. 제품 코드에 자문 잠금을 쓰는 곳은 아직 없다(`src`를 `advisory`로 Grep해 0건). 자문 잠금이 이 자리에서 그렇게 도는지는 재지 않은 어림이라고 명세에 적었고, Testing Decisions의 표에 동시 요청 장면을 더해 시험이 판정하게 했다.
- **Major 3(읽다가 상한을 넘은 파일) 고쳤다.** 지적대로다. 목록에서 크기로 걸린 파일은 후보에서 빠져 그 문서가 삭제 반영되는데, 읽다가 `too_large`가 난 파일은 "같은 사유로 센다"고만 적혀 있어 대조의 "읽지 못하면 문서는 그대로 둔다"와 겹쳐 읽혔다. 목록이 크기를 내지 않는 커넥터에서는 상한을 넘게 된 파일의 옛 내용이 동기화를 몇 번 돌려도 검색에 남는다. 수집 정책 절에 읽다가 `too_large`가 난 파일을 목록에서 걸린 파일과 똑같이 다룬다고(같은 사유로 세고 후보에서 뺀다) 적었고, 대조와 삭제 반영의 문장, 색인 작업이 `source_changed`로 끝난 뒤의 다음 동기화 문장을 그에 맞췄다. Testing Decisions의 표에 장면 하나를 더했다.
- **Minor(문서 되살리기의 보관 기간) 까닭을 적고 코드는 더하지 않았다.** 원천 되살리기가 기간을 보는 까닭은 정리 작업이 원천 하나를 여러 묶음에 걸쳐 지워서다. 문서 하나는 정리 작업이 문서 행을 잠근 작업 단위 하나에서 지우므로(명세 "정리 작업"의 첫째 단계) 지우는 도중에 끼어들 틈이 없다. 기간이 지났어도 정리 작업이 아직 지우지 않은 문서를 되살려 주는 쪽이 운영자에게 손해가 없다고 보았다. 다만 그 판정이 서려면 되살리는 요청도 문서 행을 잠근 뒤에 조건을 봐야 하므로 그 요구를 명세에 더했고, 원천과 다르게 둔 까닭과 둘이 겹칠 때의 결과(먼저 잠근 쪽대로)를 같은 항목에 적었다.
- **보류 1(빈 목록 판정이 수집 정책을 적용하기 전의 건수를 본다) 사용자에게 물었다.** 리뷰어가 든 장면(공유 폴더가 떨어졌는데 그 자리에 문서가 아닌 파일만 있다)은 붙는 자리에 표시 파일을 두는 운영 관행에서 실제로 난다. 막으면 운영자가 정책으로 모든 파일을 뺀 경우에도 옵션을 한 번 켜야 한다. 장단이 갈리는 설계 판단이고 ADR 0022 "목록이 비면 지우지 않는다"의 범위에 닿아 "승인"에서 함께 물었다.
- **보류 2(프로브의 연결 실패와 짧은 회차) 스크립트를 열어 보고 보강했다.** A~C의 연결은 예외를 모아 줄마다 찍고(출력은 모두 `오류 없음`), 연결 하나가 실패하면 나머지가 barrier에서 기다려 프로브가 멈춘다. 틀린 수를 조용히 내는 길은 아니어서 그대로 두었다. D1의 연결은 예외로 끝나면 답을 남기지 못해 그 회차가 분포에 섞일 수 있었다. 회차마다 답한 연결의 수를 세어 "연결 8개가 모두 답하지 않은 회차"를 D1 줄에 찍게 고치고 다시 돌렸다. 0이었다. stderr도 같은 파일에 받았고 예외 출력이 없었다.
- **오탐(ADR 0013 8행의 vacuum 설명) 고치지 않았다.** 리뷰어의 판정대로다. 그 문장은 이 변경 전부터 본문에 있었고, ADR 규칙(`.claude/rules/adr.md`)은 포인터를 달 때 본문의 다른 글자를 고치지 않게 한다.

**프로브 출력을 바꿨다.** `schedule-once/probe.py`는 셀프 리뷰 뒤의 검증에서 린트(`except`가 붙은 `try` 몸통의 문장 일곱 > 다섯)에 걸려 `worker`의 `try` 몸통을 `check_schedule` 함수로 뺐고, 위 보류 2로 D1에 한 줄을 더했다. 고칠 때마다 임시 컨테이너(스크립트 머리 설명의 `docker run`)에 다시 돌렸다. 두 번 모두 종료 코드 0이었고, 잠금을 쓰는 A·A2·C는 넣은 작업 1000건과 더 들어간 작업 0건, D와 E는 글자 그대로 같았다. 시간과 대조군 B의 건수는 돌릴 때마다 달랐다(B는 경쟁이 실제로 겹친 만큼 더 들어가는 수라 그렇다). 커밋하는 `probe_out.txt`는 마지막 실행의 출력으로 바꿨고, 명세와 이 일지의 수를 그 값으로 맞췄다. 대조군은 4028건과 4728건(앞 실행은 4059건과 4598건), 꺼내는 질의의 가운데값은 78.7ms, 192.8ms, 1.6ms(앞 실행은 101.2ms, 248.5ms, 2.0ms)다. 옛 수가 남지 않았는지는 명세, 프로브 폴더, 이 일지를 Grep으로 봤다.

**이 반영으로 새로 쓴 사실 문장.** PR 봇에는 주장을 넘기는 길이 없어 원문만 적어 둔다.

**질문 2 (빈 목록 판정).** 동기화의 안전장치를 어디까지 둘지 여쭙니다. 지금 명세는 '폴더에 파일이 하나도 없는데 색인에는 문서가 있으면, 지우지 않고 실패로 기록한다'까지만 막습니다. 그런데 공유 폴더(NAS)가 붙지 않은 자리에 문서가 아닌 파일만 있으면(예: 붙지 않았음을 알리려고 둔 표시 파일, 숨김 파일) 동기화는 '폴더는 읽혔고 문서가 될 파일은 0건'으로 보고 그 원천의 문서를 모두 검색에서 뺍니다. 뺀 문서는 보관 기간(기본 30일) 동안 남아서 폴더가 다시 붙은 뒤의 동기화가 되살리지만, 그때까지는 검색에 나오지 않습니다. 이 경우도 막을까요?

- 이 경우도 막는다 (Recommended): 문서가 될 파일이 하나도 없는데 색인에 문서가 있으면, 지우지 않고 그 동기화를 실패로 기록합니다. 규칙이 '동기화는 옵션 없이는 원천의 문서를 통째로 비우지 않는다' 하나로 단순해집니다. 치르는 값은 둘입니다. 제외 패턴이나 크기 상한으로 일부러 모든 파일을 뺀 운영자도 '빈 목록도 반영'을 한 번 켜서 돌려야 합니다. 그리고 ADR 0022에 이력 한 건이 더 붙습니다(초안은 오른쪽 미리보기).
  - 미리보기: "ADR 0022에 더할 이력 초안 / ### 2026-11-21 문서가 될 파일이 하나도 없을 때도 지우지 않는다 / 명세가 정했고 사용자가 골랐다. 본문은 원천 폴더가 없거나 목록이 0건일 때 지우지 않는다고 적는다. 목록에 파일은 있는데 수집 정책(제외 패턴, 지원하지 않는 형식, 크기 상한)에 모두 걸려 문서가 될 파일이 하나도 없을 때도 같게 다룬다. 색인에 그 원천의 문서가 있으면 삭제를 반영하지 않고 그 동기화를 실패로 기록하며, 운영자가 정말로 모두 빼려는 것이면 "빈 목록도 반영"을 켜서 돌린다. / 까닭: 공유 폴더가 붙지 않은 자리에 문서가 아닌 파일만 있으면(붙지 않았음을 알리려고 둔 표시 파일, 숨김 파일) 본문의 규칙만으로는 그 원천의 문서가 모두 검색에서 빠진다(PR 직전 리뷰가 냈다). / 그대로인 것: 일부만 줄어든 경우는 목록대로 지운다. 지우는 양에 비율 한도를 두지 않는다는 결정도 그대로다. / 치르는 값: 정책으로 일부러 모든 파일을 뺀 운영자도 그 옵션을 한 번 켜야 한다."(빗금은 미리보기의 줄 바꿈이다)
- 지금대로 둔다: 파일이 하나도 없을 때만 막습니다. 위 장면에서는 그 원천의 문서가 검색에서 빠졌다가 폴더가 다시 붙은 뒤의 동기화에서 돌아옵니다. 이 위험과 피하는 법(공유 폴더를 붙이는 자리에는 다른 파일을 두지 않는다)을 설치 안내에 적습니다. ADR은 그대로이고 명세에는 이 위험을 알고 남겼다는 문장만 더합니다.
  - 미리보기: "명세와 설치 안내에 더할 문장(초안) / 파일은 있는데 모두 수집 정책에 걸린 경우는 목록대로 반영한다. 그래서 공유 폴더가 붙지 않은 자리에 문서가 아닌 파일만 있으면 그 원천의 문서가 모두 검색에서 빠진다. 뺀 문서는 보관 기간 동안 남아 있고, 폴더가 다시 붙은 뒤의 동기화가 되살린다. / 설치 안내: 공유 폴더를 붙이는 자리(sources/ 아래의 폴더)에는 표시 파일을 비롯해 다른 파일을 두지 않는다."

> 사용자: 이 경우도 막는다 (Recommended)

둘째 질문의 "규칙이 … 하나로 단순해집니다"는 줄여 적은 말이다. 파일의 이름을 모두 바꾼 폴더처럼 후보가 있는 동기화는 옛 문서를 모두 지울 수 있고, 막는 것은 후보가 0건인 경우다. 명세와 ADR 이력은 그렇게 적었다.

### 답으로 고친 것

- **명세의 빈 목록 판정.** 수집 정책을 적용하기 전의 목록이 아니라 적용한 뒤의 후보로 가르게 고치고 표시를 `[사용자 선택]`으로 바꿨다. 후보가 0건이고 그 원천에 문서가 있으면 지우지 않고 실패로 끝낸다. 고르지 않은 안과 치르는 값을 같은 항목에 적었다.
- **실패 사유를 둘로 갈랐다(이 세션이 정했다).** 목록이 0건이면 지금처럼 `source_unreadable`이고, 파일은 있는데 모두 수집 정책에 걸렸으면 새 코드 `nothing_accepted`다. 폴더가 읽히는데 "읽을 수 없음"으로 알리면 운영자가 권한이나 연결을 살피게 된다. 오류 코드 절의 "여섯을 더한다"가 "일곱을 더한다"가 됐고, 재시도 없이 한 번에 끝나는 사유의 목록에도 넣었다. "셀프 리뷰"의 판정이 적은 작업 코드의 수(둘과 여섯)는 그때의 수다.
- **판정을 두 자리에서 한다(이 세션이 정했다).** 후보를 만든 직후와 삭제 반영 직전이다. 앞서 PR 직전 리뷰로 읽다가 `too_large`가 난 파일을 후보에서 빼게 했으므로, 읽은 파일이 모두 상한을 넘으면 첫 판정을 지난 뒤에 후보가 0건이 된다. 뒤의 자리가 없으면 그 길로 안전장치를 지나친다.
- **"빈 목록도 반영"의 범위.** 목록이 0건인 경우에 더해 파일이 모두 수집 정책에 걸린 경우에도 통한다. 폴더가 없거나 읽지 못하면 켜도 실패하는 것은 그대로다.
- **남는 위험을 적었다.** 공유 폴더를 붙이는 자리에 문서 형식의 파일이 놓여 있으면 그 파일이 후보가 되어 나머지 문서가 삭제 반영된다. ADR 0022가 일부만 줄어든 경우는 목록대로 지우기로 했고 비율 한도를 두지 않았으므로 막지 않는다. 단독 compose 절과 설치 안내 항목에 그 자리에 문서 파일을 두지 않는다는 것을 더했다.
- **맞춘 곳.** Solution의 문장, User Stories 19와 20, 수집 정책 절의 삭제 반영 문장, 삭제 반영 항목, Testing Decisions의 표다. 표에서는 "모든 파일이 걸려도 그 동기화는 실패가 아니다"를 문서가 없는 원천의 경우로 좁히고, 장면 둘(문서가 있는 원천에서 모든 파일이 걸린다, 문서가 하나뿐인 원천에서 그 파일이 상한을 넘는다)을 더했다. 이미 있던 장면 둘(제외 패턴을 더한 뒤, 상한을 넘게 된 뒤)은 후보가 하나 남게 고쳤다. 그대로 두면 그 장면의 원천에서 후보가 0건이 되어 새 판정에 걸린다.
- **ADR 0022.** 2026-11-21 "문서가 될 파일이 하나도 없을 때도 지우지 않는다"를 더하고 `## 이력` 절을 새로 만들었으며 본문 "목록이 비면 지우지 않는다"의 첫 문장 뒤에 포인터를 달았다. 미리보기의 초안에 문장 둘을 더했다. 남는 위험(위 항목)과 실패 사유를 둘로 가른다는 문장이다. 더한 문장은 대화에서 사용자에게 원문의 자리와 함께 알렸다.
- **받는 기능 계획은 고치지 않았다.** backup-upgrade와 diag-bundle의 계획이 적은 `source_unreadable`은 폴더가 붙지 않았거나 없는 경우의 코드이고 그대로 참이다(두 계획의 그 문장을 Grep으로 봤다). 옛 표현의 잔존은 명세 폴더를 "정책의 결과", "목록대로 반영", "실패가 아니다"로 Grep해 봤다. 남은 것은 고르지 않은 안을 적은 문장과 문서가 없는 원천의 장면이다.

표시는 `[사용자 선택]`이 하나 늘어 4, `[이력]`이 하나 늘어 5, `[정함]`은 하나가 `[사용자 선택]`으로 바뀌고 하나가 늘어 188 그대로이며 모두 240이다.

**이 반영으로 새로 쓴 사실 문장.**

1. 명세: "한 번 반영하고 나면 그 원천에 문서가 없으므로 그 뒤의 일정은 이 판정에 걸리지 않는다."
2. 명세: "후보가 모두 빠졌다는 것은 읽은 파일이 모두 상한을 넘었다는 뜻이라 그때까지 넣은 문서가 없고, 그 동기화는 `nothing_accepted`로 끝나며 아무것도 지우지 않는다."
3. 명세: "그 자리에 문서 형식의 파일이 놓여 있으면 그 파일이 후보가 되어, 나머지 문서는 목록에 없는 문서로 삭제 반영된다(일부만 줄어든 경우는 목록대로 지운다는 ADR 0022의 결정이다)."
4. ADR 0022 이력: "본문의 규칙만으로는 폴더가 읽히고 목록이 0건이 아니어서 그 원천의 문서가 모두 검색에서 빠진다(PR 직전 리뷰가 냈다)."

## 검증

**손으로 친 것.** 명령은 하나씩 따로 돌렸다.

- 셀프 리뷰를 반영한 뒤: `uv run ruff check .`는 `All checks passed!`, `uv run ruff format --check .`는 `817 files already formatted`, `uv run pyright`는 오류 0건, `uv run lint-imports`는 계약 둘이 지켜지고 깨진 것이 없다고 냈다.
- PR 직전 리뷰를 반영한 뒤: `uv run ruff check .`와 `uv run ruff format --check .`가 같은 글로 끝났고, `uv run python tools/check_adr_pointers.py`와 `uv run python tools/plan_table.py --check`가 출력 없이 끝났다.
- 사용자의 답으로 명세와 ADR 0022를 고친 뒤: `uv run python tools/check_adr_pointers.py`, `uv run ruff format --check .`, `uv run python tools/plan_table.py --check`를 다시 돌렸고 결과가 같았다. 이 사이에 고친 것은 마크다운뿐이다.

타입체크와 import 경계는 `src`, `tests`, `tools`만 보고(`pyproject.toml`의 pyright include를 읽었다) 이 변경은 그 셋을 고치지 않는다. 프로브의 파이썬 파일은 린트와 포맷 검사의 대상이다. 전체 pytest는 커밋이 부르는 pre-commit의 결과로 갈음하고(code-review 6단계 5) 결과는 아래 "커밋과 PR"에 적는다.

**표시 수.** 명세에서 줄 머리의 표시를 Grep으로 세어 `[넘겨받음]` 42, `[사용자 선택]` 4, `[정함]` 188, `[이력]` 5, `[거절]` 1을 얻었다. 다섯 표시를 한 번에 센 값도 240이고 명세 머리의 수와 같다.

**프로브.** 넷 가운데 `schedule-once`만 PR 직전 리뷰 뒤에 고쳐 다시 돌렸고(위 "판정과 반영"), 커밋하는 출력 파일은 커밋하는 스크립트가 낸 마지막 출력이다. 나머지 셋은 셀프 리뷰 반영 뒤의 출력 그대로다.

**커밋 전에 dev를 받았다.** `git fetch origin` 뒤 `git log --oneline HEAD..origin/dev`가 커밋 셋(`79cd78c`, `64bd055`, `5e80700`)을 냈다. 이 브랜치에는 아직 커밋이 없었고 `uv run python tools/sibling_overlap.py`가 "번호 겹침 없음"과 "함께 고친 파일 없음"을 냈으므로, 커밋하고 나서 합치는 대신 `git merge --ff-only origin/dev`로 브랜치를 `79cd78c`로 먼저 옮겼다. 커밋 전 검사를 한 번만 돌리고, dev에 새로 들어온 검사가 이 커밋에도 걸리게 하려는 것이다.

**줄 끝.** 그 커밋 가운데 `79cd78c`가 줄 끝 검사(`tools/check_line_separators.py`)에 CRLF를 더했다. 스테이징할 때 git이 프로브 출력 넷(`cron-expr/probe_out.txt`, `schedule-once/probe_out.txt`, `source-delete/probe_out.txt`, `source-delete/probe_out_batch50.txt`)에 CRLF 경고를 냈고, 검사를 손으로 돌리니 그 넷이 걸렸다(91줄, 60줄, 33줄, 33줄). Windows의 셸에서 표준 출력을 파일로 받으며 줄 끝이 바뀐 것이다. `sed -i 's/\r$//'`로 줄 끝의 CR 문자만 지웠고 글자는 그대로다. 그 뒤 스테이징한 스물다섯 파일 모두에 검사를 돌려 출력 없이 끝나는 것을 봤다. `mount-propagation/probe_out.txt`는 처음부터 LF였다.
