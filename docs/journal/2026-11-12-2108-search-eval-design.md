# search-eval 설계: 검색 평가의 구조, 최소 점수, LLM 관련성 판정 · 2026-11-12

사용자가 설계 인터뷰를 진행할 기능이 있는지 물었고 search-eval을 먼저 하라고 해서 연 세션의 기록이다(Fable 5.2). `grill-with-docs`로 인터뷰했고, 브랜치는 `docs/search-eval`(설계를 쓰는 면제 PR), 작업은 워크트리 `search-eval-design`에서 했다. 준비, 사용자가 넘긴 것, 확인한 것, 물은 것과 답, 합의 요약, 초안의 승인, 반영한 것, 검증, 셀프 리뷰, 회고, 다음을 차례로 둔다.

## 준비

- 워크트리 `search-eval-design`은 e95006c에서 섰다. 산출물을 쓰기 직전에 `git fetch origin`과 `git merge --ff-only origin/main`으로 3cf02f1(dev-branch 01, #26)에 맞췄다. 그때까지 이 브랜치에는 커밋이 없었다.
- `grill-with-docs`가 `grilling`과 `domain-modeling`을 불렀다. LLM 판정을 다루는 질문을 올리기 전에 `claude-api` 스킬 문서(모델 표는 2026-11-03 판)에서 모델 ID, 값, 샘플링 인자의 거부를 읽었다.
- 주 체크아웃은 11f91c9에 머물러 있고 추적하지 않는 로그 파일 둘이 있어 당기지 않았다고 사용자에게 알렸다.

## 사용자가 넘긴 것

- 기능 계획 `.scratch/search-eval/plan.md`의 "넘긴 것" 문단 넷이 입력이었다. core 명세가 넘긴 판정 다섯, dev-branch(ADR 0016)가 넘긴 게이트의 자리, 사용자가 2026-11-10에 넘긴 평가 항목 넷, 같은 날 넘긴 최소 점수 제안이다.
- 세션 도중의 답은 아래 "물은 것과 답"에 글자 그대로 있다. 선택지 밖의 글로 답한 것이 다섯이고 그 가운데 셋은 되물음이라 다시 물었다.

## 확인한 것

- **모르는 인자**(쟀다. `.scratch/search-eval/probes/mcp-args/probe_unknown_args.py`, 출력 `probe_unknown_args_out.txt`): mcp 2.3.0, pydantic 2.14.3, httpx2 2.16.0에서 도구의 inputSchema에는 최상위에도 중첩 모델에도 `additionalProperties`가 없다. 선언하지 않은 최상위 인자 `min_score`와 중첩 `filter` 안의 모르는 키는 `isError`가 거짓인 정상 결과이고 값은 버려진다. SDK 클라이언트의 요청과 raw HTTP 요청(세션 없음, JSON 응답)이 같았다. 처음의 프로브는 raw 요청으로 최상위 인자만 보냈고, 중첩 키의 경우는 셀프 리뷰 뒤에 프로브에 더해 다시 돌렸다(두 경우 모두 status 200이고 `isError`가 거짓이었다). 타입이 틀린 인자와 빠진 필수 인자는 `isError`가 참이고, 그 오류 글에는 입력 값이 그대로 실렸다.
- **LLM SDK**(쟀다. `.scratch/search-eval/probes/llm-sdk/pypi_anthropic.py`, 출력 `pypi_anthropic_out.txt`): `anthropic`의 PyPI 최신 판은 2.8.0(2026-11-10 배포)이고 `requires_python`은 `>=3.10`이다. METADATA가 `License: Apache-2.0`이고 휠의 `licenses/LICENSE`가 Apache License 2.0 원문이다. `py.typed`가 있다. 필수 의존은 anyio, docstring-parser, httpx2, jiter, opentelemetry-api, pydantic, sniffio, typing-extensions 여덟이다.
- **새로 드는 패키지**(손으로 봤다): `uv pip install --dry-run "anthropic>=2.8,<3"`이 anthropic 2.8.0, docstring-parser 0.18.0, jiter 0.19.0, sniffio 1.3.1 넷을 냈고, 필수 의존 여덟 가운데 나머지 다섯(anyio, httpx2, opentelemetry-api, pydantic, typing-extensions)은 `uv tree --no-dev --frozen`의 출력에 이미 있었다. 전이 의존 셋의 라이선스 원문은 이때 보지 않았고, 셀프 리뷰 뒤에 프로브로 쟀다(다음 항목).
- **전이 의존의 라이선스**(쟀다. `.scratch/search-eval/probes/llm-sdk/pypi_transitive_licenses.py`, 출력 `pypi_transitive_licenses_out.txt`. 셀프 리뷰 뒤에 더했다): docstring-parser 0.18.0은 METADATA가 `License: MIT`이고 휠의 `licenses/LICENSE.md`가 MIT 원문이다. jiter 0.19.0은 `License-Expression: MIT`이고 휠의 `licenses/LICENSE`가 MIT 원문이다(본 휠은 cp311 macOS 용이다). sniffio 1.3.1은 `License: MIT OR Apache-2.0`이고 휠에 두 원문이 함께 있다.
- **어댑터의 타입 검사**(쟀다. `.scratch/search-eval/probes/llm-sdk/judge_adapter_types.py`, 출력 `judge_adapter_types_out.txt`와 `judge_adapter_types_pyright_out.json`. 셀프 리뷰 뒤에 더했다): 판정기 포트와 그 구현의 꼴로 쓴 코드가 anthropic 2.8.0과 pyright 1.1.414의 strict 설정에서 `filesAnalyzed` 1, `errorCount` 0이다. 프로브는 클라이언트를 만든 데까지이고 호출하지 않는다. 손으로 본 것이 둘 있다. 원칙 II가 막는 넷을 쓰지 않는지는 `tools/check_type_escapes.py`의 `escapes_in`을 그 파일의 글에 불러 빈 목록을 봤다. 임시 pyright 설정이 strict로 도는지는 타입 표기가 없는 함수 하나만 둔 대조 파일을 같은 설정과 같은 명령으로 돌려 오류 넷이 나는 것으로 봤다. 명령은 프로브 폴더의 README에 있다.
- **점수의 눈금**(코드를 읽었다): `src/rag_engine/domain/entities.py`의 `SearchHit.score`는 `rerank_score`가 있으면 그것을, 없으면 `rrf_score`를 돌려준다. 후보를 모으는 포트 메서드는 `VectorIndex.search_candidates`이고 리랭크는 `src/rag_engine/app/search.py`의 유스케이스가 한다. `KnowledgeBase`의 `reranker_endpoint`와 `reranker_model`은 `None`일 수 있다. 오류 코드 `invalid_argument`는 `src/rag_engine/domain/errors.py`에 있다.
- **계약의 판**(코드를 읽었다): `src/rag_engine/server/tool_models.py`의 `FORMAT_VERSION`은 `"1.0.0"`이고 `SearchFilterInput`의 설정은 `frozen=True`뿐이다.
- **이미지에 드는 것**(코드를 읽었다): `Dockerfile`은 `uv sync --frozen --no-dev`로 설치하고 `.dockerignore`는 `pyproject.toml`, `uv.lock`, `README.md`, `src/`만 들인다. 그래서 운영 의존성으로 선언한 패키지와 `src/` 아래의 코드만 이미지에 든다.
- **경계 검사**(코드를 읽었다): `pyproject.toml`의 둘째 import-linter 계약은 서드파티 열여섯을 `app`과 `domain`에서 막는다. `anthropic`을 더하면 열일곱이다.
- **다른 ADR의 문장**(읽었다): ADR 0016은 느린 검사를 main PR에만 둘지를 그 기능의 설계에 미뤘고, ADR 0007은 포트 열과 유스케이스를 본문에 나열한다. `docs/adr/`를 `LLM`, `밖으로`, `외부`로 grep해 나온 ADR 0004와 0010의 문장은 이번 결정으로 거짓이 되지 않는다(검색 질문을 남기지 않는 것과 임베딩·리랭커의 자리는 그대로다).
- **면제 PR이 고칠 수 있는 파일**(코드를 읽었다): `tools/check_ticket.py`의 독스트링이 `docs/PRD.md`, `docs/constitution/tech.md`, 헌법 README, `GLOSSARY.md`, `docs/adr/*.md`, 기능 폴더의 계획과 프로브, 일지를 면제 모양으로 든다. `docs/constitution/operations.md`와 `CLAUDE.md`, `pyproject.toml`은 그 목록에 없다.
- **형제**(명령의 출력): 쓰기 전의 `uv run python tools/sibling_overlap.py`는 번호 겹침이 없다고 했고 형제가 쓴 가장 높은 헌법 판은 1.2.0이었다. `gh pr list --state open`이 낸 열린 PR은 #25(`feature/03-dev-base-skills-docs`) 하나다.
- **값과 건수**(어림): 판정은 약 3,000건(질문 150, 질의 목록 2, 상위 10)이고, 건당 입력 1,200 토큰과 출력 200 토큰으로 어림하면 Opus 5.5로 약 26달러, 배치로 약 13달러다. 값은 `claude-api` 스킬 문서의 표를 읽은 것이고 호출로 재지 않았다.

## 물은 것과 답

추천안을 첫 자리에 두고 "(Recommended)"를 붙였다. `AskUserQuestion` 호출은 열 번이었다. 선택지 밖의 글로 답한 자리에는 그 글을 따옴표로 옮기고 그 뒤의 처리를 적었다.

호출 1(네 질문).

- 질문(글 그대로): core가 search-eval에 넘긴 판정 다섯 가지(조각 크기와 겹침, 리랭커 켬·끔과 검색 후보 수, 키워드 품사 규칙, 좁은 필터의 정확 스캔, 시멘틱 청킹)를 이 기능에서 어디까지 처리할까요? (선택지 3: 설정만 바꾸는 실험까지 (Recommended), 도구와 게이트만, 다섯 가지 모두 판정)

> 사용자: "설정만 바꾸는 실험까지 (Recommended)" — 설명: 평가 도구, 첫 기준 보고서, CI 게이트를 만듭니다. 설정값만 바꿔 다시 재면 되는 두 가지(조각 크기·겹침, 리랭커 켬·끔과 후보 수)는 이 기능이 실험해서 기본값을 정합니다. 코드를 새로 짜야 하는 세 가지(품사 규칙 변경, 정확 스캔 분기, 시멘틱 청킹)는 판단에 쓸 숫자만 보고서에 남기고, 고칠지는 그 숫자를 본 뒤 별도 작업으로 정합니다.

- 질문(글 그대로): 평가에 쓸 공개 문서 묶음과 질문·정답을 어디서 마련할까요? (선택지 3: 공공 문서로 직접 구성 (Recommended), 공개 데이터셋 채택, 둘 다 사용)

> 사용자: "둘 다 사용" — 설명: CI 게이트와 공개 시연은 직접 구성한 공공 문서 묶음으로 하고, 공개 데이터셋은 로컬에서 돌리는 참고 측정으로만 씁니다. 관리할 재료가 둘로 늘지만, 사람이 만든 질문 300개로 한 번 더 확인할 수 있습니다.

- 질문(글 그대로): 적중률을 검색의 네 단계(벡터만, 키워드만, 둘을 합친 뒤, 리랭크 뒤)로 나눠 재려면 검색 내부의 중간 결과가 필요한데, 지금 코드는 그것을 밖으로 내지 않습니다. 중간 결과를 어떻게 얻을까요? (선택지 3: 진단용 검색 경로 추가 (Recommended), MCP 검색만 바깥에서 호출, 평가 도구가 DB에 직접 질의)

> 사용자: "진단용 검색 경로 추가 (Recommended)" — 설명: 조각마다 벡터 순위, 키워드 순위, 합친 순위, 리랭크 점수를 함께 돌려주는 진단용 검색을 서버 코드 안에 더하고, 실제 검색과 같은 SQL 뼈대를 쓰게 합니다. MCP로는 열지 않습니다. 색인 한 번으로 네 줄이 모두 나옵니다. 대신 검색 포트에 메서드가 하나 늘고 그만큼 시험이 늡니다.

- 질문(글 그대로): 검색 결과를 최소 점수로 거르는 인자(예: min_score)를 search 도구에 언제 더할까요? (선택지 3: 설계는 지금, 구현은 측정 뒤 (Recommended), 이 기능에서 바로 추가, 이번에는 재기만)

> 사용자: "설계는 지금, 구현은 측정 뒤 (Recommended)" — 설명: 인자의 동작(리랭커가 없을 때, 거른 뒤 결과가 0개일 때, 계약의 판)은 이번 인터뷰에서 정해 ADR에 적습니다. 구현 티켓은 점수 분포를 재는 티켓 뒤에 두고, 정답 조각과 아닌 조각의 점수가 잘 갈리는 것을 확인한 뒤에 진행합니다. 잘 갈리지 않으면 구현하지 않고 다시 여쭙니다.

호출 3(네 질문).

- 질문(글 그대로): 되물으신 내용을 반영해 다시 여쭙니다. 적중률 보고서에 어떤 숫자를 낼까요? (선택지 3: 넷 다 계산, 정답은 하나 이상만 (Recommended), 적중률과 MRR만, 학술 벤치마크 방식(정답을 빠짐없이))

> 사용자: "추천대로 진행하고 학술 벤치마크 방식은 추후에" (직접 입력. "추천대로"는 "넷 다 계산, 정답은 하나 이상만 (Recommended)"이고 그 설명은 다음과 같다. 상위 1·3·5·10 적중률, MRR, 재현율, nDCG@10을 모두 냅니다. 평가 세트에는 질문마다 정답을 하나 이상 적으면 되고, 관련 조각을 빠짐없이 찾아 적을 의무는 두지 않습니다. 정답이 하나인 질문에서는 재현율이 적중률과 같은 값이고, 문서 여러 개를 이어야 답하는 질문에서만 재현율이 '전부 찾았는지'를 따로 보여 줍니다. nDCG@10은 공개 벤치마크의 대표 숫자여서 바깥 수치와 나란히 읽을 수 있습니다. 계산 비용은 거의 없습니다.)

- 질문(글 그대로): PR마다 도는 빠른 게이트를 문서만 바뀐 PR에서도 돌릴까요? (선택지 2: 검색에 영향을 주는 변경에서만 (Recommended), 모든 PR에서 항상)

> 사용자: "검색에 영향을 주는 변경에서만 (Recommended)" — 설명: 서버 코드, 의존성 목록(형태소 분석기의 판이 바뀌면 키워드 토큰이 달라집니다), 평가 재료와 평가 구성이 바뀐 PR에서만 빠른 게이트를 돌리고, 그 밖의 PR(문서, 하네스)에서는 건너뜁니다. 건너뛴 경우 필수 검사 `verify`는 이 잡을 통과로 취급합니다. 문서 PR의 CI가 빨라지지만, 영향을 주는 경로의 목록을 관리해야 하고 목록에서 빠진 경로의 변경은 출시 때의 전체 게이트에서야 잡힙니다.

호출 9(네 질문).

- 질문(글 그대로): LLM에게 조각을 보내 관련 여부를 묻는 코드를 어디에 둘까요? (선택지 3: 제품 이미지 밖의 평가 도구에만 (Recommended), 제품 코드에 꽂는 자리만 마련, 제품 코드 안에 구현까지)

> 사용자: "제품 코드 안에 구현까지" — 설명: LLM 연동을 제품의 adapters 층에 넣습니다. 제품 이미지에 LLM SDK가 들어가고, 스택이 바뀌므로 별도의 ADR이 필요하며, PRD의 '답 생성(LLM 호출)은 만들지 않는다'는 경계를 다시 그어야 합니다.

- 질문(글 그대로): 관련성 판정에 어느 LLM을 쓸까요? 어느 쪽을 고르든 모델 이름은 설정값으로 두고, 보고서에 판정 모델을 적습니다. (선택지 4: Claude API, Opus 5.5로 시작 (Recommended), Claude API, Sonnet 5.5, Claude API, Haiku 5.5, 제공자를 설정으로 고르는 호환 끝점)

> 사용자: "Claude API, Opus 5.5로 시작 (Recommended)" — 설명: Anthropic 공식 SDK로 직접 부릅니다. 판정이 가장 정확한 모델로 기준을 세웁니다. 전체 한 번에 약 26달러, 배치로 보내면 약 13달러입니다(어림). 더 싼 모델의 판정이 이것과 충분히 일치하면 그때 설정을 낮춥니다.

- 질문(글 그대로): LLM 판정은 어디에서 돌리고, 그 결과를 어떻게 보관할까요? (선택지 3: 로컬에서만 호출, 판정 파일을 커밋 (Recommended), CI의 전체 측정에서도 호출, 로컬에서만, 커밋하지 않음)

> 사용자: "로컬에서만 호출, 판정 파일을 커밋 (Recommended)" — 설명: API는 개발자가 로컬에서 수동으로 돌릴 때만 부르고, 키는 환경 변수로만 받습니다. 판정 결과(어느 질문과 어느 조각에 어떤 판정이 났는지, 판정 모델, 지시문의 판, 날짜)를 파일로 저장소에 커밋합니다. CI는 API 키 없이 그 파일만 읽어 숫자를 계산하고, 파일에 없는 새 조합은 '판정 없음'으로 세어 그 비율을 보고서에 적습니다. 입력이 같으면 숫자가 늘 같습니다.

- 질문(글 그대로): LLM 판정으로 보고서에 어떤 숫자를 실을까요? (선택지 3: 관련 있음·없음 두 등급, 숫자 둘 (Recommended), 0~3 네 등급(학술 방식), 두 등급, 상위 10 관련 비율 하나만)

> 사용자: "관련 있음·없음 두 등급, 숫자 둘 (Recommended)" — 설명: 조각마다 관련 있음과 없음만 판정합니다. 보고서에 숫자 둘을 싣습니다. 첫째는 상위 10개 조각 가운데 LLM이 관련 있다고 본 비율입니다. 둘째는 정답표의 정답 조각을 LLM도 관련 있다고 본 비율이고, 판정기를 믿을 만한지 보는 점검 숫자입니다. 정답표에 없는데 LLM이 관련 있다고 본 조각은 '빠진 정답 후보' 목록으로 따로 내고, 사용자가 확인한 것만 정답표에 더합니다.

호출 10(세 질문).

- 질문(글 그대로): 설치처에서 LLM 판정을 쓸 때, 문서 조각과 질문이 LLM 쪽으로 나가는 조건을 어떻게 둘까요? (선택지 3: 기본은 꺼짐, 설치처가 직접 설정해야 켜짐 (Recommended), 위에 더해 지식베이스마다 따로 허용, 별도 장치 없이 키만 있으면 동작)

> 사용자: "기본은 꺼짐, 설치처가 직접 설정해야 켜짐 (Recommended)" — 설명: 주소, 모델, 키 설정이 모두 있을 때만 LLM 판정기를 조립하고, 없으면 평가는 LLM 숫자를 건너뜁니다. 조각과 질문은 설치처가 직접 적은 주소로만 갑니다. 키는 환경 변수나 비밀 파일로만 받고, 키와 판정 요청·응답의 본문은 로그에 남기지 않습니다. 지식베이스마다 따로 허용하는 장치는 관리자 페이지 설계(admin)에 넘깁니다.

- 질문(글 그대로): LLM SDK를 제품 이미지에 언제부터 실을까요? (판정기 코드 자체는 어느 쪽이든 지금 제품 코드에 들어갑니다) (선택지 2: 입구가 열릴 때 이미지에 포함 (Recommended), 지금부터 제품 이미지에 포함)

> 사용자: "지금부터 제품 이미지에 포함" — 설명: SDK를 운영 의존성으로 선언해 공개 시연 이미지부터 싣습니다. 설치 모양이 하나라 단순합니다. 그 대신 입구가 열리기 전까지는 이미지 안에서 그 SDK를 부를 길이 없고, release-image의 부품 목록과 취약점 스캔의 대상이 지금부터 늡니다.

- 질문(글 그대로): PRD의 '무엇을 안 만드나'에 있는 '답 생성(LLM 호출)' 문구를 어떻게 할까요? (선택지 2: PRD를 고쳐 경계를 다시 적음 (Recommended), PRD는 그대로 두고 ADR에만 적음)

> 사용자: "PRD를 고쳐 경계를 다시 적음 (Recommended)" — 설명: 그 줄을 '답 생성'으로 두고(괄호 속 'LLM 호출'을 뺌), 검색 요청을 처리하는 길에서는 LLM을 부르지 않으며 LLM은 설치처가 켠 검색 평가의 관련성 판정에만 쓴다는 문장을 PRD에 한 줄 더합니다. 같은 내용을 ADR에도 적습니다. PRD의 수정은 문구 초안을 보여 드리고 승인받은 뒤에 합니다.

## 합의 요약

질문을 마친 뒤 아래 요약을 올렸고 사용자가 그대로 진행하라고 했다. 요약은 에이전트가 쓴 글이다(머리 줄은 굵은 글씨로, 링크는 경로로 옮겼다).

> **1. 범위와 자리**
> 1. 평가 도구, 첫 기준 보고서, CI 게이트를 만듭니다. 설정만 바꾸면 되는 둘(조각 크기와 겹침, 리랭커 켬·끔과 후보 수)은 이 기능이 실험해 기본값을 정합니다. 코드 변경이 필요한 셋(품사 규칙, 정확 스캔 분기, 시멘틱 청킹)은 판단에 쓸 숫자만 보고서에 남기고 별도 작업으로 정합니다.
> 2. 평가의 핵심은 제품 코드의 유스케이스로 둡니다. 이번에 여는 입구는 CI와 공개 시연에 쓰는 명령줄 도구이고, 제품 이미지의 명령으로는 내지 않습니다. 관리자 페이지의 등록·실행·결과 화면, 관리 API, 저장 표는 admin 계획에 "넘긴 것"으로 적습니다.
> 3. 조각마다 벡터 순위, 키워드 순위, 합친 순위, 리랭크 점수를 돌려주는 진단용 검색 경로를 서버 코드에 더합니다. 실제 검색과 같은 SQL 뼈대를 쓰고, MCP로는 열지 않습니다.
>
> **2. 평가 재료**
> 1. CI 게이트와 공개 시연은 직접 구성한 공공 문서 묶음을 씁니다. 공개 데이터셋(allganize)은 로컬 참고 측정에만 쓰고, PDF는 링크에서 내려받아 커밋하지 않습니다.
> 2. 공공 문서 묶음은 법령과 행정규칙을 뼈대로 하고 공공누리 1유형 문서를 일부 더합니다. 에이전트가 후보 목록을 내고 사용자가 확정합니다. 문서 40개 안팎과 질문 150개 안팎은 어림이며 명세에서 확정합니다.
> 3. 묶음은 저장소에 커밋하고 용량 상한을 둡니다(예: 30MB, 명세에서 확정). 문서마다 출처, 이용 조건, 내려받은 날짜, 해시를 목록에 적습니다.
> 4. 평가 세트는 정답(기대 근거)과 질의 목록으로 나눕니다. 저장소가 사람 질문 목록과 키워드형 목록을 함께 가집니다.
> 5. 정답의 단위는 묶음마다 다릅니다. 공공 문서 묶음은 문서와 원문 글귀이고(조각 글에 글귀가 들어 있으면 적중, 경계에서 갈리면 놓침), 공개 데이터셋은 문서와 쪽 번호입니다.
> 6. 질문은 에이전트가 초안을 쓰고 사용자가 검수합니다. 원문 표현을 바꿔 묻는 규칙을 따르고, 키워드형 목록도 같은 방법으로 만듭니다.
>
> **3. 지표와 보고서**
> 1. 상위 1·3·5·10 적중률, MRR, 재현율, nDCG@10을 모두 계산합니다. 정답은 질문마다 하나 이상만 요구하고, 정답을 빠짐없이 적는 학술 방식은 나중으로 미룹니다.
> 2. 보고서는 단계별 네 줄(벡터만, 키워드만, 합친 뒤, 리랭크 뒤)을 질의 목록마다 냅니다.
> 3. 놓친 질문의 까닭은 세 겹으로 분류합니다. 미리 단 유형 표지, 자동으로 잡는 탈락 지점과 낱말 겹침, 사람의 판정입니다. 사람 판정의 초벌은 Claude Code 세션이 하고 사용자가 확인합니다.
>
> **4. CI 게이트**
> 1. 두 단계로 돕니다. 모든 PR에서는 리랭커를 뺀 세 줄을 재는 빠른 게이트가 돌고, main으로 가는 PR(출시와 핫픽스)과 수동 실행에서는 전체를 잽니다.
> 2. 빠른 게이트는 검색에 영향을 주는 변경(서버 코드, 의존성 목록, 평가 재료와 구성)이 있는 PR에서만 돌고, 건너뛴 경우 `verify`는 통과로 취급합니다.
> 3. 기준은 커밋해 둔 기준 보고서 대비 하락폭입니다(폭은 명세에서 확정, 예: 2%p). 질의 목록마다 상위 5 적중률과 MRR을 봅니다. 빠른 게이트는 "합친 뒤" 줄을, 전체 게이트는 "리랭크 뒤" 줄을 봅니다. 벡터만·키워드만 줄은 보고서에만 싣습니다.
> 4. 기준 보고서를 갱신하는 커밋은 사람이 승인합니다.
>
> **5. 최소 점수**
> 1. 동작은 지금 ADR에 적고, 구현 티켓은 점수 분포를 재는 티켓 뒤에 둡니다. 점수가 잘 갈리지 않으면 구현하지 않고 다시 여쭙니다.
> 2. 리랭커가 없는 지식베이스에 최소 점수를 주면 오류(`invalid_argument`)로 거부합니다. 그런 지식베이스에 기본값을 설정하는 것도 거부합니다.
> 3. 걸러서 남은 것이 없으면 빈 결과로 정상 응답합니다.
> 4. 요청 인자와 지식베이스 기본값을 둘 다 두고 인자가 우선합니다. 초기 상태에서는 거르지 않습니다.
> 5. 계약의 판은 입력 인자를 더할 때도 minor로 올립니다(1.0.0에서 1.1.0). 필수 인자의 추가, 인자의 삭제, 뜻의 변경은 major입니다.
>
> **6. LLM의 역할**
> 1. 채점은 정답표로 합니다. LLM은 질문 초안, 놓친 까닭의 초벌 판정, 빠진 정답 찾기에 쓰고(Claude Code 세션과 사용자 확인), 여기에 더해 평가가 LLM API를 불러 낸 관련성 숫자를 보고서에 참고로 싣습니다. 게이트로는 쓰지 않습니다.
> 2. LLM 연동은 제품 코드 안에 구현까지 둡니다. 제품 이미지에 LLM SDK가 지금부터 들어가고, 스택이 바뀌므로 별도의 ADR을 씁니다.
> 3. 판정에는 Claude API를 공식 SDK로 부르고 Opus 5.5로 시작합니다. 모델 이름은 설정값이고 보고서에 판정 모델을 적습니다. 더 싼 모델의 판정이 충분히 일치하면 그때 낮춥니다.
> 4. 이 저장소의 평가에서는 로컬 수동 실행에서만 API를 부르고, 판정 결과(판정 모델, 지시문의 판, 날짜 포함)를 파일로 커밋합니다. CI는 키 없이 그 파일만 읽어 숫자를 계산하고, 파일에 없는 조합은 "판정 없음"으로 세어 그 비율을 보고서에 적습니다.
> 5. 판정은 관련 있음과 없음의 두 등급입니다. 보고서에는 상위 10개 조각 가운데 관련 있다고 본 비율과, 정답 조각을 LLM도 관련 있다고 본 비율(판정기 점검용)을 싣습니다. 정답표에 없는데 관련 있다고 본 조각은 "빠진 정답 후보" 목록으로 내고, 사용자가 확인한 것만 정답표에 더합니다.
> 6. 설치처에서는 기본이 꺼짐입니다. 주소, 모델, 키 설정이 모두 있을 때만 판정기를 조립하고, 없으면 LLM 숫자를 건너뜁니다. 키는 환경 변수나 비밀 파일로만 받고, 키와 판정 요청·응답의 본문은 로그에 남기지 않습니다. 지식베이스마다 따로 허용하는 장치는 admin에 넘깁니다.

## 초안의 승인

프로브 둘을 돌린 뒤 ADR 0015의 이력, 새 ADR 셋, PRD 12행을 바꾸는 두 줄, `docs/constitution/tech.md`의 행을 채팅에 초안으로 올렸다. 합의 요약에 없는데 초안이 정한 것 다섯을 따로 짚었다.

1. 모르는 인자를 버리는 지금 동작을 그대로 두고, 거부로 바꾸는 것은 major의 일로 적는다(ADR 0015 이력).
2. ADR을 셋으로 나눈다. 최소 점수는 계약, 평가의 구조는 CI와 형식, LLM 판정은 스택과 PRD를 바꾸는 결정이라 되돌리는 단위가 다르다.
3. 다른 ADR에 포인터 셋을 단다. ADR 0007에 둘, ADR 0016에 하나다.
4. 헌법 판을 1.1.2에서 1.3.0으로 올린다. 스택 표에 행과 규범 문장을 더하는 변경이라 minor이고(선례는 core 설계의 1.0.0에서 1.1.0), 형제 PR #25가 1.2.0을 쓰고 있어 그 위의 번호다.
5. 명세로 넘긴 것이 둘이다. 기본값이 있는 지식베이스에서 리랭커를 빼는 경우와, 판정 파일에서 조각을 가리키는 값이다.

> 사용자: "초안대로 쓰기" (질문: 이 초안대로 ADR과 PRD를 파일로 써도 될까요?)

승인 뒤에 초안에 더한 문장이 있다. 고른 선택지의 설명에 있었는데 초안이 빠뜨린 조건이라 Consequences와 본문에 옮겼고 결정은 바꾸지 않았다. ADR 0017에는 넷이다. 리랭커가 실패할 때 오류를 내는 지금 규칙과 같은 방향이라는 것, 현재 판이 없을 때와 없는 그룹 이름으로 걸렀을 때도 빈 결과라는 것, 기본값을 설정한 설치에서는 인자를 보내지 않는 클라이언트의 결과도 걸러진다는 것, 클라이언트가 리랭커의 유무를 미리 알 길이 없다는 것이다. ADR 0018에는 넷이다. 하락폭을 첫 측정의 흔들림을 보고 정한다는 것, 리랭커 쪽의 회귀가 main으로 가는 PR에서야 드러난다는 것, 경로의 목록을 관리해야 한다는 것, 그리고 합의 요약의 가정 7에 있던 조건(기대 근거와 질의 목록의 수정도 숫자의 앞뒤 차이를 보이고 승인받은 뒤에 한다)이다. ADR 0019에는 판정의 정확도를 사람 표본과 맞춰 보는 일이 따로 필요하다는 것 하나다. ADR 0019의 샘플링 인자 문장은 `claude-api` 스킬 문서를 다시 읽고 좁혔다. 초안은 인자를 거부한다고만 적었는데, 문서가 적은 것은 기본값이 아닌 값을 거부한다는 것이다. 결정성을 판정의 저장으로 얻는다는 결정은 그대로다. 이 문장은 셀프 리뷰 뒤에 한 번 더 고쳤다(셀프 리뷰 절).

따로 짚은 다섯 밖에 초안이 정한 것이 둘 더 있다(셀프 리뷰 명세 축 Nit). SDK의 판 범위를 `>=2.8,<3`으로 둔 것과, 리랭크 점수를 진단용 포트 메서드가 돌려주지 않고 평가 유스케이스가 실제 검색과 같은 리랭커 포트로 붙이게 한 것이다. 둘 다 사용자가 승인한 초안의 글에 있었지만 합의 요약에는 없던 결정이라 최종 보고에서 따로 알린다.

셀프 리뷰 뒤에도 ADR 넷(0015 이력, 0017, 0018, 0019)의 글을 더 고쳤다. 사용자가 승인한 초안과 달라진 문장은 셀프 리뷰 절의 고친 것에 원문으로 있고, 최종 보고에서 알린다.

`/code-review`를 origin/main 이후의 작업 트리에 돌렸다. 표준 축은 sonnet·high 서브에이전트이고 명세 축은 본 세션의 모델을 물려받았다. 명세로는 이 일지의 사용자의 답과 합의 요약을 넘겼다. 두 보고와 지적별 판정은 받은 턴에 이 절로 옮기지 못했다. ADR과 프로브를 먼저 고치는 사이에 컨텍스트가 압축되어, 이 절은 압축 요약에서 다시 적었다(회고 절의 일곱째 항목).

### 고친 것

반영으로 새로 쓰거나 근거가 바뀐 사실 문장의 원문이다. PR 직전 리뷰의 브리프에 밀 주장으로 넘긴다.

- ADR 0015 이력: 입력 인자를 처음 더하는 티켓이 계약 시험에 도구 목록의 inputSchema를 보는 시험을 더한다. 지금 계약 시험은 inputSchema를 보지 않는다(손으로 봤다. `tests/`를 `inputSchema`와 `input_schema`로 grep해 0건이었다).
- ADR 0015 이력: 인자를 더하면서 판을 올리지 않으면 결과에서는 가릴 길이 없고 도구 목록의 inputSchema만 남는다.
- ADR 0015 이력(글은 그대로이고 프로브를 고쳐 근거가 바뀌었다): 최상위 인자와 중첩 모델 안의 키가 모두 그랬고, SDK 클라이언트의 요청과 raw HTTP 요청이 같았으며, inputSchema에는 `additionalProperties`가 실리지 않았다(쟀다. 프로브 `.scratch/search-eval/probes/mcp-args/probe_unknown_args.py`).
- ADR 0017 본문: 그래서 이 인자를 구현하는 티켓은 계약을 바꾸는 티켓인데도 기능의 첫 티켓이 아니다. 계약을 바꿀지가 측정에 달려 있어 `docs/agents/issue-tracker.md` 전체 계획 절의 규칙(계약을 바꾸는 티켓이 첫 티켓이다)에 두는 예외다.
- ADR 0018 범위 항목: `ts_rank`에는 IDF가 없다는 ADR 0006 Consequences의 판단과, 키워드 질의가 토큰을 OR로 잇는 지금 동작을 이 줄로 본다. (OR은 코드를 읽었다. `src/rag_engine/adapters/postgres/vector_index.py`의 `_tsquery`가 토큰을 ` | `로 잇는다.)
- ADR 0018 Consequences: 빠른 게이트의 실행은 리랭크 뒤 줄을 만들지 못하므로 기준 보고서의 그 줄은 전체 게이트의 실행에서 온다.
- ADR 0018 Consequences: `verify`는 지금 건너뛴 잡을 빨강으로 센다(`.github/workflows/ci.yml`의 verify 주석을 읽었다).
- ADR 0019 SDK 항목: 전이 의존 셋의 라이선스는 docstring-parser와 jiter가 MIT, sniffio가 MIT와 Apache-2.0 가운데 고르는 것이다(쟀다. 프로브 `.scratch/search-eval/probes/llm-sdk/pypi_transitive_licenses.py`).
- ADR 0019 SDK 항목: 판정기 어댑터의 꼴로 쓴 코드는 anthropic 2.8.0에서 pyright strict를 오류 0으로 지난다(쟀다. 프로브 `.scratch/search-eval/probes/llm-sdk/judge_adapter_types.py`. 호출은 하지 않았다).
- ADR 0019 도는 곳 항목: 판정기 없이 저장된 판정으로 숫자를 내는 것이라 위의 건너뛰기와 부딪치지 않는다. 건너뛰는 것은 판정기도 저장된 판정도 없을 때다.
- ADR 0019 도는 곳 항목: 판정 모델로 고른 Opus 5.5에는 `temperature` 같은 샘플링 인자를 쓸 수 없다. 스킬 문서의 이주 안내는 Opus 5 절에서 샘플링 인자가 계속 거부된다고 적고 Opus 5.5 절은 그 절 위에 얹어 읽으라고 적으며, Sonnet 5와 Haiku 5.5는 기본값이 아닌 값을 거부한다고 적는다(`claude-api` 스킬 문서의 `shared/model-migration.md`와 `shared/models.md`를 읽었다. Claude Code 2.1.321에 실린 판이다. 호출로 재지 않았다).
- ADR 0019 비용 항목: 한 구성을 한 번 잴 때 판정은 약 3,000건이고(질문 150, 질의 목록 2, 상위 10) Opus 5.5로 약 26달러, 배치로 약 13달러다(어림). 설정 실험처럼 구성을 여럿 재면 구성마다 새 조각이 나오는 만큼 는다.
- ADR 0019 Consequences: 재지 않은 것은 실제 호출이다. 요청과 응답이 실제 API에서 프로브의 꼴대로 도는지는 키와 비용이 들어 재지 않았고, 사용자가 비용을 승인한 뒤 첫 구현 티켓이 잰다.
- ADR 0019 Consequences: 이어 가는 실행이 판정 파일에 있는 조합을 다시 부르면 같은 비용을 두 번 쓴다.
- `.scratch/admin/plan.md`: search-eval이 구현된 뒤에는 판정기와 SDK가 이미지에 실려 있고 기본은 꺼짐이다(끝점 주소, 모델, 키 설정이 모두 있어야 조립된다).
- `.scratch/release-image/plan.md`: search-eval이 구현되면 운영 의존성에 Anthropic SDK(`anthropic`)와 전이 의존 셋(docstring-parser, jiter, sniffio)이 더해져 이미지에 실린다.

사실이 아니라 결정이나 넘김으로 새로 쓴 문장도 있다. 사용자가 승인한 초안에 없던 글이라 최종 보고에서 알린다. ADR 0017 Consequences의 끝 줄(승인 전에는 구현 티켓이 다른 세션이 집을 수 있는 상태로 놓이지 않아야 하고, 구현 티켓을 승인 뒤에 쓰는 것을 기본으로 한다), ADR 0018의 평가 세트·질문·범위 항목에 더한 조건과 Consequences의 넘김 넷, ADR 0019 Consequences의 넘김 하나, 용어집의 최소 점수·평가 세트·질의 목록 정의다.

### 남긴 것

- 프로브 헬퍼의 중복과 이름(표준 축 Nit): 프로브는 파일 하나로 다시 돌 수 있어야 하는 스크립트라 공통 모듈로 묶지 않는다.
- ADR 0017과 0018의 공공 문서 묶음(표준 축 6의 일부): 용어집의 _Avoid_는 그룹을 문서 묶음이라 부르지 말라는 것이고, 여기서는 평가 재료를 가리킨다. `docs/PRD.md` 19행도 평가 재료를 공개 문서 묶음이라 부른다.
- 실제 호출의 측정(표준 축 2의 일부): 키와 비용에 사용자 승인이 필요하다. 받는 쪽은 ADR 0019 Consequences와 다음 절의 첫 구현 티켓이 잴 것이다.

반영과 회고를 마친 뒤 검사를 다시 돌렸고, 결과는 검증 절에 있다. 전체 리뷰는 다시 돌리지 않았다.

## 회고

`retro`를 이 일지의 다음 절을 쓴 때의 계기로 돌렸다. 계기가 셀프 리뷰 도중에 들어와 리뷰의 반영을 마친 뒤에 판정을 닫았다. 후보는 열다섯이고 승인 여덟, 기각 일곱, 넘김 0이다. 승인한 여덟은 모두 회차를 세는 것이고 더하는 것이라, 다섯 번째 회차에 닿은 항목이 없어 이 세션에서 반영한 것은 없다. 만료할 항목도 없었다(`uv run python tools/queue_open_rows.py`. 워크트리에서 `--ref origin/main`으로 한 번 더 돌리는 확인은 만료 후보가 없어 하지 않았다).

이 반영을 싣는 커밋의 첫 시도는 pre-commit에서 멈춰 커밋이 만들어지지 않았다. 검사 러너의 pytest가 `1 failed, 3824 passed in 1316.30s (0:21:56)`였다. 러너의 나머지 열(test-db, check-ticket, zizmor, check-instructions, lint-imports, check-type-escapes, pyright, pyright-linux, run-hooks)과 표, 줄 구분자, 변이 표, 인용 대조 훅은 Passed였다. 실패한 시험은 `tests/adapters/test_parse_runner.py`의 `test_메시지를_보내다_멈춘_자식이_있어도_수신이_영영_막히지_않는다`다. 윈도에서 기대하는 오류 코드는 `parse_failed`인데 `parse_timeout`이 나왔다(그 시험이 러너에 준 제한 시간은 2초다).

- 그 파일만 따로 돌린 `uv run pytest tests/adapters/test_parse_runner.py -q -p no:cacheprovider`는 `36 passed in 199.27s (0:03:19)`였다.
- 같은 때에 다른 세션들의 pre-commit 검사 러너와 pytest가 돌고 있었다. 프로세스 목록을 손으로 봤고(`Get-CimInstance Win32_Process`), `C:\project\agent`의 워크트리 셋과 이 저장소의 형제 워크트리 `04-dev-branch-create`의 실행이었다. 검사 러너의 pytest 열은 이 시도에서 1350.3초였다(커밋 372065d는 755.0초, 병합 커밋 9da0c96은 613.3초였다).
- 이 브랜치의 변경은 문서뿐이고 파서 쪽 코드를 바꾸지 않았다. 시험은 고치지 않았다(원칙 I). 부하가 가라앉은 뒤에 같은 커밋을 다시 시도하고, 그 pre-commit의 결과는 PR 본문의 확인 방법에 적는다.
- 부하에서만 빨간 시간 시험이라 일지에만 적는다(retro 5단계의 끝이 열린 결함 종류). PR #22의 본문도 같은 시험이 부하 속에서 두 번 빨갰다가 따로 돌리면 초록이었다고 적었다. 대기열에서 이 시험을 다룬 항목은 찾지 못했다. `tools/queue_open_rows.py --search`로 `test_parse_runner`, `parse_timeout`, `부하`, `시간.시험`, `flaky`를 찾았고, 맞은 것은 다른 시험의 닫힌 항목 `token-expiry-test-load-margin` 하나다.

PR 직전 리뷰와 이 회차를 반영하며 ADR 0018과 0019에 더한 문장은 넷이다(PR 직전 리뷰에서 고친 것의 둘과 위의 둘). 사용자가 승인한 초안에 없던 글이므로 병합 전에 사용자의 승인을 받는다(`next-session` `merge.md`의 병합 길). PR을 연 턴의 보고에서 앞의 둘을 보이고 병합 여부를 물었고, 이 회차의 둘도 보고에서 보인다.

## 다음

이 브랜치의 변경은 커밋했고(372065d) origin/dev를 두 번 합쳤다(bcd5613을 합친 9da0c96과, PR #28이 병합된 뒤의 0caa20f를 합친 병합 커밋). 사용자가 요청해 PR #27을 base dev로 열었다. 병합은 ADR에 더한 문장 넷을 사용자가 승인한 뒤에 한다(PR 봇 리뷰 절의 병합에 앞서 받을 승인). base가 dev인 PR이므로 `/git-pr-merge`가 아니라 `next-session` `merge.md`의 워크트리에서 병합할 때 1~3으로 병합한다(`docs/constitution/operations.md` 브랜치와 병합). 병합 뒤의 다음 단계는 search-eval의 명세다(`to-spec`).

명세가 정할 것은 다섯 묶음이다.

- **게이트.** 하락폭의 값(첫 측정에서 실행마다 흔들리는 정도를 본 뒤), 빠른 게이트의 소요 시간 한도(core 16의 측정으로), 빠른 게이트를 돌릴 경로의 목록, 평가 전용 compose와 CI의 모델 캐시. dev 전환(ADR 0016) 전에 구현되면 전체 게이트는 수동 실행으로만 둔다. 셀프 리뷰가 더한 것이 넷이다. 기준 보고서의 어느 줄을 어느 실행의 값으로 갱신하는지와 첫 기준 보고서를 만드는 절차, 전체 게이트를 main 푸시에서도 돌릴지, dev 전환 뒤 전체 게이트를 main PR의 잡으로 켜는 일을 받는 티켓, 빠른 게이트를 건너뛴 PR이 `verify`를 통과하게 하는 방법이다(지금 `verify`는 건너뛴 잡을 빨강으로 센다).
- **재료.** 공공 문서 묶음의 용량 상한, 문서 수와 질문 수, 후보 목록(에이전트가 내고 사용자가 확정한다), 문서마다 적는 목록의 칸(출처, 이용 조건, 내려받은 날짜, 해시).
- **형식.** 평가 세트의 형식(판 칸, 기대 근거의 두 단위, 질의 목록, 놓친 까닭의 유형 표지, 공개 데이터셋의 그림 유형 문항 표시, 질의에 적는 필터 칸)과 보고서의 형식(JSON과 Markdown, 질의 목록마다 네 줄, 유형별 숫자. 기준 보고서는 커밋하고 CI의 보고서는 산출물로 올린다).
- **코드.** 진단용 메서드와 판정기 포트의 이름과 모양, 진단용 메서드와 `search_candidates`가 SQL 뼈대를 함께 쓰는 방식(PR 봇 첫 회차가 더했다. ADR 0018 Consequences), 명령줄 도구의 자리, 판정 파일의 형식과 조각을 가리키는 값, 질의를 가리키는 값(질의의 글이 바뀌면 옛 판정을 다시 쓰지 않는다. PR 직전 리뷰가 더했다), 지시문의 판. 판정 모델이 바뀌었을 때 옛 판정을 어떻게 다루는지와, 끊긴 실행을 이어 갈 때 이미 판정한 조합을 건너뛰는 규칙도 명세가 정한다(ADR 0019 Consequences).
- **순서.** 설정 실험(조각 크기와 겹침, 리랭커 켬·끔과 후보 수)은 로컬에서 수동으로 돌리고 결과를 프로브로 커밋하며, 기본값의 변경은 사용자 승인 뒤에 한다. 최소 점수는 분포를 재는 티켓, 사용자 승인, 구현 티켓의 순서다. 구현 티켓은 승인 뒤에 쓰는 것이 기본이고, 승인을 어디에 적는지는 명세가 정한다(ADR 0017 Consequences). 그 구현 티켓이 입력 인자를 처음 더하므로 계약 시험에 도구 목록의 inputSchema를 보는 시험도 그 티켓이 더한다(ADR 0015 이력). 기본값이 있는 지식베이스에서 리랭커를 빼는 설정 변경을 어떻게 다룰지도 명세가 정한다.

합의 요약의 가정 가운데 ADR에 적지 않고 명세로 넘긴 것은 3, 4, 11, 12이고 위 형식과 순서 묶음에 들어 있다. 가정 3 가운데 기본값의 변경은 사용자 승인 뒤에 한다는 조건은 셀프 리뷰 뒤에 ADR 0018의 범위 항목에도 적었다.

곁가지(이 설계의 범위 밖): 프로브의 대조군에서 MCP SDK가 인자 검증에 실패했을 때 낸 오류 글이 입력 값을 그대로 실었다(`input_value='많이'`). 프로브는 최소 서버로 잰 것이다. 셀프 리뷰의 표준 축 리뷰어가 이 저장소의 `register_search_tool`로 등록한 실제 도구에서도 같다고 보고했고, 일회용 스크립트로 다시 봤다(손으로 봤다. 스크래치패드의 스크립트라 커밋하지 않았다). `top_k`에 문자열 `'x'`를 주면 도구 호출이 `ToolError`로 끝났고 그 글에 `input_value='x'`가 실렸다. 서버의 로그에 그 글이 남는지는 보지 않았다. 원칙 V와 ADR 0015의 에러 봉투 항목(오류의 `detail`에 질문 내용을 넣지 않는다)에 닿을 수 있어 따로 확인할 일로 사용자에게 알린다. 세션 카드로 올리려 했으나 이 저장소의 훅이 에이전트가 스스로 내는 카드를 막아 여기에 적는다.
