# 관리자 페이지의 웹 워크스페이스는 agent-os ADR 0021의 스택을 따르고, 화면 부품은 agent-os 것을 복사하며, 릴리스 이미지를 하나 더 낸다

이 저장소에는 화면 코드가 없다. `docs/constitution/tech.md`의 "관리자 페이지" 칸은 후보 둘(pnpm과 Next의 웹 워크스페이스, 서버가 그리는 단순한 화면)을 적고 admin의 설계 인터뷰에 맡겼다. 설계 인터뷰(일지 `docs/journal/2026-11-26-1534-admin-design.md`)에서 사용자는 "Node 서버가 낸다 (Next + pnpm, agent-os와 같게)"를 골랐다. 일하는 방식의 원천은 agent-os 저장소(`njh6803/agent-os`)이고 공통 저장소는 두지 않는다(ADR 0016). 그래서 **이 저장소의 웹 워크스페이스는 agent-os의 ADR 0021(`docs/adr/0021-web-workspace-stack.md`)이 정한 스택을 따른다.** 따르는 것은 `web/` 아래의 pnpm 워크스페이스(pnpm 11), Node 24, TypeScript 5.9(strict), Next 16과 React 19, Tailwind CSS 4, 아이콘 lucide, 데이터 읽기의 SWR, 서버 계약 파일에서 만든 API 코드(openapi-typescript와 openapi-fetch. 만든 결과를 커밋하고 최신인지 검사한다), ESLint(typescript-eslint, 층의 경계를 보는 eslint-plugin-boundaries)와 Prettier, Vitest와 Testing Library와 MSW, Storybook, 실제 서버에 대고 도는 Playwright 시험이다. 결정 본문은 옮겨 적지 않고, 이 ADR은 이 저장소에서 다른 것만 적는다. 정확한 버전은 web 뼈대를 짓는 티켓이 그때 agent-os의 잠금 파일에서 옮겨 `tech.md`에 적는다.

## 이 저장소에서 다른 것

- **앱은 하나다.** agent-os의 위젯, 방문자용 페이지, 플러그인은 이 저장소에 없다. 워크스페이스에 두는 것은 관리자 페이지 앱 하나와 화면 부품 패키지 하나다. 상태 보관 라이브러리 Zustand는 쓰는 곳이 생길 때 들인다.
- **화면 부품은 복사한다.** agent-os의 부품 패키지(`web/packages/ui`. 색·글꼴·간격 값, 부품 열하나, 테마와 밀도)를 통째로 복사해 이 저장소의 `web/` 아래에 두고, 복사한 agent-os 커밋을 적어 둔다. 그 패키지는 agent-os의 다른 패키지나 앱을 가져다 쓰지 않는다(서브에이전트가 그 패키지를 Grep으로 봤다고 보고했다. 일지 "확인한 것"). 그 패키지에 없는 부품(표, 선택 목록, 체크 상자, 대화 상자, 파일 올리기, 잠깐 뜨는 알림, 페이지 넘김)은 브라우저가 기본으로 주는 요소(`<table>`, `<select>`, `<dialog>`, 파일 입력)에 같은 모양을 입혀 직접 짓는다. agent-os의 관리 화면에는 대화 상자, 선택 목록, 파일 올리기를 쓰는 곳이 아직 없어 본뜰 구현이 없다(이 세션이 그 저장소의 `web/apps/admin/components`를 봤다). 그 패키지가 직접 의존하는 바깥 패키지는 여섯이다. Tailwind CSS, 아이콘 lucide-react, 마크다운을 그리는 부품이 쓰는 react-markdown과 remark-gfm, 글꼴(Noto Sans KR, Noto Sans Mono)을 싣는 `@fontsource` 패키지 둘이다(이 세션이 그 패키지의 `package.json`을 읽었다). 통째로 복사하므로 여섯이 함께 든다. 인터뷰의 선택지 설명은 새로 드는 바깥 패키지를 "Tailwind와 아이콘(lucide)뿐"이라고 적었는데 그 설명이 틀렸다. 셀프 리뷰가 잡았고, ADR 승인 때 바로잡은 수로 다시 여쭈어 사용자가 "그대로 통째로 복사한다"를 골랐다(일지 "셀프 리뷰"와 "승인"). npm 레지스트리의 라이선스 칸은 Tailwind CSS, react-markdown, remark-gfm이 MIT, lucide-react가 ISC, 글꼴 패키지 둘이 OFL-1.1(글꼴에 쓰는 공개 라이선스)이다(이 세션이 2026-11-26에 `npm view`로 받았다. 본 버전은 그 패키지의 `package.json`이 적은 react-markdown 10.1.0, remark-gfm 4.0.1, 글꼴 패키지 5.3.0, lucide-react 1.51.0이고 Tailwind CSS는 4의 최신인 4.3.5다). web 뼈대를 짓는 티켓이 설치할 버전의 라이선스 원문을 확인해 `tech.md`에 적는다. 복사한 패키지의 이름(`@agent-os/ui`)은 이 저장소의 이름으로 바꾸고, 패키지 안에서 그 이름을 부르는 곳도 함께 고친다. 치르는 값은 부품 일곱 안팎을 직접 짓고 시험하는 것과, 복사본이라 agent-os가 고친 것이 저절로 따라오지 않는 것이다.
- **서버 계약 파일.** 이 저장소에는 커밋된 계약 파일(`openapi.json`)이 없다(ADR 0020 "제품 판의 번호가 보이는 자리"). web 뼈대를 짓는 티켓이 서버에서 계약 파일을 내보내 커밋하고, 서버와 같은지를 검사에 넣는다. 화면의 API 코드는 그 파일에서 만든다.
- **검사는 화면 사진 비교까지 둔다.** 린트, 타입 검사, 단위 시험, 만든 API 코드가 최신인지 보는 검사를 커밋 훅과 CI에 둔다. 브라우저가 실제 서버와 데이터베이스에 로그인해 화면을 눌러 보는 시험, 부품과 화면의 상태마다 두는 Storybook 견본, 견본마다 화면 사진을 찍어 저장소의 정답 사진과 한 점도 다르지 않은지 보는 사진 비교를 CI에 둔다. 사진 비교는 버전을 고정한 Playwright 컨테이너 이미지 안에서만 돈다. CI에 잡 셋(web, e2e, visual)이 늘고 필수 검사 `verify`가 그 결과를 모은다. agent-os의 2026-11-24 기록에서 세 잡이 걸린 시간의 가운데값은 4.5분, 1.6분, 7.5분이었고(실행 40개. 서브에이전트가 그 저장소의 `.scratch/harness/probes/README.md`를 읽었다고 보고했다), 부품 패키지의 정답 사진은 554장이었다(같은 서브에이전트가 `find`로 셌다고 보고했다). 이 세션의 추천은 브라우저 시험까지만 두고 Storybook과 사진 비교를 0.1 뒤로 미루는 것이었고, 사용자가 agent-os와 같게 전부를 골랐다.
- **이미지와 컨테이너.** 관리자 페이지는 Node 서버가 내므로 릴리스마다 이미지를 하나 더 낸다. 이름은 Docker Hub의 `njh6803/rag-engine-admin`이고 짓기 대상은 `admin`이다. 이미지는 release-image 명세의 규칙을 따른다. root가 아닌 사용자로 돌고, 번호를 빌드 인자로 넣으며, OCI 라벨 셋을 달고, 바탕 이미지를 digest(이미지 내용에서 나오는 고유한 식별 값)로 고정한다. 릴리스가 내는 이미지는 셋(검색 서버, 작업자, 관리자 페이지)이 되고, 소프트웨어 목록(SBOM)과 취약점 점검도 셋에 낸다. 단독 compose의 기본 컨테이너는 관리자 페이지가 더해져 여섯이 된다. 프록시가 관리 포트로 들어온 화면 요청을 이 컨테이너로 넘긴다(ADR 0025).
- **제품 변경의 범위.** 릴리스가 나는 계기인 제품 변경의 경로(ADR 0020)에 `web/`을 더한다. 화면만 고친 변경도 릴리스가 나야 운영자에게 닿기 때문이다. 그 아래에서 뺄 것(시험, 견본, 정답 사진)이 있는지는 명세가 정한다.
- **화면 그림을 명세 앞에 둔다.** 화면이 있는 기능은 명세를 쓰기 전에 화면을 그려 사용자에게 확인받고, 고른 그림을 `.scratch/<기능>/design/`에 둔다. 명세는 그 그림을 가리킨다. 이 절차는 agent-os의 그림 스킬(`ui-design`)과 그 계기 셋(디자인 폴더에 쓸 때 알리는 훅, `next-session` 결정표의 "화면 디자인" 줄, `docs/agents/issue-tracker.md`의 화면 디자인 절)을 옮겨 세운다. 그릴 때는 agent-os가 관리하는 디자인 시스템 아티팩트(Claude 아티팩트로 올린 색과 부품의 묶음)를 읽기만 해서 붙이고, 코드와 그 아티팩트를 맞추는 도구(agent-os의 `web/tools/sync-design-system`과 그 스킬)는 옮기지 않는다. 이 저장소가 새로 짓는 부품은 그 아티팩트에 없으므로 그림 안에 직접 그린다. 이 세션의 추천은 스킬을 옮기지 않고 그림 단계를 기능 계획에만 적는 것이었고, 사용자가 정식 절차로 두기를 골랐다. 옮기는 일은 하네스 티켓이 한다. 설계 PR은 `.claude/`와 `tools/`를 바꿀 수 없기 때문이다.

## Considered Options

사용자가 인터뷰에서 고르지 않은 안과, 이 세션의 추천과 다르게 고른 것이다. 선택지의 설명은 일지의 "물은 것과 답"에 글자 그대로 있다.

- **화면을 파일로 지어 내보낸다(React + Vite).** 이 세션의 추천이었다. 설치된 서버에서 Node가 돌지 않고, agent-os의 도구 대부분을 그대로 쓰되 Next만 빠진다. 사용자가 agent-os와 같은 Next를 골랐다. Next를 파일로만 내보내는 길은 `/documents/<문서 번호>`처럼 번호가 든 주소를 쓸 수 없다(Next 문서. 선택지의 설명에 적은 것이다).
- **파이썬 서버가 그린다(Jinja2 + htmx).** Node가 빌드에도 실행에도 필요 없고 이미지와 컨테이너가 늘지 않는다. 템플릿 안의 코드는 타입 검사가 보지 못하고(어림), agent-os와 도구가 완전히 달라진다. 고르지 않았다.
- **까다로운 부품만 공개 부품(Radix)을 쓰거나, 공개 라이브러리 하나(Ant Design, Mantine)를 통째로 쓴다.** 앞의 것은 직접 짓는 양이 줄지만 바깥 패키지가 하나 늘고 agent-os와 부품의 구현이 갈린다. 뒤의 것은 가장 빨리 짓지만 화면 모양이 agent-os와 달라진다. 고르지 않았다.
- **마크다운 부품은 빼고 복사한다.** ADR 승인 때 바깥 패키지의 수를 바로잡아 다시 여쭌 질문의 안이다. 마크다운 부품과 그것이 쓰는 react-markdown, remark-gfm을 복사하지 않아 바깥 패키지가 넷이 된다. 그 부품은 agent-os의 관리 화면에서도 쓰는 곳이 없다(이 세션이 그 저장소의 `web/apps/admin` 아래 `components`와 `app` 폴더를 찾아봤다). 대신 복사본이 agent-os의 부품 묶음과 한 군데 달라진다. 사용자가 통째로 복사하기를 골랐다.
- **검사를 브라우저 시험까지만 두거나, Storybook 견본까지만 둔다.** 앞의 것이 이 세션의 추천이었다. 화면 모양이 뜻하지 않게 달라진 것을 자동으로 잡지 못한다. 사용자가 사진 비교까지 전부를 골랐다.
- **그림 스킬을 옮기지 않고 그림 단계를 기능 계획에 적거나, 그림 없이 명세가 글로 적는다.** 앞의 것이 이 세션의 추천이었다. 사용자가 스킬을 옮겨 정식 절차로 두기를 골랐다.
- **이 저장소의 디자인 시스템 아티팩트를 따로 만들고 동기화 도구까지 옮긴다.** 새로 짓는 부품도 아티팩트에 실려 그림이 실제 코드와 같아진다. 부품 복사본이 먼저 있어야 해서 "명세 전에 그림"의 차례가 바뀌고, 옮길 하네스가 크게 는다(그 도구는 파일이 서른 개를 넘는다. 이 세션이 셌다). 고르지 않았다.

## Consequences

- **다른 ADR.** ADR 0007의 "프로세스와 이미지는 서버와 작업자 둘"과 기본 컨테이너의 수, ADR 0020의 이미지 둘(두 곳), 제품 변경으로 세는 것의 목록, "`web`과 `plugins`는 이 저장소에 없다", 기본 컨테이너 다섯, Docker Hub의 저장소 둘이 이 ADR로 바뀐다. 여덟 곳에 이 ADR을 가리키는 포인터를 단다.
- **헌법.** `docs/constitution/tech.md`의 "관리자 페이지" 칸과 루트를 나눈다는 문장을 이 결정에 맞게 고치고 헌법 버전을 문구 수정으로 올린다(1.5.9에서 1.5.10). 같은 문서의 컨테이너, 레지스트리, 점검 도구 칸은 지금의 사실(이미지 둘, 컨테이너 다섯, 포트 하나)을 적은 것이라 그것을 바꾸는 티켓이 고친다. 언어와 도구의 칸에 Node 쪽을 적는 일은 web 뼈대를 짓는 티켓이 한다.
- **저장소의 루트가 둘이 된다.** 파이썬(`src/`)과 노드(`web/`)다. 검사 러너와 커밋 훅, CI, `CLAUDE.md`의 레이어와 검증 명령, `README.md`, 경로별 규칙(`.claude/rules/`)에 웹 쪽이 더해진다. 그 일은 web 뼈대를 짓는 티켓이 한다.
- **사람 몫.** Docker Hub의 저장소 `rag-engine-admin`을 하나 더 만든다. 관리자 페이지 이미지를 처음 올리는 릴리스 전에 끝나 있어야 한다.
- **정답 사진과 Docker.** 정답 사진 수백 장이 저장소에 커밋되고, 모양을 일부러 고칠 때마다 Playwright 컨테이너 안에서 다시 찍어야 한다.
- **설치처의 부담.** Node 서버 컨테이너가 하나 더 돌아 메모리가 더 든다(어림이고 재지 않았다). Next와 Node의 보안 패치를 릴리스마다 따라가야 한다.
- **TypeScript는 5.x에 묶인다.** openapi-typescript 7.13.0이 `typescript ^5.x`를 요구한다. typescript-eslint 8.74.0은 `>=4.8.4 <6.1.0`을 요구하고, TypeScript의 최신은 7.0.2다(이 세션이 2026-11-26에 `npm view`로 npm 레지스트리에서 세 값을 받았다).
- **agent-os를 따라간다.** agent-os가 스택이나 부품을 고치면 이 저장소가 따라 옮겨야 한다. 그림은 agent-os의 디자인 시스템을 따르므로, 이 저장소의 부품 복사본이 원본과 달라져도 그림은 agent-os 쪽 모양이고, 웹에서 고친 디자인 값(색, 간격)을 이 저장소의 코드로 들이는 길은 없다.
- **원칙 III.** 이 ADR이 agent-os를 드는 것은 ADR 0016, 0020과 같이 하네스와 화면 도구의 원천으로서이고, MCP 클라이언트로서가 아니다.
- **명세가 정하는 것.** 워크스페이스 안의 폴더 배치와 패키지 이름, Dockerfile을 따로 둘지 한 파일의 대상으로 둘지, 커밋 훅에서 웹 검사가 도는 조건, e2e가 띄우는 서버와 데이터의 준비, 개발할 때 화면이 서버를 부르는 길, 티켓을 나누는 순서다.
