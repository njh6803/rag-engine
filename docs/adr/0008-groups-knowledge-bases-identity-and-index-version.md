# 문서는 그룹에 속하고 지식베이스는 그룹 집합 위의 색인이다. 문서는 (원천, 키)로 식별하고, 지식베이스마다 색인 판을 두며, 교체는 문서 단위와 지식베이스 판 전환이다

모델은 두 층이다. 문서는 **그룹** 하나에 속하고 접근 그룹과 원천은 그룹에 붙는다. **지식베이스**는 그룹 집합 위의 색인 하나이고 자기 임베딩 모델과 청킹 설정을 가진다. 같은 그룹이 지식베이스 둘에 들면 파싱은 한 번, 청킹과 임베딩은 지식베이스마다 한다. MCP 읽기 도구는 검색 `search`, 문서 정보 조회 `get_document`(식별자로 경로, 제목, 갱신일, 그룹, 조각 수와 원하면 전문), 지식베이스 목록 `list_knowledge_bases`(이름, 설명, 문서 수) 셋이다. 검색 도구는 인자 `knowledge_base`로 지식베이스를 고르고 없으면 기본 지식베이스를 쓴다. 첫 판은 기본 그룹 하나와 기본 지식베이스 하나다. 권한(누가 무엇을 보나)은 문서 소속의 문제이고 임베딩 모델과 청킹은 색인의 문제라서, 둘을 한 개념에 묶으면 모델을 바꾸려 할 때 그룹을 복제해야 한다.

문서의 식별은 **(원천, 원천 안의 키)** 쌍이고 내용 해시는 변경 감지에만 쓴다. 키는 서버 경로 원천이면 상대 경로, 업로드와 수집 API면 호출자가 준 키(없으면 파일 이름), SQL 원천이면 기본 키다. 같은 파일이 다른 경로에 있으면 문서 둘이다. 원칙 VI(문서마다 그 문서를 가진 원천 하나)를 식별에 그대로 쓴 것이고, 내용 해시를 식별로 쓰면 같은 파일 두 경로가 한 문서가 되어 한쪽을 지웠을 때 삭제 전파가 어긋난다. 업로드와 수집 API는 커넥터가 아니라 밀어 넣는 원천 종류이고, 그 문서도 원천 하나에 속한다.

색인 형식의 판(원칙 VII)은 **지식베이스마다 색인 판 레코드**다. 스키마 판, 임베딩 모델 ID와 차원, 청킹 설정의 해시, 토크나이저(Kiwi 모델) 판이 들고 조각 표가 그 판을 가리킨다. 요소마다 재색인 범위가 다르다. 모델, 차원, 청킹이 바뀌면 전체 재색인(파싱은 생략, 청킹부터), 토크나이저만 바뀌면 키워드 열만 다시 만들고 임베딩은 그대로, 스키마 판은 alembic이 올린다. 관리 API가 "이 지식베이스는 재색인 필요"를 보여 준다.

색인 교체는 **문서 단위 원자 교체**이고 모델이나 청킹의 교체는 **지식베이스 판 전환**이다. 문서의 새 판은 파싱, 청킹, 임베딩이 다 끝날 때까지 준비 상태에 모았다가 한 트랜잭션에서 옛 조각을 지우고 새 조각을 넣는다. 그 사이 검색은 옛 판을 그대로 본다. 재색인은 새 색인 판을 나란히 채운 뒤 지식베이스의 "현재 판" 포인터를 한 번에 바꾸고 옛 판을 지운다. 그래서 수집 중에 들어온 검색이 반쯤 바뀐 문서나 모델이 섞인 벡터를 보지 않는다.

## Considered Options

- 서버 전체를 지식베이스 하나로 본다: 임베딩 모델 하나에 묶이고 그룹마다 다른 청킹을 둘 수 없다.
- 그룹이 곧 지식베이스다(1:1): 모델을 바꾸려면 그룹과 접근 그룹을 복제해야 한다.
- 조각 단위 즉시 반영: 구현이 단순하지만 같은 문서의 옛 조각과 새 조각이 섞여 보이고 재색인 중 모델이 다른 벡터가 한 지식베이스에 섞인다(원칙 VI와 검색 품질 우선순위에 불리).
- 지식베이스 단위 블루/그린만: 문서 하나를 고치는 데도 전체 복사가 필요해 반영이 늦다.
- 설치 전체에 색인 판 하나: 지식베이스마다 모델이 다를 수 있다는 결정과 맞지 않는다.
- 판 없이 수동 재색인: 원칙 VII을 충족하지 못하고 섞인 벡터를 서버가 모른다.

## Consequences

- 저장은 두 번 커질 수 있다. 같은 그룹이 지식베이스 둘에 들면 조각이 지식베이스마다 있고, 재색인 동안 새 판과 옛 판이 나란히 있다.
- 큰 문서는 준비 상태가 길어진다. 작업 대기열(ADR 0009)의 작업이 문서의 판을 들고 간다.
- 접근 그룹으로 거르는 검색은 1.0 범위지만 조각 표의 그룹 칸은 처음부터 두고 채우기만 한다(`.scratch/plan-head.md`).
- 서버 경로 원천에서 파일을 옮기면 키가 바뀌어 삭제와 추가로 보인다.
