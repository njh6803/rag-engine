# 원천은 밀어 넣는 원천과 가져오는 원천으로 가르고, 수집 API는 원천 이름을 받으며, 서버 경로 원천은 붙인 부모 폴더 아래만 읽는다

core는 밀어 넣는 원천 `default` 하나만 두었다. 수집과 삭제의 유스케이스가 원천을 그 이름으로 고정해(`src/rag_engine/app/ingest.py`, `src/rag_engine/app/delete_document.py`), 그룹웨어와 위키가 같은 키 "123"으로 문서를 보내면 뒤에 온 문서가 앞 문서를 덮어쓴다. 원천을 만들고 고치는 관리 API와 서버가 스스로 읽어 오는 원천은 core 명세가 이 기능(source-sync)에 넘겼다. 설계 인터뷰(일지 `docs/journal/2026-11-20-2034-source-sync-design.md`)가 원천이 무엇이고 문서의 주인이 누구인지를 아래처럼 정했다. 동기화가 언제 어떻게 도는지는 ADR 0022가 정한다.

## 원천의 갈래

원천은 문서가 들어오는 방식에 따라 둘로 가른다(이름은 `GLOSSARY.md`).

- **밀어 넣는 원천**은 다른 시스템이나 사람이 문서를 보내 주는 원천이다. 운영자가 관리 API로 `groupware`, `wiki`처럼 시스템마다 하나씩 만든다. 보내는 프로그램은 수집 API의 원천 이름 칸(`source`)에 그 이름을 적는다. 같은 키라도 원천이 다르면 서로 다른 문서로 남고, 원천마다 문서 수와 실패를 따로 보며, 연동을 끊을 때는 그 원천만 지우면 된다. 원천 이름을 적지 않으면 지금처럼 `default`에 들어가므로 지금 쓰는 방법은 그대로다. 칸을 더하는 것이라 수집 API의 버전은 v1 그대로다(원칙 VII). 사람이 관리자 페이지에서 올리는 파일은 `upload` 원천에 따로 모으고, 이 원천은 `default`와 함께 `migrate`가 만들어 둔다.
- **가져오는 원천**은 이 서버가 커넥터로 문서 목록을 받아 스스로 읽어 오는 원천이다. 0.1에는 서버 경로 하나가 들고 1.0에 SQL 원천이 온다(ADR 0012). 커넥터 인터페이스는 ADR 0012가 정한 모양(인터페이스 버전, 목록, 가져오기, 연결 확인)대로 이 기능이 처음 코드로 짓고, 서버 경로 커넥터가 그 첫 구현이다.

## 문서의 주인

- **수집 API는 밀어 넣는 원천의 문서만 넣고 지운다.** 가져오는 원천의 이름을 적어 보낸 요청은 거부한다. 문서마다 그 문서를 가진 원천이 하나이고(원칙 VI), 가져오는 원천의 문서는 원천의 목록이 진실이라 밖에서 넣거나 지워도 다음 동기화가 되돌리기 때문이다.
- **그룹.** 가져오는 원천은 만들 때 그룹 하나를 정하고 그 원천의 문서는 모두 그 그룹에 속한다. 밀어 넣는 원천은 지금처럼 요청마다 그룹을 적고, 적지 않으면 기본 그룹이다. ADR 0008이 "원천은 그룹에 붙는다"고 적은 것은 가져오는 원천에만 해당하게 된다. 밀어 넣는 원천까지 그룹 하나에 묶으면 지금 `default` 원천에 그룹을 골라 보내는 요청의 뜻이 바뀐다.
- **원천을 지우면 그 원천의 문서도 함께 임시 삭제한다.** 지우는 순간 그 원천의 문서가 모두 검색에서 빠지고, 보관 기간(기본 30일, ADR 0013)이 지나면 정리 작업이 문서와 원천을 완전히 지운다(그 원천에 딸린 삭제 기록도 함께 지운다. ADR 0022 "정리 작업"). 원칙 VI(원천에서 지운 문서는 색인에서도 지운다)를 원천 단위로 그대로 적용한 것이다. 가져오는 원천을 잠깐 쉬게 하려는 것이면 지우지 않고 일시 중지를 쓴다(ADR 0022. 밀어 넣는 원천에는 일시 중지가 없다).
- **지운 원천은 아무것도 받지 않는다.** 지운 순간부터 그 원천으로는 새 문서가 들어오지 않고, 그 원천의 문서를 하나씩 되살리는 요청도 받지 않으며, 동기화도 시작하지 않는다. 지금 수집은 지운 문서가 같은 키로 다시 들어오면 되살리므로(`src/rag_engine/app/ingest.py`의 `_amend`. 이 세션이 읽었다), 막지 않으면 지운 원천 아래에 살아 있는 문서가 생기고 보관 기간 뒤의 정리 작업이 그 문서를 지우거나 원천을 지우지 못한다.
- **지운 원천은 보관 기간 안에 관리 API로 되살린다.** 호출 하나로 원천을 되돌리면 원천과 함께 지워졌던 문서가 같이 검색에 돌아오고, 그사이 색인 판이 바뀌지 않았으면 임베딩을 다시 하지 않는다. 가져오는 원천은 되돌린 뒤의 동기화가 그사이 폴더에서 바뀐 것을 다시 맞춘다. 원천과 함께 지워진 문서와 그 전에 따로 지운 문서를 가르는 표시를 남기고, 그 전에 따로 지운 문서는 원천을 되살려도 돌아오지 않는다. 가져오는 원천의 문서를 하나씩 되살리지 않는다는 아래 결정과 부딪치지 않는다. 그 결정의 까닭은 원천에 없는 문서를 되살려도 다음 동기화가 다시 지운다는 것인데, 원천과 함께 지워진 문서는 원천에서 사라져서 지워진 것이 아니다.
- **관리 API의 되살리기는 밀어 넣는 원천의 문서에만 연다.** 업로드와 수집 API로 넣었다가 지운 문서는 보관 기간 안에 관리 API 호출 하나로 되살린다. 보관해 둔 조각을 되돌리고, 그사이 색인 판이 바뀌었으면 보관해 둔 원본으로 다시 색인한다. 가져오는 원천의 문서는 API로 되살리지 않는다. 원천에 없는 문서를 API로 되살려도 다음 동기화가 다시 지우기 때문이고, 원천 폴더에 파일을 되돌려 놓으면 다음 동기화가 되살린다.

## 서버 경로 원천의 폴더

단독 compose에서 운영자는 `.env`에 서버 기계의 폴더 하나를 적는다. 그 폴더가 서버와 작업자 컨테이너의 `/sources`에 읽기 전용으로 붙고, 원천을 만들 때는 그 아래 하위 폴더 이름만 적는다(예: `규정집`). 서버는 `/sources` 밖의 경로를 원천으로 받지 않고, 원천 폴더 안의 심볼릭 링크(다른 파일을 가리키는 바로 가기)도 따라가지 않는다. 밖인지는 적은 글자가 아니라 그 값을 `/sources`에 이어 붙였을 때 실제로 가리키는 자리로 가른다. 그래서 위 폴더로 올라가는 `..`가 든 값과 `/`로 시작하는 절대 경로를 받지 않고, 원천으로 적은 하위 폴더 자체나 거기까지 가는 길의 폴더가 심볼릭 링크여도 받지 않는다. 이 확인은 원천을 만들거나 고칠 때 한 번으로 끝내지 않고 동기화가 돌 때마다 다시 하며, 걸리면 그 동기화는 문서를 읽지도 지우지도 않고 실패로 남긴다(원천을 만든 뒤에도 서버 기계에서 그 폴더를 링크로 바꿔 놓을 수 있다). 이 세 문장은 승인 뒤에 PR 직전 리뷰가 낸 길을 막느라 풀어 적은 것이다(일지의 PR 직전 리뷰 절). 관리 API가 받은 경로를 그대로 읽게 두면 관리 토큰을 가진 쪽이 컨테이너 안의 다른 파일을 문서로 색인해 검색으로 읽어 낼 수 있기 때문이다. 원천을 더할 때 compose 파일을 고치지 않는다. 공유 폴더(NFS, SMB)는 운영자가 서버 기계에서 그 부모 폴더 아래에 붙인다.

컨테이너가 뜬 뒤에 새로 붙인 공유 폴더는 Docker의 기본 설정에서 컨테이너에 보이지 않을 것으로 본다. Docker에는 전파 설정(컨테이너에 붙여 준 폴더 안에 나중에 또 붙인 폴더가 반대쪽에도 보이게 할지를 정하는 설정, mount propagation)이 있고, Docker 문서는 그 기본값 `rprivate`가 나중에 붙인 폴더를 어느 쪽으로도 전하지 않는다고 적는다. 보이지 않을 것이라는 말은 그 정의에서 끌어낸 어림이고 재 보지 않았다. 전파 설정은 리눅스 서버에서 서버 기계의 폴더를 컨테이너에 그대로 붙이는 방식(bind mount)에서만 바꿀 수 있고 Docker Desktop에서는 동작하지 않는다고 그 문서가 적는다(서브에이전트가 `docker/docs`의 `bind-mounts.md` 원문을 받아 봤다. 일지 "확인한 것"). 전파 설정으로 풀리는지는 명세가 재고, 풀리지 않으면 "공유 폴더를 붙인 뒤 서버와 작업자를 다시 띄운다"를 설치 안내에 적는다(바뀜: 이력 2026-11-21 "전파 설정을 쟀고, compose에는 넣지 않고 설치 안내에 다시 띄우기를 적는다").

## 이번에 짓지 않는 것

- **변환 인터페이스.** 변환(ADR 0003의 플러그인 자리 셋 가운데 하나)의 메서드 모양과 수집 파이프라인에 변환 단계를 끼우는 일은 core 명세가 이 기능에 넘겼으나, 이 기능은 짓지 않고 SQL 원천(db-source)의 설계로 넘긴다. 0.1에는 변환 자리가 없다. 0.1에서 설치처가 자기 규칙(본문에 섞인 HTML 정리, 암호화된 첨부 풀기 같은 것)을 끼울 길은 고친 문서를 수집 API로 직접 보내는 것뿐이다. 변환을 처음 쓰는 곳이 1.0의 SQL 원천이고, 한번 낸 인터페이스는 버전을 올려야만 모양을 바꿀 수 있어서다.
- **연결 정보의 암호화 보관.** 원천 설정에는 비밀 값을 넣는 칸을 두지 않는다. 0.1의 서버 경로 원천에는 비밀번호가 필요 없고(공유 폴더의 계정은 서버 기계가 폴더를 붙일 때 쓴다), 처음 쓰는 곳이 SQL 원천이다. 암호화 방법과 열쇠 관리는 db-source의 설계가 정한다. 0.1의 운영자는 암호화 열쇠를 만들고 백업할 일이 없다. 설치처가 직접 만든 커넥터에 토큰이 필요하면 0.1에서는 그 커넥터가 환경 변수나 비밀 파일에서 읽는다.
- **수집 전용 토큰.** 토큰의 역할은 지금의 둘(`admin`, `reader`) 그대로다(`src/rag_engine/domain/entities.py`의 `TokenRole`을 이 세션이 읽었다. 토큰에 역할 칸을 둔 결정은 ADR 0014다). 0.1에서는 문서를 보내는 시스템에 관리 토큰을 넣어 줘야 하고, 그 토큰이 새면 토큰 발급과 모든 문서의 삭제까지 열린다. 수집 전용 토큰은 관리자 페이지 기능(admin)의 설계로 넘긴다(바뀜: ADR 0024).

## Considered Options

사용자가 인터뷰에서 고르지 않은 안과, 이 세션의 추천과 다르게 고른 것이다. 선택지의 설명은 일지의 "물은 것과 답"에 글자 그대로 있다.

- **밀어 넣는 원천을 업로드와 수집 API 둘로 고정하거나, 지금처럼 하나로 둔다.** 서로 다른 시스템의 같은 키가 한 문서로 겹친다. 고르지 않았다.
- **원천을 지울 때 문서가 남아 있으면 거부하거나, 원천만 지우고 문서는 남긴다.** 앞의 것은 운영자가 문서를 하나씩 지워야 하고, 뒤의 것은 주인 없는 문서가 계속 검색된다(원칙 VI). 고르지 않았다.
- **지운 원천을 되돌리는 길을 두지 않는다.** 만들 것이 가장 적지만, 실수로 지운 원천을 새로 만들어 문서를 다시 보내거나 다시 동기화해야 하고 임베딩을 처음부터 다시 한다(수만 건이면 몇 시간이 걸릴 수 있다는 것은 재지 않은 어림이다). 보관해 둔 조각은 쓰이지 않고 기간이 지나면 지워진다. 고르지 않았다.
- **모든 문서를 관리 API로 되살리거나, 되살리는 API를 두지 않는다.** 앞의 것은 가져오는 원천에서 되살린 문서를 다음 동기화가 다시 지우고, 뒤의 것은 실수로 지운 업로드 문서를 같은 파일로 다시 올려야만 되살린다. 고르지 않았다.
- **원천 폴더마다 compose 파일에 붙이는 줄을 더한다.** 폴더가 서버 기계의 여러 곳에 흩어져 있어도 붙일 수 있지만, 원천을 더할 때마다 파일을 고치고 다시 띄워야 하며 어떤 경로든 붙일 수 있어 경계가 운영자의 주의에 달린다. 고르지 않았다.
- **변환을 문서 하나를 받아 하나를 돌려주거나 넣지 않는다고 답하는 모양으로 지금 짓는다.** 이 세션의 처음 추천이었다(선택지 "문서 하나를 하나로"). 파서와 같은 자식 프로세스에서 돌리고, 하나를 여럿으로 나누는 일은 db-source가 메서드를 더하는 안이다. 사용자가 "이번에는 짓지 않는다"를 골랐다. 처음부터 하나를 여럿으로 돌려주게 하는 안도 고르지 않았다.
- **연결 정보의 암호화 보관을 지금 짓거나, 비밀을 데이터베이스에 두지 않고 이름만 적는다.** 앞의 것은 0.1에 그 장치를 쓰는 내장 원천이 없는데 운영자가 열쇠를 백업해야 하고, 뒤의 것은 관리자 페이지에서 비밀번호를 넣거나 바꿀 수 없다. 고르지 않았다.
- **수집 전용 역할(`ingest`)을 더하고 토큰을 원천 하나에 묶는다.** 이 세션의 추천이었다. 한 시스템의 토큰이 새어도 다른 원천의 문서와 토큰 발급에 닿지 못한다. 사용자가 "지금처럼 관리 토큰으로"를 골랐다. 원천에 묶지 않고 수집 전용 역할만 더하는 안도 고르지 않았다.
- **원천의 두 갈래를 "받는 원천, 읽어 오는 원천"이나 "밀어 넣는 원천, 커넥터 원천"으로 부른다.** 앞의 것은 ADR 0008과 0012가 이미 쓰는 "밀어 넣는"을 바꿔야 하고, 뒤의 것은 용어집이 원천을 커넥터라고 부르지 말라고 한 것과 헷갈린다. 고르지 않았다.

## Consequences

- 원천 표가 바뀌어 마이그레이션이 생기고, 그 PR의 제목에는 느낌표가 붙는다(ADR 0020). 갈래를 적는 칸(`kind`)은 이미 있어 받는 값만 늘고(지금은 `push` 하나만 받는다. 이 세션이 `src/rag_engine/adapters/postgres/tables.py`를 읽었다), 커넥터의 이름과 설정, 그룹, 지운 시각 같은 칸이 새로 든다. 단독 compose의 서버와 작업자에 볼륨 하나를 더하는 PR에 느낌표를 붙일지는 같은 ADR의 기준으로 가른다.
- 관리 API에 원천 만들기, 보기, 고치기, 지우기, 지운 원천 되살리기, 연결 확인(커넥터의 `check()`), 밀어 넣는 원천의 문서 되살리기가 더해진다. 관리 명령은 더하지 않는다. `ingest <경로>` 명령은 지금처럼 `default` 원천에 한 번 넣는 명령으로 남는다.
- 서버 경로 원천의 키는 상대 경로라(ADR 0008) 파일을 옮기거나 이름을 바꾸면 옛 문서를 지우고 새 문서를 넣은 것으로 본다.
- 명세가 재거나 정하는 것: Docker의 전파 설정으로 나중에 붙인 공유 폴더가 보이는지, 원천 설정 가운데 만든 뒤 바꿀 수 있는 것(폴더와 그룹), 지운 원천의 이름을 보관 기간 동안 다시 쓸 수 있는지, 없는 원천이나 지운 원천의 이름을 적은 수집 요청의 오류 코드, 원천을 지우는 순간 대기 중이거나 돌고 있던 그 원천의 작업을 거두는 방법, 원천과 함께 지워진 문서를 가르는 표시의 모양.

## 이력

### 2026-11-21 전파 설정을 쟀고, compose에는 넣지 않고 설치 안내에 다시 띄우기를 적는다

명세(`.scratch/source-sync/spec.md`의 "단독 compose와 설치 안내" 절)가 쟀고 사용자가 골랐다. 본문은 전파 설정으로 풀리지 않을 때만 "다시 띄운다"를 설치 안내에 적는다고 했다. 재 보니 전파 설정으로 풀리기는 했으나 문제 둘이 따라와서, 풀리는데도 compose에는 넣지 않고 설치 안내에 "공유 폴더는 서버를 띄우기 전에 붙이고, 띄운 뒤에 붙였거나 떼었다 다시 붙였으면 서버와 작업자를 다시 띄운다(`docker compose restart server worker`)"를 적는다.

잰 것은 다음과 같다(`.scratch/source-sync/probes/mount-propagation/probe_out.txt`. 괄호의 수는 그 출력의 단계 번호다. 개발 PC의 Docker Desktop 안에 띄운 리눅스 Docker에서 쟀고, 공유 폴더는 메모리 파일 시스템으로 흉내 냈다).

- 기본 설정으로 띄운 컨테이너에는 뜬 뒤에 붙인 하위 폴더의 파일이 보이지 않았다(2). 본문의 어림대로다.
- `rslave`로 띄운 컨테이너에는 보였다(2). 그런데 서버 기계의 루트가 shared가 아닐 때는 `rslave`로 컨테이너가 뜨지 않았고(0), 읽기 전용으로 붙였는데도 나중에 전해진 폴더에는 쓰기가 됐다(3). 뒤의 것은 본문의 "`/sources`에 읽기 전용으로 붙고"를 지키지 못한다.
- 기본 설정으로 떠 있던 컨테이너를 폴더를 붙인 뒤에 `docker restart`로 다시 띄우면 그 폴더가 보였고 쓰기는 막혔다(4). 떼었다 다시 붙인 폴더는 다시 띄운 뒤에야 새 내용이 보였다(5, 6).
- Docker Desktop에서 `rslave`를 적어 띄워도 오류 없이 떴다(8, 종료 코드 0). 본문이 든 Docker 문서의 "동작하지 않는다"는 띄울 때 오류가 난다는 뜻이 아니었다. Docker Desktop에서 나중에 붙인 폴더가 실제로 전해지는지는 재지 않았다.
- 단독 compose가 붙일 모양(짧은 문법, `.env`의 변수, 서버와 작업자 두 서비스, uid 10001)에서 설치 안내가 적을 명령 `docker compose restart server worker`로 다시 띄워도 `docker restart`와 결과가 같았다. 뜬 뒤에 붙인 폴더는 다시 띄운 뒤에 두 컨테이너에 보였고 쓰기는 막혔으며, 떼었다 다시 붙인 폴더는 다시 띄운 뒤에 새 내용이 보였다(9).
- 설치 폴더에 `sources/`가 없고 변수도 적지 않았을 때 `docker compose up`은 종료 코드 0으로 끝났고, Docker가 그 폴더를 root의 것(권한 755)으로 만들었으며, uid 10001로 도는 두 컨테이너가 그 빈 폴더를 읽었다(10). 이 기능이 없던 묶음에서 올라온 설치가 손대지 않고도 뜬다는 근거다.

사용자가 고르지 않은 안은 둘이다(선택지의 글은 일지 `docs/journal/2026-11-21-1358-source-sync-spec.md`의 "물은 것과 답"에 글자 그대로 있다). compose에 `rslave`를 넣어 다시 띄우지 않아도 보이게 하는 안은 위의 문제 둘을 그대로 안는다. `.env`의 변수로 둘 가운데 고르게 하는 안은 운영자가 그 차이를 알고 골라야 한다.

재지 않은 것도 있다. 실제 NFS·SMB 공유 폴더에서는 재지 않았고, 배포판 리눅스 서버의 커널에서도 재지 않았다(명세의 같은 절).
