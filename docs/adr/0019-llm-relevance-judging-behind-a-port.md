# LLM은 검색 평가의 관련성 판정에만 쓰고, 판정기는 포트 뒤의 Claude 어댑터이며, 기본은 꺼짐이다

PRD는 "답 생성(LLM 호출)"을 만들지 않는 것으로 적어 왔고 이 서버에는 LLM 의존이 없었다. search-eval 설계 인터뷰에서 사용자가 검색 평가에 LLM 관련성 판정을 더하고 그 코드를 제품 코드에 두기로 골랐다. 그래서 경계를 다시 긋는다. 이 서버는 여전히 답을 만들지 않고, 검색 요청을 처리하는 길에서는 LLM을 부르지 않는다. LLM은 검색 평가에서 질의와 검색된 조각 한 쌍이 관련 있는지를 판정하는 데만 쓴다.

- **구조.** 판정기 포트는 `domain`의 Protocol이고 Claude 구현은 `adapters`에 둔다. 평가 유스케이스는 포트만 부르고, 검색 유스케이스는 판정기를 받지 않는다. `app`과 `domain`의 import 금지 목록에 `anthropic`을 더한다. 이번 구현은 Claude 하나이고, 다른 제공자와 로컬 모델은 같은 포트에 나중에 붙인다. 이 포트는 ADR 0007의 `domain` 포트이고 ADR 0003의 플러그인 자리 셋(커넥터, 변환, 파서)에 들지 않는다. 판을 붙여 밖에 여는 인터페이스가 아니며, 다른 제공자의 구현도 이 저장소의 `adapters`에 더한다.
- **SDK.** Anthropic 공식 SDK `anthropic`을 운영 의존성으로 선언해(`>=2.8,<3`) 지금부터 제품 이미지에 싣는다. 2.8.0은 Apache-2.0이고 `py.typed`가 있다(쟀다. 프로브 `.scratch/search-eval/probes/llm-sdk/pypi_anthropic.py`). 새로 드는 패키지는 anthropic, docstring-parser, jiter, sniffio 넷이다(손으로 봤다. `uv pip install --dry-run "anthropic>=2.8,<3"`. 프로브 폴더의 README에 적었다). 전이 의존 셋의 라이선스는 docstring-parser와 jiter가 MIT, sniffio가 MIT와 Apache-2.0 가운데 고르는 것이다(쟀다. 프로브 `.scratch/search-eval/probes/llm-sdk/pypi_transitive_licenses.py`). 판정기 어댑터의 꼴로 쓴 코드는 anthropic 2.8.0에서 pyright strict를 오류 0으로 지난다(쟀다. 프로브 `.scratch/search-eval/probes/llm-sdk/judge_adapter_types.py`. 호출은 하지 않았다).
- **모델.** 판정 모델은 설정값이고 Claude Opus 5.5(`claude-opus-5-5`)로 시작한다. 보고서에 판정 모델을 적는다. 더 싼 모델의 판정이 이것과 충분히 일치하면 그때 설정을 낮춘다.
- **나가는 조건.** 설치처에서는 기본이 꺼짐이다. 끝점 주소, 모델, 키 설정이 모두 있을 때만 판정기를 조립하고, 없으면 평가는 API를 부르지 않고 LLM 숫자를 건너뛴다. 조각과 질문은 설치처가 직접 적은 주소로만 간다. 키는 환경 변수나 비밀 파일로만 받고, 키와 판정 요청·응답의 본문은 로그에 남기지 않는다(원칙 V). 지식베이스마다 따로 허용하는 장치는 admin 설계에 넘긴다.
- **숫자.** 조각마다 관련 있음과 없음만 판정한다. 보고서에 숫자 둘을 싣는다. 첫째는 상위 10개 조각 가운데 LLM이 관련 있다고 본 비율이다. 둘째는 기대 근거에 닿은 조각을 LLM도 관련 있다고 본 비율이고, 판정기를 믿을 만한지 보는 점검 숫자다. 기대 근거에 없는데 LLM이 관련 있다고 본 조각은 "빠진 정답 후보" 목록으로 따로 내고, 사용자가 확인한 것만 기대 근거에 더한다. 이 목록이 놓친 까닭의 초벌 판정과 빠진 정답 찾기의 입력이다(ADR 0018).
- **도는 곳과 결정성.** 이 저장소의 평가에서는 API를 개발자가 로컬에서 수동으로 돌릴 때만 부른다. 판정 결과(어느 질문과 어느 조각에 어떤 판정이 났는지, 판정 모델, 지시문의 판, 날짜)를 파일로 커밋하고, CI는 키 없이 그 파일만 읽어 숫자를 낸다. 판정기 없이 저장된 판정으로 숫자를 내는 것이라 위의 건너뛰기와 부딪치지 않는다. 건너뛰는 것은 판정기도 저장된 판정도 없을 때다. 파일에 없는 조합은 "판정 없음"으로 세어 그 비율을 보고서에 적는다. 판정 모델로 고른 Opus 5.5에는 `temperature` 같은 샘플링 인자를 쓸 수 없다. 스킬 문서의 이주 안내는 Opus 5 절에서 샘플링 인자가 계속 거부된다고 적고 Opus 5.5 절은 그 절 위에 얹어 읽으라고 적으며, Sonnet 5와 Haiku 5.5는 기본값이 아닌 값을 거부한다고 적는다(`claude-api` 스킬 문서의 `shared/model-migration.md`와 `shared/models.md`를 읽었다. Claude Code 2.1.321에 실린 판이다. 호출로 재지 않았다). 그래서 결정성은 판정을 저장해 다시 쓰는 것으로 얻는다. 지시문에 판 번호를 두고, 판이 바뀌면 옛 판정은 쓰지 않는다.
- **비용.** 한 구성을 한 번 잴 때 판정은 약 3,000건이고(질문 150, 질의 목록 2, 상위 10) Opus 5.5로 약 26달러, 배치로 약 13달러다(어림). 설정 실험처럼 구성을 여럿 재면 구성마다 새 조각이 나오는 만큼 는다. API를 부르는 실행은 예상 건수와 비용을 보이고 사용자가 승인한 뒤에 한다. 키는 사용자가 직접 환경 변수에 두고 에이전트는 키를 다루지 않는다.

사용자가 2026-11-12 search-eval 설계 인터뷰에서 골랐다(`docs/journal/2026-11-12-2108-search-eval-design.md`).

## Considered Options

- 제품 이미지 밖의 평가 도구에만 둔다(처음 추천): 제품에 LLM 의존이 없고 PRD를 고치지 않는다. 사용자가 제품 코드 안의 구현을 골랐다.
- SDK를 선택 의존성으로 두고 입구가 열릴 때 이미지에 싣는다(추천): 쓰이지 않는 패키지가 이미지에 없다. 사용자가 지금부터 싣기를 골랐다. 설치 모양이 하나라 단순하다.
- 제공자를 설정으로 고르는 호환 끝점: 기준을 세울 판정 모델이 설치마다 달라진다. 포트가 있어 나중에 붙일 수 있다.
- Sonnet 5.5나 Haiku 5.5로 시작한다: 싸지만, 가장 정확한 모델로 기준을 세운 뒤 낮추는 순서를 골랐다.
- CI에서 API를 부른다: 키를 CI에 두어야 하고 PR마다 비용이 들며 숫자가 실행마다 달라질 수 있다.

## Consequences

- `docs/PRD.md`의 "무엇을 안 만드나"와 `docs/constitution/tech.md`의 스택 표를 고친다.
- 이번 범위는 제품 이미지의 명령이나 관리 API로 평가를 열지 않는다. 그래서 이미지에 실린 SDK와 판정기는 admin이 입구를 열 때까지 이미지 안에서 쓰이지 않고, release-image의 부품 목록과 취약점 스캔의 대상은 지금부터 는다.
- 재지 않은 것은 실제 호출이다. 요청과 응답이 실제 API에서 프로브의 꼴대로 도는지는 키와 비용이 들어 재지 않았고, 사용자가 비용을 승인한 뒤 첫 구현 티켓이 잰다. 돌지 않으면 이 ADR로 돌아온다.
- 판정 모델이 바뀌었을 때 옛 판정을 어떻게 다루는지와, 끊긴 실행을 이어 갈 때 이미 판정한 조합을 건너뛰는 규칙은 명세가 정한다. 이어 가는 실행이 판정 파일에 있는 조합을 다시 부르면 같은 비용을 두 번 쓴다.
- import 금지 목록이 열일곱이 된다. `pyproject.toml`의 계약과 `CLAUDE.md`의 "열여섯"은 구현 티켓이 고친다.
- 판정의 정확도를 사람 표본과 맞춰 보는 일이 따로 필요하다.
- 판정 파일에서 조각을 가리키는 값은 명세가 정한다. 조각 식별자는 색인할 때 새로 생기므로 조각 글에서 낸 값이어야 한다. 질의를 가리키는 값도 명세가 정한다. 질의의 글이 바뀌면 그 질의의 옛 판정은 새 글에 다시 쓰지 않고 판정 없음으로 세어야 한다.
- CI는 LLM을 부르지 않으므로 ADR 0016의 "LLM을 부르는 테스트가 없고"는 그대로다.
