# 삭제는 소프트 삭제 뒤 보관 기간이 지나면 물리 삭제하고, 원본은 파일 저장소 포트 뒤의 볼륨에 둔다

원천에서 지운 문서는 색인에서도 지운다(원칙 VI). 그 지움의 모양이다. 처음 추천은 물리 삭제와 묘비 행이었으나 사용자가 소프트 삭제를 골랐다. 삭제하면 문서 행에 `deleted_at`을 적고, 조각(본문, 벡터, 키워드 값)을 검색 표에서 보관 표로 옮겨 검색 표에는 산 것만 남긴다. 원본 파일은 보관 기간 동안 둔다. `RAG_DELETED_RETENTION_DAYS`(기본 30) 뒤에 작업 대기열의 정리 작업이 보관 표의 조각과 원본을 지우고 내용 없는 묘비 행만 남긴다(바뀜: ADR 0022). 검색에서는 즉시 빠지므로 원칙 VI는 지키면서, 실수 삭제나 원천의 오동작(비어 버린 열거)에서 되살릴 창을 둔다. 검색 표에 산 것만 두어 검색 SQL에 삭제 필터가 없고, 옮겨 간 조각이 남긴 죽은 튜플은 PostgreSQL의 vacuum이 치운 뒤 벡터 색인에서도 빠진다(그때까지 색인에 죽은 튜플이 머무는 것은 PostgreSQL 일반의 동작이다)(바뀜: 이력 2026-11-21 "검색은 지운 원천의 조각을 결과에서 뺀다").

원본은 `BlobStore` 포트(ADR 0007) 뒤의 로컬 볼륨에 둔다. 설정 `RAG_DATA_DIR` 아래 `blobs/<문서 UUID>`이고, 데이터베이스에는 경로, 크기, sha256, MIME만 둔다(바뀜: 이력 2026-11-10 "원본은 문서 UUID 디렉터리 아래에 수집 요청마다 새 이름으로 둔다"). 서버와 작업자가 같은 볼륨을 공유한다. 서버 경로 원천은 원본이 그 경로에 이미 있으므로 복사하지 않고 경로만 가리킨다. S3 호환 저장소는 나중에 같은 포트의 어댑터로 더한다. 원본이 있어야 파서 판이 올랐을 때 다시 파싱하고, 보관 기간 동안 되살리며, ADR 0002의 백업 대상("원본 문서")이 된다.

## Considered Options

- 물리 삭제와 묘비 행만(처음 추천): 단순하지만 되살릴 길이 없다.
- 소프트 삭제 플래그만 두고 조각은 제자리: 검색 SQL마다 필터가 들고 벡터 색인에 죽은 행이 남아 k개 채우기가 느려진다.
- 지식베이스 단위 블루/그린으로 삭제 반영: 문서 하나 지우는 데 전체 전환이 필요하다.
- 원본을 PostgreSQL bytea로: 백업이 하나지만 PDF 수천 개면 데이터베이스가 수십 GB가 되어 덤프·복원·복제가 느려지고 한 값의 한도가 1GB다.
- 서버 경로 원천까지 모두 복사: 디스크가 두 배이고, 원천에서 지우면 색인도 지운다는 원칙 VI 아래서 사본을 들고 있을 까닭이 약하다.

## Consequences

- 백업은 PostgreSQL 덤프와 `RAG_DATA_DIR` 둘이다. ADR 0002가 백업 대상을 "데이터베이스 하나와 색인, 원본 문서"로 적은 것과 같다.
- 서버 경로 원천의 문서는 사본을 들지 않으므로(Considered Options의 마지막 안을 거부한 값), 원천 파일이 지워진 뒤에는 보관 표의 조각으로 되살릴 수는 있어도 다시 파싱할 수는 없고, `RAG_DATA_DIR` 백업에도 그 파일은 들지 않는다. 그 파일의 백업은 원천 서버의 몫이다.
- compose에 볼륨 하나가 더 들고 서버 복제본이 여럿이면 볼륨을 공유해야 한다.
- 보관 중인 문서를 되살리는 관리 API와 정리 작업의 주기는 명세가 정한다(바뀜: ADR 0021)(바뀜: ADR 0022).
- 같은 (원천, 키)가 보관 기간 안에 다시 들어오면 새 문서가 아니라 되살림인지는 명세가 정한다(어림: 되살린 뒤 갱신으로 처리).

## 이력

### 2026-11-10 원본은 문서 UUID 디렉터리 아래에 수집 요청마다 새 이름으로 둔다

명세(`.scratch/core/spec.md`의 수집 파이프라인 절)가 정했다. 수집 요청이 저장하는 원본의 경로는 `RAG_DATA_DIR/blobs/<문서 UUID>/<원본 UUID>`이고, `<원본 UUID>`는 수집 요청마다 새로 만든다. 본문의 `blobs/<문서 UUID>`는 파일 하나가 아니라 그 문서의 원본들이 드는 디렉터리다. 갱신의 새 원본이 옛 원본을 덮지 않아 옛 원본을 읽던 작업자가 반쯤 바뀐 파일을 읽지 않고, 같은 문서에 같은 내용을 동시에 넣는 두 요청이 서로 다른 경로에 써서 한쪽의 정리가 다른 쪽이 커밋한 원본을 지우지 않는다. 문서 행이 지금 원본의 경로를 가지므로 데이터베이스에 경로, 크기, sha256, MIME만 둔다는 본문은 그대로다. 수집 요청이 저장한 원본 가운데 문서 행이 가리키지 않는 것(바뀌어 물러난 옛 원본, 문서 행이 가리키지 않은 새 원본)은 작업 단위가 끝난 뒤 지우고(최선 노력), 지우지 못한 고아 원본은 source-sync의 정리 작업이 받는다. 서버 경로 원천의 원본은 본문대로 복사하지 않으므로 이 경로 규칙 밖이다.

고르지 않은 안: 문서 UUID를 파일 이름으로 두는 본문의 모양은 갱신이 같은 파일을 덮어 옛 원본을 읽던 작업자와 경쟁한다. 내용 해시를 이름으로 두는 안은 같은 문서의 같은 내용에 늘 같은 경로를 주어, 같은 내용을 동시에 넣는 두 요청 가운데 한쪽의 정리나 내용을 바꾼 요청이 옛 원본을 지우는 일이 같은 경로에 다른 요청이 커밋한 원본(같은 내용으로 되돌린 요청의 것)까지 지운다(PR #3 봇 6회차).

### 2026-11-18 용어집이 묘비, 보관 표, 소프트 삭제의 이름을 쉬운 말로 바꿨다

`GLOSSARY.md`가 이름 셋을 바꿨다. 묘비는 "삭제 기록", 보관 표는 "삭제 보관함", 소프트 삭제는 "임시 삭제"다. 제목과 본문의 옛 이름은 새 이름으로 읽는다. 이름만 바뀌었고 이 ADR의 결정은 그대로이며, 코드의 이름(`archived_chunks`, `tombstone`)과 설정 이름(`RAG_DELETED_RETENTION_DAYS`)도 그대로다. 옛 이름은 영어를 옮긴 비유이거나(묘비) 데이터베이스의 테이블을 옮긴 말이거나(보관 표) 영어를 소리대로 적은 말이 섞여 있어(소프트 삭제), 처음 보는 사람이 이름만 읽고 무엇인지 짐작하기 어려웠다. 사용자가 2026-11-18에 골랐다(일지 `docs/journal/2026-11-18-1008-plain-words-in-written-artifacts.md`의 "보인 후보와 사용자의 답").

### 2026-11-19 용어집이 계약에 붙이는 번호의 이름을 판에서 버전으로 바꿨다

계약에 붙이는 번호를 가리키는 말이 "판"에서 "버전"으로 바뀌었다. 본문의 "원본이 있어야 파서 판이 올랐을 때 다시 파싱하고"에서 "파서 판"은 코드의 `ParserVersion`(파서 이름, 파서 인터페이스의 버전, 라이브러리의 버전)이라 "파서 버전"으로 읽는다. 이름만 바뀌었고 이 ADR의 결정은 그대로다. 같은 낱말을 바꾼 일의 까닭과 헌법 버전을 올린 까닭은 ADR 0016의 이력 2026-11-19 "계약에 붙이는 번호의 이름을 버전으로 바꿔 헌법 버전을 1.5.3으로 올렸다"에 있다(티켓 `.scratch/harness/issues/glossary-contract-version-names.md`).

### 2026-11-21 검색은 지운 원천의 조각을 결과에서 뺀다

명세(`.scratch/source-sync/spec.md`의 "원천 삭제와 되살리기" 절)가 정했다. 원천을 지우면(ADR 0021) 그 순간에는 원천에 지운 시각만 적고, 그 원천의 문서와 조각을 삭제 보관함으로 옮기는 일은 작업자가 문서 50건씩 나눠서 한다. 그래서 옮기기가 끝날 때까지는 검색 표에 지운 원천의 조각이 남아 있고, 검색은 결과 조각의 문서와 원천을 읽는 자리에서 지운 원천의 조각을 뺀다. 본문의 "검색 표에 산 것만 두어 검색 SQL에 삭제 필터가 없고"는 문서 하나를 지울 때는 그대로이고, 원천을 지운 직후의 이 한 자리가 예외다. 후보 조각을 뽑는 질의는 지금처럼 조각 표만 읽는다. 치르는 값은 옮기기가 끝나기 전의 검색 결과가 요청한 건수보다 적을 수 있다는 것이다.

까닭은 잰 시간이다(`.scratch/source-sync/probes/source-delete/`의 `probe_out.txt`와 `probe_out_batch50.txt`. 개발 PC의 Docker Desktop에서 쟀다). 문서 1만 건과 조각 10만 개인 원천을 한 트랜잭션에서 삭제 보관함으로 옮기면 커밋 전까지 16.12초가 걸렸고, 그동안 그 원천의 문서 행 하나를 `FOR UPDATE`로 잠그려던 다른 연결이 막혔다. 50건씩 나누면 묶음 하나의 가운데값이 0.08초였다. 제품의 색인 작업과 수집은 문서 행을 `FOR NO KEY UPDATE`로 잠그는데, 문서 행을 고치는 트랜잭션은 그 잠금도 막으므로 제품에서도 막힐 것으로 본다. 이것은 PostgreSQL의 행 잠금 규칙에 따른 어림이고, 그 잠금으로 재지는 않았다.

고르지 않은 안은 둘이다. 원천을 지우는 요청이 한 트랜잭션에서 모두 옮기는 안은 요청 하나가 문서 수만큼 길어지고 그동안 그 원천의 수집과 색인이 기다린다. 나눠 옮기되 검색이 원천을 보지 않는 안은 옮기기가 끝날 때까지 지운 원천의 문서가 검색에 남아, ADR 0021의 "지우는 순간 그 원천의 문서가 모두 검색에서 빠지고"를 지키지 못한다.

### 2026-11-27 용어집이 되살림의 이름을 복구로 바꿨다

`GLOSSARY.md`가 "되살림"의 이름을 "복구"로 바꿨다. 본문의 되살림, 되살리기, 되살리다는 복구, 복구하다로 읽는다. 이름만 바뀌었고 이 ADR의 결정은 그대로이며, 코드의 영어 식별자(`restore_*`), 관리 API 경로(`/restore`), 오류 코드, 설정 이름(`RAG_DELETED_RETENTION_DAYS`)도 그대로다. 바꾼 것은 사람이 읽는 글(주석, 독스트링, 오류 응답의 제목과 문구, API 칸의 설명, 한국어 시험 이름)이다. 앞 이력 2026-11-21이 인용한 "원천 삭제와 되살리기"는 끝난 명세(`.scratch/source-sync/spec.md`)의 절 제목이라 그 명세에서 그 제목으로 찾는다.

관리자 페이지의 화면 디자인 세션(일지 `docs/journal/2026-11-26-1938-admin-screens.md`)에서 사용자가 화면의 "되살리기"와 "되살리는 중"을 "복구"와 "복구 중"으로 바꾸게 했고, 화면과 문서가 같은 일을 다른 이름으로 부르지 않도록 용어집의 이름도 복구로 바꾸는 쪽을 골랐다. 용어집은 전에 "복구"를 백업의 말이라며 피할 말로 두었다. 이제 백업에서 데이터를 되돌리는 일은 "복원"으로만 부르고, 복구의 풀이에 둘이 다른 일이라는 문장을 더했다. 고르지 않은 안은 둘이다. 용어집의 이름을 되살림으로 두고 화면의 글자만 복구로 쓰는 것과, 화면도 지금처럼 되살리기로 두는 것이다.
