# 삭제는 소프트 삭제 뒤 보관 기간이 지나면 물리 삭제하고, 원본은 파일 저장소 포트 뒤의 볼륨에 둔다

원천에서 지운 문서는 색인에서도 지운다(원칙 VI). 그 지움의 모양이다. 처음 추천은 물리 삭제와 묘비 행이었으나 사용자가 소프트 삭제를 골랐다. 삭제하면 문서 행에 `deleted_at`을 적고, 조각(본문, 벡터, 키워드 값)을 검색 표에서 보관 표로 옮겨 검색 표에는 산 것만 남긴다. 원본 파일은 보관 기간 동안 둔다. `RAG_DELETED_RETENTION_DAYS`(기본 30) 뒤에 작업 대기열의 정리 작업이 보관 표의 조각과 원본을 지우고 내용 없는 묘비 행만 남긴다. 검색에서는 즉시 빠지므로 원칙 VI는 지키면서, 실수 삭제나 원천의 오동작(비어 버린 열거)에서 되살릴 창을 둔다. 검색 표에 산 것만 두어 검색 SQL에 삭제 필터가 없고, 옮겨 간 조각이 남긴 죽은 튜플은 PostgreSQL의 vacuum이 치운 뒤 벡터 색인에서도 빠진다(그때까지 색인에 죽은 튜플이 머무는 것은 PostgreSQL 일반의 동작이다).

원본은 `BlobStore` 포트(ADR 0007) 뒤의 로컬 볼륨에 둔다. 설정 `RAG_DATA_DIR` 아래 `blobs/<문서 UUID>`이고, 데이터베이스에는 경로, 크기, sha256, MIME만 둔다(바뀜: 이력 2026-11-10 "원본은 문서 UUID 디렉터리 아래에 수집 요청마다 새 이름으로 둔다"). 서버와 작업자가 같은 볼륨을 공유한다. 서버 경로 원천은 원본이 그 경로에 이미 있으므로 복사하지 않고 경로만 가리킨다. S3 호환 저장소는 나중에 같은 포트의 어댑터로 더한다. 원본이 있어야 파서 판이 올랐을 때 다시 파싱하고, 보관 기간 동안 되살리며, ADR 0002의 백업 대상("원본 문서")이 된다.

## Considered Options

- 물리 삭제와 묘비 행만(처음 추천): 단순하지만 되살릴 길이 없다.
- 소프트 삭제 플래그만 두고 조각은 제자리: 검색 SQL마다 필터가 들고 벡터 색인에 죽은 행이 남아 k개 채우기가 느려진다.
- 지식베이스 단위 블루/그린으로 삭제 반영: 문서 하나 지우는 데 전체 전환이 필요하다.
- 원본을 PostgreSQL bytea로: 백업이 하나지만 PDF 수천 개면 데이터베이스가 수십 GB가 되어 덤프·복원·복제가 느려지고 한 값의 한도가 1GB다.
- 서버 경로 원천까지 모두 복사: 디스크가 두 배이고, 원천에서 지우면 색인도 지운다는 원칙 VI 아래서 사본을 들고 있을 까닭이 약하다.

## Consequences

- 백업은 PostgreSQL 덤프와 `RAG_DATA_DIR` 둘이다. ADR 0002가 백업 대상을 "데이터베이스 하나와 색인, 원본 문서"로 적은 것과 같다.
- 서버 경로 원천의 문서는 사본을 들지 않으므로(Considered Options의 마지막 안을 거부한 값), 원천 파일이 지워진 뒤에는 보관 표의 조각으로 되살릴 수는 있어도 다시 파싱할 수는 없고, `RAG_DATA_DIR` 백업에도 그 파일은 들지 않는다. 그 파일의 백업은 원천 서버의 몫이다.
- compose에 볼륨 하나가 더 들고 서버 복제본이 여럿이면 볼륨을 공유해야 한다.
- 보관 중인 문서를 되살리는 관리 API와 정리 작업의 주기는 명세가 정한다.
- 같은 (원천, 키)가 보관 기간 안에 다시 들어오면 새 문서가 아니라 되살림인지는 명세가 정한다(어림: 되살린 뒤 갱신으로 처리).

## 이력

### 2026-11-10 원본은 문서 UUID 디렉터리 아래에 수집 요청마다 새 이름으로 둔다

명세(`.scratch/core/spec.md`의 수집 파이프라인 절)가 정했다. 수집 요청이 저장하는 원본의 경로는 `RAG_DATA_DIR/blobs/<문서 UUID>/<원본 UUID>`이고, `<원본 UUID>`는 수집 요청마다 새로 만든다. 본문의 `blobs/<문서 UUID>`는 파일 하나가 아니라 그 문서의 원본들이 드는 디렉터리다. 갱신의 새 원본이 옛 원본을 덮지 않아 옛 원본을 읽던 작업자가 반쯤 바뀐 파일을 읽지 않고, 같은 문서에 같은 내용을 동시에 넣는 두 요청이 서로 다른 경로에 써서 한쪽의 정리가 다른 쪽이 커밋한 원본을 지우지 않는다. 문서 행이 지금 원본의 경로를 가지므로 데이터베이스에 경로, 크기, sha256, MIME만 둔다는 본문은 그대로다. 수집 요청이 저장한 원본 가운데 문서 행이 가리키지 않는 것(바뀌어 물러난 옛 원본, 문서 행이 가리키지 않은 새 원본)은 작업 단위가 끝난 뒤 지우고(최선 노력), 지우지 못한 고아 원본은 source-sync의 정리 작업이 받는다. 서버 경로 원천의 원본은 본문대로 복사하지 않으므로 이 경로 규칙 밖이다.

고르지 않은 안: 문서 UUID를 파일 이름으로 두는 본문의 모양은 갱신이 같은 파일을 덮어 옛 원본을 읽던 작업자와 경쟁한다. 내용 해시를 이름으로 두는 안은 같은 문서의 같은 내용에 늘 같은 경로를 주어, 같은 내용을 동시에 넣는 두 요청 가운데 한쪽의 정리나 내용을 바꾼 요청이 옛 원본을 지우는 일이 같은 경로에 다른 요청이 커밋한 원본(같은 내용으로 되돌린 요청의 것)까지 지운다(PR #3 봇 6회차).
