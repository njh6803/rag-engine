# 검색 도구에 최소 점수 인자를 두되 리랭커가 없으면 거부하고, 구현은 점수 분포를 잰 뒤에 한다

검색 도구는 지금 `top_k`개를 점수와 무관하게 돌려준다. 색인에 답이 없는 질의에도 관련 없는 조각이 `top_k`개 나가고, 클라이언트는 그것을 근거로 쓴다. 그래서 검색 도구에 선택 인자 `min_score`(0 이상 1 이하)를 두어, 리랭크 점수가 그 값보다 낮은 조각을 결과에서 뺀다.

- **기준은 리랭크 점수다.** 결과의 `score`는 리랭커가 있으면 리랭크 점수이고 없으면 RRF 점수다(`src/rag_engine/domain/entities.py`의 `SearchHit.score`, 코드를 읽었다). RRF 점수는 순위만으로 계산해 관련 정도를 담지 않는다. 그래서 리랭커가 없는 지식베이스에 `min_score`를 주면 `invalid_argument`로 거부한다. 리랭커가 실패하면 조용히 대체하지 않고 오류를 내는 지금 규칙과 같은 방향이다.
- **남은 조각이 없으면 빈 결과를 정상 응답으로 낸다.** 오류가 아니다. 현재 판이 없을 때와 없는 그룹 이름으로 걸렀을 때도 지금 빈 결과를 내므로 같은 규칙이다.
- **지식베이스마다 기본값을 둘 수 있다.** 요청 인자가 있으면 인자가 이기고, 없으면 지식베이스의 기본값을 쓰며, 둘 다 없으면 거르지 않는다(지금 동작). 리랭커가 없는 지식베이스에 기본값을 설정하는 것도 거부한다.
- **판.** 입력 인자를 더하므로 `format_version`은 `1.0.0`에서 `1.1.0`이 된다(ADR 0015 이력 2026-11-12 "검색 도구의 입력 인자를 더하는 것도 minor로 올린다").
- **구현은 측정 뒤다.** search-eval이 먼저 공공 문서 묶음에서 리랭크 점수의 분포를 기대 근거에 닿은 조각과 그렇지 않은 조각으로 갈라 보고서로 낸다(ADR 0018의 범위 항목). 사용자가 그 보고서를 보고 구현을 승인한다. 두 분포가 한 문턱으로 잘 갈리지 않으면 구현하지 않고 다시 묻는다. 그때까지 판은 `1.0.0`이다. 그래서 이 인자를 구현하는 티켓은 계약을 바꾸는 티켓인데도 기능의 첫 티켓이 아니다. 계약을 바꿀지가 측정에 달려 있어 `docs/agents/issue-tracker.md` 전체 계획 절의 규칙(계약을 바꾸는 티켓이 첫 티켓이다)에 두는 예외다.

사용자가 2026-11-12 search-eval 설계 인터뷰에서 골랐다(`docs/journal/2026-11-12-2108-search-eval-design.md`).

## Considered Options

- 리랭커가 없으면 조용히 무시: 클라이언트가 걸러졌다고 믿는다.
- 남은 조각이 없으면 오류: 클라이언트가 "근거 없음"과 고장을 가르지 못한다.
- 지식베이스 기본값만 두거나 요청 인자만 둔다: 앞의 것은 질의마다 조절할 수 없고, 뒤의 것은 클라이언트를 고칠 수 없는 설치처가 쓸 수 없다.
- 지금 바로 구현: 문턱이 통하는지 모르는 채 계약에 인자를 넣으면, 빼야 할 때 major가 든다.

## Consequences

- 계약 시험이 inputSchema의 `min_score`와 `format_version` `1.1.0`을 본다.
- 지식베이스 설정에 기본값 칸이 는다. 색인 판의 요소가 아니라 재색인은 필요 없다.
- 운영자가 기본값을 설정한 설치에서는 인자를 보내지 않는 클라이언트의 결과도 걸러진다.
- 클라이언트는 지식베이스에 리랭커가 있는지 미리 알 길이 없어(목록 도구가 알려 주지 않는다) 불러 본 뒤에야 거부를 안다.
- 기본값이 있는 지식베이스에서 리랭커를 빼는 설정 변경을 어떻게 다룰지는 명세가 정한다.
- 사용자가 승인하기 전에는 구현 티켓이 다른 세션이 집을 수 있는 상태로 놓이지 않아야 한다. 측정 티켓이 닫힌 것만으로는 승인이 아니다. 구현 티켓을 승인 뒤에 쓰는 것을 기본으로 하고, 승인을 어디에 적는지는 명세가 정한다.
