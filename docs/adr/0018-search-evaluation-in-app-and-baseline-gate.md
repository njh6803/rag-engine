# 검색 평가의 핵심은 제품 코드의 유스케이스이고, 기대 근거로 채점하며, 기준 보고서보다 떨어지면 CI가 막는다

검색 품질은 운영 질문이 아니라 평가 세트로 잰다(ADR 0004). 그 평가를 어디에 두고 무엇으로 채점하며 CI가 무엇을 막는지를 정한다.

- **자리.** 평가의 핵심(채점, 지표, 보고서)은 `app`의 유스케이스이고 포트만 부른다. 이번 입구는 저장소의 명령줄 도구이고(CI와 공개 시연용) 제품 이미지의 관리 명령으로는 내지 않는다. 관리자 페이지의 등록·실행·결과 화면, 관리 API, 저장 표는 admin 설계에 넘긴다.
- **단계별 측정.** 검색 포트 `VectorIndex`에 진단용 메서드 하나를 더한다. 조각마다 벡터 순위, 키워드 순위, 합친 순위를 돌려주고 실제 검색(`search_candidates`)과 같은 SQL 뼈대를 쓴다. 리랭크 점수는 평가 유스케이스가 실제 검색과 같은 리랭커 포트로 붙인다. MCP 도구로는 열지 않는다.
- **평가 세트.** 기대 근거와 질의 목록으로 나눈다. 기대 근거는 질문 하나가 찾아야 하는 자리이고, 질의 목록은 같은 기대 근거를 겨냥한 질의의 묶음이다. 같은 기대 근거에 질의 목록을 여러 개 붙일 수 있고, 저장소는 사람이 묻는 문장으로 쓴 질의 목록과 키워드형 질의 목록을 함께 가진다. 형식에 판 칸을 두되 원칙 VII의 계약 목록에는 아직 넣지 않는다.
- **적중의 단위.** 공공 문서 묶음은 문서와 원문 글귀로 적고, 그 문서의 조각 글에 그 글귀가 들어 있으면 적중이다. 글귀가 조각의 경계에서 갈리면 놓친 것으로 센다. 공개 데이터셋은 문서와 쪽 번호로 본다. 조각 단위로 정답을 달지 않는 까닭은 청킹 설정을 바꾸면 조각의 경계가 달라지기 때문이다.
- **재료.** CI 게이트와 공개 시연은 직접 구성한 공공 문서 묶음(법령·행정규칙을 뼈대로 하고 공공누리 1유형 일부)을 저장소에 커밋해 쓴다. 문서마다 출처, 이용 조건, 내려받은 날짜, 해시를 목록에 적고 용량 상한을 둔다(예: 30MB, 명세가 확정). 후보 목록은 에이전트가 내고 사용자가 확정한다. 공개 데이터셋(allganize)은 로컬 참고 측정이고 PDF는 커밋하지 않는다.
- **질문.** 질문과 기대 근거는 에이전트가 초안을 쓰고 사용자가 검수한다. 질문은 문서의 문장을 베끼지 않고 표현을 바꿔 묻는다. 키워드형 질의 목록도 같은 방법으로 만든다. 규모는 문서 40개 안팎, 질문 150개 안팎이다(어림, 명세가 확정).
- **지표.** 상위 1·3·5·10 적중률, MRR, 재현율, nDCG@10을 모두 계산한다. 기대 근거는 질문마다 하나 이상만 요구한다. 관련 문서를 빠짐없이 다는 방식은 나중으로 미루므로, 재현율과 nDCG는 단 것만을 기준으로 한 값이다.
- **게이트.** 절대 문턱이 아니라 커밋한 기준 보고서 대비 하락폭으로 막는다(폭은 첫 측정에서 실행마다 흔들리는 정도를 보고 명세가 정한다. 예: 2%p). 질의 목록마다 상위 5 적중률과 MRR을 본다. 모든 PR의 빠른 게이트는 리랭커를 빼고 돌려 "합친 뒤" 줄을 보고, main으로 가는 PR과 수동 실행의 전체 게이트는 "리랭크 뒤" 줄을 본다. 벡터만, 키워드만 줄은 보고서에만 싣는다. 빠른 게이트는 서버 코드, 의존성 목록, 평가 재료와 구성이 바뀐 PR에서만 돌고, 건너뛰면 `verify`는 통과로 센다.
- **기준 보고서.** CI에서 만든 값을 커밋한다. 갱신 커밋은 사람이 승인한다. 게이트가 빨강일 때 에이전트는 기준 보고서를 스스로 갱신하지 않고 멈춰 보고한다. 기대 근거와 질의 목록의 수정, 기준 보고서의 갱신은 숫자의 앞뒤 차이를 보이고 사용자가 승인한 뒤에 한다.
- **놓친 까닭.** 세 겹으로 본다. 질문에 미리 단 유형 표지, 진단용 검색이 알려 주는 탈락 지점과 낱말 겹침, 사람 판정이다. 사람 판정의 초벌은 Claude Code 세션이 하고 사용자가 확인한다.
- **LLM의 자리.** 채점은 기대 근거로만 한다. LLM 관련성 판정은 참고 숫자이고 게이트로 쓰지 않는다(ADR 0019).
- **범위.** 이 기능이 실험해 기본값을 정하는 것은 설정만 바꾸면 되는 둘(조각 크기와 겹침, 리랭커 켬·끔과 후보 수)이고, 기본값의 변경은 사용자 승인 뒤에 한다. 코드 변경이 필요한 셋(품사 규칙, 정확 스캔 분기, 시멘틱 청킹)은 판단용 숫자만 보고서에 남기고, 고칠지는 그 숫자를 본 뒤 별도 작업으로 정한다. 보고서는 판단용 숫자를 둘 더 낸다. 하나는 최소 점수(ADR 0017)를 판정할 리랭크 점수의 분포다. 기대 근거에 닿은 조각과 그렇지 않은 조각으로 갈라 내고, 문턱마다의 적중률과 빈 결과의 비율을 함께 낸다. 다른 하나는 키워드만 줄이다. `ts_rank`에는 IDF가 없다는 ADR 0006 Consequences의 판단과, 키워드 질의가 토큰을 OR로 잇는 지금 동작을 이 줄로 본다.

사용자가 2026-11-12 search-eval 설계 인터뷰에서 골랐다(`docs/journal/2026-11-12-2108-search-eval-design.md`).

## Considered Options

- 평가를 `tools/`의 스크립트로만 둔다: 관리자 페이지가 평가를 열 때 핵심을 옮겨야 한다.
- 단계마다 검색을 따로 돌린다: 실제 검색과 다른 SQL을 재게 된다.
- 절대 문턱 게이트: 묶음이나 질문을 고칠 때마다 문턱을 다시 정해야 하고, 첫 값을 모른다.
- LLM 관련성 판정을 주 지표로 쓴다: 판정이 모델과 지시문에 따라 달라져 게이트가 흔들리고 실행마다 비용이 든다.
- 묶음을 내려받는 스크립트만 커밋한다: 원천이 바뀌면 같은 커밋이 다른 숫자를 낸다.
- 전체 게이트를 모든 PR에 돌린다: 리랭커를 CPU로 돌리는 시간이 PR마다 든다(어림. core 16의 측정값을 보고 명세가 확정).

## Consequences

- 전체 게이트가 들어오면 main PR에만 도는 잡이 생긴다. dev 전환(ADR 0016) 전에 구현되면 전체 게이트는 수동 실행만 둔다.
- 리랭커 쪽의 회귀는 main으로 가는 PR에서야 드러난다. dev 전환 전에는 수동 실행에서만 드러난다.
- 빠른 게이트의 실행은 리랭크 뒤 줄을 만들지 못하므로 기준 보고서의 그 줄은 전체 게이트의 실행에서 온다. 어느 줄을 어느 실행의 값으로 갱신하는지와 첫 기준 보고서를 만드는 절차는 명세가 정한다.
- 전체 게이트를 main 푸시에서도 돌릴지와, dev 전환 전에 수동 실행으로만 둔 전체 게이트를 전환 뒤 main PR의 잡으로 켜는 일을 어느 티켓이 받는지는 명세가 정한다.
- 빠른 게이트를 돌릴 경로의 목록을 관리해야 하고, 목록에서 빠진 경로의 변경은 전체 게이트에서야 잡힌다.
- 평가 전용 compose(PostgreSQL, 임베딩 TEI, 리랭커 TEI)가 release-image와 독립으로 서고, CI는 모델을 캐시한다. 빠른 게이트의 소요 시간이 한도를 넘으면 다시 묻는다.
- `docs/constitution/operations.md`의 CI 절과 `.github/workflows/ci.yml`의 머리 주석(느린 검사를 main PR에만 둘지를 설계에 미룬 문장)은 게이트를 넣는 티켓이 고친다. `verify`는 지금 건너뛴 잡을 빨강으로 센다(`.github/workflows/ci.yml`의 verify 주석을 읽었다). 그래서 빠른 게이트를 건너뛴 PR이 통과하게 하는 방법도 그 티켓이 정한다.
- 게이트는 CI 전용이고 pre-commit 러너에는 넣지 않는다.
