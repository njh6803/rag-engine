# 검색 평가의 핵심은 제품 코드의 유스케이스이고, 기대 근거로 채점하며, 기준 보고서보다 떨어지면 CI가 막는다

검색 품질은 운영 질문이 아니라 평가 세트로 잰다(ADR 0004). 그 평가를 어디에 두고 무엇으로 채점하며 CI가 무엇을 막는지를 정한다.

- **자리.** 평가의 핵심(채점, 지표, 보고서)은 `app`의 유스케이스이고 포트만 부른다. 이번 입구는 저장소의 명령줄 도구이고(CI와 공개 시연용) 제품 이미지의 관리 명령으로는 내지 않는다. 관리자 페이지의 등록·실행·결과 화면, 관리 API, 저장 표는 admin 설계에 넘긴다.
- **단계별 측정.** 검색 포트 `VectorIndex`에 진단용 메서드 하나를 더한다. 조각마다 벡터 순위, 키워드 순위, 합친 순위를 돌려주고 실제 검색(`search_candidates`)과 같은 SQL 뼈대를 쓴다. 리랭크 점수는 평가 유스케이스가 실제 검색과 같은 리랭커 포트로 붙인다. MCP 도구로는 열지 않는다.
- **평가 세트.** 기대 근거와 질의 목록으로 나눈다. 기대 근거는 질문 하나가 찾아야 하는 자리이고, 질의 목록은 같은 기대 근거를 겨냥한 질의의 묶음이다. 같은 기대 근거에 질의 목록을 여러 개 붙일 수 있고, 저장소는 사람이 묻는 문장으로 쓴 질의 목록과 키워드형 질의 목록을 함께 가진다. 형식에 판 칸을 두되 원칙 VII의 계약 목록에는 아직 넣지 않는다.
- **적중의 단위.** 공공 문서 묶음은 문서와 원문 글귀로 적고, 그 문서의 조각 글에 그 글귀가 들어 있으면 적중이다. 글귀가 조각의 경계에서 갈리면 놓친 것으로 센다. 공개 데이터셋은 문서와 쪽 번호로 본다. 조각 단위로 정답을 달지 않는 까닭은 청킹 설정을 바꾸면 조각의 경계가 달라지기 때문이다.
- **재료.** CI 게이트와 공개 시연은 직접 구성한 공공 문서 묶음(법령·행정규칙을 뼈대로 하고 공공누리 1유형 일부)을 저장소에 커밋해 쓴다. 문서마다 출처, 이용 조건, 내려받은 날짜, 해시를 목록에 적고 용량 상한을 둔다(예: 30MB, 명세가 확정). 후보 목록은 에이전트가 내고 사용자가 확정한다. 공개 데이터셋(allganize)은 로컬 참고 측정이고 PDF는 커밋하지 않는다.
- **질문.** 질문과 기대 근거는 에이전트가 초안을 쓰고 사용자가 검수한다. 질문은 문서의 문장을 베끼지 않고 표현을 바꿔 묻는다. 키워드형 질의 목록도 같은 방법으로 만든다. 규모는 문서 40개 안팎, 질문 150개 안팎이다(어림, 명세가 확정).
- **지표.** 상위 1·3·5·10 적중률, MRR, 재현율, nDCG@10을 모두 계산한다. 기대 근거는 질문마다 하나 이상만 요구한다. 관련 문서를 빠짐없이 다는 방식은 나중으로 미루므로, 재현율과 nDCG는 단 것만을 기준으로 한 값이다.
- **게이트.** 절대 문턱이 아니라 커밋한 기준 보고서 대비 하락폭으로 막는다(폭은 첫 측정에서 실행마다 흔들리는 정도를 보고 명세가 정한다. 예: 2%p)(바뀜: 이력 2026-11-13 "모델이 계산한 결과는 로컬에서 만든 추론 기록으로 커밋하고, CI는 그 기록을 읽는다"). 질의 목록마다 상위 5 적중률과 MRR을 본다. 모든 PR의 빠른 게이트는 리랭커를 빼고 돌려 "합친 뒤" 줄을 보고, main으로 가는 PR과 수동 실행의 전체 게이트는 "리랭크 뒤" 줄을 본다. 벡터만, 키워드만 줄은 보고서에만 싣는다. 빠른 게이트는 서버 코드, 의존성 목록, 평가 재료와 구성이 바뀐 PR에서만 돌고, 건너뛰면 `verify`는 통과로 센다(바뀜: 이력 2026-11-13 "모델이 계산한 결과는 로컬에서 만든 추론 기록으로 커밋하고, CI는 그 기록을 읽는다").
- **기준 보고서.** CI에서 만든 값을 커밋한다. 갱신 커밋은 사람이 승인한다. 게이트가 빨강일 때 에이전트는 기준 보고서를 스스로 갱신하지 않고 멈춰 보고한다. 기대 근거와 질의 목록의 수정, 기준 보고서의 갱신은 숫자의 앞뒤 차이를 보이고 사용자가 승인한 뒤에 한다.
- **놓친 까닭.** 세 겹으로 본다. 질문에 미리 단 유형 표지, 진단용 검색이 알려 주는 탈락 지점과 낱말 겹침, 사람 판정이다. 사람 판정의 초벌은 Claude Code 세션이 하고 사용자가 확인한다.
- **LLM의 자리.** 채점은 기대 근거로만 한다. LLM 관련성 판정은 참고 숫자이고 게이트로 쓰지 않는다(ADR 0019).
- **범위.** 이 기능이 실험해 기본값을 정하는 것은 설정만 바꾸면 되는 둘(조각 크기와 겹침, 리랭커 켬·끔과 후보 수)이고, 기본값의 변경은 사용자 승인 뒤에 한다. 코드 변경이 필요한 셋(품사 규칙, 정확 스캔 분기, 시멘틱 청킹)은 판단용 숫자만 보고서에 남기고, 고칠지는 그 숫자를 본 뒤 별도 작업으로 정한다. 보고서는 판단용 숫자를 둘 더 낸다. 하나는 최소 점수(ADR 0017)를 판정할 리랭크 점수의 분포다. 기대 근거에 닿은 조각과 그렇지 않은 조각으로 갈라 내고, 문턱마다의 적중률과 빈 결과의 비율을 함께 낸다. 다른 하나는 키워드만 줄이다. `ts_rank`에는 IDF가 없다는 ADR 0006 Consequences의 판단과, 키워드 질의가 토큰을 OR로 잇는 지금 동작을 이 줄로 본다.

사용자가 2026-11-12 search-eval 설계 인터뷰에서 골랐다(`docs/journal/2026-11-12-2108-search-eval-design.md`).

## Considered Options

- 평가를 `tools/`의 스크립트로만 둔다: 관리자 페이지가 평가를 열 때 핵심을 옮겨야 한다.
- 단계마다 검색을 따로 돌린다: 실제 검색과 다른 SQL을 재게 된다.
- 절대 문턱 게이트: 묶음이나 질문을 고칠 때마다 문턱을 다시 정해야 하고, 첫 값을 모른다.
- LLM 관련성 판정을 주 지표로 쓴다: 판정이 모델과 지시문에 따라 달라져 게이트가 흔들리고 실행마다 비용이 든다.
- 묶음을 내려받는 스크립트만 커밋한다: 원천이 바뀌면 같은 커밋이 다른 숫자를 낸다.
- 전체 게이트를 모든 PR에 돌린다: 리랭커를 CPU로 돌리는 시간이 PR마다 든다(어림. core 16의 측정값을 보고 명세가 확정).

## Consequences

- 전체 게이트가 들어오면 main PR에만 도는 잡이 생긴다. dev 전환(ADR 0016) 전에 구현되면 전체 게이트는 수동 실행만 둔다.
- 리랭커 쪽의 회귀는 main으로 가는 PR에서야 드러난다. dev 전환 전에는 수동 실행에서만 드러난다.
- 빠른 게이트의 실행은 리랭크 뒤 줄을 만들지 못하므로 기준 보고서의 그 줄은 전체 게이트의 실행에서 온다. 어느 줄을 어느 실행의 값으로 갱신하는지와 첫 기준 보고서를 만드는 절차는 명세가 정한다.
- 전체 게이트를 main 푸시에서도 돌릴지와, dev 전환 전에 수동 실행으로만 둔 전체 게이트를 전환 뒤 main PR의 잡으로 켜는 일을 어느 티켓이 받는지는 명세가 정한다.
- 빠른 게이트를 돌릴 경로의 목록을 관리해야 하고, 목록에서 빠진 경로의 변경은 전체 게이트에서야 잡힌다.
- 평가 전용 compose(PostgreSQL, 임베딩 TEI, 리랭커 TEI)가 release-image와 독립으로 서고, CI는 모델을 캐시한다(바뀜: 이력 2026-11-13 "모델이 계산한 결과는 로컬에서 만든 추론 기록으로 커밋하고, CI는 그 기록을 읽는다"). 빠른 게이트의 소요 시간이 한도를 넘으면 다시 묻는다.
- `docs/constitution/operations.md`의 CI 절과 `.github/workflows/ci.yml`의 머리 주석(느린 검사를 main PR에만 둘지를 설계에 미룬 문장)은 게이트를 넣는 티켓이 고친다. `verify`는 지금 건너뛴 잡을 빨강으로 센다(`.github/workflows/ci.yml`의 verify 주석을 읽었다). 그래서 빠른 게이트를 건너뛴 PR이 통과하게 하는 방법도 그 티켓이 정한다(바뀜: 이력 2026-11-13 "모델이 계산한 결과는 로컬에서 만든 추론 기록으로 커밋하고, CI는 그 기록을 읽는다").
- 진단용 메서드와 `search_candidates`가 같은 SQL 뼈대를 쓴다는 조건을 어떻게 지키는지는 명세가 정한다. 두 메서드의 SQL이 따로 고쳐져 갈라지면 평가가 실제 검색과 다른 것을 재게 된다.
- 게이트는 CI 전용이고 pre-commit 러너에는 넣지 않는다.

## 이력

### 2026-11-13 모델이 계산한 결과는 로컬에서 만든 추론 기록으로 커밋하고, CI는 그 기록을 읽는다

명세(`.scratch/search-eval/spec.md`)가 정했다. 명세 세션이 코어 4개로 묶은 TEI CPU 이미지(`cpu-1.9.4`)의 처리량을 쟀다(프로브 `.scratch/search-eval/probes/tei-cpu/`). 임베딩(`BAAI/bge-m3`)은 471토큰의 글 32개를 한 배치에 49.7~108.6초에 계산했고(0.48개/s), 리랭커(`BAAI/bge-reranker-v2-m3`)는 질의와 같은 방식으로 만든 글의 쌍 32개를 한 배치에 200.6~297.6초에 채점했다(0.12쌍/s. 쌍의 토큰 수는 재지 않았다). 리랭커는 모델 저장소에 ONNX 파일이 없어 TEI가 Candle 백엔드로 돌렸다(프로브의 서버 로그). 개발 PC에서 다른 컨테이너가 함께 돌기도 한 값이라(프로브 README) 자릿수를 보는 어림이다. 그래도 조각 3,000개의 임베딩이 약 100분이고 평가 한 번의 리랭크(질의 300개에 후보 50개씩 15,000쌍)가 약 34시간이라, CPU뿐인 CI가 PR마다 새로 계산할 수 없다.

그래서 모델이 계산한 결과를 다루는 방식이 바뀐다. 임베딩 벡터와 리랭크 점수를 모델 이름과 글의 해시를 열쇠로 한 파일(명세의 "추론 기록")로 저장소에 커밋하고, 평가는 기록에 있는 글을 다시 계산하지 않는다. 기록은 로컬에서 만들고, 리랭크 점수의 기록은 GPU로 만든다. CI에서 기록에 없는 글이 명세가 정한 수를 넘으면 실패하고, 로컬에서 기록을 만들어 커밋하라고 알린다. 기준 보고서가 CI의 실행이 낸 보고서라는 것은 그대로이되, 그 실행이 쓰는 벡터와 리랭크 점수는 커밋된 기록에서 온다. 기준 보고서는 빠른 게이트의 것과 전체 게이트의 것을 파일 둘로 나눠 둔다. dev로 가는 PR은 리랭크 뒤 줄을 만들 수 없어, 파일이 하나면 그 PR이 기준을 갈 때 그 줄이 사라지기 때문이다. Consequences의 평가 전용 compose는 CI에서 PostgreSQL과 임베딩 TEI 둘만 띄우는 것으로 좁아진다. 임베딩 TEI는 토큰 세기와 기록에 없는 적은 수의 글에 쓰고, 전체 게이트는 리랭크 점수를 기록에서만 읽어 CI가 리랭커를 띄우지 않는다.

전체 게이트의 결정(main으로 가는 PR에서 리랭크 뒤 줄을 본다)은 바뀌지 않는다. 다만 합친 뒤의 후보를 바꾸는 변경은 리랭크할 쌍을 바꾸므로, 그 변경이 main으로 가려면 GPU가 있는 기계에서 리랭크 기록을 다시 만들어 커밋해야 한다. 명세는 그 일을 dev에서 main으로 가는 출시 PR 앞에 둔다. GPU의 처리량은 재지 못했다. 명세 세션이 개발 PC의 GPU(GTX 1660 Ti)로 TEI GPU 이미지(`turing-1.9.4`)를 띄워 보았는데 그대로는 뜨지 않았다. 드라이버 요구 검사를 끄고 이미지의 상위 호환 라이브러리 폴더를 가린 뒤에야 GPU를 잡았고, 그래도 모델을 올리다 `CUDA_ERROR_UNSUPPORTED_PTX_VERSION`으로 끝났다(프로브의 서버 로그 `gpu_turing_start_server_log.txt`, 띄운 방법은 프로브 README). 설치된 NVIDIA 드라이버(560.94)가 이미지의 CUDA 12.9보다 낡은 것으로 본다. 드라이버는 사용자가 올리고, 리랭크 기록을 만드는 티켓이 GPU의 처리량과, 다시 계산한 값의 차(같은 장치에서 두 번, CPU와 GPU 사이)를 잰다. 기록 만들기가 2시간을 넘으면 멈춰 사용자에게 다시 묻는다. ADR 0010에서 개발과 CI는 CPU 이미지를 쓰고 배포 대상만 GPU 이미지를 쓴다고 한 문장은 범위가 달라진다. 리랭크 기록은 개발 PC의 GPU 이미지로 만들기 때문이고, 그 문장에 이 이력을 가리키는 포인터를 단다. 리랭커가 CPU에서 검색 한 번의 시간 제한을 넘긴다는 것은 제품의 문제로 남는다. core 16(검색 지연 측정, PR #31)이 같은 날 그것을 쟀고(리랭커를 켠 검색이 후보 50개에서 한 번에 130초. 한 번 잰 값이다. 프로브 `.scratch/core/probes/search-latency/`), 길 셋(리랭커를 끄는 기본, ONNX 리랭커나 GPU 이미지, 검색 시간 제한을 늘리는 것) 가운데 어느 것도 고르지 않고 결정을 사용자와 이 기능에 넘겼다(일지 `docs/journal/2026-11-13-0615-search-latency-probe.md`). 명세는 그 결정을 이 기능의 리랭커 켬·끔 실험 뒤에 둔다. 그 실험의 보고서와 core 16이 잰 지연을 함께 사용자에게 보이고 사용자가 길을 고른다. 사용자가 리랭커의 모델을 바꾸는 길을 고르면 기록과 기준 보고서를 그 모델로 만들고, 리랭커를 끄는 기본을 고르면 전체 게이트와 최소 점수(ADR 0017)를 어떻게 둘지를 함께 묻는다.

본문이 거부한 안 가운데 전체 게이트를 모든 PR에 돌리는 안의 근거는 어림이었고 core 16의 측정값을 보고 명세가 확정하기로 되어 있었다. 측정은 그 어림보다 크다. 리랭커를 켠 검색이 후보 50개에서 한 번에 130초이므로 질의 300개면 약 11시간이고(계산이다), 명세 세션의 프로브로는 약 34시간이다. CPU로는 PR마다가 아니라 한 번도 돌리기 어렵다. 추론 기록을 쓰는 지금은 CI가 리랭크를 계산하지 않으므로 그 안을 거부하는 까닭이 달라진다. 합친 뒤의 후보를 바꾸는 PR마다 GPU가 있는 기계에서 리랭크 기록을 다시 만들어야 하기 때문이다. 결론은 같다. core 16은 TEI의 기본 `--max-batch-tokens`에서 임베딩 컨테이너 하나가 13.25GiB를 점유하는 것도 봤다(손으로 본 값). 그래서 명세는 평가 전용 compose의 임베딩 TEI를 그 값을 낮춰 띄우게 한다.

본문이 명세와 티켓에 맡긴 것 둘도 자리가 달라졌다. 하락폭은 상위 5 적중률 2%p와 MRR 0.02로 시작한다. 실행 사이에 흔들리는 정도는 평가 도구가 아직 없어 명세가 재지 못했고, 게이트를 넣는 티켓이 같은 커밋을 CI에서 세 번 돌려 잰다. 차가 질문 하나의 몫을 넘으면 멈춰 사용자에게 다시 묻는다. 빠른 게이트를 건너뛴 PR이 통과하게 하는 방법은 티켓이 아니라 명세가 정했다. 빠른 게이트의 잡은 건너뛰지 않고 늘 시작하며, 첫 스텝이 바뀐 경로를 보아 평가하지 않을 때는 성공으로 끝난다. 그래서 `verify`의 판정은 고치지 않는다. 본문의 "PR에서만 돌고"도 범위가 넓어진다. 빠른 게이트는 PR만이 아니라 dev와 main의 푸시에서도 돈다. dev는 최신 기준을 강제하지 않아 병합된 결과가 PR에서 잰 것과 다를 수 있기 때문이다.

사용자가 2026-11-13 명세 세션에서 넷을 골랐다. 추론 기록을 저장소에 커밋한다, 하락폭을 2%p로 시작한다, 전체 게이트와 리랭크 점수에 기대는 측정을 core 16의 판정에 묶지 않고 GPU로 만든 기록으로 진행한다, 리랭커의 CPU 속도를 푸는 길은 이 기능의 리랭커 켬·끔 실험 뒤에 고른다. 셋째는 처음에 core 16의 판정 뒤로 미루기로 골랐다가 GPU로 띄워 본 결과를 본 뒤 바꾼 것이다. 넷째는 core 16이 결정을 넘긴 뒤에 세 선택지(리랭커 실험 뒤에 고른다, 지금 리랭커를 끄는 기본으로 바꾼다, 지금 ONNX와 GPU의 조사부터 한다) 가운데 고른 것이다. core 16은 이 이력이 병합되기 전인 같은 날 닫혔고 그것으로 core가 끝났으므로(`.scratch/core/plan.md`의 `**끝:**` 줄), 기능 계획의 `Blocked by: core`는 search-eval의 티켓을 더 막지 않는다. 푸시에서의 실행과 기준 보고서를 둘로 나누는 것은 사용자가 고른 것이 아니라 명세가 정한 것이다.
