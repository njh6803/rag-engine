# 이슈 트래커: 로컬 마크다운

이 저장소의 이슈와 명세는 `.scratch/` 아래 마크다운 파일로 산다. 원격 트래커는 쓰지 않는다.

## 규약

- **PR마다 티켓 하나.** 기준 브랜치로 가는 티켓 PR(dev가 생기기 전에는 base가 main이다)과 main으로 가는 핫픽스 PR은 모두 티켓 파일 하나를 가리킨다. 출시 PR(머리가 dev)과 되돌려 합치기 PR(머리가 main)은 티켓 하나를 가리키지 않으므로 커밋 검사가 그대로 지난다(ADR 0016). 오타 하나만 고치는 PR도 짧은 티켓을 쓴다. 열린 PR에 반영하는 커밋, 셀프 리뷰가 고친 것, 그 PR의 일지는 그 PR의 티켓에 든다. 면제는 둘이다. 기능의 설계·명세·티켓을 쓰는 PR(그 PR이 티켓을 만드는 일이다)과, 기록(일지·대기열)만 바꾸는 PR이다. 면제 PR은 `docs/<slug>` 브랜치이고 티켓을 쓰지 않는다. 커밋 검사(`tools/check_ticket.py`)가 커밋마다 이 규약으로 판정하고, 면제 PR이 바꿀 수 있는 파일의 모양과 판정의 차례는 그 검사의 독스트링이 원천이다
- 기능 하나에 디렉터리 하나: `.scratch/<feature-slug>/`. 명세가 필요한 하네스 기능도 자기 디렉터리를 갖는다
- 기능 계획은 `.scratch/<feature-slug>/plan.md`(모양과 쓰는 때는 아래 전체 계획 절)
- 명세는 `.scratch/<feature-slug>/spec.md`
- 구현 티켓은 티켓 하나에 파일 하나: `.scratch/<feature-slug>/issues/<NN>-<slug>.md`. `01`부터 번호를 매기고, 여러 티켓을 한 파일에 합치지 않는다
- **harness 티켓.** 명세 없이 티켓 하나로 끝나는 하네스 일과 기능에 들지 않는 작은 문서 고침은 `.scratch/harness/issues/<slug>.md`다. 번호를 받지 않고, 티켓 이름만 보고 무엇을 하는 티켓인지 알 수 있게 slug를 짓는다. slug는 영어 소문자로 시작하고 소문자·숫자·하이픈으로 이루어진다. 커밋과 PR 제목의 꼬리는 `(harness <slug>)`다
- harness 티켓의 서식은 `to-tickets`의 로컬 티켓 서식에서 `Blocked by` 대신 가리키는 대기열 항목을 든다. 머리 `# <slug>: <제목>`, `**What to build:**`, `**대기열:**`(항목 식별자들, 없으면 `없음`. 항목의 내용은 옮기지 않는다), `**Status:**`, 수용 기준 체크박스다. 크기는 새 세션 하나에 들어가는 만큼이다
- 기능 밖에서 제품 코드를 고치는 일은 그 동작을 만든 기능 디렉터리에 다음 두 자리 번호로 티켓을 더한다. 그 기능 계획의 `끝` 줄은 그대로 둔다
- **브랜치 이름은 티켓 파일 이름의 stem 그대로다.** 기능 디렉터리의 티켓은 `feature/<NN>-<slug>`, harness 티켓은 `chore/<slug>`다. 브랜치 이름만 보고 티켓 파일을 찾는다
- 상태는 각 이슈 파일 상단의 `Status:` 줄에 적는다. 값은 `ready-for-agent`(to-tickets가 발행할 때 쓴다), `in-progress`, `done`, `wontfix` 넷 가운데 하나다. 그 일을 하는 세션이 코드를 고치기 전에 티켓을 쓰고 상태는 `in-progress`다. `to-tickets`가 미리 쓴 `ready-for-agent` 티켓은 받는 세션의 첫 편집이 `in-progress`로 바꿔 첫 커밋에 싣는다. PR을 열기 전에 `done`으로 바꾼다. 티켓은 그 일을 하는 PR에 함께 싣는다
- PR이 병합된 티켓은 다시 열지 않는다. 그 일을 이으면 남은 일로 새 티켓을 쓰고(harness 티켓이면 새 이름, 기능 디렉터리의 티켓이면 그 디렉터리의 다음 두 자리) 앞 티켓의 경로를 든다
- 코멘트와 대화 이력은 파일 끝 `## Comments` 제목 아래에 덧붙인다
- `.scratch/`는 git에 커밋한다. 이 저장소의 유일한 작업 기록이기 때문이다

## 프로브와 근거

측정 스크립트(프로브)를 어디 두는지, 그리고 그것을 드는 근거 문장을 어떻게 쓰는지.

- 명세·ADR·코드 주석이 근거로 드는 프로브는 `.scratch/<feature-slug>/probes/`에 커밋한다. 하네스(`tools/`, `.claude/`)를 받치는 것은 slug 자리에 `harness`를 쓴다. 세션 스크래치패드는 사라지고, 근거를 다시 재거나 반박하려면 스크립트가 있어야 한다. 근거를 드는 자리는 프로브를 파일 이름으로 가리키고, 같은 디렉터리의 `README.md` 표에 프로브마다 한 줄(무엇을 재는지, 어디가 근거로 드는지, 다시 돌 때 필요한 것, 잰 라이브러리나 도구의 판)을 둔다. 검색 지연, 첫 대량 적재 시간처럼 대상 사양에서 재는 값도 이 자리에 둔다
- 근거는 무엇으로 섰는지 밝힌다. 명세·ADR·코드 주석·프로브 README·대기열·일지처럼 뒤에 근거로 읽히는 글에서 "쟀다"·"실측"은 커밋한 프로브가 다시 내는 것에만 쓰고 그 파일을 가리킨다. 손으로 돌려 본 것은 그 명령과 함께 손으로 봤다고, 코드를 읽은 것은 파일과 판과 함께 읽었다고 적는다. 재지 않은 수와 해석은 재고 나서 적거나 어림이라고 적는다. 결과를 본 뒤 판정 기준을 바꿨으면 바꾼 기준과 그 까닭을 결과와 함께 적는다. 조사 서브에이전트에게도 보고를 이 넷(프로브, 손, 코드 읽기, 어림)과 웹 요약으로 갈라 달라고 한다
- 웹 요약이 준 수와 인용은 근거가 아니다. 웹 요약은 WebFetch처럼 페이지를 받아 작은 모델이 질문에 답하는 도구의 출력이다. 원문(내려받은 파일, 페이지 본문)을 받아 세거나 대 보았으면 그 방법대로 적고, 그러지 않은 것은 주소와 함께 웹 요약이라고 적는다. 따옴표 인용은 원문에서 옮긴다. 라이선스 조건(파서, 임베딩 모델, DB 드라이버의 재배포)은 특히 원문으로 확인한다
- 라이브러리나 도구의 조합을 고르는 측정은 소비 지점까지 간다. 생성물이나 단언으로 받은 출력에서 멈추지 않고, 그것을 쓰는 코드가 타입 검사와 실행을 지나는 데까지 잰다. 판은 설치할 판으로 재고, 측정한 판과 설치할 판이 major로 다르면 다시 잰다

## 전체 계획

전체 계획 `.scratch/plan.md`는 손으로 쓰지 않는다. `uv run python tools/plan_table.py`가 손 파일 `.scratch/plan-head.md`(표 밖의 글: 제목, 머리말, 목표 배치, 첫 슬라이스의 범위와 비목표)와 기능 계획과 티켓에서 만들어 커밋하는 생성 파일이다. 파일 첫 줄의 주석이 그렇게 알린다. 모양과 판정의 원천은 그 도구의 독스트링이고, 이 절은 규칙을 적는다.

- **기능 계획.** 제품 기능마다 `.scratch/<slug>/plan.md`다. 첫 줄 `# <slug>: <한 줄 요약>`(slug는 폴더 이름), 이어서 빈 줄 앞까지 `**슬라이스:** N`, `**Blocked by:** <slug>, …`(없으면 `없음`), 있을 때만 `**설계:** …`과 `**끝:** YYYY-MM-DD`, 빈 줄 뒤에 본문이다. 본문은 범위와 다른 기능이 넘긴 것이고 표에 들지 않는다. 계약의 모양은 ADR 번호로만 가리킨다. 표의 내용 칸은 첫 줄의 한 줄 요약과 기능 계획으로 가는 링크뿐이다. 하네스 기능의 기능 계획은 `**슬라이스:**` 줄이 없고 전체 계획에 들지 않는다. 하네스 기능과 harness 티켓의 상태는 티켓의 `Status:` 줄이다
- **상태는 손으로 바꾸지 않는다.** `끝` 줄이 있으면 done, 없고 그 폴더 `issues/`에 done 티켓이 있으면 in-progress, 아니면 todo다. 명세와 티켓이 생긴 것만으로는 todo다. 티켓의 상태는 줄 머리가 `Status:`이거나 `**Status:**`인 첫 줄의 첫 낱말이다
- **프론티어.** 도구가 계산해 전체 계획 끝에 적는다. done이 아니고, Blocked by가 비었거나 막는 기능이 모두 done인 기능이다. 프론티어는 병렬로 돌린다
- **도는 때.** 기능 계획이나 `.scratch/plan-head.md`를 고치거나 티켓의 상태를 바꾼 세션이 도구를 손으로 돌리고 결과를 같은 커밋에 싣는다. 잊으면 저장소 대조 시험(`tests/test_plan_status.py`)이 빨개진다. 도구가 2로 끝나면 찍은 경로의 기능 계획이나 티켓을 고친다. 필드 줄은 기능 계획 첫 줄 뒤의 첫 문단에서만 읽는다. 키의 철자가 틀려 `**슬라이스:**` 줄이 없어지면 하네스 기능으로 읽혀 오류 없이 표에서 빠지므로, 새 기능 계획은 도구를 돈 뒤 표에 그 행이 생겼는지 본다
- **병합 충돌.** `.scratch/plan.md`의 충돌은 표지를 손으로 풀지 않고 도구를 다시 돌려 푼다. 입력 파일의 충돌은 그 파일에서 풀고 도구를 돈다
- **설계 줄.** 설계 인터뷰를 마친 세션(`grill-with-docs`의 산출물 단계)이 기능 계획에 `**설계:** ADR NNNN`을 적는다. ADR을 내지 않은 설계면 설계 일지의 이름을 적는다. 설계 인터뷰의 계기는 명세도 설계 줄도 없는 기능이고, 설계 줄이 있고 명세가 없으면 명세 차례다
- **끝 줄을 적는 때.** 기능의 마지막 열린 티켓을 닫는 커밋이, 닫은 뒤 그 기능의 done 티켓이 하나 이상이면 같은 커밋에서 기능 계획에 `**끝:** YYYY-MM-DD`(그 커밋의 로컬 날짜)를 적고 도구를 돈다. 끝 줄이 이미 있는 기능의 고침 티켓을 닫을 때는 다시 적지 않는다. 끝 줄을 적은 커밋이 dev에 병합되면 출시 PR(dev→main)을 여는 계기가 된다(`next-session` `merge.md`의 "출시 PR"). 끝 줄이 없는 하네스 기능(`**슬라이스:**` 줄이 없는 기능 계획)과 harness 티켓은 계기가 아니다
- 계약(검색 도구의 형식, 수집 API, 커넥터·변환·파서 인터페이스, 색인 형식, 헌법)을 바꾸는 티켓은 그 기능의 첫 티켓이며 다른 티켓을 막는다

## 스킬이 "이슈 트래커에 발행하라"고 할 때

`.scratch/<feature-slug>/` 아래에 새 파일을 만든다. 디렉터리가 없으면 만든다.

## 스킬이 "해당 티켓을 가져오라"고 할 때

참조된 경로의 파일을 읽는다. 사용자는 보통 경로나 이슈 번호를 직접 넘긴다.
