# rag-engine 헌법 · 검증과 운영

커밋, 병합, 리뷰, 트래커, 가드레일을 만질 때 읽는다.

## 검증
- 손으로 치는 검증 명령(테스트, 린트, 타입체크)은 `CLAUDE.md`의 검증 명령 칸이 원천이다. 티켓의 "검사 N이 초록"은 손으로 치는 것을 말한다.
- 계약 시험은 첫날부터 CI에 둔다. 공식 MCP SDK의 클라이언트로 서버에 HTTP 접속해 도구 목록과 검색 도구의 형식을 본다. core가 검색 도구를 만들기 전에는 빈 서버의 `/health`와, MCP 도구 목록에 쓰기 도구가 없음을 본다(원칙 IV).
- 컨테이너 이미지는 첫날부터 CI에서 짓는다. 릴리스는 main이 움직일 때 CI가 낸다. 번호, 노트, 차례, 실패한 릴리스를 다시 돌리는 절차는 아래 "릴리스 노트 원고"와 "릴리스가 나는 차례와 실패한 릴리스를 다시 돌리는 절차"가 적는다.
- 검색 품질은 search-eval의 게이트 둘이 지킨다. 빠른 게이트는 검색에 영향을 주는 경로가 바뀐 PR과 dev·main 푸시, 수동 실행에서 CI의 `eval-fast` 잡이 평가 세트를 색인해 기준 보고서(`baseline-fast.json`)와 견주고, 질의 목록마다 상위 5 적중률이 2%p, MRR이 0.02를 넘어 떨어지면 실패한다. 경로의 목록은 `tools/eval_gate_paths.py`가 원천이다. 전체 게이트는 base가 main인 PR과 수동 실행에서 `eval-full` 잡이 리랭크 기록을 읽어 리랭크 뒤 줄을 `baseline-full.json`과 같은 폭으로 견준다. 푸시와 base가 dev인 PR에서는 평가하지 않고 성공으로 끝난다. 두 기준 보고서는 사용자의 승인으로만 바꾸고, 게이트가 빨갛다고 에이전트가 스스로 갱신하지 않는다. LLM을 부르는 시험은 두지 않는다(이 서버는 답을 만들지 않는다).
- 대상 사양에서 재야 하는 값(동시 요청의 검색 지연, 첫 대량 적재 시간)은 프로브로 남긴다. 자리와 근거 문장의 규칙은 `docs/agents/issue-tracker.md`의 프로브와 근거 절이다.

## 가드레일
- pre-commit이 커밋마다 린트, 포맷, 검사 러너(타입체크, 타입 우회 검사, 테스트, 지침 검사, 커밋 검사)를 돌고, CI가 같은 검사를 PR마다 돈다. 훅과 검사의 목록과 등록은 `.claude/settings.json`, `.pre-commit-config.yaml`, `.github/workflows/ci.yml`이 원천이다.
- 반드시 실행되어야 하는 것은 문서가 아니라 훅이나 검사로 둔다(`CLAUDE.md` 교정 루프).
- 보호 브랜치는 둘이다. main(설정은 `tools/protection.json`)은 필수 검사 `verify`, 최신 main 기준(strict), 강제 푸시와 삭제 금지를 건다. dev(설정은 `tools/protection-dev.json`)는 같되 strict가 아니다. 두 브랜치 모두 선형 이력을 강제하지 않는다. 출시 PR과 운영에서 개발로 합치기 PR이 merge 커밋이기 때문이다. dev가 strict가 아닌 것은, strict이면 dev에 main에 없는 커밋이 있는 동안 머리가 main인 운영에서 개발로 합치기 PR이 늘 뒤처진 것으로 막히기 때문이다. 값은 ADR 0016이 정했고, 티켓 `04-dev-branch-create`가 2026-11-12에 사용자의 승인을 다시 받고 걸었다(main의 선형 이력 강제를 껐고, dev를 `origin/main`의 머리에서 따서 이 보호를 걸었으며, 기본 브랜치를 dev로 옮겼다).

## 브랜치와 병합
브랜치 모델은 agent-os의 ADR 0043을 따르고, 이 저장소에서 다른 것은 ADR 0016이 적는다. 용어는 `GLOSSARY.md`가 제품의 말만 들기 때문에 이 절이 정의한다(ADR 0016).
- **용어.** 티켓 PR은 티켓 하나를 가리키는 PR로, 기준 브랜치로 가서 커밋 하나로 합쳐진다. 운영 브랜치는 운영에 내보낼 수 있는 머리를 지키는 `main`이고 출시 PR과 핫픽스로만 바뀐다. 개발 브랜치는 티켓 PR이 모이는 `dev`이고 운영 브랜치보다 앞서 있다. 기준 브랜치는 브랜치 하나가 PR로 갈 브랜치다. 주 체크아웃(워크트리가 아닌 원래 폴더)이 따르는 브랜치는 이 클론에 `origin/dev`가 있으면 dev, 없으면 main이다(옛 이름은 루트 브랜치이고 2026-11-18에 바꿨다). 출시 PR은 개발 브랜치의 머리를 운영 브랜치로 올리는 PR로 티켓을 가리키지 않고 커밋을 그대로 올린다. 핫픽스는 운영에서 발견된 버그를 `main`에서 따서 `main`으로 바로 돌려보내는 티켓 PR이다. 운영에서 개발로 합치기는 운영 브랜치에 먼저 오른 변경을 개발 브랜치에 합치는 것으로, 핫픽스나 출시 PR을 병합한 세션이 바로 한다(옛 이름은 되돌려 합치기이고 2026-11-18에 바꿨다).
- **기준 브랜치 규칙.** `hotfix/*`는 `origin/main`이고, 그 밖(`feature/*`, `chore/*`, `docs/*`와 앱이 만든 이름)은 이 클론에 `origin/dev`의 추적 ref가 있으면 `origin/dev`, 없으면 `origin/main`이다. 원격에 dev가 있어도 이 클론이 받은 적이 없으면 없는 것이므로 `git fetch origin`을 먼저 친다. 문서와 스킬의 `<기준 브랜치>`는 이 줄을 가리키고, 구현은 `tools/base_rule.py`다(`tools/check_ticket.py`의 `base_ref`와 `tools/hook_push_behind_main.py`의 `base_branch`가 같은 기준을 낸다). 주 체크아웃이 따르는 브랜치도 같은 규칙으로 dev가 있으면 dev, 없으면 main이다(`tidy-checkouts`). dev는 티켓 `04-dev-branch-create`가 2026-11-12에 `origin/main`의 머리에서 땄다. 그 뒤로 `git fetch origin`으로 dev를 받은 클론에서는 `hotfix/*`가 아닌 브랜치의 기준이 dev다.
- main과 dev에 바로 커밋하지 않는다. 두 브랜치는 보호된다(가드레일 절).
- PR마다 티켓 하나다. 티켓, 브랜치 이름, 면제 PR의 규약은 `docs/agents/issue-tracker.md`가 원천이고, 커밋 검사(`tools/check_ticket.py`)가 판정한다. 출시 PR(머리가 dev)과 운영에서 개발로 합치기 PR(머리가 main)은 티켓을 가리키지 않고 커밋 검사가 그대로 지난다.
- 티켓 PR과 핫픽스는 스쿼시 병합이고 출시 PR과 운영에서 개발로 합치기 PR은 merge 커밋이다. 병합 방법과 운영에서 개발로 합치는 순서는 `next-session` `merge.md`("병합 방법", "운영에서 개발로 합치기")가 원천이다. `/git-pr-merge`는 squash 병합과 main 갱신을 가정하므로 base가 main인 squash 병합(핫픽스 PR)에만 쓴다. base가 dev인 PR과 merge 커밋으로 병합하는 출시 PR은 사용자 수준 스킬이 dev와 merge 커밋을 가르치지 못해 `merge.md`의 "워크트리에서 병합할 때" 1~2로 하고(머리가 dev라 3은 건너뛴다), 병합 뒤 처리는 그 파일의 "출시 PR"을 따른다. PR은 `/git-pr`이 `.github/PULL_REQUEST_TEMPLATE.md`를 채워 연다. 그 스킬과 `gh pr create`는 base를 따로 주지 않으면 원격의 기본 브랜치로 잡으므로, 기본 브랜치가 dev가 된 뒤의 핫픽스 PR은 `gh pr create --base main`으로 연다.
- **출시 PR을 여는 때.** 기능 계획의 `**끝:**` 줄을 적은 커밋이 dev에 병합되면 그 기능의 마지막 티켓을 병합한 세션이 출시 PR(dev→main)을 연다. 그 세션이 못 했으면 다음 병합 뒤의 세션이 `next-session`의 결정표로 같은 상태를 읽고 연다. 하네스 기능(끝 줄이 없다)은 계기가 아니고 다음 기능의 출시 PR에 실려 오른다. 열기 전에 main CI가 초록이고 dev가 main의 끝 커밋을 품었는지 본다. 또 dev의 머리에서 전체 게이트가 초록인지 본다. 합친 뒤의 후보를 바꾼 변경이 dev에 있으면 출시 PR 앞에 리랭크 기록과 `baseline-full.json`을 맞추는 PR을 하나 둔다. 계기, 전제 확인, PR 서식, 병합 뒤 처리의 순서는 `next-session` `merge.md`의 "출시 PR"이 원천이다.
- **main의 strict.** 그대로 둔다. strict이면 출시 PR은 dev가 main의 머리를 품어야 병합되는데 앞 출시 PR이 main에 남긴 merge 커밋은 dev에 없으므로, 출시 PR을 병합한 세션이 바로 main을 dev에 합친다(`merge.md`의 "운영에서 개발로 합치기". 둘째 출시 PR부터 `BEHIND`가 날 것이라는 것은 커밋 관계로 따진 어림이고 출시 PR로 재 보지 않았다). 출시 PR만 관리자 우회로 병합하는 길과 strict를 끄는 길은 사용자가 고르지 않았다. 이 값은 티켓 `05-dev-release-pr-step`에서 사용자가 2026-11-13에 정했다(ADR 0016 이력). 이 줄이나 보호 설정을 바꾸면 위 가드레일 절과 `merge.md`의 운영에서 개발로 합치기 필요 판정 근거를 같이 고친다.
- 나란히 도는 두 티켓 PR이 각자 초록으로 병합된 뒤 dev가 빨개질 수 있다. dev에는 strict가 없기 때문이다. 늦게 병합하는 세션은 병합 직전에 `git fetch origin` 뒤 기준 브랜치를 합치고 저장소 상태 시험을 직접 돈다(`tests/test_plan_status.py` 머리 독스트링).

## 릴리스 노트 원고
이 절과 다음 절이 하네스의 말 셋을 정의한다(ADR 0020 "용어"). **릴리스한다**는 main이 움직일 때 CI가 새 릴리스를 만들어 내는 일이다. 번호를 계산하고, 이미지를 짓고 시험하고 점검해 Docker Hub에 올리고, 버전 태그와 GitHub 릴리스를 만든다. **제품 변경**은 운영자가 받는 것을 바꾸는 변경이다. 어느 경로를 고친 변경이 제품 변경인지는 `tools/release.py`의 `PRODUCT_PATHS`와 그 독스트링이 정하고(경로를 고른 까닭은 명세 `.scratch/release-image/spec.md`의 "제품 변경의 경로"가 적는다), 지난 릴리스 뒤로 제품 변경이 없으면 릴리스하지 않는다. **릴리스 노트 원고**는 릴리스 노트에 그대로 실리도록 세션이 미리 써 두는 글이다.

릴리스 노트는 커밋 제목의 묶음 위에 원고 셋을 싣고, 릴리스 워크플로는 그 파일을 글자 그대로 옮긴다(모델을 부르지 않는다. agent-os ADR 0056 결정 "판마다 나오는 것"을 따른다). 원고는 `docs/release-notes/` 아래에 있고, 폴더는 첫 원고가 들 때 생긴다. 노트의 절 차례는 경고, 소개, 기능 소개, 업그레이드할 때 할 일, 계약의 판, 새 기능, 고친 것, 그 밖의 변경이다. 계약의 판 절은 원고 없이 CI가 지은 서버 이미지의 `rag-engine --version`에서 옮긴다. 원고의 모양과 막는 판정의 원천은 `tools/check_notes.py`의 독스트링이다.
- **기능 단락** `features/<기능 slug>.md`. 제품 변경을 담은 기능의 마지막 티켓을 닫는 커밋이 `**끝:**` 줄과 함께 싣는다(`docs/agents/issue-tracker.md`의 "끝 줄을 적는 때"). 운영자에게 무엇이 달라지는지를, 운영자가 만지는 것(설정 칸, 명령, API 경로)의 이름으로 쓴 한 단락이다. 줄바꿈을 뺀 400자 이하이고 빈 줄이 없다. 파일 경로, ADR 번호, 티켓 이름, 업그레이드할 때 할 일은 싣지 않는다.
- **업그레이드 원고** `upgrade/<이름>.md`. 제목 접두에 느낌표를 붙인 PR이 그 PR에 새로 싣는다. 운영자가 업그레이드할 때 무엇을 무엇으로 바꾸는지 구체적으로 쓴다. 마이그레이션이 든 PR의 원고는 업그레이드 전에 백업하라고 적는다. 백업과 복원의 절차는 backup-upgrade가 정하고, 그 전에는 PostgreSQL 볼륨을 백업하라는 한 줄로 쓴다.
- **소개 글** `intro/<X.Y.Z>.md`. 그 정식 릴리스와 출시 후보들의 노트 맨 위에 선다. `intro/0.1.0.md`는 release-image의 마지막 티켓이 기능 단락과 함께 쓰고(core와 search-eval을 설명한다), 정식 릴리스를 내기 전에 release-0-1이 고칠 수 있다.

**느낌표의 기준.** 운영자가 업그레이드할 때 손댈 것(설정, 환경 변수, 데이터, 플러그인 코드)이 있는 변경의 PR 제목 접두에 느낌표를 붙인다(`feat!:` 꼴. ADR 0020 "올릴 때 운영자가 손댈 것의 기준"). 설정에는 `.env`와 배포 파일 묶음에서 운영자가 고친 파일이 든다. 손대지 않으면 업그레이드한 뒤 동작이 멈추는 변경도 든다. 기본값이 안전한 새 선택 설정은 들지 않는다. 이 저장소는 아래 셋을 언제나 그 기준에 드는 변경으로 못박는다.
- 데이터베이스 마이그레이션이 든 변경. 마이그레이션 파일은 `src/rag_engine/adapters/postgres/migrations/versions/` 아래의 `.py`다. 이미 릴리스된 마이그레이션을 고치는 것도 같다.
- 재색인이 필요해지는 변경. 색인 판의 요소가 바뀌는 것이다(ADR 0008).
- 계약 버전에서 앞자리를 올리는 변경(원칙 VII).

**보는 자리.** PR 서식(`.github/PULL_REQUEST_TEMPLATE.md`)의 "업그레이드할 때 운영자가 손댈 것" 칸이 PR을 쓰는 세션에게 위 셋을 따로 묻는다. 노트 검사의 판정 (가)가 느낌표와 `upgrade/` 원고의 짝을 보고, 마이그레이션 파일을 더하거나 고치거나 지우거나 옮긴 PR의 제목에 느낌표가 없으면 막는다. 이 검사는 티켓 PR과 핫픽스 PR에 걸고 출시 PR과 운영에서 개발로 합치기 PR은 면제한다. 그 둘은 제목이 번호의 원천이 아니고 변경 목록에 그동안의 마이그레이션이 모두 들기 때문이다. 리뷰 봇이 변경과 제목의 접두를 맞대는 줄은 release-image의 07이 `claude-code-review.yml`에 더한다. 노트 검사는 pre-commit의 검사 러너와 `ci.yml`의 `ticket` 잡에서 돈다. 제목이 틀려 `ticket` 잡이 빨갛던 PR은 제목을 고쳐도 그 잡이 다시 돌지 않아(`ci.yml`의 `pull_request`가 `edited`를 받지 않는다) 필수 검사 `verify`가 빨강으로 남는다. 제목을 고치면 도는 PR 제목 워크플로의 초록은 그 빨강을 지우지 않으므로, 제목을 고친 뒤 푸시를 한 번 더 해 `ci.yml`이 새 제목으로 돌게 한다(agent-os 운영 문서가 적은 것을 옮겼고, 실행만 다시 돌리면 처음 이벤트의 제목을 쓰는지는 확인하지 않았다). 병합하는 쪽은 squash 병합의 제목을 직접 주지 않는다. 제목을 주면 저장소 설정과 상관없이 그 제목이 main에 남아 느낌표가 빠질 수 있기 때문이다(`next-session` `merge.md`의 "병합 방법").

## 릴리스가 나는 차례와 실패한 릴리스를 다시 돌리는 절차
릴리스는 main이 움직일 때 CI가 스스로 낸다. 워크플로는 `.github/workflows/release.yml`이고 결정의 원천은 ADR 0020(agent-os ADR 0056을 따른다), 풀이는 `.scratch/release-image/spec.md`의 "릴리스 워크플로"다. 병합한 세션이 실행을 끝까지 보고 결과를 적는 절차는 `next-session` `merge.md`의 "릴리스를 기다린다"다. 워크플로는 release-image의 마지막 티켓이 들이므로 아래 잡과 단계의 이름은 agent-os의 `release.yml`을 옮긴 것이고, 그 티켓이 워크플로를 옮긴 뒤 이름이 같은지 본다.

**차례.** main의 푸시마다 한 번에 하나만 돌고(동시 실행 묶음 `release`) 기다리는 실행은 가장 나중 것만 남는다. 남은 실행이 지난 릴리스의 버전 태그 뒤의 제품 변경을 다시 보므로 밀려 취소된 실행의 변경도 그 릴리스에 실린다. 잡은 둘이고 둘 다 환경 `release`(배포 브랜치는 main 하나)를 쓴다. 환경에 비밀 값 `DOCKERHUB_TOKEN`(Docker Hub 접근 토큰)과 `RELEASE_GH_TOKEN`(저장소 하나에 Contents와 Workflows의 읽기·쓰기를 준 세분 토큰), 변수 `DOCKERHUB_NAMESPACE`(Docker Hub 계정 이름)가 든다. 기본 토큰은 `contents: read`뿐이다.
1. `build`: 체크아웃 → 번호와 노트 계산 → 지난 릴리스의 GitHub 릴리스 확인(단계 이름은 `지난 판의 공개 릴리스 확인`. 번호 태그가 하나도 없는 첫 릴리스에는 지난 릴리스가 없어 이 단계를 건너뛴다. agent-os `release.yml`의 조건을 읽었고 이 저장소에서는 돌려 보지 않았다) → (제품 변경이 없으면 여기서 성공으로 끝) → 빌더 준비 → 이미지 짓기(시험용) → 준비 단계(파이썬 의존성과 임베딩 모델 폴더를 맞추는 단계. 이름은 08이 정한다) → 단독 compose 시험 → 점검 → 노트와 배포 파일 묶음 → Docker Hub 로그인 → 이미지 올리기(커밋 태그 `sha-<커밋 해시 40자>`만) → 시험한 이미지와 올린 이미지 대조 → 아티팩트 `release-files` 올리기. 아티팩트는 워크플로가 잡 사이에 넘기는 파일 묶음이다. 출력은 릴리스 번호와 이미지 둘의 digest다. digest는 이미지 내용에서 나오는 고유한 식별 값이라, 같은 이미지는 어디서나 같다. 같은 커밋을 다시 지으면 달라질 수 있다(아래 표의 `아티팩트 받기`·`아티팩트 대조` 줄이 그 일을 적는다). 번호 태그는 릴리스 번호(`<이름공간>/<저장소>:<번호>`의 `<번호>`)를 이름으로 삼아 이미지에 붙이는 이름표이고, 커밋 태그(`sha-<해시>`)와 달리 한 번 붙으면 다른 digest로 옮기지 않는다. 아래 표와 "남긴 초안으로 끝낸다"에 나오는 "지키는 차례"는 이 약속을 지키려고 새 digest를 거부하는 판정(`tools/release_ci.py`의 `judge`)이다.
2. `publish`: 아티팩트 받기 → 아티팩트 대조 → Docker Hub 로그인 → 사전 확인 → 이미 공개된 판(사전 확인이 "이 번호의 공개 릴리스가 이미 이 커밋을 가리킨다"고 가르면 이 단계가 그 말을 찍고 성공으로 끝나며 뒤 단계는 모두 건너뛴다. agent-os의 `release.yml`을 읽은 것이고 돌려 보지 않았다) → 앞 실행의 초안 지우기 → 초안 만들기 → 초안 직후 태그 대조 → 자산 올리기 → 번호 태그 붙이기 → 공개. 번호 태그 붙이기 앞에서 실패하면 마지막 단계 `정리`가 초안과 그 번호의 git 태그를 지운다. 번호 태그 붙이기부터 뒤에서 실패하면 초안을 남긴다. 사전 확인이 앞 실행의 이 커밋 초안을 지우고 새로 만든 실행은 번호 태그 앞에서 실패해도 새 초안을 남긴다(단 `초안 직후 태그 대조`로 실패한 실행은 지운다). 취소와 제한 시간은 `정리`가 돌지 못하므로 남은 초안은 다음 실행의 사전 확인이 맡는다.

**원인의 자리가 길을 정한다.** 원인이 저장소 밖이면(러너나 레지스트리의 일시 장애, 만료·삭제된 토큰을 갱신한 뒤) 실패한 잡만 다시 돌린다.
```bash
gh run rerun <실행 번호> --failed
```
`publish`만 실패했으면 `build`가 낸 digest와 아티팩트를 그대로 쓰고, 번호 태그를 지키는 차례가 같은 digest를 보고 이어 간다. 실행 전체를 다시 돌리면 같은 커밋을 다시 지어 digest가 달라지고(agent-os가 쟀다. 그 저장소의 프로브 `release_mechanics` README 8번이고, 이 저장소에서 다시 재지 않았다), 번호 태그가 이미 붙었다면 지키는 차례가 거부한다. 다시 돌리기는 처음 실행 뒤 30일 안에만 된다. 원인이 저장소 안이면 핫픽스다. 번호 태그를 붙이기 전의 실패는 레지스트리에 많아야 커밋 태그만 남아 핫픽스의 실행이 같은 번호로 릴리스를 낸다. 다만 취소나 제한 시간으로 `정리`가 돌지 못했다면 그 번호의 초안이 남아 있을 수 있으므로, 핫픽스 전에 그 번호의 초안과 번호 태그를 먼저 본다(초안만 있으면 사용자에게 청해 지운다. 핫픽스의 `build`는 이미지를 다 짓고 올린 뒤 `publish`의 사전 확인에서야 그 초안에 막힌다). 번호 태그를 붙인 뒤의 실패는 핫픽스로 바로 가지 않고 아래 "남긴 초안으로 끝낸다"를 먼저 한다.

**실패한 단계별 길.** 단계 이름은 `gh run view <실행 번호> --json jobs`의 `steps[].name`이다.

| 실패한 단계 | 남은 것 | 다음 작업 |
|---|---|---|
| `build`의 `지난 판의 공개 릴리스 확인` | 첫 릴리스에서는 이 단계가 건너뛰어져 이 줄에 오지 않는다. 오류 문구가 "찾지 못했다"(404)면 앞 실행이 정리 없이 끝나 지난 릴리스의 태그나 초안이 남았다. "404 가 아닌 오류"면 GitHub의 일시 장애나 속도 제한이고 남은 것이 없다. 이 릴리스의 번호 태그는 없다 | "찾지 못했다"면 지우기 전에 지난 릴리스의 이미지 번호 태그가 붙었는지 레지스트리에서 먼저 본다. 하나라도 붙었으면 실행 전체를 다시 돌리지 않고(다시 지은 digest가 번호 태그와 달라 지키는 차례가 거부한다) 아래 "남긴 초안으로 끝낸다"를 따른다. 하나도 없으면 사용자에게 청해 그 초안과 태그를 지운 뒤 실패한 실행 전체를 다시 돌린다(`gh run rerun <실행 번호>`). "404 가 아닌 오류"면 `--failed` |
| `build`의 `번호와 노트 계산` | 없음 | 구성 오류(`deploy/release.toml`, 태그 상태)다. 원인은 저장소 안이니 고쳐서 핫픽스나 다음 병합으로 올린다 |
| `build`의 `체크아웃`, `Docker Hub 로그인`, `publish`의 `체크아웃`, `Docker Hub 로그인` | `build`면 레지스트리에 아무것도 없다. `publish`면 커밋 태그만 있다 | 러너나 서비스의 일시 장애면 `--failed`. 로그인 실패는 접근 토큰이 만료·삭제됐거나 권한이 바뀐 것이므로 사용자에게 `DOCKERHUB_TOKEN`을 새로 넣어 달라고 청한 뒤 `--failed`다 |
| `build`의 `빌더 준비`, `이미지 짓기(시험용)`, 준비 단계(파이썬 의존성과 임베딩 모델 폴더를 맞추는 단계), `단독 compose 시험`, `점검`, `노트와 배포 파일 묶음`, `이미지 올리기`, `시험한 이미지와 올린 이미지 대조`, `아티팩트 올리기` | 레지스트리에 많아야 커밋 태그 | 원인이 밖이면 `--failed`, 안이면 핫픽스. `점검`은 Grype의 종료 코드가 0과 2 밖일 때, `노트와 배포 파일 묶음`은 점검이 고칠 수 있는 Critical을 찾았는데 노트에 경고가 없을 때(저장소 안), `시험한 이미지와 올린 이미지 대조`는 두 이미지의 설정 해시가 다를 때, 또는 올린 색인의 digest를 커밋 태그에서 레지스트리에 물어 읽지 못할 때(조회 실패나 digest 꼴이 아닌 값) 실패한다. 뒤의 것은 레지스트리의 일시 장애일 수 있어 로그의 `::error::` 문구를 보고 가른다 |
| `publish`의 `아티팩트 받기`, `아티팩트 대조` | 초안도 번호 태그도 없고 커밋 태그만 있다 | 실패한 실행 전체를 다시 돌린다. 같은 커밋을 다시 지어 커밋 태그의 digest가 바뀌지만 번호 태그가 없어 막지 않는다(어림. agent-os 명세가 돌려 보지 않았다고 적은 길이다). 둘째 잡만 다시 돌린 회차의 실패면 앞 회차가 초안과 번호 태그를 남겼을 수 있으니, 사람이 GitHub 화면과 레지스트리에서 그 번호의 초안과 번호 태그를 본다. 번호 태그가 하나라도 붙었으면 "남긴 초안으로 끝낸다", 없으면 실행 전체를 다시 돌린다(같은 커밋의 남은 초안은 사전 확인이 지우고 새로 만든다) |
| `publish`의 `사전 확인` | 앞 릴리스가 끝나지 않았다(GitHub 릴리스가 다른 커밋을 가리킴, 다른 커밋의 초안, GitHub 릴리스 없는 git 태그) | main이 번호 태그 뒤에 실패한 릴리스가 끝나기 전에 다시 움직인 경우다. 앞 릴리스를 "남긴 초안으로 끝낸다"로 끝낸 뒤 새 실행을 처음부터 다시 돌린다. GitHub 릴리스 없이 git 태그만 있으면 사용자에게 넘긴다 |
| `publish`의 `초안 직후 태그 대조` | 커밋 태그뿐(`정리`가 초안과 태그를 지운다) | 로그에 "git 태그가 원격에 있다"가 있으면 초안이 git 태그를 만든다는 뜻이다. 그 문구 없이 `gh api` 오류로 끝났으면 조회의 일시 장애이므로 `--failed`로 다시 돌린다. 문구가 있으면 다시 돌리지 않고 agent-os ADR 0056 결정 "판 내기의 차례와 실패"로 돌아가 차례를 다시 정한 뒤, 고친 워크플로를 핫픽스로 올린다 |
| `publish`의 `앞 실행의 초안 지우기`, `초안 만들기`, `자산 올리기` | 초안은 지워지고 커밋 태그뿐(사전 확인이 앞 초안을 지우고 새로 만든 실행은 새 초안이 남는다. `앞 실행의 초안 지우기`가 실패했으면 새 초안은 아직 없다) | 원인이 밖이면 `--failed`(남은 같은 커밋의 초안은 사전 확인이 지우고 새로 만든다), 안이면 핫픽스. 핫픽스는 다른 커밋이라 그 번호의 초안이 남아 있으면 사전 확인이 실패하므로(`tools/release_ci.py`의 `precheck`가 다른 커밋의 초안이면 `ReleaseError`를 낸다. agent-os의 코드를 읽은 것이다), 핫픽스 전에 GitHub 화면에서 그 번호의 초안을 보고 남았으면 사용자에게 청해 지운다 |
| `publish`의 `번호 태그 붙이기` | 초안이 남고, 번호 태그가 일부 붙었을 수 있다 | 조회 실패나 일시 장애(원인이 밖)면 `--failed`. 다른 digest를 가리켜 거부했으면 이 릴리스는 남긴 초안으로 끝낼 수 없다. 사용자에게 넘기고 ADR 0020과 agent-os ADR 0056으로 돌아간다 |
| `publish`의 `공개` | 초안과 번호 태그 둘이 있다 | 원인이 밖이면 `--failed`. 그래도 안 되면 "남긴 초안으로 끝낸다" |
| `publish`의 `정리` | 지우려던 초안이나 그 번호의 git 태그가 남았을 수 있다 | 사용자에게 청해 GitHub 화면에서 그 번호의 초안과 git 태그를 지운 뒤 앞 실패의 줄을 따른다 |
| 어느 잡이든 제한 시간 초과(`timed_out`) | 멈춘 단계의 `conclusion`이 `cancelled`나 `failure`로 읽힌다(어림. 돌려 보지 않았다). `정리`가 돌지 못해 `publish`에서는 초안이 남을 수 있다 | 멈춘 단계의 줄을 따른다. 원인이 잰 시간에 정한 `timeout-minutes`가 모자란 것이면 저장소 안이므로 핫픽스로 고친다(값의 근거는 `release.yml` 머리 주석) |

**남긴 초안으로 끝낸다.** 번호 태그를 붙인 뒤의 실패는 앞 실행을 다시 돌려도 처음 실행과 같은 커밋으로 돌아 고친 워크플로로 끝낼 수 없다. 그래서 그 릴리스는 남긴 초안으로 끝낸다. 실행 전체를 다시 돌리는 길은 막혀 있다. 번호 태그가 붙은 뒤라 새 digest를 지키는 차례가 거부한다.
1. 번호 태그를 이미지 둘 모두에 지키는 차례와 같은 명령으로 확인한다. `docker buildx imagetools create`는 Docker Hub에 쓰므로 사용자가 `docker login`을 한 상태에서 친다(접근 토큰은 읽기·쓰기 권한이고 세션에 넘기지 않는다). 이미지(`<이미지>`는 `server`, `worker`. 저장소 이름 `<저장소>`는 `uv run python tools/release_ci.py repository <이미지>`가 `deploy/images/docker-bake.hcl`에서 읽어 주며 순서대로 `rag-engine-server`, `rag-engine-worker`다) 각각에 `docker buildx imagetools inspect <이름공간>/<저장소>:<번호> 2>&1`을 쳐(태그가 없을 때의 오류는 stderr로 나오므로 stdout과 stderr를 함께 모으고, 그 명령의 종료 코드를 따로 적어 둔다) 모은 출력을 `uv run python tools/release_ci.py judge --exit-code <종료 코드> --digest <아티팩트의 digest>`에 넣고, `attach`면 `docker buildx imagetools create -t <이름공간>/<저장소>:<번호> <이름공간>/<저장소>@<digest>`를 친 뒤 같은 확인을 다시 한다. `keep`이면 그대로 두고, `reject`와 `hold`면 멈추고 사용자에게 넘긴다.
2. 초안에 배포 파일 묶음 `rag-engine-<번호>.tar.gz`와 이미지마다의 `grype-<이미지>.json`, `sbom-<이미지>.spdx.json`이 모두 있고 본문에 노트의 글이 있는지 본다. 빠진 것은 그 실행의 아티팩트 `release-files`에서 받는다. 올리기 전에 `uv run python tools/release_ci.py verify-files --dir <받은 폴더> --number <번호> --sha <커밋 해시> --digest server=<digest> --digest worker=<digest>`로 둘째 잡과 같은 대조를 거친다. 대조에 실패하면 올리지 않고 공개하지 않은 채 멈추고 agent-os ADR 0056 결정 "판 내기의 차례와 실패"로 돌아가 다시 정한다.
3. 사람이 GitHub 화면에서 초안을 공개한다(사용자에게 청한다). 공개가 git 태그를 만든다. 원인이 저장소 안이면 그 뒤에 핫픽스를 올리고, 그 실행은 다음 번호를 계산한다.

**다시 돌리지 않는 것.** 동시 실행 묶음이 기다리던 실행을 더 나중 실행으로 바꾸며 취소한 것은 다시 돌리지 않는다. 남은 실행이 그 변경까지 싣는다.

**이 저장소에서 agent-os와 다른 것.** 이미지가 둘(`server`, `worker`)이다. 시험 단계는 agent-os의 브라우저 시험 대신 단독 compose 시험이다. 위 표의 단계 이름 가운데 `판`이 든 것은 agent-os의 이름을 그대로 옮긴 것이다.

## 리뷰 파이프라인
- 커밋 전: `/code-review`로 셀프 리뷰하고 Critical과 Major를 고친다. 판단 기준은 `CODING_STANDARDS.md`다.
- PR 직전: CodeRabbit CLI로 한 번 더 본다(`.claude/agents/coderabbit-review.md`). CLI가 못 돌면 `.claude/agents/bug-perf-review.md`가 같은 축을 본다.
- PR: 공개 저장소이므로 CodeRabbit PR 리뷰와 Claude Code Review 워크플로가 함께 돈다. base 브랜치에 따른 차이는 아래 `/security-review`, 리뷰 봇, CodeRabbit 세 줄이 적는다.
- 내장 `/security-review`의 범위는 `origin/HEAD`부터다. 그 명령의 프롬프트가 커밋 목록과 diff를 `origin/HEAD...`로 채운다는 것은 agent-os가 2026-10에 `claude` 실행 파일에서 읽은 내용을 옮긴 것이고, 이 저장소에서 재 보지 않았다. `origin/HEAD`는 원격의 기본 브랜치를 가리키는 클론마다의 ref라, 기본 브랜치를 dev로 옮겼으므로(티켓 `04-dev-branch-create`, 2026-11-12) 각 클론에서 `git remote set-head origin dev`를 쳐야 바뀐다. 기준 브랜치가 dev인 브랜치에서는 그 범위가 맞다. 기준 브랜치가 main인 핫픽스 브랜치에서는 커밋 목록에 main에 없는 dev의 커밋이 들어갈 것으로 보이므로(diff는 merge-base부터라 들지 않을 것이다. 프롬프트를 읽고 내린 추정이고 핫픽스로는 돌려 보지 않았다) 리뷰에 넘길 범위를 `git merge-base origin/main HEAD` 이후로 손으로 좁힌다.
- 리뷰 봇과 기준 브랜치(티켓 `02-dev-review-bot-off`와 `03-dev-base-skills-docs`가 적었다). Claude Code Review 워크플로는 머리가 dev이고 base가 main인 출시 PR을 건너뛴다. 그 PR의 내용은 모두 티켓 PR마다 리뷰를 받았기 때문이다. 운영에서 개발로 합치기 PR(머리 main, base dev)은 건너뛰지 않고 돈다. 충돌을 푼 줄은 그 PR에서 처음 생기는 코드라 리뷰가 필요하기 때문이다. 기본 브랜치가 dev인 동안 dev의 `claude-code-review.yml`이 아직 출시되지 않았으면, base가 main인 핫픽스 PR의 Claude Code Review가 액션의 워크플로 검증으로 건너뛰어져 코멘트 0개 가드가 빨개질 수 있다. 이것은 알려진 빨강이다. 필수 검사가 아니라 병합을 막지 않고, 그 PR의 리뷰는 PR 직전 리뷰와 셀프 리뷰가 대신한다. 이 갈래는 액션 소스의 오류 코드와 안내 문구에서 읽은 추론이고 서버 쪽 비교는 보지 못했으며, 첫 핫픽스 PR에서 처음 본다.
- CodeRabbit과 기준 브랜치. 자동 리뷰는 기본적으로 기본 브랜치를 base로 둔 PR만 본다. `reviews.auto_review.base_branches`가 다른 base를 더하고, 기본 브랜치는 늘 든다. 수동 호출은 자동 리뷰 설정과 상관없이 언제나 된다고 문서가 적는다(공식 문서 `docs.coderabbit.ai/configuration/auto-review.md`를 2026-11-12에 `curl`로 내려받아 읽었다). 이 저장소는 별이 10개 미만(2026-11-12에 `gh repo view`가 0개)이라 자동 리뷰가 어느 PR에도 돌지 않고 `@coderabbitai review`로 불러야 돈다(아래 실측). 그래서 base가 기본 브랜치가 아닌 PR(기본 브랜치가 dev가 된 뒤의 핫픽스 PR과 출시 PR)에서도 부르면 돈다고 본다. 이 결론은 문서가 base를 따로 가르지 않아 읽어 끌어낸 어림이고 그런 PR에서 불러 재 보지 않았다. 첫 핫픽스 PR에서 볼 일이다. 별이 10개를 넘겨 자동 리뷰가 열리면 `.coderabbit.yaml`의 `auto_review.base_branches`에 `main`이 필요한지 그때 다시 정한다. 기본 브랜치 dev는 늘 들어 있으므로 티켓 PR은 그대로 자동 리뷰를 받는다.
- 초록 착시: 봇이 코멘트 없이 초록이면 리뷰가 돈 것으로 보지 않고 실행 로그를 읽는다.
- 실측(PR #1~#3, 2026-11-09~10). 첫 PR은 #1이다. CodeRabbit 좌석은 없다(CLI가 `Seat: not assigned`를 찍고도 `review_completed`로 끝났다). 별 10개 미만의 공개 저장소라 PR을 열면 CodeRabbit이 요약 코멘트만 바로 달고 리뷰는 자동으로 돌지 않으며(`This repository does not receive automatic reviews because it has fewer than 10 stars`), `@coderabbitai review` 코멘트로 불러야 돈다. 포함 한도는 시간당 리뷰 1회이고(`1 included review per hour`) 같은 시간 안의 둘째 호출은 `Review rate limited`다. 불러서 리뷰가 달리기까지 12~15분 걸렸다(#2, #3). Claude Code Review 워크플로는 푸시마다 코멘트 하나를 단다(#1, #2 각 둘).

## 설치처 정보
- 설치처의 정보(주소, 계정, 연결 정보, 설치처별 변환 플러그인)는 이 저장소에 넣지 않고 설치처의 비공개 저장소에 둔다(ADR 0003). 이 저장소의 표본 문서와 평가 세트는 공개 문서 묶음으로만 만든다.
- 비밀 값은 `.env`나 설치 환경의 비밀 저장소에만 둔다. `.env`에는 개발용 값만 두고 커밋하지 않는다.
